Title

AndroidReferenceMatchers.BLOCKING_QUEUE has false positives

Description
Found an example of false positive on Stack Overflow: [URL]

```
┬
├─ android.os.MessageQueue
│    Leaking: NO (MessageQueue#mQuitting is false)
│    GC Root: Input or output parameters in native code
│    ↓ MessageQueue.mMessages
... [Log Snipped] ...

pattern=instance field android.os.Message#next
```

Here's an example of true positive: [URL]

```
┬
├─ android.os.HandlerThread
│    Leaking: UNKNOWN
│    Thread name: 'queued-work-looper'
│    GC Root: Java local variable
... [Log Snipped] ...

pattern=instance field android.os.Message#obj
```

BLOCKING_QUEUE is defined as:

```
BLOCKING_QUEUE {
    override fun add(
      references: MutableList 
    ) {
      val description = "..."
... [Log Snipped] ...
    }
  },
```
Discussion
- This leak manifests itself when a Message is held by a local variable on a handler thread, but is out of the pool and also out of any queue (it was taken out to set up a dialog listener message and then never used). As such, `Message.next` should be null when this happens so we can remove `next`.

`target` is never set with AlertDialog builder, unless you call the deprecated APIs that pass in a Messages created manually. I'm going to assume that's not worth tracking. We probably were a bit over zealous.

Ideally we'd have pattern matching for java local variables on HandlerThread instances but unfortunately the java local pattern matching can only be based on thread names for now.
- I tried going back in history and that's we had it in the initial import: [URL]

Then I went back and found the old repo prior to GitHub initial import with history cleanup,  and found that the 3 were added all at once with the first set of excluded refs.
