Title

Skyframe cycle in RegisteredExecutionPlatformsFunction

Description
GRPC has reported a hard Bazel crash due to a cycle arising from RegisteredExecutionPlatformsFunction.

Command and error:
```
roth@segfault:~/grpc> bazel test test/cpp/end2end/client_lb_end2end_test --incompatible_remove_native_git_repository=false --incompatible_remove_native_http_archive=false
Starting local Bazel server and connecting to it...
INFO: Invocation ID: 0058df2b-dca2-4fd7-81e1-829d1eba8332
Internal error thrown during build. Printing stack trace: java.lang.IllegalStateException: topLevelKey: //test/cpp/end2end:client_lb_end2end_test BuildConfigurationValue.Key[ ] false
alreadyReported: false
... [Log Snipped] ...
        at java.base/java.util.concurrent.ThreadPoolExecutor$Worker.run(Unknown Source)
        at java.base/java.lang.Thread.run(Unknown Source)
```
Discussion
- I was able to work around this by changeing grpc's WORKSPACE file to not use `:all` target patterns for `register_execution_platforms` and `register_toolchains`:
```
register_execution_platforms(
    "//third_party/toolchains:rbe_ubuntu1604",
    "//third_party/toolchains:rbe_ubuntu1604_large",
)

register_toolchains(
    "//third_party/toolchains:cc-toolchain-clang-x86_64-default",
)
```

However, we still need to fix this and make sure it cannot happen again.
- Email comment from @haxorz: is such a skyframe cycle possible? if so, SkyframeExecutor#createCyclesReporter needs to be updated?
- ... [Middle Discussions Snipped for Brevity] ...
- Okay, that commit fixes the problem by causing the `toolchain` rule to not require toolchain resolution. While this is the correct result, it's not a good general solution, because based on this, any use of `register_execution_platforms` with a wildcard target that expands to a target which _does_ require toolchain resolution will fail with this cycle error.

The target pattern expansion for `register_execution_platforms` needs to be fixed. Either:
1. Detect which targets require toolchains, and ignore them, or
2. Only allow target patterns to match targets which explicitly use the `platform` rule.

The second is annoying (it will prevent any future attempts to allow custom platform rules), but may be the best practical solution.
