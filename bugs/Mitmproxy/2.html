Title

mitmdump -S... raises `AttributeError: 'NoneType' object has no attribute '_assemble'`

Description
### Summary

`mitmdump -S` ... raises `AttributeError: 'NoneType' object has no attribute '_assemble'`
### Versions

OS: Debian testing (up to date as of 2014-02-07)

mitmproxy: 0.10.0
### How to Reproduce
1. Issue:
   
   ```
   $ mitmdump -e -a -F [URL] -p 3333 -w test
   # Switch terminal...
   $ curl -k -x "[URL] '[URL]
   $ curl -k -x "[URL] '[URL]
   ```
   
   `mitmdump`'s output will look like this:
   
   ```
 :54820: connect
     GET [URL]
     :54820: disconnect
     -> handled 1 requests
... [Log Snipped] ...
    :54824: disconnect
     -> handled 1 requests
```
2. Kill mitmdump.
3. Issue:
   
   ```
   $ mitmdump -e -a -F [URL] -p 3333 -S test
   # Switch terminal...
   $ curl -k -x "[URL] '[URL]
   $ curl -k -x "[URL] '[URL]
   ```
   
   `mitmdump`'s output will look like this:
   
   ```
 :54832: connect
     GET [URL]
     :54832: disconnect
     -> handled 1 requests
... [Log Snipped] ...
     GET [URL]
    << [replay] 200 OK 15.66kB
```
   
   `curl`'s output:
   
   ```
   curl: (52) Empty reply from server
   ```
### Actual Results

`mitmdump` crashes while serving the second request.
### Expected Results

No crash, and the second request served successfully.
### Observations
1. At the step of replaying server responses, starting `mitmproxy` with the same parameters as given to `mitmdump` above WORKS!
2. If `mitmdump` is started with `--no-pop``, it WORKS!
3. I'm able to reproduce the behavior with versions 0.10.0 and 0.9.2.
4. I've reproduced this behavior with `api.zotero.org` and `www.eff.org` (which both use SSL). So it is not a problem with `www.gnome.org`
5. I'm able to reproduce the behavior by connecting to the proxy with Python's `urllib2`, so `curl` is not the problem.

Here's a workaround that might help those who are facing the same problem, need a solution now, and land on this page. The `--no-pop` argument allows working around the problem but only partially because it creates another problem. While replaying server responses, I ran into the (very predictable) problem of running the same request twice but expecting two different responses: with `--no-pop` the first response is replayed twice. I've worked around the problem created by `--no-pop` like this:
- After recording interactions with the server, open the file in which interactions are saved and add a private field to all requests. It could be named `X-MyApp-Sequence:`. It gets a value which starts at 0 and is incremented for each subsequent request. Here's a partial bit of code that shows what I'm talking about:
  
  ```
  freader = flow.FlowReader(inf)
  fwriter = flow.FlowWriter(outf)
  sequence = 0
  for i in freader.stream():
      i.request.headers["X-MyApp-Sequence"] = [sequence]
      sequence += 1
      fwriter.add(i)
  ```
  
  In the code above `inf` is the file into which the request and responses were recorded.
- When replaying, use a filter (`-s foo.py`) that rewrites requests to add `X-MyApp-Sequence` and set it in the same fashion as above:
  
  ```
  sequence = 0
  def request(_context, flow):
      global sequence  # pylint: disable=global-statement
      flow.request.headers["X-MyApp-Sequence"] = [sequence]
      sequence += 1
  ```
- When replaying, pass the argument necessary to match the header: `--rheader X-MyApp-Sequence`.

Used in conjunction with `--no-pop`, this method of numbering requests completely works around the issue for me.
