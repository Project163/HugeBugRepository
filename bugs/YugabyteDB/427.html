Title

[YCQL] failed create index is not dropped; trying to drop it later crashes yb-master

Description
The test creates a simple table where the name column has some duplicates. It then attempts to create a unique index on the name column-- and this operation is expected to fail since the table contains duplicate entries for the name column.

But 'describe' on the table still shows the index is present. The good part is that it seems to be in a failed state internally - so the query plan doesn't use the index. An attempt to later explicity drop the index crashes the yb-master.

```
ycqlsh> CREATE KEYSPACE k;
ycqlsh> USE k;
ycqlsh:k> CREATE TABLE IF NOT EXISTS users(id text, name text, age int, PRIMARY KEY(id)) WITH TRANSACTIONS = {'enabled' : true};
ycqlsh:k> INSERT INTO users(id, name, age) VALUES ('1', 'abc', 10);
ycqlsh:k> INSERT INTO users(id, name, age) VALUES ('2', 'abc', 10);
... [Log Snipped] ...
ycqlsh:k> DROP INDEX name_idx;
OperationTimedOut: errors={' ': 'Client request timeout. See Session.execute[Link: _async]'}, last_host= 
```

But an attempt to drop the "failed" index crashes yb-master, with the following FATAL:

```
F20200718 04:12:21 ../../src/yb/master/catalog_manager.cc:3894] Check failed: l->data().pb.state() == SysTablesEntryPB::ALTERING
    @        yb::LogFatalHandlerSink::send()
    @        google::LogMessage::SendToLog()
    @        google::LogMessage::Flush()
    @        google::LogMessageFatal::~LogMessageFatal()
... [Log Snipped] ...
    @        start_thread
    @        __clone
```
Discussion
- Looks like the following in MultiStageAlterTable::UpdateIndexPermission wasn't executed :
```
      indexed_table_data.set_state(SysTablesEntryPB::ALTERING,
```
Maybe CatalogManager can use the state not being SysTablesEntryPB::ALTERING to infer that index was not successfully created.

Another choice is to remove index metadata from the underlying table if the index cannot be created.
- Looks like there are 2 issues here :

1 ) D7996 implemented index removal upon backfill failure. However it only removed the index from the Index Map. The index table was to be deleted after #4039 was addressed. However, that is not yet done, although #4039 has now landed as of last week. 

2) The issue of running into a check failure seems to be caused by a relatively new interaction between D7996 and D8713 (which landed last week).  The issue seems to be essentially one where fully_applied_* fields are populated in preparation of sending an alter request; however the ALTERING state is only being set if there is a non-trivial change to the table schema.
     Doing so makes sense in situations where we are waiting for the pg permissions to catch up. However, seems like it can leave the table’s info in a RUNNING state with fully_applied* fields, when it happens from a delete index code path.
