Title

Read queries hanging after attempting to add indexes

Description
Jira Link: [Link: DB-2469]
It looks like the database encounters a bug where it will not propagate schema changes to a the tservers after running multiple CREATE INDEX statements concurrently. 

For setup, initialize a server with `backfill_index_rate_rows_per_sec=5`. Using a ycql table like the following:

```
CREATE KEYSPACE k;
CREATE TABLE k.hn (i int PRIMARY KEY, j int, k int, l int) WITH transactions = { 'enabled' : true };
```

I populate the table with data:

```
$ for i in {1..400}; do j=$(($i*400-400));echo ycqlsh `hostname -i` -e $(echo -n '"'; for k in {1..1000}; do j=$(($j+1)); echo -n "INSERT INTO k.hn (i,j,k,l) VALUES ($j, $j, $j, $j); "; done;echo -n '"') >> test.out; done;
$ bash test.out
```

Now I create indexes on the table:

```
ycqlsh> select * from system_schema.indexes ;

 keyspace_name | table_name | index_name | kind | options | table_id | index_id | transactions | is_unique
---------------+------------+------------+------+---------+----------+----------+--------------+-----------

... [Log Snipped] ...

(1 rows)
```

Meanwhile backfill is running for the index on `j`... I create an index on `k` and immediately we lose the ability to query the table.

```
ycqlsh> CREATE INDEX ON k.hn (k) ;
ycqlsh> select i,j,k,l from k.hn where j=11123;
OperationTimedOut: errors={' ': 'Client request timeout. See Session.execute[Link: _async]'}, last_host= 
ycqlsh> select i,j,k,l from k.hn where j=11123;
InvalidRequest: Error from server: code=2200 [Invalid query] message="Wrong Metadata Version. schema version mismatch for table  : expected 226, got 225
... [Log Snipped] ...
 (ql error -303)"
ycqlsh> select i,j,k,l from k.hn where j=11123;
```

Until something comes along that forces the table to update the schema version, the table remains un-queryable
Discussion
- The main change would be
```
@@ -550,9 +553,13 @@ Status MultiStageAlterTable::LaunchNextTableInfoVersionIfNecessary(
     VLOG(3) << "Start backfilling for " << yb::ToString(index_info_to_update);
     TRACE("Starting backfill process");
     VLOG(1) << "Starting backfill process";
-    WARN_NOT_OK(
... [Log Snipped] ...
     return Status::OK();
   }
```
Essentially, when the 2nd index goes through a bunch of changes to get into the “DO_BACKFILL” state, the next step is to launch the backfill
if we already have a backfill-in progress, we get a NOT-OK status, and so we do not launch the backfill ….. however, we do not go through and mark the “alter to DO_BACKFILL” state as complted (by calling ClearAlteringState)
this causes the clients to continue to receive the “old” version of the table …. even though all the tablets have now moved to the “newer” version
D8946 also would have fixed this issue --- by allowing the TServer/Client to accept off-by-one schema versions, is possible
But, the simpler, real fix is what I posted above — to just clear the altering state, even though we are unable to launch the 2nd backfill because one is already in progress.
