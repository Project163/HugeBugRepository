Title

ClassTooLargeException in JacocoProcessor during instrumentation

Description
### Describe the bug

Hello everyone,

I'm not sure if this problem belongs here or [URL]

We have updated our project to Quarkus 3.25. There is a problem with Jacoco and the AWS services, more precisely the `DefaultSsmAsyncClient`. 

During instrumentation there is a `ClassTooLargeException` concerning `DefaultSsmAsyncClient` in the quarkus `JacocoProcessor`

Stack trace (complete stack trace s. readme of reproducer repo)

```
Caused by: java.lang.RuntimeException: java.io.IOException: Error while instrumenting software.amazon.awssdk.services.ssm.DefaultSsmAsyncClient with JaCoCo 0.8.13.202504020838/78d5eff.
	at io.quarkus.jacoco.deployment.JacocoProcessor$1.apply(JacocoProcessor.java:93)
	at io.quarkus.jacoco.deployment.JacocoProcessor$1.apply(JacocoProcessor.java:83)
	at io.quarkus.deployment.steps.ClassTransformingBuildStep.transformClass(ClassTransformingBuildStep.java:350)
	at io.quarkus.deployment.steps.ClassTransformingBuildStep$2.call(ClassTransformingBuildStep.java:238)
... [Log Snipped] ...
	at org.jacoco.core.instr.Instrumenter.instrument(Instrumenter.java:109)
	... 13 more
```

I also tried to add the class to `quarkus.jacoco.excludes`, but this config property seems only to exclude classes from the report.

### Expected behavior

The build is successful and Jacoco report generated.

### Actual behavior

The build fails.

Clone [URL] and run `./gradlew build`.

- Hi @gsmet 

I tried your fix with a project with submodules. The project follows a hexagonal architecture and is modelled the following way.

```
project root
|
| - application core with only a few dependencies
| - AWS & Quarkus stuff, API client for external services, etc.
| - integration tests
... [Log Snipped] ...
| - AWS lambdas domain C
...
```

Test coverage has fallen from around 85% to 60%. The decrease in coverage seems to be due to the fact that most classes in the `AWS & Quarkus stuff, API client for external services, etc` module are tested in the `integration tests` module and not in the module itself. 

When looking at the Jacoco project, I noticed in particular that the coverage there has fallen sharply, often even to 0%. This could probably be due to the fact that the classes from the other module are no longer taken into account.

Would it even be possible to distinguish between classes from the application itself and external libraries in such a project structure?

I then tried a "brute force" approach and changed the affected lines to.

```
try {
        byte[] enhanced = instrumenter.instrument(bytes, className);
        if (enhanced == null) {
            return bytes;
        }
... [Log Snipped] ...
        return bytes;
    }
```

The build was successful and the coverage was also at the same level as before. Of course, this is not a “nice” approach, but at least the build is not blocked and the coverage is calculated correctly.
