Title

When auto read is false, SslHandler should invoke Channel.read() if whole encrypted packets are not coming yet.

Description
Netty version: 4.0.26.Final (auto read option is false)

I'm using Netty as HTTP/SPDY file server. My server turns off auto read option in order to control incoming request traffic.

I found that sometimes the final handler's channelRead() method was not called even it called Channel.read() before. It's caused by the following codes, when the whole encrypted packets didn't coming yet. SslHandler consumed other handler's Channel.read() call, but it did not call the method again.

I found this problem more often when using FixedRecvByteBufAllocator of 8Kbytes than AdaptiveRecvByteBufAllocator. (FYI) 

```
// If we calculated the length of the current SSL record before, use that information.
    if (packetLength > 0) {
        if (endOffset - startOffset < packetLength) {
            return;
        } else {
... [Log Snipped] ...
        }
    }
```

I think that SslHandler should invoke Channel.read() before returning its decode() method when the followings are met:
1. the channel is not set as auto read 
2. SslHandler didn't fire channelRead to the next handler during decoding. 

What do you think?
Discussion
- That's interesting. We thought we address this issue in 4.0.26. (See `AbstractChannelHandlerContext.fireChannelReadComplete()` calls `ctx.read()` automatically to prevent the stall like you mentioned.)

Would you mind if I ask you to write a simple reproducer?  You could take a look at `SocketSslEchoTest` and write something similar.
- @trustin I read the codes you mentioned and found steps of this problem. 
1. SslHandler decodes packets and call next.fireChannelRead()
   - At this time, invokeNextChannelRead of SslHandler context is true, and invokePrevRead is false.
2. The next handler handles channelRead() and call Channel.read() before returning it.
   - At this time, invokePrevRead of SslHandler context becomes true.
3. SslHandler handles channelReadComplete().
   - At this time, the flags are changed to false by the following codes.
     
       if (invokedNextChannelRead ||  // The handler of this context produced a message, or
           !invokedThisChannelRead) { // it is not required to produce a message to trigger the event.
     
     ```
       invokedNextChannelRead = false;
       invokedPrevRead = false;
     ```
4. SslHandler handles channelRead(). But SslHandler cannot call next.fireChannelRead() because it does not have the whole encrypted packets. (I mentioned above)
   - At this time, there is no change of the flags of SslHandler context.
5. SslHandler handles channelReadComplete(). Channel.read() will not be called because invokePrevRead of context is false. Refer to the following codes.
   
   ```
/**
    * At this point, we are sure the handler of this context did not produce anything and
    * we suppressed the {@code channelReadComplete()} event.
    *
    * If the next handler invoked {@link #read()} to read something but nothing was produced
... [Log Snipped] ...
       invokedPrevRead = false;
   }
```
6. After that, no more channelRead() will be called.
