Title

Range of gamepad axes mapped from digital source incorrect?

Description
Some gamepads do not have analogue triggers. In such cases, the mapping simply assigns a digital source to the axis -- usually a button (apparently always, in the current SDL_GameControllerDB). Let's call this type of mapping a digital axis. This case is handled [Link: here] in glfw. The resulting range of the axis is from 0 to 1.0 instead of the expected(?) -1.0 to 1.0. Other gamepads with analogue triggers produce values in the full range. I propose changing the behaviour to something like this:
```state->axes[i] = js->buttons[e->index] ? 1.0f : -1.0f;```
Similarly with the hat case [Link: just above].

Of course, one has to consider the behaviour with regard to standard "stick" axes, which in the default state are expected to return 0.0f. The current SDL_GameControllerDB contains only two cases of this

1. the ` ,hori` with `leftx:b4,lefty:b5` and
2. the ` ,PS360+ v1.66` with `leftx:h0.4`.

The negative range is however never reached in these two mappings, which, to me, makes no sense either. On the other hand, cases of digital triggers in the database are countless.

Another option is to mimic SDL, which always uses the [Link: positive-only range with triggers]. The current glfw implementation follows [Link: that of SDL], which also only returns positive values for digital axes. This makes sense in SDL, due to the different trigger range.

I appreciate any thoughts.
Discussion
- Personally, I think 0 to 1 range makes the most sense for both analogue and digital triggers. Is there a good reason we went with -1 to 1 in the first place?
- @tombsar There is no good reason for it. It's my mistake, sorry. At this point I'm afraid enough people are running `master` that we'll have to wait until the next API revision to fix it. I'll make them all map to [-1,1] for now.

@sammko Thank you for spotting this!
