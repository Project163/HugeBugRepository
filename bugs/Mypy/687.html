Discussion
- Thanks for the detailed bug report! Something is clearly wrong here.
- Well, I encounter a similar situation with class T inherited from `NamedTuple`. It seems like this kind of inheritance cause TypeInfo of class `b` to have no node of attribute `T`, but I'm still trying to figure out the deeper reason.
- Hey! I had a look into this one to see if I could find the reason for you. I've had a go at trying to explain what I found, and have opened a PR so you can see a potential fix. 

When the first class is analysed we add it to missing_names. This is because the first analysis of the TypeDict will be incomplete so we don't want to add its type information anywhere. 

But then when analysing the second class we then don't add the member T's symbol to the symbol table because we see it under the missing_names variable.

This behaviour was added in [URL] and is expected to apply to anything that defines a name in the current scope. But in the example given shows that in the case of TypedDicts we are ignoring not just at this top scope. 

My initial thought was to update add_symbol_table_node() in seminal.py to add to the symbol table when the symbol has kind MDEF (when it's a member variable). This solved this example, but any feedback/other edge cases would be great! 

This works because we want the class T to be ignored (because it's a subclass of TypedDict), but we still want the symbol for member T to be added to the symbol table. Once added to the symbol table it can then be found.
