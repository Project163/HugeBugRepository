Title

[Transform] Terms ordering specified via `"order"` parameter is ignored.

Description
### Elasticsearch Version

main

### Installed Plugins

_No response_

### Java Version

_bundled_

### OS Version

MacOS

### Problem Description

This bug report comes from [Link: Elasticsearch discuss forum].

`"order"` parameter ([Link: docs]) is ignored when specified in the `"aggregations"` section of a transform.
It works fine when specified in the search request (outside of transform).

### Steps to Reproduce

1. Create the index
```
PUT my-index
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1
... [Log Snipped] ...
  }
}
```

2. Populate the index with data
```
POST my-index/_bulk
{"index":{}}
{ "group_id": "gA", "item_id": "iA", "item_value": 1 }
{"index":{}}
{ "group_id": "gA", "item_id": "iB", "item_value": 1 }
... [Log Snipped] ...
{"index":{}}
{ "group_id": "gE", "item_id": "iC", "item_value": 1 }
```

3. Observe that the search request orders the bucket keys descending ("iC", "iB", "iA")
```
GET my-index/_search
{
  "size": 0,
  "aggregations": {
    "groups": {
... [Log Snipped] ...
  }
}
```

```
{
  "took": 10,
  "timed_out": false,
  "_shards": {
    "total": 1,
... [Log Snipped] ...
  }
}
```

4. Observe that the transform ignored the order
```
GET _transform/_preview
{
  "source": {
    "index": "my-index"
  },
... [Log Snipped] ...
  }
}
```

```
{
  "preview": [
    {
      "group_id": "gA",
      "items": {
... [Log Snipped] ...
  }
}
```

Discussion
- Pinging @elastic/ml-core (Team:ML)
- For the person that will handle this issue, `AggregationResultUtils.MultiBucketsAggExtractor.value` method is the place in the code where the order is lost:
- the method gets an aggregation as an argument, the order is preserved
- the method returns `HashMap`, the order is lost
- The change mostly replaces `HashMap` with `LinkedHashMap`.  This is significantly easier than rebuilding the parsing logic and sorting it within Transforms.  In theory, `PivotConfig`'s `AggregationConfig` has enough information to inform us that the result will be sorted. In practice, we'd only be building around that information to determine if we should use a `HashMap` (when the order is not specified) or a `LinkedHashMap` (when the order is specified).

It *feels* like we should just keep the results as close to what we would get if we used the same request data in a plain search request or a transform -> search request, so all API behave the same. With that mentality it makes sense (to me) to just have Transforms always maintain the order as what is in the search result, and the search code can figure out what order it wants to return.
- Using LinkedHashMap, the responses now appear similar:

```
json
GET my-index/_search
{
  "size": 0,
  "aggregations": {
... [Log Snipped] ...
  }
}
```

```
json
{
  "took": 3,
  "timed_out": false,
  "_shards": {
... [Log Snipped] ...
  }
}
```

```
json
GET _transform/_preview
{
  "source": {
    "index": "my-index"
... [Log Snipped] ...
  }
}
```
```
json
{
  "preview": [
    {
      "group_id": "gA",
... [Log Snipped] ...
  }
}
```
