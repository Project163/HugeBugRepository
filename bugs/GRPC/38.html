Title

Client keepalive stops sending pings after 2 attempts

Description
### What version of gRPC and what language are you using?

Python 1.36.1


### What operating system (Linux, Windows,...) and version?

Linux Debian 10.8

### What runtime / compiler are you using (e.g. python version or version of gcc)

Python 3.7.3


### What did you do?

1. Configure client keepalives with a very short time `('grpc.keepalive_time_ms', 500)`.
2. Make an RPC to a server that hangs for 60 seconds.


### What did you expect to see?

* This client should ping every 10 seconds (As [Link: recommended by the Client Keepalives design doc]: "KEEPALIVE_TIME, defaulting to infinite. If smaller than ten seconds, ten seconds will be used instead."
* After pinging a few times, the server should close the channel with GOAWAY too_many_pings


### What did you see instead?

* Client writes the request and a PING_RESPONSE
* +500 ms: sends a keepalive ping
* +500 ms: TRIES to send a ping, but there is a 1s minimum so it reschedules it
* +500 ms: sends a second keepalive ping
* +500 ms: `CLIENT: Ping delayed [ipv4: :8001]: too many recent pings: 0/2` ; it never sends a ping again
* +58 s: the response is received

This explains why the connection doesn't get closed with the GOAWAY error: the client is not sending keepalives correctly. This is triggering this code: [URL]

I found this as part of my [Link: investigation of gRPC client keepalive misconfigurations]. I was curious why I only saw this with Go clients.

Discussion
- Hi, This is an artifact of how Core deals with communication with certain proxies which restrict how often pings can be sent by clients. This resulted in this channel arg `GRPC_ARG_HTTP2_MAX_PINGS_WITHOUT_DATA`
  "grpc.http2.max_pings_without_data" which controls how many pings can be sent without any data/header frame.

We intend to deprecate this channel arg as soon as we can fix this behavior, but for now please set `GRPC_ARG_HTTP2_MAX_PINGS_WITHOUT_DATA` to 0 to avoid this bottleneck.

- Thanks for the rapid response! I think this is another argument that client keepalive in gRPC needs to be documented as dangerous and/or very complicated to configure. This was absolutely NOT clear to me on my first read of the linked document, especially since it says "The above two channel arguments should be sufficient for most users". That is *not* true if you actually need keepalive to do its job during a very long running RPC.
