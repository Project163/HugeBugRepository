Title

calling ctx.expand_location() from an aspect causes outputs of rule to be required

Description
If an aspect rule calls `ctx.expand_location()` for an attribute of the aspect's `ctx.rule`, the `ctx.rule`'s outputs are added to the _required outputs_ list. This makes the build fail since the actions to create the outputs are not necessarily created.

Here is a shell script that reproduces the issue:

```
#!/bin/sh

set -eo pipefail

workdir=$(mktemp -d)
... [Log Snipped] ...
EOF
bazel clean --expunge ; bazel build simple:simple --aspects aspects/print.bzl%print_expanded_copts
```

Saving this shell script in `repro.sh` and running it produces the following output:

```
$ sh repro.sh 
Starting local Bazel server and connecting to it...
INFO: Invocation ID: bc62eba1-2daa-4c45-af6f-e776a5a4e9db
INFO: Starting clean.
Starting local Bazel server and connecting to it...
... [Log Snipped] ...
INFO: 0 processes.
FAILED: Build did NOT complete successfully (17 packages loaded, 329 targets configured)
```

The failure is due to the outputs of the `simple` rule being added to the list of required outputs, but note that `simple` is not required to expand the location, it's `headermap` that is required.

Tested with Bazel 0.21.0 and master as of   on macOS 10.14.2.
Discussion
- So looking a bit more into this bug, I think the problem is around [Link: here], where the code to expand locations creates the artifacts via a call to `CreateOutputArtifact()`. This has a side effect of adding the artifact to the list of tracked artifacts in the CachingAnalysisEnvironment, [Link: here]. 

So if you look at the flow, the action is registered in on Analysis Environment, here _d342bd6_:

```
DEBUG: Registering action 'action 'Linking simple/simple_fully_linked.a' in 'com.google.devtools.build.lib.analysis.CachingAnalysisEnvironment@d342bd6'
```

And then the artifact is looked up in a different Analysis Environment (_14773d5d_):

```
DEBUG: Aspect Created: 'com.google.devtools.build.lib.analysis.ConfiguredAspect@1b68d16c' in rule context RuleContext(//simple:headermap,  )'
DEBUG: Adding artifact bazel-out/apl-darwin_x86_64-fastbuild/bin/simple/simple_fully_linked.a to 'com.google.devtools.build.lib.analysis.CachingAnalysisEnvironment@14773d5d' AE
DEBUG: Aspect Created: 'com.google.devtools.build.lib.analysis.ConfiguredAspect@8d4f0d0' in rule context RuleContext(//simple:simple,  )'
DEBUG: Could not find bazel-out/apl-darwin_x86_64-fastbuild/bin/simple/simple_fully_linked.a in 'com.google.devtools.build.lib.analysis.CachingAnalysisEnvironment@14773d5d' AE
```

My question is, is there a way in that call to `trackArtifactAndOrigin()` to know you're actually in the aspect graph and not in the action graph? Could I wire in something from the `ruleContext` down to the `CachingAnalysisEnvironment` to avoid this issue?
