Title

rclone exits with status 0 after receiving SIGINT/SIGTERM

Description
#### What is the problem you are having with rclone?

When rclone receives a SIGINT (Ctrl+C) or SIGTERM signal while an atexit function is registered it always exits with status code 0. Unix convention is to exit with a non-zero status code. Often it's `128 + int(signum)`, but at least not zero. Wikipedia writes ([Link: source]):


The non-zero exit status enables scripts to handle commands aborted by signals, e.g. by the user. The responsible code is in `atexit.go:Run` where the exit status is hardcoded: [URL]

I'll be happy to submit a pull request. Would the rclone developers prefer to always use status 2 ("error not otherwise categorised") or the 128+signum convention?

Discussion
- I did a quick straw poll of a few commands

- `ls`, `tar` exits with 128+SIGNUM
- `rsync` exits with a special error code 20 `received SIGINT, SIGTERM, or SIGHUP (code 20)`

I note that 128+signum is very unix centric

Killing rclone with any other signal will likely exit with 128+signum (though is the done by the shell? not sure).

I think on balance 128+signum is fine, with the proviso that we discover what that does on Windows!
- If a process handles signals on its own it can implement whatever it wants. That's the case of rclone for SIGINT/SIGTERM on Unix systems.

If a program is terminated by a signal, either by the default handler or because it can't be caught (SIGKILL, etc.), the shell will assign the exit code to 128 + N after it got the signal number from `waitpid` or a related function.


I wasn't aware of this before, but [Link: Windows doesn't have signal numbers]. The PR I'm going to push shortly handles this such that on Windows the exit status upon a signal is always 2 (uncategorized error). I cross-built and ran the unit test on Windows.
