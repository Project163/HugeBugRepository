Title

Illuminate\Database\Eloquent\Builder::where() malfunctioning inside a ScopeInterface

Description
1. Steps to reproduce the problem:
   1. Create a model.. any model (extending \Illuminate\Database\Eloquent\Model)
   2. Create a simple trait to add a GlobalScope for the model
   3. Create a simple ScopeInterface implementation
   4. use a `$builder->where( ... )` (or any derivative like orWhere) with a closure as argument in it's `apply($builder)` method.
2. Expected outcome: The sql it's generated and executed normally
3. Received outcome: The sql generation loops forever until filling server memory, if launch with `php artisan serve` it simply throws a Segmentation Fault on the console.

Discussion

    
- I've been doing some research, the trace would be something like this:

M is Illuminate\Database\Eloquent\Model.php
B is Illuminate\Database\Eloquent\Builder.php
S is the ScopeInterface implementation

Let's supose I want to do a:
1. somewhere: `Product::all()`
2. M#628: `->newQuery()`
3. M#1758: `->applyGlobalScopes( new Builder )`
4. M#1794: `$scope->apply( $builder );`
5. inside S->apply($builder): `$builder->where( function ($query) { ... } );`
6. B#561: `$this->model->newQueryWithoutScopes();`
7. M#1779: `return $this->removeGlobalScopes($this->newQuery());`

At point 7, the $this->newQuery() creates a new iteration of all the steps, inside it, when reaching step 7, a new one is created... so forth, forever.

Therefore, ->where() clauses with Closures can't be used inside GlobalScopes...
- Proposed solution: 

In \Illuminate\Database\Eloquent\Model:

Instead of `newQueryWithoutScopes()` calling `removeGlobalScopes($this->newQuery())`, 
move the query initialization code to `newQueryWithoutScopes` 
and make `newQuery()` call `newQueryWithoutScopes()` and then `applyGlobalScopes()`.

It's even faster overall...
It skips the ->applyGlobalScopes()->removeGlobalScopes() currently bugging newQueryWithoutScopes...
