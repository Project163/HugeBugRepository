Title

Single character does not match high value unicode character with collation TERRITORY_BASED

Description
With TERRITORY_BASED collation '_' does not match  the character \uFA2D.  It is the same for english or norwegian. FOR collation UCS_BASIC it matches fine.  Could you tell me if this is a bug?

- I am looking at the current behavior where _ matches a single collation element instead of a single character and trying to understand what the new behavior would be.    Here is an example of the current behavior:  I insert into a table two rows: 

  agrave = "\u00C0"; 
agraveCombined ="A\u0300"; 

 agrave is one character, agraveCombined is two but they match for = and like processing with a French TERRITORY_BASED database.  Here are some queries. 

 jdbc:derby:frdb (TERRITORY_BASED - current) 
2 rows matching SELECT COUNT  FROM T WHERE VC = À 
2 rows matching SELECT COUNT  FROM T WHERE VC LIKE À 
2 rows matching SELECT COUNT  FROM T WHERE VC LIKE A_ 
0 rows matching SELECT COUNT  FROM T WHERE VC LIKE _ 
2 rows matching SELECT COUNT  FROM T WHERE VC LIKE __ 

 jdbc:derby:regdb (UCS_BASIC) 
1 rows matching SELECT COUNT  FROM T WHERE VC = À 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE À 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE A_ 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE _ 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE __ 

 So if _ is really supposed to match a single character and not a single collation element, 
I think the results should be as follows: 
jdbc:derby:frdb (TERRITORY_BASED) 
2 rows matching SELECT COUNT  FROM T WHERE VC = À 
2 rows matching SELECT COUNT  FROM T WHERE VC LIKE À 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE A_  (agraveCombined) 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE _  (agrave) 
1 rows matching SELECT COUNT  FROM T WHERE VC LIKE __ (agraveCombined) 

 Does that sound right?  How I might implement this I have no idea but just trying to get my head around how it should behave.

- I would say neither (existing or proposed)  is correct, though only after looking at your example. 

 The existing code is wrong because it is converting the '_' to a collation element then skipping that number of collation elements? 

 The proposed results are wrong because in the French locale agraveCombined ="A\u0300" is a single character. 
I assume the \u0300 is a 'Combining character'. 

  [URL]

 Thus I think the results should be: 

 0 rows matching SELECT COUNT  FROM T WHERE VC LIKE A_ 
2 rows matching SELECT COUNT  FROM T WHERE VC LIKE _ (agrave,agraveCombined) 
0 rows matching SELECT COUNT  FROM T WHERE VC LIKE __ 

 As for implementing it, I think one has to use the getOffset/setOffset method on CollationElementIterator. 

 E.g. along the lines of this to skip a character. The real solution would be more than this but you get the idea. 

    if (patternChar == '_') 
       iterator.setOffset(iterator.getOffset() + 1);
