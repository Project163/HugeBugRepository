Title

Recycler could cache infinite resources

Description
In Netty.4.0.24.final.

In class io.netty.util.Recycler, there's a DEFAULT_MAX_CAPACITY variable to constrain the size of the stack in Recycler. From INITIAL_CAPACITY, whenever the stack is full, it's size doubled until hitting the DEFAULT_MAX_CAPACITY limit(Line 341 in Netty.4.0.24.final). 
[Image: image]
As you can see in the image above, stack size is constrained by maxCapacity. And if the size > maxCapacity, this check will fail forever, beacuse the check use "if (size == maxCapacity)" rather than "if (size > maxCapacity)".  And there's a way to set size bigger than maxCapacity.

In class WeakOrderQueue which is an inner class in Recycler, there's a method called "transfer" which can also double the stack size in Recycler, but there's no check to ensure the stack size not exceed DEFAULT_MAX_CAPACITY limit(Line 218 in Netty.4.0.24.final) like the one mentioned before. 
[Image: image]
In the image above, variable "to" is a stack in Recycler and count is resources's quantity recycled by other thread rather than the Recycler's owner. If there's no enough space for those resources to be recycled, the stack's size will be doubled. I think there should have a check for the stack size here. And whenever the stack size greater than maxCapacity, it can grow infinitely.
Discussion
- @trustin I think you wanted to investigate here... Any luck yet ?
- @ylgrgyq You are correct. The `transfer()` method should not increase the capacity of `elements` beyond the maximum capacity.

@belliottsmith Besides the problem mentioned above, I also found that `WeakOrderQueue.add()` can grow unbounded, when a user recycles a lot of objects and does not attempt to retrieve it.  It's backed by `WeakHashMap`, so it shouldn't be as dangerous, but perhaps we could enforce some limit?
- Getting some weirdness with github not showing a message I received in email:

"@ylgrgyq Actually, transfer() method is triggered only when the stack contains no elements. Unless the capacity of the array is smaller than LINK_CAPACITY, it should never increase the capacity. Am I correct, @belliottsmith?"

@trustin right, that was the idea. although a quick closer inspection does show that there is a rare condition that could cause it to be exceeded: if the thread that recycled is collected it will transfer its entire backlog, which in the unlikely case this coincides with the thread having recycled > MAX_CAPACITY elements in the interval would result in a breach. 

We can plug this hole also by ensuring no unbounded growth. There are a couple of options: simply bound growth for each thread to some ratio of max capacity, or on adding a new thread's queue we could adjust a per-queue limit so that the total amount of growth is bounded regardless of the number of threads.
