Discussion
- The longer I stare at this method, the more I think it is wrong or at least overcomplicated 
If a bundle is built by Maven it always has both, the properties file and the pom file; so checking for both is unnecessary. 
It should be enough to get the properties. 
But then the result from the properties file (or the path of the pom.xml) is validated against the bundle name and only used if it matches. If nothing is found, the bundle name is used. 

 So I think we can simplify this by: 
 
	 extracting artifact id, classifier and version from the bundle name 
	 trying to get the group id from the path of the pom.xml (like is done today), if not found fall back to the current code
- cziegeler , I agree that should be the case - however, we had cases where a bundle didn't have both. Furthermore, I seem to remember cases where there was more than one pom. Ultimately, I'm not sure the classifier would be necessarily reflected in the bundle name.  

 I guess that is part of why the code is so complicated, it tries to find the pom properties, if not, it tries to see if a pom is there that seems to match (however, it seems like it has some potential ordering problems in that assuming it is possible to have the order of the entries in a way where a matching pom comes first that isn't the right one).  

 Cleaning it up makes a lot of sense - just wanted to point out what I remember from previous issues.
- yes, several poms as well as several properties files are possible (usually caused by embedding). 
I was wondering about a potential ordering problem here as well
- I refactored the code in  [URL]  
It seems if we actually reset groupId etc. then a lot of tests start failing, therefore I didn't not do this. But at least the code is now a little bit easier to read
