Title

mySQL connections not returned to the pool when `fetch_optional` yields no results

Description
### Bug Description

When a query executed using `fetch_optional`returns no results, the connection is not returned to the pool. Once `max_connections` is exceeded all following connections fail with a `PoolTimedOut` error.

This seems to happen only when using the mySQL driver.

### Minimal Reproduction

To reproduce run this test:

```
rust
#[tokio::test]
async fn mysql_test() {
    sqlx::any::install_default_drivers();

... [Log Snipped] ...
    }
}
```

Which fails with a `PoolTimedOut` error:

```
txt
running 1 test
Query #0 with results.
Query #1 with results.
Query #2 with results.
... [Log Snipped] ...
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
test mysql_test ... FAILED
```

### Info
* SQLx version: 0.7.1
* SQLx features enabled: [ "runtime-tokio-rustls", "postgres", "mysql", "sqlite" ]
* Database server and version: 8.0.33 
* Operating system: MacOS and Linux
* `rustc --version`: rustc 1.70.0 (90c541806 2023-05-31)
Discussion
- Update: Calling `fetch` followed by `try_next` as a replacement of `fetch_optional` works properly:

```
rust
    for i in 0..10 {
        println!("Query #{i} with results.");
        let r = sqlx::query("SELECT 1 + 1")
            .fetch(&pool)
... [Log Snipped] ...
        println!("Result: {r}");
    }
```
- Same issue is reproduced on older version of sqlx. @mdecimus Workaround with `fetch().try_next()` does not help. I also replaced all usages of `fetch_all()` with `fetch().try_collect()` as seen [Link: here], no luck as well.

I had to tune DB instance `wait_timeout` to 60 seconds, so it automatically drops the inactive connections, I consider this as a dirty workaround.

Unfortunately I cannot provide a minimal working example since it is a big web application using Rocket and `sqlx` via `rocket_db_pools` and I'm not sure which queries are actually eat-up connections.
