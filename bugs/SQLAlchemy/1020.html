Title

Wrong type for results from PostgreSQL system columns

Description
**Describe the bug**
Following the example from [URL] , when fetching an object from the database the type of the system column (`xmin`) seems to be wrong (`str` instead of `int`).

A quick check (manual query) confirms that the value in the `xmin` column is indeed an integer in the database itself.


**Expected behavior**
The `xmin` value to be an `int`.

**To Reproduce**

```
py
#!/usr/bin/env python
# -*- coding: utf-8 -*-
from sqlalchemy import *
from sqlalchemy.ext.declarative import declarative_base
... [Log Snipped] ...
assert isinstance(user.xmin, str)  # This succeeds, even though the column type is `Integer`
assert isinstance(user.xmin, int)  # and this fails
```

I also tested this code using the `xmax`, `cmin` system columns and they had the same issue.

**Versions.**
 - OS: Ubuntu 18.04.5
 - Python: 3.9.0 (also reproduced on 3.6.x)
 - SQLAlchemy: 1.3.20
 - Database: PostgreSQL 9.6
 - DBAPI: psycopg2 2.8.6

**Additional context**
It seems to me that either the result type is wrong, or the documentation example is wrong/confusing.

```

however it does neither for integer:

```
test=> select xmin::int AS "is it an integer?" from foo;
ERROR:  cannot cast type xid to integer

it seems a safe bet we should change that documentation example to use String for xmin and not integer.
- Hi,

I just did a quick query (`SELECT xmin FROM some_table WHERE ...`) and assumed the result was an int since it looked like one.  Forgetting that in `psql` string results render just like the same as ints (I don't have to use direct SQL that often anymore, I'm blaming ORMs for that ;) ).

Besides that, [URL] talks about a "transaction ID" and I also assumed that was talking about integers (combined with the SQLAlchemy documentation example also using integers), together with me vaguely remembering us hitting an internal Postgres integer max on transaction IDs many years before.

Hence the safe-guards in my initial report on this :)


I agree, especially considering your tests (even *if* Postgres may use an int internally, if it's presented like a string to clients it makes sense to me if SQLAlchemy and the docs do so as well).
