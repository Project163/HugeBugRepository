Title

WriteFiles data loss with some triggers

Description
[URL]

 Details in comments
Discussion
- User reads data from pubsub and windows it into 1-minute windows with trigger AfterProcessingTime.pastFirstElementInPane().plusDelayOf(1 minute), and writes it to TextIO.write().withWindowedWrites(). They observe that some files in the temp directory are never moved to final location, i.e. final output doesn't contain all the data it should. 

 My reconstruction of events that happens, exemplified by 1 window that experienced data loss: 
Window [2017-11-10T13:38:00.000Z..2017-11-10T13:39:00.000Z): 
Two temp files were written: 
3e3fdee3-d928-485a-b3a5-1faa3c2a58d6 (opened at 2017-11-10 06:39:51.585 PDT, closed at 2017-11-10 06:39:52.090 PDT) 
d12e91d2-39b3-43d4-b27f-3a340c25f888 (opened at 2017-11-10 06:40:00.624 PDT, closed at 2017-11-10 06:40:00.909 PDT) 

 The finalize operation for that window triggered at 2017-11-10 06:40:00.979 PDT (on a different worker) and moved only the first file. The second file was never mentioned in the logs again. 

 Explanation of why this happened - in the next comment.
- With the user's configuration (windowed writes, fixed number of shards, no dynamic destinations), WriteFiles follows the following codepath: 

 
	 ApplyShardLabel to assign each element with a destination (all null in this case) and shard (random number) 
	 Group by destination/shard  [more precisely, by hash of destination and shard]  
	 Write each group to its own temp file using WriteShardedBundles: this triggers according to the input's windowing strategy, i.e. f
...[Text Truncated]...
 a PCollection of FileResult, one per temp file written. The windowing strategy of this PCollection is the same as the input collection but the trigger is the  [continuation trigger] ( [URL] of the input trigger; in this case, this means the collection of FileResult has trigger AfterSynchronizedProcessingTime.pastFirstElementInPane(). 
	 The PCollection returned by WriteShardedBundles is grouped onto a single Void key, followed by a ParDo FinalizeWindowed that, does a bulk copy of respective temp files to final locations and then bulk deletes them. I suppose the GBK onto void key is done in order to concentrate the move activity on one worker so that it can be better batched?... I'm not sure, perhaps  reuvenlax  remembers. 
 

 Unfortunately, that last GBK, as we recall from above, uses a triggering strategy that is the continuation trigger of the original input, which means, depending on how the input triggering was configured, it may discard data. In this particular case, the continuation trigger is a fire-once trigger AfterSynchronizedProcessingTime.pastFirstElementInPane() - so, after it fires for the first time for FileResult 3e3fdee3-d928-485a-b3a5-1faa3c2a58d6, it never fires again for this window and doesn't move the other temp file.
