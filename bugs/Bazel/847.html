Title

BES upload fails on build without the bytes + broken builds

Description
### Description of the problem:

When running a build as follows:
1. Using remote execution
2. With build without the bytes flag (`--remote_download_minimal`)
3. With BES backend defined (`--bes_backend`)
4. When one of the target fails to build (compilation error , for instance)

The build finishes with error message:
```
ERROR: The Build Event Protocol local file upload failed: /root/.cache/bazel/_bazel_root/ /execroot/my_bazel_example/bazel-out/k8-fastbuild/bin/src/main/com/example/app/app_runner.jar (No such file or directory)
```
And the BES upload fails.
Instead of seeing broken build - we see Tool failure in the BES backend.

### Bugs: what's the simplest, easiest way to reproduce this bug? Please provide a minimal example if possible.

I've created [Link: minimal repo for example].
To see the issue run the build (on linux, or using the docker image `l.gcr.io/google/bazel:2.2.0`)
```bash
bazel --bazelrc=.bazelrc.remote test -k //... \
    --config=remote --config=results \
    --remote_instance_name=  \
    --project_id= 
```

### What operating system are you running Bazel on?

Linux (we're using bazel image `l.gcr.io/google/bazel:2.2.0`)

### What's the output of `bazel info release`?

We've been using bazel `2.1.0` for while and started seeing the issue when we tried to upgrade to `3.3.0`.
Using bazelisk I ran the build on several releases and it seem like the first version that fails like this is `2.2.0`.

Discussion
- I believe I understand what's going on here.

We have a feature to report successful output groups of top-level targets even if other output groups in the same top-level target failed. This is relatively new. We have a bug here where we're not appropriately applying path transformation to the "remote" filesystem related to --experimental_remote_download_outputs=minimal. When we go to upload the properly built output file, we're improperly consulting the _local_ filesystem where it will not be present.

A similar issue occurs in Blaze, but we're more tolerant to missing files in that case. Here, we fail to upload the file, which fails the BES upload, and that triggers a follow-on threadpool crash.
