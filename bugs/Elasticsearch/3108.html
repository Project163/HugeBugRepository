Title

Aggregations: `change_point` agg does not return results when nested in `categorize_text` agg

Description
### Elasticsearch Version

8.15.0-SNAPSHOT, build hash:  

### Installed Plugins

none

### Java Version

_bundled_

### OS Version

Darwin 23.6.0 Darwin Kernel Version 23.6.0: Fri Jul  5 17:56:41 PDT 2024; root:xnu-10063.141.1~2/RELEASE_ARM64_T6000 arm64

### Problem Description

When nesting a `change_point` agg within a `categorize_text` agg, the change point information is missing from the response. The same works when the outer `categorize_text` agg get replaced with for example a `terms` agg.

### Steps to Reproduce

I used the Kibana Sample Data Logs dataset with the following queries in Kibana Dev Tools.

Here's an example query where the change point agg results is missing from the response:

```
POST kibana_sample_data_logs/_search
{
  "size": 0,
  "aggs": {
    "my_categories": {
... [Log Snipped] ...
  }
}
```

In the response, the histogram agg works, but there's not change point output on the same level:

```
...
              {
                "key_as_string": "2024-08-28T00:00:00.000Z",
                "key": 1724803200000,
                "doc_count": 88
... [Log Snipped] ...
            "buckets": [
...
```

Replacing `categorize_text` with `terms` works:

```
POST kibana_sample_data_logs/_search
{
  "size": 0,
  "aggs": {
    "my_terms": {
... [Log Snipped] ...
  }
}
```

The response shows up even when no change points get detected as `stationary`:

```
...
              {
                "key_as_string": "2024-08-29T00:00:00.000Z",
                "key": 1724889600000,
                "doc_count": 194
... [Log Snipped] ...
            }
          }
```

This is critical, but for those following along at home, in java if you don't override `equals` things are *unequal* by default. I presume this is what @original-brownbear assumed would happen. Alas, we [Link: flipped] this so aggs are considered equal to each other if their name and metadata are equal by default. I believe it's been like this since 2019 in #43214. Like Ben says, for Armin's change to work equality needs to be correct on all aggregations and you can forget that, given how things stand now.
