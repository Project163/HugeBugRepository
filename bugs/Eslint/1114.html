Title

`no-extra-semi` mistakenly removes necessary semicolon when `semi` is `never`

Description
**Tell us about your environment**

* **ESLint Version:**
3.13.1
* **Node Version:**
6.9.3
* **npm Version:**
4.1.1
**What parser (default, Babel-ESLint, etc.) are you using?**
default
**Please show your full configuration:**

 
```yaml
rules:
  semi:
    - error
    - never
  no-extra-semi:
    - error
```

**What did you do? Please include the actual source code causing the issue.**

 
```js
var foo = function(){};
;[1].map(foo)
```

**What did you expect to happen?**
```js
var foo = function(){}
;[1].map(foo)
```
**What actually happened? Please include the actual, raw output from ESLint.**
```js
var foo = function(){}
[1].map(foo)
```

When `semi` is `never`, `no-extra-semi` is true, and there are whitespaces between two semicolons, those rules will delete both of semicolons. `semi` deletes the first one, and `no-extra-semi` deletes the second one.
Discussion
- Thanks for the report -- I was able to reproduce this issue.

I'm not sure what the correct fix for this should be. Two problems are getting autofixed here (`semi` and `no-extra-semi` both remove extra semicolons), and both fixes are independently correct. However, the behavior of the code changes when both fixes are applied simultaneously. We might need to make the conflict detection more strict in [Link: `source-code-fixer`].

- @alangpierce Your analysis of how autofixing works is basically correct. One additional note: fixable rules also must export a `meta.fixable` property, which has a value of either `code` or `whitespace`. (At the moment, the property isn't actually used for anything, but it was introduced in case we ever needed to filter fixes to avoid conflicts, e.g. by only applying fixes that don't affect the AST.)

Your idea of specifying a "don't touch this code" range for fixes seems like it would work. My main concern is that it might be difficult for a rule author to think of all the possible conflicting fixes that could cause a problem. I like that the current autofixing system doesn't have much mental overhead -- a rule can (supposedly) just convert code to other valid code, and assume that core will take care of any conflicts.

to your suggestion of using larger fix ranges. I think your suggestion is probably better, because this would tightly couple the report range with the internal fix logic.)

- @ilyavolodin I think both fixes would still happen in your example (if I'm understanding things right). All that the locking would ensure is that the two fixes aren't applied *in the same pass*. In this case, the source-code-fixer code would pick either `linebreak-style` or `semi` to apply in the first pass, and skip the other, and in the second pass, the other fix would be detected and applied.

This might make eslint slower on average (e.g. 3 or 4 passes instead of 2) and more likely to hit the 10 pass limit, but my impression is that it won't be a really big deal, and that correctness for autofixing is really important.
