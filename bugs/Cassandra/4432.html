 The important line is this: 

  
 record [REMOVE:[/data/cassandra/data/schema/cf- /mc-68950-big,1482011137000,8][2304719904]]: last update time [21:45:36] should have been [21:45:37]
 
  

 This line indicates that the max update time of this sstable files jumped one second in the past. 

 This would typically happen if the files are deleted out of order. Cassandra deletes obsoleted sstable files from the oldest to the newest, so the max update time should not change. It is possible that there is some code that I have not yet identified that does not respect this, but it isn't very likely.  

 Looking at the raw timestamp, 1482011137000, it indicates a rounding problem to me. It seems the precision is in seconds, given the last 3 zeros, but   File::lastModified  , which we use for calculating the last modifified time  here , should return milliseconds. I found a number of articles suggesting possible rounding problems on Linux depending on file system and JVM version, for example  this article .
