Three different issues, involving different remotes. (Btw, all 3 tests are new ones I added -- not regressions.)

### TestFixCase

Proposed fix: [URL]
I think this actually revealed a pre-existing bug in rclone that was not previously covered by the tests. In a nutshell, `operations.moveOrCopyFile` had a special section to handle changing case of a file on a case insensitive remote, but `operations.Move` did not. The issue only affects backends that are incapable of renaming a file in-place to an equal-folding name, which is not all case-insensitive remotes. This is why I did not catch it when testing on macOS (which is case-insensitive but can rename in place.)

Note also that while testing, Dropbox sometimes complained about `too_many_write_operations` unless I slept for a second or two between moves (https://github.com/nielash/rclone/commit/ ). This probably isn't the right fix, and may not actually be needed (is it just a limitation of the free account I'm using? does the real integration test account have higher API limits?)

### TestCaseInsensitiveMoveFileDryRun
[URL]

It appears that `ci.DryRun = true` affects the behavior of `r.WriteObject` on `chunker` only, and no other remotes. This change puts a quick bandaid on it by setting it later on in the test, but perhaps the underlying issue warrants a closer look at some point... is `chunker` checking `ci.DryRun` itself in a way that no other remote does? If so, should it? (Does this break encapsulation?)

### TestApplyTransforms

I think this one is actually an issue with the 3 failing backends (Jottacloud, Koofr, and Owncloud) not the test or code. I suspect the issue is that these 3 are normalizing to NFC on the server side, so they are actually incapable of supporting `NoUnicodeNormalization` (i.e. if you give it NFD, it will convert it to NFC anyway). A quick search seems to confirm this (for example, see Owncloud issue 6338.) So, not sure what the right fix is here -- perhaps we should just skip this test for these 3 backends, by name?
