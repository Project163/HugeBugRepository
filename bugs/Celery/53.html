Title

celery worker fails to remove stale pidfile when run as non-privileged user

Description
This is bug straightforward and exists in master as well as the latest 3.1 branch.

I would think it is best to run celery workers as non-privileged users so it is surprising this bug has not been reported already.

If you have a stale pidfile, a pidfile holding the process id of a process that has already terminated, you will get this message when trying to start the worker with the following command.

Message:
```
celery beat v3.1.25 (Cipater) is starting.
ERROR: Pidfile (/path/writable/by/this/user/celery-beat.pid) already exists.
Seems we're already running? (pid: 2646)
```
Command:
```
/path/to/virtualenv/bin/celery beat --pidfile=/path/writable/by/this/user/celery-beat.pid --logfile=/path/writable/by/this/user/celery-beat.log --loglevel=INFO --app=my_app --workdir=/my_app/root
```

The bug is here: [URL]

When you try to kill a non-existent process as a non-privileged user you get errno==1, not errno.ESRCH (which evaluates to 3):

```
Traceback (most recent call last):
  File " ", line 1, in  
OSError: [Errno 1] Operation not permitted
```

So the fix is to update that line from,
```
            if exc.errno == errno.ESRCH:
```
to,
```
if exc.errno == errno.ESRCH or exc.errno == errno.EPERM:
```

I suspect you no longer publish updates to the 3.1.x version so I will plan to work around this by wrapping the "celery" script with a stale pid checker.

But please fix it in your master branch.
