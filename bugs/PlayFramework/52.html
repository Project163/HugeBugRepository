Discussion
- Hmm, that doesn't sound good. I'll take a look at this.
- I've replicated this bug now. I'll work on getting it fixed. @btnguyen2k, thanks for testing out the experimental HTTP/2 support and reporting this issue!
- The problem seems to be that Akka HTTP sends different info for HTTP/1.1 vs HTTP/2 requests.

For example, here is a working HTTP/1.1 request:

```
request = {HttpRequest@22648,…,HttpProtocol(HTTP/1.1))"
 method = {HttpMethod@20503} "HttpMethod(GET)"
 uri = {Uri$$anon$1@22655} "[URL]
 headers = {$colon$colon@22656} "::" size = 11
  …
  1 = {Raw$minusRequest$minusURI@22664} "Raw-Request-URI: /test?param=s"
```

And here is a failing HTTP/2 request:

```
request = {HttpRequest@22599} "HttpRequest(…,HttpProtocol(HTTP/2.0))"
 method = {HttpMethod@20503} "HttpMethod(GET)"
 uri = {Uri$$anon$1@22603} "[URL]
 headers = {Vector@22604} "Vector" size = 9
   >>
…
```

There are two differences I can see:
1. The `HttpRequest`'s `uri` field is different for both. For the HTTP/1 request the query parameter is properly separated by a `?`. For the HTTP/2 request the query parameter is shown as part of the path.
2. The `HttpRequest` includes a `Raw-Request-URI` header in the HTTP/1.1 request, but not in the HTTP/2 request. This affects the conversion logic: [URL]

Actions:
1. raise bug upstream in Akka HTTP and possibly implement fix
2. if Play actually requires the `Raw-Request-URI` field to be present then it should _require_ it to be present and give an error if it is missing, instead of just falling back to the `HttpRequest` `uri` field.
2. add unit tests to Play for path parsing when using HTTP/2
- I have created an Akka HTTP issue to track this: [URL]
