Title

Flyway / Picocli native build fail with ClassNotFoundException org.jboss.vfs.VirtualFileFilter

Description
### Describe the bug

I try to build a native executable for a Quarkus project using Picocli and Flyway quarkus extensions.
The native build fail with the following exceptions : 
```
posh
Fatal error: java.lang.NoClassDefFoundError: software/amazon/awssdk/awscore/exception/AwsServiceException
        at java.base/java.lang.Class.getDeclaredFields0(Native Method)
        at java.base/java.lang.Class.privateGetDeclaredFields(Class.java:2930)
        at java.base/java.lang.Class.getDeclaredFields(Class.java:2249)
... [Log Snipped] ...
        at java.base/java.lang.ClassLoader.loadClass(ClassLoader.java:490)
        ... 14 more
```

My project doesn't make use of Amazon S3 or Jboss VFS but native build try to load these classes. 

I tried to add `quarkus.native.additional-build-args=--initialize-at-run-time=org.flywaydb.core.internal.scanner.classpath.jboss.JBossVFSv3ClassPathLocationScanner\\,org.flywaydb.core.internal.resource.s3.AwsS3Resource` option but with no success.

How could i tell the native builder to ignore these optional dependencies ?

### Expected behavior

Native build must ignore these classes because VFS and S3 are not used in this project.

### Actual behavior

Native build try to load VFS and S3 related classes.

Discussion
- @zakkak I don't see why this would be happening as we have `ClassPathScannerSubstitutions`
- @geoand I see `org.jboss.vfs.VirtualFileFilter` being reached through [URL] which is being registered for reflection:

```
  {
    "allDeclaredClasses": true,
    "allDeclaredConstructors": true,
    "name": "org.flywaydb.core.internal.scanner.classpath.jboss.JBossVFSv3ClassPathLocationScanner",
    "allDeclaredMethods": true,
    "allDeclaredFields": true
  },
```

Passing `-Dquarkus.native.include-reasons-in-config-files` to the build I see that the "reason" it is being registered is:

```
      "PicocliNativeImageProcessor > fr.mipih.dumpbo.SubCommand > org.flywaydb.core.Flyway > org.flywaydb.core.FlywayExecutor > org.flywaydb.core.internal.scanner.LocationScannerCache > java.util.Map > org.flywaydb.core.internal.scanner.classpath.ClassPathLocationScanner"
```

Similarly for `org.flywaydb.core.internal.resource.s3.AwsS3Resource` which leads to `software.amazon.awssdk.awscore.exception.AwsServiceException`:

```
      "PicocliNativeImageProcessor > fr.mipih.dumpbo.SubCommand > org.flywaydb.core.Flyway > org.flywaydb.core.api.configuration.ClassicConfiguration > org.flywaydb.core.api.ResourceProvider > java.util.HashMap > org.flywaydb.core.api.resource.LoadableResource"
```

Which indicates that the class is being registered for reflection [Link: by the picocli extension] through the class hierarchy of `fr.mipih.dumpbo.SubCommand`. And more specifically by registering `org.flywaydb.core.internal.scanner.classpath.ClassPathLocationScanner` implementers in [URL]

It looks like this could be fixed by:
1. augmenting [URL] but I can't tell if that's the right thing to do.
2. Removing `JBossVFSv3ClassPathLocationScanner` (and `AwsS3Resource`?) from the classpath when not needed.
