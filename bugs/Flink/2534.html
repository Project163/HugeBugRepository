Title

Processing-time timers fire too early

Description
The firing of processing-time timers is off by one. This leads to problems in edge cases, as discovered  here (mailing list)  when elements arrive at the timestamp that is the end of the window. 

 The problem is  here (github) . For event-time, we fire timers when the watermark is >= the timestamp, this is correct because a watermark T says that we will not see elements with a timestamp smaller or equal to T. For processing time, a time of T does not say that we won't see an element with timestamp T, which makes processing-time timers fire one ms too early. 

 I think we can fix it by turning that  <=  into a  < .
Discussion
- We can fix this at one of two places: 
 
	  SystemProcessingTimeService  service, by moving firing of timers back by 1 ms 
	  HeapInternalTimerService , which uses  SystemProcessingTimeService  but is one level higher in the layer of abstractions
- On a side note: even if we change this off-by-one bug, I think there can still be races because current processing time is queried using System.currentTimeMillis() and we set timers using a ScheduledThreadPoolExecutor (currently). If there's any race between those two you can also get weird results. 

 For these reasons, I would always suggest to go with event time or ingestion time, but I think the latter is currently not possible with the Table API/SQL.
