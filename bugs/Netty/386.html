Title

PendingWriteQueue.recycle() triggers channelWritabilityChanged() without updating its state

Description
`PendingWriteQueue.recycle()` updates its data structure _after_ triggering a `channelWritabilityChanged()` event.  It causes a rare corruption such as double free when `channelWritabilityChanged()` method accesses the `PendingWriteQueue`.
Discussion
- fixes this problem, but it still leaves another issue that can cause data corruption in a complicated handler such as `SslHandler`.

When `SslHandler` and `ChunkedWriteHandler` exists in a pipeline together, it is possible that `ChunkedWriteHandler.channelWritabilityChanged()` invokes `SslHandler.flush()` and vice versa. Because they can feed each other (i.e. `ChunkedWriteHandler.channelWritabilityChanged()` -> `SslHandler.flush()` -> `ChunkedWriteHandler.channelWritabilityChanged()` -> ..), they can fall into an inconsistent state due to reentrance (e.g. bad MAC record at the remote peer due to incorrect ordering.)

We could work around this specific issue by adding some protection to `SslHandler`, but the better approach is probably making `PendingWriteQueue` trigger `channelWritabilityChanged()` via `Executor.execute()`.

Actually, `channelWritabilityChanged()` is triggered by `ChannelOutboundBuffer`, and thus this guarantees some change there, too.
