Title

Persistent Settings Takes Effect After RecoverStateUpdateTask's Reroute

Description
RecoverStateUpdateTask execute Reroute before persistent settings takes effect, this may cause the logic about `AllocationService#reroute`  execute in an unexpected way.
`    class RecoverStateUpdateTask extends ClusterStateUpdateTask {

        @Override
        public ClusterState execute(final ClusterState currentState) {
            if (currentState.blocks().hasGlobalBlock(STATE_NOT_RECOVERED_BLOCK) == false) {
                logger.debug("cluster is already recovered");
                return currentState;
            }

            final ClusterState newState = Function. identity()
                .andThen(ClusterStateUpdaters::updateRoutingTable)
                .andThen(ClusterStateUpdaters::removeStateNotRecoveredBlock)
                .apply(currentState);

            return allocationService.reroute(newState, "state recovered");
        }
       ....
`
The place where the persistent settings is applied in master is after clusterstate publish .
Discussion
- We want to  move `allocationService.reroute(newState, "state recovered")` to callback method  `RecoverStateUpdateTask#clusterStateProcessed`,and in it we can  submit a `ClusterStateUpdateTask` that execute `allocationService.reroute(currentState, "state recovered")`
- I'm not sure I understand the impact of this: the task in question doesn't change any cluster settings so the latest persistent settings should all be applied already. Could you share some more details of which settings this affects and what the unexpected behaviour is? Maybe open a PR with a test that shows the problem?
