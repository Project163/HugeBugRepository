Title

[DocDB] Potential duplicate WRITE_OP due to split and WriteRPC timeout interference

Description
Jira Link: [Link: DB-3505]
### Description

Scenario for the potential issue:
1. Parent tablet leader received `WriteRpc` 1 and added `WRITE_OP` 1 to the WAL. But `YBClient` didn’t get the response.
2. Parent tablet got `SPLIT_OP` and added it to the WAL.
3. YBClient is retrying `WriteRpc` 1 to the parent tablet leader and getting error that tablet started split (or already split).
4. YBClient is preparing new `WriteRpc` 2 to retry the same YBOperation to the child tablet and sends it to the child tablet.
5. Child tablet leader applies `WRITE_OP` 2 caused by the same user request as `WRITE_OP` 1.

We need to implement a unit-test and then fix it. ~~Idea for fix - make tablet leader first checking for duplicate request and only after that for whether it started split. Then at step 3 parent tablet leader will reject `WriteRpc` 1 as a duplicate and `YBClient` will not retry it to the child tablet.~~

UPDATE: Consider reusing the same request_id for splitting-related retries (we would need to keep filling retryable requests for child tablets).
