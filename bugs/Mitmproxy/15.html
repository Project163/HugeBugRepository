Title

handle_sni crashes the Python Interpreter

Description
There's some weird SSL behaviour, which can be triggered by running mitmproxy with

```
mitmdump --cert cert.pem
```

[Link: cert.pem] (self-signed CA cert + leaf including privkey)

For some reason, this triggers a 

```
`('SSL routines', 'SSL3_GET_CLIENT_HELLO', 'no shared cipher')`
```

in [Link: server.py#L195]. What's even more weird is that `handle_sni` is called a second time when the server conn has already been cleaned up ([Link: server.py#L96]). The python interpreter crashes when the first call to `handle_sni` updates the context ([Link: server.py#L275]). If we remove `connection.set_context(new_context)`, we get a traceback at least, but that doesn't really explain why it's called twice in the first place.

- I think I found the reason for the second `handle_sni` call in the following log:
[URL]
When the handshake fails, we run `netlib.tcp._Connection.close`, which tries to read all pending data from the connection, to make sure that no TCP RST is sent ([Link: tcp.py#L240]).

This calls OpenSSL's SSL_read, which apparently thinks "oh, an uninitialized SSL connection!" and tries to negotiate a session. m(

Maybe it's sufficient if we just read all pending data on unencrypted connections. Will need to investigate that.
