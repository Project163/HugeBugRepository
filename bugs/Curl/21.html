Title

Unable to connect to unix socket of Linux's abstract namespace

Description
### I did this

```
$ netstat -l 
[root@Foo:/]# netstat -l
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address           Foreign Address         State
Active UNIX domain sockets (only servers)
... [Log Snipped] ...

$ curl --unix-socket @/tmp/test.sock http:/api/version
```
### I expected the following

`0.0.1`
Instead, I got `curl: (7) Couldn't connect to server`
### curl/libcurl version

```
7.49.1
```

[curl -V output perhaps?]

```
curl 7.49.1 (arm-broadcom-linux-gnueabi) libcurl/7.49.1 zlib/1.2.8
Protocols: dict file ftp gopher http imap pop3 rtsp smtp telnet tftp
Features: IPv6 Largefile libz UnixSockets
```
### operating system

Linux 3.10.100 (ARCH=arm)
Discussion
- The domain socket path is probably incorrectly specified to curl, as it is only shown with that `@` character in the netstat output. Maybe `-v` helps to figure that out.

Also, your specified URL doesn't look like a valid URL as it doesn't have two slashes after the `http:`.
- I think the '@' sign is just a way netstat chose to denote it is in abstract socket namespace, because they begin with a NULL character which cannot be displayed.
Technically, perhaps the curl tool could support the same notation (and change to NULL).
- ... [Middle Discussions Snipped for Brevity] ...
- @bagder I like the first idea, though perhaps CURLOPT_UNIX_SOCKET_URL would be more descriptive.

I'm trying to implement it, but came across another issue with unix socket. It looks like we don't distinguish between unix sockets and regular ones when reusing a connection and might reuse incorrectly IMO. I've also looked at the initial commit introducing unix domain sockets (https://github.com/curl/curl/commit/ ).

So I've tested it with the 'socat' command above:
socat UNIX-LISTEN:/tmp/foo.sock TCP:localhost:80
Then if I run:
curl -v --unix-socket /tmp/foo.sock [URL] --next [URL]
I can see that the unix connection is reused, same happens with libcurl if set CURLOPT_UNIX_SOCKET_PATH to null or call curl_easy_reset() just before reusing the easy handle (it reuses the unix connection).

I've made a patch for this problem, which fixes my libcurl tests but not the '--next' example.
I think though, this should be fixed in the '--next' logic to have it invoke curl_easy_reset (judging by their manual pages, this should be ok).
My patch can be found at: [URL]

Note, the fix is not complete yet as it lacks freeing of 'conn->unix_domain_socket' in the reuse_conn() call, but I'm thinking to refactor it so that reuse_conn() would not bother with freeing stuff but instead call conn_free() right afterwards.

Thoughts?
- I think I found one more justification for the refactoring of reuse_conn() as suggested above.
The 'conn->oauth_bearer' is allocated in create_conn() before ConnectionExists(), but it is only freed in conn_free(), so it may leak if we decide to reuse another connection instead of the 'needle'.
