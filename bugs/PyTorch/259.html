Title

Nesting torch.cuda.use_mem_pool() context managers results in the second pool not getting any allocations.

Description
### 🐛 Describe the bug

This fails today on main:

```
python
import torch

pool1 = torch.cuda.MemPool()
pool2 = torch.cuda.MemPool()
... [Log Snipped] ...
assert len(pool1_segments) == 1
assert len(pool2_segments) == 1 # this fails. Both data1 and data2 get allocated to pool1, but we would expect data2 to get allocated to pool2
```

Most users would normally expect that data2 would be allocated into pool2, but that doesn't happen.

Here is a quick fix, which helps elucidate the problem:

```
modified   c10/cuda/CUDACachingAllocator.cpp
@@ -2233,7 +2227,8 @@ class DeviceCachingAllocator {
           it2->first != mempool_id,
           "beginAllocateToPool: already recording to mempool_id");
     }
... [Log Snipped] ...
 
   // Called by CUDAGraph::capture_end
```

The issue is that the filter method used, which simply checks the thread ID can return true for multiple different pools:

[URL]

Note that it wasn't possible for two separate private pools to have a filter return true previously, back when this infrastructure was used only for cuda stream capture to a cuda graph. So I think it is basically just an oversight.

An obvious way to fix the issue is to enforce a LIFO order on the order in which filters are evaluated, which my above patch does, albeit in an inefficient way. Simply iterating over captures_underway from back to front in all the appropriate places would also fix the problem, which is what I would do for a proper fix, so we don't have O(N) insertion.

### Context

I encountered this bug while adding support for memory pools to the CachingHostAllocator (which is necessary for doing stream capture of code that allocates pinned memory; I started that here [URL] but realized multiple issues and that PR is now very out of date).

I don't think anyone is nesting memory pools right now, but I think it is very very conceivable that people like me will do that in the future.
