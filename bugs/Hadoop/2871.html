- This is vaguely familiar. I think we hit it with one of the other stores.  

 The fs declares itself as closed before the processing takes place, so API calls get rejected. I would blame mockito, somehow, I but I am not sure it is at fault. 

 The Fix here is to do what has been discussed before: do a better cleanup routine for S3A. 

 
	 parallelise the delete 
	 skip existence checks 
	 call the innerDelete method so the fs openness check is skipped. 
 

 I'm not working on this, as the feature is mostly used in testing, it doesn't seem that critical.  
But: it is also part of the error handling in the hadoop fs shell commands, so it may surface in production.
- Thanks  stevel@apache.org . Yeah, your analysis is right, S3A fs declares itself as closed before processing of deleteOnExit happens. The mockito is not the cause, it is just used to demo the issue as I was developing a unittest to show the issue.  

 Could you let me know which store hit this issue before? I want to see how it was handled in other stores. Right now, the fix I am proposing is as follows (i.e, processDeleteOnExit before isClosed set to true in S3A). I will also take a look at other stores' processing as well.
