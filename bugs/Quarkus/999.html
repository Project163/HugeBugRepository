Title

Vert.x Routes Wrong Behaviour when using hyphens (-) in params

Description
**Describe the bug**
When using a route with param names that includes hyphen characters:

```java
@Route(methods = HttpMethod.GET, path = "/path/:my-param")
boolean myRoute(@Param("my-param") String param) {
    return true;
}
```

If we call our route, we will get a HTTP 404 Not Found error. 

Now, if we change our route to get rid of hyphens:

```java
@Route(methods = HttpMethod.GET, path = "/path/:myParam")
boolean myRoute(@Param("myParam") String param) {
    return true;
}
```

Everything works fine now.

**Expected behavior**
If there is a strong technical reason to not support hyphens, this should be documented. However, I think it should be supported. And for sure, not return HTTP Not Found 404 status.

**Actual behavior**
It returns HTTP Not Found 404 status.

**Environment (please complete the following information):**
 - Quarkus version or git rev: 1.12.0.Final
Discussion
- FWIW, this works as expected with RESTEasy Reactive (I just checked as I was curious)
- It seems that a dash (`-`) may not be used in a [Link: path parameter name]: _"The placeholders consist of : followed by the parameter name. Parameter names consist of any alphabetic character, numeric character or underscore."_

Unfortunately, Vertx Web does not seem to validate the path at all. I think that we should add a least a quarkus-specific validation for `@Param`...
- ... [Middle Discussions Snipped for Brevity] ...
- Hi @pmlopes, I wonder if it would be possible to verify the path parameter during registration? It seems that the route is currently just ignored.
- @mkouba Validation is now present on the PR too. However, the PR is now different. By default, the naming rules are as described on the documentation of vert.x web (alphanumeric characters and underscore). If a system property is set:

```
-Dio.vertx.web.route.param.extended-pattern=true
```

Then the rule is extended to allow `-` and `$`. The reason for this choice is as follows, imagine that you had designed an API as:

```
Route path: /flights/:from-:to
Request URL: [URL]
ctx.params: { "from": "LAX", "to": "SFO" }
```

If the pattern switch would happen now it would mean we just introduced a breaking change for all users of vert.x + downstream users.

Regarding validation, if the "normal" pattern is in place validation on the route path above *will* pass as the 2 variables will be found as `from` and `to`. However, with the extended mode, the validation will also pass as the there are 2 variables but this time with sligthly different names: `from-` and `to`. (note the dash).

It is common to use `/` to split variables, but that is just a common practice and never a requirement from vert.x as the goal was to be non-opinionated.

With this flag, we can switch between "normal" and "extended" modes, so I think this is a good middle ground that will not break backwards compatibility and ensure that the upcoming quarkus 2.0 uses the desired "extended" behavior.
