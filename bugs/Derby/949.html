Discussion
- My guess is that the intermittent locks being reported are actually internal background process 
locks.  Just prior to this diff a delete and commit has been executed, so it is quite possible 
the post commit thread is running async to the user thread. 

 This test should be changed to only query  user locks.  For an example see the lock 
queries used in the tests in the store test directory: 
opensource/java/testing/org/apache/derbyTesting/functionTests/tests/store/LockTableQuery.subsql , it uses a view to just query the user thread locks: 
create view lock_table as 
select 
    cast(username as char(8)) as username, 
    cast(t.type as char(8)) as trantype, 
    cast(l.type as char(8)) as type, 
    cast(lockcount as char(3)) as cnt, 
    mode, 
    cast(tablename as char(12)) as tabname, 
    cast(lockname as char(10)) as lockname, 
    state, 
    status 
from 
    syscs_diag.lock_table l  right outer join syscs_diag.transaction_table t 
on l.xid = t.xid where l.tableType <> 'S' and t.type='UserTransaction'; 
--on l.xid = t.xid where l.tableType <> 'S' or l.tableType is null 
– order by 
–     tabname, type desc, mode, cnt, lockname
