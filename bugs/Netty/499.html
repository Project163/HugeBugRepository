Title

ByteToMessageDecoder have to watch out for empty buffers

Description
Netty version: 4.0.31

Context:
Unexpected behavior when implementing a `ByteToMessageDecoder`. Following up in issue #4087.

The Javadoc of `ByteToMessageDecoder` urges the implementer to let another filter handle the actual frame detection, so that the implementation of `ByteToMessageDecoder` can focus on decode the content of the frame. Which is a good idea.

However will the `decode` method always be called when the channel is closed, even if there is no remaining data. This seems illogical (to me) since the prepended `LengthFieldBasedFrameDecoder` has the task of not pushing through data in your chain which does not have a full frame (other decoders like `LengthFieldBasedFrameDecoder`do the same).

So in the end implementations of `ByteToMessageDecoder` and `ByteToMessageDecoder` (since issue #4087 is fixed) do need to check for the received buffer size before being able to decode.

Steps to reproduce:
1. Implement a `ByteToMessageDecoder`
2. Add a `LengthFieldBasedFrameDecoder` and your `ByteToMessageDecoder` implementation to the chain
3. Close the connection
4. `decode` gets called with an empty buffer

- `decodeLast()` is called to give a decoder a chance to perform the last task like creating a new message from a cumulation buffer or releasing resources.

`decodeLast()` is a sort of `finally` block, so it must be invoked regardless if the cumulation buffer is empty or not.

The default behavior of `decodeLast()` is currently to delegate to `decode()` and thus it will drive `decode()` into the situation where it has to handle an empty buffer like @ctron and @alexstaytuned mentioned.

Assuming that `decode()` is not a place to perform a clean-up task but `decodeLast()` is, I think `decodeLast()` should not call `decode()` if the buffer is empty.

What do you think, @normanmaurer ?
