Title

Weird interaction between expand_location and alias

Description
I'm seeing a very bizarre error when using `expand_location` and `alias` together. Here's a minimalish reproducer:

[URL]
(I just plopped those three files and nothing else into a scratch directory in `/tmp`)

Here's what happens when I attempt to build:
```
/private/tmp/blub$ bazel build //...
ERROR: /private/tmp/blub/BUILD:8:1: in sad rule //:oh_noes:
Traceback (most recent call last):
	File "/private/tmp/blub/BUILD", line 8
		sad(name = 'oh_noes')
... [Log Snipped] ...
expected type 'Target' for 'targets' element but got type 'Target' instead.
ERROR: Analysis of target '//:oh_noes' failed; build aborted.
```

Certainly the error message is a bug—it makes no sense. I suspect the underlying incompatibility is also a bug, but I'm very new to Bazel and could just be misunderstanding something

### Environment info
`release 0.5.2-homebrew` (also saw it with `0.4.5`) on OS X 10.12.5

###  Have you found anything relevant by searching the web?
No (I googled for variants of `expand_location alias`)
Discussion
- The specific error is that `alias()` rules create an instance of [Link: AliasConfiguredTarget], but `expand_location` requires instances to be [Link: AbstractConfiguredTarget] instances.

This error message is confusing, because both AbstractConfiguredTarget and AliasConfiguredTarget implement [Link: TransitiveInfoCollection], which declares that its name is "Target".

The fix is probably for AliasConfiguredTarget to extend AbstractConfiguredTarget, or for expand_location to relax what it's willing to work with.
