Title

## JWT realm bug

The JWT realm supports rotation of the keys that can validate the signature of the JWT used for authentication. The general strategy for rotation is upon failure to validate the signature, then the key material (JWKs) will be reloaded automatically, if there are any changes to the key material then the cache is evicted and the signature validation will be attempted again. Of note, the reload only holds up the second authentication attempt (blocking for file based reloads, async call back for http) on the single thread that triggered the reload and other threads can still be attempting (and succeeding) with authentication. Upon successful authentication we add to the cache.

We end up in situation where we can concurrently (across different threads) call Cache#put(k,v) (T#1) and Cache#invalidateAll() (T#20) on the same cache instance at the same time.  If you use a frequent rotation strategy with frequent calls that use the JWT realm can increase the likelyhood of those two method happening concurrently. These are the two calls that end up deadl

To put it another way:
```
T#1  put(k,v)        -> lock lru -> lock swl -> unlock swl -> unlock lru
T#20 invalidateAll() -> lock swl -> lock lru -> unlock lru -> unlock swl
```
So the sequence of events for a dead lock must be 

1) T#1 grabs the lru lock
2) T#20 grabs segment write lock
3) T#1 tries to grab the segment write lock but is blocked by T#20
4) T#20 tries to grab the lru lock but is blocked by T#1

or some variant of that. The important bit is that put(k,v) and invalidateAll() must be happening at the same time across different threads and the attempts to grab the different 2 locks must be intertwined between the 2 different threads. 

Fixing this could be challenging and I have not explored if there other potential cases this deadlock could occur.

I think the use of [Link: CacheHelper] was not trying to make `put` and `invalidateAll` mutually exclusive. It was itself a mis-use for a scenario that it does not apply.
