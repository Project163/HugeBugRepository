Title

linux-sandbox didn't config /proc/sys/net/ipv4/ping_group_range, leads IPPROTO_ICMP not usable inside network namespace

Description
### Description of the bug:

I found my code which create socket with IPPROTO_ICMP 
```
C
#include  
#include  
#include  
int main() {
... [Log Snipped] ...
  }
}
```
can't run under linux-sandbox, without tags requires-network.
 if test has no requires-network tag, linux-sandbox will create network namespace,
but sys config /proc/sys/net/ipv4/ping_group_range which controls the usability of IPPROTO_ICMP,
will be reset to default "forbidden all" value (see [URL] and [URL] so after enter linux-sandbox,
testcase won't be able to use IPPROTO_ICMP to create socket.
this can be resolved when fakeroot is used and write valid gid "0 0 " to /proc/sys/net/ipv4/ping_group_range.

Discussion
- A PR sounds reasonable to me, would it work if you used the `gid` set in `SetupUserNamespace` [URL] and set `ping_group_range` to `0  `?
- I've tried it and it won't work (https://github.com/opencontainers/runc/discussions/4366)

both value of ping_group_range, must be valid gid in the namespace, if any one of them is not, then kernel will reject changes and write fail (https://discuss.linuxcontainers.org/t/setting-net-ipv4-ping-group-range-inside-an-lxd-container/2162/4), 
  bazel use unpriviledged namespace, it can only have 1 gid mapped, thus both values must be inner_gid.  write to this file requires root permission, so it's impossible to write values other than 0 0 .  so in conclusion, this can only works under fakeroot  (seems a bug of kernel to me, too restrict on IPPROTO_ICMP, or default config inconsistent between sysctl and unpriviledged namespace),
