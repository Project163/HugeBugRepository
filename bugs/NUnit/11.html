Title

Changes to Tolerance definitions

Description
Quoting Rob from a discussion on nunit-discuss...

"I think that Tolerance.Empty is probably misnamed and should be something like Tolerance.Default, but it is probably too late for that change. We should at least fix the documentation which is misleading as it says "equivalent to specifying an exact match." It is also misleading that ToleranceMode.None uses default linear values if the amount is 0, but ToleranceMode.Linear with an amount of 0 means no tolerance.

"I think we should add a new static factory on Tolerance, Tolerance.None which doesn't use the defaults. I don't know if we need another ToleranceMode since Linear already does what we want, it might be that we just need to improve the documentation."

Beyond that, I'd say we need to do some tests to see if we need another tolerance mode. That's because Tolerance(0) is really only compatible with numerics, but we allow use of tolerance for DateTimes and TimeSpans. Some experimentation will show if another mode, where we don't try to do any subtraction before comparing, would make life easier.
Discussion
- I had thought that I couldn't change Tolerance.Empty to a better named property like Default because it would be a breaking change, but looking at the code, it appears that even though it is public, it wouldn't normally be used by people using NUnit. The tolerance is normally created internally through the Within() method or by passing in the delta to AreEqual().

Technically, people could write code using it, but I think it is unlikely. Therefore, I am going to change Tolerance.Empty to Tolerance.Default and add a new Tolerance.None.
