Title

Reading from partitioned bucketed tables has high overhead in MapOperator.cleanUpInputFileChangedOp

Description
Reading from bucketed partitioned tables has significantly higher overhead compared to non-bucketed non-partitioned files. 

 50% of the profile is spent in MapOperator.cleanUpInputFileChangedOp 

 5% the CPU in  
  
  Path onepath = normalizePath(onefile);
 
  

 And  
45% the CPU in  
  
  onepath.toUri().relativize(fpath.toUri()).equals(fpath.toUri());

- Traced it down to 

  
   @Override
   public   boolean  pushRecord()  throws  HiveException {
    execContext.resetRow(); <-- resets input checks
 
  

 This is why the cleanup input is being called once per row.
- Worse, I printed out the identity hashcode of the ExecMapperContext there. 

  
 resetRow: (1043064988)  null  update to  null 
isInputChanged: (773110290)  null  != hdfs: //sandbox03.hortonworks.com:8020/user/hive/external/tpch-100/region/data-m-00099.snappy 
 
  

 Looks like the resetRow and isInputChanged are going to different objects, which is obviously broken. 

 There's a good possibility IOContext doesn't work correctly when the reader threads are running parallel with the processor threads.
