Discussion
- I reviewed PR#5798 and the changes seem reasonable. One question though is why do we refer to the virtual columns when lateral views are involved?  

  
 CBO PLAN:
HiveProject(id=[$0], arr=[$1], name=[$8], name1=[$9])
  HiveTableFunctionScan(invocation=[LATERAL(explode($1), $0, $1, $2, $3, $4, $5, $6, $7, $8)], rowType=[RecordType(INTEGER id, VARCHAR(2147483647) ARRAY arr, INTEGER PARTITION__SPEC__ID, BIGINT PARTITION__HASH, VARCHAR(2147483647) FILE__PATH, BIGINT ROW__POSITION, VARCHAR(2147483647) PARTITION__PROJECTION, BIGINT SNAPSHOT__ID, VARCHAR(2147483647) tbl1.name, VARCHAR(2147483647) tbl2.name1)])

      HiveTableFunctionScan(invocation=[LATERAL(explode($1), $0, $1, $2, $3, $4, $5, $6, $7)], rowType=[RecordType(INTEGER id, VARCHAR(2147483647) ARRAY arr, INTEGER PARTITION__SPEC__ID, BIGINT PARTITION__HASH, VARCHAR(2147483647) FILE__PATH, BIGINT ROW__POSITION, VARCHAR(2147483647) PARTITION__PROJECTION, BIGINT SNAPSHOT__ID, VARCHAR(2147483647) tbl1.name)])
        HiveTableScan(table=[[default, test]], table:alias=[test]) 
 
  

 Even after removing non-existent columns such as  BLOCK_OFFSETINSIDE_FILE  the plan still contains technical columns like  PARTITION_ PROJECTION ,  SNAPSHOT _ID , etc. I think that these technical columns should not be introduced in the first place. Anyways removing "redundant" columns is more like an optimization that we can possibly leave as a follow-up patch if it makes sense.
- Another point to note is that virtual columns 
  
  
 BLOCK__OFFSET__INSIDE__FILE 
INPUT__FILE__NAME 
ROW__OFFSET__INSIDE__BLOCK
ROW__ID
ROW__IS__DELETED     
  
   
were getting added to other non native tables (HBase, Kudu). 

 After this patch is merged these columns will not be present anymore which, I think, is the correct behavior.
- soumyakanti.das  Please check if it was possible to query the aforementioned virtual columns for HBase and Kudu tables before the changes in PR#5798. In case the query wasn't failing with an error check also the returned results.
