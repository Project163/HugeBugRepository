- It seems one of the playlistUrl was null.

@christosts @AquilesCanta any idea where this could come from? Additionally, in order for the exception to be raised early, maybe `HlsChunkSource` should check that all url are non null and make a defensive copy of the array.
- We inspected the code and saw there is a case where this may happen: if the playlist has a subtitles track but it does not include a URI for the subtitles. This would be in violation of the HLS spec, but the player at the moment does not raise an exception immediately. As a result, a null value may be inserted in the `playlistUrls`  array. We are going to fix this and it will be available to the dev-v2 branch in the coming days. The fix would make the player fail fast and make this error more obvious. 

Our hypothesis of what is probably happening: the playlist does not have a URI for subtitles but the player does not raise a parse exception, therefore it contains the null element in the array. This is not causing an error immediately because subtitles are not displayed, then later a possibly unrelated error triggers the onLoadError() event (HTTP 404 maybe?) which eventually raises the NPE.

We should try to verify this is indeed the case causing the error at hand. @stari4ek is it possible provide any playlist samples that have caused this? You did mention that it's not possible, but I'm asking in case something has changed since the issue was filed. Or, in case you have found reproduction steps in your app, will you be able to test locally on your app after we commit the fix?
- Yeah, it could be provoked by network/loader error. Some of reports have

But this error happens with the same service, so it's very possible that this is media issue.

While pro-active reaction to HLS spec violation sounds as proper implementation, it makes ExoPlayer less steady and friendly to media already floating around (especially comparing to non-ExoPlayer based players). Any chances to ignore invalid tracks? Mark them unsupported?
From user perspective since it's subtitles track - loosing playback for such media is bigger harm than loosing track itself.
- Hi, commit [Link: 8da4eaa] ignores subtitles that do not have a URI, but does not raise an exception in order to maintain playback. This is in the dev-v2 branch at the moment and will be available on a next release. 

Closing the issue, feel free to re-open if the fix did not address the issue, or there are any other questions.
