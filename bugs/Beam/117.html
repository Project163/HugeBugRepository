Discussion
- Side note: we should treat checksums as a shortcut for a quick positive match. When they fail to match, the full diff should then be computed and dumped, so the error is actionable. I recent saw a message like like "checksum <x> was not <y>" with no following information.
- Yes, it's worth having retry in file path matching and reading in order to handle IO failures from filesystem and some special cases like no file is found.   

 As for example2, one place to add sharding name template is the ouputpath argument passing to FileChecksumMatcher. Instead of using ".../result*, we can use ".../result* of *". This can avoid reading irrelevant files but can't guaranty all shards are read unless given total number of shards.  

 The current thought in my mind is passing the number of shards from command line as an optional test option, then pass it to the verifier. Not sure if we have a better way to do that. Since from previous test results, I found that the number of shards is runner dependent.
