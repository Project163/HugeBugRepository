Title

Bug in dbforge->modify_column() for PostgreSQL and null columns

Description
Maybe related to #5421

## Steps to reproduce:
1. Create a table with a nullable column and fill it with some null values.
2. Create a migration to change the name of the nullable column and run it.

Example migration up:
```
$fields = array(
        'example_field' => array(
		'name' => 'example_field_new',
		'null' => TRUE
	),
 );
$this->dbforge->modify_column('example_table', $fields);
```
## Bug
Digging in the code I found that the condition on this line is always `FALSE`:
[URL]

The reason for this is that this line sets the 'null' property to a string, breaking the previous condition:
[URL]

This leads to a situation in column modification will trigger a `SET NOT NULL` in all cases, and it doesn't matter if the `null` attribute is set to `TRUE`. I bet this only happens in PostgreSQL because of the syntax.

## Workaround
1. Load your database in __construct()
```
$this->db = $this->load->database('default', TRUE);
```
2. Run a raw query in up() and another in down()
```
$this->db->query('ALTER TABLE "example_table" RENAME COLUMN "example_field" TO "example_field_new"');
```
Discussion
- Can you please verify that the fix patch is working correctly?
- It works only in the case ```'null' => TRUE``` is specified, which simplifies the workaround.

I think it is still not ideal, as the documentation won't warn you about having to specify null even if the field was already nullable.

In my opinion this fix is good but at some point these migrations should not trigger any change regarding nullable status if the developer doesn't make it explicit.
