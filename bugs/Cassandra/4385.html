Discussion
- The assertion is due to the code in  DataResolver  mistakenly assuming a marker is open when it may not. But this is actually a manifestation of a larger problem, which is that the code in  DataResolver  dealing with range tombstone is incorrect (it doesn't compute read-repair correctly). In fact, the  MergeListener  interface that it uses isn't providing enough information for it to do its job properly. Attaching a patch that solves that, including a new unit test that both reproduce the assertion of this ticket, but also shows the code wasn't doing what it should have in the first place.
