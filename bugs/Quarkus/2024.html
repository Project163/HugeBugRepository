Title

Container debug option not work with base image registry.access.redhat.com/ubi8/openjdk-17:1.17

Description
### Describe the bug

After updating the base image in Dockerfile to latest certified version registry.access.redhat.com/ubi8/openjdk-17:1.1**7**, the debug option for quarkus can no longer be activated.

With base image version registry.access.redhat.com/ubi8/openjdk-17:1.1**6**, the debug option works.


### Expected behavior

```
$ docker run -it --rm -e JAVA_DEBUG=true quarkus/code-with-quarkus-jvm

INFO exec -a "java" java -Dquarkus.http.host=  -Djava.util.logging.manager=org.jboss.logmanager.LogManager -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005 -XX:MaxRAMPercentage=50.0 -XX:+UseParallelGC -XX:MinHeapFreeRatio=10 -XX:MaxHeapFreeRatio=20 -XX:GCTimeRatio=4 -XX:AdaptiveSizePolicyWeight=90 -XX:+ExitOnOutOfMemoryError -cp "." -jar /deployments/quarkus-run.jar 
Listening for transport dt_socket at address: 5005
INFO running in /deployments
```

### Actual behavior

```
$ docker run -it --rm -e JAVA_DEBUG=true quarkus/code-with-quarkus-jvm

INFO exec -a "java" java -Dquarkus.http.host=  -Djava.util.logging.manager=org.jboss.logmanager.LogManager -cp "." -jar /deployments/quarkus-run.jar 
INFO running in /deployments
```

Discussion
- I haven't reproduced this (yet), but I think I know what the problem is. In the getting-started quickstart, there is this [URL]

    JAVA_OPTIONS=-Dquarkus.http.host= 

The original OpenJDK container behaviour of `JAVA_OPTIONS` was to have *only* user-provided JVM tuning parameters, and not script-provided. I.e.  if you define `JAVA_OPTIONS`, any JVM options  generated by the run script are ignored. To instead append to the script-generated JVM options, we added `JAVA_OPTS_APPEND`.

This behaviour broke at some point a long time ago, such that `JAVA_OPTIONS` overrode *some* of the run script-generated options, but not all -- notably, not the ones enabled by setting `JAVA_DEBUG`. And I think this (broken) behaviour has been in place for the whole lifetime of Quarkus.

In the latest version of the UBI8-based images, 1.17, we fixed this regression, so that `JAVA_OPTIONS` completely replaces the JVM generated options.

(Separately, `JAVA_OPTIONS` was deprecated and replaced by `JAVA_OPTS` (I've no idea why), but remained functional in the UBI8 images. (only `JAVA_OPTS` is supported in the UBI9 images.))

So: if you want to append to the script's options, use `JAVA_OPTS_APPEND`; if you want to replace them, use `JAVA_OPTS`.

Is it possible that a file like `.s2i/environment` is put in a new quarkus project skeleton by the new project generator?

(A related quick note about the .s2i/environment file in the getting-started quickstart. Recent version of the OpenJDK container, both ubi8 and ubi9, should auto-detect the correct paths for quarkus fast-jar and uber-jar build layouts, so MAVEN_S2I_ARTIFACT_DIRS, S2I_SOURCE_DEPLOYMENTS_FILTER, and JAVA_APP_JAR are not necessary. I guess you still want `-Dquarkus.http.host= ` so I would suggest defining `JAVA_OPTS_APPEND`.  `AB_JOLOKIA_OFF` is only necessary for UBI8-based images JDK versions 8 or 11: all JDK17 and all UBI9-based images have dropped Jolokia.)
- I created the reproducer project with click on "START CODING" on [URL] and click on "Generate your application".  The generated project archive doesn't contain a file .s2i/environment.
