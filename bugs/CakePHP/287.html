Title

The MySQL dbo should check if the delete query has deleted anything

Description
Created by **Joan Coll Cerdán**, 11th Mar 2011. _(originally [Link: Lighthouse ticket #1584])_:

---
#### What I did

Imagine I have two models, User and Post:
- Post belongsTo User
- User hasMany Post

For whatever reason, Post is related with User with the parameter 'type' => 'inner'.
I delete a User with $cascade = false, and some time later I delete one of his Posts.
#### What happened

When deleting the Post:
- $this->Post->delete() returns True, but nothing was deleted because of the INNER join.
- PHP throws a Notice "Undefined index: Post [CORE\cake\libs\model\model.php, line 1477]"
#### What I expected to happen

$this->Post->delete() to return False and no PHP notice :)

---

Database data integrity aside I think that, upon deletion, either the function mysql_affected_rows() should be used to verify if anything was deleted or use a second $this->exists() to determine if it really was deleted from database. That way Model->updateCounterCache() won't be called unnecessarily and cause the PHP notice.
Discussion
- 26th Jul 2011, **[Link: Mark Story]** said:

---

One of the problems with changing DboMysql::delete() is that it could result in a behavior change and adversely effect applications.  Currently delete() returns true as long as the query ran successfully.  This means it succeeds regardless to the number of rows deleted.  Changing the behavior as requested would make delete() calls that remove 0 records appear to have failed, even though the requested data no longer exists.

I think the correct fix it to repair the notice error here, as that shouldn't ever really happen.  Changing the behavior in 1.3 seems fraught with peril as the risk of breaking existing applications is reasonably high.
- If this is still relevant, then the milestone should be changed to 2.x.
- I personally think the current behaviour is fine, as the result is that any matching rows no longer exist.
- I agree with @markstory, the current behavior is fine. the method should not return a falsey value even thought it ran successfully.
