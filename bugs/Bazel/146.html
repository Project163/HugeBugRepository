Title

Unable to build my android_binary due to IllegalArgumentException

Description
I had a problem building my Android app due to issue #1222, so when it was fixed I wanted to see if I could build again. Turns out I can't - due to another issue.

These TODD print statements come from modifying src/main/java/com/google/devtools/build/lib/pkgcache/LoadingPhaseRunner.java to print 
pkg.getPackageIdentifier() and pkg.getSourceRoot() inside collectPackageRoots()

```
TODD [@bazel_tools//src/tools/android/java/com/google/devtools/build/android][/home/tcj/.cache/bazel/_bazel_tcj/ ]
TODD [@local_jdk//][/home/tcj/.cache/bazel/_bazel_tcj/ ]
TODD [@bazel_tools//tools/jdk][/home/tcj/.cache/bazel/_bazel_tcj/ ]
TODD [external][/home/tcj/src]
TODD [@bazel_tools//third_party/java/jdk/langtools][/home/tcj/.cache/bazel/_bazel_tcj/ ]
... [Log Snipped] ...
    at com.google.devtools.build.lib.runtime.BlazeRuntime.main(BlazeRuntime.java:643)
    at com.google.devtools.build.lib.bazel.BazelMain.main(BazelMain.java:56)
```

The source of the duplication is [external] pointing to /home/tcj/src, which is really strange because my bazel root is /home/tcj/src/blaze_workspace, so why would getPackageRoot() point _outside_ it?

I hacked up collectPackageRoots to handle duplicates by using a HashMap instead of an ImmutableMap.Builder, and I can build my target successfully. Though the issue is how did the duplicate key get in the system with getPackageRoot() pointing outside my workspace?
Discussion
- /cc @kchodorow this looks related to external repositories. I feel like I have already seen that but I cannot remember how.
- Can you share what your WORKSPACE file looks like?  

The reason it's got /home/tcj/src instead of /home/tcj/src/blaze_workspace is due to some hackery shoehorning //external into being a package.  Generally, the package defined by foo/bar/BUILD finds its source root by stripping the two pieces of package name (foo/bar) off of the full directory path (/home/tcj/src/blaze_workspace/foo/bar becomes /home/tcj/src/blaze_workspace).  However, for the external package, its name "package name" is "external" and it's already rooted at /home/tcj/src/blaze_workspace, so Bazel assumes there is one path piece to strip off and removes the blaze_workspace.

- I'm going to decrease the priority of this to P2 since there is a viable workaround, but here's what I've found debugging:

Two different Package(external)s are added to the configured target's transitive packages.  One is added by resolveConfiguredTargetDependencies() and the other is added by resolveAspectDependencies, so I'm guessing that something about the aspect dependencies is not resolving //external right.
