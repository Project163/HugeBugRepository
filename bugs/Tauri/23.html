Title

Memory Leak in renderer process when regularly emitting events from Rust -> js

Description
**Describe the bug**
I've been able to replicate this issue both on Linux and Windows (Edge backend). The app I'm writing will emit an update to the renderer process using `tauri::event::emit` with updated data and I have single `listen` call on the javascript to receive the events. Over time the memory usage will slowly go up, the more events per second, the quicker it increases. I attempted mitigation by forcing updates at 15Hz rather than the 100Hz it was before but that just delays the issue. I started on Linux and couldn't determine the source of all the added memory due to lack of memory profiling tools. However, when I tried it on Windows and noticed the same behaviour, I was able to somewhat find the root of the issue using the Edge dev tools.

**To Reproduce**
Steps to reproduce the behavior:
1. Repeatedly emit events from Rust -> Js
2. Watch memory creep up

(If needed I can try whip up a basic app to demo the issue)

**Expected behavior**
Not have all my ram eaten

From what I can tell, every time an event is emitted it makes another call back to validate the salt. Each one of these creates a function handler for getting the response, but the `once` property is not being set correctly so the function handler never gets deleted after the function has been used to get the response for the salt validation

I believe [Link: here], `true` needs to be passed to the `transformCallback` function so they get properly cleaned up. I imagine that this issue effects every promisified call that happens, so this is quite severe.
