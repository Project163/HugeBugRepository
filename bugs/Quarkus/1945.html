Title

AroundInvoke Interceptors can only modify parameters if first in chain

Description
### Describe the bug

If there is a chain of interceptors applied to a method call, only the first interceptor in the chain can modify the InvocationContext parameters using setParameters. Changes made by interceptors other than the first are ignored. This occurs because the 2nd and later interceptors are passed an instance of `AroundInvokeInvocationContext.NextAroundInvokeInvocationContext` whose parameters array reference is copied from the outer `AroundInvokeInvocationContext` - but if setParameters is called, the new array is not reflected back to the outer context.

This change appears to have been made in this commit [URL]

While the comments added to this commit do suggest some limitations to the use of setParameters, in fact the actual behaviour is far more limited than suggested. This change appears to break the standard contract of `jakarta.interceptor.InvocationContext` whose comments suggest no such limitations.

This behaviour makes it effectively impossible to write an Interceptor that will work with Kotlin continuations, because in order to perform operations before the caller's continuation is resumed, we need to pass a new continuation to the callee. This requires us to be able to modify the continuation parameter in the InvocationContext, and also - if such interceptors are to be chained successfully - for interceptors further along the chain to receive the continuation set by earlier interceptors.

### Expected behavior

Changes made by InvocationContext.setParameters are reflected in both the parameters passed to the callee and to callers of InvocationContext.getParameters further down the chain.

### Actual behavior

Changes made by Invocation.setParameters only take effect if the Interceptor is the first in the chain.

Discussion
- After writing all this up, and spending the time looking at the AroundInvocationContext code, I realized there is a workaround for this that does not involve reflection - because provided `setParameters` has not been called, what `getParameters` returns is a reference to `AroundInvocationContext.this.parameters`. So instead of...

```
                val newParameters: Array  = ctxParameters.clone()
                newParameters[newParameters.size - 1] = chainedContinuation
                ctx.parameters = newParameters
```

I can write 
```ctx.parameters[ctx.parameters.size - 1] = chainedContinuation```

And everything works.

While this is a lot better than using reflection, this workaround is highly implementation dependent and I do still think this bug report stands - there needs to be a standard way of achieving this goal without knowledge of the internal implementation of InvocationContext.
