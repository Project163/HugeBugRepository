Title

yb-master can occasionally allocate lots (~100GB) of ram

Description
Despite `--memory_limit_hard_bytes 4294967296` (4 GB), Yugabyte   community edition can, during Jepsen tests involving network partitions, have a single yb-master process allocate hundreds of gigabytes of ram, eventually causing the box to run out of ram, and processes to start crashing. I don't know yet whether this was specifically triggered by a partition, but I do have a reproduction case for you, if you've got Jepsen available:

```
git checkout  
lein run test -o debian --version   --concurrency 4n -w single-key-acid --nemesis partition-half --nemesis-interval 20 --nemesis-schedule fixed --time-limit 600 --test-count 10
```

I know this isn't much to go on, but I do have a [Link: tarball] of the data files on each node. The invocation parameters for yb-master and yb-tserver are in the log directories, in files called `stdout`.
Discussion

This was running Jepsen  , with the following command:

```
lein run test-all -o debian --version  -b2 --url [URL] --concurrency 4n --time-limit 300 --test-count 3 --only-workloads-expected-to-pass -w bank
```

It's sporadic: I'm hitting memory leaks about once a day in my tests right now. This particular test involved network partitions (`--nemesis partition-half,partition-one,partition-ring`), but we've seen in earlier tests that this can happen even without any partitions, process kills, restarts, etc.
