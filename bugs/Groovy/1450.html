Title

groovy.lang.Binding is not thread-safe

Description
groovy.lang.Binding does a lazy, non thread-safe initialization of the private Map variables. Also, the LinkedHashMap itself is not thread-safe. If we use, eg,  Groovy in a webapp where there is one binding for each session, that does not mean that all access to that session is single-threaded. I suggest using 

  
  final   private  Map variables =  new  java.util.concurrent.ConcurrentHashMap()
 
  

 which is both a thread-safe initialization and a thread-safe map.
Discussion
- what is a scenario in which you have a binding per session, but no single threaded access to that per session binding?
- jochen, i was thinking of a java web application (a typical combination of servlets, jsp, portlets, whatever...) and that application also uses groovy scripts for plug-ins and extensibility. a user might log into that application and get an authenticated session (javax.servlet.http.HttpSession). now it could be useful to have one Binding per http session, so that different scripts inside that application have a common scope, as long as they are invoked for the same session. even if there is typically only one session per authenticated user, the user's browser will run many http requests in parallel resulting in parallel threads accessing the same binding. (in such a scenario, of course all objects shared between threads must be thread-safe, but that is something the application must do.) -jay
