Discussion
- So the reason for this error is that ngcc does not currently support parsing UMD/CommonJS properties of the form `exports.Xxxx`. It doesn't know how to interpret the `exports` identifier.

This is a bug in ngcc. The question is what priority we should give to fixing it.
Our experience is that UMD formats in libraries are usually not required for most use cases. Do you have concrete situations where this format is required?

As you said, if you just let the CLI do the work of running ngcc everything passes. This is because the CLI knows that your project does not need the UMD format, and just gets ngcc to process one of the other formats instead (e.g. ES2015).

By default running `ngcc` with no options will attempt to process every format of every package in node_modules. There are various ways to avoid this, such as adding the `--first-only` property or specifying a list of properties to consider (excluding `main` which maps to UMD) - e.g `-p esm2015 esm5 module browser`. Finally one can exclude the `main` property from just this package by adding a suitably configured `ngcc.config.js` file.
