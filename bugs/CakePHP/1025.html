Title

CakePHP 4.0.3: Asserting Session Variable after Request in Test Case clears $_SESSION

Description
Let me know if you need any more info from me. Possible I am missing something here, but this worked before.

___

This is a (multiple allowed):

* [x] bug
* [ ] enhancement
* [ ] feature-discussion (RFC)

* CakePHP Version: 4.0.3
* Platform and Target: Apache 2.4, Ubuntu 18.04, Microsoft SQL Server 2017

### What you did
We're trying to upgrade a Cake 3.8 application to Cake 4.0.x. Some of our test cases do the following:
```
public function testSomePostRequest()
    {
        $this->enableCsrfToken();
        $this->enableSecurityToken();
       
... [Log Snipped] ...
        $this->assertRedirect('/redirect/somehwere/else');
    }
```

### What happened
$_SESSION is getting cleared when $this->_requestSession->read() or $this->_controller->getRequest()->getSession()->read() is being called.

When I dug a little deeper, for some reason, $this->started() in Session.php is returning false, which is causing $this->start() to be executed under the first IF condition in ->read(). 

### What you expected to happen
$_SESSION should contain the session variables that were set by the controller POST action, as in Cake 3.8.
Discussion
- Do the assertSession() methods work? [URL] has an example usage of assertSession().
- The assertSession() method works if I know what value to expect in the session at a given key, so we could use this for many of our cases for sure. However, for some of our cases, we have an assertion that just checks that something was set, because it could be a random value like a UUID generated from the database during testing. I might be missing something here, but I am not sure how assertSession() can be used to just check the existence of something not null in the session key.

Asserting that $_SESSION['keyName'] is set and not null is a workaround for now, but it isn't clean and feels like a hack. 

Here is another snippet:
```
        // assume 'testValue' is a non-random value in 'testKey'
        $this->assertSession('testValue', 'testKey'); // passes, no errors

        // now assume that 'testValue' is random (such as a UUID)
        $value = $_SESSION['testKey'];
        $this->assertNotNull($value); // passes, no errors
        $value = $this->_requestSession->read('testKey');
        $this->assertNotNull($value); // fails, $_SESSION is empty now
```

I've noticed that internally assertSession() also uses _requestSession and passes it to a SessionEquals constraint. It seems the first check in _requestSession->read() method is causing $_SESSION to clear.
- ... [Middle Discussions Snipped for Brevity] ...
- I was looking into building a new assertion for `assertSessionHasKey` and found an interesting comment

```
        // Server::run calls Session::close at the end of the request.
        // Which means, that we cannot use Session object here to access the session data.
        // Call to Session::read will start new session (and will erase the data).
```

Which matches your results. It would seem like the simulated request closes the session which results in the next read restarting and wiping the session.

We might be able to use a stubbed session that doesn't open/close the session storage, but that will likely break applications that have tests that reach into the underlying session storage, so I'm hesitant to make a change like that.

Using the `$_SESSION` variable seems like your best option in the short term, unless other changes can be made to session handling that won't break existing applications.
