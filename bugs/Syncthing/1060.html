Discussion
- I assume that "28TB" is the size of your whole data set, right? What is the size of the old database (i.e. the `index-v0.14.0.db` directory)?
- 28TB is the current (4th) folder under migration. Third folder was 13TB. First line in the log show that it finished in about 7 hours. That had more files, but less data.

Whole old db is 9.2GB.
- ... [Middle Discussions Snipped for Brevity] ...
- Yeah, if you're going to insert a million rows in an empty table, better do it in order. No argument from me, and that's what they're testing. However, when you have a table with ten million random rows in it, the order in which you insert the next thousand random rows has no practical significance -- they're going to be in a thousand different random pages regardless. I've just benchmarked it. Prove me wrong.

Or, put another way, during migration only, it would be nice to process blocks in order. We can't do that because we're dealing with files and get the blocks they have in the order they have them. We can sort each individual block list, _but it doesn't matter_.
- I think there's two or three different parts to this issue:

- We should find a better way to scale the large block table. We're not there yet, though it's faster now than it was on launch day.
- The migration process is giving slightly misleading output, as files/s is usually not the limiting factor but blocks/s. With the numbers from the initial issue description, we have `30028318 / (23*3600 + 24*60) ~= 350` blocks/s insertion rate happening. That's not blazingly fast, but it's moving. However, ...
- ... on my laptop, currently (at approximately the same point as the OP, 61k files, 30M blocks): `db_bench_test.go:72: t=11m2.694011084s, files=61700, blocks=30850000, files/s=93.1, blocks/s=46552.4` (average up to that point; instant rate was about half)

So I'm not really sure what's going on with the OP. Really slow storage? But it doesn't seem absolutely inherent to the code.
