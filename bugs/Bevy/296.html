Title

Generic types with multiple parameters can have two different types with the same `TypeUuid`

Description
## Bevy version

Commit  

## What you did
If you have a generic type with multiple parameters, if the deriving types have the same parameters but in different orders the `TYPE_UUID` will be the same. 
```rust 
#[derive(TypeUuid)]
struct Foo ;
assert_ne!(Foo:: ::TYPE_UUID, Foo:: ::TYPE_UUID); // fails
```

## What went wrong

- Expected different `TYPE_UUID`'s but they are the same. 
- This is due to the fact the `TYPE_UUID`'s are the XOR of the params' types, and so even if they are XOR'd in different orders the result will be the same.

## Additional Information
- can be fixed by #6633
Discussion
- I don't understand why this is broken. I thought we had the `rotate_right` in `generate_composite_uuid` to break the associativity of `XOR`:
[URL]

Why does this not work?
- That's a good point. When I saw that I wondered why that is, and now I think I get it. The problem is that in one case we have right associativity and in another we have left

The cases are 1.
```rust
C > == C >
````
which expands with right associativity like
```rust
A  = f(A, B)
C > = f(C, f(A, B))
```

and 2.
```rust
C  == C 
```
which expands with left associativity like
```rust
C  = f(f(C, A), B)
```
with case `2` we expand like:
 ```rust
C  = f(f(C, A), B)
= C ^ r(A) ^ r(B)
 ```
therefore
```rust
C  = C ^ r(B) ^ r(A)
```
and so this fails as 
```rust
C ^ r(A) ^ r(B) == C ^ r(B) ^ r(A) 
```

What's the solution? Well we can
- Do what I did in #6633 and `wrapping_add` the index of the parameter to the uuid or
- change the expansion of case 2 to right associativity
I did the first solution as it seems simpler.
