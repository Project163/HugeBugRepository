Title

Jena 3.0.1 model halts reading large rdf file partway through

Description
The progress halts, or becomes slow to the point where progress is unnoticable, without execution stopping or crashing, when attempting to read a large (~250MB) turtle rdf file into a Jena model, created with org.apache.jena.rdf.model.ModelFactory.createDefaultModel(), using org.apache.jena.rdf.model.Model's read() method (tested with both the methods using String url and InputStream in). 

 The progress will continue until the process uses 1-1.5GB RAM, and progress halts, but execution neither stops nor crashes. The code on the bottom displays the behaviour with a progress bar for the file being read. 

 This has been the case for my laptop running Windows 10 using 
Eclipse 
Version: Mars.1 Release (4.5.1) 
Build id: 20150924-1200 

 My desktop running Windows 7 using  
Eclipse 
Version: Kepler Service Release 2 
Build id: 20140224-627 

 My professor's Mac using Eclipse, however I don't know which versions. 

 All three systems were employing Apache Jena 3.0.1, and all of them experienced the same issue. 

 I have attempted to manually set the max heap size of the JVM by using the -Xmx3G, however the result did not change. 

 Employing Apache Jena Version 2.7.4, and using the same resources in the com.hp.hpl package instead of org.apache fixed the problem on all three systems.

Discussion
- Thank you for the complete report. 

 There is a regression somewhere happening between v2.13.0 and v3.0.0. 

 From an initial exploration, it does not look like it related to heap usage. 

 Using the new transactional in-memory dataset does not show the problem so it is related to the implementation of the in-memory graph being influenced by some change made between 2.13.0 and 3.0.0.
- So far: 

 The data contains many  xsd:dateTimeStamp  literals. 

 Jena3 added value support for  xsd:dateTimeStamp . In Jena2,   xsd:dateTimeStamp  were not indexed by value, but by a placeholder  BaseDatatype.TypedValue . 

 If the data is converted to use  xsd:dateTime , then it runs slowly in Jena 2.13.0. 

 Profiling is currently masking exactly where the additional time is going.  It may be HashCommon.findSlot, it may be XSDDatatype.equals or it may be the quality of the hash code.
- The problem seems to be the quality of the hash code. The attached data ( data-500k ) is an extract from the report - it is all the triples with an  xsd:dateTimeStamp , with the datatype changed to  xsd:dateTime . It is slow on Jena2 as well as Jena3, taking about 300s to load.  

 A 250K dataset was fast with the old code. 

  xsd:dateTimeStamp  loads fast on 2.13.0 because  xsd:dateTimeStamp  is not indexed by value. 

 With the improved hash code, the load time is 2.6s (2.13.0 or 3.0.1). 

 The original code (below) generates close hash codes for close XSD dateTimes and XSD dateTimeStamps (Jena 3 onwards). 

 The bad hash code leads to hash table collision and long probe chains due to slots already in-use. The hash table is a closed hash table (AKA open addressing) with linear probing. 

 This was the hash code: 
  
     @Override
    public int hashCode() {
        int hash = 0;
        for ( int aData : data )
        {
            hash = ( hash << 1 ) ^ aData;
        }
        return hash;
    }    
 
  

 "<< 1" does not work well : datetimes that are close in value, lead to close has codes. Array items that are close by index need to be spread out more. 

 Changing to "<< 3" worked slightly better than "<< 2".  "<< 4" did not make much difference. 

 Changing the order so the hashing mixing date and time slots made "<< 2" work as well as "<< 3" (e.g. hash in the order (constants from  AbstractDateTime ) CY=0, h=, M, m, D, s ....). The key is that, for example, m and s are 2 slot hashs apart i.e. "<<4" when the "<<2" is used. 

  Using the Eclipse generated hashCode works just as well and is probably better researched. This is the fixed committed.
