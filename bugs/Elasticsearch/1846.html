Title

Unify `query_string` free text parsing and `multi_match` parsing

Description
We discussed the removal of the long standing `split_on_whitespace` issue for the `query_string`
 with @jpounz and @colings86 and decided that 6.0 is the right time to introduce a major change in `query_string` behavior:
**Disable the ability to split_on_whitespace entirely.**

This proposal goes further than #25470 by unifying the parsing experience between the `match` family query and the `query_string` parser but also to force users to not use a mode that relies on whitespace splitting. `match_query` and `muti_match_query` do not have the concept of `split_on_whitespace` so instead we want to align `query_string` to use the same mechanism than a `multi_match` query but applied only on the "text part" separated by operators.
For instance the query string `"foo bar AND foobar"` has two "free text" parts: 

- `foo bar` 
- and `foobar`.  

Changing the behavior requires also to adapt the other options to the new rule.
The following is the list of required changes for `query_string` to split text on operators only without loosing any features from the ancient mode:

- [ ]  Ignore `split_on_whitespace` and always split on operators instead.

- [ ]  Logs a deprecation warning when `split_on_whitespace` is set

- [ ] Introduce a new option named `type` that applies the [URL] on each free text part of the `query_string`.

- [ ] Makes the new option `type` mutually exclusive with `use_dismax` and `auto_generate_phrase_queries`

- [ ]  Make`use_dismax:true` query equivalent to`type:best_fields` or `type:most_fields` depending on the value of the `tiebreaker` option.

 - [ ] Make `auto_generate_queries:true` equivalent to `match_phrase` type. 

 - [ ] Document the new behavior and adds a section regarding the behavior of `min_should_match`
 coupled with the new `type`option.
