**Versions.**

At line 284, the 1st coroutine owned the lock and proceeded on to execute async queries in `first_connect()` (context-switched to the event loop), and the 2nd coroutine came in and blocked the whole main thread trying to acquire the same lock twice.

As a proof-of-concept, using `asyncio.Lock()` solves the problem:

```
python
class _CompoundListener(_InstanceLevelDispatch):
    __slots__ = "_exec_once_mutex", "_exec_once"

    def _memoized_attr__exec_once_mutex(self):
... [Log Snipped] ...
        finally:
            self._exec_once_mutex.release()
```

But obviously this is not a proper fix, and I don't have much idea for a proper fix atm. For this particular issue, some async-adaption changes may be needed for the event system. I haven't tried to find problematic scenarios for other `threading.Lock()` usages, but theoretically they are at risk too.
