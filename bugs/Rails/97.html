Title

Polymorphic eager loading fails when using a string foreign key

Description
The below fails with an exception on Rails master and 4.1, but works fine on 4.0 and 3.2.

```
ruby
unless File.exist?('Gemfile')
  File.write('Gemfile', <<-GEMFILE)
    source '[URL]
    gem 'rails', github: 'rails/rails'
... [Log Snipped] ...
  end
end
```

```
Finished in 0.020612s, 97.0309 runs/s, 48.5154 assertions/s.

  1) Error:
BugTest#test_polymorphic_includes_with_string_id:
NoMethodError: undefined method `each' for nil:NilClass
... [Log Snipped] ...

2 runs, 1 assertions, 0 failures, 1 errors, 0 skips
```
Discussion
- @seanlinsley I'll take a look.
- I think this worked by accident. If you have a string key, the table you link to, should have a string primary key. Creating the things table as follows will solve the issue:

``` ruby
  execute "CREATE TABLE things (id varchar PRIMARY KEY)"
```
- You're probably justified in thinking that this was accidental behavior, since there were apparently no tests for it. Be that as it may, Active Admin has been depending on this behavior for years now so its built-in commenting system works for any model, whether it uses a string or a number as its primary key.

Despite my vested interest in seeing this fixed, I think the old behavior is a very useful feature for polymorphic associations and shouldn't be removed between 4.0 and 4.1.
- We used to `to_s` to compare PK & FK. There was no test, but it is a regression.

We could check corresponding column types and only `to_s` if they don't match.
