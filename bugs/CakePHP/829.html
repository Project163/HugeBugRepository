Title

Digest Authentication doesn't actively use the nonce, so a replay attack is possible

Description
This is a (multiple allowed):
- [x] bug
- [ ] enhancement
- [ ] feature-discussion (RFC)
- CakePHP Version: 3.3.6
- Platform and Target: Vagrant bento/debian-8.6, PHP7.0, MySQL. Request tested via Postman and cURL.
### What I did

I have set up a simple Digest Authentication (the app I'm building is going to be the core of a simple API centerend architecture).

```
$this->loadComponent('Auth', [
    'authenticate' => [
        'Digest' => [
            'userModel' => 'ApiClients',
            'fields' => ['username' => 'client', 'password' => 'digest_hash'],
... [Log Snipped] ...
    'unauthorizedRedirect' => false,
]);
```

(The response="xxx" is of course a correct md5 hash)

When I make a request via Postman or cURL with the following header: `Authorization: Digest username="jelmer", realm="api", response="xxx"` it fails as expected, because as you can see at [URL] it returns false because not all required keys are provided.

So I add the missing keys, and thus sending the following header: `Authorization: Digest username="jelmer", realm="api", nonce="random", uri="/ping", qop=auth, nc=8, cnonce="random", response="xxx", opaque="random"`. And yes, I really provided `random` for the nonce, cnonce, opaque and nc keys.
### What happened

It authenticates me with truly random nonce, cnonce, opaque and nc keys.
### Expected Behavior

I expected it to block the request, since the nonce value wasn't requested from the server earlier on, so it wasn't provided to me via a 401 response.
- I expect the DigestAuthenticate to return a nonce and other keys when I do not provide them.
- I expect the DigestAuthenticate to block the request when I provide a wrong nonce or other keys.

Expectations based on [URL]

I'm not that well known with Digest authentication and I'm really trying to understand it all, but as far as I'm concerned the RFC's and other articles about Digest, I expect it to make a handshake first, before I'm authenticated to request data.
Discussion
- By handshake do you mean that you expected the server to send a `WWW-Authenticate` header when you failed to authenticate properly?
- @markstory, I expect the following behaviour:
1. I send a request to the API with just the username, realm and response keys provided.
2. The server responds with a 401 and provides the nonce, cnonce, nc and opaque keys.
3. For every request following these two steps, I will supply the username, realm, reponse, nonce, cnonce, nc and opaque keys (those that were given by the server).
4. The server will now also check the nonce and other keys to check if I'm still the same person and to check I'm still part of that "secure connection".

What happens is:
1. I send a request to the API with just the username, realm and response keys
2. the server responds with a 401 and WWW-Authenticate header, as expected.

But what also happens:
1. I send a request to the API with the username, realm and response keys. But also with a random nonce, cnonce, nc and opaque key.
2. The server responds with a 200.

So, it never checks if the nonce provided is the same as the one that was provided by the server in the first place. With other words: there is no handshake.

I'm not 100% sure if that's the way Digest authentication works, but that is what I make of the RFC's and other source documents that explain the Digest authentication process.
