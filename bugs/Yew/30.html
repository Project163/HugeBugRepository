Title

Uncaught RangeError: Maximum call stack size exceeded

Description
We still get this bug:

[URL]
[URL]

I think the implemention of  PartialEq for NodeRef is terribly wrong:

```
impl PartialEq for NodeRef {
    fn eq(&self, other: &Self) -> bool {
        self.0.as_ptr() == other.0.as_ptr() || Some(self) == other.0.borrow().link.as_ref()
    }
}
```
Because "Some(self) == other.0.borrow().link.as_ref()" call  PartialEq recursively?!

Aside from  that, the additional check seems to be unnecessary, because it can never trigger.

```
  pub(crate) fn link(&self, node_ref: Self) {
            // Avoid circular references
            debug_assert!(
                self != &node_ref,
                "no circular references allowed! Report this as a bug in yew"
            );
```

The following patch solves the problem  for me:

```
diff --git a/packages/yew/src/html/mod.rs b/packages/yew/src/html/mod.rs

 }
```

Discussion
- I just wonder what kind of app exceeds the stack size. Keep in mind, that this check was recently changed to a `debug_assert!` from a simple early return, because the krause's js-framework-benchmark has shown a performance regression. But that already renders 10k elements in a large list, which would be a strain in real apps, and doesn't hit the stack size limit. Are you doing something similar?

Regardless, for the fix, either:
- change it to an iterative instead of recursive check, but recurse on both sides of the equal sign, not just on the right... In this case, also change it for `NodeRef::get`, it suffers from a similar problem.
- change the way we internally use `NodeRef` to a better data structure. Note though a [Link: very similar performance comment] when comparing our "linked list of siblings via NodeRefs" to their searching procedure. We kinda wanted to do this for some time anyway, since this could enable callback refs.
- Yes, we observed this when doing performance tests with very large tables (worst case scenario). It basically only happens for a debug compile and when the browser debug console is open. Everything runs fine when compiled with release mode.
- :+1: @hamza1311 floated the idea of a patch release some days ago, I think this should definitely make it in there.
