Title

Bevy should propagate system's panic payloads rather than creating additional panics

Description
## What problem does this solve or what need does it fill?

I just got this unwieldy panic:

```
thread ' ' panicked at 'Error in Queue::submit: Buffer (2, 1, Vulkan) is still mapped', /home/sludge/.cargo/registry/src/github.com- /wgpu-0.15.1/src/backend/direct.rs:316:9
stack backtrace:
   0: rust_begin_unwind
             at /rustc/ /library/std/src/panicking.rs:575:5
   1: core::panicking::panic_fmt
... [Log Snipped] ...
  20: sludgerender::main
note: Some details are omitted, run with `RUST_BACKTRACE=full` for a verbose backtrace.
```

Only the very first panic is actually relevant, all the subsequent panics and their backtraces are noise ultimately caused by the first one.

## What solution would you like?

Ideally, bevy's executor should catch and propagate all panics originating from a system by using [Link: `resume_unwind`], all the way up to the user's `App::run` invocation.

This establishes a 1-to-1 relationship between panics caused by the user, and panics seen or caught by the user, which seems like a much cleaner design than what's happening now.

Doing this might require a rather large refactoring, so maybe treat this as more of a wishlist item :)

## What alternative(s) have you considered?

Embrace the Javaist backtraces and do nothing :coffee:
