Title

[YCQL] Performance issue - secondary index should not be chosen over primary index

Description
Jira Link: [Link: DB-4651]
```
ycqlsh:test> create table t (i int, j int, x int, y int, primary key (i))
        ...   with transactions = {'enabled' : true};
ycqlsh:test> create index tidx on t (x);
ycqlsh:test> explain select * from t where i = 1 and x = 1;
 QUERY PLAN
... [Log Snipped] ...
   Key Conditions: (x = 1)                 
   Filter: (i = 1)
```
Discussion
- This bug should be fixed together with #7069  - different symptoms but same coding/design issue.
- I added some log statements in operator> of Selectivity.
It seems primary index is among the candidates. However, due to the covers_fully attribute being considered later in the comparator, secondary index is chosen.

Even though moving the following to immediately after comparison of full_table_scan_:
```
    // If one covers the read fully and the other does not, prefer the one that does.
    if (covers_fully_ != other.covers_fully_) {
      return covers_fully_ > other.covers_fully_;
    }
```
would yield the new order among the candidates:
```
ts3|pid3780462|:13544|[URL] I0220 18:27:38.814424 3780545 pt_select.cc:526] there are 2 selectivities
ts3|pid3780462|:13544|[URL] I0220 18:27:38.814496 3780545 pt_select.cc:528] Selectivity: index_id  is_local true prefix_length 1 single_key_read true full_table_scan false ends_with_range false covers_fully true
ts3|pid3780462|:13544|[URL] I0220 18:27:38.814504 3780545 pt_select.cc:528] Selectivity: index_id   is_local false prefix_length 2 single_key_read true full_table_scan false ends_with_range false covers_fully false
```
and primary index being chosen:
```
ts3|pid3780462|:13544|[URL] I0220 18:27:38.814510 3780545 pt_select.cc:536] Selected = Selectivity: index_id  is_local true prefix_length 1 single_key_read true full_table_scan false ends_with_range false covers_fully true
```
the change would make QLTestAnalyzer.TestIndexSelection fail because there're cases where index with longer prefix would be preferred.

Investigating the case of prefix_length for secondary index being longer (as shown in example above) and yet primary index should be chosen.
- Some comments on this bug from Mihnea and Piyush on range-scan.

When both primary and secondary-index scans are RANGE-scan, which one should we choose?

Piyush:
```
I agree with use of primary index over secondary index for single key lookup and in case both are full table scan. But for following case, secondary indexes might be better? -

[Range scan with longer prefix in secondary index - i.e., if the range to be scanned is less enough in the secondary to offset the extra RPC cost involved (of the parent select).]
```
Mihnea:
```Agree. I think the covers_fully_ fully check below covers this case -- but it needs to be done _after_ we check prefix length so that we don't pick a bad-match for a primary key index over a great match for a secondary index.```
- The problem is that "prefix-length" for secondary path counts primary-key columns as part of its own.  Some further evaluation needs to be looked at.
```
TABLE tab (h int, r1 int, r2 int, k1 int, k2 int, PRIMARY KEY(h, r1, r2));
INDEX idx ON tab (h, k1, k2);
SELECT ... WHERE h = 1 and r1 =1 and k1 =1
```
For PRIMARY PATH, the above SELECT has number key-count as ```2```
For SECONDARY PATH, the above SELECT has number key-count as ```3```
