Title

Files loaded via setAnimationFromUrl are not cached in memory.

Description
**Link to fork with a repro in the issue-repro module**

URL: [URL]

**NOTES:**

* The repro is in the `issue-url-animation-file-no-memory-cache` branch - _not_ `master`. This is because I couldn't actually build `master`, `v3.4.4`, or `v3.4.3` on Android Studio 4.0 or 4.1, seemingly due to the use of an RC version of the Android gradle plugin. Rather than allowing AS to update the plugin and potentially introducing unrelated changes as a result, I decided to use `v3.4.2` as a base instead.
* The repro is extremely minimal, and verification of the issue requires use of the debugger in Android Studio rather than visual/log inspection (see steps to reproduce below for more details).

**Describe the bug**

A very similar issue, #978, was opened a few years ago. It was subsequently closed in #986, which claims to add memory caching for files downloaded asynchronously via URL. However, it appears that these animation files are not actually being stored in the memory cache. In particular (for my use case), this affects `LottieAnimationView.setAnimationFromUrl`.

I investigated this with the debugger. Using the sample app linked above, I discovered the following:

`setAnimationFromUrl` calls `LottieCompositionFactory.fromUrl` with no 3rd parameter (cache key), so a cache key is automatically generated by prepending `url_` to the beginning of the URL. The cache key used in the app is therefore:
 `url_[URL]

When the app has been clean installed and is opened, all of the caches (memory, task, and disk) return misses, so the file is fetched from the URL. This is expected.

After closing the app and opening it again, the memory cache and task cache return misses, but the disk cache returns a hit, so the file is _not_ fetched from the URL. This is expected.

Keeping the app open and tapping the reload button (which simply calls `setAnimationFromUrl` with the same URL), the memory cache returns a miss. This is _not_ expected.
