Title

no-fallthrough doesn't seem to work

Description
Maybe I am missing something, but the following code snippet lints successfully when I enter it into [URL] I expected it to fail with `no-fallthrough`.

``` javascript
switch ("foo") {
case "foo":
case "bar":
    break;
default:
    throw new Error();
}
```
Discussion
- This rule allows for empty case clauses, which explains why that snippet of code does not generate a warning. A similar snippet is included among the examples of passing code for this rule: [URL]

This rule aims to protect against accidentally forgetting a `break` statement. If a case clause is empty, it's likely intentional.
- Thank you for the clarification. Do you think it might be useful for others to add an option (e.g. `AllowEmptyCase`) to change this behavior? In a current project of mine a fellow developer commented out the content of a `case` clause. This didn't cause a bug in this particular instance but it would have been good if ESLint caught this right away.
- ... [Middle Discussions Snipped for Brevity] ...
- @Grandrath To be clear, are you requesting an option to enable lint errors for all empty cases, or just ones that are empty syntactically but which have comments that don't match the "falls through" expression?

Put another way, should this warn on the `case 1` line?

``` js
switch (something) {
    case 1:
    case 2:
        yay();
}
```

Or should we only warn when the case is empty, but has a comment in it?

``` js
switch (something) {
    case 1:
        // yay();
    case 2:
        yay();
}
```
- We originally had this as an exception because it's a pretty common way to say you want fall through (even JSLint allows it):

``` js
switch (something) {
    case 1:
    case 2:
        yay();
}
```

My opinion is that this should still not warn. However, this definitely should warn:

``` js
switch (something) {
    case 1:
        // yay();
    case 2:
        yay();
}
```

So, if I've read this issue correct, it's really the latter case that is problematic and I'd say it's a bug that it's not being flagged right now. @Grandrath is that correct?
