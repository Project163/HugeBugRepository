Title

Cursor jumping after being disabled

Description
Hi !

When using GLFW_CURSOR_DISABLED, mouse is going to move to the center og the current window every time it moves. Seems logic to keep unlimited area for mouse. Every time WM_MOUSEMOVE is called, mouse is moved as an offset compared to last check. 

Im kinda confused with bug I have for a long time. When rotating camera, I'm doing (just once every time I want to rotate camera ).

-- start --
RememberPos = MousePos 
glfwHideMouse(); //  -> glfwSetInputMode( .. , GLFW_CURSOR , GLFW_CURSOR_DISABLED );

-- loop --

set angle change as ( RememberPos - MousePos )

--end --

glfwShowMouse();
glfwSetCursorPos( .. RememberPos  .. );

Another words : in the next glfwPollEvents I'm getting some wird position jump as in the video : [URL] ( will be avaible in 1.5h from 'now' ).

The jump length seem to be similar to MousePosBeforeHiding-Center . So it might be linked somehow to setting mousepos to the center during glfwHideMouse. I'll try to investigate what couse that bug. 

Problem doesn't occur when I cut the hiding/showing part . But I loose the infinite rotate feature.
Discussion
- I haven't looked into the details recently, but I've dealt with this task some time ago. Most likely the problem is that doing glfwShowMouse() actually issues an internal call that moves the mouse pointer, or something like that. I remember having to do a lot of trial and error in the exact order in which you issue the hide/show/GetCursorPos/SetCursorPos to solve this task, and there were bugs that had to be fixed along the way...

I really think a proper solution (that requires improving/breaking the API) is to expose the mouse input as two independent types of events. Relative mouse movement deltas (always sent, preferably ignoring mouse acceleration), and absolute cursor position updates (only issued when cursor is visible, naturally includes OS-level mouse acceleration).

Hiding, showing, and moving the cursor via glfwSetCursorPos() should cause _zero_ mouse movement deltas.

It's unfortunate that every user of GLFW that cares about both relative and absolute mouse positions has to do the non-trivial (and error prone) calculation on their own, despite the physical input device generating true relative deltas. All because improving it requires an API change.
- GLFW does its own saving and restoring of the cursor position in `setCursorMode`.
- All of this is going to become less bug prone with the removal of cursor position caching for modes other than captured mode. That is one of the things I'm working on for 3.1.
