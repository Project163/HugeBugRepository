Title

quarkus-logging-json not working 1.3.0

Description
**Describe the bug**
After Upgrading quarkus to 1.3.0.Alpha2 quarkus-logging-json fails in dev mode:
```

	at io.quarkus.runner.ApplicationImpl.doStart(ApplicationImpl.zig:232)

	at java.base/jdk.internal.reflect.NativeMethodAccessorImpl.invoke(NativeMethodAccessorImpl.java:62)
... [Log Snipped] ...
	at java.base/java.lang.ClassLoader.loadClass(ClassLoader.java:521)
	... 18 more
```

**Expected behavior**
quarkus starts and logs in json format

**Actual behavior**
quarkus does not start


**To Reproduce**
Steps to reproduce the behavior:
1. Upgrade quarkus to 1.3.0.Alpha2
2. Add the quarkus-logging-json extension
3. run quarkus in dev mode (mvn quarkus:dev)

Discussion
- @stuartwdouglas looks like a new CL issue.
- The `org.jboss.logmanager.formatters.JsonFormatter` which is used in the recorder of `quarkus-logging-json` extension, is a class that's part of the `org.jboss.logmanager:jboss-logmanager-embedded` artifact/jar. It so happens that this specific artifact is marked as "parentFirst" here[1]. So when Quarkus runtime classloader tries to load the `JsonFormatter` it gives preference to the parent classloader (to see if it can load that class). It also happens to be the case that this `org.jboss.logmanager:jboss-logmanager-embedded` is an entry in the `META-INF/MANIFEST.MF` of the application's dev mode jar (which is used to launch dev mode) and hence the Java application launch classloader has this available in its classpath and when Quarkus asks this classloader to load `JsonFormatter`, it readily does that. However, this `JsonFormatter` class has a dependency on classes that belong to `javax.json` package. This package is provided by the `org.glassfish:jakarta.json:jar:1.1.6` artifact. This artifact however isn't part of the Java applicaiton launch classloader (it however is, rightly, part of the Quarkus runtime classloader) and hence when it tries to load `JsonFormatter` it doesn't find these `javax.json.*` classes.

Long story short - the jboss-logmanager-embedded which is visible to the Java launch classloader doesn't have some of its dependencies available in that classloader. I can't think of a clean way to get past this, other than maybe adding this artifact to the "parentFirst" list too (however, that won't solve this cleanly - for example what happens if jboss-logmanager-embedded depends on some other similar dependencies, do we keep adding them statically?).
