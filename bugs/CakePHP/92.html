Title

Media View sends an extra "1" at the end

Description
Using Cake2.4.5, the media view returns an extra "1" at the end of the file.  If I remove the "return true" at the end of MediaView's render function, then the "1" goes away.

I know the media view is depreciated, but it should still work correctly if it's included at all.

I see View/View.php returns true in some circumstances as well.  It looks like the only reason the render function returns true is for the test cases.  Should the render functions be changed to never return a bool?  Or should everywhere that calls the view's render be checking is_bool?
Discussion
- There are passing test cases for MediaView. Digging into a potential bug in deprecated code is pointless. You are using cake 2.4.5 so just update your code to use the request object to render file as shown in manual.
- Wow.  Then let's pretend for the sake of argument that the test cases are not robust enough and there actually is a breaking bug in the MediaView.  The MediaView then goes beyond "depreciated" to "broken and will not fix".  In that case, a note should be added to the cookbook and upgrade notes that applications using the MediaView _must_ be upgraded to the new file format.

I'd consider this a breaking bug because sending a file with an extra "1" at the end can cause many different files to be considered corrupt by their interpreters.  This is how I found the bug.

Additionally, this issue may extend beyond just the MediaView because there are other views that return true in certain cases as well.
- ... [Middle Discussions Snipped for Brevity] ...
- A view class returning true is indeed problematic since [Link: Controller::render()] sets the return value of it's render() method as response body (which would end up as "1" when echoed).

So possible fixes are:
- View classes must not return true to indicate success.
- Controller::render() should not set return value from view class as response body if it's boolean.

While we can fix the core classes there might be custom view classes out there which might be doing the same. So probably the second fix is more desirable (or both).
