Discussion
- Recently  I encountered the same problem - the worker's memory was not released upon an exception. A fairly large amount of data was generated in the task - about a hundred megabytes, then an error occurred. Each time an error occurred, the worker's resident memory increased by one hundred megabytes and was not released. Worker memory usage was limited to four gigabytes, and by running tasks it was possible to reach this value, after which the worker crashed.

After some investigating, I found that the answer indeed lies in traceback. From the [Link: python documentation]:

Celery creates variables with an exception object, which creates a reference cycle, but actually it takes this into account and cleans up the traceback: 

[URL]

However, the point seems to be that it doesn't take into account that exceptions can be nested.

Let's imagine the following situation:

```
def foo():
    foo_data = ... # there are some local data
    raise SomeException()

... [Log Snipped] ...
    except Exception:
        raise SomeAnotherException()
```
So `clear_traceback` function will clear `task_data`, but not `foo_data`.
To clear `foo_data`, `clear_traceback` must not only clear `exc.__traceback__`, but also `exc.__context__.__traceback__` if `__context__` is not `None`. Exception in `__context__` might have its own `__context__`, so is seems that clearing must be done recursively, something like this in the end of  `traceback_clear`:

```
if exc.__context__ is not None:
    traceback_clear(exc.__context__)
```

In the example of ralphie0112358 there are not any nested exceptions, and I could not reproduced the issue with it. But when I added a nested exception with the generation of a large amount of data, the situation with unreleased memory was consistently reproduced.
Perhaps the increase in memory in ralphie0112358 example was not related to the problem I described, but the increase in memory in production was.

Is seems that for now the solution is indeed to call `gc.collect()` directly or not to use nested exceptions.

Anyway, hopefully this will be fixed in future versions.
- would you mind come with a prospective fix in a draft pr, please?
