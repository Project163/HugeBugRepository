Title

replaceState throws away functions in 0.13

Description
I'm still learning React, so it's possible I'm misunderstanding something.

I'm trying to use React with Immutable.js, and hit a stumbling block, by upgrading to React 0.13. There is [Link: wiki page] on the immutable.js repository, that explains how to use immutable as a react state, and it provides the following example (I transpiled it to ES3):

```
js
'use strict';

var React = require('react');
var Immutable = require('immutable');
... [Log Snipped] ...

React.render( , document.body);
```

This works great in 0.12, but in 0.13, you will receive the following error when clicking on the div:

```
TypeError: this.state.get is not a function
this.state.get('count')
```

Putting a breakpoint on the error, and inspecting this.state with a debugger reveals that all the methods on this.state have disappeared.

Is this the expected behavior in 0.13?
Discussion
- @WishCow `this.state` should be a plain object, you're not allowed to put classes in there.
- So the wiki page I linked to is incorrect? It would make working with immutable.js (and probably other immutable implementions) a pita, since you would have to pack/unpack the object every time you store/retrieve it.
- ... [Middle Discussions Snipped for Brevity] ...
- @jeffutter AFAIK this is not going to change. Personally I still don't understand why people want to put third-party objects as state, I don't see what benefit there is. What's wrong with just using `setState`?
- @syranide For me there were two main advantages.

1.) My stores already deal in immutable hashes, With react 0.12 I didn't have to bother converting them
2.) Deep comparison for updates is _simple_ with immutable objects. With react 0.12 when you setState with an immutable object, if _any_ of it's contents had changed, it would re-render. If it was the same, it would not. Comparing immutable objects is cheap. Deep comparing hashes is not. There is more upfront cost with the immutable objects, but they are way easier to reason about wether or not they have changed.

If there is definitely no plan to support this then I suppose the best plan of action is to to_js everything and manually deep compare?
