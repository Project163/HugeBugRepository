Title

Current file path is not taken into account when caching duplicate relative import paths

Description
### Brief summary

k6 appears to be re-using a cached import for a relative path `../fragments/index.js` wherever you use it in the code that's being used in a testrun. 

### k6 version

0.42

### OS

macOS11 / Ubuntu Linux

### Docker version and image (if applicable)

_No response_

### Steps to reproduce the problem

Using the relative path from the brief summary, if imported first in `src/graphql/a/operations/index.js` (to indicate `src/graphql/a/fragments/index.js`) and then later in `src/graphql/b/operations/index.js` (to indicate `src/graphql/b/fragments/index.js`) it will provide me with the former import (`src/graphql/a/fragments/index.js`).

We recently updated to v0.42.0 from v0.40 (where this issue did not occur) and after some digging into any recent changes, it appears to me (though bear in mind I have next to no knowledge in Go) that is what introduced the issue: [URL]

At this point it seems to me that `../fragments/index.js` is what will serve as key in the cache, instead of the full URL (or anything that includes the file that is doing the importing).

### Expected behaviour

For the relative import to provide me with the correct file relative to whatever file it is being imported from.

### Actual behaviour

A cached import for the exact same relative path name is being returned regardless of where it is being imported from.
