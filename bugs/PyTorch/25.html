Title

test_binary_ufuncs.test_inplace_comparison_ops_require_inputs_have_same_dtype May have been damaged

Description
## 🐛 Bug

 
In file test_binary_ufuncs.py, This test expects every operation to throw a runtime error, but in fact only logical_xor_, logical_and_, logical_or_ throws a runtime error
```
@onlyCPU
def test_inplace_comparison_ops_require_inputs_have_same_dtype(self, device):
    with self.assertRaisesRegex(RuntimeError, 'Expected object of scalar type'):
        for op in ['lt_', 'le_', 'gt_', 'ge_', 'eq_', 'ne_', 'logical_xor_', 'logical_and_', 'logical_or_']:
            x = torch.tensor([1], dtype=torch.int)
            y = torch.tensor([2], dtype=torch.long)
            in_place_method = getattr(x, op)
            in_place_method(y)
```


## To Reproduce

Steps to reproduce the behavior:

```
In [13]: x = torch.tensor([1], dtype=torch.int)

In [14]: y = torch.tensor([2], dtype=torch.long)

In [15]: x.lt_(y)
... [Log Snipped] ...

RuntimeError: Expected object of scalar type int but got scalar type long long for argument 'other'
```


 

## Expected behavior
I've recently been trying to port logical_xor to structured, and logical_xor doesn't throw runtime errors either, I'm not sure what the correct behavior should be

- I'm not sure, and would have to analyze the situation. Maybe you can trace through and see why?
- Apparently, that check was introduced when porting `lt` to ATen, in #25998. Here is the reason given in that PR:

Expects that a and b has same dtype, otherwise it's possible to get an overflow(Example: 'a' is uint8, 'b' is float32. 'a' will be promoted to float32 and the result will be also float32. Then it will be casted back to uint8 so potential for overflow). Will not compute common dtype. Result will have type of a.

Maybe I'm missing something, but I can't see how that's the case. Both CPU and CUDA had very similar implementations, differing only in which `TensorIterator` consumer function was used: `cpu_kernel` and `gpu_kernel_with_scalars`, respectively. For example, the relevant part of [Link: the CPU kernel] follows:

```c++
AT_DISPATCH_ALL_TYPES_AND(kBFloat16, iter.dtype(), "lt_cpu", [Link: &] {
  cpu_kernel(iter,
    [Link: =] -> scalar_t {
      return a < b;
    });
});
```

Note that the lambda function used return an implicit conversion of `bool` (the return type of the `<` operator) to `scalar_t`. As far as I understand, in that case, the result will always be either 0 or 1 of the return type. I can't really see how that could cause an overflow.

That said, I may be missing something. Any thoughts?
