Title

TCP timeout issue

Description
From [URL]

tested with multiple versions of rclone including 1.39 (current version) and 1.39-125 (current beta)

when tcp read connections stop sending data rclone successfully detects and recovers if --time-out=1m but not with the default setting (5m)

Tested on Dell R7910 workstation running Windows 10 with all current MS updates, latest Intel X540 NIC driver.
Tested against a DellEMC ECS
Attached logs showing the timeout setting at 1m and recovering from a tcp i/o error and with the timeout setting at 5m and not recovering (at about 30 minutes I killed rclone since it was never going to complete)
Interestingly in the 5m file it did detect a few of the dead connections but not all of them.

- Very interesting logs thanks.  That must be the fastest rclone transfer I've seen so far!

All the files which stalled are big files and so are using chunked uploads in the S3 uploader.  These should be 5 MB chunks by default I think.

So it seems that the problem is probably not the passing of the chunks but the negotiation for the next one.

Can you run `nbtstat -n -o` when rclone has stopped transferring any data?  That should show whether rclone has any open connections or not.

Also if you could run a failing transfer with `-vv --dump headers` this will print a lot of stuff, but will enable me to work out if rclone has failed during the transfer of a block, or after a transfer.
