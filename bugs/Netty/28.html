Title

Description
In migrating to using DefaultEventExecutor within a pipeline I'm noticing elevated context switching and CPU utilization even when there are no clients connected.  Using io.netty.example.http.websocketx.server.WebSocketServerInitializer as a starting point: if you add a DefaultEventExecutor as such:

```
{ ...
private static final DefaultEventExecutor evntExec = new DefaultEventExecutor(64);

  @Override
  public void initChannel(SocketChannel ch) throws Exception {
... [Log Snipped] ...
  }  
}
```

Then: connect, send some messages, disconnect and repeat this a few times you'll observe elevated CPU even when no clients are connected.  Running visualvm (when there are no clients connected) reports io.netty.util.internal.LinkedTransferQueue.awaitMatch() taking up many of the cycles (whereas if DefaultEventExecutor isn't included in the pipeline, LinkedTransferQueue.awaitMatch() doesn't show up in the profiler when there are no clients connected).  Just wanted to ping the list and find out if the above is the correct way to utilize DefaultEventExecutor or if there is a bug at hand.
