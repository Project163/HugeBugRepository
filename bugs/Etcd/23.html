Title

RWMutex recipe bug

Description
ETCD version: v3.0.8

There is a bug in the current [Link: RWMutex recipe]. If two processes try to lock the mutex at the same time, the second one starts spinning indefinitely after the first one unlocks the mutex. 

The problem appears to be in the way the previous key revision is taken from the server. It always returns the previous key which already has been deleted ( the watcher in 'waitonlowest' correctly returns that all the time ).

The code I have attached demonstrates the problem. Simply compile and run two instances at the same time.

```
golang
package main

import (
    "fmt"
... [Log Snipped] ...
    mtx.Unlock()
}
```
