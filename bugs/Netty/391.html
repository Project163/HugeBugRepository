Title

Performance regression in GlobalTrafficShapingHandler, version 4.0.22

Description
GlobalTrafficShapingHandler is marked @Sharable, but the super-class, AbstractTrafficShapingHandler, calls down into a method marked 'synchronized' in the subclass on each write. This is forcing all writes to block on a single lock.

See [URL]

It looks like it was introduced in 4.0.22, see [URL]

Reproducing the issue is a matter of doing concurrent writes on multiple eventloops, all of which have this handler as part of their pipeline.
Discussion
- @gsoltis previously, sadly, the traffic shaping handler (whatever global or channel) was not really working on write part.
The new version takes care of the write by adding them into a queue for the channel. To prevent unordered write output (from business handler, A then B were written, while in the queue, B then A will be added, thus producing a wrong output order), a synchronization is needed.
On Channel TSH, this is not a big issue, but on Global, I understand it is.

To fix this issue, we should add a specific "lock" per channel, which could be tidious, something like:

in AbstractTSH

```
submitWrite(...) {
    ReentrantLock lock = ctx.attr(ChannelLock).get();
    lock.lock();
    try {
        ...
... [Log Snipped] ...
    }
  }
```

And of course adding at handlerAdded/handlerRemoved the necessary handling of those lock per channel.
A better idea?
- @gsoltis Hmm, not that simple. The TrafficCounter below is also using synchronized methods since it has to be "as exact as pssible", for each write/read request of time for a message (readTimeToWait, writeTimeToWait).
Maybe we could "support" those methods to be not that accurate and removing the synchronization?

WDYT?
- @gsoltis I made some tests, removing all synchronized from Global (letting them in Channel since it is ok there), replacing them by a ChannelLock per Channel, and it works.
Only the creation/destruction of this lock is synchronized to prevent multiple concurrent creations/destructions.
Even the TrafficCounter has then no more synchronized on the xxxTimeToWait() (even no lock).

I will add those changes to the current fix (see #2945 ).
Thanks to report this !
