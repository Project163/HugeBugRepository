Title

AssertionError raised after #19248

Description
**Bug Report**

 

After upgrading to 1.16.1 we are seeing occasional `AssertionError`s being logged:

```console
$ mypy
mypy 1.16.1 (compiled: yes)
Exception ignored in PyObject_HasAttr(); consider using PyObject_HasAttrWithError(), PyObject_GetOptionalAttr() or PyObject_GetAttr():
Traceback (most recent call last):
  File "mypy/nodes.py", line 615, in setter
AssertionError: 
... (repeated many times)
```

It seems like the code introduced in [URL] to fix [URL] makes an assert which is not always true. It seems like the worry expressed in a [Link: comment] on that PR was justified ;).

**To Reproduce**

We haven't managed to find a reliable reproducer yet. Switching between branches in our repo and invoking `mypy`, sometimes triggers it, but sometimes doesn't.

**Expected Behavior**

 

No errors.

**Actual Behavior**

 

Errors.

**Your Environment**

 

- Mypy version used: 1.6.1
- Mypy command-line flags: `dmypy run -- --cache-dir .mypy_cache/not_recently_touched  `
- Mypy configuration options from `mypy.ini` (and other config files):
```
toml
[tool.mypy]
plugins = [
  "pydantic.mypy",
  "pydantic.v1.mypy",
... [Log Snipped] ...
    "asyncpg.*",
]
```
- Python version used:

```console
$ python --version
Python 3.13.3
```
Discussion
- Does this ever happen without cache? Your mention of switching between branches suggests some relationship with cache, and it's important to know whether "clean" run without cache is prone to this.
- I suspect the `astmerge` in the `dmypy` server triggers this error, because `OverloadedFuncDef.setter` is defined as a `@property`.

From the error logs above we can see that the `AssertionError` is triggered during an `hasattr` call. Searching the codebase for an interesting `hasattr`, we find a `hasattr` call in [Link: `replace_object_state`]. This results in possibly calling `hasattr` on `OverloadedFuncDef.setter`, which evaluates the property unconditionally (since `hasattr` is implemented using `getattr` [Link: [1]]), triggering the `assert` on [Link: `mypy/nodes.py:615`].

Main uses of `replace_object_state` are in [Link: `mypy/server/astmerge.py`].

Assuming the above I tried to create a reproducer. Which indeed made it reproducable:

```
console
$ mkdir /tmp/hello
$ cd /tmp/hello
$ uv init
$ uv add mypy==1.16.1
... [Log Snipped] ...

$ ... cycling between the versions of `test.py` consistently reproduces the error.
```

We probably want `OverloadedFuncDef.setter` to not be a `@property`, s.t. it is not evaluated by `hasattr`? Or we should prevent it from being evaluated by accident in some other way.

Quite a tricky bug ;).
