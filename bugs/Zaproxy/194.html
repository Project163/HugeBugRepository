Title

Spider/Active Scan Hangs scanning [URL] redirect to non-existent port

Description
I was originally starting with running zap-full-scan.py scans against a number of hosts, one of which was [URL] and the active scan was seeming running indefinitely.  I moved to the UI to try and get more information on this and I worked with @thc202 a fair bit in #websectools trying to debug this.  We ultimately didn't find a resolution, but putting all my debug information/intel here in the hopes it eventually finds a root cause and we can work past this.

Reproduction Steps

1. Open up the ZAP UI (I was running 2.7.0 release on Mac OS Sierra)
2. URL to Attack: [URL]
3. You will then witness it move through and complete the Spider quite quickly and move on to the Active Scan
4. In the active scan it will start with the Path Traversal plugin, make up to about ~50 requests and then the request counter will stop increasing.

Troubleshooting/Debug Context

1. We originally thought this was some IPS/WAF solution, but I have verified with the service owner this is not the case and I verified with other MiTM proxies and this behavior was not observed there.  We believe we ruled this out.

2. We ran ZAP and got stack traces from all the threads.  Based on this @thc202 concluded that the scanner was waiting, not timing out

[URL]

3.  @thc202 also just realized that [URL] which redirects to [URL] and believes this is the source of the issue.
Discussion
- Ok, after some looking around it appears the issue is the redirect to a non-active port.

Things I think we could do to make this work better...

1.  Restrict the scope to the service being scanned (ie. if we ask it to scan :443, it will not observe redirects and add them to the scan scope automatigally, maybe this is a prompt/alert the user somehow?).  As a user of ZAP, my expectation would be that we'd never scan the directed service due to scope restrictions and if were to redirect, then it would simply timeout and not halt the entire scan process.

2. Go fix this redirect behavior in Observatory, which I have raised with @april in [URL] (it seems this is the internal listening port)
- At the very least, ZAP should definitely not hang attempting to get the resource any longer than however long it or the webserver takes to timeout.
- Closing, this should be addressed with #4173.
