Title

Create collection API always has status 0

Description
The responses below are from a successful create collection API ( [URL] call and an unsuccessful create collection API call. It seems the 'status' is always 0. 

 Success: 
{u'responseHeader':  
{u'status': 0, u'QTime': 4421}
 , u'success': {u'': {u'core': u'test1_shard1_replica1', u'responseHeader': {u'status': 0, u'QTime': 3449}}}} 

 Failure: 
{u'failure':  
   
{u'': u"org.apache.solr.client.solrj.impl.HttpSolrServer$RemoteSolrException:Error CREATEing SolrCore 'test43_shard1_replica1': Unable to create core: test43_shard1_replica1 Caused by: Could not find configName for collection test43 found:[test1]"}
 , 
 u'responseHeader':  
{u'status': 0, u'QTime': 17149}
 } 

 It seems like the status should be 400 or something similar for an unsuccessful attempt?
Discussion
- I looked into this a bit.  It looks like the collection creation always returns status 0, and returns the failures of the individual shards in the "failure" field of the response and successes in "success."  That's interesting information, although I'm not sure it's that more useful for the end-user than just throwing an exception listing all the failures or just the first failure. 

 This also appears to be an issue with the other OverseerCollectionProcessor, although I'm not sure if there is any case where an individual operation is not successful, but we'd want to not throw an exception.  Anyone have an opinion?   markrmiller@gmail.com ?
- Collections API responses really need an overhaul I think. One of those things that has gotten no real attention. Very hard to process the response currently I think. 

 I do think we need fine grained results available of some kind, unless we change how things work - for instance, you can create a collection and it fails to create on 4 nodes and succeeds on 3 - that collection will exist regardless the way things currently work - it just won't be what you wanted. That's a lot more effort to improve I think, but an all or nothing system would be nicer at some point IMO.

- When we don't know why the failure happens, a 400 is not appropriate as it blames the client.  500 is a better default.  Ideally the Overseer would look for a response code in the failed request to create a replica and propagate that.
