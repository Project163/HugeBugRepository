Title

[Ingest Pipeline] Date processor ignores timezone offset XXX

Description
Currently tested in Dev Console on 7.9.2 running on ESS.

**Steps to reproduce**:

It seems that timezone formats that work in pure Java is being ignored when using the date processor in ingest pipelines. Example:

```
POST /_ingest/pipeline/_simulate
{
  "pipeline": {
    "description": "_description",
    "processors": [
... [Log Snipped] ...
  ]
}
```

This will output:

```
{
  "docs" : [
    {
      "doc" : {
        "_index" : "index",
... [Log Snipped] ...
  ]
}
```

As you can see even though the offset is -04:00, and date processors defaults to UTC; it does not calculate any offset?

The same behavior is seen with other offset examples like `Z`, `z`, `VV` etc.

The same format in Java will work (sample code provided by @marc-gr ):
```
import java.util.*;
import java.util.Date;
import java.text.SimpleDateFormat;
public class Main {
    public static void main(String[] args) throws Exception {
... [Log Snipped] ...
    }
}
```

Anyone know if this is intended behavior?
Discussion
- Pinging @elastic/es-core-features (:Core/Features/Ingest)
- @P1llus , I think there are two problems:
1. If `timezone` is set to `UTC` explicitly, the time zone specified in the format will be ignored, we can find that from the source code: [Link: DataFormat.java]. So `timezone`  canot be set to `UTC` if we want to parse the timezone from the field `message `.

2. When we remove the `timezone` parameter, nothing changed! That's because the year format `YYYY` is `week based year`, there's a bug I think: [Link: DataFormat.java]. The workaround is setting the year format to `yyyy`. 

Finally, we can use `date processor` as follows:

```
{
  "pipeline": {
    "description": "_description",
    "processors": [
      {
... [Log Snipped] ...
  ]
}
```
- Using yyyy resolved the issue indeed @gaobinlong , thanks for the pointer there! Will take a look at the bug you mentioned and see if we should keep this issue open.
- I think the bug is valid. I thought I fixed this in [URL] but I missed this use case.
I will work on it
