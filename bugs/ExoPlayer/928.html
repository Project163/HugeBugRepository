Title

Potential bug in calculation of trackBitrates in AdaptiveTrackSelection

Description
### ExoPlayer Version

2.17.1

### Devices that reproduce the issue

A proprietary device running Android 10

### Devices that do not reproduce the issue

_No response_

### Reproducible in the demo app?

Not tested

### Reproduction steps

This is not a user facing bug and it was noticed during debugging.
While an HLS playback is being established check (with a debugger or log) what is being summed in the following loop in AdaptiveTrackSelection.java:

```Java
    for (int i = 0; i < checkpointBitrates.length; i++) {
      totalBitrate += checkpointBitrates[i];
    }
```
It looks like the values for checkpointBitrates are coming from 

``` Java
definition.group.getFormat(definition.tracks[j]).bitrate
```
which can contain the value of Format.NO_VALUE (= -1)

As 'normal' values in checkpointBitrates have the order of magnitude of 10^6 this does not change behavior in any significant way, however, this still feels like a bug. 

### Expected result

totalBitrate has a value equal exactly to the sum of all the bitrate components.

### Actual result

totalBitrate has a value slightly lower than the sum of all the bitrate components.

### Media

Not applicable

Discussion
- The HLS spec requires every #EXT-X-STREAM-INF tag to have the BANDWIDTH tag defined. See [URL]  _Every EXT-X-STREAM-INF tag MUST include the BANDWIDTH attribute._

This value eventually ends up in the track bitrates. In addition, ExoPlayer has safeguards to only include tracks with a defined bitrate in adaptive track selections in its `DefaultTrackSelector`. All this together implies that the code in `AdaptiveTrackSelection` can assume that all bitrates are set and none of them are `Format.NO_VALUE`. 

If you have a case (using ExoPlayer's default classes) where this isn't true, please provide an example playlist to reproduce the issue (or send it dev.exoplayer@gmail.com with "Issue #10664" in the subject).
