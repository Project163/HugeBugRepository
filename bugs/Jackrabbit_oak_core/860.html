Title

OrderedIndex does not comply with JCR's compareTo semantics

Description
The ordered index currently uses the lexicographical order of the string representation of the values. This does not comply with  JCR's compareTo sementics   for e.g. double values.
Discussion
- In the index we receive only Strings and  no knowledge of the original type . 

  
 IndexStoreStrategy.update(NodeBuilder,  String , Set< String >, Set< String >)
 
  

 while a proper fix would require an API change that pass down the original type I could add some heuristic inspection of the value to see if it's a number/decimal or not and adding therefore padding of   MAX_STRING_LENGTH    0s . 

 Would that suit?
- I wouldn't go for the heuristic as it could be wrong in the case where people intentionally put numbers in strings. It would e.g. change the place in a list of strings where the "numbers would go". Also how would you handle doubles? e.g. 2.0E17 < 1.0E18 but "2.0E17" > "1.0E18". 

 If we want to resolve this by encoding the values to strings such that the lexicographical order of the encoded values correspond to the compareTo semantics of the underlying values then  org.apache.jackrabbit.oak.plugins.index.property.PropertyIndex#encode  would probably be the right place to do that.
