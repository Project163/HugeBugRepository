Title

array_insert() give wrong results for ngative index

Description
Unlike in Snowflake we decided that array_inert() is 1 based. 
This means 1 is the first element in an array and -1 is the last.  
This matches the behavior of functions such as substr() and element_at(). 

   
  
 
> SELECT array_insert(array( 'a' ,  'b' ,  'c' ), 1,  'z' );
[ "z" , "a" , "b" , "c" ]
> SELECT array_insert(array( 'a' ,  'b' ,  'c' ), 0,  'z' );
Error
> SELECT array_insert(array( 'a' ,  'b' ,  'c' ), -1,  'z' );
[ "a" , "b" , "c" , "z" ]
> SELECT array_insert(array( 'a' ,  'b' ,  'c' ), 5,  'z' );
[ "a" , "b" , "c" ,NULL, "z" ]
> SELECT array_insert(array( 'a' ,  'b' ,  'c' ), -5,  'z' );
[ "z" ,NULL, "a" , "b" , "c" ]
> SELECT array_insert(array( 'a' ,  'b' ,  'c' ), 2,  cast (NULL AS STRING));
[ "a" ,NULL, "b" , "c" ]
Discussion
- What is the desired behavior - is Snowflake's behavior 'standard'?
- srowen  There is no standard as such. 
However, there are multiple reasons not to be compatible with Snowflake: 
1. Precedence: SUBSTR('Hello', 1, 1) => 'H', SUBSTR('Hello', -1, 1) => 'o' (not 'l'). 
2. array access has been a mixed bag for us (some 0, some 1-based), but we have tried to move towards 1-based as well. e.g., element_at() is 1-based, and we use -1   to get the last element. 

 3. Snowflake had no choice but to use -1 for the second last element because 1 is their second element. Because they are 0-based they are unable to use array_insert() to append an element (short of passing the (length - 1) as parameter. So the proposal is  objectively more powerful.
