Title

Passing NaN to Float column in Oracle leads to crash

Description
**Migrated issue, originally created by Leonid Butenko**

Hi,

I think it might be somehow related to the #4259, but with floats now.

I use Oracle 11g, cx_oracle 6.3, oracle_instantclient 11.2 and sqlalchemy 1.2.7

here is my test program
```
import sqlalchemy as sa
import sqlalchemy.orm
import datetime
import sqlalchemy.ext.declarative

... [Log Snipped] ...
session.add(Pod(id=1, fval=float('nan')))
session.commit()
```

Here is the error I get
```
sqlalchemy.exc.DatabaseError: (cx_Oracle.DatabaseError) DPI-1055: value 
is not a number (NaN) and cannot be used in Oracle numbers [SQL: 
u'INSERT INTO nan_test (id, fval) VALUES (:id, :fval)'] [parameters: 
{'id': 1, 'fval': nan}] (Background on this error 
at: [URL]
```

Here is the way how to reproduce it in anaconda docker:
```

The following NEW packages will be INSTALLED:

... [Log Snipped] ...
    cursor.execute(statement, parameters)
sqlalchemy.exc.DatabaseError: (cx_Oracle.DatabaseError) DPI-1055: value is not a number (NaN) and cannot be used in Oracle numbers [SQL: u'INSERT INTO nan_test (id, fval) VALUES (:id, :fval)'] [parameters: {'id': 1, 'fval': nan}] (Background on this error at: [URL]
```

I'm not sure whether it is the correct place to report about this problem. It might be cx_oracle related issue. From my point of view, passing NaNs to floating columns should be a normal practice at least in the scientific world, so I thought sqlalchemy might handle this situation as well. Pls advise! 

The solution I found so far is to downgrade the version of cx_oracle to 6.0.1 or ealier.
```

The following packages will be DOWNGRADED:

    cx_oracle: 6.0.3-py27hc82e58e_0 --> 6.0b2-py27_0

2018-05-22 20:53:13,835 INFO sqlalchemy.engine.base.Engine COMMIT
```
So the problem should appear somewhere between version 6.0.1 and 6.0.3 of cx_Oracle and still exist in the most recent version 6.3.

- **Michael Bayer ([Link: @zzzeek]) wrote:**

it's a little confusing to explain how this is failing.  there are two fixes I can make both of which will resolve the above test script but differently.

first off, usually, if you have a special TypeDecorator, that implies you want there to be some special in-Python behaviors for it, which means you'd want to make sure that is specified when you reflect:

```
class Pod(Base):
    __table__ = sa.Table(
        "nan_test", Base.metadata,

        sa.Column("fval", BinaryFloat ),

        autoload = True, autoload_with = engine)

```

however, this is still not resolving your case, since the thing I'm doing for #4264 as well as the previous issue in this regard is not taking TypeDecorators into account.    That is the the first thing I have to fix.

Next, you really don't need to be using a TypeDecorator here, you should use a Variant (which is itself a TypeDecorator designed for this purpose):

    BinaryFloat = sqlalchemy.types.Numeric().with_variant(sa.dialects.oracle.BINARY_FLOAT(), "oracle") 

That still needs me to do the same fix since this is still a TypeDecorator.

But next, to confuse the whole matter entirely, you are reflecting the table, so that should be giving you the correct Oracle datatype in any case, and then you *dont* need to override the column, and it will all work.  But!  that is *also* not working since this type needs to be added to a list, right now you see:

/opt/mettools/envs/py27/lib/python2.7/site-packages/SQLAlchemy-1.3.0b1.dev0-py2.7-linux-x86_64.egg/sqlalchemy/dialects/oracle/base.py:1410: SAWarning: Did not recognize type 'BINARY_FLOAT' of column 'fval'

so there are two issues to fix and test.
