Title

erlang: struct member name conflicts due to lowercased names

Description
the erlang backend generates records to represent structs. instead of the unique sequential id they use the struct field name as the record keys. records in erlang do not support repeated keys so generated erlang modules do not compile 

 the most obvious fix is to refuse to generate code from structs with repeated keys but this means the erlang backend is not capable of handling all valid structs 

 the easiest fix is to switch structs to use the unique sequential ids as the keys of the record but this breaks backwards compatibility and probably necessitates generating helper functions to retrieve fields by name 

 also possible is switching to an erlang data structure that supports repeated keys but this would also require breaking backwards compatibility
Discussion
- The description for this ticket is confusing because you say 'repeated keys', and I immediately thought 'those shouldn't be allowed' and tried 
  
 struct foo {
1: string bar,
2: string bar
}
 
  
 Which when compiled with master gave 
  
 [ERROR:/Users/molinaro/projects/opensource/thrift-env/foo.thrift:4] (last token was '}')
"2: bar" - field identifier/name has already been used
 
  
 I then noticed that what is actually the problem is the lowercasing of record fields causing a conflict.  So an actual failing case is something like 
  
 struct foo {
1: string bar,
2: string Bar
}
 
  
 Which could be fixed by providing a generator option for erlang, called 'mixed_case' which just adds single quotes around all record keys and skip lowercasing anything, because while the current record definition for the second 'foo' struct above is currently this 
  
 -record(foo2, {bar :: string() | binary(),
               bar :: string() | binary()}).
 
  
 which does not compile, you could generate 
  
 -record(foo2, {'bar' :: string() | binary(),
               'Bar' :: string() | binary()}).
 
  
 which would compile fine.  By introducing a generator option, you could preserve current behavior for current invocations of 'thrift -gen erl', but get the new form with 'thrift -gen erl:mixed_case'.
