Title

Bug: Running CLI with only one rule fails to match any file

Description
### Environment

Node version: v20.18.1
npm version: v10.8.2
Local ESLint version: v9.18.0 (Currently used)
Global ESLint version: Not found
Operating System: darwin 24.2.0

### What parser are you using?

@typescript-eslint/parser

### What did you do?

When running eslint strictly using the CLI command it will report that no files are matching. But using the legacy engine through `ESLINT_USE_FLAT_CONFIG` works.

The use case is that we have a large repository (> 1M LoC) where we want to update rules from warn to error one at a time. And we want to use the auto fix of eslint to fix only a single rule, instead of all fixable problems.

The command I am trying to run for flat config:

```
bash
node_modules/.bin/eslint \
--plugin '@typescript-eslint' \
--parser '@typescript-eslint/parser' \
--parser-options '{"project":"packages/awesome-helpers/tsconfig.json"}' \
... [Log Snipped] ...
--no-cache \
"packages/awesome-helpers/src/**/*.ts"
```

### What did you expect to happen?

```
/path/to/packages/awesome-helpers/src/index.ts
  1:1  error  All exports in the declaration are only used as types. Use `export type`  @typescript-eslint/consistent-type-exports

✖ 1 problem (1 error, 0 warnings)
  1 error and 0 warnings potentially fixable with the `--fix` option.
```

### What actually happened?

```
Oops! Something went wrong! :(

ESLint: 9.18.0

You are linting "packages/awesome-helpers/src/**/*.ts", but all of the files matching the glob pattern "packages/awesome-helpers/src/**/*.ts" are ignored.

Discussion
- Thanks for the report. I can reproduce this.

So, the problem here is because you aren't using a configuration file and you're trying to lint a `.ts` file, which is not configured by default. ESLint only configures `.js`, `.cjs`, and `.mjs` by default, so all of the command-line options that take the place of a config file are only applied to those files and the one you passed on the command line doesn't match, so it's skipped. This is clearly an oversight in how everything works together.

I'm not sure what the right solution is for this. On the one hand, if `--no-config-lookup` is passed, we could assume that you intend for other options to be applied to just the files passed on the command line, but that would also mean you wouldn't be able to just pass a directory because we'd have no idea what you wanted to lint in there. 

Another approach would be to add back the `--ext` command line option that we initially removed with flag config. That would allow you to explicitly pass which files should match the other options on the command line.

@eslint/eslint-team thoughts?
- This is a ton of config to specify in the CLI:

ESLint _could_ add more options to allow specifying more and more things on the CLI. I'm not a fan of that direction. The spread of useful-in-narrow-scenarios cases like this is unbounded. I worry about the codebase and docs needlessly increasing in complexity to support them.

Instead, how about making a custom config file, and specifying the rule in there? It could even be passed in as an env var:

```
js
// eslint.one-rule.config.js
import eslint from "@eslint/js";
import tseslint from "typescript-eslint";
