Title

Confussing requirement condition evaluation with aliases and umbrella chart

Description
I've created an *umbrella* chart using 3 aliased copies a *foo* chart (foo1, foo2, foo3). *Foo* chart has a single dependency *foo-feature* that can be enabled or disabled (enabled by default). The picture below illustrates these dependencies. 
[Image: image]

My goal here is to make a deployment where foo3 has its 'foo-feature' disabled and other aliases have this feature enabled. Desired deployment:

[Image: image]

The natural course of action it would seem is to edit the values in the umbrella chart:
~~~
foo1:
  foo-feature:
    enabled: true

foo2:
  foo-feature:
    enabled: true

foo3:
  foo-feature:
    enabled: false
~~~

However, regardless of the true/false values I always end up with all 3 *foo-feature* being rendered.

How can I achieve the desired deployment?

I attach a tgz with all 3 charts. My test was to edit the values in the *umbrella* chart and then run:
[Link: example.zip]
~~~
helm template umbrella | grep Source: | grep deployment.yaml | grep foo-feature
~~~
to see how many deployments of *foo-feature* were rendered.

Discussion
- @groundnuty Unfortunately this appears to be a consequence of evaluating the condition from the true root of the computed values from the umbrella chart. If you change `foo/requirements.yaml`'s condition to `foo1.foo-feature.enabled` you will get different results (but its not a solution). There are some other issues arising from `alias` and `conditions` not working perfectly together and there is a suggestion to change it to a relative evaluation. 

I fear breaking backwards compatibility but Id like to enable your use case here since its so efficient on disk and facilitates a flat directory structure. If you would be interested in a proposal/PR i would help support it.
- It doesn't appear that aliasing is even necessary here. If a subchart's `requirements.yaml` includes `condition: foo.enabled` and I define subchart as a dependency in another chart, the only way to affect that condition is by setting `foo.enabled` _at the top level_.

This seems more like a bug in value resolution than anything. Every other value I want to override goes into `subchart.key = value`, so why would a condition in the requirements need `key = value` instead? This is especially misleading when the subchart is referring to a dependency both charts share because now my `values.yaml` looks like this:

```yaml
common-thing:
  thing1: thing2
  enabled: false
subchart:
  what: ever
```

It looks like `common-thing` is disabled, but in reality it's there purely for `subchart` to avoid having *it* require `common-thing`, thereby breaking the install with "service `my-common-thing` already exists`.
