Title

createMessage(PlayerMessage.Target target) gives multiple callback.

Description
Our requirement is to have a callback at different time positions of the video duration. 

Below is our method to set createMessage() with the callback.

        fun addCuePosition(cuePositionInMillisecond: Int) {
            simpleExoPlayer
                    .createMessage(PlayerMessage.Target { messageType, payload ->
                        HDialogue.log("payload = $payload")
                    })
                    .setPosition(cuePositionInMillisecond.toLong())
                    .setPayload(cuePositionInMillisecond)
                    .setDeleteAfterDelivery(false)
                    .send()
        }


However, 
1) Once Player is prepared 
2) all the positions are set 
3) then we call simpleExoPlayer.seekTo(position.toLong()), here position is one of the same exact values which we set in create messages. 
Then it gives continuous multiple callbacks for PlayerMessage.Target, even before the video starts playing and also while it is playing.

Note:
I am new to ExoPlayer2, and we are planning to replace our existing media player [URL] with ExoPlayer. So we are looking for similar feature addCue, removeCue, setOnCueListener as in that library. 

Let us know if createMessage is not suitable for this and there is another method we can use instead. We referred [URL] and [URL]
Discussion
- I would say that using createMessage is the right thing for this use case. That works for me when trying this out:

```
int positionMs = 30_000;
player.createMessage((messageType, payload)
         -> Log.d("player-message", payload.toString()))
     .setPosition(positionMs)
     .setPayload("payload 1")
     .send();
player.seekTo(positionMs);
player.prepare(mediaSource, false, false);
```

I think it is expected that the message is sent at the moment when the position defined is reached. There is no guarantee that this is only fired when in STATE_READY. So receiving the message while in STATE_BUFFERING sounds ok to me in case you are seeking to this position.
- Marking as a bug as setting 

```
.setDeleteAfterDelivery(false)
```

produces the continuous delivery of the message while the player is on the same position in BUFFERING_STATE.
- I think this is triggered by our special handling for the start position. In all other cases, we only trigger an  event when the requested time actually passed (and not when it stays constant).
