Title

`firstChange` not set properly in `ngOnChanges` for pre-bound properties

Description
# 🐞 bug report

### Affected Package
The issue is caused by package @angular/elements

### Is this a regression?
No.

### Description
When a property is set on an element prior to it being attached to the DOM, the initial call to `ngOnChanges` does not have `firstChange` properties set to `true`.

This requires code from #36114, to fix #30848 in order for `ngOnChanges` to fire at all -- this is a follow-on issue.

## 🔬 Minimal Reproduction
[URL]
You can look at console logs to see lifecycle events for both the Native Angular element, and the Custom Element. The reproduction uses artifacts from a [Link: CI build] associated with #36114.

There is a secondary issue here, that is -- event listeners on component outputs won't fire during `ngOnInit`, `ngOnChanges`, `ngAfterViewInit`, and `ngAfterContentInit`. This is in contrast to the native element which does fire the callback during these hooks. You can see this by examining the `ul` and `li` elements in each section.

- I just updated the repro project locally with the new artifacts and it looks to be working well. I also tested not setting the input property right away and doing it later, and it correctly omits the property from `changes` at first, and later includes it with `firstChange` in that case 👍. This scenario isn't really possible with a Native Element -- you can either set `undefined` explicitly (which behaves identical to the Custom Element now, hooray!) or make it an optional `@Input` and not set it at all (which also behaves identically to the Custom Element during initialization).
