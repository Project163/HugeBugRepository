Discussion
- this was not tested on 5.0, but very likely happens there as well
- been debugging this issue, and my findings are as follows 

 1) the test does partial updates to rows/partitions 
2) the flush isn't nodetool flush, but instead triggered by nodetool repair 
3) nodetool repair flushes based off the repair ranges, so generates 1+ sstables 

 What I see so far is that there are writes to the index, but for partition X, which exists in SSTable 3.  SSTable 1/2 do not have any updates for the column, yet don't look to remove the index from the SSTable's Components.  Since the SStables 1/2 never saw the column, the Meta file doesn't get created, but its present in the TOC; when we validate this on the peer we fail as we don't see the metadata file!
