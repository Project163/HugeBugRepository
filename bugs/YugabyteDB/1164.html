Title

[DB Clone][YSQL] DB Cloning is not happening to the time before table drop

Description
DB Cloning is not happening to the time before table drop
Steps:

1. Create database(demo1) and create snapshot schedule
2. Create table and load some data
3. Collect time(t1)
4. Drop table
5. Clone demo1 to demo2 at time t1

Observations
1. DB clone command works and returns namespace id and seq number, but is_clone_done command returns false and there wont be any cloned DB

Discussion
- Cannot reproduce. Likely fixed by #21572.
- Initially, we thought this is a duplication of  #21572 . However, it turns out that this is another issue in YSQL case only.
It mainly happens as `ysql_dump` is failing with the following error:

```
I0509 19:43:46.936661 175723 client_master_rpc.cc:77]   -> GetTableSchemaRpc(table_identifier: table_id: " ", num_attempts: 1): Failed, got resp error: Service unavailable (yb/master/catalog_manager_util.h:162): The object ' .t' is not running: OBJECT_NOT_FOUND (master error 3)
W0509 19:43:46.937044 175723 client-internal.cc:1556] GetTableSchemaRpc(table_identifier: table_id: " ", num_attempts: 1) failed: Service unavailable (yb/master/catalog_manager_util.h:162): The object ' .t' is not running: OBJECT_NOT_FOUND (master error 3)
```
`ysql_dump` fails in case the `read-time` option is used to dump the data/schema as of time `t` and `t` is a time before a drop table happens. This is due to bad interaction between `--include-yb-metadata` and `--read-time` options.  In fact,  part of including YB metadata, a select query `select * from yb_table_properties('table_name'::regclass);` is issued. This in turn sends a `GetTableSchema` rpc to the master leader.
The master leader returns `The object 'table_name' is not running` as the table is in a hidden state (dropped tables covered by a snapshot schedule are marked as hidden).
Using `--include-yb-metadata` is required for backup/restore, specially for the colocated case as it contains the `colocation_id`. Therefore, we need to make the two options work together.
- The proposed solution is to return the TableSchema of table `T` as a response to the `GetTableSchema` rpc even-though `T` might be marked as hidden (not always though).
The successful return of `GetTableSchema` in case of a hidden table will only happen when the client provides the table id in the `GetTableSchemaRequestPB`. This should be the case for all YSQL tables as table names cannot be used as identifiers and might introduce ambiguity due to Postgres concept of "schemas".  The assumption is that there is no harm in returning the TableSchema of a hidden table as long as the client requests the table by id. 
In contrast, TableSchema of a hidden table isn't returned in case only table name is provided as identifier.
