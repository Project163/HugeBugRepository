Title

invalid EstimatedHistogramReservoirSnapshot::getValue values due to race condition in DecayingEstimatedHistogramReservoir

Description
`DecayingEstimatedHistogramReservoir` has a race condition between `update` and `rescaleIfNeeded`. 
A sample which ends up (`update`) in an already scaled decayingBucket (`rescaleIfNeeded`) may still use a non-scaled weight because `decayLandmark` has not been updated yet at the moment of `update`. 
  
The observed consequence was flooding of the cluster with speculative retries (we happened to hit low-percentile buckets with overweight samples, which drove p99 below true p50 for a long time). 

 Please note that despite the manifestation being similar to  CASSANDRA-19330 , these are two distinct bugs in their own right. 

 This bug affects versions 4.0+ 
On 3.11 there's locking in DEHR. I did not check earlier versions.
Discussion
- I see three ways to solve this. 
 
	 Introduce RW locks (read for `update`, write for `rescale`), just like codehale does it 
	 trade some correctness in the hope of achieving better update throughput i.e. invert the consequences of the race condition: make the `update` path (that doesn't do rescale) non-blocking, and make the `rescale` path blocking (block until the already started updates finish); this inverts the race condition effects i.e. there may be some too-little weighed samples at the very end of the `LANDMARK_RESET_INTERVAL_IN_NS` interval 
	 trade some correctness (just like above) and add some more complexity to make the `rescale` separate from the `update` path, with the benefit of non-blocking of every `update` 
 

 I will measure the performance impact of 1 and 2 to make an informed decision...
- [URL]

 The proposed PR keeps changes to almost a minimum to stay consistent with the current state of DEHR.  

 The solution doesn't introduce synchronization between updates and rescales for the sake of update performance. Instead, it introduces an atomic change of decay landmark and decaying buckets together. This lets us keep updates non-synchronized at the price of letting some updates be missed during rescale. It also prevents the creation of snapshots that are half-rescaled.
