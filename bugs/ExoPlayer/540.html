Title

The stream which width/height are not aligned with VideoCapabilities.mWidthAlignment/VideoCapabilities.mHeightAlignment can't be played.

Description
### [REQUIRED] Issue description
As described in #[URL] If the HLS live output stream's resolution is 1129 * 480,  the player can't played it.  
The decoder's capabilities are not support the width/height which not aligned with `VideoCapabilities.mWidthAlignment / VideoCapabilities.mHeightAlignment`.

Discussion
- I think it's a property of H.264 itself that odd resolutions are not supported. In which case 1129 in not a valid width, and so it's correct that the decoder (or any decoder, for that matter) would not advertise support for it.

I think the problem here is just that the RESOLUTION tag in `hls.m3u8` is incorrect. The real width of the stream is 1130, as seen if you inspect the actual media using a tool like `mediainfo`:

```
[...]
Width                                    : 1130 pixels
Height                                   : 480 pixels
[...]
```
- So this is an error in the source media. If it's your media then you should fix it [edit: I just saw your shaka bug. If they're responsible for generating `hls.m3u8` then it seems like a bug in their packager?].

I think we've seen the same issue before, so we might put a workaround into ExoPlayer that'll round odd H.264 resolutions up to the nearest even resolution. Note that this assumes the error in the source media is a rounding error. Let's use this issue to track deciding whether we want to do this.

- @ojw28 I believe there is another bug in ExoPlayer. 

The resolution in HLS master playlist is the "display" resolution. See [URL]

      VIDEO attribute, then every alternative video Rendition MUST have
      an optimal display resolution matching the value of the RESOLUTION
      attribute.

The display resolution is not the same as frame resolution (a.k.a storage resolution or codec resolution) for non square pixels. 

As shown in [URL] the content has a frame resolution of 1130:480 and a display resolution of 1129:480. 

The player should use frame resolution instead of display resolution when querying video capabilities as frame resolution is what decoder cares. 
 - For mp4 files, frame resolution can be extracted from width and height in Sample Description box.
 - For TS files, the player has to inspect SPS to extract the frame resolution.
- It's unfortunate that the HLS specification has defined it that way...


It's infeasible to implement this efficiently, since it would require downloading the start of every variant prior to the start of playback. The increased latency doesn't seem like an acceptable tradeoff, so I think it's better to leave things as they are now. Note that the commit referenced above should solve the problem in practice unless the display and frame resolutions are significantly different, which is not something we've seen in practice.
