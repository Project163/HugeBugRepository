Title

[YSQL] Scanning snapshots for CURSOR is set at different TIMESTAMP between Postgres and YugaByte DBMS

Description
Jira Link: [Link: DB-4863]
The scanning snapshot is set at different timestamp between Postgres and Yugabyte.
- Postgres uses a snapshot at the 'DECLARE CURSOR' timestamp to scan.
- Yugabyte uses a snapshot at the 'FETCH' timestamp to scan.

This difference shows up in the following examples - One for STABLE FUNCTION, and another for CURSOR's row-lock.

**Example 1: Execution schedule for STABLE FUNCTION is different between Postgres and YugaByte**
Postgres and YugaByte has different schedules for STABLE FUNCTION when using CURSOR to execute function. They uses two different timestamps for execution.
- Postgres uses the 'DECLARE CURSOR' timestamp to execute.
- Yugabyte uses the 'FETCH' timestamp to execute.

The following examples illustrate the above observation.

1. Output from Postgres
```
postgres=# create table tab(f1 int);
CREATE TABLE
postgres=# create function cnt() returns int8 as 'select count(*) from tab' language sql;
CREATE FUNCTION
postgres=# create function cnt_s() returns int8 as 'select count(*) from tab' language sql stable;
... [Log Snipped] ...
   4 |     1
(1 row)
```

2. Output from YugaByte
```
yugabyte=# create table tab(f1 int);
CREATE TABLE
yugabyte=# create function cnt() returns int8 as 'select count(*) from tab' language sql;
CREATE FUNCTION
yugabyte=# create function cnt_s() returns int8 as 'select count(*) from tab' language sql stable;
... [Log Snipped] ...
   4 |     4
(1 row)
```

**Example 2: Different set of rows are locked between Postgres and Yugabyte**
As they chose different snapshot at different timestamp, the rows to be locked might be also different.
- Postgres would lock rows that are in the table when DECLARE command is executed.
- Yugabyte would lock rows that are in the table when FETCH command is executed.
