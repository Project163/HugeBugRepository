Title

base logging helper function clobbers log message metadata

Description
### Describe the bug

[Link: `lib/sqlalchemy/engine/base.py` contains a logging helper function]:
```python
    def _log_info(self, message, *arg, **kw):
        fmt = self._message_formatter

        if fmt:
            message = fmt(message)

        self.engine.logger.info(message, *arg, **kw)
```
Using this function will cause all emitted log messages to contain the metadata `function='_log_info'` and `line=131`. This makes it harder to group and filter messages.

### To Reproduce

```
python
import sqlalchemy.engine.base
import logging
from unittest import mock

... [Log Snipped] ...
mock_self._message_formatter = None
sqlalchemy.engine.base.Connection._log_info(mock_self, "Metadata overwritten")
```


### Error

```
2022-01-25 10:09:48,658  :12: Message with correct metadata
2022-01-25 10:09:48,658 _log_info:131: Metadata overwritten
```

### Versions

- OS: independent
- Python: independent
- SQLAlchemy: 1.4.6 and newer, haven't checked when this was introduced


### Additional context

I don't have a ready solution that allows retaining the metadata with a helper function (ie. it's not as simple as adding a `stacklevel=2` with the `warnings` module)
Discussion
- im not familiar with "funcname" and "lineno" tokens in logging, and IIUC from what you have there it looks like it's doing some kind of traceback inspection when you emit a log line, which means that no logging helper functions of any kind can be used by any application.   if I have all that right, that's unfortunately an unreasonable constraint so I wouldnt see any way to fix this.   But this is just my reading in the last 30 seconds, so correct me if im not getting it right.

I would recommend setting a separate formatter for the sqlalchemy.engine namespace that has the prefixing information you want pre-formatted.
- [Link: funcname and lineno are part of the Python `LogRecord` object, next to 'message'], which is of course the text that is usually shown on stdout. However all the other fields are on an equal level, even if not shown. For my use case we forward all logging records to a graylog server, where they are aggregated. All sqlalchemy related log messages are shown as coming from the same file, the same function, and the same line, although it is clear that they come from separate log calls. This makes it hard to filter for relevant messages.
[Image: image]

Judging from the code the only reason these helper functions exist is to include prefixes into the log message, specifically a [Link: `logging_token`]. That token is then prefixed into the message.

This is unfortunate, as a cleaner way would have been to leave the message alone, add the token as an [Link: _`extra`_] field to the log message (example from the Python logging documentation):
```python
d = {'clientip': ' ', 'user': 'fbloggs'}
logger = logging.getLogger('tcpserver')
logger.warning('Protocol problem: %s', 'connection reset', extra=d)
```
That way the field can be directly filtered on, the original message is retained - and there would not be a need for a helper function, therefore you'd also get the correct logging context in the message (There's no need to add the field to every individual message, [Link: a `LoggerAdapter` can do that for you]).

I guess the main underlying issue is that people weren't aware that the logging framework does a lot more underneath the hood than just carry a flat string...

I'm happy to have a look into upgrading SQLAlchemy to make full use of python logging framework features. It would probably be incompatible with the current `logging_token` functionality though.
