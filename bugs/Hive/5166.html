Title

LLAP: GroupByOperator flushes hash table too frequently

Description
GroupByOperator::isTez  would be true in LLAP mode. Current memory computations can go wrong with  isTez  checks in  GroupByOperator . For e.g, in a LLAP instance with Xmx128G and 12 executors, it would start flushing hash table for every record once it reaches around 42GB (hive.tez.container.size=7100, hive.map.aggr.hash.percentmemory=0.5).

Discussion
- For LLAP, GBY hashtable memory should be shared by all executors. The problem is with tracking memory usage per thread. There is already an open jira for this.  HIVE-15508  
Ideally, we want to track memory usage per executor and flush based on usage vs max memory available per executor ratio.
