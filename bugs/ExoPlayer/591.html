Discussion
- I think this is working as intended. Can you elaborate why you think the documentation of `onRenderedFirstFrame()` is not matching the behaviour you see?

I'm a bit confused around the mediaPos=0.00 which shows up in your logs above from BUFFERING and then goes back to 281.77 (if you think this is relevant, can you send me the uri to the media?).

However, my understanding of `seekProcessed` is, that the player has selected the next period to be played and updated the public playback position accordingly. No data is necessarily downloaded at this point and when needed this starts after updating the playback position. Rendering the next frame is then done by the render component. It obviously needs data first for rendering and this can only happen after updating the playback position which needs to be known before.

When I looked into this on my device the log was as follows:

```
D/EventLogger: loading [eventTime=27.31, mediaPos=86.83, window=0, period=0, true]
D/EventLogger: state [eventTime=27.31, mediaPos=86.83, window=0, period=0, BUFFERING]
D/EventLogger: isPlaying [eventTime=27.31, mediaPos=86.83, window=0, period=0, false]
D/EventLogger: seekProcessed [eventTime=27.31, mediaPos=86.83, window=0, period=0]
D/EventLogger: renderedFirstFrame [eventTime=28.30, mediaPos=86.83, window=0, period=0, Surface(name=null)/@ ]
```

It shows that the first four events are issued at the very same event time. They have been notified in the same listener iteration as we call this. The the renderFirstFrame event happens at eventTime 28.30 which is not in the same iteration as the other events because, it is issued by the renderer after the data has been made available.

Does this make sense? Please let me know if you think the documentation is misleading.
- I think the point is that seeking doesn't fall into either of the cases that the documentation says the event is fired for:

1. Called when a frame is rendered for the first time since setting the surface - Not true
1. and when a frame is rendered for the first time since a video track was selected - Also not true

It's worth noting that the same method in both `AnalyticsListener` and `VideoRendererEventListener` is documented differently, and more accurately, so we probably just need to update the `VideoListener` documentation to say the same thing?
