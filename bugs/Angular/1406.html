Title

i18n doesn't play nicely with interpolated attr.attr-name

Description
### Which @angular/* package(s) are the source of the bug?

compiler, localize

### Is this a regression?

Yes

### Description

i18n doesn't produce the output I'd expect when used on an `attr.attr-name` attribute. My hope here is to be able to translate interpolated aria attributes, e.g.: `  ` -- which I am trying to use because Angular rejects an interpolated `aria-label` without the `attr.`. My example here uses `title` instead of `aria-label` just so I can provide more "working" variations.

1. Create a new project with the CLI and `ng add @angular/localize`.

2. Put the following in app.component.html
```html
 case 1 
 case 2 
 case 3 
 case 4 
```

3. Run `npm start` and visit in a browser.

I see the following rendered markup:
```html
 
   case 1 
   case 2 
   case 3 
   case 4 
 
```

The `title` attribute is misnamed `attr.title` in case 3 and is omitted in case 4.

I would expect the following instead:
```html
 
   case 1 
   case 2 
   case 3 
   case 4 
 
```

v11.2.14 with Ivy enabled gives the same output as v12. With Ivy disabled, case 4 has a `title` attribute as expected. Case 3 still has `attr.title` in the output either way.  (Case 3 is output as a literal `attr.title` even without i18n; am I misunderstanding how `attr.` is supposed to work, or is that wrong as well?)

4. Run `ng extract-i18n`

In the resulting messages.xlf file, case 4 is missing. I tried this with Angular v11.2.14 and if ivy is disabled, it gives the expected result (all four cases present); if ivy is enabled, case 4 is missing.

- Here is another reproduction: [URL]

```
html
 case 1 
 case 2 
 case 3 
 case 4 
... [Log Snipped] ...
 aria 5 
 aria 6 
```

Only three i18n messages are generated:

```ts
i18n_0 = $localize `:@@case1:case 1`;
i18n_2 = $localize `:@@case2:case ${{ '{' }}"\uFFFD0\uFFFD"}:INTERPOLATION:`;
i18n_4 = $localize `:@@aria1:aria 1`;
```

* `case 1` and `aria 1` are expected and correct: the system correctly generates i18n messages for static attributes that are marked with `i18n-...`.

* `case 2` is correct and expected: the system is able to generate an i18n message for an interpolated property (not attribute). This only works because the DOM element has a `title` property as well as a `title` attribute - and the two are mapped to each other by the DOM.
  Unfortunately, as mentioned in this issue, it is not possible to use this approach for ARIA attributes since they do not have an equivalent DOM property.

* `case 3` and `aria 3` are correct and expected: the i18n message extraction is not able to process property bindings of the form: `[prop]="expression"`.
  By the way, this is the correct usage of `attr....` to bind any expression to an attribute - as documented in [URL]

So finally we come to cases 4, 5 and 6. 

* 4 and 6 set the `title`/`aria-label` correctly, but do not generate an i18n message
* 5 does neither!

I think that case 4 is actually the usage that we want to support. When matching `i18n-` markers to attributes we should ignore the `attr.` prefix from the attribute name.

So I think that is the bug that needs to be fixed. Probably around this bit of code: [URL]

@petebacondarwin thanks for the investigation! The current logic in inline with ViewEngine extraction mechanisms (in VE the `attr.xyz` is not extracted), but since VE is now deprecated (and people would not be switching between Ivy/VE anymore), we can extend Ivy to take care of more scenarios. I think scenario 4 and 5 are good candidates. My only concern regarding scenario 4 (`attr.aria-label="aria {{4}}" i18n-aria-label="@@aria4"`) is that it might not be straightforward for users since the existing mental model is that you just prefix whatever you want to translate with `i18n-`, so I'm leaning towards `i18n-attr.xyz` as a marker. However we can also consider supporting both `i18n-attr.xyz` and `i18n-xyz`. What do you think?
