Title

KeyCache deserialization doesn't properly read indexed entries

Description
When we write the key cache, we write the RowIndeEntry entirely, as can be seen in  CacheService.KeyCacheSerializer.serialize : 
  
 ByteBufferUtil.writeWithLength(key.key, out);
out.writeInt(key.desc.generation);
out.writeBoolean(true);
key.desc.getFormat().getIndexSerializer(cfm, key.desc.version, SerializationHeader.forKeyCache(cfm)).serialize(entry, out);
 
  
 When we deserialize such entry, we have the case where an entry correspon to a sstable that doesn't exist anymore (presumably, it's been deleted between the last cache saving and the restart that triggers the cache loading), which goes this way: 
  
 ByteBuffer key = ByteBufferUtil.read(input, keyLength);
int generation = input.readInt();
SSTableReader reader = findDesc(generation, cfs.getSSTables(SSTableSet.CANONICAL));
input.readBoolean(); // backwards compatibility for "promoted indexes" boolean
if (reader == null)
{
    RowIndexEntry.Serializer.skipPromotedIndex(input);
    return null;
}
 
  
 But the thing is,  RowIndexEntry.Serializer.skipPromotedIndex  doesn't skip a full  RowIndexEntry , it doesn't skip the position in particular, and so as far as I can tell, that part is buggy. I believe we should call  RowIndexEntry.Serializer.skip . 

 I'll note that I just noticed this while reading the code but I haven't reproduced that problem personally. I also haven't pin-pointed the exact source of that problem, but it's been there for a while as far as I can tell. At the same time, the condition to reach that branch is probably pretty uncommon, and failure to load the key cache does not prevent the node from starting and it doesn't even seem that we log an error (we log at DEBUG, maybe we should log at WARN), which would explain nobody reporting this.
Discussion
- Pushed  2.1  and  3.0  branches with fix. 

 The fix replaces the  skipPromoted  with  skip  and adds a test of recovering the rest of the cache after losing an sstable. It is very rare that this could cause problems of any kind (truncation or drop are fine as the whole of the cache for that CF is invalid in that case), and since the potential problem is some missing cache entries I think we were right to not even log it at a significant level. Feel free to change the "harmless error" log level in  AutoSavingCache  when committing if you disagree. 

 That exception wasn't even firing with the old code as the wrong skip causes the next read to see a very high length, which in turn causes the rest of the file to be skipped without raising an exception as  FileInputStream  happily reports skipping over more than the length of the file. 

 Both patches include warning clean-up; in the 3.0 version I've taken the liberty to remove the generic type parameter of  RowIndexEntry , which wasn't used in any way but caused quite a few unnecessary raw type warnings.
