Title

[YSQL] GIN index backfill batching can miss deadlines

Description
Jira Link: [Link: DB-1126]
When working with GIN indexes where each row's indexed column is large, it can fail to make progress in index backfill because master-tserver deadline is not met and master resends the BackfillChunk RPC.

Master sends BackfillChunk RPCs to tserver asking it to backfill a tablet starting from a given partition key.  Tserver sends `BACKFILL INDEX` requests to its local tserver asking it to backfill starting from a given partition key up to a given limit (default 128).

Tserver needs to respond to master before the master-tserver deadline (default 60s).  Tserver therefore keeps track of time and, by default, once it finds there's only 1s left till deadline, it wraps up and responds.  If tserver doesn't check the time within every 1s (ideally less), the deadline may be missed.

The tserver-postgres RPC can take a long time for GIN indexes: an indexed column value may expand to many index writes.  Then, it is possible for it to take over 10s.  This makes it much more likely to miss the master-tserver deadline, causing master to send a retry RPC with the same start partition to redo the work.

Another issue is that this can possibly go undetected: there may be a lot of master-tserver RPC retries, but if they happen to succeed sometimes, the index backfill may finish, though it took much longer than it needed.  For users, this may be difficult to figure out since there isn't much progress-reporting, especially on ysqlsh language side.  Probably simplest way to catch these is looking for WARNING logs like `BackfillIndex RPC (request call id 27) to  :9100 timed out after 60.000s`.  A deeper look is using `--vmodule=tablet=2` on tserver and looking at tserver logs.

For solution, I'm not sure yet.  Maybe GIN indexes can have a lowered batch size, but the effectiveness/viability of this depends on whether we know the index is GIN and estimates of how big each column value is.  Maybe switching to a time-based timeout approach is worth it.
