Title

[bug] naming an argument `cmd` causes unexpected and undocumented error

Description
### Describe the bug

I named an argument for a custom command `cmd`, which used to work previously but now it seems to be a special name that gets treated differently by tauri. In fact it seems to override the command specified as the first parameter to `invoke()`.

```rust
#[tauri::command]
pub fn my_command(
  cmd: String
) -> Result  {
    info!("This never gets logged");
    Ok(String::new())
}
```
I invoked it from JS like this:
```
window.__TAURI__.invoke("my_command", {cmd: "test"})
```
and instead of calling my_command and passing that argument, it returns the error message `command "test" not found` in the frontend and the backend command was never executed.

This seems really strange to me. Why would certain argument names be considered special?
Is this documented anywhere?

Given that there are such special argument names, could these please be documented here? or at least somewhere prominent?
[URL]

Even better, I'd argue that any "special" args internal to tauri should be an optional 3rd parameter to invoke() rather than overloading the user-supplied args list.

### Reproduction

```rust
#[tauri::command]
pub fn my_command(
  cmd: String
) -> Result  {
    info!("This never gets logged");
    Ok(String::new())
}
```

Now try to invoke the above command. This doesn't work:
```
window.__TAURI__.invoke("my_command", {cmd: "test"})
```
Instead it gives the error `Uncaught command test not found`

### Expected behavior

I'd expect all of the arguments given in the 2nd parameter to `invoke()` to be delivered to my function regardless, and not to have any "magic" args that are treated differently. Any such special internal args should be in a separate parameter given to `invoke()`
