Title

Http2MultiplexCodec leaks ping payloads

Description
### Expected behavior

The payload of a PingFrame would be released or passed somewhere into the application for consumption.

### Actual behavior

It appears that `Http2PingFrame`s are dropped on the floor in the [Link: `Http2MultiplexCodec.onHttp2Frame`] method.

### Steps to reproduce

Start HTTP/2 server and send it ping frames with advanced leak detection yields logs as follows:

Copying _8_ bytes? The ByteBuf pointer chasing and vtable indirection will be much more costly than that. And a pointer is 8 bytes, so we're _already_ copying the equivalent amount of data. And a pointer assignment is also more expensive in Java to coordinate with the GC. The ByteBuf will also need read and write indexes and a capacity and ref counting and...

The copying could be a bigger concern for GOAWAY, but the messages tend to be short. (I've not seen one larger than, say, 16 bytes?) But the GOAWAY case is also the one that benefits the most, in that [Link: we're duplicating a DefaultHttp2GoAwayFrame and a ByteBuf for each child channel]. That's (8+4+4)+(8+4+4+4+4+4) = 44 bytes (assuming a DuplicatedByteBuf). If we used a byte[], we could actually share the same DefaultHttp2GoAwayFrame across all child channels, because there's no longer the readerIndex.

To me, the argument for keeping it as a ByteBuf is that it is convenient, because people are familiar with working with them.
- Agreed `ByteBuf` currently has a high constant overhead and is bloated for small payloads (which is exacerbated by duplication/wrapping). Good point about the payload size. Even if its a few hundred bytes (GOAWAY debug information) it is likely a rare occurrence and may not be worth the extra complexity. I think the main selling point would be consistency, but I agree it doesn't seem worth it. @normanmaurer - WDYT?


Sharing should be possible either way, no? Just with `ByteBuf` it requires reference count management and may not incur framing overhead (copy from byte[] to the frame to write).
