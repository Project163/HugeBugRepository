Title

Segmentation fault is raised when torch._C._nn.adaptive_avg_pool2d is called with some parameters

Description
### 🐛 Describe the bug

The segmentation fault appears when `torch._C._nn.adaptive_avg_pool2d` is called for some combinations of input and output shapes.

#### Code example

Here is the python script named `test.py`.

```
python:test.py
from __future__ import annotations
import sys
import torch

... [Log Snipped] ...
    imgs = torch.randint(low=0, high=256, size=(1,)+_input_size).type(torch.float32)
    imgs_ = torch._C._nn.adaptive_avg_pool2d(imgs, _output_size)
```

By using this script,
all lines below raise `Segmentation fault (core dumped)`.

```
python test.py 5877 3697 2855 1
python test.py 5877 3697 2863 1
python test.py 4757 560 3527 2219
python test.py 5873 3693 3527 2219
```

#### A comment on parameters

Here are some combinations I found:

* input = `(1, 5877, 3697)`, output = `(2855+4*i, j)`
  for any i,j >= 0 as far as I checked

* input = `(1, 4757+4*i, j)`, output = `(3527, 2219)`
  for any i >= 0 and many j > 200 (?) as far as I checked
  examples of j are 280, 560, 867, 870, 884, >= 1060 at least

It seems there are other patterns and some rules behind but I don't know.

Discussion
- It seems the kernel is running into an invalid read [Link: here]:
```
sum += accscalar_t(input_ptr[ih * input_width + iw]);
```
where `ih` has a value of `5877` and is thus indexing `input_ptr` out-of-bounds.

This is unexpected as `ih` is calculated via `c10::irange(ih0, ih1)` and `ih0` as well as `ih1` via:
```
        int64_t ih0 = start_index(oh, output_height, input_height);
        int64_t ih1 = end_index(oh, output_height, input_height);
```
which should do the right thing as seen [Link: here].

In the failing iteration we have:
```
(gdb) print ih
$1 = 5877
(gdb) print ih0
$2 = 5874
(gdb) print ih1
... [Log Snipped] ...
(gdb) print input_height
$6 = (int64_t &) @ : 5877
```
so it seems `ih1` is rounding up.

If we check the `end_index` calculation we see:
```
static inline int64_t end_index(int64_t a, int64_t b, int64_t c) {
  return (int64_t)std::ceil((float)((a + 1) * c) / b);
}
```
which looks correct, as the calculated value should be:
```
ceil((float)(2854 + 1) * 5877 / 2855) = 5877
```
However, it's also interesting to check the intermediates and we see that `(a + 1) * c` starts to round to even multiples of 2 for integers as it's `>2**24`:
```
python
a = torch.tensor(2854.)
b = torch.tensor(2855.)
c = torch.tensor(5877.)

... [Log Snipped] ...
print(((a + 1) * c) > 2**24)
# tensor(True)
```
The `ceil` operation then rounds the value up to `5878` which creates the seg fault.

One solution could be to use `double` in:
```
return (int64_t)std::ceil((double)((a + 1) * c) / b);
```
as `float64` starts to round on integer values to even multiples of 2 for values `>2**53`, but I'm unsure if this could yield a performance overhead (I would not think so).
What do you think @ngimel?
