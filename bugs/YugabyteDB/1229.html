Title

[DocDB] Disabling packed row feature can lead to compactions to crash

Description
Jira Link: [Link: DB-13579]
### Description

If ysql_enable_packed_row is turned off on a universe where it was on before, and there are packed rows existing in DB, compaction may hit segfault with the following stack:
```
[m-1] *** SIGSEGV (@0x0) received by PID 120292 (TID  ) from PID 0; stack trace: ***
[m-1]     @       google::(anonymous namespace)::FailureSignalHandler()
[m-1]     @       (unknown)
[m-1]     @       yb::dockv::RowPackerBase::NextColumnId()
[m-1]     @       yb::docdb::(anonymous namespace)::PackedRowData::ProcessColumn()
... [Log Snipped] ...
[m-1]     @       start_thread
[m-1]     @       __GI___clone
```
The root cause is that the packer is not initialized when packed row is disabled. But if there exists packed rows, it will still re-pack the rows with the new columns or new schema, which can cause segfault.

Discussion
- Consider the following scenario:

(1) Universe with Packed Row feature on.
(2) A packed row with initial values is inserted.
(3) Update one of the columns of the row in (2) - This is stored in unpacked form.
(4) Packed Row is turned off on the universe/tserver.
(5) After the history retention interval (default 15 minutes), when compaction runs, it tries to repack the row (Even though Packed Row feature is off, since the base row was compacted). This can lead to the crash.
