Title

Relationship pointing to a class with two level inheritance emits unnecessary sql

Description
### Describe the bug

Accessing a relationship that is pointing to a class with two level inheritance emits sql even if the instance is already in the identity map.

### To Reproduce

```
python
from sqlalchemy import Column
from sqlalchemy import create_engine
from sqlalchemy import ForeignKey
from sqlalchemy import Integer
... [Log Snipped] ...
# Raises
a.ds[0].a
```

### Error

```
2022-01-07 13:15:30,195 INFO sqlalchemy.engine.Engine BEGIN (implicit)
2022-01-07 13:15:30,195 INFO sqlalchemy.engine.Engine PRAGMA main.table_info("a")
2022-01-07 13:15:30,195 INFO sqlalchemy.engine.Engine [raw sql] ()
2022-01-07 13:15:30,198 INFO sqlalchemy.engine.Engine PRAGMA temp.table_info("a")
2022-01-07 13:15:30,198 INFO sqlalchemy.engine.Engine [raw sql] ()

InvalidRequestError: 'D.a' is not available due to lazy='raise_on_sql'
``` 

### Versions

- OS: macOS 12
- Python: 3.9.9
- SQLAlchemy: 1.4.29
- Database: sqlite, postgresql
- DBAPI: pysqlite, psycopg

### Additional context

`.options(joinedload(A.ds), raiseload("*", sql_only=True))` is just to raise exception when the sql is emitted. The bug manifests even without it.

Backref is not relevant:
```
python
d1 = D(a=a)
s.add(d1)
d2 = D(a=a)
s.add(d2)
... [Log Snipped] ...
# Emits sql for a
d2.a
``` 

Accessing, for example, `a.id` doesn't emit sql if `a` is already in the identity map.

Extra sql is not emitted without the `B` class.
Discussion
- the mapper assumes objects of type "B" cannot be loaded polymorphically because it has no polymorphic_identity.  so it sets the identity keys for B objects (which includes C) to look like (B, [ ]).  this produces a mismatch with use_get in this case, since you have D->A, it's looking for an identity key of (A, [ ]).

one way the mapper can fix your case, is to just make the identity key for all non-concrete mapped classes based on the basemost class, regardless of polymorphic_identity being available.  but this breaks some assumptions that are made for class hierarchies that don't have polymorphic_identity attributes set up.   revisiting those assumptions is probably an option, but not in 1.4.30, and probably not at all because it's much easier to emit a warning here so that you can change your mapping to make the intent clear.

The warning is:

"Mapper Mapper[B(a)] does not indicate a polymorphic_identity, yet is part of an inheritance hierarchy that has a polymorphic_on column of 'a.type'.  Objects of this type cannot be loaded polymorphically which can lead to degraded or incorrect loading behavior in some scenarios.  Please establish a polmorphic_identity for this class, or leave it un-mapped.  To omit mapping an intermediary class when using declarative, set the `'__abstract__ = True'` attribute on that class."


in your test case, it looks a lot like you don't want B mapped by itself, you would never instantiate a B() object.  So make it abstract:

```py
class B(A):
    __abstract__ = True
```
