Title

Some of the Notifications::NewReactionJobs fail with "Validation failed" on save!

Description
Some of the `Notifications::NewReactionJobs` fail with `Validation failed: User has already been taken` on `save!` in the `Notifications::Reactions::Send#call`

Maybe it happens when a user creates several reactions on an article, several jobs are created, and those jobs run simultaneously.
Discussion
- I have made the research on the topic and still suppose that this error happens when 2 reaction notification jobs run simultaneously. 2 notifications with the same attributes are initialized, then. on `save!` one of them is not saved because the user validation fails.
However, it's not clear why this job doesn't succeed on retry. On retry, the `find_or_initialize` should be executed again, so it should find the existing notification, update it and the job should succeed. 
It's hard to do further research w/o access to the console, so I suggest one of the 2 options:
- pass this issue to someone who has this access
- just replace `save!` with `save`. It's not a big deal if the notification is not updated once - it'll be updated when the next reaction will be created or deleted
- I feel like I've heard of this race condition before. Definitely one of of DHH's video and maybe the reason why `create_or_find_by` will be added to Rails 6.

I agree with switching to `save`. Shouldn't be too big of a deal.

- I found out that duplicate notifications can be created in spite of the unique index.
We have a unique index on fields `["user_id", "organization_id", "notifiable_id", "notifiable_type", "action"]`.  Some of these fields can be `nil` (`user_id`, `organization_id`, `action`). When one of them is nil Postgres will allow creating multiple notifications with the same data. I've returned validation instead of relying on db constraints in the pr #3010 to reduce creating duplicate notifications. Now I'm working on creating proper unique indexes.
