Discussion
- This seems to happen with parallelProcessing on the route.
- We found that:  

 1. This happens only when using parallelProcessing  
2. We also found that in that case, it call the  close on checkNullAnswer  and  the close on the ZipIterator  before the  close on the ZipInputStreamWrapper . This is the contrary of the non-parallel mode, in which it calls the close on the ZipInputstream before the one in hasNext and the one in close (see below)  

  
 
#### Baseline (running in non parallel)

Calling close on ZipInputStreamWrapper # 1
Calling close on ZipInputStreamWrapper # 2
Calling close on ZipInputStreamWrapper # 3
Calling close on ZipInputStreamWrapper # 4
Calling close on ZipInputStreamWrapper # 5
Calling hasNext # 1
Calling close # 1

###### With parallelProcessing

Calling checkNullAnswer # 1
Calling close # 1
Calling close on ZipInputStreamWrapper # 1
Calling close on ZipInputStreamWrapper # 3
Calling close on ZipInputStreamWrapper # 4
Calling close on ZipInputStreamWrapper # 2
Calling close on ZipInputStreamWrapper # 5
 
  

 A reproducer can be  found here . Essentially it can be reproduced using a route like:  

  
 
 public  void configure() {
