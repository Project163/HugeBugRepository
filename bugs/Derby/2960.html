Title

A immediate Fk constraint blows up iff its referenced PK is deferred and we modify a duplicate key column

Description
Similar to the issue in   DERBY-6559  , except here we modify the key in the referenced table. This leads Derby to check for any referencing FK and throw, even if there are other (formerly) duplicate rows that satisfy the FK constraint.
Discussion
- The solution is similar to that of   DERBY-6559  ; we need to compute if any rows remain after the update to fulfill 
the foreign key constraint.
- Uploading a patch for this, with the needed logic, plus test cases. During the work, I discovered that the code path for deferred delete (delete was addressed in   DERBY-6559  ) was still broken, so this patch fixes that hole, too.

   DERBY-6576   A immediate Fk constraint blows up iff its referenced PK is deferred and we modify a duplicate key column 

 A follow-up patch, derby-6576-repeatable-read. In the case where we do 
not throw an exception because the deferred unique/pk constraint 
referenced by an fk is upheld by another row, we need to make sure 
that condition holds until we commit. This patch changes the check (in 
ReferencedKeyRIChecker#isDuplicated) to scan using repeatable read 
isolation level instead of read committed. This will set a read lock 
on any (well, the first we find) duplicate row till transaction end 
and thus ensure things are good till we commit.
- bug is dependent on deferred constraint work which was introduced in 10.11, settling label to not backport.
