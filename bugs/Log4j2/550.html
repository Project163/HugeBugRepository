Title

Unable to configure Multiple triggering policies on rolling file appender using yaml configuration file

Description
I wanted to use yaml instead of XML for better lisibility of the configuration. I tried the attached log4j2.yaml configuration file and when running the application I have the following error in the console : 
  
 2015-08-21 11:25:26,052 ERROR appender RollingFile has no parameter that matches element Policies
 
  

 I tried different changes but had no success. From what I understand the configuration below seems to be correct, but I may be wrong. The XML and JSON version of my configuration (also attached to this issue) work fine.
Discussion
- What happens with an XML configuration?
- This XML configuration worked fine : 
  
  <?xml version= "1.0"  encoding= "UTF-8" ?> 
 <Configuration status= "WARN" > 
   <Appenders> 
     <Console name= "Console"  target= "SYSTEM_OUT" > 
       <PatternLayout pattern= "%d{HH:mm:ss.SSS} [%t] %-5level %logger{36} - %msg%n" /> 
     </Console> 
     <RollingFile name= "File"  fileName= "${sys:user.home}/.btat/btat.log"  filePattern= "${sys:user.home}/.btat/logs/btat-%d{yyyy-MM}-%i.log.gz" > 
       <PatternLayout pattern= "%d{HH:mm:ss.SSS} [%t] %-5level %logger{36} - %msg%n" /> 
       <Policies> 
         <TimeBasedTriggeringPolicy /> 
         <SizeBasedTriggeringPolicy size= "100 MB" /> 
       </Policies> 
       <DefaultRolloverStrategy max= "20"  /> 
     </RollingFile> 
   </Appenders> 
   <Loggers> 
     <Root level= "info" > 
       <AppenderRef ref= "Console" /> 
       <AppenderRef ref= "File" /> 
     </Root> 
   </Loggers> 
 </Configuration>

- I was worried about something like that... 

 Should we and can we put out an error message if we see the wrong kind of structure? Hm... is there a schema language for YAML?
- There is no schma language for YAML. Even if there were you would hit the same problems as strict/non-strict XML file. 

 JSON and YAML make a difference between maps and sequence; XML doesn't. This caused the error and could have occured exactly the same way with JSON. 

 Given the structure of the configuration system, it won't be easy to have a more precise error message. Perhaps it would be simpler to just put a little bit more details in it (what's excpected in the Policies element and what has been found).
