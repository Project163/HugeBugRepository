Title

[BC] Filter method `trans` of Twig Bridge should allow null values for `$message` parameter again

Description
**Symfony version(s) affected**: 5.*

**Description**  
Upgrading Symfony from 4.4 to 5.* has led to BC breaks in our projects since filter method `trans` of class `Symfony\Bridge\Twig\Extension\TranslationExtension` does not allow null values for `$message` anymore. In our projects, we tried to overcome this problem by using the null coalescing operator with an empty string where it was required, but this change turned out to be too time-consuming, so we just provided our own Twig implementation for `trans` hiding/overriding that from the Symfony Twig Bridge. Yes, this is pretty dirty and we feel bad about it, so we hope for a "correction" of the BC break.

**How to reproduce**  
To reproduce the problem just call `trans` on a null value in one of your Twig templates, for example:
```
{{ null|trans }}
```

**Possible Solution**  
I suggest allowing null values for the `$message` parameter of filter method `trans` in `Symfony\Bridge\Twig\Extension\TranslationExtension` again:
```
public function trans(?string $message, array $arguments = [], string $domain = null, string $locale = null, int $count = null): string
{
    if (empty($message)) {
        return ''; // Early out, but not really necessary.
    }

- Thank you for your reply, @jvasseur. I get your point, well, somehow. We _already have_ a BC break here, in the Twig Bridge, because null values were allowed before, but now they are not anymore.

How would loosen the type declaration from `string` to `?string` in the interface lead to BC breaks, especially while the implementations disregard it anyway? Consequently, the implementations would have to be tighten to only allow `string` as well, but _this_ would really lead to _further_ BC breaks.

However, I don't care too much about the translator interface, because the Twig Bridge doesn't implement the interface at all: it just _uses_ the interface for delegation. So the easiest and probably cleanest solution would be to allow null values in the Twig Bridge again to fix the BC break, and then to explicitly check for null values here, for an early out, in order to not pass possible null values to the actual translator, which currently still allows null values as well, but might follow the specification of the "not-null interface" one day.

I have added a commit for this additional aspect of explicitly checking for null values in order to not pass them to the actual translator.
