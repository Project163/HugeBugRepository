Title

SetUpFixture not respecting NonParallelizable tag on TestFixtures.

Description
It seems since version 3.8.0, the inclusion of a SetUpFixture causes issues when trying to run multiple fixtures marked as parallelizable but some fixtures marked as non-parallelizable.

I have parallelism set at the assembly level with the following in my AssemblyInfo.cs:
`[assembly: Parallelizable(ParallelScope.Fixtures)]`

Here's my test setup:
```
namespace Tests
{
	[SetUpFixture]
	public class TestsSetUpFixture
	{
... [Log Snipped] ...
	}
}
```

All three test fixtures get run in parallel, I would expect 1 and 3 to run in parallel whilst 2 is run separately. This is the behaviour when running under version 3.7.1, however upgrading to 3.8 causes them all to run in parallel (the same is also true under 3.8.1).

We get the same problem if you remove the parallelism setting from AssemblyInfo and instead mark TestFixture1 and TestFixture3 as [Parallelizable(ParallelScope.Self)].

As work around, for now,  you can change the ParallelScope in AssemblyInfo to Children instead of Fixtures and the behaviour returns to what is expected where all TestFixture 2 waits for the other 2 fixtures to finish executing. If you have more than 1 test in a fixture  you do end up with tests within fixtures running in parallel; this can be further fixed by adding the ParallelScope.Self above the fixtures which need to run in parallel.

- I put the queues into a stack inside `WorkItemQueue` so that I would not have to create new workers. The same workers keep pulling from the `WorkItemQueue` but the underlying implementation`changes. Writing it down like that makes the fragility pretty obvious.

I can imagine two alternate models...

1. Dispatcher => SetOfShifts => Shifts => Queues => Workers
2. MasterController => Dispatchers => Shifts => Queues => Workers

In the first the `SetOfShifts` encapsulates the isolation. It could have some other name, of course. In the second a master controller creates an entirely new dispatcher when we need to have isolation of a fixture.

All this creating of new objects could get inefficient. We can make it less so if we ensure that all the classes are cheap to create and that any resource usage like thread creation is postponed till needed. We could also do some predictive analysis and use isolation when it's not needed. For example, a non-parallel fixture without any parallel or STA tests in it doesn't need to enqueue anything - it can just execute all the items directly. My inclination would be to solve the problems and live with any inefficiency until we see how bad it is, then optimize.
