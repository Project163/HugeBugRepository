Title

Aggressive concurrent flush could cause a deletion of newly generated SST file

Description
`DBImpl::BackgroundCallFlush` calls `DBImpl::BackgroundFlush` and then `DBImpl::FindObsoleteFiles/PurgeObsoleteFiles` in order to delete temporary files on failed flushes. 
`BackgroundFlush` delegates flush to `FlushJob::Run` which is supposed to add generated output file into the `VersionSet` using `MemTableList::InstallMemtableFlushResults`, so `DBImpl::FindObsoleteFiles/PurgeObsoleteFiles` won't delete it. But in case of concurrent flushes, if `MemTableList::InstallMemtableFlushResults` is called when this is already committing SST files to `VersionSet` in a concurrent thread - it will skip doing this and relies on this another thread to do that. But this leads to `MemTableList::InstallMemtableFlushResults` doesn't guarantee SST file is actually installed into `VersionSet` exactly in this call, it might be done in concurrent thread later. Therefore `DBImpl::FindObsoleteFiles/PurgeObsoleteFiles` can delete it meanwhile.

Here is more detailed diagram:
```
timeline  thread_1                            thread_2
t0        Flush started (BackgroundCallFlush)                                   
t1        Generated 73.sst (WriteLevel0Table)                                    Flush started (BackgroundCallFlush)
t2        Started commit 73.sst to VersionSet (InstallMemtableFlushResults)      Generated 74.sst (WriteLevel0Table)
t2                                                                               Trying to commit 74.sst into VersionSet, but skips due to concurrent commit is in progress (InstallMemtableFlushResults)
t3                                                                               BackgroundCallFlush calls Find/PurgeObsoletedFiles which deletes 74.sst, because it is not in VersionSet
t4        Finished commit 73.sst to VersionSet (InstallMemtableFlushResults)
t5        Committed 74.sst (deleted) to VersionSet (InstallMemtableFlushResults)
```
