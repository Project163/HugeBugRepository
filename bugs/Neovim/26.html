Title

Default behavior of `:edit`

Description
I notice that if I try to do this to edit a filename with spaces
```vim
:e filename with spaces
```

I get the error `E172: only one filename allowed`. If I can only edit one file anyway, shouldn't a better default behavior be to treat the rest of the line as a filename (up to separators like pipes, which would have to be escaped if in filenames)?
Discussion
- Makes sense to me.  Same thing happens with:

```vim
:enew
:w filename with spaces
```

This is where it's happening: [Link: ex_docmd.c#L4020-L4039]

```
c
    // Replace any other wildcards, remove backslashes.
#ifdef UNIX
    /*
     * Only for Unix we check for more than one file name.
... [Log Snipped] ...
      }
#endif
```

I'm not exactly sure how advantageous ``:e `ls ve*.c` `` is considering tab completion works pretty well and it'll show the error `E77: Too many files` if the glob matches more than one.  It also displays `E79: Cannot expand wildcards` if the glob matches nothing.
- This comment convinces me that the current behavior serves no purpose:

```
     * Only for Unix we check for more than one file name.
     * For other systems spaces are considered to be part
     * of the file name.
```

It doesn't make sense for this to be platform specific. Filenames may contain spaces on _any platform_. Why should the behavior be different for unix?

Also `:help :argedit` mentions (incorrectly):
