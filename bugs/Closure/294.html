Title

weird type-inference failure when type-casts added to an unrelated function

Description
Try the following code.

// ==ClosureCompiler==
// @compilation_level ADVANCED_OPTIMIZATIONS
// @output_file_name default.js
// ==/ClosureCompiler==

/**
 * @param {string} x
 * @return {number}
 */
var f1 = function (x) {
  return 3;
};

/** Function */
var f2 = function (x) {
  if (!x) throw new Error()
  return /** @type {number} */ (f1('x'))
}

/**
 * @param {string} x
 */
var f3 = function (x) {};

f1(f3);

I get the warning:
actual parameter 1 of f1 does not match formal parameter
found   : function (?): undefined
required: string
f1(f3);

Notice that type inference of f3 has failed.

If I remove the type-cast, the type of 'f3' is inferred correctly.

actual parameter 1 of f1 does not match formal parameter
found   : function (string): undefined
required: string
f1(f3);

It seems odd to me that changing the definition of f2 breaks type inference for f3, which makes me suspect a problem with jsdoc parsing.
Discussion
- poking at this a bit more, i think the pattern
if (x) throw Error()
without a semi-colon at the end makes the type-checker fail in all sorts of bizarre ways. Adding a semi-colon fixes the issue.
- I see the problem. Rhino attaches crazy bogus position information to the THROW node, and the new AttachJsDoc uses this information as the source of truth.

We might want to be a bit more defensive about idiosyncratic Rhino behavior, but for now I'll apply the easy fix.
