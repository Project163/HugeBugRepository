Title

Editing authorization config via REST API fails in standalone mode due to version caching

Description
Hello again, 

 We use 6.6.3 and I was trying to update my security.json (in solr home, non-zookeeper) using: 
  
 
curl -u myuser:mypass -H  'Content-type:application/json'  -d  '{ "set-user-role" :{ "dummy" : "dummy" }}'  http: //localhost:8080/solr/admin/authorization 
 
  
 The first time this is called, the security.json is written AND reloaded in memory correctly. The output json then contains at the end: 
  
 
 "":{" v":0}
 
  
 However, subsequent calls using the same command, no matter the users specifed, always output the same meta version, 0. 

 The result is that the the security.json file is correctly updated, but the RuleBasedAuthorizationPlugin is never reloaded in memory, so the new settings never take effect. 

 The version never increases, so this condition in org.apache.solr.core.CoreContainer.initializeAuthorizationPlugin always returns and memory plugin reload is skipped:

- For reference, here is what the zookeeper handler does: org.apache.solr.handler.admin.SecurityConfHandlerZk.getSecurityConfig(boolean) 
  
 
  @Override
   public  SecurityConfig getSecurityConfig( boolean  getFresh) {
    ZkStateReader.ConfigData configDataFromZk = cores.getZkController().getZkStateReader().getSecurityProps(getFresh);
     return  configDataFromZk ==  null  ?
         new  SecurityConfig() :
         new  SecurityConfig().setData(configDataFromZk.data).setVersion(configDataFromZk.version);
  }
 
  
 So presumably org.apache.solr.handler.admin.SecurityConfHandlerLocal.getSecurityConfig(boolean) is missing a call to setVersion after calling setData: 
  
 
  @Override
   public  SecurityConfig getSecurityConfig( boolean  getFresh) {
     if  (Files.exists(securityJsonPath)) {
       try  (InputStream securityJsonIs = Files.newInputStream(securityJsonPath)) {
         return   new  SecurityConfig().setData(securityJsonIs);
      }  catch  (Exception e) {
         throw   new  SolrException(SolrException.ErrorCode.SERVER_ERROR,  "Failed opening existing security.json file: "  + securityJsonPath, e);
      }
    }
     return   new  SecurityConfig();
  }
 
  
  (or SecurityConfig could encapsulate the initialization of version from data, but I have no idea if that can be generalized there)
- Is this still a problem for you? As far as I recall, using security.json without SolrCloud does not attempt to version the file. So how do you recognise this as a problem in your system?
