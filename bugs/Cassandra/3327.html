Title

deleted row still can be selected out

Description
first 
  
 CREATE  KEYSPACE space1 WITH replication = { 'class' :  'SimpleStrategy' ,  'replication_factor' : 3};
CREATE  TABLE space1.table3(a  int , b  int , c text,primary key(a,b));
CREATE  KEYSPACE space2 WITH replication = { 'class' :  'SimpleStrategy' ,  'replication_factor' : 3}; 
  
 second 
  
 CREATE  TABLE space2.table1(a  int , b  int , c  int , primary key(a,b));
CREATE  TABLE space2.table2(a  int , b  int , c  int , primary key(a,b));
INSERT INTO space1.table3(a,b,c) VALUES(1,1, '1' );
drop table space2.table1;
DELETE FROM space1.table3 where a=1 and b=1;
drop table space2.table2;
select * from space1.table3 where a=1 and b=1; 
  

 you will find that the row (a=1 and b=1)  in space1.table3 is not deleted.

- ... [Middle Discussions Snipped for Brevity] ...
- In IndexSliceReader.fetchMoreData(), it seems like gotSome should only be set to true if we read a non-RangeTombstone.  

 No, any range tombstone we add to  blockColumns  should be absolutely be returned and if we don't set  gotSome ,  getNextBlock  might well return  false , which would make  fetchMoreData  return  false  and the overal iterator skip some range tombstones it shouldn't. But the attached patches do have a bug in that they forget to set it to  true  in the added code so I fixed that. That said, I realized that  gotSome  could really be remove in favor of testing if  blockColumns.isEmpty()  so I'll commit that simplification (as it's also less error prone).   

  In the 2.1 patch, nextKind is a bit of a strange name. I suggest nextFlags instead.  

 Yeah,  nextFlags  was my initial choice but we have another thing called  flag  in that class so I feared this would be confusing. Anyway, it's probably not a big deal and I agree that  nextKind  is weird so I went with  nextFlags . 

  CellNameType.readNextFully() is also a confusing name.  

 Maybe, though the reason is that its main goal was to guarantee the name was read from the underlying  InputStream . But I actually realized that it's not needed: we always call  nextIsRangeTombstone()  after  compareNext()  anyway in  AtomDeserializer  so the name will have been read anyway and we can ignore that method entirely. Committed with that simplication.
