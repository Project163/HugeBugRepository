Discussion
- On investigating the issue only seems to occur with multi-part primary keys on 2.16 and 2.14 branch.
- Recently we have added multi-part PRIMARY KEY as part of the automation, the above test started failing just after that.

Also, in a new read-committed test I am seeing the above issue but this time it happens to be on 2.19.1
cc: @Karvy-yb
- Root cause: This is happening because the retry logic for kReadRestart error in read committed isolation is partially incorrect right now (this doesn't break safety, but can lead to repeated read restart errors internally and hence indefinite amount of waiting until the write workload stops/ slows down).

To be precise, when a kReadRestart is seen by the query layer for read committed, it has to issue a retry with a `restarted` read point. However, due to a bug, the retry ends up `resetting` the read point like any new read committed statement instead of `restarting` it. This is because after `tserver::ReadTimeManipulation::RESTART` is set for the read time manipulation in the next retry via `YBCPgRestartReadPoint()`, it is overwritten by `tserver::ReadTimeManipulation::RESET` via `YBCPgResetTransactionReadPoint()` in `GetTransactionSnapshot()` that is called for each new read committed statement attempt. And each time we reset the read point with current time, we face a read restart error again if there is ongoing write workload.
- Can be reproduced in  -b27
