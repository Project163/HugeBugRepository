Title

Matches(Constraint) does not work as expected.

Description
I am trying to write an Assert that tests that a TreeNode has a number of children and a specific text.

What I was doing was something like: 

``` csharp

Assert.That(mapper.Node, 
Has.Property("Text").EqualTo("SomeText")
& Has.Property("Nodes").Matches(Is.Unique.And.Count.EqualTo(2)));

```

```
Expected: property Text equal to "SomeName" and property Nodes equal to 2
  But was:   ,   >
```

Notice how the output it seems to disregard Unique and Count and just jumb to the "Equal" constraint, and obviously 2 and a list of nodes are not equal.

Simplified fully self-contained example without dependencies to windows forms etc:

```
csharp
using System.Collections.Generic;
using System.Linq;
using NUnit.Framework;

... [Log Snipped] ...
    }
}
```

```
Expected: property Name equal to "Unit" and property Items equal to 10
  But was:   
```
Discussion
- An even simpler test that fails is 
   Assert.That(unit, Has.Property("Items").Matches.Has.Count.EqualTo(10));
showing that the & has nothing to do with the problem.

All of the following variations pass
   Assert.That(unit, Has.Property("Items").With.Property("Count").EqualTo(10));
   Assert.That(unit, Has.Property("Items").With.Count.EqualTo(10));
   Assert.That(unit, Has.Property("Items).Property("Count").EqualTo(10));
   Assert.That(unit, Has.Property("Items).Count.EqualTo(10));
indicating that the problem is definitely with the use of Matches in the example.

The problem is that Matches, as documented, is intended for use with custom constraint classes, as in the example...  Matches(new MyNewConstraint())

NUnit has no special fluent syntax for the newly created MyNewConstraint, so we need some general way to incorporate it in the syntax and Matches is designed for that job.

Unfortunately, the syntax also accepts a general expression like Has.Count.EqualTo(5). Examining the code, I can see that Matches really expects a "resolved constraint" but the expression provided is "unresolved." What these terms mean is that Matches gets an EqualConstraint with some prefix operators attached that have not yet been resolved. As a result, the Property("Count") operation is never resolved.

Since the syntax allows this, we should make it work. On the other hand, it's not a high priority since there are so many simpler syntactic options that will work.

Guidance for whoever (including myself) works on this:

We need to look closely at how the ConstraintExpression and ConstraintBuilder Append methods work. There are places in the code where Constraint is used and others where IConstraint is used. This may need to be adjusted and we may want to call Resolve on constrains passed as arguments to one or both of these Append methods.

Charlie
