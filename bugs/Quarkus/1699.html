Discussion
- Hi @jerboaa, thanks for the report - this is going to be interesting :)

I've created this test myself, to verify some assumptions we have on how GraalVM's dead code elimination could be "guided" and enable stronger optimisations.

This implies that such a regression isn't critical in terms of functionality: the application will behave the same semantically; but it might be a performance regression - how far I don't know yet.

Essentially with this particualr integration test I was expecting us to be able to avoid needing to include the XML parser code within the native-image; there's some tricky code in the Hibernate ORM (JPA) extension that was supposed to "help" the GraalVM compiler to come to this conclusion - either this is no longer effective (changes on the compiler side?) or some other component in Quarkus has inadvertently lead to including the XML parser on its reachability graph.

However  since this only failed in GraalVM 23.3.0-dev (and not in the current one we use for integration testing), I suspect it's more likely to be due to a change in GraalVM than a change in Quarkus - otherwise we'd have seen the test fail earlier.

Admittedly the things we did in Quarkus to avoid including the parser were rather "fragile"; that's why I added this test, so to spot such cases quickly.

Do you know the range of commits in GraalVM at which it started failing?
