Title

Surface Library leaks in UI

Description
### Description

Often got a leak from leakCanary on emulator:

```
Known leak pattern: instance field android.app.Activity$1#this$0
Android Q added a new android.app.IRequestFinishCallback$Stub class. android.app.Activity creates an implementation of that interface as an anonymous subclass. That anonymous subclass has a reference to the activity. Another process is keeping the android.app.IRequestFinishCallback$Stub reference alive long after Activity.onDestroyed() has been called, causing the activity to leak.
152062 bytes retained
┬
├─ android.app.Activity$1
... [Log Snipped] ...
App process name: xxxxxx
Analysis duration: 29014 ms
```

### Version Information

* LeakCanary version: 2.0
* Android OS version: Q emulator

### Additional Information
Should probably be fixed or automatically ignored :)

The additional question is that when sharing the leak trace as text there's some added information that I can't see inside LeakCanary like:

```
Known leak pattern: instance field android.app.Activity$1#this$0
Android Q added a new android.app.IRequestFinishCallback$Stub class. android.app.Activity creates an implementation of that interface as an anonymous subclass. That anonymous subclass has a reference to the activity. Another process is keeping the android.app.IRequestFinishCallback$Stub reference alive long after Activity.onDestroyed() has been called, causing the activity to leak.
```

Is there a way to directly see this information from LeakCanary on the device to gain time?
Discussion
- This is a known AOSP leak, LeakCanary cannot fix or ignore leaks, it can only show you that they're known.

In any case, that's a good point, we need to surface these details in the UI.
- By fixing / ignoring I meant the leak generated by leakcanary itself :(

In my app only LeakCanary create the other process that causes this according to description.
