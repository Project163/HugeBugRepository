**Background**: DocDB packed row format has a dependency on the schema version in order to read rows. If a table undergoes schema change, then the older schema versions are kept around as long as there are SSTs that refer to the older schema versions. The schema versions cannot be kept around forever. Compactions garbage collect the unused schema versions metadata. The schema versions for each SST file and memtable is stored in Frontiers. 

**Problem**: When a large transaction is inserting rows to the table, the data can be split into multiple RocksDB batches. It is possible that each batch may be flushed independently, to a different SSTs - Say File A, File B, File C. The current issue is that only the last batch updates the schema version in the frontier. This can lead to the situation where in the schema version/packing metadata is aggressively garbage collected if: 
     - The schema version changed after the file was flushed (File A and File B were flushed).
     - Files containing this schema version (File C) was compacted independently, allowing the garbage collection mechanism to remove the schema version.

**Conditions**: It seems like the parent of the split went through a compaction and decided to update its own min_schema_version  to 2, even though it was in the middle of a split. It is unclear why the child tablet has  incorrect metadata - min_schema_version  of 2.
