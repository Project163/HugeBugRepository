Title

Calling a method that takes a closure containing a list or number (and maybe others) constant throws a weird exception

Description
This script: 

  
  for (myVal in evaluate( '[10,11,12]' , 2,  'foo' ) { [10,11,12] }) { 
 println myVal
}

def evaluate(text, num, thing, closure) {
   closure.call()
}
 
  

 Produces: 

  
 Exception thrown: $ const $1

java.lang.NoSuchFieldError: $ const $1
       at ConsoleScript1$_run_closure1.doCall(ConsoleScript1:1)
       at ConsoleScript1$_run_closure1.doCall(ConsoleScript1)
       at ConsoleScript1.evaluate(ConsoleScript1:6)
       at ConsoleScript1$evaluate.callCurrent(Unknown Source)
 
  

 Whilst this one that has a String inside the closure works fine: 

  
  for (myVal in evaluate( '[10,11,12]' , 2,  'foo' ) {  "one"  }) { 
 println myVal
}

def evaluate(text, num, thing, closure) {
   closure.call()
}
Discussion
- Trimming down the code even further (to make debugging easier), the following piece fails too: 
  
  //---------TestScript.groovy---------
  for (myVal in evaluate({[10]})) {
	println myVal
}

def evaluate(closure) {
   closure.call()
}
 
  

 The issue is related to the constants that are added for raw numbers by OptimizeVisitor. In this piece of code, the synthetic field that is being defined for value 10 is being defined in the outer class TestScript.class and not in the class that gets generated for closure. So the field is defined and initialized in one class but used in closure class. It fails in TestScript_run_closure1->doCall() where it tries to create the list with cached constant $const$0.
- The following piece of code has no issues in running in Java. The inner class is comfortably able to access the constant that is defined in the enclosing class. 
  
  class  Try 
{
	 private   static   final  java.lang. Integer  a = 10;
	 class  TryInner
	{
	     public  void doCall()
	    {
	       System .out.println(a);
	    }
	}
}
 
  

 Does it mean that the inner class generated for closure is not able to see the constant ($const$0) defined in the enclosing class because it is synthetic? That is the only difference I can see in groovy classes and java classes above.

- Fixed on 1.6.x (not on 1.6.0) and trunk. 

 Modified the OptimizerVisitor so that it does not visit ClosureExpression anymore - to avoid cached constants from mistakenly being referred to in the closure classes.
- Created   GROOVY-3342   to raise the optimization requirement for closure classes.
