Title

Conflict behaviour is overeager

Description
### What happened?

Our intended behaviour is to only create a conflict copy when there's an actual conflict in contents and not when the "conflict" is only in file metadata. However this breaks down in a fairly common scenario of filesystems not properly retaining permissions, for example. Consider:

- Devices A and B are in sync. B has a filesystem with unexpected limitations, like FAT on Linux or something.
- A file is synced from A to B. This includes setting permissions, which succeeds but is ignored on B.
- (At this point, permissions are different from expected on B. We don't know that yet, because it wasn't a change that would trigger a fs notification or rescan.)
- Another change happens to that file, it is synced from A to B.
- On B, when syncing, Syncthing sees that the metadata isn't what it should be according to the database, aborts the sync and triggers a rescan. Rescan will pick up the new permissions and create a new version.
- On B, at next sync attempt, we have a conflict. Both the metadata and content are different from the new version of the file, so we need to create a conflict copy of the old file.
