Title

no-spaced-func counts comments as spaces

Description
I was not expecting [Link: padded-blocks] to result in errors when a comment is the first or last line of a block. Assuming this is a bug but it could also be intentional.

Rule:

```
"padded-blocks": [2, "never"],
```

Code:

```
function fn(a, b) {
  /**
   * comment
   */
  return function () {
    return a + b;
  };
}
```

Error:

```
error  Block must not be padded by blank lines  padded-blocks
```
Discussion
- Also noticed that other rules have similar results when comments are involved (e.g., no-spaced-func: 2):

```
describe/*.only*/('foo', function () {});
```

```
error  Unexpected space between function name and paren  no-spaced-func
```
- `padded-blocks` shouldn’t count comments as empty lines, there is a [Link: test-case for this scenario].

Can you provide more information? Do you use the default parser `espree` or a different parser?
- ... [Middle Discussions Snipped for Brevity] ...
- I've investigated doing something along these lines (inspired by what millermedeiros/rocambole does with tokens), but merging tokens and comments was a big enough perf hit (~30% iirc) that I didn't pursue it much further. I got far enough to know we'd probably need to augment the tokens API with methods that skipped comments, so that style rules would get comments and semantic rules wouldn't.
- It seems like there should be a fairly inexpensive way to do this. I'm assuming you were doing some array splicing, but I'm not sure that's necessary. In token store, we're already iterating over each token to setup the lookups. What if we just, in that same loop, checked to see if a comment comes next and add `leadingComments` and `trailingComments` as we do for nodes?
