Title

bevy_ecs::schedule::executor_parallel::system tracing span should have an explicit parent

Description
## Bevy version

git master

## What you did

Ran systems under the parallel scheduler.

## What actually happened

Events logged pretty much randomly either had `bevy_ecs::schedule::executor_parallel::system` as the root span, or had `bevy_ecs::schedule::stage with name: "PostUpdate"` as a parent span.

e.g. overly-pretty log excerpt (minus nice ANSI formatting)

```
Oct 02 02:57:35.685  INFO bevy diagnostic: fps                             :  549.882600  (avg 541.647029)
    at D:\.rust\cargo\git\checkouts\bevy- \eab225f\crates\bevy_diagnostic\src\log_diagnostics_plugin.rs:57
    in bevy_ecs::schedule::executor_parallel::system with name: "bevy_diagnostic::log_diagnostics_plugin::LogDiagnosticsPlugin::log_diagnostics_system"

  Oct 02 02:57:35.686  INFO bevy diagnostic: entity_count                    :    0.000000  (avg 0.000000)
... [Log Snipped] ...
    in patina_backend::system::main
    in bevy_app::app::bevy_app
```

## What you expected to happen

Either all systems are childed to the containing `bevy_ecs::schedule::stage` span (as they are logically contained within said span) or they are all considered unique units of work, and rooted.

## Potential fix

The issue likely comes from one of two factors:

- Creation of the `info_span!` is disconnected from the actual lifetime of the span, so the auto-parenting of the span does not function as intended, or
- `info_span!`s are created on multiple threads, so the thread-local "entered span" doesn't help for worker threads.

[URL]

Where the `info_span!` is created, it should specify an explicit `parent: parent_span`, to avoid either (and both) of the above potential causes.

### No parent

`info_span!(parent: None, "system", name = &*system.name())` should suffice.

### Explicit parent

The parent span

[URL]

will need to be passed down to the creation of the child span in some fashion.
