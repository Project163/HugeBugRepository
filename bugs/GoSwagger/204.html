Title

Missing models during client generation

Description
## Problem statement

Generated client library fails to build due to missing models that aren't generated.

There's a `models` modules referenced in one of the generated files (`client/webhooks/webhooks_create_responses.go`), but it's not generated, therefore not available.

No matter what combination of command line flags I use I'm not able to generate the missing models. The spec validates successfully using `swagger validate ...` but not sure if there's perhaps something odd about it.

Any help or pointers would be greatly appreciated, thanks.

## Swagger specification

[URL]

## Steps to reproduce

Create the following files:

`go.mod`

```
module github.com/cloudsmith-io/cloudsmith-go

go 1.14
```

`main.go`

```go
package main

import "github.com/cloudsmith-io/cloudsmith-go/client"

func main {
	client.New(nil, nil)
}
```

Then run:

```
curl -o swagger.json "[URL]
swagger generate client -f swagger.json
go build
```

Discussion
- @paddycarey  it looks from your spec that all schemas are inlined with the paths definitions. In situations like this, goswagger sets out to generate all inlined things in the `operations` package rather than in `models`.

The fact that there is still a reference to some model package looks like a bug. Needs to be investigated - your spec is quite large... -.

As a workaround, you might give a try to the `--with-flatten=full`  option which externalizes inlined objects to definitions, hence models.
- @paddycarey  I've investigated your issue over the last (rainy) weekend and it stems from a name conflict when generating the anonymous structures (aka inline).
This is an interesting spec, but it looks like it will be difficult to use to develop a server, since all models are anonymous, hence no structure sharing. To an external eye, it looks like this spec has been generated and expanded.

Nevertheless, go-swagger should be able to process it and this is a bug.

As far as I can see, there is only one set of operations that is sensitive to this bug: in webhooks, all operations define an inline array `Templates`.  The generation of the items structures is in the `operations/webhooks` package 

A proper way to work around this would be to define the common definition of the template items under "definitions" and refer to it with something like "$ref": "#/definitions/TemplateItems".
Renaming the different "templates" with different names also works...

So now you have a workaround. The bug is indeed complex to solve.
