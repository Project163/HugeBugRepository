Title

[k8s-deployment] Master process can fail on startup if FQDN is not resolvable yet

Description
Noticed on GKE. Created one cluster of 4 n1-standard-16s using Yugaware to instantiate the universes.

First universe (test-1): 3 yb-master pods (2 cpu), 3 tserver pods (4 cpu) - 1 volume 100GB

Creation successful.

Second universe (test-2): 3 yb-master pods (2 cpu), 3 tserver pods (4 cpu) - 1 volume 100GB

Universe fails to create as one or more yb-masters fails to create with the following message:

```
I1220 13:33:51.777537     1 init.cc:110] version   build 1 revision   build_type RELEASE built at 19 Dec 2018 21:16:12 UTC
I1220 13:33:51.778090     1 mem_tracker.cc:240] MemTracker: hard memory limit is 3.398438 GB
I1220 13:33:51.778111     1 mem_tracker.cc:242] MemTracker: soft memory limit is 2.888672 GB
I1220 13:33:51.784497     1 master_main.cc:90] Initializing master server...
I1220 13:33:51.785696     1 fs_manager.cc:260] Opened local filesystem: /mnt/disk0
... [Log Snipped] ...
I1220 13:33:51.794431     1 master.cc:265] Master@ :7100 shutting down...
I1220 13:33:51.806542     1 master.cc:269] Master@ :7100 shutdown complete.
```

If you delete the aborting pod -- it recreates and throws the same error again. However, if you delete the second universe, and recreate it with the same parameters (including the same namespace/universe-name) that you tried (test-2) again, it succeeds.
Discussion
- Dug into this a bit, seems like the log error is a bit of a throw off. What happens is that the master fails to come up the first time around, but creates enough state for us to think we've successfully come up, but not all the state we need to successfully load the CatalogManager data and run normally.

Digging into the actual logs from the initial failure:
```
E1220 22:00:08.072484    28 master.cc:222] Master@ :7100: Unable to init master catalog manager: Configuration error (yb/master/catalog_manager.cc:1393): Unable to initialize catalog manager: Failed to initialize sys tables async: Could not resolve address of yb-master-0.yb-masters.yb-dev-bogdan-test1:7100
E1220 22:00:08.073012     1 main_util.cc:22] Configuration error (yb/master/catalog_manager.cc:1393): Unable to initialize catalog manager: Failed to initialize sys tables async: Could not resolve address of yb-master-0.yb-masters.yb-dev-bogdan-test1:7100
```

This clearly highlights the startup sequence where it failed:

CatalogManager init code:
```
1412 Status CatalogManager::InitSysCatalogAsync(bool is_first_run) {
...
1421     RETURN_NOT_OK(CheckLocalHostInMasterAddresses());
```

Underlying CatalogManager call that ends up causing the initial failure:
```
1364 Status CatalogManager::CheckLocalHostInMasterAddresses() {
...
1379   auto master_addresses_shared_ptr = master_->opts().GetMasterAddresses();
1380   const auto kResolveSleepInterval = 1s;
1381   const auto kResolveMaxIterations = 5;
... [Log Snipped] ...
1395         s = peer_addr.ResolveAddresses(&addresses);
1396       }
```

Basically, we're doing a 5x1s loop to try to resolve the master peers. If that fails, we fail to start, but we're in a section where we've still not written all our startup info yet...

We should probably just make the retry count a GFLAG and make it longer.

cc @spolitov, @mbautin
- `master_discovery_timeout_ms` flag could be reused for this purpose as well...
