Title

Extended attributes are only synced one way

Description
This happens using Syncthing v1.22.0.

Given two clients, A and B. For a file created by A, extended attribute modifications are only synced from A to B, not from B to A.

So let's say I do the following (Scenario 1):

1. A: `touch test.txt; setfattr -n user.test -v test test.txt`
2. B: `setfattr -n user.test2 -v test2 test.txt`

Only `test.txt` on B will have both attributes, it's not being synced from B. The same happens the other way around (Scenario 2):

1. B: `touch test2.txt; setfattr -n user.test -v test test2.txt`
2. A: `setfattr -n user.test2 -v test2 test2.txt`

Only `test.txt` on A will have both attributes.

Restarting syncthing makes no difference, this behavior seems set at file creation.

Interestingly, the change is picked up, but not transmitted for some reason (this is B from scenario 1, step 2):

- OK, so here's the thing (FYI myself and other developers)... I thought I was clever when I crafted the comparisons for xattrs and ownership, in that we only consider a file info different if it's set on both sides -- otherwise a file would be unequal and require resync as soon as it's synced to a new operating system and new attributes picked up. But precisely that actually needs to happen, otherwise we don't send out the change when a file comes from linux and we add attributes on macos, and things like that. We need to pick up those attributes and send back the changed file. There are details in making that happen properly that I'll hopefully be able to deal with, PR upcoming at some point tomorrowish...

One potentially interesting side effect is a cluster with two sendOwnership or sendXattrs devices won't work. Device A will send a file with some ownership information, device B will sync the file and not apply the ownership information, then pick up its own ownership info and send that, which will cause a resync on A where it doesn't apply the ownership info but sends out a new update with its own ownership info and then goto 10
