Discussion
- Steps to reproduce locally / on a dev-server:
1) It's required to force restore procedure to increase schema version. The easiest way to do that is to backup with one partitioning version and restore to the cluster with increased partitioning version -- this is a real scenario for upgrades from version  -b122 to the version >=  -b122
```
$ ./bin/yb-ctl start --master_flags "TEST_partitioning_version=0" \
  --tserver_flags "TEST_partitioning_version=0"
```
2) Create a table
```
$ ./bin/ysqlsh -c "create table t1(id int primary key, name text)"
$ ./bin/ysqlsh -c "insert into t1 select i, i::text from generate_series(1,50000) as i"
```
3) Make a backup
```
$ rm -rf ~/tmp/backup_test; mkdir ~/tmp/backup_test
$ source ~/code/yugabyte-db/build/venv/bin/activate
$ ./managed/devops/bin/yb_backup.py --masters   \
--remote_yb_admin_binary ./build/latest/bin/yb-admin \
--remote_ysql_dump_binary ./build/latest/postgres/bin/ysql_dump \
... [Log Snipped] ...
--backup_location ~/tmp/backup_test --no_auto_name \
--keyspace ysql.yugabyte create
```
4) Recreate cluster with partitioning_version greater previous value (starting from  -b122 default value is 1)
```
$ ./bin/yb-ctl destroy && ./bin/yb-ctl start
```
5) Restore previous backup
```
$ ./managed/devops/bin/yb_backup.py --masters   \
--remote_yb_admin_binary ./build/latest/bin/yb-admin \
--remote_ysql_dump_binary ./build/latest/postgres/bin/ysql_dump \
--remote_ysql_shell_binary ./build/latest/postgres/bin/ysq

  ~In short, global catalog refresh does not completely refresh the table schema cache but table schema version mismatch does.~

  ~I believe the tserver's pg_client_service table cache should stay up-to-date.  That was probably the assumption so that we could avoid redundant reopens of the tserver's table cache whenever each postgres backend gets a table schema version mismatch.~  `InvalidateAllTablesCache` sets `invalidate_table_cache_time_` which will make sure tserver's cache is refreshed.
- In case of cache refresh postgres invalidates its table cache (and table cache in `PgClientService` as well). Here is the stack trace for such invalidation

```

As a result current problem can be fixed by changing postgre's sys catalog version after restore procedure.
