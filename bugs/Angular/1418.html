Title

Service Worker performance strategy ignores images

Description
### Which @angular/* package(s) are the source of the bug?

service-worker

### Is this a regression?

Yes

### Description

When adding service worker to angular app and configure `dataGroups` cache `strategy` to `performance`, matching images are not cached. When using the same project with `strategy` set to `freshness`, images are cached for offline use.

```
json
  "dataGroups": [
    {
      "name": "images",
      "cacheConfig": {
... [Log Snipped] ...
    }
  ]
```

To Reproduce:
* clone linked repo (Angular CLI project enhanced with `ng add @angular/pwa`)
* build project: `ng build` (no `--prod` needed as production build is the default)
* serve build files by e.g. http-server (`http-server dist/Image-Cache-Service-Worker`)
* open browser on [URL]
* Check in DevTools that image is not cached

When following above steps but changing the cache strategy to freshness, the image is cached (at least after one reload of the page).

Discussion
- Thx for reporting this, @fstorz!

This is indeed a bug. The reason this works differently depending on the strategy is that the internal [handleFetchWithFreshness()][1] and [handleFetchWithPerformance()][2] methods treat opaque responses differently. The former calls [safeCacheResponse()][3] with the `okToCacheOpaque` argument set to `true`, while the latter calls it with the `okToCacheOpaque` argument set to `false` (leading in ignoring opaque responses (such as the one you get here) and not caching them).

[1]: [URL]
[2]: [URL]
[3]: [URL]
- I was thinking some more about this today and I believe the current behavior is intentional:

When we get an opaque response, we cannot tell whether the request was successful or not (i.e. if we got the requested data or an error response, such as 404).

For data-groups with the `freshness` strategy, it doesn't matter if we cache an error response, because the data will be requested anew every time (and we will only fall back to the cached response when offline/on a slow connection).

For data-groups with the `performance` strategy however, caching an error response would be quite problematic, because the SW will continue to serve the error response until `maxAge` expires (even if the error was due to a temporary network or server issue).

##
So, here are the options I am thinking about now:

1. Document this behavior and explain the reasoning behind it. People can then choose to either implement CORS (if they control the origin) or put requests affected by this issue to a separate data-group with the `freshness` strategy and probably a small timeout (potentially 0).

2. In addition to documenting it, add a new option to the data-group [cacheConfig][1] object to allow configuring how to handle opaque responses. The defaults will still be "cache" for `freshness` and "don't cache" for `performance`, but people will be able to override that for specific groups.
