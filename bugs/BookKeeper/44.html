Title

Bookie server failed to restart because of too many ledgers (more than ~50,000 ledgers)

Description
If we have ~500,000 topics in hedwig, we might have more than ~500,000 ledgers in bookkeeper (a topic has more than 1 ledger). So when the bookie server restarted, a logfile GC thread is started, which will call zk.getChildren to fetch all ledgers, and it failed because of package length limitation.

Discussion
- Some initial thoughts: 

 a) getChildren's semantic is not scalable. It would be great that zookeeper can provide a scanner interface to get children of a node. 

 b) don’t put all the ledgers in a single zk node "/ledgers". Use hash scheme to put ledgers in different zk nodes which can reduce the number of children in a single node. E.g. Suppose ledger a, computes its h1 hash value h1(a) and put it in /ledgers/h1(a)/a . 

 c) use a scalable partitioned/sharded storage to store the ledgers meta data.
- Create a patch to partition the ledgers into 2-level hashed zk nodes, which avoid packetLen exception during garbage collection.
