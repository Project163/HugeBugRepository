Title

All widget state is lost in a st.Navigation app when a button is pressed soon after number_input

Description
### Checklist

### Summary

Under certain conditions, the state of all widgets is lost when a `st.button` is pressed as a `st.number_input` widget is updated.

This issue is perhaps similar to #9100 , although occurs in different circumstances, and the workaround for that (disabling fast reruns) does not work for this bug.

### Reproducible Code Example

```
Python
import streamlit as st
import pypsa  # import a reasonably large 3rd party module

def my_func():
... [Log Snipped] ...
pg = st.navigation(pages=pages)
pg.run()
```


### Steps To Reproduce

1. Type a value into the numeric widget (e.g. `7`). Do not press "Enter".
2. Quickly click the button.
3. Repeat steps 1&2, and at some point the number_input will "reset" and be blank.

It was a rather hard to pin down exactly what conditions are required for this bug occur. It occurs reliably in a large complex app, and occurs about 70% of the time with the minimal example above. It seems at two key ingredients are required:

1. Only occurs when running as part of a sub-page in an `st.Navigation` app.
2. Only occurs if a fairly large 3rd party library is imported as part of the app.
 
In the example below we import `pypsa` (can be installed with `pip install pypsa`), which takes ~1s to import for the first time, and leads to several thousand entries in `sys.modules`.

If I don't import `pypsa` the bug does not occur. However, if I navigate to a _differrent page_ of a larger multi-page app which includes a lot of imports, then back to this minimal example page, the bug _does_  occur. This leads me to think it might have something to do with the state of `sys.modules`.

Interestingly, the bug _doesn't_ occur when the imports are replaced with a `time.sleep(1)` command.

- The problem seems to be coming from the forward message queue being cleared when a rerun is performed. 

When a script runner starts up it emits a `ScriptRunnerEvent.SCRIPT_STARTED` event with clear_forward_msg_queue, which deletes all messages from the forward queue, except for new_session, script_finished, session_status_changed, and parent_message. 

This effectively means, that the script_finished can be recieved without the message which says that the  number_input should be rendered. 

When the frontend recieves the FINISHED_SUCCESSFULLY message it seems to delete nodes which it hasnt recieved an explicit message for.

```
// Clear any stale elements left over from the previous run.
      // (We don't do this if our script had a compilation error and didn't
      // finish successfully.)
      this.setState(
        ({ scriptRunId, fragmentIdsThisRun }) => ({

          ),
        }),
```

This then removes the number_input element from the page. It will then be added by the response from the next message.

This relies on quite an exact timing, the first script runner must have completed by the time the back message gets processed and the second script runner should fire off the SCRIPT_STARTED event before the forward message has been sent, and it seems plausible that the extra time taken to process a larger sys.path by the various places it is introspected could make this bug only visible when a large module is imported.
