Title

Fix TPipeServer unpredictable behavior on interrupt()

Description
If TPipeServer::interrupt() is invoked from other thread than the thread that is blocked on TPipeServer::serve() the handle may be closed by interrupting thread while still used by servicing thread.
Discussion
- -1 

 close() doesn't need to be / shouldn't be thread safe, and this patch doesn't solve the race condition.  The 'other' thread should be calling interrupt() on the pipe, then let the main server thread close the pipe when it is complete. 

 Closing a transport that is currently in use is an anti-pattern.  You wouldn't delete memory while it is in use.  You shouldn't close a transport while it is in use.  This 'mostly' works for sockets, but only 'mostly'.
