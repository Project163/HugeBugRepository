Title

Multiselect with Pandas Index as options has exception on reruns

Description
[Link: Forum link]
The reported issue is that an app with multiselect doesn't update after the first item is selected. I locally replicated it, and the cause is the Pandas `Index` type being used as the source of options, but not having an `index` method.

In 0.83, this was not an issue, because the default values remained `None` throughout the reruns, so we never tried to look up an index. In 0.84, on the second script run, our value lookup is being called with `["a"]` as the default values when serializing the multiselect widget's state.

It is unclear if the problem is with our handling of values in serialization, or if instead this should be fixed by more aggressively ensuring the type being indexed supports the needed operations.
Discussion
- While we’re fixing this…

@AnOctopus : I’ve always thought that the [Link: `labels` argument] to `st.multiselect()` should accept [Link: any `Collection`]. What do you think?
- @treuille Do you mean the `options` argument?

`Collection` seems reasonable. Currently, we effectively require it to be a `Sequence`, which provides the `index` method, but it would be easy to adjust things so we could accept any `Collection` and fall back to converting it to a list, which should always be possible since `Collection` requires iterability.

This would clean up the API a fair bit too, since it would be a clear abstract description of the requirements for the type rather than a kinda ad hoc union of a bunch of common types. And it would make sense to extend it to other widgets that take options.
- After considering it this morning, I think the fact that we now call the indexing function with different values is correct. Previously it would only be called for handling the default values during the first widget initialization, and so wasn't called with the values that reflect the widget's changed state, but there is nothing fundamentally different happening now, and the bug happening here could have just as easily been triggered on the first run by explicitly including default options in the widget creation.

So the fix should be to more robustly ensure the `options` value supports the operations we need. Our `ensure_iterable` function is not quite enough, because iterability does not imply indexability, so we need to also convert it to something indexable first. This will be easy to do.
- So how about your idea of just converting the options to list immediately, @anOctopus? I think that would be great! 🙂
