Title

CXF 3.0 ApplicationPath issue with JAX-RS

Description
It seems CXF JAX-RS implementation has something wrong with the relationship between defined servlet-mapping and the value of ApplicationPath annotation. 

 From JSR-339 spec, section 2.3.2: If the Application subclass is annotated with @ApplicationPath, implementations are REQUIRED to use the value of this annotation appended with ”/*” to define a mapping for the added server. Otherwise, the application MUST be packaged with a web.xml that specifies a servlet mapping. 

 Also from ApplicationPath javadoc: 
Identifies the application path that serves as the base URI for all resource URIs provided by Path. May only be applied to a subclass of Application.  When published in a Servlet container, the value of the application path may be overridden using a servlet-mapping element in the web.xml.  
 [URL]

 From above information, if both servlet-mapping in web.xml and ApplicationPath has value, only one of them should be used as the base URI, and it should be the value of servlet-mapping in web.xml.

- You are right, ApplicationPath needs to be ignored by default
- I'm experiencing a problem migrating from CXF 2.7, and wonder if this fix was the cause. I am relying on the ApplicationPath parameter, and NOT overriding it in web.xml.  

 With the CXFNonSpringJaxrsServlet configured for /api/*, and my ApplicationV1 class annotated with @ApplicationPath("v1"), and my search service annotated with @Path("search"), in CXF 2.7 I can request /api/v1/search and get my search results. In the log I see 
 
 DEBUG JAXRSUtils - Trying to select a resource class, request path : /search/  
 After migrating to CXF 3.0.1, for the same request I get a 404 error and see: 
 
 DEBUG JAXRSUtils - Trying to select a resource class, request path : /v1/search/  
 Aside from being backward-incompatible, this seems inconsistent with the javadoc for the Path annotation: 
 
 Paths are relative. For an annotated class the base URI is the application path, see  {@link ApplicationPath}.  
 I wonder if the ignoring of ApplicationPath by default got a bit too aggressive.
