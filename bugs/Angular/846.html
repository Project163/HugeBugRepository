Discussion
- Thanks for reporting! The error you are seeing is emitted by Ivy's type checking mechanism, which currently does not provide information on which Angular template is responsible for the errors. This is being worked on in #30181.

In this particular case however, you have identified a false positive in the type-checker. As of today, structural directives can specify a template guard function to narrow the type of a given expression. For `NgIf` this looks as follows:

```typescript
export declare class NgIf {
  static ngTemplateGuard_ngIf (dir: NgIf, expr: E): expr is NonNullable 
}
```

For example, a template with `*ngIf="person"` with `person` being of type `Person | undefined`, the following code would be generated:

```typescript
if (NgIf.ngTemplateGuard_ngIf(directive, person) {
  // Usages of `person` within this block would be
  // of type `NonNullable `, which is just `Person`
}
```

In your case however, the expression passed to `ngIf`'s template guard is `buch !== undefined`:

```typescript
if (NgIf.ngTemplateGuard_ngIf(directive, buch !== undefined)) {
  // ...
}
```

This structure won't allow TypeScript to narrow the type of `buch` not to include `undefined`, so any usages of `buch` within the if-block are considered unsafe.

This is a current limitation of the generated type check code and we may be able to improve it by allowing the type of `NgIf.ngTemplateGuard_ngIf` to be something special that indicates to the type check generator that the binding expression (`buch !== undefined`) should itself be used as template guard:

```typescript
export declare class NgIf {
  static ngTemplateGuard_ngIf: 'verbatim'; // Just an example
}
```
This may then result in the following type-check code, which enables narrowing of `buch` to not include `undefined` in the if-block.
```typescript
if (buch !== undefined) {
  // ...
}
```
- The type narrowing limitation has been addressed in #30248 and accurate template source mapping was implemented in #30181 so this issue has been resolved.
