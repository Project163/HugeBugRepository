Title

Generated `asExpression` columns not in `RETURNING` clause on save

Description
## Issue Description

When an entity with a `STORED` generated column is saved, the generated column is not included in the `RETURNING` clause, causing the object not to get populated with the generated column's value.

### Expected Behavior

 

```sql
query: START TRANSACTION
query: INSERT INTO "typeorm"."user"("generated", "email", "username", "password") VALUES (DEFAULT, $1, $2, $3) RETURNING "counter", "generated" -- PARAMETERS: ["email@example.com","username","hash"]
query: COMMIT
```

The generated `generated` column is in the RETURNING statement.

```
ts
BEFORE SAVE: UserEntity {
  email: 'email@example.com',
  username: 'username',
  password: 'hash'
... [Log Snipped] ...
  password: 'hash'
}
```

### Actual Behavior

 

Using the new stored generated column type:
```sql
query: START TRANSACTION
query: INSERT INTO "typeorm"."user"("generated", "email", "username", "password") VALUES (DEFAULT, $1, $2, $3) RETURNING "counter" -- PARAMETERS: ["email@example.com","username","hash"]
query: COMMIT
```

As you can see, the column `generated` is not in the RETURNING statement, which causes the entity not to get populated properly with the column's value:

```
ts
BEFORE SAVE: UserEntity {
  email: 'email@example.com',
  username: 'username',
  password: 'hash'
... [Log Snipped] ...
  password: 'hash'
}
```

### Steps to Reproduce

 

```
ts
@Entity()
export class UserEntity extends BaseEntity {

    @PrimaryGeneratedColumn()
... [Log Snipped] ...

}
```

The code I use to test this:
```ts
const user = UserEntity.create({email, password, username});
console.log("BEFORE SAVE:", user)
user.save();
console.log("AFTER SAVE:", user)

const userFound = await UserEntity.find({where: {email}})
console.log("WHEN FETCHING MANUALLY:", userFound)
```

Discussion
- I never intended this feature for usage with PrimaryColumn. Is this the only way how you could archive this?
- I have thought of making `counter` the primary column, and making `id` unique and adding an index. I would still need to add a foreign key referencing `id` which is not possible.

Addition: using the computed `id` as primary key reduces complexity. It would allow my system to identify entities by a single type of id, instead of allowing both a computed id and a numeric id everywhere. These two might get mixed up unintentionally (numeric ids are in the range of the computed ids)
- It seems the issue of not returning the generated column is not specific to cascaded inserts, nor to primary columns. I have updated the issue quite a bit, so please read it again.
- I can confirm this bug still exists on `0.3.*`
