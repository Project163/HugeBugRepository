Title

takeUntilDestroyed might not work as expected in certain situations

Description
### Which @angular/* package(s) are the source of the bug?

core

### Is this a regression?

No

### Description

The current implementation of `takeUntilDestroyed()` operator assumes that the operator is used before the component is destroyed.
If the operator is used after the component is destroyed then it will not unsubscribe as expected and observables might leak.

Here is an example of misuse where this can happen:

```ts
class MyCmp {
 destroyRef = inject(DestroyRef);
 ngOnDestroy() {
  setTimeout(() => source$.pipe(takeUntilDestroyed(this.destroyRef).subscribe());
 }
}
```

While in most cases, this wouldn't happen as the injection context would be missing... but then we can pass a `destroyRef` manually like in the example above.

Cf. [URL]

It might be interesting to add a `isDestroyed` property on `DestroyRef` for late subscriber use cases like `takeUntilDestroyed()` usage above.

Discussion
- We would rather throw an informative error in that case. What would be the usage of `isDestroyed`?
- An alternative would be to immediately invoke the onDestroy callback when the DestroyRef is out of its lifecycle scope.
- **TL;DR:** 💯 for `DestroyRef.onDestroy()` to throw an error if already destroyed.


This is definitely my favorite solution. I really like it as it encourages & inspires better design.


To throw an error like described above. Of course, it's better if it's handled in `DestroyRef`. 
I didn't consider as an option initially as I didn't know the implications (i.e. existing usages of `DestroyRef`).

While this would work, I still prefer the option of throwing an error for multiple reasons:
- pedagogical reasons as it teaches better design and could link to a resource explaining RxJS flattening strategies etc...
- invoking the `onDestroy` callback immediately if already destroyed is kind of surprising. Its name indicates an event and the late subscriber issue shouldn't be handled at this level.
- in some "extreme situations", having the callback be triggered both synchronously or asynchronously can cause trouble.
e.g. 
```ts
let name = 'foo';
destroyRef.onDestroy(() => name = null)
console.log(user); // null or not depending if the callback is executed synchronously or not.
``` 
Of course, we shouldn't rely on that... but eventually, someone will.
