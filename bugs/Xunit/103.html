Title

Change of behavior in v2.5.0 when using `Assert.Equal()` with a custom `IEqualityComparer`

Description
I'm experiencing the following change of behavior when bumping xunit to from 2.4.2 to 2.5.0.

Given:

```
csharp
public class BitArrayComparer : IEqualityComparer 
{
    public bool Equals(BitArray? x, BitArray? y)
    {
... [Log Snipped] ...
    }
}
```

and the following test code:

```
csharp
public class BitArrayComparerTest
{
    [Fact]
    public void BitArrayComparer()
... [Log Snipped] ...
        Assert.Equal(set, otherSet, new BitArrayComparer());      // <----- Passing before, failing now
}
```

This test went red when Dependabot tried to bump xunit version in this PR: [URL]

```
log

  Failed SheepTools.Test.BitArrayComparerTest.BitArrayComparer [Link: [54] ms]
  Error Message:
   Assert.Equal() Failure: HashSets differ
... [Log Snipped] ...
  Stack Trace:
     at SheepTools.Test.BitArrayComparerTest.BitArrayComparer() in /_/tests/SheepTools.Test/BitArrayComparerTest.cs:line 34
```

.NET version: 6.0.411

[Link: Here's another CI run] (using the same .NET version and xunit 2.4.2) that I triggered after the failed one to make sure the results were consistent.
Discussion
- **Note that this does not just change the behavior when using a custom IEqualityComparer**, as XUnit is [Link: internally using equality comparers] in the overload without equality comparers.

For example we have a case in our code where an `Assert.Equal(x, y)` suddenly fails with two strings. Looking at the details the two strings are different but equivalent under unicode rules (i.e. `StringComparison.InvariantCulture` will treat the strings as equal). Up to now this assert succeeded; after updating XUnit it fails.

This looks like a serious regression to me.

- I have no problem with saying that unintended behavior is unsupported. I've done it more than once in the past when closing issues. It's impossible to cover every single case when so many of them are simply unknown ahead of time (like this one). I have a bit of curiosity as to exactly _why_ it passed in the past, but that doesn't necessarily mean I want to revert to the old behavior. When in doubt, behaving like the framework does (unless we're explicitly and purposefully doing something different) is a pretty good rule of thumb for me.
