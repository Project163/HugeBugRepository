- Oh that's an tricky edge case. I try to solve it...
- I apologize for commenting on a closed bug. I've been unable to get rxjs-es to work well, and this seemed like the same hoisting problem still. As stated in the bug above, ES6 code:

```
  // assign.js of RxJS
  import { root } from './root';
  const Object = root.Object;
```

converts to `var Object = _root.root.Object;`, which has the `Object` var that is hoisted and masks webpack code trying to build the exports. When I rewrite the function with `const obj = root.Object;`, the problem is avoided. 

 It does seem like it may be cleanly stated:

So... using `Object` as your own variable seems like a risky prospect, but I don't see it's a reserved word (http://www.ecma-international.org/ecma-262/6.0/#sec-reserved-words), so I am assuming this is legit and should be supported.

I've tried a few combinations Webpack 2.1.0-beta-8, 11, 12, 20 with similar versions as listed above and rxjs-es v5.0.0-beta.10.

- This would still be a problem even without webpack converting the `const Object` to `var Object`. `Object` would just be in the temporal dead-zone when the import runs.

The only ways around it is to either internally rename the module-scope `Object` to, say, `_Object`; wrap the module code that runs after the `import`s are evaluated in an IIFE, or use `global.Object` in places where webpack tries to call into `Object`...
- I'll move the export statements into the runtime, as this is repeated often anyway.
