Title

IllegalReferenceCountException in DNS resolver

Description
#### Netty Version

4.1.0.Beta5 (using latest code/API per [URL] @trustin )
#### Context

Continuing to test the DNS resolver, now trying a very high volume of queries. We have experienced a reference counting exception while submitting queries to the resolver:

```
[root@localhost]# java com.ourapp.smtp.Domain
Exception in thread "main" io.netty.util.IllegalReferenceCountException: refCnt: 0, increment: 1
        at io.netty.util.AbstractReferenceCounted.retain(AbstractReferenceCounted.java:57)
        at io.netty.handler.codec.dns.AbstractDnsMessage.retain(AbstractDnsMessage.java:367)
        at io.netty.handler.codec.dns.DefaultDnsResponse.retain(DefaultDnsResponse.java:163)
... [Log Snipped] ...
        at com.ourapp.smtp.Domain$ResolverBatch.process(Domain.java:304)
        at com.ourapp.smtp.Domain.main(Domain.java:466)
```

The line submitting the query is quite straightforward and I'd think no call to `query` should ever cause any exceptions like the one above.

```
resolver.query(new DefaultDnsQuestion(domain, DnsRecordType.MX)).addListener(this);
```
#### Step to Reproduce

There is not much more to go on here, since we are just running a large list of domains processed in random order - and we have not yet instrumented more detailed reporting of the context that caused this specific exception. So really we should just think what could be causing this sort of error in principle.

One possibility might be short max cache lifetime, per this setup:

```
        resolver.setTtl(0, 300);
```

Our resolver job is believed to have run in excess of 5 min and it is possible that some records were evicted from cache in a way that made the reference counts inconsistent. I have not reviewed the code base in depth to think of further details - wanted to share the error for discussion first.

Discussion
- More findings to report.

We confirmed that the error happens only for repeatedly queried domains that re-occurred in our input (e.g. hotmail.com, gte.com) - so this has to be a bug in the cache. The errors happened within the timeframe way under DNS record's TTL - when these records should be looked up....

With duplicates removed from the input or the cache disabled (with `resolver.setTtl(0, 0);`) all these exceptions go away. Our own solution is to disable the cache (which consumes way too much RAM anyways) but seems like this is something worth reviewing / fixing...

4. Our use case is to run DNS intelligence / analytics on the large scale. We've gotten the performance to resolving ~1M queries in ~3 min on a box with just 2 cores, EPoll event loop with default thread count, 50K concurrent queries and ~3K public DNS resolvers. I should also note that this has not saturated the CPU, so the workload seems to be bound by either network / resolver or perhaps memory bus.

In terms of practical suggestions for DNS cache in Netty - I do not see an easy / quick fix here... Doing it "properly" may involve designing something like MapDB (per links above) or adopting some of its concepts to use existing Netty framework / primitives. The key is compact storage of everything, aggregating lots of small objects in large buffers and providing efficient enough ways to look them up. This definitely looks like "major release" material...
