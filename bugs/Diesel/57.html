Title

Unsoundness with `diesel::sqlite::SerializedDatabase::new()`

Description
`diesel::sqlite::SerializedDatabase` looks to be memory-unsafe.

## Setup

### Versions

- **Rust:** 1.79.0
- **Diesel:** 2.2.1
- **Database:** sqlite
- **Operating System** macOS Sonoma 14.5

### Feature Flags

- **diesel:** sqlite

## Problem Description

[Link: `diesel::sqlite::SerializedDatabase::new()`] is a safe function that takes a pointer.  [Link: `SerializedDatabase::drop()`] always passes that pointer to [Link: `sqlite3_free()`].  That means that the following call will cause heap corruption:
```rust
diesel::sqlite::SerializedDatabase::new(&mut 0, 1);
```

### What are you trying to accomplish?

Safely serialize and deserialize a SQLite database.

Discussion
- Thanks for opening filling this issue. This shouldn't happen. From a look at the source code it seems like the `diesel::sqlite::SerializedDatabase::new` is not supposed to be public at all. (It should be marked as unsafe nevertheless).

Given that semver allows us to perform "breaking changes" to fix serve bugs and I would consider that a serve bug I propose to:

* Mark this function as `pub(crate)` instead of `pub`
* Mark it as unsafe and fix the internal code correspondingly. 

cc @diesel-rs/contributors
- There likely should be some way for the end user to create a `SerializedDatabase` since it’s needed to subsequently deserialize a DB (which is SQLite’s supported method of repopulating a DB without using the filesystem), but I certainly agree with the priority of fixing the issue first.

(My guess would be that a proper solution would be to have the initializer create the underlying buffer with `sqlite3_malloc()` and provide a mechanism to populate it with a Reader, Writer, or similar.)
- We don't use `SerializedDatabase` directly for deserialization. The relevant function accepts a `&[u8]` instead. [URL]

The `SerializedDatabase` type mostly exists to have a RAII wrapper around the pointer returned by the serialize function. It just implement `Deref ` for to allow the user to access the actual data + handles the deallocation.
- I filled [URL] to fix this.
