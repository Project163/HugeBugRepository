Title

Bug: `FlatESLint#getRulesMetaForResults` throws on unknown rules

Description
### Environment

Node version: v16.14.0
npm version: 8.3.1
Local ESLint version: `main` branch
Global ESLint version: 
Operating System: windows

### What parser are you using?

Default (Espree)

### What did you do?

While working on [URL] where we switched from `eslint-plugin-node` to `eslint-plugin-n`, I noticed that vscode-eslint extension (set to use FlatESLint) crashes, and therefore doesn't show any lint messages, when I open a file that has directives with now-unknown `node/*` rules. For example, `// eslint-disable-next-line node/no-unsupported-features/es-syntax`:

```
[Error - 11:54:29 PM] TypeError: Could not find the rule "node/no-unsupported-features/es-syntax".
    at FlatESLint.getRulesMetaForResults (C:\milos\espree\node_modules\eslint\lib\eslint\flat-eslint.js:720:27)

```

This doesn't happen when vscode-eslint is using the `ESLint` class.

To reproduce this difference in behavior, I wrote a script that runs `lintText` and then `getRulesMetaForResults`, as IDE integrations do.

### Additional comments

It's debatable whether lint messages that report unknown rules should really have those rules set as `ruleId`, but that looks like a bigger change.
Discussion
- This can also be reproduced by running `eslint -f json-with-metadata` on a file that contains directives with unknown rules.
- That's interesting. I'm a bit on the fence as to what the desired behavior is -- in theory, you'd want to be informed if you're using a rule that doesn't exist.

It looks like this issue really stems from the fact that when a rule ID doesn't exist, we generate a lint message where `ruleId` is the missing rule ID, which will obviously not be found.

Given that it's disruptive to the VS Code plugin, it seems best to quietly fail to include the rule result for the missing ID.
