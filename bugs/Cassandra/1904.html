Title

Estimated Row Cache Entry size incorrect (always 24?)

Description
After running for several hours the RowCacheSize was suspicious low (ie 70 something MB)  I used    CASSANDRA-4859   to measure the size and number of entries on a node: 

 In  [3] : 1560504./65021 
Out [3] : 24.0 

 In  [4] : 2149464./89561 
Out [4] : 24.0 

 In  [6] : 7216096./300785 
Out [6] : 23.990877204647838 

 That's RowCacheSize/RowCacheNumEntires  .  Just to prove I don't have crazy small rows the mean size of the row  keys  in the saved cache is 67 and Compacted row mean size: 355.  No jamm errors in the log 

 Config notes: 
row_cache_provider: ConcurrentLinkedHashCacheProvider 
row_cache_size_in_mb: 2048 

 Version info: 
 
	 C*: 1.1.6 
	 centos 2.6.32-220.13.1.el6.x86_64 
	 java 6u31 Java HotSpot(TM) 64-Bit Server VM (build 20.6-b01, mixed mode)

- Simple patch to fix the issue.... 

 Looks like the issue is that we do Mesure (instead of MeasureDeep) which will not measure the byte[] attached to the RK. 

 *-for-11.patch is for 1.1 and *.patch is for 1.2.
- I've been working on a 2.0/1.2 read performance regression analysis ( report is here ) and it brought me back to this ticket. 

 The patch as it was applied in revision   introduces a read performance penalty of about ~20%. 

 I've tested reverting this patch and applying on top of the latest 2.0 branch and it greatly improves read performance.  

 I don't claim to know what this patch really does, so not sure if that's an appropriate action to take or not, but I've attached my patch here regardless (trunk-4860-revert.patch).
- ... [Middle Discussions Snipped for Brevity] ...
- The issue is in the following code from RowIndexEntry:208 

  
  long  internal = 0;
             for  (IndexHelper.IndexInfo idx : columnsIndex)
                internal += idx.memorySize();
             long  listSize = ObjectSizes.getFieldSize(ObjectSizes.getArraySize(columnsIndex.size(), internal) + 4);
             return  ObjectSizes.getFieldSize(deletionTime.memorySize() + listSize);
 
  

 The list size is  not  getArraySize(columnsIndex.size(), internal). That multiplies the number of elements by the size that was just calculated. 

 It should instead be: 
  
 ObjectSizes.getFieldSize(internal + 4)
 
  

 There are no other suspicious usages of getArraySize, the only other ones are from the ObjectSizes file for byte array sizes (those make sense).
