Title

Internal Psalm error: Intersection types

Description
*Version:* Psalm 3.11.2@ 

Please see the [Link: demo project here] for a working demo of this issue.

Alternatively the contents of [Link: this file] can be pasted into the psalm.dev home page to show the error.

In short: trying to analyse a project containing the dependency `dg/ftp` throws the following internal error, even in the case where `vendor/` is ignored in `psalm.xml`.

```
Uncaught Psalm\Exception\TypeParseTreeException: Intersection types must be all objects or all object-like arrays, Psalm\Type\Atomic\TString provided in ~/psalm-ftp-bug/vendor/vimeo/psalm/src/Psalm/Type.php:586
Stack trace:
#0 ~/psalm-ftp-bug/vendor/vimeo/psalm/src/Psalm/Internal/Analyzer/CommentAnalyzer.php(1041): Psalm\Type::getTypeFromTree(Object(Psalm\Internal\Type\ParseTree\IntersectionTree), Object(Psalm\Codebase))
#1 ~/psalm-ftp-bug/vendor/vimeo/psalm/src/Psalm/Internal/PhpVisitor/ReflectorVisitor.php(1105): Psalm\Internal\Analyzer\CommentAnalyzer::extractClassLikeDocblockInfo(Object(PhpParser\Node\Stmt\Class_), Object(PhpParser\Comment\Doc), Object(Psalm\Aliases))
#2 ~/psalm-ftp-bug/vendor/vimeo/psalm/src/Psalm/Internal/PhpVisitor/ReflectorVisitor.php(272): Psalm\Internal\PhpVisitor\ReflectorVisitor->registerClassLike(Object(PhpParser\Node\Stmt\Class_))
... [Log Snipped] ...
#14 {main}
(Psalm 3.11.2@  crashed due to an uncaught Throwable)
```

If it's in scope I'd be happy to look into a fix for this; I presume that whether or not users have dependencies with any odd formatting of types, Psalm shouldn't hard error, as bringing it into a large existing codebase it's unfeasible to ensure all dependencies conform to a specification. So I'd guess that's not the intention here and we've just stumbled across possibly a legitimate bug.
Discussion
- I should have dug slightly more; it's this line in the docblock that breaks Psalm:

```
@method void alloc(int $filesize, string & $result) - Allocates space for a file to be uploaded
```

Note `string & $result` which doesn't seem valid annotation syntax.

Writing `string &$result` (no space after ampersand) makes the issue go away. So depending on complexity of the parser it _might_ be a simple fix?
- It's just a matter of catching the exception and providing a sane error message – feel free to PR, and thanks for digging
- @muglug PR now open but there's a fail in CI which I think could be unrelated but don't know enough to say for sure
