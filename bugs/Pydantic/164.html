Title

Nested generic models

Description
# Bug / Feature Request

Nested generic models seem to be significantly bugged, at least in 0.32.2 (I believe it's the same for 1.0?)

* OS: **Windows 10**
* Python version `import sys; print(sys.version)`: **3.7.3 (conda-forge)**
* Pydantic version `import pydantic; print(pydantic.VERSION)`: **0.32.2**

Tagging @dmontagu as per request from gitter.

It seems the direct issue I had in 0.30 doesn't exist, but I'm still unable to do what I wanted to do. 😛 

Ideally I would be able to set parametrized hierarchies of models using one generic TypeVar, and have them pick them up (as `OSet` below), similarly to `template ` in C++.

The way it currently works (`OUnset` and `OListNested` below) doesn't seem to support type checking, and doesn't support roundtripping in dicts at all (due to not knowing what to set in the generic type).

I would expect to be able to pass and "inherit" (for lack of better term in my knowledge) the same `TypeVar`s down the hierarchy of models, and enforce the concrete types. Also, it's strange that `OUnset` and `OListNested` work at all (though I guess X[T] is a subclass of X...), but I think that behaviour might be useful, as long as the caveats are documented.

Currently:

```
py

not GenericModel
```

Expected:

```
py
...     i: InnerT[AT]
...     
... [Log Snipped] ...
ValidationError: Type of `i` (inner_str) doesn't match OSet[int] (int != str).
```

One thing I disagreed with in your gist:

```python
# This should also fail, as the type is "wider" than Inner[int]
try:
    OuterT_SameType[Link: int]
except pydantic.error_wrappers.ValidationError:
    print("This correctly fails.")
else:
    print("This should fail, but was OK")
```

I'm not sure this case should actually fail, because we generally allow things to be parsed when possible, and in this case, it *can* be safely parsed. In particular, if you were declare models with the fields you'd get by substituting the typevars manually, no validation error would be raised. Moreover, it would probably be *more challenging* to implement it in a way where this raised an error anyway.

So I think for consistency, this should be allowed, and in #1104 it works.
- Seems reasonable to me, especially since it's in line with how it works now with Dict/List. Plus more use cases vs the "purist" implementation, and easier to check at runtime. I tried to think of a useful counterexample where the "purist" behavior is preferable, but couldn't.
