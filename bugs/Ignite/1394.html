- The race is possible between the NIO server and any Thread that calls  TcpCommunicationSpi.sendMessage  method. 

 Will investigate further in order to make up a fix.
- The following bugs were found and fixed: 

 
	 fixed a bug when a Future wasn't completed in NIO Server listener. This might cause hangs when a TCP client is being created locally; 
 

 
	 fixed a race condition between shmem and TCP communication clients. Sometimes a NIO server listener could create a TCP client while shmem client creation was in progress.

- The worst case scenario is that a node may hang (see issue description above). However, the race happens only when these conditions are met: 
1) two nodes are running on the same host; 
2) shared memory feature is configured for the communication SPI (shmem port is set properly). Enabled by default; 
3) two clients start opening communication sessions with each other concurrently and one of the clients is opening a shmem based session. 

 If anyone runs nodes on the same host in production and uses shmem then this is quite a serious issue. Do you have any statistics on such configuration in production?
- Can we increase priority of this issue?
