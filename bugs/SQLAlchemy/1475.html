Title

PGDialect_asyncpg.do_ping occasionally uses prepared statements

Description
### Describe the bug

I upgraded from 1.4 to 2.0 and noticed a problem with connecting to PgBouncer in transactional mode.
The problem occurs when engine configured to use `asyncpg` with `pool_pre_ping = True`.

After a small lookup I found the commit that brings this problem [URL]

This is how temporary working solution can look like:

``` python
from sqlalchemy.dialects.postgresql.asyncpg import PGDialect_asyncpg

del PGDialect_asyncpg.do_ping
```

- hi - 

I dont understand this issue as of yet.

SQLAlchemy's asyncpg dialect uses prepared statements for all statements, *except* this particular ping.

also, I dont understand why you would be using connection pooling with pgbouncer.  shouldn't you use `NullPool` in any case?

- There seems to be no advantage to using a client-side pool and additionally pgbouncer on top.

You should specify `poolclass=NullPool,` to let pgbouncer do all the work instead of the client.

And there is also no need to use the `pool_pre_ping=True,` because pgbouncer already does it for you (see [Link: server_check_delay and server_check_query parameters])
- I think it mostly depends on the deployment / connection requirements. When using tls etc creating a new connection requires several round trips, so it may still make sense keeping connections in the pool on the client
