Title

Ivy template type checking doesn't narrow types in output positions

Description
# 🐞 bug report

### Scope
@angular/compiler-cli
Specifically: Ivy template type checking


### Is this a regression?
No.

### Description / Reproduction
Given a template such as
```
      public myVar?: {otherVal: number};
    public myFunc(aDefinedVal: {otherVal: number}) {}
  

The type checker will correctly know that `myVar.otherVal` is a safe operation under `strictNullChecks` because of the `*ngIf`, but the checker will incorrectly throw an error on the `myFunc(myVar)`, claiming that `myVar` is of type `{otherVal: number} | undefined` which is not assignable to type `{otherVal: number}` (diagnostic code `NG2345`).

"@angular/common": "9.0.0-rc.11",

"@angular/compiler-cli": "9.0.0-rc.11",
"@angular/core": "9.0.0-rc.11",

Compiled using Bazel and `--define=angular_ivy_enabled=True`

The issue happens both with and without `strictOutputEventTypes`
- The issue here is that TypeScript's CFA (Control Flow Analysis) does not retain the narrowing result of a non-const variable inside of a closure, as the value may have changed before the closure is invoked. More info can be found in numerous reported TypeScript issues, refer to microsoft/TypeScript#7719, microsoft/TypeScript#10357, microsoft/TypeScript#9998 and various others for more detail.

In below samples, let's assume the following code snippet:

```
ts
interface Person { name: string }

@Component({
  template: '  ',
... [Log Snipped] ...
  dirOutput = new EventEmitter ();
}
```

I see two possibilities to address this limitation:

1. Introduce a `const` variable for each property read from the component, and relay reads to this variable in the type-check block. This approach should benefit from retaining the narrowing result because of the `const`ness of the variable:

```
ts
function tcb(ctx: AppComponent): void {
  const person = ctx.person;
  const handleEvent = ctx.handleEvent;
  const dir: SomeDirective = null!;
... [Log Snipped] ...
  }
}
```

2. Avoid using function callbacks for checking events altogether. We do use a callback function currently to infer the type of `$event` based on `document.addEventListener`/`EventEmitter.subscribe`, but we can use an alternative approach to infer the type of `$event`:

```
ts
function tcb(ctx: AppComponent): void {
  const dir: SomeDirective = null!;
  if (ctx.person !== null) {
    // DOM event
... [Log Snipped] ...
  }
}
```

**EDIT**: Option 2 has a downside for DOM events, as the type of the element is not used. For that to work we'd need to go through a call to `el.addEventListener`, but I can't think of a way to refer to the type of a parameter of a callback in that function invocation. Additionally, the above example does not have the fallback to `Event` for unknown events, which `el.addEventListener` would provide.
