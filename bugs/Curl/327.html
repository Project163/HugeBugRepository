Title

Threaded resolver shutdown can hang and/or leak memory

Description
### I did this

Upgraded our application from curl 8.15.0 to 8.16.0 with no other changes.

While I don't have all of the details at this time, here are two issues that we immediately noticed which seem to have been introduced with #18263.

1. Intermittent `getaddrinfo` memory leak on shutdown:

Running our application with LeakSanitizer enabled, performing a single HTTP request with libcurl, and quickly exiting the application (potentially before the request completes) results in a LeakSanitizer report about 10% of the time due to a memory leak where `freeaddrinfo` is apparently never called:

```
==275324==ERROR: LeakSanitizer: detected memory leaks

Direct leak of 64 byte(s) in 1 object(s) allocated from:
    #0   in malloc asan_malloc_linux.cpp:67:3
    #1   in generate_addrinfo nss/getaddrinfo.c:1081:16
... [Log Snipped] ...

SUMMARY: AddressSanitizer: 192 byte(s) leaked in 3 allocation(s).
```

2. Intermittent hang in `async_thrdd_shutdown`

Similarly, running our application many times in a loop results in a hang about 5% of the time. The hang occurs in `async_thrdd_shutdown` with the following callstack:

```

Discussion
- I assume when you disable the call to `Curl_thread_cancel()`, the problems go away?

1. the `nsswitch` based [Link: `libnss_getdns`] does not seem to cope with `pthread_cancel` as well as the standard resolver does.
2. The thread being cancelled while holding the mutex lock, I do not understand. pthread cancellation is "deferred" by default and there is no call that could be cancelled while curl is holding the mutex. So...I fail to understand how that could happen.
3. the leak sanitizer I do not fully trust with cancelled pthreads. glibc has some warnings about replacing malloc in such situations.

You could try running #18534 on your system. I'd be interested to learn if that eliminiates the blocking.
- That's correct, after disabling this call I could not reproduce the issues after 500 iterations.

Whether LSan can be fully trusted or not with thread cancellation, the fact is that `freeaddrinfo` is sometimes not called at all, which is definitely a memory leak. I do not think `libcurl` should be leaking memory.
```

There seems to be some unwritten output there (`**` is the start of one of the log lines that was never finished), suggesting that maybe the resolver thread was canceled in the middle of a print while holding the mutex? Maybe the hang is caused by my addition of `printf` calls inside the mutex to track down the leak, and not an existing bug in curl? If that's the case, then you can disregard my report about the hang, but I feel this is a very subtle issue and the code right now gives you no indication that you must avoid [Link: function calls that represent cancellation points] while holding that mutex. There is a potential issue in debug builds where [Link: this call to `assert`] might print and thus become a cancellation point, causing the hang, and in general I'd be concerned that calls might be added to curl in the future inside these critical sections unless someone really remembers that you must avoid that.
- @jblazquez thanks for all the analysis. I think we have to abandon the use of `pthread_cancel()`. I'll update the PR to remove it.

As to the deadlocks: if you do I/O in a locked region, that adds a function point where pthread_cancel() might abort the thread. And this explain the deadlocks.
