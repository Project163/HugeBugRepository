Title

Internal assert failed when using Tensorly on MPS

Description
### 🐛 Describe the bug

I am using the tensorly library (https://tensorly.org) to compute a PARAFAC decomposition of a tensor:

```
python
import tensorly as tl
tl.set_backend("pytorch")
from tensorly.decomposition import parafac

... [Log Snipped] ...

a, m, b = factors
``` 

This works fine on CPU. On MPS, it fails with the following error:

```
RuntimeError                              Traceback (most recent call last)
Cell In[Link: 163], [line 6]
      3 # x.unsqueeze_(1).repeat(1, 3, 1).contiguous()
      4 print(x.shape)
----> [Link: 6] weights, factors = parafac(x.detach(), 12, init="random", tol=1e-6)
... [Log Snipped] ...

RuntimeError: false INTERNAL ASSERT FAILED at "/Users/runner/work/pytorch/pytorch/pytorch/aten/src/ATen/native/BatchLinearAlgebra.cpp":1614, please report a bug to PyTorch. torch.linalg.solve: Argument 2 has illegal value. Most certainly there is a bug in the implementation calling the backend library.
```

It fails in this way when doing `x = torch.zeros(12,3,12).to("mps")` and `x = torch.ones(12,3,12).to("mps") * scalar` as well.

I know this is related to a third-party library, but the assert seems to be failing inside PyTorch, so I thought I would make an issue here.

Discussion
- Can you give a small reproducer with torch only? Then I could take a look
- Looks like the issue is with singular matrices in `torch.linalg.solve` in the MPS backend. Here is a minimal example:
```python
import torch

arg1 = torch.tensor([[1.0, 2.0], [2.0, 4.0]], device="mps")
arg2 = torch.rand_like(arg1)

torch.linalg.solve(arg1, arg2)
```
With `device="cpu"` we get a normal error: `torch._C._LinAlgError: torch.linalg.solve: The solver failed because the input matrix is singular.`

It seems the problem is handling the info status code from the [Link: MPSMatrixDecompositionLU] kernel. `_linalg_check_errors` in `BatchLinearAlgebra.cpp` needs to be special cased to handle the negative code with the MPS backend.

I put up #165254 as a quick patch, but there may be a more robust implementation less dependent on internal changes from Apple.
