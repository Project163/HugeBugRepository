Title

Rclone unnecessarily wait for token availability when downloading from PikPak

Description
#### What is the problem you are having with rclone?
rclone seems to unnecessarily (?) wait for token availability for downloading files from pikpak.

From the logs below, you can see that rclone keep saying "error no link" until at some point it started working. So I tried to see what was happening underneath with `--dump bodies`.

It seems to me like rclone tries to check if the `token` field is filled in download structure used (either `links["application/octet-stream"]` or the item in the `medias` list) depending on what rclone chooses.

Rclone keeps giving error and retrying if it receives the following format with an empty token field
```
"links": {
      "application/octet-stream": {
          "expire": "2025-06-13T23:59:50.604+08:00",
          "token": "",
          "type": "",
... [Log Snipped] ...
      }
  ],
```

but it started working as soon as the token field is filled with a token `eyJhbGc...`. Not sure what's the condition for it to get filled? Seems to get filled randomly. 

The issue here is that I can copy and use the download url (the one without a token in the response) directly and download just fine using external downloader or just copy pasting into the browser. So I'm not sure why it is necessary for rclone to wait for the token to be available.

This time, I got lucky and it started downloading after 7 retries from the log below but sometimes it goes up to 10~20 retries for each file causing unnecessary delays especially if you have lots of files to download.

Discussion
- I ran into the same issue. But reading rclone source code, there is no reference to the `token` field. Instead, rclone checks `expire` field.

[URL]

I collected the following data from PikPak api responses:
```
HTTP Respone Header Date:                 Wed, 17 Sep 2025 05:40:18 GMT
.links."application/octet-stream".url:    expire=1758174018
.links."application/octet-stream".token:  "exp":1758130818
.links."application/octet-stream".expire: 2025-09-18T01:40:18.474+08:00
.medias[0].link.url:                      expire=1758174017
... [Log Snipped] ...
.medias[0].link.token:                    (empty)
.medias[0].link.expire:                   2025-09-17T13:43:21.306+08:00
```

From the data collected, we can see that `Link.Expire` field is not reliable. I am going to prepare a PR, switching to `Link.Url` query param `expire`.
