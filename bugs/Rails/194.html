Title

Callback chain broken in unexpected way with combination of association + callbacks

Description
This is related to #36082 in that the issue we're seeing in the GitHub application is caused by the same commit but I think we have discovered some buggy behavior.

In our application we have some models that have a corresponding "archived" table so we can "delete" records and their associations without having to actually delete them. We do a replace into the archived table and then delete from the original table. There are reasons we do this, and I could get into why, but I can demonstrate an unexpected change in behavior in Rails due to #36082 in the callback chain without explaining why we do that in our app.

In our case we have models that have `after_commit on: :destroy` callbacks that we use to loop through and throttle the deletion of records. For large repositories this is really important for us.

Since updating Rails last week we've had a few test failures we're working through, one is showing our `after_commit` callbacks are **not** firing at all on destroy for our archive code. I've reproduced the issue outside of our app in the script below. In order to reproduce the issue a few things must be true:

1) A model (Post) has a `has_many` association (Comment) that is `dependent: :destroy` and a lambda adding an order (I don't know why but the lambda is required to repro this, it could be empty, or where or whatever but the lambda is one part of reproducing this).
2) The `has_many` model (Comment) belongs to Post, and has an `after_destroy` callback that updates the Post record. In our app we use this to update the number of downloads before a repo is deleted. A `before_destroy` callback also breaks the chain if it also updates the Post.

With this scenario any callbacks that are `after_commit on: :destroy` on the Post model will NOT be called and will be completely skipped. If I change this to an `after_destroy` it works fine.

Discussion
- @matthewd asked if this was related to how in tests the records aren't truly committed but I verified in a demo application that this occurs outside of the test framework so it's not related to that.
- Identified. This regression is due to changing record registration order to the transaction.

In the reproduction script, `comment.post` loads new post (since automatic inverse_of is disabled due to association having lambda), then the records in the transaction will be `[ ,  ]`, and ` ` wins by `records.uniq`.

We should keep the registration order to avoid any regression.
I'll create a PR to fix that.

I don't have a whole lot of an idea about what's happening, but I did notice that multiple instances of the Post record are added to the transaction records (i.e. `self.class.connection.current_transaction.records`) and saw this in `ActiveRecord::Persistence#destroy`:

```
@_trigger_destroy_callback = if persisted?
  destroy_row > 0
else
  true
end
```

It seems as though the original Post record is registered, then a second Post instance for the same `id` is created via the `Comment` after destroy callback. The second `Post` instance is destroyed first. When the first `Post` instance later calls `destroy_row` there is no database record to destroy so `@_trigger_destroy_callback` is set to false. Because this first registered record is the one we check for callbacks, and `@_trigger_destroy_callback` on that record is not true the callbacks do not run.
