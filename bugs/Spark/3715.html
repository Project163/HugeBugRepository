Title

CombineFilters should keep the ordering in the logical plan

Description
cmccubbin  reported a bug when he used StringIndexer in an ML pipeline with additional filters. It seems that during filter pushdown, we changed the ordering in the logical plan. I'm not sure whether we should treat this as a bug. 

  
 val df1 = (0 until 3).map(_.toString).toDF
val indexer =  new  StringIndexer()
  .setInputCol( "value" )
  .setOutputCol( "idx" )
  .setHandleInvalid( "skip" )
  .fit(df1)
val df2 = (0 until 5).map(_.toString).toDF
val predictions = indexer.transform(df2)
predictions.show()  //  this  is okay
 predictions.where('idx > 2).show()  //  this  will  throw  an exception 
 
  

 Please see the notebook at  [URL] for error messages.

The root cause seems to be `CombineFilters`. (It is called after predicate push down as you mentioned.) 
Currently, `CombineFilters` makes the final condition with `parent condition & child condition`. 
We should switch them to solve this issue.

 I didn't use UDF explicitly in a filter expression. It is like the following: 

  
 filter b > 0
set a = udf(b)
filter a > 2
and the optimizer merged them into
 
  

  
 filter udf(b) > 2 and b > 0
 
  

 This could happen for any UDFs that throw exceptions. Are we assuming that UDFs never throw exceptions?
- I'm not saying that we should make this explicit, but our current implementation does require that a UDF can't throw exceptions when the UDF is not defined at a given input value. 

 We should probably support the use case you hit since it seems to be quite natural. But I'm not sure how to support it in an efficient way (i.e. without sacrificing significant optimization opportunities).
