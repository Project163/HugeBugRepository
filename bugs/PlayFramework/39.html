Title

HEAD request on websocket throws ugly 500

Description
Tripped over this by complete coincidence, but when you do a `HEAD` request to a websocket endpoint, you get a ugly internal server error (see stacktrace at the bottom).

I started poking around, but this is the only case I could come up with that would break, so I'm guessing this is the automagic `GET`s-also-serve-`HEAD`s code messing things up here, probably failing to return a `WebSocket.reject response`.
Other things I tried, but were handled perfectly fine:
- normal `GET` request to the websocket endpoint, without websocket headers (`400 bad request`, expecting this from the `HEAD` request too)
- other HTTP method requests (like `DELETE`, `OPTION`, `PUT`) to the websocket endpoint (`404 not found`)
- `HEAD` request to non websocket endpoints (`200 OK`)

It would be nice to get a clean response instead of a nasty stacktrace, even though it is unlikely that someone will run in to this.

Discussion
- Basically, the issue is that we permit HEAD requests against GETs without an explicit mapping in routes, but the match in `GlobalSettings` isn't exhaustive: [URL]

If you use the new `HttpRequestHandler`, it looks like it will serve a 404 in this case: [URL]

It would probably make sense to specifically handle `WebSocket` in both cases, and always serve a 400 for a HEAD request on a websocket.
- The new `HttpRequestHandler` looks like it will handle this case the same, the code for HEAD handling looks identical to me. But yeah, those are the bits of code I suspect to be the cause here too.
