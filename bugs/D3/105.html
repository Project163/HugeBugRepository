Title

d3.geo.conicConformal winding order bug.

Description
In the following simple example:

```
html
 
 
 
 
```

The world.json file is created as:

```
topojson -o world.json -- countries=ne_10m_admin_0_countries.shp
```

Results in a black screen:

[Link: [Image: screen shot 2014-03-22 at 10 10 36 am]]

Switching to the [Link: 1:50M] or [Link: 1:110M] datasets does not appear to help.

However, and this is a little weird, pre-projecting the 50M dataset seems to produce the desired result (perhaps because it isn’t preserving polygon semantics?).

[Link: [Image: screen shot 2014-03-22 at 10 19 11 am]]

I’ve _also_ noticed that using `--no-stitch-poles` [Link: fixes the winding order] with the 50M dataset. However, this appears to be a coincidence as well, since this does not fix the 110M or 10M datasets. I tried using the adder branch and the preserve-polygon-semantics fix in D3, and those didn’t appear to help either but I’m not sure I tried all permutations.
Discussion
- Here’s a simpler reduced example, just showing the main polygon for Antarctica which appears to be the source of the problem. Generated from the 1:110M Natural Earth dataset.

[Link: [Image: screen shot 2014-03-22 at 1 16 08 pm]]

This was generated with TopoJSON using the default settings (and then capturing the resulting GeoJSON for the main Polygon). As before, --no-stitch-poles fixes the problem for the 1:50M dataset but not for 1:10M or 1:110M.
- I think the problem here has something to do with the Lambert conic conformal projection extending to infinity at the bottom of the map.
