Title

Inverted joystick enumeration

Description
Linux Mint 17.2 (kernel 4.1.6).

Having a problem where all the joystick devices provided by udev are enumerated from last-to-first by GLFW.  So if I have 4 joystick devices, GFWL will expose the _highest_ enumerated /dev/input/js\* (or /dev/input/event*) device provided by udev as joy[0]/GLFW_JOYSTICK_1.

Consistently able to produce this output:
/dev/input/js0  ->  /dev/input/event19  ->  GLFW_JOYSTICK_4 (joy[3])
/dev/input/js1  ->  /dev/input/event20  ->  GLFW_JOYSTICK_3 (joy[2])
/dev/input/js2  ->  /dev/input/event21  ->  GLFW_JOYSTICK_2 (joy[1])
/dev/input/js3  ->  /dev/input/event22  ->  GLFW_JOYSTICK_1 (joy[0])

Reproduced on three machines running Mint 17.2, using both Hidromancer and the kernel xboxdrv.  Built GLFW from source using master; BUILD_SHARED_LIBS ON, RelWithDebInfo.

I haven't experience this behaviour with any other application.  evtest, jstest-gtk and every other game and API (SD2/SFML/libudev) seems to address them in the correct order.  I verified GLFW_JOYSTICK_n macros are all correct.
Discussion
- So GLFW doesn't guarantee any ordering of joysticks, and it looks like SDL mostly returns them in the order you desire by accident. SDL guesses a bunch of file names in ascending order while GLFW uses `readdir` and `regexec` (and it's a todo in SDL to do it the GLFW way).

Are you suggesting that the indices should always match, even if it leaves holes in the index space on init?
- Well, I think making a case for ordering is easy enough.  Joystick[0]/GLFW_JOYSTICK_1 should always represent the first joystick enumerated by the system.  With hidromancer, xpad (kernel) and xboxdrv, the driver reserves a block of devices and assigns the each physical device that connects to it the next available js\* device within the block in ascending order.

So, for example, if you connect a usb xbox receiver, 4 devices become exposed to a GLFW application.  As far as GLFW can see all the devices are valid, but the user probably only has one controller connected.  If the enumeration is inverted and the application assigns GLFW_JOYSTICK_1 for, say, menu navigation.  The user would then have to connect 3 additional controllers to the receiver, using the 4th, in order to 'be' player one.

Making a case for literal mapping is a little trickier, but I think it's best that input API's expose the functions of the driver/hw as directly as possible with regard to crossplatform uniformity. - I understand that it's not specific to your receiver device and that the bug applied to any set of more than one joystick.

I know that holes are unavoidable once you start plugging things out, but due to a sentence in the GLFW API spec I need the initial set to be packed.

The remapping will _only_ apply to a specific list of devices that I know will be expected to behave like an Xbox controller. Anything not in that list will not be affected and will work exactly as before. Initially, if anything, the list will be too short and we will have to crowd-source the necessary IDs.
- The reason for this remapping is so that games written for Xbox-like controllers on one platform will behave as expected when compiled on another. Actual joysticks and wheels have such variance that any game making use of them need to be able to handle that anyway.
