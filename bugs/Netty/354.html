Title

AbstractConstant compareTo inconsistancy

Description
If their names are the same (ie. line 60 returns 0), then they must belong to two different pools (getting to line 60 implied object equality failed). This is presumably an exceptional and unexpected case (multiple pools are impossible for the included Constant impls). If they belong to different pools, then they can easily also have the same id. If that is the case then compareTo() will return 0 at the same time equals() will return false. I assume pretending Constants are Enums somehow resolves nebulous class unloading object pointer comparison bugs, because otherwise it strikes me as much todo over a couple static boundless loading caches for objects that largely ignore name/id.
