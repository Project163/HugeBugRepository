- It's just named in a potential misleading way.

A RIFF chunk has always three parts:

* 4 characters identifier (in our case: "RIFF", "fmt ", and "data").
* 4 bytes telling the remaining bytes in this chunk (after this number).
* The actual data.

When closing only the offsets have to be updated:

* Offset 4 is the `mainChunkSize`, which is basically our root node and its size (file size minus 8 bytes previous header). The remaining nodes are children, therefore it's named "main" I guess.
* Offset 40 is the `dataChunkSize`, which should always be file size minus 44 bytes (together with the 8 bytes offset for `mainChunkSize` this explains SFML's magic number `36`).

The calculation used is certainly correct. The sample count is per channel and has to be multiplied with the number of channels. There might be a problem somewhere else; I haven't tested this yet, but if you have a sample rate of 44100, then you'll need 44,100 samples **per channel per second**; **not** 44,100 samples per second total.
- Okay, just had to look this up, because it felt odd.

The problem is not in writing the header, but determining `m_sampleCount`, because it's misleading with multi-channel files.

Whenever a sample is written, `m_sampleCount` is increased by 1. However, this happens when both a sample is written for the left and the right (or any other channel).

This causes the weird discrepancy reported above. In the case of a stereo file, we're incrementing `m_sampleCount` twice as often due to having two channels.

I guess the easiest solution would be to just read the file size and calculate the offsets based on that, considering we're only supporting one sub format anyway.
