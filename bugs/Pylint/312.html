Title

Allow accessing protected and private attributes in __new__

Description
When implementing `__new__`, you usually create an instance of the class in which the `__new__` is defined. `pylint` currently does not allow setting protected and private attributes inside `__new__`.

### Steps to reproduce
Lint the follwing code

```
python
# pylint: disable=blacklisted-name, missing-docstring

class MyObj:

... [Log Snipped] ...

main()
```

### Current behavior

This currently returns the following:

```
************* Module example
W:  7, 8: Access to a protected member _foo of a client class (protected-access)
W:  8, 8: Access to a protected member __bar of a client class (protected-access)

------------------------------------------------------------------
Your code has been rated at 8.67/10 (previous run: 7.69/10, +0.97)
```

### Expected behavior

No warning should be reported.

This may be controversial, but I wonder if it would make sense to silence the warnings in this case. just like they are inside of `__init__`. While `__new__` is used really rarely, it does not strike me as *wrong* to access private/protected members in there unless I am missing something. Would that really be a bad practice?

### pylint --version output

```
pylint 1.8.1,
astroid 1.6.0
Python 3.5.2 (default, Nov 23 2017, 16:37:01)
[GCC 5.4.0 20160609]
```

This is also somewhat related to #1801 as I noticed this error with that enum, but it turns out that the warning is also emitted for normal objects.
Discussion
- I'm not entirely sure that this would make sense in the general case. If we could infer that the left hand side of the assignment is an object generated by a call to that `__new__` then we could assume this is good enough and we are mutating the same object. But unless we can do that, ignoring by default messages emitted in `__new__` sounds a bit artificial, since some of them might be still valid (e.g one can use a different object to fetch a private attribute)
- I agree. Did not think of that one.

In the worst case, I think it is acceptable to append `# pylint: disable= ` to the violating line. This is in any case which should not happen *often*. If the implementation of this detection turns out to be a huge can of worms this could be seen as "not worth the effort" ;)

- What about private variables of other instances of the same class? E.g.:
```python
class Foo:
    def __init__(self, child: 'Foo'):
        self.child: 'Foo' = child
        self._private: int = 1

    def do_thing(self):
        self.child._private += 1  # This should not raise a warning
```
- This feels a bit more controversial to me. When marking a variable as "private", you normally want to say that *no* external actor should be able to modify (or access) it. Think of two instances of `Car` for example. Should one instance be allowed to start the engine of the other?

If you expect that the attribute is accessed from the outside, then it might actually not be a good candidate for a "private" attribute.

My initial post was triggered by the `__new__` function, which is a bit special.
