Title

[YSQL] PG Caches are not cleared properly if Rename Table operation fails.

Description
Jira Link: [Link: DB-3815]
### Description

1. Create a table

```
yugabyte=# CREATE TABLE mytable (id INT);
```

2. Introduce error injection
```
yugabyte=# SET yb_test_fail_next_ddl=true;
```

3. Perform failing Rename
```
yugabyte=# ALTER TABLE mytable RENAME TO my1;
ERROR:  Failing DDL operation as requested.           
```

4. However there exists a mapping to "my1" still??
```
yugabyte=# CREATE TABLE my1 (id INT);
ERROR:  relation "my1" already exists
```

5. Note that I can select from both names:
```
yugabyte=# SELECT * FROM my1;
 id 
----
(0 rows)

... [Log Snipped] ...
----
(0 rows)
```

However in a new connection, the error does not exist:
```
yugabyte=# CREATE TABLE my1 (id INT);
```

Thus this looks like an issue with clearing of caches.
Discussion
- Some additional notes from the code:

In `AbortTransaction` code, there is a call to `AtEOXact_Inval(false)` to invalidate caches. Here is the logic in performing cache invalidation:
```
/*                                                                              
 * AtEOXact_Inval                                                               
 *      Process queued-up invalidation messages at end of main transaction.     
 *                                                                              
 * If isCommit, we must send out the messages in our PriorCmdInvalidMsgs list   
... [Log Snipped] ...
    .....                                        
}
```

Note that when a transaction is aborted, we only process cache invalidations issued up until the last call to `CommandCounterIncrement `(`PriorCmdInvalidMsgs`).
The comment above the function explicitly says that during abort we don't have to worry about what happened so far in the current command - but this doesn't seem to look right, from what I can see we do seem to be updating the caches.

To validate this theory, I tried calling `CommandCounterIncrement` right after `RenameRelationInternal`.
Conversely, I also tried removing the above `CommandCounterIncrement `and instead adding one more line to the above `AtEOXact_Inval `function to process invalidation messages for the current command as well.

Either change fixes the issue.
- Update: Tested the same erroneous case on upstream postgres, and this error did not occur there. This is because only YB performs aggressive caching, i.e. we update the cache as soon as we try to update/insert tuples into the PG catalog.
Therefore this comment in PG code:
```
 * If not isCommit, we are aborting, and must locally process the messages      
 * in PriorCmdInvalidMsgs.  No messages need be sent to other backends,         
 * since they'll not have seen our changed tuples anyway.  We can forget        
 * about CurrentCmdInvalidMsgs too, since those changes haven't touched         
 * the caches yet. 
 ```
is true for upstream PG but not for YB. We should process invalidation messages for both prior and current commands.
