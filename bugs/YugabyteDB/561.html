Title

CoarseBackoffWaiter can get into a busy loop, ClientUnitTest.TestRetryFunc fails on aarch64

Description
@spolitov pointed out that ClientUnitTest.TestRetryFunc fails on aarch64:

```

[----------] Global test environment set-up.
[----------] 1 test from ClientUnitTest
[ RUN      ] ClientUnitTest.TestRetryFunc

```

The retry loop works like so:
```
Status RetryFunc(
    CoarseTimePoint deadline,
    const string& retry_msg,
    const string& timeout_msg,
    const std::function & func,
... [Log Snipped] ...
  return STATUS(TimedOut, timeout_msg);

```
and the `Wait` function is implemented as:
```
bool Wait() {
    auto now = Clock::now();
    if (ExpiredAt(now)) {
      return false;
    }
... [Log Snipped] ...

```

In the test, we get way too many retries compared to what's expected.

- @es1024 thanks for finding the root cause! I think we have two options: always round the delay up to the nearest clock granularity, or, maybe, waiting in increments of e.g. 1ms if adding 10ms to the wait time is too much in some cases (e.g. if the timeout itself is on that order of magnitude). Or we could make this conditional based on the total timeout duration.
- Waiting in 1ms increments won't work, since the problem is that the clock can only observe time in 10ms increments (it'd end up just waiting for up to ~10 iterations of 1ms on top of the expected number from exponential backoff, until it hits the next 10ms increment and the clock time changes again); in cases where we need wait times on that order of magnitude, we have to use finer resolution clocks instead. 

Given that the very first wait is set to be anywhere from 4~54ms right now though, timeouts of that magnitude should probably also have the jitter calculation adjusted to be much smaller.
