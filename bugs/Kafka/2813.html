Title

Kafka Streams Stuck in infinite REBALANCING loop when stream <> table join partitions don't match

Description
Here's integration test:  [URL]

   

 From the first glance, issue is that when one joins stream to table, and table source topic doesn't have same number of partitions as stream topic, `StateChangelogReader` tries to recover state from changelog (which in this case is the same as source topic) for table from partitions that don't exist. - Huh, thanks for the report and repro,  lkokhreidze  ! 

 I think that if we didn't do selectKey in there, then you  would  get an exception, since we would check that the stream and table have the same number of partitions for the join. I'm guessing that the selectKey is inserting a repartition node, which is (correctly) configured to be co-partitioned with the table, but the source-changelog optimization is kicking in and ignoring that the repartition node and source topic have different numbers of partitions. 

 If that sounds right to you, then the solution should be to add a partition-count check before applying the source-changelog optimization. Your workaround looks like it works also to disable the source-changelog optimization because the repartition() operator always forces a repartition node.
