Discussion
- Thank you for auditing the examples! This is very helpful! 
I renamed this Jira to be more explicit in it's intent. 

 As the direct runner is currently written, not all pipelines can run on the Direct runner. The is largely for small scale local testing at best, with simplicity being the goal (batch only, everything is a single bundle, etc). In principle, this is fine, as the Go SDK is intended to be a portability first Beam SDK, so it should be possible to run it on the java based Universal Local Runner, which already implements the beam model fully. That work hasn't been done yet though. 

 However, a consequence of the way the direct runner has been written, some things aren't being checked/validated correctly in the direct runner, such as the encoding issues when trying to run on Dataflow. Fixing the direct runner to be able to do the encoding/decoding step like a distributed runner does would go a long way to fixing some of these issues, and catch these kinds of issues, before a user's pipeline development moves too far. 
This is fixable at least, it just requires someone to do the work.    

 Conversely, some examples, such as reading and writing to local file systems (which is very useful for local testing), isn't likely to work very well for most distributed runners, and mechanisms to get that to work would be runner specific.
- For an overview of certain design choices made for the Go SDK, please see the RFC that was published: along side it's initial import:  

  [URL]

 Relevant to one of your questions above, is that Go doesn't have serialized type support. This means that Structural DoFns need to have their types registered (with beam.RegisterType) so that distributed runners can run them on worker machines properly. The direct runner is as described "direct", and doesn't serialize anything, leading to it not to require these registrations.
