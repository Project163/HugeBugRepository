Title

Abort multikey commands after `timeoutlen`

Description
Over the msgpack-rpc connection it is possible to send `vim_input " "` and then to wait forever for the second part of the key sequence. Actually there should be a timeout. It would make sense to use the same value that is already used in vim, namely `timeoutlen`.
Discussion
- Using the same config via the TUI, what happens?
- I don't know how to test this via the TUI. How to do so?
- @sschaef This has nothing to do with msgpack-rpc, or Neovim at all. Internal multikey commands are all (`g`, `Z`, `z` included) implemented in a fashion that they start “pseudo-mode” when received (actually they call vgetc or equivalent which will wait for next key indefinitely). And this code is inherited from Vim, to fix this issue a big refactoring is needed. @tarruda may probably say more because he refactored code that is near the relevant one.
- I just stumbled upon this with my custom mapping of `gd`. I got :confused: when I sometimes got different behaviors when pressing the keybinding. I have `gd` set to this:

```vimscript
nmap   gd  (coc-definition)
```
When I input this binding slower than my `timeoutlen` it falls back to the default binding. This behavior is **very** confusing.
