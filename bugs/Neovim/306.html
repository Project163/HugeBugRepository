Title

Segfault after switching switching buffer (with lsp)

Description
- `nvim --version`:
```
NVIM v0.5.0-dev
Build type: Release
LuaJIT 2.1.0-beta3
Compilation:
Compiled by me

Features: +acl +iconv +tui
```
Specifically commit:  
- Operating system/version: MacOS 10.14.6
- Terminal name/version: Alacritty/iterm/iterm2
- `$TERM`: xterm-256color

### Steps to reproduce using `nvim -u NORC`

Not quite NORC, I can only reproduce when something with a significant delay modifies the buffer before saving it while also having the built-in lsp enabled. In this case, I use ale running isort on save.
```
vim
set nocompatible
set runtimepath^=~/.config/nvim/pack/packager/start/ale " or path to ale 
set runtimepath^=~/.config/nvim/pack/packager/start/nvim-lsp " or path to nvim-lsp
set hidden
... [Log Snipped] ...
" or nvim_lsp.pyls.setup({})
EOF
```

* Open any buffer
* Open another buffer that ale will run a fixer on (here, a python file)
* Modify the file in a way that the fixer will actually do something (here, unorder the imports)
* quickly switch to the other buffer before isort has completed

At this point, once the isort has completed, you should be forced back to the python buffer, indicating it worked. The next time you switch buffers, you should segfault.

Some notes:
* Ale without the lsp, doing the same process will format and save the buffer in the background without forcing you back to the buffer being saved, unlike here
* It's easily reproducible with both pyls and pyls_ms, i assume because both are relatively slow.
  * I attempted to reproduce this just now with rustfmt + rust-analyzer lsp, but i'm hardpressed to switch the buffer before it completes. I want to say I've seen hit this before when working with rust, but i can't prove it right now.

I'm sure there's a more minimal/general way of reproducing this, but I wasn't personally able to minimize it further
