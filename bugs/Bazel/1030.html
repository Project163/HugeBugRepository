Title

extra_toolchains precedence not respected when duplicates occur

Description
### Description of the bug:

Per [URL] it was decided that elements later in the `--extra_toolchains` list should have higher precedence. This mostly works, but seems to regress when there are duplicates of a target in the list. When that happens, the _first_ position of a target takes precedence instead of the last.

This isn't too big a deal, but does makes having a `--extra_toolchains` value with consistent behavior between Bazel 6 and Bazel 7 a bit of a pain. Specifically, there isn't a single list that can get the desired behavior in both versions. For example, lets say we have two toolchain targets, `//a:all` and `//b:all`. We want to always use `b`.

```
extra_toolchains=[a, b]
Bazel 6: picks a
Bazel 7: picks b

extra_toolchains=[b, a]
... [Log Snipped] ...
Bazel 6: picks a
Bazel 7: picks b
```

So yeah, it seems like the first position in the list determines the final position when iterating. This smells very much like LinkedHashSet (first added is iteration order), or depset (first iterated upon is yielded, subsequents are ignored) doing something, somewhere.

I skimmed through the RegisterToolchainsFunction.java code, but nothing in particular stuck out to me.

Discussion
- Ha ha sigh.

The problem here is in the normalization used (see [Link: `PlatformOptions.getNormalized`]): it calls into [Link: `dedupeOnly`], which keeps the **first** instance of the value, and so shows the behavior you report.

This flag (and maybe also `--extra_execution_platforms`?) really wants a currently-doesn't-exist `dedupeOnlyKeepingLast`, instead.

This probably isn't difficult, I'll take a look at it sometime soon.
