Title

zookeeper should set a default value for SERVER_JVMFLAGS and CLIENT_JVMFLAGS so that memory usage is controlled

Description
We noticed this with jdk 1.6 where if no heap size is set the process takes up to 1/4 of mem available on the machine. 

 More info  [URL]

 You can run the following command to see what are the defaults for your machine 

  
 java -XX:+PrintFlagsFinal -version 2>&1 | grep -i -E  'heapsize|permsize|version' 
 
  

 And we noticed on two different class of machines that this was 1/4th of total memory on the machine.

- Reverted b3.4 commit. Committed revision 1528221.
- This change has unintended consequences when migrating containerized Zookeeper running as a pod in Kubernetes from version 3.4 to 3.5. In 3.4, we used to utilize the new (JVM > 8u212) default behavior of JVM that sets 1/4 of container (cgroup) memory limit as the max heap size value (Xmx) (consult  [URL] With Xmx being explicitly set by zkEnv.sh, this feature is disabled, which causes pod memory settings and JVM settings to become out of sync. In radical cases (small footprint deployments), the default value of 1000m may overgrow pod limit, causing Kubernetes to kill the Zookeeper pods due to pod OOM condition. 

 I'm not against the change in general and understand the rationale for bare metal deployments. However, it feels like there should be a "safety valve" available - e.g. an additional flag to disable adding an explicit Xmx setting to SERVER_JVMFLAGS, so that it could be consciously decided to let JVM set the actual max heap size value. 

 Finally, perhaps the new behavior should be mentioned in  [URL]
