Title

[docdb] Wrong preceding op id is sent after empty update consensus

Description
This issue was triggered as a side-effect of  D9577 (https://github.com/yugabyte/yugabyte-db/commit/ ).

After the write is paused, the empty update consensus request is created for the peer.

This request is not sent.

But the consensus queue is not notified about it and left in the wrong state like we did not receive a response for this request.
So when it creates a new update consensus request for this peer, it would think that we were not able to send even an empty set of operations and will try to create another empty update consensus request.

Because of another bug preceding op id will be set to the wrong value causing this request to be rejected.
So we will have 2 extra update consensus requests in case of a short write pause.

The issue could be identified by "Got LMP mismatch error from peer:" message spam in logs.

For the user side, it could decrease performance a bit.

Symptoms:

```
I1210 04:45:43.827607  1111 consensus_queue.cc:1139] T   P   [LEADER]: Got LMP mismatch error from peer: { peer:   is_new: 0 last_received: 9.25048668 next_index: 25048669 last_known_committed_idx: 25048666 is_last_exchange_successful: 0 needs_remote_bootstrap: 0 member_type: VOTER num_sst_files: 5 last_applied: 9.25048666 }
I1210 04:45:43.833618 32522 raft_consensus.cc:1566] T   P   [term 2 FOLLOWER]: Refusing update from remote peer  : Log matching property violated. Preceding OpId in replica: 2.25054230. Preceding OpId from leader: 2.25054231. (index mismatch)
```
