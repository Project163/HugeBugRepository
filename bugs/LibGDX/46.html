Title

alcDestroyContext/DSoundOpenPlayback bug

Description
```
AL lib: (EE) DSoundOpenPlayback: Device init failed:  
AL lib: (EE) DSoundOpenPlayback: Device init failed:  
Exception in thread "main" java.lang.NullPointerException
at org.lwjgl.openal.ALC10.alcDestroyContext(ALC10.java:362)
at org.lwjgl.openal.AL.destroy(AL.java:210)
... [Log Snipped] ...
at com.badlogic.gdx.backends.lwjgl.LwjglApplication. (LwjglApplication.java:64)
at whatever.desktop.DesktopLauncher.main(DesktopLauncher.java:10)
```

happens quite randomly, without any apparent reason, usually when debugging, but not always. Doesn't depend on the exact client code, happened with code not using sound/music, with project with almost no code at all (test one-liners) etc.

but:

b) I _don't_ have any non-ASCII chars in pathnames,
c) I _do_ use NetBeans, but the issue also (at least per the report of one other user) happened on Eclipse,
d) NetBeans team closed this issue as "invalid",
e) the issue still happens as of 1.4.1/1.4.2 on various desktop systems/boxes (Win7, WinXP, Java8u25),
f) it also did occur a couple of time _after_ I closed a previous instance of the app and tried to run it again from the command line, if my memory serves me well.

Also, since the problem affects all desktop users (thought some /NetBeans/ more than other), is obviously related to OpenAL/LWJGL and it _did_ happen and happens still in newest libGDX, I consider we should keep this open until somebody figures what _really_ happens there and how to fix it permanently.

The only solid info about this very error is that   is HRESULT E_INVALIDARG, "invalid parameter passed to function",
[URL]

My idea is that this happens because the audio device is not yet ready to function (for whatever reason), and because we assume the device _is_ present and ready, we get NPEx. Because the error happens at (in libGDX scope) OpenALAudio.init but propagates through the entire LwjglApplication.init making the app init fail completely, we should _at least_ provide a temporary workaround to allow running the app when it fails, e.g. by catching the exception and issuing a gdx error instead here:
[URL]
putting a try/catch for NPEx around this would give audio == null as if disableAudio was set previously.
IMO it's better to have an app with no sound and a clear error message than no app at all in the end. The programmer would later check the value of audio field in LwjglApplication, and could try to init the sound system manualy at some later time or on user request.
- Also, I have a gut feeling this JNI crash could be prevented as well by checking some internal conditions... it happens quite randomly, but often enough to make it really annoying for desktop users, as well as developers:

[URL]

It also happened on different Win platforms, both XP 32 & 7 64.
- Thanks for the research! I temporarily "fixed" this as you suggested, by catching the exception, logging it and continuing as if disableAudio was set.
- Many thanks for the patch, badlogic.
