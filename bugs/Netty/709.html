Title

WebSocketClientHandshakers are too restrictive on handshake response status

Description
Netty 4+

From [Link: RFC6455]:

But WebSocketClientHandshakerXX verify crashes with `WebSocketHandshakeException` when [Link: status isn't 101].

This makes WebSocketClientHandshaker unable to deal with standard HTTP mechanisms such as redirect and non-preemptive authentication.

PS: I'm trying to upgrade AHC to Netty 4.1.
The migration path from 4.0 is very hard, possibly because of a bad AHC design. But still.
So far, I've been dealing with handshake and pipeline upgrade manually (meaning that AHC does support redirect and auth during WebSocket handshake).
But now:
- I can't migrate to `WebSocketClientHandshaker` because of this bug
- I can't figure out how to use `HttpClientUpgradeHandler`, I don't see it used anywhere in the WebSocket examples, nor in the `websocketx` package
- In order to upgrade the pipeline manually, I have to do a very ugly hack: `HttpClientCodec` no longer exists in the pipeline, and `Decoder` and `Encoder` classes are private, so I can't look up by class and have to look up by name, such as `HttpClientCodec$Decoder#0`

Here's how I've been doing things prior to 4.1:
- Channel initially have a HttpClientCodec
- Send initial upgrade request
- If status is different from 101, perform standard HTTP operations such as redirect or auth, and perform upgrade request again
- Otherwise, add the WebSocketEncoder and Decoder in the pipeline, based on HttpClientCodec position, and remove HttpClientCodec. HttpClientCodec lookup is based on the name that was used to set it in the first place.

But now with 4.1:
- HttpClient is no longer a Handler in the pipeline. There's an Encoder and a Decoder instead, whose names are not even based to the name that was used to set the HttpClientCodec.
- I had to use the internal names for the Encoder and Decoder (`HttpClientCodec$Decoder#0` and such) to remove them and find out where to place the WebSocket handlers.

[Link: Definitively hacky. Maybe/probably I'm doing it wrong.]
But I think the new design overlooked the fact that the WebSocket handler didn't cover the fact that the handshake response could be something else than 101 and be perfectly valid and have to be handled downstream.
