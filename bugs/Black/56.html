Discussion
- Yeah, this is a bug to be fixed although fortunately low priority.

This only happens for atypical classes of Unicode identifiers. Usual Unicode identifiers work fine and real-world code is unlikely to encounter this (unless malicious code). What's unsupported in lib2to3 is a certain class of legacy identifiers and variant forms. The latter is what we're dealing with in this example.

I happen to have the UTF-8 decoding table on my desk, as you do, so I checked and this example is pretty insidious. It's a base `x` letter followed by a [Link: "variation selector"]). Variants are for people to be able to choose which *glyph* should be used in rendering the character. It's ambiguous if a glyph variant should be considered a unique identifier since it's rendered with the base glyph if a given font lacks the variant (as is the case here, see example below).
```
# which one is variant-17?
x
x󠄀
```
- Another example with no variation selectors, reduced from [URL]
```python
មុ = 1
```
That’s U+1798 KHMER LETTER MO + U+17BB KHMER VOWEL SIGN U.
