Title

Do the zoom and drag behaviors need to cancel click events?

Description
[URL]
It cancels the first click event after the drag, the one assumed to be created by the drag. Is there any reason it needs to be cancelled? Could leaving the click event cause trouble?

It also seems to cause problems with Opera, which doesn't trigger click events for drags, which could be an Opera bug or an accepted inconsistency (not sure yet). Ran into that at systemed/iD#357
Discussion
- The reason it cancels the click event is so that you can drag elements that have click listeners without triggering their click event on mouseup. For example, in a force layout, you might have clickable nodes, but the click action is only triggered when the node is clicked on without dragging.

Could you describe the problem in Opera more explicitly? What behavior are you seeing?
- That makes sense, thanks.

Opera doesn't trigger click events if the mouse has moved while down. Other browsers trigger, as long as its within the element. The next click after dragging is captured and stopped.

I'm not sure if this behavior is considered a bug or expected behavior by Opera. I've filed a bug report, but no response yet.
[URL]

- The issue you are seeing is indeed related to draggable nodes with multiple elements. See #312 and specifically @jasondavies’ comment:

That said, it looks like we don’t need this sanity-check since we added the 0ms timeout, which automatically expires click suppression if a click event doesn’t immediately fire. In other words, since we only suppress an _immediate_ click event, we don’t have to worry about false positives due to inconsistent browser behavior. (Before the 0ms-timeout, the click could be suppressed indefinitely!)

So, I’d be okay with removing target checks and relying on the timeout for click suppression.
