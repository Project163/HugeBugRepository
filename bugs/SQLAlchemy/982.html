Title

"CREATE TABLE" statement doesn't provide COLLATE correctly with MySQL

Description
**Describe the bug**
The syntax to define a collation and charset when creating a table has to follow the following grammar rule ([Link: relevant documentation]):
```
CREATE TABLE tbl_name (column_list)
    [[DEFAULT] CHARACTER SET charset_name]
    [COLLATE collation_name]]
```

Sqlalchemy seems to not respect the order of CHARACTER SET and COLLATION, resulting in the wrong collation being used for the created table.

**Expected behavior**
I expect Sqlalchemy to emit a CREATE TABLE statement that correctly sets the COLLATION and CHARACTER SET.

**To Reproduce**
The following snippet reproduces the issue, but not consistently. You may need to run this multiple times before it fails on the assertion.
EDIT: See the comment below to get it consistently failing. TL;DR set PYTHONHASHSEED=1.
My guess here is that the compile for the CREATE TABLE statement does not define the order of the "post table parenthesis" options, (like CHARACTER SET, COLLATION, ENGINE, etc.), and the for some reason the order of these options is randomized at every run.

- Yes, I've just run into this behavior. MariaDB will ignore the collation if it doesn't appear last and then pickup the default from the SCHEMA -- ignoring the explicitly provided one if it comes prior to a CHARSET.

For future searchers: this can then break FKs to string fields with further cryptic 105 errors that were difficult to debug in production and pipelines.

For example, the SQL emitted from Alembic migration CreateTable() that reads:
```COLLATE utf8mb4_unicode_ci CHARSET=utf8mb4 ENGINE=InnoDB``` would in my case cause the columns to pick up utf8mb4_general_ci (SCHEMA default) which would then fail on FK creation with mismatched FK definitions.
