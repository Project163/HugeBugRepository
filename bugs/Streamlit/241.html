Title

experimental_fragment/dialog decorator before set_page_config (such as via import) breaks on 1.37

Description
### Checklist

- [Link: X] I have searched the [existing issues] for similar issues.
- [X] I added a very descriptive title to this issue.
- [X] I have provided sufficient information below to help reproduce this issue.

### Summary

st.fragment and st.dialog were de-experimentalized on 1.37, which means existing apps that used the experimental versions would start showing the deprecation warning. If the deprecation warning shows before set_page_config is called (such as during an import), it causes an error.

So, packages that use experimental_fragment cause apps to break in 1.37

### Reproducible Code Example

```
Python
import streamlit as st

@st.experimental_fragment
def fragment():
... [Log Snipped] ...
st.title("Simple repro")
fragment()
```

### Steps To Reproduce

Open the app in 1.37

### Expected Behavior

The app runs as expected

### Current Behavior

Error message:
`StreamlitAPIException: set_page_config() can only be called once per app page, and must be called as the first Streamlit command in your script.`

### Is this a regression?

- [X] Yes, this used to work in a previous version.

### Debug info

- Streamlit version: 1.37
- Python version: 3.12.4
- Operating System: MacOS
- Browser: Chrome

### Additional Information

I ran into this issue while using the TruLens package. it works on 1.36 but I see this error on 1.37. The fix is to move the imports below set_page_config, but that breaks python convention.
Discussion
- Thanks @JoshuaC215 (also, hi 👋)! Marking as P3 since I think the fix of removing the `experimental_` prefix from fragment/dialog when updating to 1.37 is an easy one that I'm assuming people shouldn't generally be blocked from doing. I think the most reasonable thing to do here for a fix will be to defer when the deprecation warning is printed until the fragment function actually runs (vs when the decorator is called like how things currently work) so that there's no need add special cases to our rules of when `set_page_config` can be called.

I'll look into getting a quick fix out next week.
