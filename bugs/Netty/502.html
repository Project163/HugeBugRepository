Title

Race in PoolArena.allocate

Description
It appears there might be a race in `io.netty.buffer.PoolArena.allocate`, where `allocationsTiny` is incremented.  While the value is incremented under a lock, it also appears to be mutated elsewhere in the file without a lock.  A race detector suggested the two places where the class accesses this field in an unsynchronized way:

```

    #1 io.netty.buffer.PoolArena.reallocate(Lio/netty/buffer/PooledByteBuf;IZ)V (PoolArena.java:359)  
    #2 io.netty.buffer.PooledByteBuf.capacity(I)Lio/netty/buffer/ByteBuf; (PooledByteBuf.java:120)

```

Discussion
- yep that's a possible race, but it doesn't really happen in practice and I think if it does nobody will notice or care :).

It may happen if two threads have the same arena's assigned to them, and those two threads need to concurrently allocate from two different tiny size classes and there must not be any free regions available in the thread caches for both of those two tiny size classes (same is true for `allocationsSmall`).

However, by default Netty settings, each thread has its own arena (cores \* 2) and almost all tiny allocations should be served by the cache. If it happens it shouldn't matter, cause `allocationsTiny` and `allocationsSmall` are just counter variables for stats, that aren't really in use.

Just saying ... still a bug :smile:
