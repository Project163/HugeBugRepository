Title

Behaviour for HTTP API is not the same as with CLI API

Description
#### What is the problem you are having with rclone?

Sending requests that should fail (missing local dir, access denied to remote, etc.) to rclone HTTP server are not failing. They end with empty object and 200 code result. Tested with both curl and rclone rc.

Example:

```
a> rclone rcd -vv --rc-no-auth
b> rclone rc sync/move srcFs=/non-existent/ dstFs=created-but-inaccessible-remote:bucket/test
{}
b> curl --verbose -H "Content-Type: application/json" -d '{"srcFs":"local-dir-that-exists", "dstFs":"created-but-inaccessible-remote:bucket/test"}' [URL]
*   Trying  ...
... [Log Snipped] ...
 
```
Discussion
- Yes I can verify this.  The error appears in the log

    2019/05/07 13:29:58 ERROR : : error reading source directory: directory not found

But isn't propagated to the caller.


That is a very good point.  `cmd.Run` does retries and it also checks the state of the global error flag.

Reading the source directory failing isn't being reported synchronously because you want the sync to run even if it can't read all the source directories.

it would be easy enough to make an analog of `cmd.Run` for the operations to call.  It will need a lock though as running more than one at once isn't a good idea.

Or the API of [Link: fs/march] needs reconsidering so it can report if anything failed at the end.  I see no reason why `March.Run` shouldn't return the listing error at the end - this would then make the error be returned properly.

So, I think you've identified two problems
1. Not all errors are returned to the API
2. Commands are not being retried when they should

This is all down to `cmd.Run` not being called.

Possible solutions
1. Make a version of `cmd.Run` for the API to call
2. Try to make the errors be returned synchronously. We've identified one place in `fs/march` where this is the case, there may be others though.
- I should probably mention that creating jobs with `_async=true` also doesn't capture errors and jobs always finish without error.
- I'm pretty sure that is the same problem...
