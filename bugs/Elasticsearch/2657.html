Title

Strange garbage collector behavior after upgrade from 7.10.2 (OSS) to 7.13.2

Description
Hello!

On July 7, I upgraded several clusters from 7.10.2 (OSS) to 7.13.2.
At first it seemed that everything went well. However, later, errors began to pour. (not enough memory). At the same time, neither the load on the cluster, nor the application software changed. 

....
Monitoring has shown that the "old" is constantly growing. 

[Image: GS1s]

The strangest thing is that the heap grows most actively on the dedicated master server (red line). All traffic to the cluster goes only through this master server. This is done preferentially, since this is a test north and it’s easier to sort out problems by traffic. But, there is nothing to take up so much space. In our queries, there is not even aggregation, it only routes traffic to data nodes. 

I did a heap dump and it was over 6GB. VisualVM showed it to take up the most space:  transport.CopyBytesSocketChannel.
[Image: sizes1]

And M.A.T. swore at x-pack.....HttpTransport
[Image: mat]

Then I remembered that in the beginning there were still problems. Due to an error in the request, I flooded the cluster and put the monitoring system down. It turned out a lot of pairs of sockets, and somewhere between these versions, Elastic included the collection of HTTP connection statistics. 

To prevent this situation from happening again, I disabled the collection of these statistics: 
`http.client_stats.enabled: false`

I decided to check what's there now in these statistics: 
```
curl -s  [URL] '.nodes[].http'
{
  "current_open": 19811,
  "total_opened": 19811,
  "clients": []
... [Log Snipped] ...
  "clients": []
}
```
How! The number of current connections is equal to the total number of connections. This cluster has at best 5-10 simultaneous connections. IMHO, something, somewhere is clearly not released. In any case, they should not be equal. 

It seems that only statistics output is disabled, but it is still being collected. 
[Image: mat2]
