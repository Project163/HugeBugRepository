Title

Is it correct to mark fragment leaks when mFragmentManager is null？

Description
AndroidObjectInspectors mark the fragment is leaking when Fragment.mFragmentManager is null. However, fragment may reattach to activity later, right? 
If I analyze the heap use shark standalone, might I get wrong results?
Discussion
- As far as I know, Fragments are never resuscitated after receiving their on destroy callback.

Historically, the FragmentManager would clear out the manager instance when the fragment is destroyed: [URL]

Interestingly, it looks like the implementation in the AndroidX fragment has changed, the FragmentManager is set to null in detach: [URL]

Do you have a working example / repro where you're able to detach then reattach a fragment, and LeakCanary is reporting a leak anyway?

It looks like we might need to change how we detect leaks for android x fragments in Shark.

From what I can tell, we could switch to looking into `androidx.fragment.app.Fragment.mLifecycleRegistry.state` and see if that's equal to `State.DESTROYED`: [URL]

The state field was named `mState` prior to the conversion to Kotlin so we'll also have to account for that:
