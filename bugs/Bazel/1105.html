Title

"stopBranch called more than once by remote on" exception crashing Bazel

Description
### Description of the bug:

We are somewhat frequently seeing error messages like :
```
00:01:03.956   126 FATAL: bazel crashed due to an internal error. Printing stack trace:
00:01:03.956   127 java.lang.AssertionError: stopBranch called more than once by remote on external/rules_jvm_external+/private/tools/java/com/github/bazelbuild/rules_jvm_external/zip/libzip.jar
00:01:03.956   128 	at com.google.devtools.build.lib.dynamic.DynamicSpawnStrategy.stopBranch(DynamicSpawnStrategy.java:623)
00:01:03.956   129 	at com.google.devtools.build.lib.dynamic.RemoteBranch.lambda$callImpl$1(RemoteBranch.java:160)
00:01:03.956   130 	at com.google.devtools.build.lib.exec.AbstractSpawnStrategy$SpawnExecutionContextImpl.lockOutputFiles(AbstractSpawnStrategy.java:363)
... [Log Snipped] ...
00:01:03.956   145 	at java.base/java.util.concurrent.ThreadPoolExecutor$Worker.run(Unknown Source)
00:01:03.956   146 	at java.base/java.lang.Thread.run(Unknown Source)
```

We've seen this error with the same stack trace, other than a differing file ~50 times in the last month.
The files listed that stopBranch was called more than once by remote on are most frequently build tools, persistent worker executables, frequently used external jars, and compiler binaries. A few other example files it's hit on are `cake/closure_compiler.jar`, `external/rules_scala_annex+/third_party/bazel/src/java_tools/buildjar/java/com/google/devtools/build/buildjar/jarhelper/libjarhelper.jar`, and `cake/build/css/less_worker.js` if that's helpful at all.

We suspect that this might have something to do with dynamic spawn strategy, but are unsure. We are using buildfarm as our remote execution software.

### Which category does this issue belong to?

Remote Execution

If I'm not mistaken, I believe we can just remove the assertion because the case @smore566 explains here sounds like a valid use case to me.

I've also thought about some solutions like disallowing the "local fallback triggered by the failing remote branch" to call stopBranch, but that fundamentally breaks how the dynamic strategy was designed since `stopBranch` is not a simple "stop-the-branch" call. On top of that, a similar scenario can happen: a remote branch can fail before the first "stopBranch" is even called, so adding restrictions to whether a local fallback can call `stopBranch` might add unintentional side effect.

I think removing the AssertionError here makes sense, as the current implementation acts differently from the state prior to  . At that moment, all `stopBranch` calls cancelled the branch in the params.
