- Here's what happens on a normal run -
1) The server requests a call with a tag of 1.
2) The data provided by the fuzzer is written to the server.
3) The server performs a cq_next to perform the READ_INITIAL_METADATA op. The op completes and the cq returns GRPC_OP_COMPLETE with the tag of 1.
4) The server performs another cq_next which ends in a GRPC_QUEUE_TIMEOUT.
5) The server then begins shutdown by calling grpc_server_shutdown_and_notify and then cancels all calls.
6) It performs another cq_next and expects to receive GRPC_OP_COMPLETE with the shutdown tag.
7) Finally, it shuts down its completion queues and performs another cq_next expecting the GRPC_QUEUE_SHUTDOWN result.

In the error case, a deadline timer is started after reading the initial metadata. This deadline timer fires and the timer thread grabs a few references to the call stack and tries to perform a CANCEL op. While this is progress, the server tries to complete steps 5 and 6, but since the timer thread is owning references to the callstack, the server thread cannot finish shutting down with a single non-polling completion queue. It needs to wait for the timer thread to give up the references before finishing.
