Title

Malformed listen address causes hang on startup

Description
### Overview

With syncthing 1.5 a slightly malformed listen address (tcp4:/ :22000) causes the process to hang.  

### Does your log mention database corruption?

Negative

### Include required information

Please be sure to include at least:

 - **Version:** syncthing 1.5.0 on Linux Mint 19.3 (based on Ubuntu 18.04)  with kernel 5.3.0-53
 - **Steps to reproduce:** Replace the listen address with tcp4:/  and restart
 - **Errant behaviour:** Syncthing hangs.  Ctrl-C is detected but not actioned.  Kill -9 is required to terminate the process.
 - **Expected behaviour:** syncthing should detect malformed addresses and display an error message, especially addresses that are malformed in common ways
Discussion
- What do you mean by hang? What do the logs say?

I think it simply won't listen on that address and operate "as usual" other than that, it just won't connect anywhere, but UI etc should still be accessible.

I think it does detect that it's malformed, and prints a warning to both web ui and console, so I am not sure what else is expected here.
- "Hang" is sometimes a vague term, I apologize.  I mean it in the traditional sense, though.  Does not respond to any input or stimulus.  Web UI is non-functional, the browser is not launched at syncthing startup, and syncthing does not initiate outside connections.  The process detected a CTRL-C but would not then terminate.

- The problem is that a listening address like `tcp:/ :22000` gets parsed into a URL like `tcp:/// :22000` and we're not entirely consistent in where we use the original string and where we use the parsed string. The result is that try to stop a listener when the supervisor for it hasn't started yet, and this hangs forever.
- Fixing this is easy, it's just a matter of canonicalizing the URL before we use it as a key in a bunch of places. But there's an interesting footgun here, because `tcp:/ :22000` gets leniently parsed into a URL with `Host:"", Path:"/ :22000"`. The lack of host gets fixed by us into the unspecified host and default port, i.e., ` :22000`. That's probably a bit unexpected. So with the naive fix we'll just use this config and silently listen on all interfaces instead of localhost.

Should it be an error to have a URL in non-canonical form?
