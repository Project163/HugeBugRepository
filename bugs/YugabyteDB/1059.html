Title

[DocDB] Possible deadlock within Wait-Queue Shutdown path

Description
Jira Link: [Link: DB-8808]
### Description

Thread T1 - peer shutdown
`TabletPeer::StartShutdown()` ends up calling `WaitQueue::Impl::StartShutdown` while holding tablet peer's `lock_`. The latter ends up executing `thread_pool_token_->Shutdown()`, which waits for the last running task to finish.

Thread T2 - thread processing `TriggerPoll` tasks off `thread_pool_token_`.
Assume this thread is already running and is about to resume a waiter with `Status::OK()` (this would be the last task). when invoking the write query's callback, the thread calls `CreateOperationDriver` while preparing the write for replication, which in turn calls `GetRaftConsensusUnsafe()`, where we end up waiting for the tablet peer's `lock_`

So this leads to a deadlock, where T1 acquires `lock_` and waits for the last task in the threadpool to finish. While T2 processing the last task in the threadpool waits for peer's `lock_`.

cc: @robertsami 

One possible solution is to refactor Wait-Queue shutdown path. `StartShutdown` should only set shutdown flags, and all callbacks should be executed as part of `CompleteShutdown`, which doesn't hold the peer's `lock_`
