Title

SIGSEGV(segmentation fault) with fzf inside terminal emulator

Description
### Neovim version (nvim -v)

NVIM v0.7.0-dev+737-g818ae74ea

### Vim (not Nvim) behaves the same?

idk

### Operating system/version

5.10.70-1-MANJARO

### Terminal name/version

xfce4-terminal

### $TERM environment variable

xterm-256color

### Installation

AUR

### How to reproduce the issue

#### Script
The following script is used to create a simple popup window. Save the script to somewhere in your local file system.

```
lua
local api = vim.api

local function create_temp_buf()
  local buf = api.nvim_create_buf(false, true) -- create new emtpy buffer
... [Log Snipped] ...

open_window()
```

#### Reproduciable Steps
- Start pure nvim: `/usr/bin/nvim --clean`
- Open a floating window by sourcing the simple popup window script.
- Run a terminal with fzf command inside the floating window by executing `:terminal fzf --reverse --height 80\%`

  (to keep fzf program busy, you can `:lcd` to a directory with a large number of files)

- During fzf continuing searching files, exit the floating window by fisrt pressing `  ` then executing `:q`

### Expected behavior

The popup window exits without any error.

### Actual behavior

The nvim program crashes with message `fish: Job 1, '/usr/bin/nvim --clean' terminated by signal SIGSEGV (Address boundary error)`
  [Image: [URL]

### Additional Info
Tried removing one of the `--reverse` and `--height 80%` options for fzf and after that no segmentation fault happened.
Discussion
- Can reproduce on HEAD. Looks like a NULL pointer deref (possibly in libvterm?)
Backtrace:

```
AddressSanitizer:DEADLYSIGNAL
=================================================================

==111434==The signal is caused by a WRITE memory access.
==111434==Hint: address points to the zero page.
... [Log Snipped] ...
SUMMARY: AddressSanitizer: SEGV neovim/.deps/build/src/libvterm/src/screen.c:278:22 in erase_internal

```
- More minimal repro (still requires fzf):
```vim
split
lcd /
terminal fzf --reverse --height 80\%
call timer_start(1000, {-> execute('quit')})
```

The floating window doesn't seem to be necessary, but interestingly the creation of a new window (e.g: `split`) is required?

In `terminal_receive`, `term->vt->rows` is 5, which makes me think the ol' dummy window from `win_alloc_aucmd_win` is involved somehow (similar to the crashes in #14887). This is not the case for when `split` is omitted (the crash doesn't happen in that case). Maybe we need a `terminal_check_size` call somewhere?

Looks like this might be a duplicate of #13966, but this issue has a more general repro that doesn't require vim-floaterm.

---

Seems `refresh_timer_cb` calls `refresh_terminal` -> `aucmd_prepbuf` (`win_alloc_aucmd_win` creates a dummy window with 5 rows) -> `win_config_float` -> `terminal_check_size`, which sets `term->vt->rows` to 5. Skipping the resize for autocmd windows seems to fix the crash (should we even bother resizing for those?), but I'm not yet sure _why_ the resize crashes...
