Title

SslHandler defers channelActive event, confusing a user about the connection life cycle

Description
I can't really pretend to understand what is happening, but by having modified SecureChat example from netty 4 alpha6 to manually ssl handshake so that to avoid seeing this message: `Your session is protected by SSL_NULL_WITH_NULL_NULL cipher suite.` and actually have a cipher, causes the client to operationComplete() the handshake only after the next client send and server reply.

I'm not able to explain that well, but the code is here: [URL]

Simply run: SecureChatServer  and then SecureChatClient
and what you see is that the Server completes the handshake with
`INFO: cipher=TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA proto=TLSv1`
which is all well, but the client is now waiting for a line/message from user to send to server (it's a chat program after all) but didn't trigger the operationComplete() method of the sslHandler.handshake() ChannelFuture which was added as a listener (line 25 in HandShake.java)

But it will trigger it as soon as you enter one message/line and press Enter, in other words a send from client and a receive from server have to happen for the client handshake to trigger. I might be missing something, but I think this shouldn't happen?

This is the output on client:

```
java
Usage: SecureChatClient    
Oct 09, 2012 5:56:20 AM io.netty.handler.logging.LoggingHandler
INFO: [id:  ] REGISTERED
Oct 09, 2012 5:56:20 AM io.netty.handler.logging.LoggingHandler
... [Log Snipped] ...
client connected/handshook
type a line:
```

the part with `djsalkdjsalda` is the line that I have to type in order to see the handshake triggering. Hey I mean, likely the handshake is completed on both server and client (certainly it's done on server side already by the time I've about to type that line) but the triggering of it's completion on client side happens only later. (operationComplete() at line 25 on HandShake.java when running Client)
Discussion
- This is due to the change made with respect to #358.  However, I think `channelActive` should be invoked even before handshake is completed (i.e. as soon as connection is established) so that we don't give a user misconception about the life cycle of the connection.
- Fix checked in. Thanks for reporting! :-)
