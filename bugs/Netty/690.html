Title

Invalid HTTP2 pseudo-headers kill the session instead of being treated as malformed

Description
### Expected behavior

When a peer receives invalid pseudo headers the request or response should be treated as malformed as prescribed in section [Link:  ]. This entails a stream level PROTOCOL_ERROR as described in section [Link:  ]

### Actual behavior

The [Link: HpackDecoder] throws a connection level PROTOCOL_ERROR mid-decode, resulting in the connection being torn down.

### Steps to reproduce

Attempt to send a HTTP/2 request with an unknown pseudo header, pseudo headers out of order, or a mix of request and response type pseudo headers.
Discussion
- This is causing minor issues for us migrating to version of Netty that included the commit associated with PR [URL] Those problems include killing connections in production (relatively infrequent, but happens enough to be noticed) and some failing tests. We can work around it by validating headers before they are sent to the peer or disabling validation but ideally the receiving end, which should do this validation regardless to adhere to the spec, only needs to do it and behave correctly.
- @Scottmitch @ejona86 any comments ?
- ... [Middle Discussions Snipped for Brevity] ...
- I'm happy to work on this and I think we have two options.

1. We can leave validation in the HPACK decoder but move it to the end of the decode phase: we need to completely decode the headers to keep the HPACK state consistent.
2. We can move it clear out of the HPACK decoder (it's not really a HPACK concern) and change the API to specify if the headers belong to a request, response, or trailers.

I'd speculate that we should start with 1 and do 2 after a bit more research into the right place and how it will affect current users.
- 1) sounds good to me... @ejona86 @carl-mastrangelo @Scottmitch agree ?
