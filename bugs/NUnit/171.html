Title

Assume.That no longer works in Setup

Description
Since the latest release (4.4.0) Assume.That no longer ignores tests when it's in a setup method, where it did ignore them prior (4.3.2).

```
namespace TestProject1
{
    public class Tests
    {
        [SetUp]
... [Log Snipped] ...
    }
}
```

Notice that on 4.4.0 the test passes but on 4.3.2 it is ignored.
Discussion
- [URL] may be a different manifestation of this behaviour, with perhaps a common underlying root cause
- I haven't stepped through this in code, but having reviewed the milestone I am wondering if this could be an unintentional side effect of our fixing #4537 

If it is then perhaps we would just need to special case Inconclusive/Pass/ etc to differentiate from failed assertions.
- As unusual @stevenaw found the ticket that caused this.

The ticket treats exceptions as failures for registration.

An `Assume.That` failure throws an `InconclusiveException` which is caught and the test result set to its `ResultState` property, which is `Inconclusive`.
The problem is that `Inconclusive` is the default state. A `SetUp` with no failures also has this result.
It is not considered an error state and hence the code will execute the actual `Test1` method.

I changed the conditions in the BeforeTest...Command to check for `Inconclusive` with a `FailureSite.SetUp`.

The `Test1` method now no longer gets executed.
But the overall Test result is still `Passed`.

The `CompositeWorkItem` explicitly starts a test as `Success` with the comment:
_Assume success, since the result will otherwise default to inconclusive._
I would say `Inconclusive` would be a better result for a test with no `Assert`. 
At least that would prevent some developers from deleting all failing Asserts to make the test pass.

Also `TestSuiteResult.MergeChildResult` ignores `Inconclusive` because the suite starts of as `Passed`.

I added a commit to change the initial state to `Inconclusive` which solves this issue.
