Title

[gRPC Python] Stop using unstable Cython versions

Description
### What version of gRPC and what language are you using?
Python with gRPC 1.70.0/1.71.0/1.72.0, but the version is irrelevant

### What operating system (Linux, Windows,...) and version?
Windows & Linux & macOS

### What runtime / compiler are you using (e.g. python version or version of gcc)
Python 3.12.10, but that's irrelevant

### What did you do?
`pip install grpcio== `

macOS killed my async Python gRPC server after 1 minute, since it was using 100 GB of memory.
Tried the same code on Linux with the same gRPC version, and it worked fine.
After a long investigation, it turns out this is neither my bug nor your bug nor macOS's fault, it's a [Link: Cython bug], because `grpcio==1.71.0` was built with `Cython==3.1.0a1` which is an unstable unreleased alpha version of Cython. Additionally, it only happens on macOS because the same gRPC version is built using different Cython versions for each OS.

### What did you expect to see?
gRPC uses Cython, so I expected stable gRPC to use stable released Cython versions, not alpha and beta versions.
Also, I expected the Cython versions to be constant across different operating systems.

Using an unstable version of Cython in a stable version of gRPC doesn't make sense to me - it means you'll likely have bugs that will be fixed when it releases, and I don't think you gain anything from using unstable versions.

I think that using unstable Cython in unstable gRPC is still weird, but might make sense if you want your latest version to use the latest Cython version. I think it's best to always use stable Cython versions, so that bugs reported about your release candidates will be your bugs and not Cython bugs. If you're worried about Cython affecting you in weird ways, maybe your stable version should always use a month-old stable Cython version, and use the latest stable Cython only in rc versions.

- Hi @NotWearingPants thanks for raising this issue. We'll look into our builds to check why MacOS and some specific architectures are using the release candidate versions of Cython. 

My guess is that we specify Cython bounds in our builds as `Cython<4.0.0rc1`, which were working fine previously, however a [Link: recent change in pip]) allows installing release candidate versions if the requirement specifies a release candidate in the requirement bounds.

I believe this is the cause for the release candidate versions of Cython being installed. Also coming to the memory leak issue with Cython, I believe it has now been fixed in Cython's patch version 3.1.1. Given that this is now the most recent version that satisfies our requirement constraints `Cython<4.0.0rc1`, I believe our artifacts from upcoming releases should automatically pick up the new Cython version and the memory leak should be solved too.
- Thanks for the report, @NotWearingPants. We will update our build systems to pin cython to a stable version and re-release grpcio 1.71 and 1.72 as soon as we can.
