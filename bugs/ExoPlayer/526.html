- Using player.getTotalBufferedDuration() I manage to understand how this issue is be produce.

we are playing a live stream that has as base this values

	#EXT-X-TARGETDURATION:6
	#EXTINF:4.166,live
	#EXTINF:2.000,live
	#EXTINF:1.084,live

the rule for **#EXT-X-TARGETDURATION** says that all Media Segments will be less or equal to defined value so is not a problem that the TARGETDURATION = 6 and EXTINF lower then that;

The value for **TARGETDURATION** never changes, the playback starts the value for **player.getTotalBufferedDuration()** stays at 6 to 7s for about 10s of playback (setBufferDurationsMs is allowing the value to go above this it can't because is live content), after this initial 10s the **player.getTotalBufferedDuration()** stars to get lower, lower than 6s,
[Link: loadPlaylist()] is triggered but the segments loaded aren't enough to fill the 6s duration of TARGETDURATION, the **player.getTotalBufferedDuration()** get higher but is less than 6s, the buffers keeps going down and down until it reaches 0, at this point **loadPlaylist()** already triggered again but is too late Player.STATE_BUFFERING already trigger the playback has stopped and when the segments are available again the **player.getTotalBufferedDuration()** may go above 6s or not and stay like this for some time, until eventually goes above 6s stays like that for some time but eventually will drop and the issue shows up again and again, can take minutes to happen sometimes but it does all the time.

Keep the value **targetDurationUs = 1s** prevent this from ever happen, but causes unnecessary loadPlaylist() calls every 1s in the case TS are only be created at a 2s rate for example.

So the scenario that probably can occurs to any live stream where at some point has a amount of segments with they added duration time is almost equal or less than targetDurationUs we have this issue.

The first thing that comes to mind is not only call **loadPlaylist()** on the situation that **targetDurationUs** demands but also on the situation that the buffer has already consume all the segments available, not constantly all the time to prevent a race, but at the time the segments are all consumed, and then again in 1s or so if the server didn't provide enough on last update call.

Take a look here and see what can be done, I think I provide enough info about the issue, if need test or more info let me know.
