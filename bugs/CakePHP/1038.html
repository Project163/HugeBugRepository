Title

Cannot store "false" values as a hidden field in a reliable way

Description
This is a (multiple allowed):

* [x] bug
* [ ] enhancement
* [ ] feature-discussion (RFC)

* CakePHP Version: 4.0
* Platform and Target: Debian Buster

### What you did
See #5639 
I have a column declared as "TINYINT(1) DEFAULT 0 NOT NULL". When I store the value "false" as a hidden field in a form it is read back and converted to NULL, which cannot be written back into the table.

### What happened
I get a database error indicating that NULL instead of false was written back

### What you expected to happen
That the value is converted back to false and written back as such instead of NULL

"Before you open an issue, please check if a similar issue already exists or has been closed before."
Yes, I did :)

In my form I write
`echo $this->Form->control(" . ", "hidden")`
which produces the output
` `
Note, that there is no `value="..."` in the input field.
On submit, the POST parameter is empty, which translates to an empty string, which is marshaled as NULL in patchEntity.

In my opinion, we have 4 different values of bool: true, false, and "not a value" aka null, and "not specified". A hidden field should somehow be able to distinguish between them, though I have no idea how to do that with the last 2 (null and undefined).
Discussion
- I agree that at least for a not null column as boolean (tinyint 1) the empty string must default to false instead of null here.
As @markstory once said:


And the null conversation would just create a DB error here.
- The database type classes have no info about the table schema, hence marshalling values based whether column is nullable or not is not possible.
- ... [Middle Discussions Snipped for Brevity] ...
- Marshalling empty string to `null` would make sense if the column was nullable. One can have nullable boolean columns. So we need to think of a solution which works for both nullable and non-nullable columns.

One way to deal with this is make the FormHelper convert `false` to `0` for boolean fields. Making `ContextInterface::val()` do that could be considered, since context classes do have the schema info.
- That sounds like a fair compromise.
I think we had similar issues also in some other place before, where a `false` => `''` => null aka nothing then would result in an undesired value in the end.

If we scope this to booleans, this should be without side effects then.
