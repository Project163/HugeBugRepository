Title

hpack_encoder.cc sets END_STREAM flag on CONTINUATION frame

Description
If a gRPC C++ server's trailers are large enough to be split over a HEADER frame plus subsequent CONTINUATION frames, C++'s implementation sets the END_STREAM flag on the final CONTINUATION frame rather than on the HEADER frame. This is a bug because HTTP/2 CONTINUATION frames do not have an END_STREAM flag (see [Link: relevant section of the spec]); rather, then the END_STREAM should be set on the HEADERS frame itself (the lack of the END_HEADERS flag will let client's know that this really means the stream is over after the subsequent CONTINUATION frames are received). As-is, compliant client implementations will see that the HEADER frame received from a gRPC C++ server does not specify that it is end-of-stream, process the continuations, then dutifully wait (hang forever) until end-of-stream is received on another HEADERS frame that is not going to come.

This issue was reported by a user with a gRPC Java client and a gRPC C++ server ([Link: original issue]). The reporter's [Link: second comment] details the behavior of C++ here, including the lines of code responsible for this behavior.
