Title

Teardown failures are not reported

Description
Ever since the merge of the issue-54 branch, our test run results have indicated "Overall result: Failed" even though no failures or errors are shown.

It turns out this is due to a test, introduced in that merge, which fails during TearDown. 

This assertion in TestContextOneTimeTearDownTests always fails...
   Assert.That(context.Result.SkipCount, Is.EqualTo(1)));
It fails because an explicit test is not counted as a skip in the results.

This went unnoticed because the failure itself is not reported. We need to figure out how to report TearDown failures first, before fixing the error in the assertion.

We should also address the general question of how we handle explicit tests, but first let's get the errors reported correctly!
Discussion
- @rprouse: Since this really is a critical error, let me know if you don't have time to work it right now and I'll do an interim fix for the alpha-1 release. Meanwhile, some ideas...

Looking at the code in nunit-console ResultReporter.cs, I see that I put a // TODO there indicating that we need to report setup and  teardown tests. The nunitlite runner ResultReporter has the same problem, although it's not commented. Both classes only report suite failures when the suite is a Theory.

NUnit 2.6 reported failures in TestFixtureSetUp and TestFixtureTearDown by checking the FailureSite property of the result, which indicated whether a failure occured in SetUp, TearDown, etc. There is no corresponding property in the XML for NUnit 3.0.

A short term solution would be to report any suite failures or errors if there is a message other than "One or more child tests had errors". This is pretty ugly, but could work in the short term.

Any permanent solution requires adding some info to the result that is delivered to nunit-console. We could re-introduce FailureSite, but I'd prefer to try to do  without it. Perhaps the easiest would be to distinguish teardown failures by the result state. We could have Failed:TearDown for example. Alternatively, we could have a special state for a suite that failed because some child failed, like
Failed:ChildFailure. Any of these require changes all through the framework, so they may be better to introduce later.
