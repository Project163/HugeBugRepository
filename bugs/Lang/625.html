Title

StringUtils.abbreviate is not emoji aware, breaks surrogate pairs

Description
---------- Forwarded message --------- 
From: Carsten Kirschner <carsten.kirschner@corussoft.de.invalid> 
Date: Fri, Apr 11, 2025 at 10:15 AM 
Subject:  [lang]  StringUtils.abbreviate is not emoji aware, breaks surrogate pairs 
To: dev@commons.apache.org <dev@commons.apache.org> 

 Hello, 

 The current commons lang3 StringUtils.abbreviate (3.17.0) implementation will destroy 4 byte emoji characters and larger grapheme clusters. I know that handling grapheme correctly before java 20 is not possible, but at least a codepoint aware solution with String.offsetByCodPoints could be build. I wrote a small test to show the problem. 
The zero width joiners in the family emoji are questionable for the abbreviate, but there should never be a question mark for an invalid char in the result as there is now. 

 The problem is not so much the „doesn’t look nice“ aspect of the broken emoji, but if that abbreviated string is passed to an XML Writer (com.ctc.wstx.io.UTF8Writer in my case) it throws an exception on this broken byte sequence. Like this: Caused by: java.io.IOException: Broken surrogate pair: first char  , second 0x2e; illegal combination 
                at com.ctc.wstx.io.UTF8Writer._convertSurrogate(UTF8Writer.java:402) ~ [woodstox-core-7.0.0.jar:7.0.0]  

 Thanks, 
Carsten

Discussion
- I've experimented with fixing this, it's possible, but introduces non-trivial changes that will likely have performance implications. 

 The bigger issue is that such a change will single out the "abbreviate" methods while leaving the issue present in the rest of the class and in Lang in general. 

 The simple policy would be to say that in Lang at large grapheme clusters are not supported, which is not great but easy to understand. 

 I think this needs more exploration as to what the performance implications are of fixing the "abbreviate" methods and then what can be extrapolated on making similar changes in the rest of the class, and Lang. 

 An alternative would be to extend the new "Strings" class with a subclass that supports grapheme clusters. 

 The fact that a String can be created that is effectively "broken" is an issue for the XML example that we should address, somehow.
