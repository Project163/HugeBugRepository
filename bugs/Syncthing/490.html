Title

Inaccessible files during scan are marked as deleted

Description
Repro:

1. Create `dir/file` and make sure they are synced between devices A and B.
2. Change ownership/permission for `dir` on device A such that the user syncthing is running as is no longer able to access `dir` (e.g. `sudo chown root:root dir && sudo chmod 700 dir`).
3. Hit the rescan button on device A and wait for "changes" to propagate to B.

Result: `dir/file` gets deleted from device B.

Expected: Some kind of error or at least "nothing" (see #4480), but certainly not deletion of the file on the remote.

Origin of bug:  
Lstat returning any error is considered equal to file having been deleted: [URL]

Possible solutions:  
Maybe this can be handled with stricter checking of the error returned by Lstat. If we do this, I believe we need to add `IsNotExist(err) bool` to the filesystem interface to make sure all filesystem implementations are compatible with this check.  
The following idea doesn't actually work (we also detect "ordinary" deletes this way). It might be both more consistent and performant to drop these lstat checks and replace them by comparing the new file info with the one it has replaced. Thus cases like replacing a dir with a file can still be detected and handled, while the case described here wont result in data loss.   
Another possibility would be to implement #4480 and skip the current lstat tests on paths that failed to be scanned.
Discussion
- This is mostly deliberate, as it's kind of hard to decide which errors mean the file doesn't exist. One typical case (that might be solved by your new stuff) is when a directory becomes a file, for example. Stat of the files inside the (previous) dir doesn't return NotExist.

Similarly, your test case (we lose permissions to a directory) means to me that we *should* propagate this as a delete, as it might be deliberate.

Deliberate or not it may still be wrong, so feel free to improve it. :)
- I guess that's the only thing to be discussed then, because if this is to be expected, this bug report is invalid. For me it is unexpected that something gets deleted when it becomes unavailable for any other reason than being deleted (e.g. permissions changed), and thus falls under our 1. goal against data loss. I tried to find arguments, but I don't have any. It just feels wrong to "delete" files by changing permissions: In my opinion changing permissions should prevent Syncthing from accessing something, but isn't simultaneously a sign to get rid of it...

- There's a handful of very specific error codes that should probably not be treated as deletion, namely whatever the Go equivalents are to EIO, ESTALE, EAGAIN, all of which aren't indicative of the file being gone, just not being accessible for reasons other than permissions (I do agree that lack of access permissions makes sense to trigger deletion though).
- This is already solved, see #4765. It will not remove anything unless we know for sure it has been deleted (parent is file/symlink or IsNotExist from Go's os package is true).
