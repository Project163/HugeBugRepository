Title

Surprising behaviour of DelayedConstraint pollingInterval

Description
The Syntax Helper `After(int, int)` creates a DelayedConstraint with a 'pollingInterval', which allows a test to run quicker in the event that it passes early.

However, it has some surprising behaviour if the test is going to fail. The 'delay' parameter is not the absolute time delay between starting the assertion and failing, but it is the elapsed time only while waiting to poll. It ignores any time spent in the condition expression.

If the condition expression is calling a method with a timeout, then the test can fail much more slowly than if the pollingInterval were not there.

For example:

```
Assert.That(() => { Thread.Sleep(1000); return false; }, Is.True.After(2000));
```

fails after 3s as expected.

But

```
Assert.That(() => { Thread.Sleep(1000); return false; }, Is.True.After(2000, 100));
```

fails after 20s.

For pure unit testing, this shouldn't be a problem. But when integration testing async expressions which might be timing out, then I think it's undesirable.

Is there a good reason for it to work this way?
Discussion
- Good point, I don't think there's any reason and long delays when executing the delegate during polling have simply not been considered.
