Title

ActiveRecord counter_cache column calculated even when not specified in 4.2.0

Description
I found this unexpected behavior while updating my apps to 4.2.0 from 4.1.9. It is a breaking change for me because I am managing counter columns manually with the assumption that Rails doesn't increment them unless I explicitly specify `counter_cache` on my `belongs_to`.

Example code:

``` ruby
# Gemfile
gem 'activerecord', '4.2.0'
# gem 'activerecord', '4.1.9'
gem 'sqlite3'
```

```
ruby
require 'bundler'
Bundler.setup(:default)
require 'active_record'

... [Log Snipped] ...
puts "user.comments_count: #{user.comments_count}"
puts "user.reload.comments_count: #{user.reload.comments_count}"
```

I get:

``` ruby
# Rails 4.1.9
user.comments_count: 0
user.reload.comments_count: 0

# Rails 4.2.0
user.comments_count: 1
user.reload.comments_count: 0
```

Also, if `counter_cache` is specified like so:

``` ruby
class Comment < ActiveRecord::Base
  belongs_to :user, counter_cache: true
end
```

It seems the in memory counter is fixed to 1:

```
ruby
user = User.create!(comments: [Comment.new, Comment.new])
# Rails 4.1.9
user.comments_count: 0
user.reload.comments_count: 2
... [Log Snipped] ...
user.comments_count: 1
user.reload.comments_count: 2
```

- @sgrif That's because the hash

``` ruby
comments: [Comment.new, Comment.new]
```

is wrapped to

``` ruby
[[Comment.new, Comment.new]]
```

in the call stack (maybe at ActiveRecord::Associations::concat) and its length is 1.

If you try appending with <<, you'll get:

``` ruby
user = User.create!(comments: [Comment.new, Comment.new])

user.comments << Comment.new << Comment.new

user.comments_count: 3
user.comments_count: 4
```

So @negative it is not "fixed".
