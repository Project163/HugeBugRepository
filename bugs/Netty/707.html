Title

UDP ports may remain open after calling RoundRobinDnsAddressResolverGroup#close()

Description
In Netty 4.1.36 (and several versions prior), we've found that UDP ports can "leak" when using multiple `RoundRobinDnsAddressResolverGroup` instances. Please let me begin by acknowledging that I may be missing something important about how `RoundRobinDnsAddressResolverGroup` is _supposed_ to be used, but I _think_ this might be a bug.

### Expected behavior

When calling `RoundRobinDnsAddressResolverGroup#close()`, any persistent resources (UDP ports, in this case) opened by the resolver group should be closed/released.

### Actual behavior

Some UDP ports may remain open after calling `RoundRobinDnsAddressResolverGroup#close()`.

### Steps to reproduce

In a loop, create a new `RoundRobinDnsAddressResolverGroup` and use it to resolve an address. Close the resolver group at the end of each iteration. While running, observe the number of open UDP ports over time (I used `netstat -ap udp | wc -l` under macOS).

### Minimal yet complete reproducer code (or URL to code)

```
java
final NioEventLoopGroup eventLoopGroup = new NioEventLoopGroup(1);

try {
    while (true) {
... [Log Snipped] ...
    eventLoopGroup.shutdownGracefully().await();
}
```

### Netty version

4.1.36 (going back to at least 4.1.32, and probably earlier than that)

Discussion
- Simplifying further, it turns out we don't actually need to try to resolve anything to demonstrate this issue; just getting a resolver will do the trick:

```
java
while (true) {
    final RoundRobinDnsAddressResolverGroup resolverGroup =
            new RoundRobinDnsAddressResolverGroup(NioDatagramChannel.class,
                    DefaultDnsServerAddressStreamProvider.INSTANCE);
... [Log Snipped] ...
    Thread.sleep(1000);
}
```
- I've opened #9214 as a potential fix for this issue.
