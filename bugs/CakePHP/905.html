Title

BC breaks with deprecations

Description
I think we discussed this a while back, but it just took me by surprise again in a few cases.
If we do not follow the inheritance principle here closely, we will have soon a lot of broken user apps due to this issue.

In my case I have a contact form and a validator:
```
	/**
	 * @param \Cake\Validation\Validator $validator
	 * @return \Cake\Validation\Validator
	 */
	protected function _buildValidator(Validator $validator) { ... }
```
With 3.6 this would now break silently and can be a security issue (no validation anymore at all for all forms!) as the core code internally shortcuts it due to the deprecation refactor:
```
* @deprecated 3.6.0 Use Form::getValidator()/setValidator() instead.
     */
    public function validator(Validator $validator = null)
    {
        deprecationWarning(
... [Log Snipped] ...
        return $this->getValidator();
    }
```
But the actual code is never calling this old one which would set the ones as CakePHP 3.x so far depended on.
It directly goes to getValidator().

## So to sum things up
We must always call internally the old methods still and only from the outside of core are allowed to replace our own old method calls with new ones. Even in plugins this is already quite dangerous and can lead to side effects in apps depending on the plugins. But this is sure worse with the core code here and apps depending on the functionality behind protected methods being overwritten as designed to be done.

Not sure how we can still have deprecation warnings then, though. How to distinguish outside vs inside usage.

There are lots of other places where core-internal using the new methods will shortcut the user land methods. We should probably revert those where it could be also critical in terms of functionality BC breaks.
