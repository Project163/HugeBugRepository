Title

ijar zipper refuses to create directories: default directory are created with wrong permission

Description
I'm writing a genrule that creates a .ear file by unpacking several .war files into a directory and then repacking them into a single artifact. I'm trying to use `//third_party/ijar:zipper`, but it is failing when trying to extract war files that contain subdirectories that don't yet exist in the destination.

For example, my genrule does this:

```
mkdir backend
cd backend
../../$(location //third_party/ijar:zipper) x ../../$(location :backend)
cd ..
```

And when running it I get a failure that looks like this:

```
Cannot open file /root/.cache/bazel/_bazel_root/ /master/ear/backend/WEB-INF/web.xml for writing: Permission denied
```

If I change `mkdir backend` to `mkdir -p backend/WEB-INF` the error goes away, but then I have to pre-create each subdirectory manually. This makes the ijar zipper not very useful for extracting archives that might contain subdirectories.

I can work around this easily enough by using jar instead of ijar zipper for extraction.

- I think you've got it -

`ls -lR` with `-type f`:

```
.:
total 4
drw-r--r-- 2 nobody nogroup 4096 Dec  2 00:13 WEB-INF

./WEB-INF:
total 0
```

`ls -lR` without `-type f`:

```
.:
total 4
drwxr-xr-x 3 nobody nogroup 4096 Dec  2 00:13 WEB-INF

./WEB-INF:
... [Log Snipped] ...
-rw-r--r-- 1 nobody nogroup   14 Dec  2 00:13 logging.properties
-rw-r--r-- 1 nobody nogroup 2110 Dec  2 00:13 web.xml
```

So in the happy case the directory is created with permissions 755, but when it auto-creates it it does so with permissions 644 in the sandbox, which would explain the later error.
