Title

preserve classLoader in Script.evaluate() method

Description
I'm using the ant task to run a groovy script. It first does some preparation stuff so users of the system can rely on it in their scripts. The way it reads is something like: 

 do_some_stuff_and_set_some_vars; 
evaluate(myScript); 

 When I set additional classpath through the ant task and have "import package.from.the.additional.classpath.class", it is available in the step "do_some_stuff_and_set_some_vars", but it is not available in the evaluate step. Fails with "unable to resolve class package.from.the.additional.classpath.class". 

 To workaround I do 
gsh = new GroovyShell(this.class.classLoader, getBinding()); 
gsh.evaluate(myScript); 

 And now works. So I believe this is a bug because one would expect to have the same parent ClassLoader besides Binding when using the Script.evaluate() method. 

 When using the command line groovy this is not really an issue because classpath is set globally through the -cp argument. But when running groovy scripts programatically like with ant, then it turns out to be an issue.
Discussion
- just to be clear... you have a script like this  
  
  package  bar
 import  foo.Bar
 new  Bar()
evaluate """
   new  Bar()  // Bar exists only in  package  foo
 """
 
  
 and you expect this not to fail. If yes, then sorry, that is no  error. If you have a script   
  
  package  bar
 import  foo.Bar
 new  Bar()
evaluate """
   import  foo.Bar
   new  Bar()  // Bar exists only in  package  foo
 """
 
  
 and the first import and "new Bar()" works, but the second in evaluate does not, then it is a bug, yes. Script#evaluate does look like this: 
  
         GroovyShell shell =  new  GroovyShell(binding);
         return  shell.evaluate(expression); 
  
  so the parent class loader will be set in the wrong way, yes. 

 So I guess it is a bug
- Yes, in your second example it would fail  on  "import foo.Bar" in the evaluated script. 

 As you show the code of Script#evaluate, one obvious solution is to change it so it passes its ClassLoader when constructing the GroovyShell. But I wonder why GroovyShell doesn't pick up by default its classloader? 

  
      public  GroovyShell(Binding binding) {
         this ( null , binding);
    }
 
  

 Could be: 
  
      public  GroovyShell(Binding binding) {
         this ( this . class. classLoader, binding);
    }
- this(this.class.classLoader, binding); 

 will not work, in Java this would not be legal, in Groovy this.class.classLoader would return the application loader maybe, but in the end it would be much different from the version with null
