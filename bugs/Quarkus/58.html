- Hm, I think that it could be related to the fact that we replace the MP Config "data" during various phases of bootstrap... so it might be some sort of timing issue. @dmlloyd David could pls shed some light on this?  

In any case,  the validation in [Link: ConfigBuildStep] **is wrong** because it can only validate static config properties, e.g. it could fail for runtime properties (system properties, environment properties, etc.). On the other hand, we have to valide all the `@ConfigProperty` injection points (MP Config requirement). So we'll have to collect all the injetion points during augmentation but run the validation at RUNTIME_INIT. Which is not very good because A) we will not fail fast and B) we'll prolong the startup time...
- There's not a lot to say (after #1478): the build configuration is set up by consuming config sources, converters, etc. and then producing (and installing) the config object.  At run time, we parse the configuration and install the config object in a very similar way (though we use a couple of fixed config sources containing properties copied from the build `application.properties` and preset defaults from extensions).


I don't think you'll prolong the startup time in any significant manner, especially if the config part is just: read config value, store in field, read config value, store in field, etc.
