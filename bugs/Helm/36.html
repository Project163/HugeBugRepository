Title

Lock digest differs when performing dependency build on chart in Helm 2 and then Helm 3

Description
When doing `helm dependency build` with the Helm v3 CLI on a chart using the Helm `v1` API, the following error occurs:

```
┌─[/tmp/test-chart]
└─▪ helm dependency build
Error: Chart.lock is out of sync with Chart.yaml
```

#### Expected Behaviour
Based on the [Link: Helm v2 to v3 FAQ], Helm v3 should behave the same as Helm v2 with a chart using the Helm `v1` API.

### Steps To Reproduce

1. Create a new chart using the Helm v2 CLI

```
┌─[/tmp]
└─▪ helm2 create test-chart
Creating test-chart
```

2. Add a `requirements.yaml` to the chart and add one or more dependencies. I used the following:

```yaml
dependencies:
- name: postgresql
  version: 6.5.5
  repository: [URL]
  condition: postgresql.enabled
```

3. Run `dependency build` using the Helm v2 and v3 CLI, observing the different outputs.
Helm v2
```
┌─[/tmp/test-chart]
└─▪ helm2 dependency build
Hang tight while we grab the latest from your chart repositories...
...Unable to get an update from the "local" chart repository (http:// :8879/charts):
	Get [URL] dial tcp  :8879: connect: connection refused
... [Log Snipped] ...
Downloading postgresql from repo [URL]
Deleting outdated charts
```
Helm v3
```
┌─[/tmp/test-chart]
└─▪ helm dependency build
Error: Chart.lock is out of sync with Chart.yaml
```

### CLI Versions

```
└─▪ helm2 version

└─▪ helm version

```

- One thing to consider here would be to emit a warning when the hash verification failed, but the versions are different. Something like:


I would suggest adding a `strict` flag of some sort to allow security-minded individuals a way of preventing this. However, with signed charts I can't think of any real security issue this introduces. (With unsigned charts, though, it is admittedly dangerous)

While this is ugly, it doesn't hide what is happening, whereas the other solutions i have seen attempt to silently work around the hash mismatch by regenerating, ignoring, or updating.

- Regenerating is safer if and only if we can do it without altering any "meaningful" data. But I haven't yet seen a good way of doing this.
- Ignoring is always bad, and opens security holes
- Updating basically ignores the entire intention of having a lock file in the first place, since the build is not reproducible, but I think it would be fine to add a flag that let people CHOOSE to force an update.

The lockfile does have a _specific_ version of a package in it (as opposed to a SemVer pattern). So we could regenerate just the hashes by reading a lock, fetching the packages, and re-hashing. 

Here's the Lock.Dependency struct:

```
go
type Dependency struct {
	// Name is the name of the dependency.
	//
	// This must mach the name in the dependency's Chart.yaml.
... [Log Snipped] ...
	Alias string `json:"alias,omitempty"`
}
```

It is possible to parse into that struct, then get the exact dependencies. Then fetch them and regenerate just the hashes. Again, it is not _secure_ unless charts are all signed. But it is one way to try to reproduce an existing app without having to call `Update` on the manager.
- Would you even need to download everything again? It just needs to update the digest against the right structure based on the input. The algorithm didn't change, it just went from hashing the requirements, to hashing the requirements+lock (#5874 + #6736). I don't see any recursion or walking for sub-charts involved here, and my _recollection_ is that the `chart.Dependency` structure didn't change particularly in the Helm v2->v3 change, when I went looking previously.
