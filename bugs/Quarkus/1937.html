Title

Generic CDI Decorator Throws java.lang.NoSuchMethodError

Description
### Describe the bug

When using CDI decorators with generic type parameters in a Quarkus application, a `NoSuchMethodError` is thrown when invoking a decorated method. The error message indicates that it cannot find the method in the decorator class.

The following configuration fails when executing the `GreetingResource.hello()` method:

```
java
interface Repository  {
  T get();
}

... [Log Snipped] ...
  }
}
```

The exception is:

```
	Suppressed: java.lang.NoSuchMethodError: 'java.lang.String org.acme.LoggingRepository.get()'
		at org.acme.GreetingRepository_Subclass.get(Unknown Source)
		at org.acme.GreetingRepository_ClientProxy.get(Unknown Source)
		at org.acme.GreetingResource.hello(GreetingResource.java:53)
		at org.acme.GreetingResource$quarkusrestinvoker$hello_e747664148511e1e5212d3e0f4b40d45c56ab8a1.invoke(Unknown Source)
		at org.jboss.resteasy.reactive.server.handlers.InvocationHandler.handle(InvocationHandler.java:29)
		at io.quarkus.resteasy.reactive.server.runtime.QuarkusResteasyReactiveRequestContext.invokeHandler(QuarkusResteasyReactiveRequestContext.java:141)
		at org.jboss.resteasy.reactive.common.core.AbstractResteasyReactiveContext.run(AbstractResteasyReactiveContext.java:145)
```

A similar configuration works as expected in Weld.

### Expected behavior

Quarkus Arc decorates all beans that implement the interface with the decorator and no exception is thrown. In this example, the `GreetingRepository` is decorated with logic in the `LoggingRepository ` decorator.

### Actual behavior

Decorated bean throws `NoSuchMethodException`.

Discussion
- Likely an Arc bug. I know I already saw another issue with generic decorators (https://github.com/quarkusio/quarkus/issues/30811).
Note that Quarkus/Arc doesn't have full support of decorators like Weld.
I am not sure how far we are with supporting these cases, can take a look on Mon.
- `java.lang.NoSuchMethodError: 'java.lang.String org.acme.LoggingRepository.get()'`

The decorator only has a method with return type of `Object` (after erasure), so not sure where that `String` comes from. Perhaps we expect the decorators have a method with the same signature/descriptor as the decorated class? Or something like that.
- It seems that when we create the `invokevirtual` call to the decorator (from bean `_Subclass`), we build the call from the method descriptor of the original method - in this case it means we expect return type `String` but the decorator only knows one with `Object`.
