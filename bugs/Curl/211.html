Discussion
- @icing: Curl_conn_socket_set() is called before the transfer and connection have been "attached" to each other with `Curl_attach_connection` so ` data->conn` is still NULL.

I did a first attempt at passing in `conn` separately to handle this, but when I did I just ran into another problem in `Curl_quic_connect()` which calls `quic_set_client_cert` and the assert on line 308 triggers. I presume the   commit moved it so that it now isn't setup in time for this h3 call trace?
- @bagder I won't name names, but someone said that `data` always has a `conn` and we should remove that extra parameter. I am about to submit a PR that re-instates that.

The problem with `quic_set_client_cert` is that the method for handing out the effective ssl config is returning `NULL` if no SSL filter is detected. I'll change that in the PR as well. In the future, the QUIC connect filter should be of type `IP_CONNECT | SSL` to reflect what it does.

Another thing I will also  change is that, reflecting on the fact that during the "setup" calls things are not really fully initialized, filters should really do no action *other* than setting things up. Actions against the network should only start at the first "connect" call. I'll change that in the socket filter.

I think this gives us a cleaner init phase and a better idea what happens when.
- "Always" is a tricky word since it seems to imply that it is always that way and not always except in some cases... :grimacing:  (Thanks)
