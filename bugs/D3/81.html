Title

transition "end" callback broken when used with chained transitions (?)

Description
Please open small test case, which uses d3 v3.1.6:
[URL]
Then open web browser console and you will see following logs:

```
transition 0 end
transition 1 start
transition 1 end
transition 2 start
transition 2 end
transition 3 start
transition 3 end 
```

What makes perfect sense to me.

However when newer version of d3 is used:
v3.2.6: [URL]
v3.2.2: [URL]
I can see:

   transition 0 start
   transition 0 end
   transition 1 start
   transition 2 start
   transition 3 start
   transition 3 end 

Is it expected? ;) "start" event is triggered for each transition, while "end" only for the first and the last one.
Discussion
- It was basically luck that it worked before, but I think we can fix this.

The way transitions are currently implemented, there is no guarantee that the "end" event listener for transition _i_ will be notified before the start of transition _i_+1. In the past it happened to work out that way, but it was luck. Prior to  , timers were called back in the opposite order they were registered; now they are called back in the order they were registered, which is much less surprising and fixes  #1245. However, this change broke the usage pattern you described.

Since timers are called back in the order they are registered, I think we can guarantee that the start callback for transition _i+1_ is registered after the tick callback of transition _i_. Currently, that’s not the case, because it goes like this:
1. Transition 1 registers its schedule callback.
2. Transition 2 registers its schedule callback.
3. Transition 3 registers its schedule callback.
4. Transition 1 receives its schedule callback and starts immediately.
5. Transition 1 registers its tick callback.
6. Transition 2 receives its schedule callback, and registers its start callback.
7. Transition 3 receives its schedule callback, and registers its start callback.
8. Transition 1 receives some number of tick callbacks.
9. Transition 1 ends.
10. Transition 2 receives its start callback, and registers its tick callback.

ick callback is registered _after_ transition 3’s start callback. Another way to look at it is the priority of the callbacks because of the order in which they are registered:
1. Transition 1 schedule

So, the simplest fix is probably to adjust the implementation such that transition 2’s tick callback is registered before transition 3’s start callback, perhaps by combining the start and tick callbacks. Alternatively, we could do implement more formal ordering for the d3.timer queue to guarantee that transition 2’s callbacks always get called before transition 3… but I think it will be easier to just fix the one condition that violates this now, rather than complicate the run loop.
