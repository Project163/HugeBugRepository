Title

operator== now behaves unexpectedly

Description
It appears the == operator on vectors and matrices have changed behavior since the   release. If you run the following code snippet with   and then with the current master branch they do not produce the same results. Objects that used to be considered equal are no longer equal.

---- ----
#include  
#include  

int main(int argc, const char* arg[]) {

  glm::vec2 a(0.0f, 1.0f);
  glm::vec2 b(-0.0f, 1.0f);

  std::cout  ----

It appears the new behavior was introduced  by [URL] to silence compiler warnings, but this breaks compatibility and violates my expectation that an == operator is equivalent to per-element application of ==. 

I understand some folks may want this stricter form of equality, but could this at least be placed behind a feature define to avoid breaking existing code?
Discussion
- The code added in 384dab0 is actually explicitly checking for IEEE 754 floating point types and using `std::memcmp` for them, and continues to use `==` operator otherwise. The commit is about silencing compiler warnings, but I fail to see any possible warnings that could be suppressed in this way.
If this is perhaps an optimization, then it is strange that the new equality comparison functions are still called member-wise in a loop, which is much inferior to calling `std::memcpy` on a continuous memory range once.

But this is still a silent/unexpected breaking change not mentioned in 0.9.9 release notes, so this bug being labeled an enhancement is strange. I think that this part of the change should be either reverted, or provided with an explicit opt-out and some documentation/explanation.

I personally think that comparing IEEE 754 types not by IEEE 754 rules is very unexpected and does not actually match glsl semantics. And modern hardware often has direct support for efficient IEEE 754 comparisons.
- This issue is fixed in master branch for GLM   release.
