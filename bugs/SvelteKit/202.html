Title

npm run check make app reload and CSP blocks the navigation

Description
### Describe the bug

I start development. The app starts in the browser. Everything works.

I launch in another shell's console "`npm run check`" and then the browser reloads the page and I cannot use more the app because of the below errors (I'm using CSP):

```shell
Refused to connect to 'ws://localhost:4000/' because it violates the following Content Security Policy directive: "default-src [URL] Note that 'connect-src' was not explicitly set, so 'default-src' is used as a fallback.
```

In my `svelte.config.js` I have this:

```
js
import adapter from "@sveltejs/adapter-static";
import { vitePreprocess } from "@sveltejs/kit/vite";
import "dotenv/config";

... [Log Snipped] ...

export default config;
```

I think `npm run check` is restarting the app without `process.env.NODE_ENV === 'development'`.

My `npm run check` is: `"check": "svelte-kit sync && svelte-check --tsconfig ./tsconfig.json"`.

**Is there a way to disable CSP during development?**

Discussion
- Ah, I see what's happening here.

When you run `pnpm dev` or `pnpm build`, various files are generated, including `.svelte-kit/generated/server-internal.js` which contains this:

```js
export const options = {
  csp: {...} // the CSP options specified in your svelte.config.js
```

The dev server reads the contents of that file and configures the page headers accordingly.

When you run `npm run check` (or just `npx svelte-kit sync`, since `svelte-check` isn't part of the problem) that file is regenerated, except this time `process.env.NODE_DEV` is not `development`. So the generated file includes the production CSP config.

(This didn't happen in older versions, where `options` wasn't written out to a module but was generated in memory for each new request — the new approach is simpler and has certain advantages, but it means we're uncovering these fun edge cases.)

I suspect the solution is for `svelte-kit sync` (the CLI, not the internal API) to only write out the files that are necessary for typechecking to be successful, since that's what it's designed for.
- I can confirm [URL] fixes this.
