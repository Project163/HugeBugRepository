Title

Controller action "cell" should be allowed

Description
And

With an ArticlesController:

```
/**
 * Controller action for testing cells.
 *
 * @return void
 */
... [Log Snipped] ...
    $this->set(compact('foo', 'bar'));
}
```

I think the cell trait should have a less conflicting method name so that the action name "cell" itself is not reserved and can be used in user land.
Or does the controller even need the CellTrait? I understand that the view needs it, but controllers itself should not necessarily have to.

In general the new traits in 3.0 make the controllers inherit quite a few "method names" that will most likely conflict with user land action names and might have to be documented (reserved non-usable action names so to speak). E.g. `log` via LogTrait, `set` via ViewVarsTrait.
IMHO some of those methods could just be protected to avoid this issue. 
The only ones that need to be public are the ones called from outside - usually via dispatching.
Logging and setting don't sound much like they fit into this. They would be called from inside the controller - thus in a scope accessible via protected methods.
`set` will probably have to stay public as it could be invoked from helpers setting data to the View class. But the others not so much.

On top of that some of the other controller methods like "render()", "paginate()", ... could also be protected. Way too many of them are exposed without the need to do so probably and also might conflict with action names.

Finally, the same can be said about the Shell class (or any other dispatching invoked class in CakePHP) which also has way too many exposed methods. All IO operations as well as most other methods could also be protected here, e.g. `$this->_in()`, `$this->_createFile()` etc.
Discussion
- The `log()` and `set()` methods are not _new_. They have both been around since pre 1.x days.  Making `render()` protected could break userland components.

While I agree that many of the methods could be protected, they have historically been public. I'm not sure switching them really has much benefit to the end developer. Changing them does create more code they have to churn if/when applications upgrade to 3.0
- @markstory I think we should prefer to not add more reserved action names, so +1 to not making cell a reserved word.

Using an underscore might be better, though I think that breaks some PSR. So I have no suggestions for a fix :(

- @markstory You don't get that exception. You get the E_STRICT errors mentioned above + `Private Method in ArticlesController` exception. At least for "log" and "cell" and all non-action public methods declared in the controller.
- Just a word of caution. With the increasing usage of traits we're going to have more and more method name conflict problems. Not only that, but code is harder to read and understand, it's happenning now to me with CakePHP3. Using object composition instead of traits would encapsulate functionality inside objects and less conflicts would happen. Code readability would be improved too since we're forced to split functionality in objects. Traits can be great for protopying, but I think they're not so beneficial in a framework. Composition over inheritance is a good design principle, traits are like multiple inheritance and can be easily abused.
