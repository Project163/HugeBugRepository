**Steps to reproduce or a small repository showing the problem:**

MySQL version: 5.7
Typescript version: 3.0.1

Everytime schema:sync is called, typeorm drops all fk and re-create them. It also performs alter table change column to timestamp columns. The problem is when findChangedColumns is called.
[Link: Line]

```ts
console.log("width:", tableColumn.width, columnMetadata.width);
console.log("precision:", tableColumn.precision, columnMetadata.precision);
```

output:

for fk:
```ts
width: 10 undefined
```

for timestamp:
```ts
precision: 0 null
```

Example entity:

```
ts
@Entity('assignments')
export class Assignment {

  @PrimaryGeneratedColumn({unsigned: true})
... [Log Snipped] ...
  @Column({precision: null, type: 'timestamp', default: () => null, nullable: true})
  to: Date;
```
Discussion
- It my case the comparison of default values fails because of case difference. The `MysqlDriver#compareDefaultValues` ends up comparing the following values:

```javascript
"CURRENT_TIMESTAMP(6)" === "current_timestamp(6)"
```

Running:

- `typeorm@0.2.19` (`@latest`)
- `mariadb  5.5.5-10.3.13-MariaDB-1:10.3.13+maria~bionic mariadb.org binary distribution`
   docker image: `mariadb:10`
   sha256: ` `) 
   command: `['mysqld', '--character-set-server=utf8mb4', '--collation-server=utf8mb4_unicode_ci']`

I've also tested this on `mariadb:latest`.

Notice the case difference of the default value in `mysql` CLI utility when executing `CREATE TABLE` and `SHOW CREATE TABLE`:

```
mysql
mysql> CREATE TABLE test(created_at TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6));
Query OK, 0 rows affected (0.02 sec)

mysql> SHOW CREATE TABLE test;
... [Log Snipped] ...
+-------+------------------------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set (0.01 sec)
```

The `MysqlDriver#mappedDataTypes.createDateDefault` and `MysqlDriver#mappedDataTypes.updateDateDefault` are both set to `CURRENT_TIMESTAMP(6)`.

I'm not sure if all versions of MariaDB and/or MySQL behave the same, but I guess the comparison here should be case-insensitive.

---
### Update 

I tried to test this on `mysql:latest`, and it looks like the issue here is non-existent:

```
mysql
Server version: 8.0.17 MySQL Community Server - GPL

mysql> create database test;
Query OK, 1 row affected (0.02 sec)
... [Log Snipped] ...
+-------+------------------------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set (0.00 sec)
```

**Edit** A workaround seems to be to explicitly set the default values of `createDate` and `updateDate` columns to `current_timestamp(6)`, but then it gets tricky to use the same base entity config with different databases.

### Update 2

The unique column indices also get recreated. This is because the following check fails at:

[URL]

```
dbIndex["NON_UNIQUE"] === "0"
```

The value of `dbIndex["NON_UNIQUE"]` on MariaDB is `0`, but the type is `Number` so this check fails.

**Edit** I just realized this has been happening because the type of `NON_UNIQUE` column in `INFORMATION.SCHEMA` is `BIGINT(1)`, and I had the `bigNumberStrings` option explicitly set to `false`.

### Update 3

I've created a patch for my problem with create date in Mariadb. During that process I've realized that the issue I've described above is not related to the initial issue. I will be opening a new issue  and create a pull request linking to that issue.
