Title

Tablet stuck without a leader after one replica was tombstoned and another was removed

Description
Observed a scenario similar to the following. Suppose a certain tablet had three replicas, A, B, and C.
- C gets tombstoned but is still in the Raft configuration
- A (the leader) receives a request to remove B from the quorum, appends it to its log, and crashes

Now the tablet is stuck without a leader, because:
- A has a pending config that only includes A and C, so it won't send its vote request to B when its starts an election, and C can't vote for it because the tablet is tombstoned on that replica.
- B sends its vote requests to A, B, and C, but C won't vote for it (it is tombstoned), and A won't vote for it because it has a more up-to-date log.
Discussion
- Few observations:
- Replica C gets tombstones the tablet incorrectly after a remote bootstrap (RBS) which was fine otherwise.
- The RBS does go ahead and issue a CHANGE_ROLE, but replica C does not get to process that consensus update.
- So other replicas A & B believe C is part of the quorum as a VOTER, as they do apply the CHANGE_ROLE.

The ideal case (as was before) is to keep C in the quorum even if it does not apply the CHANGE_ROLE immediately after an otherwise successful RBS. That way it would eventually apply the change role, become a voter and help A win the election...

 @hectorgcr is digging into the resolution to revert a possible regression and fix it up.
