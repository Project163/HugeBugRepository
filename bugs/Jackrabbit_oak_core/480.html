Title

Query with descendent node and access control fails to return result

Description
The scenario is bit complex. Running a query with following condition does not give any result 

 
	 Node path is like  /home/users/geometrixx-outdoors/emily.andrews@mailinator.com/social/relationships/following/aaron.mcdonald@mailinator.com  
	 It has a Glob jcr:read for everyone at  */social/relationships/following/*  
	 The query is like
  /jcr:root/home//social/relationships/following//* [id='aaron.mcdonald@mailinator.com']    
	 The query is executed with anonymous session 
 

 On JR2 it returns expected result while on Oak it does not give any result
Discussion
- Testcase which demonstrates the issue. The testcase passes on JR2 and fails with Oak 

 Couple of notes 
 
	 The testcase would pass if admin session is used 
	 The GlobPattern passes while query result is fetched for the test path but then somehow the Query restriction fails
- this is the sql2 query: 
  
 select d.[jcr:path] as [jcr:path], d.[jcr:score] as [jcr:score], d.* from [nt:base] as a 
 inner  join [nt:base] as b on ischildnode(b, a) 
 inner  join [nt:base] as c on ischildnode(c, b) 
 inner  join [nt:base] as d on isdescendantnode(d, c) 
where 
name(a) =  'social'  and 
isdescendantnode(a,  '/home' ) and 
name(b) =  'relationships'  and 
name(c) =  'following'  and 
d.[id/*] =  'aaron.mcdonald@mailinator.com'  
 
  

  The GlobPattern passes while query result is fetched for the test path but then somehow the Query restriction fails  

 let's dig deeper into this a bit: 
checking with the anonymous session, it doesn't seem like you can read _ /home/users/geometrixx-outdoors/emily.andrews@mailinator.com/social/relationships/following_,  /home/users/geometrixx-outdoors/emily.andrews@mailinator.com/social/relationships ,  /home/users/geometrixx-outdoors/emily.andrews@mailinator.com/social  
but you can read  /home/users/geometrixx-outdoors/emily.andrews@mailinator.com/social/relationships/following/aaron.mcdonald@mailinator.com  

 the way this is supposed to work is the 'a' selector should be able to read the 'social' node, allowing the other selectors to read the next level and so on, drilling down to the 4th level where the 'id' condition is checked. this fails at the  Tree tree = getTree(currentRow.getPath()); if (tree == null || !tree.exists()) {  part when the selector doesn't have enough read rights. 

 what you notice debugging is in fact the 'a' selector reading the  /home/users/geometrixx-outdoors/emily.andrews@mailinator.com/social/relationships/following/aaron.mcdonald@mailinator.com  row, but unfortunately the query engine will check the 4th level deep child node for the 'id' property which will effectively fail. 

 there was a security related issue filed against JR that showed you could use joins to guess the content structure that you can't see (don't have read access to), so I guess this issue falls under the same category now (thanks to the automatic xpath to sql2 transformation).
