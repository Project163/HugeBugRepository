Title

Avoid specialized assert formatting when we detect that `__eq__` is overridden

Description
The issue reported for introspecting numpy arrays #5347, is still present for dataclasses when invoking `assertrepr_compare`.

When testing:

```
python
from dataclasses import dataclass
import numpy as np


... [Log Snipped] ...
def test_fails():
    assert A(np.array([1,2])) == A(np.array([2,1]))
```

Instead of an "Drill down" explanation you get:

```
   def test_fails():
E       assert A(a=array([1, 2])) == A(a=array([2, 1]))
E         (pytest_assertion plugin: representation of details failed: .../_pytest/assertion/util.py:430: ValueError: The truth value of an array with more than one element is ambiguous. Use a.any() or a.all().
E          Probably an object has a faulty __repr__.)

```
(Ubuntu 21.10, pytest 6.25, python 3.9)

One way to solve it: since pytest only sees difference on `repr` perhaps instead of comparing `arr1 == arr2` when determining if the fields are different, perhaps it should consider whether `repr(arr1) == repr(arr2)` which sidesteps the issue with array not returning bool for comparison.

Instead of

one could do
```python
    for field in fields_to_check:
        if repr(getattr(left, field)) == repr(getattr(right, field)):
            same.append(field)
        else:

```
If the `__repr__`s are the same and the object are not the same (or vice versa), then the explanation shown by pytest will regardless be misleading.
Discussion
- probably the more correct solution here is to avoid pytest's specialized assert formatting when it detects that `__eq__` is overridden (since it's not going to accurately represent the underlying equality comparins)
- it might also not be a bad idea for pytest to check if its numpy and use the numpy equals there as we do check numpy in a number of places - im under the impression a lot of the numpy handling should get a own plugin module by now

        left = SimpleDataObject(np.array([1, 2]))

Apart from checking if the `dataclass` or the `attrs.define` decorated class  (`attr.s` seems to ignore the customdefined `__eq__`) has a custom `__eq__` method, should we also consider handling attributes which raise an exception during there comparison, something like:
```python
E       AssertionError: assert SimpleDataObject(a=array([2, 1])) == SimpleDataObject(a=array([1, 2]))
E         Attributes which raised an exception:
E         ['a']
```

Or maybe just handle places where the `__eq__` method is overridden for this issue?
- JFTR attr.s doesn’t ignore a custom eq if auto_detect=True. In attr.define it’s on by default.
