Title

Enum machinery uses repeated enum values (aliases)

Description
**Describe the bug**
We had a legacy enum with names that have spaces so we added some aliases to make coding easier.
Notice the aliases have repeated values so they [Link: will not create enum elements].

E.g:
```
Names = enum.Enum(
    value='Names',
    names=[
        ('Name A', 1), ('a', 1),
        ('Name B', 2), ('b', 2),
        ('Name C', 3), ('c', 3),
    ]
)
```

So when you `list(Names)`, you only see the 3 original enum names and : `Names["Name A"] is Names.a` meaning that `a` is just an alias and points to the same object.

When you pass this to `name = Column(Enum(Names))`, it will create the 6 names on the column because 
`sqlalchemy.Enum._parse_into_values` is using the `__members__` atribute from enum which shows everything, including aliases.


SQL output for that column:
``` `name` ENUM('Name A','Name B','Name C','a','b','c') NOT NULL, ```


**Expected behavior**
``` `name` ENUM('Name A','Name B','Name C') NOT NULL, ```

I propose to use  `[e.name for e in enum_class]`
instead of `enum_class.__members__`
[URL]

**Versions.**
 - OS: MacOS
 - Python: 3.8
 - SQLAlchemy: 1.3.23
 - Database: MySQL
 - DBAPI: pymysql
Discussion
- pep-435 is ambiguous about iterating over enums, with just the phrase "Within an enumeration, the values can be compared by identity, and the enumeration itself can be iterated over." being all it has.  It does however fully define `__members__` and that's also [Link: what we document] as well as use in tests.

So it has to keep using `__members__` but it can just use a `set()` to check for dupes.
- If you intend to keep using `__members__`, the docs define how to get aliases here:
[URL]

So you can replace `!=` with `==` to get the actual enum names:

```[name for name, member in Shape.__members__.items() if member.name == name]```


EDIT: Now I see, you need to be compatible with pep-435 that can allow anything, so yes, you need to use a set
EDIT 2: No, enums must have `.name`, so you can use that and also a set might pick an alias instead of the original name (Python < 3.6, I guess). Specially because pep-435 uses that same line to define how to find aliases

- I think you could show a warning if the enum has aliases and the user didn't pick the flag value.

But i don't believe someone would want aliases stored. Because you will fragment the data. If they want to rename the enum value stored, they can do a migration
- that's not as easy as it should be. For example, when using postgresql native enums, there is no way of removing enum values, you can only add them to an enum type.

So sadly I think it we will need to keep this flag for the foreseeable future. But yes, I think we will have a warning shown if the enum has aliases and the flag is not specified. Probably the flag will be initially off, and we could probably toggle it to on in v2
