Title

Property2Index: node type is used when indexing, but ignored when querying

Description
The Property2Index filters by node type, so each index only contains data for a list of node types. 

 But the getCost and and query methods ignore the node type. 

 Because of that, if there are multiple indexes for the same property, each index filtering on certain node types, then running a query might pick the wrong index. 

 The result is that the query doesn't return any data where it should, because the index doesn't return the right nodes.
Discussion
- this might go along with the lack of proper node type resolution with the node type aware 
index definitions: according to alexP that restriction will currently only work if the 
'exact' node type names are specified (super types will not work). since the evaluation 
needs to be aware of super types it might be worth addressing that as well in the definition 
setup.

- The workaround disabled the second index on rep:principalName, so queries that filter on rep:principalName don't use it. 

 Please note the "reproducability" of this bug depends on the order of child nodes in the MicroKernel. So you might not be able to reproduce it when using the MicroKernelImpl, but only with the MongoMK (for example).
- good find! 

 my tests did not cover this scenario at all really: having 2 indexes on the same property but with different node types. 

 I've seen both indexing and query time problems: as mentioned it all could work or fail based on which index node came up first.
