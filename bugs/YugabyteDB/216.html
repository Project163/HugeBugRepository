Title

[YSQL] Server crashes when setting GFLAGS "ysql_prefetch_limit" to small number

Description
To reproduce:
- Start server with small setting for prefetch limit.  For example, ``` yb-ctl start --tserver_flags="ysql_prefetch_limit=2" ```
- Run ysqlsh command.

Crash happens right away.

It appears that the prefetch limit must be at least equal to the number of tablet-servers to avoid the crash.
```
ysql_prefetch_limit >= "number of tablet servers"
```
Discussion
- Another set of steps to recreate the issue -

1. `./bin/yb-ctl --replication_factor 3 create --tserver_flags "yb_num_shards_per_tserver=2,leader_failure_max_missed_heartbeat_periods=60,ysql_prefetch_limit=4"`

2. In `./bin/ysqlsh` - 
    `create table tab(h int, ri int, rt text, rd double precision, v text, primary key(h, ri, rt, rd));`


Note: different errors on `ysql_prefetch_limit` = `2 | 4 | 6 | 8`
- Recording some offline conversations here (to help debugging):

Per @m-iancu,
It’s a table with a nested index request — We have this optimization for system tables to do the table and index lookup in one request (since they are guaranteed to both be in one tablet — the master tablet).
In that case, if we need to do paging, we need to make sure whether we need the main table or index row key.
- This error occurs when selecting from large system table that has secondary index.
- For this select statement, YugaByte send nested queries to DocDB (storage layer), when the result set is larger than prefetch-limit, DocDB sent back a paging state for the subsequent fetches.
- The returned paging state is for the innermost query (the last operation node), but it is kept in the outermost query / node, and that causes a crash.
