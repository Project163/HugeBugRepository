Title

3.x - `Dispatcher.afterDispatch` event not being invoked on error

Description
This is a (multiple allowed):
- [x] bug
- [ ] enhancement
- [ ] feature-discussion (RFC)
- CakePHP Version: 3.3.3

refs #8667

---

With the introduction of the `ActionDispatcher`, dispatcher filters are not going to receive the `Dispatcher.afterDispatch` event anymore in case an error occurs in the application.

While `ExceptionRenderer::_shutdown()` does dispatch the event, the `Dispatcher` has been changed so that filters are only being registered as listeners anymore inside of the `ActionDispatcher` object, ie when `Dispatcher::dispatch()` is being invoked.

```
php
public function testAfterDispatchOnError()
{
    $filter = $this
        ->getMockBuilder('Cake\Routing\DispatcherFilter')

    \Cake\Routing\DispatcherFactory::clear();
}
```
Discussion
- I'm not sure the ExceptionRenderer should be triggering the event. Perhaps the ErrorHanderMiddleware should do that?
- For applications that are using the new middleware stack that would probably be a good place.

But as long as the stack isn't mandatory and dispatcher filters are only deprecated, backwards compatibility would be nice to have, ie the exception renderer will probably have to be kept involved in one way or another for the time being.

- Correct, the problem isn't that the exception renderer wouldn't  dispatch the event anymore, it still is doing that, the problem is that the filters/listeners do not get subscribed until `Dispatcher::dispatch()` is being invoked, which the exception render will of course not do.

Previously the filters/listeners have been registered in `Dispatcher::addFilter()`, so whenever an instance of `Dispatcher` has been created via `DispatcherFactory::create()`, the filters where subscribed as listeners, since the factory adds all the statically registered filters:
- [URL]
- [URL]

So dispatching the event on `$dispatcher` in the exception renderer invoked the filters/listeners properly.

With the action dispatcher introduced, `Dispatcher::addFilter()` does not subscribe the filters/listeners anymore, instead they are being subscribed in `ActionDispatcher::addFilter()`, and while the `ActionDispatcher` instance used by the `Dispatcher` class gets the `Dispatcher` instances event manager passed to it to subscribe the filters on, all this only happens when `Dispatcher::dispatch()` is being invoked.
