- I'm not convinced that this fully addresses the problem. I agree with your analysis and the essence of your fix but I believe there's another case which can cause these timeouts and in fact I'm still seeing intermittent failures with your patch applied, though less often. 

 What I think is sometimes happening in the test is that one node issues a request to another which is already shutting down. This request cannot be served but the issuer will wait on it for up to  cms_await_timeout  (current default is 120s). 
I've pushed a branch  here  which adds a tracker for the inflight futures, so we can cancel them all directly when closing. I would expect there to never be more than a handful of requests active at any time (these are debounced after all) but for safety, the tracker is bounded in size and automatically expires entries.
