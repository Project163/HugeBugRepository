Title

Crash when curl is used from inside an OpenSSL engine

Description
Hi!
The yubihsm-pkcs11 module internally uses the curl library, which on initialization calls CONF_modules_load_file to disable errors on missing config files (I presume). When yubihsm-pkcs11 is used by the openssl command through libengine-pkcs11-openssl on Ubuntu Focal or Groovy there is a crash in int_ctx_new (crypto/evp/pmeth_lib.c:171). This seems to happen because CONF_modules_load_file seems to be called twice in this case, once implicitly from openssl library initialization, and then again later when the pkcs11 engine initializes yubihsm-pkcs11, which calls curl_global_init, which in turn calls CONF_modules_load_file. Both calls use NULL as the config file name so they end up loading the default config file twice, and some debugging revealed that the EVP_PKEY_METHOD it finds contains an invalid function pointer in pmeth->init. It might be the fact that the pkcs11 engine gets loaded twice, but the second time it gets rejected because it is already registered with the same id, and subsequently freed. Maybe this freeing messes up some common state also used by the existing pkcs11 engine.

The command i use is

YUBIHSM_PKCS11_CONF=yubihsm_pkcs11.conf OPENSSL_CONF=engine.cnf openssl dgst -engine pkcs11 -keyform engine -sha256 -sign -label_xxx

I explicitly point to the following config file 'engine.cnf'

...
openssl_conf = openssl_init

[openssl_init]
engines = engines_section

[engines_section]
pkcs11 = pkcs11_section

[pkcs11_section]
engine_id = pkcs11
dynamic_path = /usr/lib/x86_64-linux-gnu/engines-1.1/pkcs11.so
MODULE_PATH = /usr/local/lib/pkcs11/yubihsm_pkcs11.so
PIN = 0001password
init = 0
...

And yubihsm_pkcs11.conf:

...
connector=[URL]
...

The line number comes from an openssl built with --debug from github branch OpenSSL_1_1_1-stable and installed to the default location /usr/local/lib (where it will be used by default).

Discussion
- I think the solution to this is for curl to call OPENSSL_init_ssl with an OPENSSL_INIT_SETTINGS that specifies the same flags to not error on missing config files that it now uses in the call to CONF_modules_load_file. The documentation and historical functionality of CONF_module_load_file seem to indicate it should work, but it clearly doesn't. I'm thinking the intent of the call is to avoid having applications using curl failing unexpectedly, but the current flags will still fail on errors in files it does find, so that goal is perhaps not fully achieved anyway... My proposed change shouldn't change that functionality, hopefully.
- I have tested a modified version of curl that has the CONF_module_load replaced with OPENSSL_init_ssl with the same flags (to allow a missing config file) and that makes it work. So I think curl should use the 'modern' apis if openssl version is >= 1.1. I'll provide a PR.
