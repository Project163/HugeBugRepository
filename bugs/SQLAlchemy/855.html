Discussion
- hey there, and thanks for the clear issue report.

There's a lot to say on this as there are many different behaviors intersecting here.

Regarding the column defaults, those are not consulted by the ORM, so whether or not you apply a column default, the value of the deleted_when attribute at the Python level will return None until the object is persisted.   This None is not part of the object's state, however, and in fact the whole idea of "None" magically appearing will be going away in SQLAlchemy 2 and it will instead raise an AttributeError like normal Python does, that's #4519.   The column-level defaults are part of the object's persistent state, so if the object you have is not persistent, as is the case here where the object is transient, you should not expect the persistence defaults to be present.   (see [Link: here] for these terms).

if you do want to explicitly set column level defaults  when you instantiate an object, there's an example that illustrates how to use the attribute-level default behavior event to do this [Link: here].       so for the thing you said "should" happen, you can use this recipe.

I also noticed you have a funny situation going on with that comparison, where you will get the warning:

```

/home/classic/dev/sqlalchemy/lib/sqlalchemy/orm/relationships.py:1504: SAWarning: Got None for value of column a.deleted_when; this is unsupported for a relationship comparison and will not currently produce an IS comparison (but may in a fu
...[Text Truncated]...
ink re-applying this "None" as meaningful is not the right direction to go.    Especially given that you've been assuming this is the column-level default generator you're seeing.  It means if your default generator returned a non-None value, and then a transient object were used in the comparison, it would again do the wrong thing.  

so three takeaways:

1. the column level defaults don't apply to transient objects unless you add events to do that

2. the change in question is so that the ORM isn't making possibly broken assumptions about objects

3. the longer term plan is to make even fewer assumptions about un-set attributes

My main suggestion would be to not be using transient objects in comparisons like this, in fact, because semantically they don't make sense.  ORM instances are not value objects, they are proxies for a database row, so the transient object doesn't actually have meaning when used in a database context.
