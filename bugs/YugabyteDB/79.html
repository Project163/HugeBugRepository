Title

Write operation should check if NoOp is committed

Description
**Original description:**
After a Raft leader election, a new leader appends a NoOp and commits it, thus committing all previous records. Currently, we wait until we commit the NoOp before declaring the leader ready. However, we should also wait until all existing entries in the leader's log are also applied as far as MvccManager is concerned.

**Update:**
Actually, leader NoOp is marked as committed inside `RaftConsensus::NonTxRoundReplicationFinished` which is invoked as `ConsensusRound::replicated_cb_` from `ConsensusRound::NotifyReplicationFinished`, which is called from `ApplyPendingOperationsUnlocked` after operations are applied. So, operations from previous leader are always applied before NoOp is commited.

Though, we have another related inconsistency bug. In `TabletServiceImpl::Read` we call `GetTabletOrRespond` which invokes a `CheckPeerIsLeader`. `CheckPeerIsLeader` makes sure that NoOp is committed.
But in `TabletServiceImpl::Write` we don't call `CheckPeerIsLeader` and don't have any checks that NoOp is committed. This causes inconsistency when handling read-modify-write because it can read stale data and decide to overwrite new value based on the old one.
For example, consider the following example scenario with operations on the same key of the two-column table :

- n1 is a leader and receives set val=10000, which is replicated to n2, n3
- n1 receives set val=10002 and sends Consensus Update RPC to n2 and n3, but Update RPC processing is delayed due to some reasons.
- n1 is killed due to some reason.
- n2,n3 detect leader fail and n2 is elected as a new leader.
- n2 appends 10002 to RAFT log, but not yet applied stuck at the beginning of `RaftConsensus::UpdateMajorityReplicated`.
- n2 receives set val=10001 if val=10000, didn't check that NoOp is not yet committed, reads old value 10000 from DocDB and put 10001 to RAFT log.
