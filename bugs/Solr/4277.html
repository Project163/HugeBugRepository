Title

Admin UI/ZK Status page: Zookeeper 3.5 : 4lw.commands.whitellist error

Description
After upgrading to Solr 8.2 and Zookeeper 3.5.5 one sees the following error in the Admin UI / Cloud / ZkStatus:  

  *"Errors: - membership: Check 4lw.commands.whitelist setting in zookeeper  
  configuration file."*  

  Aside of the UI, the Solr Cloud nodes seem to work perfectly normal.  

  This issue only occurs with ZooKeeper ensembles. It does not appear if one Zookeeper standalone instance is used.  

  We tried the 4lw.commands.whitelist with wildcard * and "mntr,conf,ruok" (with and without spaces).
Discussion
- Ok, I reproduced it here. Apparently 3.5.5 has some new format of the response in `conf` 4lw command, e.g.: 
  
 clientPort=2181
secureClientPort=-1
dataDir=/data/version-2
dataDirSize=201326640
dataLogDir=/datalog/version-2
dataLogSize=582
tickTime=2000
maxClientCnxns=60
minSessionTimeout=4000
maxSessionTimeout=40000
serverId=1
initLimit=5
syncLimit=2
electionAlg=3
electionPort=3888
quorumPort=2888
peerType=0
membership: 
server.1=zoo1:2888:3888:participant; :2181
server.2=zoo2:2888:3888:participant; :2181
server.3=zoo3:2888:3888:participant; :2181
version=0Connection closed by foreign host.
 
  
 Obviously the parsing logic expects strictly  key=value  for each line, but there is a line here that is only  membership:  which I believe causes some parsing error in  ZookeeperStatusHandler
- I think I would call this a bug in ZK.  But since getting a fix from them could take a long time, we need to tackle this in Solr. 

 There are probably two ways to handle this.  1) Look for the = separator, and if not found, use the : separator.  2) Treat the conf output as a .properties file and let Java parse it for us. 

 I'm attaching a patch that takes the first approach.
