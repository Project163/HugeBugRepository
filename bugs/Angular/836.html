- @StephenFluin have you looked into the issue at all and could maybe provide your findings? If not, no big deal(: would save me some legwork
- Initial findings are that the CLI will first kickof ngcc with `"browser", "module", "main"`, resulting in the ES5 sources being analyzed and because it is the first request, will also update the `.d.ts` files.

That is all fine, however the ES5 analysis ends up completely empty. I found using `ts.Program.getSourceFiles().map(sf => sf.fileName).filter(n => n.endsWith('.js'))` that the program's sources only included the entry point's `index.js`, its import to `./public_api` was not within the list.

So, what is going on? Some more debugging let me to the root problem here: the typing files and JS source files are all located in the same directory. Hence, when TypeScript resolves `./public_api` its module resolution system will end up with `./public_api.d.ts`! Hence, the actually interesting source files that ngcc needs to process never become part of the analysis program; causing ngcc to conclude there's nothing to update in the source nor in the typings but the package is marked as being processed regardless (which is correct).

We'll probably need some way of customizing TypeScript's module resolution system here, such that it prefers '.js' files over '.d.ts'.
