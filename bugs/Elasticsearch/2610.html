Title

Wrong forced shard allocation setting crashing the cluster

Description
**Elasticsearch version** (`bin/elasticsearch --version`):
Version: 7.8.1, Build: default/tar/ /2020-07-21T16:40:44.668009Z, JVM: 14.0.1 (and others)

**Plugins installed**: []
None

**JVM version** (`java -version`):
JVM[AdoptOpenJDK/OpenJDK 64-Bit Server VM/14.0.1/14.0.1+7]

**OS version** (`uname -a` if on a Unix-like system):
Linux server1 4.4.0-1117-aws #131-Ubuntu SMP Tue Oct 6 20:45:33 UTC 2020 x86_64 x86_64 x86_64 GNU/Linux

**Description of the problem including expected versus actual behavior**:
A wrong forced shard allocation awareness setting crashes Elasticsearch, dropping nodes from the cluster and making it no longer possible for them to re-join.

A student by mistake used an underscore (following the attribute name) instead of a dot when configuring forced shard allocation awareness (see [URL] The bogus setting did not get rejected and brought the cluster state in a non-working configuration. Any bogus setting results in the same behavior.

Expected behavior: A bogus / mal-formatted setting should get rejected.

**Steps to reproduce**:
 1. Start up a cluster
 2. Execute 
```
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.awareness.force.nonsense": ""
  }
}
```

- By design the force setting takes arbitrary key/values, similar to node attributes. @DaveCTurner Can you elaborate on why you think this is a settings infrastructure issue?
- Maybe I'm confused by the meaning of a `groupSetting` but my understanding was that calling `getAsGroups` here is legitimate assuming the setting is valid as a group setting.
