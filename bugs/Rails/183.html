Title

String#parameterize raises Encoding::CompatibilityError for non-Unicode Strings on master

Description
### Steps to reproduce

Run this script [URL] The tests with `non_unicode_string` will raise the exception.

Run [URL] to verify it works on 5.2.

### Expected behavior

Before Rails 6, `String#parameterize` and the underlying methods it calls supported non-Unicode strings. Maybe they still should in Rails 6?

### Actual behavior

`String#parameterize` and the underlying methods it calls no longer support non-Unicode strings. They now raise `Encoding::CompatibilityError`s.

It looks like the change in behavior was introduced in [URL] `String#parameterize` eventually calls `ActiveSupport::Unicode::Multibyte#normalize`. `#normalize` [Link: used to do a bunch of stuff] and now it's [Link: mostly a wrapper around the native Ruby method].

### System configuration
**Rails version**: master

**Ruby version**: 2.5.0p0

Discussion
- Good find. Yes, I think we should maintain the behavior. Maybe we can change the encode to utf8 and pass a utf8 string to the Ruby API?

@mtsmfm can you investigate?
- I found the previous implementation of `ActiveSupport::Unicode::Multibyte#normalize` doesn't work well with non-unicode strings.

```ruby
# Fullwidth Latin Capital Letter A in Windows 31J
str = "\u{ff21}".encode(Encoding::Windows_31J)
result = ActiveSupport::Multibyte::Unicode.normalize(str)
# This `result` should A ("\u{41}") but got another char, 艠 ("\u{8260}")
puts result # => 艠
p result.codepoints # => [33376]
```


The above example shows unwanted and unexpected result.
So I think current behavior with non-unicode string is not defined.
If so, I think it's ok to raise an error if given string is non-unicode one.
I'll add a test to clarify the behavior.

@rafaelfranca What do you think?
- Looks like this issue slipped through.

@rafaelfranca I agree with @mtsmfm.
