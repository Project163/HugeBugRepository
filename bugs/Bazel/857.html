Title

--experimental_windows_watchfs fails when --symlink_prefix is specified

Description
### Description of the problem / feature request:

Settings `--symlink_prefix=.build/` and `--experimental_windows_watchfs` together cause infinite symlink loop.

### Bugs: what's the simplest, easiest way to reproduce this bug?

Bazel user guide recommends setting `--symlink_prefix=.bazel/` to reduce clutter and that is what we do. With the arrival of Bazel 3.3.0 we tried new setting `common --experimental_windows_watchfs` in .bazelrc file and as the result we observe this in the build output: ```WARNING: Error encountered with local file system watcher java.nio.file.FileSystemException: D:\dev\bazel\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build\product_root\.build: The name of the file cannot be resolved by the system.
... temporarily falling back to manually checking files for changes```

Apparently this is caused by the folder `.build` (specified by --symlink_prefix) where Bazel creates symlink `product_root` (root of the workspace). This somehow confuses file system watcher on Windows. 

### What operating system are you running Bazel on?

Windows 10 1806.

### What's the output of `bazel info release`?

3.3.0
