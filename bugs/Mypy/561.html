Title

Inner class not recognised

Description
Consider this snippet:

```
python
from typing import *

class A:
    class B:
... [Log Snipped] ...
    def f() -> None:
        x = []  # type: List[B]
```

mypy outputs:

```
In function "f":
line 8: Name 'B' is not defined
```
Discussion
- Thanks for reporting this!

This is probably the same issue as #307, but I'll keep this separate for now.
- Actually, this is a different issue from #307. Referring to `B` within a method body is normally not possible without using `self.X` or `A.B`, and thus disallowing it in type annotations is consistent. For example, this would fail:

```
python
from typing import *

class A:
    class B:
... [Log Snipped] ...
    def f() -> None:
        x = List[Link: B]   # B not bound in this scope
```

`A.B` is currently supported by mypy, but `self.B` is not recognized as a valid type. Maybe `self.B` should be a valid type in the above example? However, `self.B` is a different type from `A.B`, since a subclass of `A` could override `B`, but the type system can't represent this distinction. Oh well.
- ... [Middle Discussions Snipped for Brevity] ...
- I don't understand this issue, The inner class is recognized when accessed using `A.B` as it should be. If the discussion is about `self.B` (which to me sounds like requiring Scala-style path-dependent type system) then the title of the issue and the example are unrelated.
- Looking at the original example, I think PEP 484 is not completely clear about the scope in which type comments like `# type: List[B]` are looked up; for type annotations in argument declarations the scope might be different than for variable declarations in the body.

However PEP 526 provides an alternate syntax that requires the type to be evaluatable:
```python
class A:
    class B:
        pass

    def f() -> None:
        x: List[B] = []
```
Here B is clearly inaccessible (because of Python's inscrutable scope rules for method bodies, which intentionally skip the containing class's scope) so I think we should use the same rule for type comments.

Closing; agreed that the discussion about subclasses of A overriding B belongs somewhere else.
