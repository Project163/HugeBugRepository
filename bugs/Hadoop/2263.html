Title

FairCallQueue may defer servicing calls

Description
HADOOP-14033   switched a lock to a semaphore to allow concurrency for producers & consumers to the underlying queues.  A race condition was created that may cause a consumer to acquire a permit but not extract an element, leaving the semaphore with fewer permits than queued elements.  This causes a minimum number of calls to always be present in the call queue.
Discussion
- In practice the impact isn't severe.  The next call will dislodge one of the "stuck" queued calls.  Latency is affected to some degree, but is skewed towards increased latency for lower priority buckets.  Across multiple production clusters, the number of lost permits is usually low single digit.
- Very simple patch to ensure an element is always extracted after a permit is obtained.  Basically change an if to while.  Attempting to reproduce the race with a test has proven futile (or it wouldn't have vexed me this long).  The issue has only been observed at scale.
