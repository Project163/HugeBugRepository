Title

When a field has multiple types, and one includes time_series_metric, then original_types is broken

Description
When multiple indexes with the same field name have different types on those fields, and ES|QL is used to query multiple indexes, ES|QL will return those fields as type `unsupported` with all values set to `null`. Kibana likes to keep clean tables, so it sends `drop_null_columns` along with the query. This removes the entire column of nulls. Users get confused. To help reduce confusion, ES|QL returns an extra header called `all_columns` which includes the missing column, and also lists the `original_types` for the column switched to `unsupported` so that Kibana can explain to the users why that column has `null` values.

If `drop_null_columns` is not sent, the original columns will have the unsupported type, but will also include the `original_types` field:

```
{
      "name": "metric.value",
      "type": "unsupported",
      "original_types": [
        "double",
... [Log Snipped] ...
      "suggested_cast": "keyword"
    }
```

Whether `drop_null_columns` is used or not, this `original_types` information is useful for users to make sense of what is going on. In Kibana, there are warning icons with additional information provided:

 

However, when the indexes in question have `index.mode:time_series` and one of the field mappings includes `time_series_metric`, then the `original_types` is not provided, and Kibana cannot help the users, leading to much confusion on the part of the user. In Kibana there are no warnings on the fields:

 

### Reproduction

```
PUT /metrics-counter
{
 "settings": {
   "index.mode": "time_series",
   "index.routing_path": [ "metric.name" ]
... [Log Snipped] ...
    "query": "FROM metrics-*"
}
```

If we change the index settings to not have `index-mode:time_series` or we remove the `time_series_metric` from the fields, then the missing `original_types` come back.
Discussion
- Pinging @elastic/es-storage-engine (Team:StorageEngine)
- I was also thinking that the current format for original_types is insufficient, because it does not include the time_series_metric, which in this case is the key reason for the incompatibility. Right now original_types looks like:
```
"original_types": [
  "double",
  "keyword"
]
```

And that makes sense when it is just the DataType that clashes, but when it is two doubles, one a gauge and the other a counter, this does not make sense. We need an expanded format, perhaps:
```
"original_types": [
  {"type": "double", "time_series_metric": "gauge"},
  {"type": "double", "time_series_metric": "counter"}
]
```

And Kibana needs to be updated to cope with the type being either a string `"double"` or an object `{"type": "double"}`, possibly with additional information: `{"type": "double", "time_series_metric": "gauge"}`
