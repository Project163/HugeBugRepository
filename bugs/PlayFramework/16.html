Title

Race condition in Java WebSockets

Description
This build:

[URL]

failed with:

```
[info]   allow handling a WebSocket in java
[info]   + allow consuming messages
[info]   x allow sending messages
[error]      List(TextWebSocketFrame(text: b), CloseWebSocketFrame) does not contain exactly 3 correct values in order
[error]      - TextWebSocketFrame(text: b)
[error]       * 'b' is not equal to 'a'
[error]      - CloseWebSocketFrame
[error]       * 'CloseWebSocketFrame' is incorrect:  (WebSocketSpec.scala:82)
```

This failure looks to me like a legitimate race condition in the Java WebSocket support in Play, the first message sent by the server is being lost.  There's a chance it could be a race condition in the WebSocket test client, but I doubt that.
Discussion

- Ok, doing an analysis of all build failures, I've found that this doesn't just impact Java WebSockets, it impacts Scala WebSockets too.  I'm therefore thinking that it's not the server side implementation, as I can't see how that could cause this, rather it's the test client.
- @hepin1989 You were right, this was caused by that issue.

The problem happens when the server accepts a connection, and then immediately sends a message.  Under some circumstances, this message could well end up being part of the first selector read.

I managed to produce by ensuring that Netty only used one worker thread, and putting a Thread.sleep after initiating the handshake.  This meant on the next read, it read both the handshake response, and the first (and in fact second and third) messages, and all those messages were lost.  I then upgrade to Netty 3.9.3, and the problem was fixed.

Good news is, this is only in the Netty WebSocket client, so this doesn't affect Play's server side WebSocket handling.  I've merged #3298 to fix.
