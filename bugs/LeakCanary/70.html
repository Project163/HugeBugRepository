Discussion
- Thx, received 2021-10-27_14-17-17_656.hprof

Sounds like the VM only has 20Mb free and expanding the LongLongScatterMap requires 32Mb. One thing to look at here is why there's only 20Mb free, i.e. if LeakCanary is using more memory than it should, or if the app code itself is doing that. If it's LeakCanary, we should fix that.

If it's the app itself, we can't quite fix that, but it might be worth building support for handling this. E.g. maybe catch and report the error and ask the user to kill the app then rerun?
- I took a look at one of our heaps, and it looks like we're using ~400MBs, of which a good chunk is for reflection which only exists in debug builds (to speed up build times). If there's nothing Leakcanary can do because the heap is too big, that's fine. :) I do like your idea of telling the user to kill the app so more memory is available... maybe docs to shark-cli can also be linked so that users know there's an alternative as a last resort?
- We ended up using `leakcanary-android-process` to go back to the separate analyzer process so it has enough memory. Maybe that could also be suggested?
- Yup. You really should consider using less memory though ;)
