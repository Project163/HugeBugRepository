Title

Synchronize Keyspace instance store/clear

Description
DTest failure: dtest-large.repair_tests.repair_test.TestRepairDataSystemTable.test_repair_table (vnodes) - one random failure was reported which pointed to a race condition to be spotted.
Discussion
- The issue is that it was possible to open a new Keyspace instance in the middle of Schema.dropKeyspace(). To see the problem the drop has to progress to the following  state : 1) Keyspace instance doesn't exist - it has been already removed.  
 2) KeyspaceMetadata still exists 
 Keyspace.open in this state creates a new Keyspace instance (with ColumnFamilyStore instances) and stores it in Schema.keyspaceInstances. This is an object leak.

- I think you were right originally about this patch not applying to 4.0. The call hierarchy to the private  Schema.dropKeyspace(..)   method is only three only methods, all of which are  synchronized . 

 In 3.11: at runtime it's only accessed by method in  SchemaKeyspace.mergeSchema(..)   which is also  synchronized . But the method itself is public and not  synchronized  so the tests can get into the race condition. Ideally i would think it's better to have synchronized at the test layer, but that's maybe asking a bit much for such a small fix, so I'm +1 on the 3.11 patch.
