Title

Unable to establish/maintain multiple connections due to connection priority error

Description
### What happened?

Connections are getting unexpectedly closed ("replacing connection" on one side, "connection reset by peer" on the other) for no discernible reason, making it so that more than one connection never stays open despite both sides being configured for eight connections. Problem seems to be incorrect connection priorities. Linux side drops the link local IPv6 connection:

```
[PSEUD] 2024/09/20 09:25:37.501964 service.go:1453: DEBUG: Closing connection [fd7a:115c:a1e0::5501:4880]:22000-[fd7a:115c:a1e0::7301:283d]:22000/tcp-server/TLS1.3-TLS_AES_128_GCM_SHA256/WAN-P30-5VMT6ACVKOPSMK1QVES23Q3HUO to HX2ELNU with priority 30 (cutoff 20)
```

Priority 30 in my setup is "TCP WAN", while this is clearly a LAN connection.

Mac side keeps dialing those connections, correctly classifying them as TCP-LAN (priority 10):

```
2024-09-20 11:23:32 dialing PSEUDOP-YLA5DBR-XO2HBNT-2FOG4AC-SWOW5EZ-H3QQY76-GISB7PG-E2SWOA2 tcp://[fd7a:115c:a1e0::5501:4880]:22000 success: [fd7a:115c:a1e0::7301:283d]:22000-[fd7a:115c:a1e0::5501:4880]:22000/tcp-client/TLS1.3-TLS_AES_128_GCM_SHA256/LAN-P10-
```

Discussion
- So actually the problem here seems to be not Syncthing but my networking setup. The fd7a address is Tailscale, and how that is set up network-wise differs between Mac and Linux. On Mac there is a tunnel interface:

```
utun4: flags=8051  mtu 1280
	options=6460 
	inet6 fe80::f0ed:7e22:2e82:5b83%utun4 prefixlen 64 scopeid 0x16
	inet   -->   netmask  
	inet6 fd7a:115c:a1e0::7301:283d prefixlen 48
	nd6 options=201 
```

Note prefixlen 48 on the fd7a address, so Syncthing will see fd7a:115c:a1e0::/48 as a local network.

On Linux, the interface is this:

```
135: tailscale0:   mtu 1280 qdisc fq_codel state UNKNOWN group default qlen 500
    link/none
    inet  /32 scope global tailscale0
       valid_lft forever preferred_lft forever
    inet6 fd7a:115c:a1e0::5501:4880/128 scope global
       valid_lft forever preferred_lft forever
    inet6 fe80::d865:aa9f:518a:9904/64 scope link stable-privacy
       valid_lft forever preferred_lft forever
```

That is, a /128 address and nothing else, accompanied by a route for the /48 (not shown here), but that means Syncthing doesn't see it as a LAN.

And really, the Linux side does it better here, because there is no reason in my setup for the connections to go via Tailscale when there is an alternative direct IPv4 network they can use...
- Is there a valid reason to not treat all ULAs as LAN? If we're able to dial them, it's some kind of LAN. We're not able to classify VPN'ed connections as WAN either way.
- ... [Middle Discussions Snipped for Brevity] ...
- Syncthing running inside a regular Docker container isn't able to list the network interfaces of the host and the IPs assigned to them. A connection from e.g. ` ` would be treated as TCP-WAN because the virtual interface of the container only knows about its ` /16` subnet.
- That should be fine though, that's just like being behind a router. The above was only a problem because there were multiple networks available between my devices, one was preferred by device A (ipv6 over tailscale, because it looked like "lan" and we do ipv6 before ipv4) and the opposite was preferred by device B (ipv4 on the lan which was proper lan).
