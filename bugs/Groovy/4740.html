Title

STC: floating-point literals no longer accepted as args to method with double parameter

Description
I'm not sure if this recent change was intentional or not.  If it is intended, so be it.  But in case this has not been seen by anyone else, we had a lot of code that did floating-point computations and used @CompileStatic.  Starting with Groovy 2.4.13 (I think), we are seeing STC errors. 

  
 
 import  groovy.transform.CompileStatic

@CompileStatic
 class  Static {

   def  main() {
    meth(1.0)  // STC error
   }

   def  meth( double  val) {
  }
}
Discussion
- This is related to the change for   GROOVY-8325    commit d965023c266899 . Looks like the change restricts the comparison of the primitive (number) types and their wrappers. Before the change it was valid to pass a  BigDecimal  or  BigInteger  (or even an  AtomicLong ) to a method taking a  short . 

 In the test case provided the  1.0  is a  BigDecimal , the method call works if  1.0f  is used.
- Just to follow up, we used to be able to pass literals like  1.0  to methods taking a double and it would be converted automatically.  Now we must use  1.0d  or else face a compile error under  @CompileStatic .  Is the error the new expected behavior?  If so, I'll close.
- It is better to convert type automatically IMO. The issue is a bit similar to   GROOVY-6668  . 

 To  paulk   jwagenleitner  We should discuss "Least Surprise  VS  Strict Type Check" seriously in mailing list. 

  
 
 import  groovy.transform.CompileStatic

@CompileStatic
 class  Static {

  def main() {
    meth(1.0d)   // works
   }

  def meth( double  val) {
  }
}
