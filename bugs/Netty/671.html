Title

JdkZlibDecoder ignores everything but first GZIP stream, non-compliant with RFC 1952

Description
### Expected behavior
gzip content is fully consumed
### Actual behavior
gzip content is partially consumed
### Steps to reproduce
n/a
### Minimal yet complete reproducer code (or URL to code)
n/a
### Netty version
4.1.17
### JVM version (e.g. `java -version`)
n/a
### OS version (e.g. `uname -a`)
n/a


I'm using Spring WebClient to read a large (12 million records) gzipped response. I've set up the Netty pipeline as follows:
```
ctx.addHandlerLast(new ReadTimeoutHandler(readTimeoutMillis, TimeUnit.MILLISECONDS));
ctx.addHandlerLast(new Slf4JLoggingHandler());
if (forceDecompression) {
    io.netty.handler.codec.http.HttpHeaders httpHeaders = new ReadOnlyHttpHeaders(
            true,
... [Log Snipped] ...
}
ctx.addHandlerLast(new HttpContentDecompressor());
```
The `HttpResponseHeadersHandler` overwrites headers in the response because the server doesn't send an `Content-Encoding` header. Details and implementation can be found [Link: here].

Problem is, processing stops after about 130,000 records. No errors are shown. I've debugged and found out that the `JdkZlibDecoder` used for decompression stops reading and enters the finished block. I've tests that work fine for fewer number of records (100 or so).

However, using a different client (okhttp), if I don't set the `Content-Encoding` header and wrap the input stream with `GZIPInputStream`, everything works as expected.

So, question is, if `GZIPInputStream` doesn't have a problem, why does `JdkZlibDecoder`? And since it does, why won't it report what it thinks is the issue?
