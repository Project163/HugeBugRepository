Title

Async search status endpoint returns for deleted search

Description
### Elasticsearch Version

9.2.0-SNAPSHOT

### Installed Plugins

_No response_

### Java Version

_bundled_

### OS Version

Darwin

### Problem Description

If you delete an async search, the async search status endpoint does not indicate that the search request is deleted and it seems to keep running.

### Steps to Reproduce

1. Submit an async search (`POST _async_search`) (for reproducing this bug, it needs to take awhile)
2. Delete the search (`DELETE _async_search/{id}`)

```
{
  "acknowledged": true
}
```

3. Get the status (`GET _async_search/status/{id}`) 

```
{
  "id": "FnIybFJmcFRjU1JTLV9RWFd1dDEwRmceOU40cFl4Mk5RZW1uSkZCYjQ4NVNNUTozNDQ5MDYw",
  "is_running": true,
  "is_partial": true,
  "start_time_in_millis": 1754347528891,
... [Log Snipped] ...
  }
}
```

The status is returned as if it hasn't been deleted. This is in contrast with what happens if you call `GET _async_search/{id}` directly (which correctly reports the search cannot be found, since it has been deleted):

```
{
  "error": {
    "root_cause": [
      {
        "type": "resource_not_found_exception",
... [Log Snipped] ...
  "status": 404
}
```

- I'm seeing a race condition in this scenario.

The DELETE API only starts the deletion process, which takes time and happens asynchronously. If I immediately query the status, I get the response detailed in the description. However, if I add a short sleep (1 sec), I get the correct response (resource not found). This is a case of eventual consistency.

@lukasolson does that fit with what you saw?

As I see it, we have 3 options:
1. Delay the response for the DELETE API, making it synchronous. This may have repercussions that are not immediately clear to me.
2. Add an API for the cancellation status. A bit much for my taste, but very conventional in eventual consistency. Probably worth hearing from product on this.
3. Decide that we can live with this, and update the documentation, since this behavior can be surprising.
