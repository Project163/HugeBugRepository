Title

clearTimeout runs another setTimeout callback

Description
### Brief summary

When clearing a callback, set by `setTimeout()`, using `clearTimeout()` will run another `setTimeout()` callback on the cancelled timer.

### k6 version

1.2.3

### OS

macOS 15.6

### Docker version and image (if applicable)

_No response_

### Steps to reproduce the problem

Run this simple test:
```
export default function () {
    setTimeout(() => {
       console.log("timeout"); 
    }, 60000);
    const cancelTimeout = setTimeout(() => {}, 1000);
    clearTimeout(cancelTimeout);
}
```

### Expected behaviour

The first `setTimeout()` (that logs "timeout") should run after 60s.

### Actual behaviour

The first `setTimeout()` is ran after 1s, and the test immediatly ends.
Discussion
- Hi @kyriog, thank you for reporting this 🙇 

I have confirmed the bug, and it seems to be due to clearTimeout not making the necessary adjustments if it is removing the *first* timeout. Here first is the one that will be ran first, not in order of being added.

In that case it doesn't do any adjustments but we are already running a timer for it so it will go and execute the first thing in the queue - in this case that means that it will get the one after.

In your example if you put the second timeout to 2-3-4s. It will be the time that it will take for the fist `setTiemout` callback to be queued and executued.

I have made a PR and a fix already.
- I indeed noticed it runs the shortest timer (If you setup 3 `setTimeout()`, after cancel, the one that will be run early is the shortest of the two remainings), though I did not included it in my bug report to avoid adding complexity to test case :) 

In my specific use case, I’m actually cancelling an interval (which has a very short timer), and it impacted a completly unrelated long-running timeout (but it makes sense as the timeout and interval ids are shared).

Thanks for your PR!
