Title

Data racing in core/lib/channel/channel_trace.cc

Description
### What version of gRPC and what language are you using?
v1.62.2, C++


### What operating system (Linux, Windows,...) and version?
Linux


### What runtime / compiler are you using (e.g. python version or version of gcc)
clang 18.1.4


### What did you do?
In a standalone thread, I periodically (at 1Hz) poll data from `grpc_channelz_get_top_channels`, and walk through the result by calling `grpc_channelz_get_subchannel` and `grpc_channelz_get_socket` to get detailed information. 

### What did you expect to see?
Do not crash.

### What did you see instead?
I experienced SEGSEGV fault with callstack like below (callstack sanitized with removing proprietary info）
```
grpc_core::channelz::ChannelTrace::RenderJson()
FailureSignalHandler()
(unknown)
grpc_core::channelz::ChannelTrace::RenderJson()
grpc_core::channelz::SubchannelNode::RenderJson()
... [Log Snipped] ...
...
start_thread
```

The crash happens at `grpc_core::channelz::ChannelTrace::RenderJson()`, which is called from `grpc_core::channelz::SubchannelNode::RenderJson()`.   Look at [URL] the member variable of the `ChannelTrace` is accessed without proper synchronization. A mutex object is created at [URL] but it is never used. 

As of now, I am setting up the `GRPC_ARG_MAX_CHANNEL_TRACE_EVENT_MEMORY_PER_NODE` to 0 (since channel trace is not something I am interested in anyways). But the data racing problem should be fixed. 

See [Link: TROUBLESHOOTING.md] for how to diagnose problems better.
