Title

no-extra-bind should flag arrow functions using 'this'

Description
Arrow functions bind `this` lexically.  When an arrow function is used with `Function.prototype.apply`, `Function.prototype.bind`, `Function.prototype.call`, or `Reflect.apply` the thisArgument is silently ignored.  These functions are still useful for specifying arguments to the arrow function but they can create confusing errors if the new value of `this` is expected to be applied.  I propose a new rule be added to warn when trying to set a new value for `this` in an arrow function.

I'm not sure exactly how to define such a rule.  My initial thought is to warn whenever a non-null value is used as the thisArgument for an arrow function.  By always passing `null` as the thisArgument, no one would ever be confused as to why the function wasn't using their custom object as `this`.  On the other hand, someone might expect `this` to be set to `null` within the arrow function and still cause confusion.

So in summary, I'd like to request a few enhancements.
- Instead of just checking `Function.prototype.bind`, check for all mechanisms that could change the `this` value.
  - There's a dilemma I mentioned originally.  Other functions like `Function.prototype.call` are still perfectly valid for specifying arguments so warnings should only be generated when obviously attempting to set the thisArgument.
- Instead of just checking function expressions also check for extra bindings when the function has been saved to a variable (where possible)
- Instead of just checking functions that don't use `this` also check for arrow functions that contain `this` which can not be rebound.
- We don't ever do this, it's too dangerous to check in some cases but not others. It also sets expectations poorly for how ESLint works.

If we did this, it would be a separate rule. That said, I don't see this as the same as `bind`, so I'm not sure such a rule would be useful. Unlike `bind`, the other methods don't create a new function so there's less occasion for trouble. 

As already mentioned, we do not track variable values, so we don't do these sorts of checks.

I think this is an actual bug we should fix.
