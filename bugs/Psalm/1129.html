Title

ParamNameMismatch issues from vendor leak

Description
Since last commit  , psalm reports issues for classes extending vendor classes with ParamNameMismatch issues, even though project subclass doesn't define methods that use those params. Such classes look such as

```php
use GuzzleHttp\Psr7\Request;

class OrganisationAwareRequest extends Request
{
}
```


```
 ParamNameMismatch - src/AppBundle/DataProvider/Eportfolio/Pellcomp/OrganisationAwareRequest.php:10:7 - Argument 1 of GuzzleHttp\Psr7\MessageTrait::withHeader has wrong name $header, expecting $name as defined by Psr\Http\Message\MessageInterface::withHeader (see [URL]
class OrganisationAwareRequest extends Request
```
Discussion
- Consider the following code:
```php
use Psr\Http\Message\MessageInterface;

function addHeader(MessageInterface $request): MessageInterface {
    return $request->withHeader(name: 'X-Header', value: '42');
}
$request = addHeader(new OrganizationAwareRequest);
```
It will break in PHP 8 (https://3v4l.org/FfBho), so it makes sense to report it. Feel free to suppress the issue if you're targeting PHP 7.
- But this is completely vendor issue, there is nothing I can do to fix it. And I cannot exclude the rule while keeping it enabled for non-vendor issues, can I?
