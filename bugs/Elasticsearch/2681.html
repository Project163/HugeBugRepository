Title

_terms_enum not supporting fields by alias for non-super user

Description
**Elasticsearch version** (`bin/elasticsearch --version`): 7.14.1 /7.15.0

**OS version** (`uname -a` if on a Unix-like system): darwin_x86_64

**Description of the problem including expected versus actual behavior**: _terms_enum stopped supporting fields by alias.

This bug is the result of an SDH and discuss post - [URL]

**Steps to reproduce**:
 1.  Create an alias to index pattern
 2. Create a user with a role with all privileges to the alias from the first step.
 3. Login with that user and try to create a filter - filter values are not getting populated. 

This works in 7.13.4 and in 7.15.0 - this works if I change autocomplete:valueSuggestionMethod to terms_agg from terms_enum (default) in Kibana advanced settings.

Here is the Kibana bug -  [URL]
Discussion
- From the terms_enum design docs:


The issue with the new (fast) implementation is that it relies on quickly reading terms directly from Lucene's alphabetically sorted index without checking if the docs that contain those terms are accessible to the end user. Based on this "unfiltered" assumption, things like document-level security or filters associated with aliases can't be supported and no results are returned in these scenarios.
- @markharwood this isn't a doc level security or filtering issue.  

The issue is that the _terms_enum endpoint when called with an alias, seems to check the user's privs first on that alias, and then also on the index.  And in these cases (SDH's from upgrades, etc.) the users only had privs on the alias.

@bhavyarm has some logs she could post here from Elasticsearch audit logging which shows access_granted on the alias and then access_denied on the index.  From the Kibana query log, we only see Kibana querying using the alias.

Since Kibana changed in 7.14 to use this endpoint, it causes a regression in functionality to the Kibana user.  Those users have a workaround to switch a Kibana advanced settings to terms_agg.

So I'm guessing that terms_enum always had this issue (not a regression).

- Just wanted to add a follow-up here:

I've configured an index alias that points to specific indices. I created a role that has access to the alias (but not the underlying indices themselves).

I am able to do a terms aggregation against the alias and get results, but when I try to do a `_terms_enum` call to that alias, no results are returned.

Just wanted to clarify the issue here 😄
- Incidentally, note that this is the expected behaviour if you happen to have DLS enabled on an index - aggs will work, terms_enum will not. Regardless of any aliases. I'm not saying that DLS rules are behind this issue here - just a heads up.

I checked this out and it does appear to be a security discrepancy of the type that causes us to consider [Link: removing support for security on aliases] (still an open issue I see).

The terms enum API has aliases resolved into index names on the coordinating node and does additional access checks on data nodes using the index names. These fail for the same reason that `GET my_alias/_search` works and `GET my_index/_search` fails if the user is granted access to an index via an alias. I added some [Link: comments] to that issue to solicit opinion on if this is something we should support and fix. See also the comment there on false positives for any alias filters.
