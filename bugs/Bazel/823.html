Title

sandboxfs not working with --output_base or --output_user_root

Description
### Description of the problem / feature request:

Sanboxfs is producing errors (Operation not permitted while opening output file) when defining --output_base or --output_user_root not in /private/var/tmp

### Bugs: what's the simplest, easiest way to reproduce this bug? Please provide a minimal example if possible.

`bazel build --experimental_use_sandboxfs //absl/...` and 
`bazel --output_base=$HOME/abseil/ build //absl/...` passes without erros
but 
`bazel --output_base=$HOME/abseil/ build --experimental_use_sandboxfs //absl/...` produces 
`error: unable to open output file 'bazel-out/darwin-fastbuild/bin/absl/strings/_objs/ascii_benchmark/ascii_benchmark.o': 'Operation not permitted'`

### What operating system are you running Bazel on?

MacOS 10.12.6

### What's the output of `bazel info release`?

release 0.22.0-homebrew

[URL]
 

### Sandboxfs Version

sandboxfs-0.1.0-20190205

Discussion
- @jmmv - this error is still present with bazel 3.1.0 and sandboxfs 0.2.0

Changing the default output directory layout as described in [URL] using either --output_base or --output_user_root breaks the sandbox build
- Sorry for the delay...

So the problem comes from here:

```
(version 1)
(debug deny)
(allow default)
(deny file-write*)
(allow file-write*
... [Log Snipped] ...
    (subpath "/private/tmp")
)
```

This is the configuration we write for `sandbox-exec`. When we use the default output base, we get blanket access to write into `.../tmp/` and because the sandboxfs instance is there, things work. When we move the output tree elsewhere, the sandbox only allows access to the `.../sandbox/darwin-sandbox/...` paths. This is fine for the symlinked sandbox because the symlinks are there, but when sandboxfs is active, we are issuing the writes to a path that is not covered by the sandbox.

Should be easy to fix. Let me see if I can do something quickly.
- This uncovers something else though: because the default output base is under `/private/var/tmp`, and because the sandbox configuration allows blanket write access to `tmp` directories... the sandbox isn't really protecting against writes across different per-action directories! Yikes. I'll add a note to #11100 about this, which I think is where we should tackle this separate issue.
