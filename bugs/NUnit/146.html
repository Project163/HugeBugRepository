Title

PropertyConstraint throws away the more helpful message in the base constraint result

Description
## Problem

PropertyConstraint keeps the base constraint description but throws away the actual comparison message and just prints the actual value.

Starting with a familiar example, `Is.EquivalentTo`:

```cs
var actual = new SomeClass { SomeProperty = { 2, 3, 5, 7 } };
Assert.That(actual.SomeProperty, Is.EquivalentTo(new List  { 2, 3, 5, 8 }));
```


But as soon as you compose it with `PropertyConstraint`:

```cs
var actual = new SomeClass { SomeProperty = { 2, 3, 5, 7 } };
Assert.That(actual, Has.Property("SomeProperty").EquivalentTo(new List  { 2, 3, 5, 8 }));
```


In that example, just printing the actual value is still pretty okay.
But when the value is a complex object that doesn't `.ToString()` to something you care about, you get something like this:


```cs
Assert.That(new SomeClass(), Has.Property("SomeComplexThing")
    .SomeCustomConstraint(expectedComplexThing));
```

## Proposal

Here you can see the constraint, which understands the semantics of the actual value, getting thrown away. Only the actual value and success bool are retained:

Rather than the existing code below, I think we should have an internal-for-now  `ChainedConstraintResult` class which delegates all its writing to the base constraint result:

```
cs
internal class ChainedConstraintResult : ConstraintResult
{
    private readonly ConstraintResult _baseResult;

... [Log Snipped] ...
    }
}
```

PropertyConstraint would then do this:

```cs
var baseResult = BaseConstraint.ApplyTo(propValue);
return new ChainedConstraintResult(this, baseResult);
```
Discussion
- All our other "chained" constraints produce a single result because that's what the Assert methods expect to deal with. Internally, they look at the nested constraint in producing their result. It seems like this was missed in `PropertyConstraint`. 

IMO, a linked chain of constraint results gives Assert too much to do. Note that whatever Assert needs to do, Assume, Warn and any other similar classes also have to do. Having a single `ConstraintResult` was intended to simplify things for those upstream classes. The idea was that `ConstraintResult` should be the class that knows how to "flatten" the chain or tree of nested `Constraints`.
- @CharliePoole I don't understand how this impacts `Assert` and the rest. They still get handed a single `ConstraintResult`. They don't know that it is a `ChainedConstraintResult`, and even if they did, they can't access the chain.

The chain is retained as a private implementation detail because otherwise the logic for writing the message is not retained.
