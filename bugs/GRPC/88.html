Title

After "Failed getpeername: Bad file descriptor" the unix domain grpc server does not recover unless restarted

Description
### What version of gRPC and what language are you using?
1.52.1

### What operating system (Linux, Windows,...) and version?
Linux

### What runtime / compiler are you using (e.g. python version or version of gcc)
g++

### What did you do?
I have two c++ applications (grpc server and client) running on the same device. They both communicate over the Unix domain socket. Both are using same grpc library version 1.52.1.
Server listens on "unix:/var/run/server_uds"
The client keeps creating new channels, fires a unary RPC and closes the channel.
Occasionally the client is restarted

**In some extremely rare cases, I see the following error on server side:**
E1011 19:45:02.624072018    1864 tcp_server_posix.cc:245]              Failed getpeername: Bad file descriptor

Once the above error is seen, the server no longer accepts any new connections.

The issue was seen 3 times in the production environment and I was not able to reproduce the "Failed getpeername: Bad file descriptor" error myself. However, one correlating factor from the logs was the restart of the client.
Just after the restart of client, this error is seen on the server and the server goes to a bad state.
I tried restarting the client multiple times around the time of channel creation but getpeername always succeeded.

While I agree that we need to identify the reason which lands up in this scenario. Should it be handled in such a way that the server does not give up listening
"Bad file descriptor" is one of the failure and there could be many other failure scenarios such as {EBADF, EFAULT, EINVAL, ENOBUFS, ENOTCONN, ENOTSOCK}
In any of the scenario, if the server stops listening completely, then it could be a problem (unless the reason is unrecoverable for example: ENOBUFS)
