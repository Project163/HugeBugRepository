Title

Improperly set "Range" header when retrying file download from Dropbox

Description
#### What is the problem you are having with rclone?

Rclone consistently fails to sync huge files from Dropbox to Backblaze (wrapped in rclone crypt). When doing so the percentage counter goes way beyond 100% (170%+) and then it fails because of an invalid target size.
This is due to an improperly set "Range" header when retrying download from Dropbox, which results in re-downloading already processed data and inflating the target file - resulting in sync failure.
Looks like rclone does not update the start of the range when it was already set.

#### Correct behavior
- Line 205 Request   - Rclone starts downloading the file from Dropbox (1st attempt)
- Line 5309 - Latest uploaded chunk before reading failure (chunk 202 size 96Mi offset 18.938Gi/67.258Gi - 20333985792 bytes sent)
- Line 5310 - A reading error occurred on offset 20766346465 due to an unexpected end-of-file
- Line 5311 Request   - Rclone starts downloading the file from Dropbox (2nd attempt), using range 20766346465-72200451298

#### Incorrect behavior
- Line 5632 - Latest uploaded chunk before reading failure (chunk 214 size 96Mi offset 20.062Gi/67.258Gi - 21541945344 bytes sent)
- Line 5633 - A reading error occurred on offset 21662613633 due to a timeout
- Line 5634 Request   - Rclone starts downloading the file from Dropbox (3rd attempt), using a wrong range 20766346465-72200451298
- However correct request range from Dropbox should be 21662613633-72200451298
- Rclone is now reprocessing range 20766346465-21662613633 (854.74MB of data) from Dropbox which is already (or will be) on Backblaze

Discussion
- Thanks for reporting this, it does look like a bug. And thank you for your excellent log and analysis.

The problem seems to be in the re-open code

First failure

    Reopening on read failure after offset 20766346465 bytes: retry 1/10: unexpected EOF

Reopens with range request - looks good

    Range: bytes=20766346465-72200451298

Second failure

    Reopening on read failure after offset 21662613633 bytes: retry 2/10: ... i/o timeout

Reopens with incorrect range request - should clearly start from 21662613633 as per the log

    Range: bytes=20766346465-72200451298

Third failure

    Reopening on read failure after offset 34544399248 bytes: retry 3/10: ... i/o timeout

Re-opens with the same incorrect range request

    Range: bytes=20766346465-72200451298

I can reproduce this by patching the dropbox backend to return errors every 1000 bytes.

I've managed to fix this I think.

It turned out to be quite a subtle bug and I think it has caused a lot of issues with rclone downloading too much data over the years.

Please give this a go
