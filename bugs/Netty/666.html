Title

Epoll deadlock during classload

Description
### Netty version
4.1.17


This was a tricky one reported by one of our gRPC users.  There is a deadlock that can occur during initialization of netty Epoll code.     The core of the problem is that the Epoll class load JNI code, which then calls back into java code to load more classes.  I think it would be best if all JNI code in netty did NOT call back into Java to avoid these cycle problems.  

In the reported case there are two event loops that are trying to load.    The abbreviated interleaving that causes the lock is listed below, using T1 and T2 as the threads.

1.  T1 calls `Epoll. `
2.  T1 calls `Runtime.loadLibrary0`, which is synchronized on the `Runtime` class.  The **`Runtime.class` lock is held.**
3.  T2 creates a new channel, resulting in `AbstractChannel.newId` calling `DefaultChannelId.newInstance`.  
4.  T2 calls `DefaultChannelId. `, which calls `MacAddressUtil. ` which finally calls  ` java.net.NetworkInterface. `.  
5.  T2 **Now hold the classloader lock for NetworkInterface**
6.  T2  `NetworkInterface. `   attempts to call `System.loadLibrary` for library `net` which then blocks trying to acquire the `Runtime.class` lock
7.  T1 now continues, calling `netty_epoll_native_JNI_OnLoad`, followed by `netty_unix_socket_JNI_OnLoad`
8.  T1 tries to initialize `NetUtil` with `(*env)->FindClass(env, netty_unix_util_prepend(packagePrefix, "io/netty/util/NetUtil"));`
9.  T1 In `NetUtil. ` tries to initialize `NetworkInterface`, but waits to acquire the class init lock.



At this point both threads hold each others' locks, and progress ceases.
