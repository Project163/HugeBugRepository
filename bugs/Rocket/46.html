Title

`Route.set_uri` does not play well with segment offset calculation

Description
Consider this example code (adapted from an issue reported on IRC):

 

```
rust
#![feature(proc_macro_hygiene, decl_macro)]

#[macro_use] extern crate rocket;

... [Log Snipped] ...
    rocket::ignite().mount("/", routes![hello]).mount("/", a::routes()).launch();
}
```

 

Trying to access `/a/b/3` fails, because the `id` parameter tries to decode `b` as a `u8`. I am not quite sure where exactly the blame lies here, but it has to do with the behavior of `set_uri` and of `Request::routed_path_segment`.

* `Request::routed_path_segment` is used to calculate which part of a URI corresponds to the "nth" segment. This is done by calculating how many segments are in the "base" URI, then skipping over that many segments in the full URI.
* When calling `set_uri` manually it is difficult to correctly preserve the relationship between "base" and "original" URIs such that it does not break `routed_path_segment`. The code above does that (I think), but in a hacky way.
* `mount` calls `set_uri` in such a way that it does *not* preserve the relationship between base and original URIs. Consider the route with `base`="/a" and `uri`="/a/b/ " (`uri` always includes `base`). `mount`ing this route at "/" will adjust the route to have `base`="/" and `uri`="/a/b/\ ", which has changed the base-to-uri offset and adversely affected `routed_path_segment`.

I am not sure what the best way to solve this is, but I definitely think the `set_uri` API and/or documentation should be improved to avoid falling into this trap.
Discussion
- I'm labeling this as a bug: Rocket should ensure that no API can break codegen. Fix is incoming.

By the way, to be clear, that snippet uses private APIs and is thus not valid. Nevertheless, a bug remains.
