Title

Passing a filter statement to session when updating emits an update without any clauses

Description
Today we released to production a statement that looks like this:
```
session.query(User.name == 'filter').update({'name': 'update'})
```
as you can see, it's a wrong version of:
```
session.query(User).filter(User.name == 'filter').update({'name': 'update'})
```
and the emited SQL was the following, which updated the whole table.
```
UPDATE users SET name='update'
```

We would like to know if there's a reason to allow this behavior and if there's not, maybe it'd be a good idea to block this kind of statement. 

Working example:
```
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy import Column, Integer, String, create_engine
from sqlalchemy.orm import sessionmaker

engine = create_engine("postgresql://root:root@postgres/test")

session.query(User.name == 'filter').update({'name': 'update'})
# UPDATE users SET name='update'
```
Discussion
- this has been supported behavior mostly because it is valid to say something like, `query(User.__table__).update(...)`, when that form is used, it is equivalent to saying `query(user_table.c.id, user_table.c.name, user_table.c. , ...).update()`, so we consider a Column expression to be valid.  your query was definitively against a certain table and the internals don't make it easy to figure out this was not your intent, although it is likely possible to guard against this *specific* case, sure.   

There is a long term tentative plan for SQLAlchemy 2 where Query() would no longer have an update() method at all and the regular update() construct would be used, so that there would be less awkwardness in this regard.


I'm not sure if this is intended to suggest some form of urgency on SQLAlchemy's part to alter this behavior ; as mentioned above, we can always add logic to test for a specific mistake someone made, but that is just one out of potentially infinite other kinds of mistakes we didn't think of that day, so depending on the situation (this one is sort of in the middle) it may be more or less feasible as a generally useful catch that can prevent a large class of mistakes while not disallowing for valid use cases or breaking reasonable backwards compatibility (this one would break backwards compatibility for someone relying on this behavior right now which makes it less likely for anything to change soon).
