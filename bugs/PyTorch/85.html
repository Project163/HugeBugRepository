Title

Segmentation fault when dividing by zero with integer tensors

Description
This seems to be an issue with TH and not pytorch, the same thing happens in lua torch.

```python
import torch
a = torch.IntTensor([0,1])
b = torch.IntTensor([0,1])
print(a.div(b)) # Floating point exception (core dumped)
```

Another unrelated weirdness happens with float tensors when the answer is `inf`

```python
import torch
a = torch.FloatTensor([1,1])
b = torch.FloatTensor([0,0])
a.div(b)
```
which works on lua torch, but gives
```
 >) failed: RuntimeError: inconsistent tensor size at /tmp/pip-zh0a53-build/torch/lib/TH/generic/THTensorMath.c:90>
```
in pytorch.

Discussion
- integer division by zero getting a FP exception is something we cannot avoid, it's a hardware exception. Numpy wraps it's integer division code to literally check the denominators with conditionals and instead generates fpectl exceptions. I dont think this can be a hi-pri issue for us just looking at the amount of work involved in refactoring TH.

Your second issue looks more like a bug.
- The first one is expected, second one is a bug in printing, when there are no non NaN and inf values in the tensor.

- I'm re-opening this issue because it has appeared plenty of times in the past (see linked issues, plus many others that haven't been linked).

From discussion in [URL] both TensorFlow and numpy handles the 0 / 0 division gracefully, so the performance hit of adding an extra check (for integer tensors) wouldn't be that bad in comparison.

With the current implementation, adding those checks only amounts to a few extra lines, so I think it should be reconsidered.
- Here is what I propose that we do for now.

We only handle the division case explicitly for now.

Other operators which might internally have a division by zero (like `log(0)`) can be handled later. As an example, `log(0)` does not segfault currently because `log` is not implemented for integer types in PyTorch for now.

Instead of following an approach similar to `numpy`, [Link: where the integer and floating point cases are handled similarly], we instead only add the runtime checks for integer types, [Link: as is BTW what numpy has in a FIXME note].

## What it looks like

### For the CPU case:

modify [URL] to also check if `b` is zero, in which case we set a  flag in the loop indicating that a `ZeroDivisionError` should be raised

### For the GPU case:

add an `assert` in the lambda if the divisor is zero for integer types. This is not consistent with CPU (which raises a `ZeroDivisionError`), but is the same as what we do for advanced indexing for now, see
[URL] 
Once [URL] gets merged, we can revisit the assert with something else.
