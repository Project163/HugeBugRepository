Title

ivy fails to compile a template with [ngTemplateOutletContext]=""

Description
# 🐞 bug report

### Affected Package
The issue is caused by package @angular/compiler


### Is this a regression?

Nope, ivy only


### Description
When trying to compile our app with ivy I was hit with a rather cryptic error message, I managed to track the cause to a `[ngTemplateOutletContext]=""` on a template. This used to work fine in the view engine, and the workaround is easy to fix in your app once you know where the problem lies, but I think this should be fixed in the interests of backwards compatibility and also it's not obvious where the problem lies.

Discussion
- Pesky `EmptyExpr` has a `visit` method that doesn't do anything, hence returns `undefined`, causing issues downstream. This is not allowed by its type signature, unfortunately that code seems to predate `strictNullChecks`.
- Should this really be valid? Angular 8 already has stricter template type checking, so compatibility for something that has no use isn't necessarily a good argument, IMHO. To me this reads like a syntax error, much like

```
const foo = ;
```

would be. I'd argue that if the user wants an undefined context, they should bind to `undefined` rather than an empty expression (?)

In total there is no good reason to use an empty expression, but on the other hand an error could uncover mistakes by the developer who forgot to add the proper context.
- @Airblader I agree, however there's two concerns here: template compilation and template type checking. From the stacktrace, it can be seen that the error occurs during template compilation and the empty expression binding currently crashes the whole compilation effort; that should never happen.

The template compiler is given the template AST to compile. If the parser had produced parse errors,  template compilation would not have been attempted. Apparently, the parser is okay with empty binding expressions and produces `EmptyExpr` nodes, so the template AST in itself is valid meaning that template compilation should be able to process it just fine. Therefore, it is then up to the template type checker phase (currently done independently from template compilation, but still always _after_ template compilation) to create diagnostics for such `EmptyExpr` nodes.

I am not sure when/if an `EmptyExpr` is ever a valid thing in an AST. If it is never valid, it could become an error during parsing and the template compiler would never have to deal with it. Otherwise, the template compiler should be able to handle it gracefully (like VE did apparently) and not crash (as Ivy currently does).
