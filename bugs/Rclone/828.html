Discussion
- I don't think this is a duplicate of #8063 - I think it is most likely to do with the SDK v2 re-organisation

I suspect this is the problem here


You are telling rclone to look for AWS authentication (eg `~/.aws/config` the AWS environment variables, eg 

- Access Key ID: `AWS_ACCESS_KEY_ID` or `AWS_ACCESS_KEY`
- Secret Access Key: `AWS_SECRET_ACCESS_KEY` or `AWS_SECRET_KEY`
- Session Token: `AWS_SESSION_TOKEN` (optional)

You don't need to do that because you are using rclone config variables, eg `RCLONE_S3_ACCESS_KEY_ID=EDIT`

So if you remove that line from your config I think it will work.

If that does work it means that somehow we've introduced a backwards incompatibility into rclone which needs looking at.

Using the follwing install script provided on [Link: the download page]

```bash
curl [URL] | sudo bash
```

simply caused our pipeline to stop working. rclone 1.68.0 has a breaking change and I just rolled back to 1.67.0 for now.

This being said, I quickly tried your recommandation. Setting `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` instead of `RCLONE_S3_ACCESS_KEY_ID` and `RCLONE_S3_SECRET_ACCESS_KEY` **alongside** with `RCLONE_S3_ENDPOINT` and `RCLONE_S3_PROVIDER` worked on my computer, so this should work as a work-around for people willing to setup _rclone 1.68.0_ with env vars.

I can imagine that other users are in the same situation. CI/CD variables in GitLab or _secrets_ in k8s are often used to set environment variable in pipeline/container. Deployments is probably one of the important use-cases for _rclone_.

`env_auth = true` is indeed the default setting when calling it without config file, this value has not been set explicity.
