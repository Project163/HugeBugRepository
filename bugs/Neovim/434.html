Title

`vim.lsp.util.make_given_range_params()` can return wrong range for unsaved buffers

Description
### Neovim version (nvim -v)

0.6.1 release

### Language server name/version

not server related

### Operating system/version

Linux arch 5.15.13-arch1-1

### Steps to reproduce using "nvim -u minimal_init.lua"

1. Edit some new file `nvim test.txt`.
2. Insert some text, and write `:w` the buffer.
3. Now open  o  a new line and write some more text, *do not write/save yet*.
4. Make a visual selection in the new line and execute `:' lua print(vim.inspect(vim.lsp.util.make_given_range_params()))`. You'll see that the start col will be `0` and the end col will be `1`, regardless of the selection.
5. If you now save the buffer `:w` and repeat the previous step, you'll see that the start and end cols will have the correct values that correspond to your selection.

### Expected behavior

When opening a new line and not saving the buffer first, the returned range should be correct (match the selection).

### Actual behavior

When opening a new line and not saving the buffer first, the returned range will always have the start col set to `0` and the end col set to `1`, no matter the selection.

### Log file

_No response_
Discussion
- This is a regression in Neovim 0.6.1 caused by the newly introduced offset encoding handling. The bug is somewhere in `runtime/lua/vim/lsp/util.lua`: `get_lines(bufnr, rows)`.
I haven't had time yet to figure out what exactly is wrong in this function.
