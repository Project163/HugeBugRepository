Title

Svelte Kit's `fetch` and the Browser's `fetch` Produce Inconsistent Results

Description
### Describe the bug

Calling `await fetch(url)` from Svelte Kit `load` produces different results than when calling from the browser.

In a nutshell, given at least one special case, Svelte Kit's `fetch` will be able to retrieve a file, even if the browser's `fetch` will not.

While the special case given in the reproducing repo is not a very common use case, it may still shed some light on other inconsistencies in the custom implementation of `fetch`.

Discussion
- Changing the URL from `/#bug.html` to `/%23bug.html` lets the browser retrieve the file\*. So the difference here is that Svelte-Kit's `fetch` can handle some characters that aren't URL-encoded. Whereas the browser's `fetch` treats that as retrieving the `/` URL with a hash of `bug.html`, and `/` maps to `/src/routes/index.html`.

\* I did have to edit the browser example as follows:

```js
    import { browser } from '$app/env';
    async function loadBrowser() { /* ... */ }
    if (browser) loadBrowser();
```

That allows it to run *only* on the browser, instead of during server-side rendering. If I allowed the `loadBrowser` function from your reproduction to run during SSR, Node was throwing `TypeError [ERR_INVALID_URL]: Invalid URL` because the URL wasn't complete (no host, no protocol). (Svelte-Kit's `fetch` has an extra feature where you can write relative URLs and it will expand them based on the base URL you've specified in the config).

IMHO this is a feature, not a bug, but I won't close this issue as I'd like to let a core team member weigh in in case they think this really is a bug.
- Yeah, I was just thrown off by the fact that I did not have to escape the hash (#) character.
