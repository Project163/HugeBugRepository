Title

@RegisterProvider required for resteasy interfaces

Description
## Description
When a filter is defined with @Provider is should be applied to the resteasy interface.

[URL]

### Expected behavior
The following code should be enough to apply a filter
@Provider  
public class LogClientResponseFilter implements ClientResponseFilter 
Currently the following must also be done:
It also has to be registered to the interface:
@RegisterProvider(LogClientResponseFilter.class)

### Actual behavior
The filter is not applied to the resteasy interface


## To Reproduce

[Link: rest-client-reactive-quickstart.tar.gz]


Steps to reproduce the behavior:
1. run test, check output
2. remove @RegisterProvider and verify that the output is missing

Discussion
- So, JAX-RS says this:
```
A client filter is a class that implements ClientRequestFilter or ClientResponseFilter or both. A
container filter is a class that implements ContainerRequestFilter or ContainerResponseFilter,
or both. An entity interceptor is a class that implements ReaderInterceptor or WriterInterceptor,
or both. Filters and entity interceptors are providers and, as such, may be annotated with @Provider for
automatic discovery.
```

So I think it should be applied to clients. @ronsigal @jamezp what do you guys think? How does it work in pure RESTEasy?
- It applies only to the Container(reactive) now. It would be nice if also would be applied to the client, to be consistent
- @maciejwalkowiak They are discovered if the client runs in the container. Outside the container I don't think things are auto-discovered.
- The ClientRequestFilter or ClientResponseFilter are also discovered in the resteasy classic(non reactive) case
