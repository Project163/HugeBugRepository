- @TysonAndre that's one thing I was afraid of, and I think this was triggered by adding support for non-literal types in your PR. Is there a specific code that will stop to work correctly without this support?
- I think my change only affected the sealed array (TKeyedArray, i.e. array literals) and not the branch being referred to, but I may be mistaken

But my change still introduced a bug. For now, the conservative approach of returning the empty array for non-literals would avoid the false positives at the cost of not inferring types.

```php
function contains2(string $a, string $b, $element): void
{
    if (in_array($element, [$a], true)) {
    } elseif (in_array($element, [$b], true)) { // false positive Condition ($element is string) contradicts a previously-established condition ($element is not string)
    }
}
```

The code for handling strict equality in AssertionFinder::scrapeEqualityAssertions may be of use.

Unfortunately,
- The example only works for union types with a single type (literal or non-literal)
- The isSingle check seems to be related to union types only working for getAssertionString with a single type
- `$var_type->getAssertionString() !== $assertion` for atomic types seems useful in avoiding redundant condition warnings, but not paradoxical condition warnings. Type\Union::getAssertionString won't work for variables with more than one type, it only works for union types of a single type, which is why I see isSingle checks elsewhere
- Not sure why that code in scrapeEqualityAssertions is using `~` for approximate equality. Possibly a bug or workaround. Seems to be used in AssertionReconciler::reconcile(). Probably, it's so that negated the condition such as `if ($var === $otherString)` in the else branch isn't treated as a non-string, which happened when I tried to change it.
