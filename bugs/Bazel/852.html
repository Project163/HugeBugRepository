Title

interrupting build-runfiles prints a stacktrace

Description
If you hit Control-C while `build-runfiles` is executing, the following stacktrace will be printed:
```
ERROR: BUILD:2:10: Creating runfiles tree bazel-out/k8-fastbuild/bin/hi.runfiles failed due to build-runfiles failed: error executing command 
  (cd /home/benjamin/.cache/bazel/_bazel_benjamin/ /execroot/__main__ && \
  exec env - ): Process terminated by signal 15: Process terminated by signal 15
com.google.devtools.build.lib.shell.AbnormalTerminationException: Process terminated by signal 15
	at com.google.devtools.build.lib.shell.FutureCommandResultImpl.get(FutureCommandResultImpl.java:84)
... [Log Snipped] ...
	at java.base/java.util.concurrent.ThreadPoolExecutor$Worker.run(Unknown Source)
	at java.base/java.lang.Thread.run(Unknown Source)
```
Discussion
- Looks like this was introduced by @ulfjack in [URL] Fix should be trivial, test may be less so.
- Actually, it predates that commit: that commit just moved it from [URL] which says that it's intentional. So we just need to suppress it when the exception comes from an interrupt.
- One more correction: it is the fault of that commit. We used to only print the stack trace for IOException, now it's unconditional. This is kind of a mess, especially since EnvironmentalExecException has an "Exception" constructor.
- I have a pending fix, sent internally. The change to EnvironmentalExecException was maybe ok, on further reflection. I think it was an (unintentional?) behavior change, but since EnvironmentalExecException is only supposed to happen on "system" errors anyway, the right firs for this issue is just to make this exception not an EnvironmentalExecException, since it's a user-triggered failure. There's a separate question of whether EnvironmentalExecException should embed a stack trace or (probably better) log a stack trace to the info log and try to show the user something nicer.
