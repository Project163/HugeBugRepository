Title

Inconsistent bucket ordering using term aggregation

Description
**Elasticsearch version**: 
[5.1.2]

**JVM version**:
java version "1.8.0_112"
Java(TM) SE Runtime Environment (build 1.8.0_112-b16)
Java HotSpot(TM) 64-Bit Server VM (build 25.112-b16, mixed mode)

**OS version**:
macOS 10.12.2

**Description of the problem including expected versus actual behavior**:
```
{
  "size": 0,
  "query": {
    "bool": {
      "must": [
... [Log Snipped] ...
  }
}
```

I have a query (see above) that uses a term aggregation combined with a top-hits aggregation to achieve field collapsing. 
As suggested in the top-hits documentation an additional max-aggregation is used to sort the term buckets by their score.
This is working when the request is submitted using curl but NOT using the java API.

Using curl I can adjust the "size" of the term aggregation from x to x + y and the first x elements are sorted EXACTLY the same, which is needed for paging.
Using the java API the order is 1) different from the curl request and 2) changes when i adjust the size parameter.
In my case, the _score for every bucket is the exact same and using the java API the sorting doesn't seem to be stable.

I have found a workaround for my case using a second sort criteria as a tie breaker: 

```
"order": [
	{
	"top_hit": "desc"
	},
	{
	"_term": "asc"
	}
]
```
**Steps to reproduce**:
```
SearchRequestBuilder srb = buildSearch();
SearchResponse response = srb.execute().actionGet();
```
Using the SearchRequestBuilder I can copy the JSON request and execute it using curl.
Now I can compare the ordering of the buckets returned by curl and in the SearchResponse.

Is this a bug or am I doing something stupid?
Discussion
- If you are using the `TermsAggregationBuilder#order(Terms.Order)` method in your Java code to add just that single aggregation order then it would explain this behavior. The curl REST request parser uses the `TermsAggregationBuilder#order(java.util.List )` method instead which calls `order(Terms.Order.compound(orders));` internally (even if there is only one order). The `CompoundOrder` constructor checks if the last order is a tie-breaker, i.e. `_term`, **and if not adds term order ascending as a tie-breaker**. As you mentioned the `_score` is the same for some or all of the hits so without a tie-breaker the final order is undefined.

IMO this is a bug or at the very least unexpected/surprising behavior, especially given that we get different results for `SearchRequestBuilder#execute().actionGet()` vs using `SearchRequestBuilder#toString()` in the REST API.

@colings86 thoughts on this? Possible solution is to use a `CompoundOrder` if the single order is not a tie-breaker. Perhaps something I can do in #22343 ?
- @qwerty4030 I think we should just have `TermsAggregationBuilder#order(Terms.Order)` call `TermsAggregationBuilder#order(java.util.List )` with `Collections.SingletonList(Terms.Order)` and then the behaviour will be guaranteed to be the same for both cases?
