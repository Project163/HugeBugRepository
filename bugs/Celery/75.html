Discussion
- I think I found why this is happening. If you check the code of the Redis backend, you can see [Link: here] that the results are pushed in a Redis list. When [Link: all results have been gathered], the chord callback is executed, fetching the Redis list, without any other re-ordering. With parallel execution, the order of the results in the list will not be deterministic and the sequence of the stored results will be the same with the task execution sequence.

So, I am guessing that in order to maintain the order, the code would have to keep track of the sequence of the tasks when storing them in a Redis structure. Perhaps [Link: sorted sets] could be a solution here, setting the score to the task's group sequence index for example.

However, I am not sure that generally the order of task results from a group is guaranteed to be preserved by design, since they are executed in parallel, or if this happens to be a side-effect of the AMQP backend.
- Thank you for replying! Now it makes sense. But I actually forgot to mention one more point here. Redis, with Celery v3.x works properly, with the exact order of task results. So now I'm thinking, in the older version, celery might have been sending the results to backend, in the order its been assigned. But in v4.x, that process changed to sending the results in the order the task finishes.

Anyway, I finally used something similar to what you had mentioned to maintain the order. It seems like a dirty fix, but does the job.
