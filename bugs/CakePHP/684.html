Title

Http Client is not auto-sending application/x-www-form-urlencoded header

Description
According to [URL] doing the following should automatically set the `content-type` to `application/x-www-form-urlencoded`

``` php
$http = new Client();
$response = $http->post('[URL] [
  'title' => 'testing',
  'body' => 'content in the post'
]);
```

However, [URL] says otherwise, and [URL] goes even further and forces array form data to be `multipart/form-data` regardless of the `content-type` header set.

We either need to correct the docs, or at least document how to get an `application/x-www-form-urlencoded` request. Alternatively, the code needs to be changed.
Discussion
- Is there a problem if `mulitpart/form-data` is used? It defaults to that encoding as the various parts don't know if there are files hiding in the payload and defaults to a value that will always be safe.

I think changing the docs here might be the simplest thing unless there is an issue with defaulting to `multipart/form-data`.
- It might be safe to use multipart/form-data for POST requests (if the docs get updated), but an underlying problem with the Stream adapter is that it switches to multipart regardless of what method is being used. So if you make a PUT request and feed it an array (as in the documentation example that @dakota cited), it ends up getting submitted as multipart PUT request.

This is a problem, because PHP (on the receiving end) doesn't know how to handle that, and it may not even be legal under the HTTP spec: [URL]

I've got two Cake apps (one is a RESTful API, and the other is a web app that needs to talk to it). If I use Cake's HTTP client to make a PUT request to the API (and pass it an array as in the documentation's example), the API's $this->request->data is empty. For the moment, I'm working around this by wrapping my data array in http_build_query() before sending it to \Cake\Network\Http\Client::put().

- From the guzzle thread, guzzle now supports multipart/form-data requests with PUT, so I see no reason not to support it. We'll continue to bound by the limitation of needing to fit all fileuploads in PHP memory, but that isn't new.
