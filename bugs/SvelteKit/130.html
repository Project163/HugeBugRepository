Title

404 has the message "Internal Error"

Description
### Describe the bug

When you hit a route that doesn't exist, the error message is "Internal Error" instead of something like "Page not found". Pretty sure this used to be something like the latter though.

"Internal Error" is not something we should be showing to our users when it's just a simple 404 error.

### Reproduction

No custom code needed at all. Just create a new project `npm create svelte@latest sk-404-bug`, run it, and enter an unknown route in your browser.

Discussion
- This is the expected behavior. All unexpected errors (and 404 is such an unexpected one) are shown as "Internal Error" by default. You need to implement the `handleError` hooks on the server and client and return the desired error shape from it. In your case it's probably enough to do

```js
// hooks.server.js
export function handleError({error}) {
  return { message: error.message };
}
```
```js
// hooks.client.js
export function handleError({error}) {
  return { message: error.message };
}
```

It's done this way to protect your app from accidentally showing sensitive data that could appear from an unexpected error.

The docs have more info on this: [URL]
- It seems that the default behavior is kinda weird, forcing the normal happy path usage to implement two hooks or you get nonsensical error messages for even 404 pages. Why are those hooks not simply the default, and people can override it if needed?

- My initial feeling was that 404s shouldn't go via `handleError`, but @dummdidumm pointed out that `$page.error` would then have the wrong shape if you declare `App.PageError`.

So we _do_ need 404s to go via `handleError`, but we also need to be able to distinguish between 404s and 500s inside `handleError`. 

The maintainers discussed this a bit this morning and we decided that for now it's better to rely on `event.routeId` being `null` in the case of a 404:

```
js
export function handleError({ error, event }) {
  if (event.routeId) {
    // an unexpected error was thrown while handling this route
    console.log(error.stack);
... [Log Snipped] ...
  };
}
```

For the avoidance of doubt: this doesn't apply in the case of an _expected_ error...

```js
if (!item) {
  throw error(404, { message: 'not found', code: 'NOT_FOUND' });
}
```

...since these errors already have the right shape.

Aside: `App.PageError` is probably the wrong name, since the error could come from `handle` or a `+server.js` file. It should probably just be `App.Error`.
- @Rich-Harris Do you think it makes sense to return `App.PageError` from the server side `handleError` function, to allow to return another HTTP status code than 500? I see the `handleError` as a global error handler for all the server side code. If I throw a specific error in my API that some thing could not be found, I would like that the error handler catches the error, logs it and then still returns 404 to the client. Currently I think this is not possible. I could create an issue if you think this makes sense.
