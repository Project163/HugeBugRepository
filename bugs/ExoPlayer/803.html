Title

Sequence check in RtpH264Reader.processFragmentationUnitPacket skips packet number 65,535

Description
Hi,
IMO the check in [URL] skips and drops new packet number 65,535. The current calculation yields 0 for previousSequenceNumber = 65,534, however the next packet has number 65,535, while its successive packet has 0.

IMO the calculation should be

`int expectedSequenceNumber = (previousSequenceNumber + 1) % (RtpPacket.MAX_SEQUENCE_NUMBER + 1);`

Thanks a lot for considering the change.

Best regards,

Pavel.
Discussion
- Actually my RTP camera sends packets numbered from 1 to 65,535 which requires the check to be
int expectedSequenceNumber = (previousSequenceNumber % RtpPacket.MAX_SEQUENCE_NUMBER) + 1;

It's possible other RTP sources send numbers from 0 to 65,534 for which the existing code is correct. So I will just modify my local exoplayer source.

Thanks,

Pavel.
- It is indeed problematic, will fix.
- Thanks a lot. I could not find any official specs for the packet numbering, just that it's 16bit and numbers should be sequential. Maybe some devices start with 0, some with 1 (my camera). It would be surprising if some ended at 65,534, IMO 65,535 is the most logical value.
