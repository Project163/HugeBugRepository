Title

WebUI updated even if server has not processed changes

Description
The WebUI updates based on changes made to settings by the user before those changes have been processed by the server. This causes the user to assume the changes have been saved when they are not.

Background: I am running Syncthing on a slow machine. Whenever I make changes to folder settings, the WebUI changes to reflect these, giving the impression that the changes were made and have been saved. However, the changes are sent to the server asynchronously and on a slow machine it may take a very long time for them to be processed (separate bug filed for that). If I leave the webpage, the changes may not be applied on the server even though I was led to believe they were.

Workaround: leave the WebUI page open for a long time (half an hour should do) and hope the requests will get processed at some point, then refresh to see the real state.

### Version Information

Syncthing Version: v0.14.54, Linux (ARM)
OS Version: Linux 4.14.69+ on Raspberry PI
Browser Version: Tested with Firefox and Chrome; issues appears to be server-side.
Discussion
- Alternative, more reliable and faster work-around: shut down Syncthing, edit `~/.config/syncthing/config.xml` to make changes to settings, restart syncthing.
- Can you be more specific about what changes, etc? Generally speaking the GUI updates based on a "config changed" event from the backend, which gets emitted when the config has been applied successfully. Even if the commit takes time it should not, afaik, be aborted if the browser goes away in the meantime.
- Wrt. Changes: There are various folder settings that are shown in the main page. I was changing folder type from "Send & Receive" to "Receive only", which changes the folder icon in the main page immediately. I did not check but expect that changing settings such as "Folder Label" and "Shared With Devices" will also result in immediate changes to the main page.

Wrt. requests being dropped: I assume your server has a timeout on processing requests, which would be the main concern (I am seeing HTTP 500 responses sometimes but these do not mention timeout). The server may also discards queued requests as soon as the connection to the client is dropped (which might make sense in some case because it cannot send a response). If so, navigating to a different page or closing the tab would result in the browser closing the connection and the server never processing the requests. I am not familiar with how the Syncthing HTTP server works but I can tell you that changes I made in the WebUI were not applied after more than 15 minutes and the only way to find out was by refreshing the page to update the UI to the actual values.
- (From memory)

I guess we update scope.options with tmpOptions and call scope.save that is not parameterised, so if the request fails we're left in the dark.

I mean both things are equally bad, pressing save, dialog closing and settings changing back without the user noticing doesn't help the situation either.
