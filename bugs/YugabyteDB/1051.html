Title

[DocDB] Indexes grow in size even after rows are deleted, leading to slower queries.

Description
Jira Link: [Link: DB-8331]
### Description

The metadata of the index on the TServer is inconsistent with that of the Master process. TServer believes that the index build is not complete ( bit - retain_delete_markers is set), while according to the Master, the index build is complete. 

This inconsistency results in the following - **Compactions (automatic or manual) do not get rid of the delete markers (even if they are beyond the history retention window). This results in an ever growing storage for the indexes (hash/range), primarily if there are lots of deletes or overwrites to the index. Doesn't affect cases where index is primarily getting new entries.** 

**Impact**

- The issue is a regression from commit - 660e13af (2.14.0 builds onwards)
- Impacts both the YCQL and YSQL api, for all new indexes created on universes of version 2.14.x/2.16.x/2.18.x. (Note that if a customer had created indexes on 2.6 or 2.8 and then upgraded to 2.14.x, it doesn’t impact such indexes.).
- Note: If the index is only getting new entries (not update heavy), then this issue is not relevant.
- Performance Impact: Index performance - specifically the range scans on them degrades over time due to the bug (if the indexes get a lot of deletes/overwrites). Point lookups using indexes should not observe performance regression due to this.
- Compactions (full/scheduled/manual) of such indexes also take longer and longer as time proceeds.
- Space Impact: The disk consumption of affected indexes steadily increases, due to the accumulation of the delete markers.
- Databases backed up from 2.12 (or lower version) and restored to 2.14/above are not impacted.


**Scenario that was originally reported**

After some time, we've observed that range indexes (particularly on `updated_date` fields) appear to see additional growth in the SST files even after compaction.  We've observed this in at least 2.16 and 2.18.

- Update from @arybochkin's diff.

Schema table properties' field retain_delete_markers is not updated properly on index backfilling is done on tablet server side. This leads to using of HT  as a min time to check if tombstones should be removed from SST file. And as this is the min possible time, they are always kept in SST files during compaction and it's even not possible to remove them with manual compactions and with a help of tserver restart as the parameter retain_delete_markers is persisted as true and no other backfill done events can happen on an index table created and marked as backfilled.

The issue is a regression from 660e13af. On getting a backfill done event we were copying the current schema and were adding exactly one change: new_schema.SetRetainDeleteMarkers(false) and then metadata->SetSchema(new_schema). But the new schema was not applied as a subsequent call to TableInfo constructor with new_schema as an argument was ignoring a new schema as it has a requirement to have a different schema_version to make new schema be applied.
