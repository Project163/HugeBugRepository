Title

[docdb] [Pessimistic Locking] Running transaction status waiter resolution causes livelock with pessimistic locking enabled

Description
Jira Link: [Link: DB-3956]
Code in `conflict_resolution.cc` and `wait_queue.cc` can live lock with each other in the following scenario:

t0 -- Call RequestStatusAt for   here: [URL]
a request is sent to the coordinator async

t1 -- Call RequestStatusAt for   here:  [URL]
the callback is stored on the status_waiters_ of the running transaction

t2 -- RPC returns for   and status_waiters_ are invoked in order

In this case, the wait_queue.cc callback is triggered first, in which we may attempt to acquire a `LockBatch` before re-running conflict resolution for a waiter. However, if the `LockBatch` for the requested key is already held by conflict resolution, it won't be released until the status_waiter_ corresponding to conflict resolution is resumed, which won't happen until the lock acquisition in wait_queue.cc times out
