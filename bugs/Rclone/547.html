Title

tardigrade integration tests failing - range requests not working properly

Description
The integration tests for [Link: tardigrade are failing] like this

[Image: image]

The failures all look related and to do with Range requests failing.

The first one is easy to demonstrate

```
$ cd backend/tardigrade
$ go test -v -run TestIntegration/FsMkdir/FsPutFiles/ObjectOpenRange
=== RUN   TestIntegration
    TestIntegration: fstests.go:356: Using remote "TestTardigrade:"
=== RUN   TestIntegration/FsMkdir
... [Log Snipped] ...
exit status 1
FAIL	github.com/rclone/rclone/backend/tardigrade	2.588s
```

The ultimate cause here seems to be the `ranger error: buffer runoff` from the tardigrade libraries

Here is the test in question

[URL]

It is this test which fails `{fs.RangeOption{Start: 81, End: 100000}, 81, 100}` so it looks like the backend needs to clip the range at the size of the file.

Here is the code in question

[URL]

It looks like we need to read the size of the object for the `s && e` case too.

@calebcase I remember you didn't want to read the size of the object if you didn't have to. Do you think it is acceptable to read it here?

This will likely mean that all range requests read the size of the object, so maybe we should use the built in fs.FixRangeOption ?

Or is this something best fixed in the tardigrade libraries?
Discussion
