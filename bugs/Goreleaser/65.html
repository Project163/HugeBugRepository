Title

Docker section not finding binary

Description
**Describe the bug**

After the recent release of goreleaser v0.132.0, it seems that the `dockers` section can no longer find my templated binary name (though it can find it just fine in v0.131.1).

**To Reproduce**

```
yaml
# This is an example goreleaser.yaml file with some sane defaults.
# Make sure to check the documentation at [URL]
project_name: gowebapptemplate

... [Log Snipped] ...
      - "--label=org.label-schema.schema-version=1.0"
      - "--build-arg=BIN={{ .ProjectName }}"
```

**Expected behavior**

Goreleaser should be able to find a binary by templated name.

**Environment (please complete the following information):**

- OS: Docker
- GoReleaser Version v0.132.0

**Additional context**

```
none
   • releasing using goreleaser 0.132.0...
163    • loading config file       file=.goreleaser.yml
164    • running before hooks     
165       • running go get           
... [Log Snipped] ...
00:01
241 ERROR: Job failed: exit code 1
```
Discussion
- After a lot more trial-and-error, I think I've narrowed down the scope of the problem. It seems like the problem only manifests if a templated value is used in the `builds[].binary` section. For example, the docker pipeline in this `.goreleaser.yml` works just fine:

```
yaml
project_name: gowebapptemplate
builds:
  - 
    goos:
... [Log Snipped] ...
    image_templates:
      - "terrabitz/{{ .ProjectName }}:latest"
```

However, this `.goreleaser.yml` says that it can't find the binary during the docker phase:

```
yaml
project_name: gowebapptemplate
builds:
  - 
    goos:
... [Log Snipped] ...
    image_templates:
      - "terrabitz/{{ .ProjectName }}:latest"
```

This problem seems to be isolated to using a templated value like `"{{ .ProjectName }}"` in `builds[].binary`. For example, the following works just fine

```
yaml
project_name: gowebapptemplate
builds:
  - 
    goos:
... [Log Snipped] ...
    image_templates:
      - "terrabitz/{{ .ProjectName }}:latest"
```
- ~~`builds.binary` should not be templateable actually, it cause this issue (and possible others where the binary is referenced directly)...~~
