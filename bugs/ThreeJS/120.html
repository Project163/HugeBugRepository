Title

Euler.setFromQuaternion() produces incorrect results for <0.1% of possible quaternions.

Description
So I found the source of a long standing issue in [URL] which of course uses Three.JS.  It isn't yet fixed in production, but I know where it is coming from.

Basically `Euler.setFromQuaternion()` produces the wrong result on about 0.1% of possible quaternion values.  When it screws up it disagrees with the result of creating a `Euler` from a `Quaternion` via an intermediate `Matrix4`.

Here is an example that shows the disagreement on a problematic quaternion value.  Normally there is no disagreement between these two conversion routes from quaternion to euler, but if they do disagree, the eViaQ1 conversion method is wrong, while the eViaMViaQ1 conversion method is correct.

This bug has been around a long time and it is in the most recent version of Three.JS as well.

```
var eulerOrder = "ZYX";

// known problematic quaternions
var q1 = new THREE.Quaternion( 0. , -0. , 0.520776938524434, 0.  );
var q2 = new THREE.Quaternion( 0. , 0. , -0. , 0.  );
... [Log Snipped] ...
console.log( eViaQ1 );  // this result is wrong
console.log( eViaMViaQ1 );  // this result is correct
```

This appears to be a numerical issue. And, unfortunately, if it happens with "ZYX", it will be easy to construct equivalent cases with other Euler orders.

In `Euler.setFromQuaternion()`, up to rounding error, we end up making this call

```
Math.atan2( 0, 0 );
```

It is easy to construct problem quaternions:

```
var a = Math.random();
var b = Math.random();
var q1 = new THREE.Quaternion( a, -b,  a, b ).normalize(); // pattern 1
var q2 = new THREE.Quaternion( a,  b, -a, b ).normalize(); // pattern 2
```
