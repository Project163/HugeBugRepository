Title

Window not opaque on some wayland compositor

Description
GLFW windows on swaywm and rootston are always transparent.
Current method to make sure window is opaque, set_opaque_region, according to wayland protocol description, is just an optimization hint. I don't think it would necessarily make window opaque.
According to [Link: wayland mailing list], the proper way to make it opaque is to use a buffer without alpha channel.
To reproduce, comment out the transparent framebuffer hint line in the gears example and run it on swaywm or rootston.
Although it can be fixed by manually calling glfwWindowHint(GLFW_ALPHA_BITS, 0), I think this should be default on wayland.
Discussion
- The issue with that is how the Wayland code and the EGL code are completely isolated inside of GLFW. This is useful for Vulkan for instance, which doesn’t use EGL at all, or when you ask for no context during window creation.

Another issue with changing the framebuffer configuration before EGL initialisation is that some programs may expect to have an alpha channel if they require one and store things into it, even if it isn’t used for composition.

I’m not sure how to solve this issue, which also happens for Vulkan I guess, so I’ll leave this issue open for other people to chime in.
- I just began using GLFW, so correct me if what I'm saying is non-sense, but I don't understand what is wrong with the current behaviour. When I initialise a window, it is by default, completely transparent. I can then use OpenGL to add colours with alpha set to unity if I want opacity. Is that not so?

- What you should do is use an RGBX config instead of a RGBA one, that way the alpha bits will correctly get ignored on all platforms.

A possible fix would be to override the config parameters on window creation, but then if the application is storing bits in the alpha part they will be undefined IIRC, which might not be what they wanted to do.
- This is now fixed, when using drivers which expose the `EGL_EXT_present_opaque` extension, such as Mesa.
