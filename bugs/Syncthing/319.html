Discussion
- I'm guessing what happens here is that the puller is torn down and a new one is created when we retry. The new puller has less blocks available because it hasn't checked the entire temp file yet. When the progress emitter polls everything and send it to the download progress tracker thingy, it sees a puller for a file it already knows about and assumes it must have made progress (the comment above the panicing line says as much). But that assumption doesn't hold as it's actually a _new_ puller for the same file name.
- Yes, writing a fix now.
- ... [Middle Discussions Snipped for Brevity] ...
- And I still haven't reproduced the completion > 100% thing yet under controlled circumstances, even though I'm uncovering other interesting corner cases in the process...

I'm interested in the "retrying" parts because for people to reach percentages in the millions it really needs to be something that happens time after time, like blocks being added to the list every time we retry but never get removed. Except that doesn't actually happen that I can find...
- This is not the right fix tho, as it's still possible to get a file pulled in a different order and able to pull more blocks than what we had before.
