Discussion
- It is looking like a data race due to which a value of `DocDBRocksDBUtil::doc_read_context_` can be initialised with a new allocation more than once, but its content is accessed without any protection, directly or via `DocDBRocksDBUtil::doc_read_context()`. For example:
```
Result  DocDBRocksDBUtil::CotablePacking(
    const Uuid& table_id, uint32_t schema_version, HybridTime history_cutoff) {
  if (schema_version == kLatestSchemaVersion) {
    schema_version = 0;
  }
... [Log Snipped] ...
  };
}
```
For the line `.schema_packing = rpc::SharedField(doc_read_context_, &packing),`, the value of `packing` can belong to the old instance preempted in  `doc_read_context()` by another thread. The same is fair for the last line, where `doc_read_context_` and `doc_read_context_->schema()` can belong to a different instances of doc_read_context_.
In accordance with logs:

Several compactions are running the same time from different threads, however the DocDBRocksDBUtil instance (as the implementation of SchemaPackingProvider) does not protects data from an access from multiple threads. TSAN is either does not detecting the issue or does not complaining because of
```
  ANNOTATE_IGNORE_READS_BEGIN();
  auto& packing = VERIFY_RESULT_REF(
      doc_read_context().schema_packing_storage.GetPacking(schema_version));
  ANNOTATE_IGNORE_READS_END();
```
As of now `DocDBRocksDBUtil` is used for tests and bulk load tool, so both of these areas are potentially impacted by the issue. In addition to SchemaPackingProvider's methods, the implementation of at least `DocDBRocksDBUtil::doc_read_context()` should also guarantee thread safety.
Additionally, all other implementation of `SchemaPackingProvider` should be checked for thread-safetyness or their usage should be thread-safe.
