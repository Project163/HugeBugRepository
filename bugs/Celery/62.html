Title

AsyncResult.get() stuck in high cpu usage

Description
celery  4.2.1
gevent  1.3.5 
redis-py 2.10.6

With gevent.monkey.patch_all(), when try to get result of a delay executed task(shutdown worker or make task in long pending task queue), result.get() will cause very high cpu usage on the producer side.

Tested on python2.7 and python3.6, both have this issue.

Test script:

```
import gevent
import gevent.monkey
gevent.monkey.patch_all()

import time
... [Log Snipped] ...
ret = dummy.delay()
ret.get()
```
strace -p {pid}, get:

```

epoll_wait(3, [], 64, 1)                = 0
getpid()                                = 10484
epoll_wait(3, [], 64, 1)                = 0
getpid()                                = 10484
... [Log Snipped] ...
epoll_wait(3, [], 64, 1)                = 0
getpid()                                = 10484
```
It's flushing very quickly, seems gevent is checking something actively, after debuging, I find `ret.get()`  stucked in  `[URL]

If  change it to `sleep(0.1)`,  high cpu usage go way. Not sure what sleep(0) does here.
Discussion
- Why `greenletDrainer` is bypassing the `wait_for` method of the consumer?
Why we don't just use the the pub/sub of redis instead of looping with sleep(0) and destroying CPU?
- ATM in our fork we increased `sleep(0)` to `sleep(0.001)` and the CPU usage dropped, this should be configurable from `interval` and I was going to do a PR, tell me if you don't have time I can do it.

Yes, I didn't see the `run()` method, but now the question is: Why we don't execute the `run()` logic in the main greenlet and remove the loop with the sleep and just loop every timeout? Gevent should take care of releasing control during I/O, I'm missing something?
- We ran into this during a recent attempt to upgrade our servers to Celery 4.  This caused high CPU for all processes running in gevent where it waits on a result that isn't ready yet.

It looks like what's happening is that in the base `Drainer` class, it runs wait_for in a loop:
[URL]

Both gevent and eventlet have the following implementation where wait_for starts the drainer (only executed the first time) then runs a `sleep(0)`.  This causes the high CPU as observed in the original test script.

I think what should be happening instead is a call to the wait() function which has a passed in timeout so on_interval() still gets executed, something like:

```python
class geventDrainer(greenletDrainer):

    def wait_for(self, p, wait, timeout=None):
        from gevent import wait
        self.start()
        if not p.ready:
            wait([self._g], timeout=timeout)
```
- Actually, maybe we be using the passed in `wait` function in wait_for.  It doesn't look like we're currently using it at all now.

EDIT: This doesn't seem to be possible for Redis since gevent throws an error trying to share the pubsub socket between greenlets.
