- DELETE_ON_CLOSE  is a bad idea on a file used by different processes.  There's no guarantee that the file won't be deleted before close.  On linux, the file has not yet been closed in the delete_on_close process, and that process can still see and write to the file, but at the same time the other process can't find the file.  The behavior is different on Windows. 

   I tried a number of options, and I found it very hard to guarantee that the tmp file was deleted and that nothing seriously bad happened when two processes shared the tmp file when I shared a memorymapped file between processes  and  I had to allow either or both processes to be killed.  Different platforms handle the details in different ways. 

 For now, I've chosen the simplest option, which is the writer opens the file, waits for trylock, writes the status and closes the file.  The reader does the same.  This appears to avoid synchronization issues within a process (if more than one thread calls close()) and across processes.  I'm sure that we can improve the efficiency of this at some point, but it just shouldn't matter.
