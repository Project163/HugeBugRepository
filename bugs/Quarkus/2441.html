Title

Default property values for syslog logging

Description
### Describe the bug

The default values for syslog logging cause log messages not to be accepted. This was tested when using Keycloak. The original [Link: issue] was raised with Keycloak and redirected here. 

The issue comes down the [Link: quarkus.log.syslog.use-counting-framing] flag. When the [Link: quarkus.log.syslog.protocol] parameter is set to `tcp` or `ssl-tcp`, RFC5424 states that byte counting framing should be used. For Quarkus, this means also manually setting the [Link: quarkus.log.syslog.use-counting-framing] flag (which Keycloak does not have a proxy option for).

When sending logs to a receiver such as syslog-ng without the flag, these log messages are rejected with an 'invalid framing' error and the connection is dropped.

### Expected behavior

The request here is to automatically set [Link: quarkus.log.syslog.use-counting-framing] to `true` if the [Link: quarkus.log.syslog.protocol] parameter is set to `tcp` or `ssl-tcp`. It should be possible to override this manually in case there are specific edge cases not following RFC5424.

### Actual behavior

Presently, when using syslog logging, the  [Link: quarkus.log.syslog.use-counting-framing] must be manually set. In Keycloak, this is performed by setting the quarkus.properties. This is something that is recommended against in the [Link: documentation]

### How to Reproduce?

1. Setup a syslog receiver (see example on the [Link: Keycloak issue]). 
2. Set the approvriate log flags
* [Link: quarkus.log.syslog.enable]=true
* [Link: quarkus.log.syslog.endpoint]=localhost:514
* [Link: quarkus.log.syslog.app-name]=example
* [Link: quarkus.log.syslog.facility]= local-use-0
* [Link: quarkus.log.syslog.syslog-type]=rfc5424
* [Link: quarkus.log.syslog.protocol]=tcp
3. Create logging events

Discussion
- @dmlloyd @jamezp WDYT?
- Seems reasonable. We could solve this in one of two possible ways:

* A dynamic default configuration source which sets the default to `true` or `false` depending on the selected protocol
* Change the property to a `enum` with values `TRUE, FALSE, PROTOCOL_DEPENDENT`

The *most* correct answer would be to research the RFCs and prevent invalid configurations instead of exposing every knob (an anti-pattern which leads directly to user confusion and, ironically, inflexibility). But that ship has sailed in this case.

It might be tempting to make this property be an `Optional `. This would be an error.
- A little OT, but I wonder if we should deprecate RFC-3164 as it's been obsolete for over 14 years now :)
