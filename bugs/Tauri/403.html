Title

[bug] fs `readDir` fails for `BaseDirectory.Home` root with "Access is denied. (os error 5)", even as Admin

Description
### Describe the bug

**What doesn't work:**
Using `readDir('', { dir: BaseDirectory.Home, recursive: true })` on Windows throws  
`path:  : Access is denied. (os error 5)`.

**What this means:**
This suggests that the user does not have access to ` ` which can not be the case, since using `recursive: false` succeeds.

**Possible cause:**  
The error is thrown because the user doesn't have access to some subdirectory of ` ` and trying to read that directory failed.

**Why this needs fixing:**  
- The error doesn't tell which directory failed; it always uses the ` `. This makes debugging impossible.
- There is no way to obtain the entries that _didn't_ fail. This makes a `readDir` invocation useless.

### Reproduction

```
js
import { readDir, BaseDirectory } from '@tauri-apps/api/fs';

async function test() {
  // Empty string as dir parameter
... [Log Snipped] ...

await test();
```

### Expected behavior

- Only throw an error if the root directory of `readDir(rootDir, { recursive: true })` can not be read
- When throwing an error, use the path of the directory that _actually_ failed instead of the root directory
- Include the problematic subdirectory in the result but set `subdirectory.children = [];` (`'empty'`)
- Exclude the problematic subdirectory from the result (`'exclude'`)
- For backward compatibility, add `errors?: 'throw' | 'empty' | 'exclude'` to type `FsDirOptions` (defaulting to `'throw'`)

```
js
/**
 * List directory files.
 * @param {string} dir
 * @param {(import("@tauri-apps/api/fs").FsDirOptions & {errors?: "throw" | "empty" | "exclude"}) | undefined} options
... [Log Snipped] ...

```

**Usage examples with `readDir`:** -- You probably don't want this  
```js
// Throws "path:  : Access is denied. (os error 5)"
await readDir('', { dir: BaseDirectory.Home, recursive: true });
```

**Usage examples with `_readDir`:**  
```
js
// Throws "path:  : Access is denied. (os error 5)"
await _readDir('', { dir: BaseDirectory.Home, recursive: true });
await _readDir('', { dir: BaseDirectory.Home, recursive: true, errors: "throw" });

... [Log Snipped] ...
// Returns a FileEntry[] or null if access to the root directory is denied
await _readDir('', { dir: BaseDirectory.Home, recursive: true, errors: "exclude" });
```

2023-07-10: Fixed `"exclude"` mode:
```
diff
  if (!recursive)
    return entries;
-  for (let [i, entry] of entries.entries()) {
+  for (let i = 0; i < entries.length; i++) {
... [Log Snipped] ...
+       entries.splice(i--, 1);
    }
```
- Code updated to fix `"exclude"` mode. Previously, if an error occured and an entry was excluded, the next entry was skipped because the index of all the next entries was reduced by one during the `splice` operation and thus the next entry got the same index as the current entry.
- Ignoring errors is dangerous and shouldn't be done by the framework, maybe by the application depending on the use case. We should have better error information though.

For instance this is the error message from Node.js for a recursive directory read: `Error: EACCES: permission denied, scandir '/home/lucas/Downloads/x/b'`.

Also be careful reading the home directory recursively, it might have millions of files :)
- I use recursively reading the home directory in a user-invoked search for a directory with a very specific naming scheme and manually selecting said folder is still the prefered option.

I understand the risks of recursively reading directories with potentially millions of files which is why I second your opinion. As a user-invoked feature the user experience benefit of not having to look for the directory manually outweighs the possible resource and time consumptions a recursive `readDir` might have in my opinion.
