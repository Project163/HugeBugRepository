Title

Problems when using a mixture of Not and Or filters in NUnit framework 3.12.0

Description
In short, the NUnit 3 framework does not select the correct tests when using a filter like `!(test!='Some.Namespace'|...)`.

To give a minimal example, suppose that I have an assembly (referencing NUnit framework 3.12.0) with 1 test, called `Namespace.Fixture.Test`, without any attributes (and hence no categories). Running the tests with the filter `!(test!='Namespace.Fixture'|cat=='X')` will execute 0 tests. However, if it references NUnit framework version 2.6.4, it runs the test `Namespace.Fixture.Test`.

This is, of course, a very contrived example, and an easy workaround is to apply De Morgan and use the filter `test=='Namespace.Fixture'&cat!='X'`.

I believe that this relates to issue #3231.

I have tested this with version 3.10.0 of the console runner, installed with Chocolatey, as well as version 3.7.0 of the NUnit V2 Framework Driver, installed the same way. Moreover, I have added [Link: FilterTest.zip] with projects producing assemblies `NUnit2FilterTest.dll` and `NUnit3FilterTest.dll` containing the test mentioned above and referencing NUnit framework 2.6.4 and NUnit 3.12.0, respectively.  After building the projects, the problem can be reproduced with:
```
nunit3-console.exe NUnit2\bin\Debug\NUnit2FilterTest.dll --where "!(test!='Namespace.Fixture'|cat=='X')"
nunit3-console.exe NUnit3\bin\Debug\NUnit3FilterTest.dll --where "!(test!='Namespace.Fixture'|cat=='X')"
```
Discussion
- This is only somewhat related to #3231, which dealt with two Not filters directly nested. The fix for that was to simply drop both of them. Here we have ` >  >>>` so a more substantial fix is probably needed.

We really need a test that demonstrates this to be a framework problem. Running through the console opens up the possibility that either the console is generating an incorrect filter from the `--where` clause or the framework is misinterpreting the filter. For the V2 example, the V2 driver, which translates the NUnit 3 filter to a a V2 filter, also comes into play. Ideally, we want a framework test that creates the filters programmatically and applies them directly. We already have some tests like that, but not for this specific case.
- Also sounds related (or at least similar) to nunit/nunit-v2-framework-driver#21.

- The problem seems to be that, like intuitionistic logic, "not" isn't the opposite of "", and that "not not not" is semantically equivalent to "not", but "not not" isn't to "".

The reason is that "not" has different search behaviors, i.e. it would stop as soon as its inner condition matches, while "" continues searching.

One possible solution might be to detect a situation where a De-Morgan or similar would lead to "not not" and then execute that transformation (and remove the resulting "not not"). But it obviously changes semantics and might [Link: break someone's workflow.]
