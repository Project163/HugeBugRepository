Title

Any load options break `with_entities()` in 1.4

Description
**Describe the bug**
Very similar to #6052 (which is supposedly fixed?), applying any loader option breaks `with_entities()`.

**Expected behavior**
No error, this output from the test script:

```
normal
[ ]
with entities + noload
[(1,)]
with entities + joinedload
[(1,)]
```

**To Reproduce**

```
py
from sqlalchemy import *
from sqlalchemy.ext.declarative import declarative_base  # to test on 1.3
from sqlalchemy.orm import *

... [Log Snipped] ...
print('with entities + joinedload')  # fails
print(s.query(Thing).options(joinedload('owner')).with_entities(Thing.id).all())
```

**Error**

```
pytb
normal
[ ]
with entities + noload
Traceback (most recent call last):
... [Log Snipped] ...
    raise sa_exc.ArgumentError(
sqlalchemy.exc.ArgumentError: Query has only expression-based entities - can't find property named "owner".
```

**Additional context**

The example script is minimal, hence the "strange" usage of `with_entities`. In my real application the query is coming from a util function which applies a joinedload option, and overriding it with a noload doesn't help because *any* load option triggers this bug.

**Versions.**
 - OS: Linux
 - Python: 3.9.1
 - SQLAlchemy: 1.4.7
 - Database: Postgres
 - DBAPI: psycopg2
Discussion
- this is not a new behavior.  try this in 1.3, same error:

    s.query(Thing.id).options(noload("owner")).all()

the difference is that Query now processes all the options and everything at the end:  [URL]

this behavior is critical for performance.

I don't have a way to "fix" this other than just to ignore all invalid loader options in all cases, which seems bad also.
- the best we could do is add some kind of "don't warn for any options" flag if with_entities() is called, but that seems pretty hacky too.
- ... [Middle Discussions Snipped for Brevity] ...
- **Mike Bayer** has proposed a fix for this issue in the **master** branch:

**memoize current options and joins w with_entities/with_only_cols** [URL]
- as noted in the above gerrit and issue #6503, I took the elaborate approach which is that the "_options" and the "_joins" etc. are all stuffed into a brand new kind of object that is pushed onto a stack whenever with_entities() or with_only_columns() is called.   that new object then participates in all the caching, adaption, etc. and serves as the previous version of the query before the entities were changed.   then the joins/options are processed in terms of the entities they were made against.


it's a very high ratio of complexity added vs. API surface, but we're getting more consistent complaints about this one.
