Title

wired behavior for grok processor with multiple patterns

Description
**Elasticsearch version**: 5.0.0

**Plugins installed**: ["x-pack"]

**JVM version**: 1.8.0

**OS version**: CentOS 7.0

**Description of the problem including expected versus actual behavior**:
If there is only one patterns in grok process, it works.
but if there are two or more patterns, and one doc match the second pattern, the result is not completed

**Steps to reproduce**:
 1. test with the following config:
```
POST _ingest/pipeline/_simulate
{
  "pipeline": {
  "description" : "parse log",
  "processors": [
... [Log Snipped] ...
  ]
}
```

the result is:
**Note that the second doc was partially parsed**
```
{
  "docs": [
    {
      "doc": {
        "_index": "_index",
... [Log Snipped] ...
  ]
}
```

 2.
if using only one pattern, I only delete the first patten and the first doc, nothing changed:
```
POST _ingest/pipeline/_simulate
{
  "pipeline": {
  "description" : "parse log",
  "processors": [
... [Log Snipped] ...
  ]
}
```

the result is:
```
{
  "docs": [
    {
      "doc": {
        "_index": "_index",
... [Log Snipped] ...
  ]
}
```

Discussion
- @talevy any ideas what is happening here?
- In particular see this in the second (one doc one pattern) request:

```
"parse_error": "field [_grok_match_index] not present as part of path [_ingest._grok_match_index]",
```
- from initial view, I think it is because `trace_match` is set to `true` while there only being one pattern. `trace_match` is used to keep track of which of the multiple patterns matched the field, if there is only one, the behavior around this is different since there is nothing really to trace. This was meant to be as an optimization, but is probably the cause of this behavior.

I'll open a PR shortly to fix this. I suppose trace match should still work even though there is one pattern.
- @talevy could you also look at improving the docs for `trace_match` - it's not obvious from the wording what this feature should be used for.  thanks
