Title

Regression: Helm 3.18.6 fails during schema validation with `no URLLoader registered`

Description
### What happened?

```console
$ helm template ./mychart
02:33:45  Error: values don't meet the specifications of the schema(s) in the following chart(s):
02:33:45  dependency-a:
02:33:45  failing loading "urn:example:helm:schemas:v1:helm-schema-validation-conditions:v1/helmSchemaValidation-true": no URLLoader registered for "urn:example:helm:schemas:v1:helm-schema-validation-conditions:v1/helmSchemaValidation-true"
```

### What did you expect to happen?

To work as it did in 3.18.4. 3.18.5 did not work because of [Link: this].

### How can we reproduce it (as minimally and precisely as possible)?

I haven't built a minimal reproduction yet, and the chart is private.

- Maybe caused by this change?
[URL]
- Same error for me, seen in helm 3.18.6 and 3.18.5.

While the 3.18.4 is working fine.
- I dig into this subject and it was not easy to figure this out.

There is a [Link: json library migration in 3.18.5] that means that json schema is stricker now. What I understand is 3.18.4 didn’t check external URNs unless validation walked into them (and/or they were preloaded).
3.18.5’s loader wiring made external $refs compile-time strict, exposing the missing urn handler.

It seems that URN handling for external reference is not easily possible. We have to use [Link: `addResource`] in Go code to dynamicaly loading other related json files. Same-document URNs (schema has $id: urn:… and refs use urn:…#anchor) work without a loader; only external URNs need AddResource/loader.
I played with the cli tool of the new jsonschema lib and I was not able to trick the schema to use an external json expect using `--map` (see: [URL]

While reading your comment (I don't know if you own this chart), it seems that the error is on an "example". Could it be removed completly? Few options:
- Remove reference
- Put it into the value.schema.json
- Point to the other json using ./file-location.json instead of an URN.

Stil I've made a pull request that we will follow the same behavior as before. Do not expose error when it can be resolve, instead add a warning.
- Is this fixed in Helm 3.19? I guess not since #31240 and #31247 are still open. This issue seems to be affecting Flux users: [URL]
