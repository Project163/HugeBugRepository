Title

strange sftp memory leak w/ v. 8.14.1 (possible regression from 7.88.1?)

Description
### I did this

Running the Whitebox tests of an application using libcurl for sftp on Debian Trixie (libcurl version 8.14.1), Valgrind reports memory leaks which do not occur on Debian Bookworm (libcurl version 7.88.1).  The issue seems to occur only if at least one sftp transaction fails (not sure, though).

Please see the file `curl-test-sftp.c` in the attached package [Link: curl-sftp-issue.tar.gz] for a minimal test case; I *think* the function `do_transfer()` uses the easy API properly – please correct me if I'm wrong!

To simplify the test, the package includes a shell script which
1. creates a dummy user (beware – requires `sudo`!),
2. runs a dummy sftp daemon at port 65022 (beware – `sudo` again!),
3. runs the aforementioned test application in Valgrind, producing one failed, one good, and again one failed transfer, and
4. cleans up steps 1 and 2.

Note that (on Debian) the packages `openssh-server`, `valgrind` and `libcurl4-gnutls-dev` are required.

This produces the following output:
- on Bookworm/7.88.1: [Link: Bookworm.log] – everything is fine
- on Trixie/8.14.1: [Link: Trixie.log] – the memory leak.

### I expected the following

…no memory leak on Trixie, as on Bookworm 😉 

Did I miss something in my code, or is this an issue in libcurl?

TIA, Albrecht.

### curl/libcurl version

- Bookworm: libcurl 7.88.1
- Trixie: libcurl 8.14.1

### operating system

Debian Bookworm and Trixie, respectively, with all updates as of today installed.
