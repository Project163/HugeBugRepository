- I tried the code snippet on `develop` branch and it does NOT have the `client_state` failure anymore but still seems to infinitely rerun until it hits the run timeout. @AnOctopus can you take a look at this?
- Repeated calls to **streamlit.rerun()** overflow the stack because of tail recursion inside **script_runner._run_script**. This is easily fixed by someone changing this code in **script_runner.py**:

In

**def _run_script(self, rerun_data: RerunData) -> None:**

after

      assert self._is_in_script_thread()

insert immediately after

      while True:

that encompasses all of the remaining code in the def.

And change the end of the def from

        if rerun_exception_data is not None:
           self._run_script(rerun_exception_data)

to

        if rerun_exception_data is None:
            break

This change will eliminate the recursion by converting it to an optimized tail call which executes the client code in an identical fashion without overflowing the stack.

So, if someone with access to the source could change **script_runner._run_script** as outlined above, that would eliminate the stack overflow caused by repeatly calling **streamlit.rerun()**.

I made this change to my local copy and now **streamlit.rerun()** is called successfully several times per minute for 12+ hours without overflowing the stack.

ue to small differences in how it works compared to the regular script runner. The regular one resets trigger widgets at the end of a script run, so it goes into the rerun with the button no longer clicked, and it stops there.
The modified script runner used by AppTest, otoh, skips resetting trigger widgets at the end, so their values can be seen correctly in the following test code. This mostly works out, as the following script run it runs will only see a button as clicked if it was clicked since the prior run. But it breaks when the new script run happens because of `st.rerun`, which will reuse the widget state where the button is clicked, causing the infinite loop.

Since the rerun loop happens without any opportunity for input from AppTest, I don't think there's a simple way to directly fix just this problem. Instead, I think the fix will involve undoing the trigger reset skipping and instead making triggers have the right value in the tree a different way.
