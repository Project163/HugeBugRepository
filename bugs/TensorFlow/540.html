- Well... I'm of two minds, and I keep flip-flopping between whether this is actually an issue or not.

1) `tf.cast` is really supposed to be used to cast an existing tensor between two different dtypes.  For converting things that aren't tensors _into_ tensors (like python values), you're _supposed_ to use `tf.convert_to_tensor`, which does behave correctly in this case.  The fact that `tf.cast` works for non-tensor inputs (somewhat - except for cases like this)  is more out of convenience, since pretty much all our TF functions take in non-tensors, and internally use `tf.convert_to_tensor` if required.

but...

2) `tf.cast` doesn't complain about the non-tensor input, and the fact that it uses `tf.convert_to_tensor` without a dtype hint internally is an implementation detail that the user shouldn't be concerned about.  It probably *should* work as intended and use the appropriate precision, since that information _is_ available.

but...

1) The reason we default to float32 when you provide a raw python float is that in most ML applications this is sufficient, and converting to float64 would lead to large performance degradations, particularly on accelerators.  This isn't just with `tf.cast`.  If you try to `tf.math.add(2.0, 2.0)` two python floats, it will also use the lower precision `float32` versions.  `tf.cast` is no different - an input of 2.0 will be seen as a float32 2.0, which it then casts to `float64` for the output of the op.  This is really no different than any other op.
- So what's the resolution?  Let's forget about this issue?
