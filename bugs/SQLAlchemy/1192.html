Title

selectinload (others?) don't use the given query options as part of the cache key, or no way to propagate execution options

Description
this is really kind of an extension of #6881 and is here revealed by #6885.

A means of sending a message to the selectinloader would use the program below:

```
py
from sqlalchemy import Column
from sqlalchemy import create_engine
from sqlalchemy import event
from sqlalchemy import ForeignKey
... [Log Snipped] ...
stmt = select(A).options(selectinload(A.bs), SetShardOption("some_other_shard"))
s.execute(stmt).all()
```

however, lambda caching defeats this even if query caching is turned off, because we don't track on the options.  needs this patch:

```
diff
diff --git a/lib/sqlalchemy/orm/strategies.py b/lib/sqlalchemy/orm/strategies.py
index 587daa332c..aab4796861 100644
--- a/lib/sqlalchemy/orm/strategies.py
+++ b/lib/sqlalchemy/orm/strategies.py
... [Log Snipped] ...
 
         if context.populate_existing:
```

it's not clear if this actually fixes #6881 also, which would be interesting.
Discussion
- but also not to mention for a sharding scenario, the "shard id" is not at all appropriate for a cache key.   the loaders should have some means of propagating execution options that is outside of caching.      if ORMExecuteState could reveal the parent query, that is one way this could be possible.
- I'm incorrect about that patch, the lambda tracking seems to work for the loader option.   it's still just not ideal that a transitory thing like 'shard_id' would need to be in the cache key, and this might affect the dogpile recipe also, where we are not returning a cache key for the cache option so...selectinload is broke there too ?
