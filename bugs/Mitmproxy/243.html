Title

mitmdump with new proxy core hangs instead of failing if listening port unavailable

Description
ran into this because my script that restarts mitmdump to rotate the dump file or for #4456
uses a hardcoded delay after killing the old instance.
recently it took longer than usual for the old instance to die and release the port;
i always ended up with an newly started instance that was running but not listening on any ports.

did some bisecting on
```
time timeout 60 mitmdump -w /dev/null ; [ $? != 124 ]
```
(the default port is always in use by my "production" instance)

and ended up on [URL]

sadly i'm not familiar enough with python/asyncio to fix this.

it seems that `await asyncio.start_server()` simply never returns if it fails to bind the port...
[URL]
("Proxy server listening at " is never printed)

the docs don't mention anything special about error behaviour:
[URL]
the returned value is a coroutine object even in the error case.

- I personally run a gRPC server in both Node.js and mitmdump (via addon) so both can freely communicate.

In your case a simple socket or any type of ipc should work to send a signal. Mitmdump addons are really powerful. The [Link: `running`] hook should be the right place, but be aware that it's currently fired twice [URL] (I keep a flag to prevent duplicate logic)
- for some very pragmatic less complex workarounds:
* if you do all of this programatically anyway, simply choose a random listen port on each startup
* alternatively or additionally test if the port is available by trying to bind it yourself before mitmdump startup (don't forget reuseaddr)
* instead of waiting for stdout output, wait for a successful response to a simple request (just the error message on sending "GET / HTTP/1.0\r\n\r\n" works fine.)
