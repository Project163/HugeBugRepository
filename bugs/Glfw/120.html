Title

glfwGetWindowPos and glfwSetWindowPos do not ignore decorations

Description
It appears that the either the window position callback or the glfwGetWindowPos/glfwSetWindowPos are not using the correct/same reference point. As the values provided by the callback and the glfwGetWindowPos are consistantly out by the size of my window decorations.

I confirmed this by performing a test where I create a window and set the position callback.
In the position callback I store the values that are passed in and then setting the window's position to them in the main update loop.
This results in the window jumping, normally when I drag the window.
However, if in the callback I store the values provided by glfwGetWindowPos then the window remains static and correctly moves when I drag the window.

In my case the values were different by -4 x and -18 y relative to the callback's values.

This suggests that the callback is providing client-area positions and glfwGetWindowPos/glfwSetWindowPos are operating on window cordinates. This is further suggested by setting the window position so that x = 0, this results in the window decoration's edge touching the side rather than the client area. Setting the position to x = -4 causes the client area's edge to line up with the edge of the screen instead. Lastly looking at the documentation for the XMoveWindow function, it says that x and y "define the new location of the top-left pixel of the window's border or the window itself if it has no border." and (atleast in the __glfwPlatformSetWindowPos function) the coordinates aren't translated from the client-area to include the window decorations.

Discussion
- I've attempt a fix in my fork at draghi/glfw@ 

Changes in x11_window.c:
- [1224 -1237] In the ConfigureNotify event handling I changed it so that the event position is ignored and the values given by _glfwPlatformGetWindowPos are used instead 
- [1696 - 1704] _glfwPlatformGetWindowPos offsets the top-left of the window to the client area 
- [1735 - 1740] _glfwPlatformSetWindowPos offsets the client area to the top-left of the window 

This results in the expected behavour on my system. The position callback and glfwGetWindowPos provide the same values. Forcing the window to 0,0 results in the client-area being flush with the sides of the screen. The same is true when window decorations are disabled for the window.

However, the solution is untested with any other window managers or with any other linux distributions. 

It's also probbably not exactly ideal, the change to the ConfigureNotify event handling isn't strickly needed in this case and very likely changes the values passed to the callbacks (multiple move events passing the 'final' position of the window eg.), however I was unsure how to garentee that the event would consistantly provide the client-area position based on the documentation (my lack of x11/xlib/glfw-internals knowledge showing there).
