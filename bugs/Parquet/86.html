Title

Add support for non-String binary in parquet-thrift

Description
Thrift  considers binary a "special" type  that isn't in the official spec but is "to provide better interoperability with java". The parquet-thrift side doesn't currently support binary because Thrift String fields are converted to UTF8-annotated binary. The result is that binary fields get mangled when stored in Parquet because Parquet assumes they are UTF8. 

 I think some storage layer in Java Thrift must know about binary and pass the unencoded bytes, but that Parquet hasn't implemented a similar hack. (The  type conversion  code at least has no entry for binary.)
Discussion
- This was based on a  reported parquet-scrooge bug  and an incomplete analysis on my part. I looked only at the Schema converter, which doesn't show support for binary but doesn't need it. Support for binary already exists;   ParquetWriteProtocol   allows binary data to be written as either a String or binar, and the   ThriftRecordConverter   generates correct protocol events that handle both. 

 It turns out that the original bug report wasn't correct. The summary does appear to have corrupt data: 
  
 Parquet Example
---------------

    ./sbt  "run-main com.rouesnel.parquetmr.bug.ParquetExample" 

This should print the following:

    Parquet
    =======

    Parquet File written to /some/random/location/test-324324-foo.parquet

    After encoding - binary field is equal to original binary field:  false 
    After encoding - binary field is equal to UTF8 encoded binary field:  false 

    Original
    -----
    binaryField:         -123, 20, 33
    stringField:         foo
    binaryAsStringField: -17, -65, -67, 20, 33

    Thrift Serialized
    -----
    binaryField:         3, 0, 0, 0, -123, 20, 33
    stringField:         foo
    binaryAsStringField: -17, -65, -67, 20, 33
 
  

 Tests show that the underlying byte buffers are correct and the error is caused by assuming the ByteBuffer's backing array contains only the bytes serialized. When restricted to the position and limit, the data is correct.
