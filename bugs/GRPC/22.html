Title

[C#] The native method "grpcsharp_slice_buffer_create" does not exist

Description
### What version of gRPC and what language are you using?
2.23.1 & 2.24.0

### What operating system (Linux, Windows,...) and version?
Windows 10 v1803

### What runtime / compiler are you using (e.g. python version or version of gcc)
MSBuild VS 2019 (16.3.5)

### What did you do?
I tried to have a library targeting the minimum version possible (2.23.1) and an application overwriting the target to latest version possible (2.24.0).

### What did you expect to see?
The application should start. All Grpc DLLs (managed + unmanaged) should be from 2.24.0.

### What did you see instead?
`**System.MissingMethodException:** The native method "grpcsharp_slice_buffer_create" does not exist`

When checking the DLLs, the windows native DLLs are not correctly copied.

This image shows, that when only targeting 2.23.1 (left, test-23) and 2.24.0 (right, test-24) without changing the version in the app, all files are different.
[Image: grafik]

The output of 2.24.0 (app) over 2.23.1 (lib) looks like here on the left. The only files matching with 2.23.1 are the windows files.
[Image: grafik]

The output of 2.24.0 (app) over 2.23.1 (lib) again on the left. The only files NOT matching with 2.24.1 are the windows files.
[Image: grafik]

So there seems to be a bug, that the windows libraries are not taken from the correct version. The Linux libraries are taken from the correct version. So there might be a bug in the NuGET script. I sadly don't know enough about NuGET to look further for the reason why this appears.

### Anything else we should know about your project / environment?
This bug was already discovered by another user in #19211 but not followed up. Having different version in library and application is common, so this should be fixed to always work.

This occured on [URL] but I also made a minimal example at [URL]
Discussion
- I am able to reproduce, but don't know yet the exact rootcause.
I suspect that 2 versions of [URL] get included in the project (one from 2.23.1 and the other one from 2.24.1), but the one from 2.23.1 gets precedence.

When targeting netcoreapp2.1 (as opposed to net461 or net45), things work just fine (because the .targets file is only used as a workaround for the net4* platforms and under .NET core the native dependencies are handled differently).
- I assume the problem is PreserveNewest. 2.23.1 is newer than 2.24.1

But the .so and .dylib files would also be newer and were replaced by the same target.
