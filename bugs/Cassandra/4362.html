- I am now also seeing this in another upgrade test, upgrade_internal_auth_test.py:TestAuthUpgrade.upgrade_to_30_test 

  [URL]
- The failure in  upgrade_internal_auth_test.py:TestAuthUpgrade.upgrade_to_30_test  does not seems to be the same as the original one. 
I could not reproduce the problem but the stacktrace lead me to the following code in  MessagingService  in cassandra 3.0: 
  
      public   int  getVersion(InetAddress endpoint)
    {
         Integer  v = versions.get(endpoint);
         if  (v ==  null )
        {
             // we don 't know the version. assume current. we' ll know soon enough  if  that was incorrect.
             logger.trace( "Assuming current protocol version  for  {}" , endpoint);
             return  MessagingService.current_version;
        }
         else 
             return   Math .min(v, MessagingService.current_version);
    }
 
  
 The problem seems to be that when the message is build in  AbstractReadExecutor ,  MessagingService  does not know yet the current version of the endPoint. Due to that it fallbacks to  MessagingService.current_version  and the  MessageOut  is created with  ReadCommand.Serializer  instead of  ReadCommand.LegacyReadCommandSerializer . When the  MessageOut.payloadSize  is called the proper version of the endpoint has been determined and we run into the assertion.  

 I think we could avoid that problem by excluding the endPoint in  StorageService.getLiveNaturalEndpoints  if we are not able to determine its version. 
 slebresne  what do you think?
