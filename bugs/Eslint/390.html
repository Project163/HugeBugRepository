Title

Shared config doesn't cascade properly

Description
I've been trying to isolate this bug, but it seems to only occur under very specific conditions. I'll continue trying to boil this down, but for now I'll report what I know.

I have a company shared-config, with 2 modes: `node` and `browser` Our app's config hierarchy looks like:
- `.eslintrc`: `{ extends: "segment/node" }`
- `app/client/.eslintrc`: `{ extends: "segment/browser" }`

When ESLint runs, it approaches files in this order:
- `app/client/index.js`
- `app/server.js`

What happens is that the `server.js` file (which should _only_ be following `segment/node`) is wrongly failing because of rules in `segment/browser`. If I manually reverse the order, it processes the rules correctly. (which tells me that some clobbering is happening between various config objects)

I've dropped a couple `console.log` in there to try and follow the cascade and see where things go awry. The first time `segment/node` is loaded, it appears to get the right value, but all subsequent times get the wrong value.

From what I can see, `utils.mergeConfig()` modifies the `base` directly, which I suspect is the source of this problem. I'm hoping the solution can be as simple as cloning the config objects after being `require`d as to prevent clobbering.
