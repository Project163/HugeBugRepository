Discussion
- I examined the test log and guess I've found the cause. We write two records into each partition of  source_table , and each of these two records can trigger partition commit in  sink_table . So if a CP is done in between of these two records, the partition will be committed with only one record. And if the reading job checks  sink_table  for new partitions before the 2nd record is written, it only finds the 1st record but believes the partition has all the data. Therefore we'll hang at the verification code waiting for the 2nd record, which is now a late event.
