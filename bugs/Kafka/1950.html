Discussion
- Thanks for the detailed explanation of the issue. I looked at the code of 1.1, and the `checkpoint` object is always initialized in the constructor of `ProcessorStateManager`. So it is still not clear to me why EOS would hit this issue. Could you share more of your findings?
- guozhang  Note that `checkpoint` is not `final` and indeed, `ProcessorStateManager` sets `checkpoint = null` when EOS is enabled in it's own constructor. This is by design, because the checkpoint file is deleted to make sure we do full restore in case of error. Only in a clean shutdown, the checkpoint file is recreated. 

 Thus, a proper fix would be to check if EOS is enabled and only write the checkpoint file if disabled. Let me know what you think about this? If you agree that it is a proper fix, we can include it in 2.0 release. But we should not rush it – EOS is sensitive. Also, the describe scenario is a corner case that only happens is offsets get invalid for a changelog topic when we try to restore it.
