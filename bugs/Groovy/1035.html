Title

ClassCastException writing entry to map via [] when key matches private field name

Description
The convenient [] syntax for Map usage fails with a ClassCastException if the key happens to match the name of a private field in the map implementation. 
So for HashMap an easy one to accidentally hit this with is "table".  So the following code: 

 def map = new HashMap() 
map ["table"]  = "SOME_TABLE" 

 Leads to: 
Caught: org.codehaus.groovy.runtime.typehandling.GroovyCastException: Cannot cast object 'S' with class 'java.lang.String' to class 'java.util.HashMap$Entry' 

 Using  [:]  to create the map is fine though as that creates a LinkedHashMap which doesn't have a "table" property. 
It does have a header field though so we can trigger the same with this: 

 def map =  [:]  
map ["header"]  = "Some text" 

 This used to work in Groovy 1.5.6.  I haven't tried any version between that and 1.6.4.
Discussion
- I think this is no bug but by design that it is happening. Design is to give preference to class fields and properties over map entries - in that order. 

  
  class  MyMap  extends  HashMap {
	 int  p1
	def setP2( int  x) {}
}
def map =  new  MyMap()

setVal(map,  'p1' ,  'str1' )  // fails because p1 is a field on the class
 setVal(map,  'p2' ,  'str2' )  // fails because p2 is a property on the class
 setVal(map,  'p3' ,  'str3' )  // goes through because p3 is no field or property on the  class  and hence it becomes a map entry
 
println map

def setVal(map, key, val) {
	 try {
	    map[key] = val
	} catch  (ex) {
		println ex
	}
}
- I agree that the above use case makes sense but surely the private fields of some of the standard map classes should not win over string keys in the map? 

 Should a developer have to know that   [:]  creates a LinkedHashMap and then it's not safe to use a key called header? 
That just seems wrong to me.  I'd certainly say it breaks the rule of least surprise. 

 Not sure what the correct solution is though. 
As I said in the oriignal report it did used to work in Groovy 1.5.6 so I'm not sure exactly how the "rules" have changed here. 

 I'd prefer it that private map fields would not be settable by default although perhaps that behaviour could be switched, maybe by switching in a custom metaclass for the map impl class.  Perhaps that's just me though?
