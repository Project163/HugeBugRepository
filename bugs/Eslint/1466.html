**Context**

Original issue: [URL]

Investigation so far:

Our parser (`@typescript-eslint/parser`) returns an extended list of [Link: visitor-keys] (as specified [Link: by the ESLint docs]) [Link: right here]

However `esquery` uses its own (hard coded) visitor keys for 3 selectors:
- sibling `~`:
[URL]
- adjacent `+`
[URL]
- and nth-child `:nth-child(n)`
[URL]

So I *think* that this is this something we'll have to PR into the underlying esquery library?
Discussion
- I think we should treat this as a bug, since our [Link: selectors documentation] lists those selectors, so it's reasonable to expect that they can work with custom parsers.

Also, they'll crash even with the default parser on any JSX code, as in [Link: this demo].

It's true that this needs to be supported in `esquery` first, so we could pass visitors keys.

Relevant PR: [URL]

An alternative is to remove those selectors from the documentation. If this doesn't get fixed, it seems best not to use them at all.
- `esquery` has just published a new release with the support for custom visitor keys, so I think this should no longer be blocking.
- Also, `has:()` selectors are also supported which perhaps the eslint docs can be updated to indicate (the subject indicator is also supported, but per [URL] , that implementation is buggy while the `:has()` one was working enough to be used as a base for the former–though with one issue on relative keys mentioned there).
- @brettz9 can you please open a separate issue about the new esquery syntax?

ESLint selectors are using esquery, but we're also doing some optimizations and calculating specificity in [Link: NodeEventGenerator], so it's possible that some additional work has to be done before we can say that ESLint fully supports new selectors.
