Title

Test failure: org.apache.cassandra.transport.SimpleClientPerfTest

Description
SimpleClient uses a CQLMessageHandler instance to deal with response messages in the V5 framing format. It looks like   CASSANDRA-16663   broke SimpleClient's ability to return capacity allocated during the processing of inbound messages (i.e. responses from server->client) back to the global and per-endpoint resource monitors. The change in behaviour introduced in   CASSANDRA-20052  , in which we now push back to the client when a capacity for a large message can't be allocated, causes SimpleClientPerfTest in the burn suite to fail on V5/V6. This is purely because the test expects the client to run for a fixed period without interruption, but now it halts as soon as capacity is exhausted. The simple fix is to restore SimpleClient's capacity return.
Discussion
- Hi  samt , thank you for highlighting the issue, I am trying to reproduce it locally and understand the root cause better.
- Prior the suggested fix SimpleClient overrode method org.apache.cassandra.transport.CQLMessageHandler#processRequest(Envelope request) to intercept the moment when a response was fully received and processed to release capacity but it was not invoked by CQLMessageHandler (after changes done in   CASSANDRA-16663  ). CQLMessageHandler invokes processRequest(Envelope request, Overload backpressure). So, org.apache.cassandra.net.AbstractMessageHandler#releaseCapacity was not invoked for the responses within the SimpleClient. 

 So when we executed the test endpointReserveCapacity/globalReserveCapacity were leaking and "using" Limit value reached the limit value. 
    

 Prior to   CASSANDRA-20052   CQLMessageHandler and correspondently SimpleClient ignored the capacity leaking by allowing to process messages even if there is no available capacity in endpointReserveCapacity/globalReserveCapacity, as a result it masked the issue with leaking. 

 After   CASSANDRA-20052   CQLMessageHandler has started to really apply backpressure by treating lack of capacity as a signal to pause messages receiving. So, in case of SimpleClient we stuck in responses receiving due to lack of free capacity. 
    

 In the current ticket  samt  has fixed the SimpleClient logic is used to intercept CQLMessageHandler response processing, so there is no the capacity leak anymore. 
    

 The mentioned tests are failed on my laptop as well before the fix and are passing after applying the suggested change. 

 The suggested change looks good to me.
