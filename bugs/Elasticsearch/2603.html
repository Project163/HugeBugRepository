Title

Incorrect `ProfileResult` totalTime?

Description
When using profiling utility of Elasticsearch, i mentioned that sum of `breakdown` with key not end with `_count` not equals to `time_in_nanos` field:
```
json
{
  "type": "IndexOrDocValuesQuery",
  "description": "timestamp_long:[1564099200000 TO  ]",
  "time_in_nanos": 4982334261,
... [Log Snipped] ...
  }
}
```
In this example sum of each entry with key not end with `_count` is 4877922615, not 4982334261

I read the code about [Link: `ProfilingResult`], `nodeTime` field equals to sum of values of  constructor parameter `timings` map, and `timings` is generated by [Link: `AbstractInternalProfileTree#doGetTree`] method using [Link: `AbstractProfileBreakdown#toTimingMap`]:
```
java
    public Map  toTimingMap() {
        Map  map = new HashMap<>();
        for (T timingType : timingTypes) {
            map.put(timingType.toString(), timings[timingType.ordinal()].getApproximateTiming());
... [Log Snipped] ...
        return Collections.unmodifiableMap(map);
    }
```
It means that sum of `timing`'s values is not the real time costs total. Shall we estimate entries with key ends with `_count` in `timing` to calculate the REAL time costs total?

- Hm, I'm not entirely sure, but I think I see at least one bug: [URL]

It looks like this wasn't updated when we added method counts, so the counts are being included with the timings as part of the node time.  At the very least, that part is incorrect
- OK, I'll create a PR for this BUG later.
- I looked into this issue again and see the same behaviour still on 6.8.15, but it seems to be fixed in current 7.12.1.
I believe that #56208 silently fixed the summation issue by moving the nodetime calculation out of `ProfileResult` into `AbstractInternalProfileTree` where AbstractProfileBreakdown#toNodeTime is used, which only sums the timings `getApproximateTiming` results but not the counts. 
A manual check to compare this with a random profile breakdown taken on 6.8.15:

```
{
                "type" : "MatchAllDocsQuery",
                "description" : "*:*",
                "time_in_nanos" : 736842,
                "breakdown" : {
... [Log Snipped] ...
                }
              }
```
Summing the times _excluding the count_ values: 4167 + 24771 + 4670 + 703213 = 736.821 (wrong)
but incl “_count” values: 736.821 + 8 + 1 + 8 + 4 = 736.842 (equals "time_in_nanos)
So this calculation is still off on 6.8.15

On 7.12 however:
```
{
                "type" : "ConstantScoreQuery",
                "description" : "ConstantScore(DocValuesFieldExistsQuery [field=_primary_term])",
                "time_in_nanos" : 7120818,
                "breakdown" : {
... [Log Snipped] ...
                  "build_scorer" : 42589
                }
```
Here the values excluding the "_count" values sum to the correct "time_in_nanos": 7061921 + 4833 + 1435 + 10040 + 42589 = 7.120.818

Edit: I don't think we intend to port #56208 back to 6.8 so I will close this issue but will look into adding a short test (if possible) that checks this calculation going foward.
