Title

Counters are erroneously allowed as map key type

Description
We do validate collection value types, but not collection key types, which allows counters to be used as map keys: 

  
 cqlsh> create keyspace test with replication = {'class': 'SimpleStrategy', 'replication_factor': 1};
cqlsh> use test;
cqlsh:test> create table test.test (id int primary key, amap map<counter, text>);
cqlsh:test> insert into test.test (id, amap) values (0, {1: '2'});
cqlsh:test> select * from test.test;

 id | amap
----+----------
  0 | {1: '2'}

(1 rows)
 
  

 This should obviously not be allowed and must be rejected. 

 /cc  slebresne

cqlsh:test> create table test.test (id int primary key, alist list<counter>);
InvalidRequest: code=2200 [Invalid query] message="Counters are not allowed as values inside collections: list<counter>"
 
  

 Note the error message for LIST is the same as for MAP (both refer to 'values inside collections'). If this is confusing I'll just remove the 'as values'. 

 One thing I'm not 100% sure of is whether we allow counters as map keys for supercolumns. Seems we do allow counters as map values for supercolumns. If we do not allow them as map keys then the  isInternal  check in  org/apache/cassandra/cql3/CQL3Type.java  can be removed (see patch).

- Committed (with minor nits, see below), thanks. 

  the error message for LIST is the same as for MAP (both refer to 'values inside collections')  

 I took the liberty of leaving the error message alone and use the same for both case because while no-one should rely on a particular error message, I still prefer not changing them if it's not a clear improvement. And I doubt anyone will have trouble fixing their problem with just "Counters are not allowed inside collections". 

  whether we allow counters as map keys for supercolumns.  

 We don't. And truly, the storage engine doesn't support it as counter resolution rules only ever apply to cell values and a map key is part of the cell path. So removed the  isInternal  check on commit.
