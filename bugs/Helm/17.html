Title

Helm v3: lint silently ignores non existing packaged charts

Description
Output of `helm version`:
```
$ helm3 version
version.BuildInfo{Version:"v3.0.0-beta.3", GitCommit:" ", GitTreeState:"clean", GoVersion:"go1.12.9"}

$ helm version --client
Client: &version.Version{SemVer:"v2.14.3", GitCommit:" ", GitTreeState:"clean"}
```
Output of `kubectl version`:
N/A

Cloud Provider/Platform (AKS, GKE, Minikube etc.): 
N/A

----

If you try to lint a packaged chart that doesn't exist, helm3 silently ignores it.
 
```
$ helm3 lint aaa-1.0.0.tgz
==> Linting aaa-1.0.0.tgz

1 chart(s) linted, 0 chart(s) failed
```

```
$ helm lint aaa-1.0.0.tgz
==> Skipping aaa-1.0.0.tgz
open aaa-1.0.0.tgz: no such file or directory

0 chart(s) linted, no failures
```
Discussion
- For helm2, looks like it was expected 🤔 as I can see a `Skipping` message. Let me check code. So, what's expectation? Both helm2 and helm3 should say that there was one failure and set an exit code? Or helm3 should work similar to helm2's current flow ?
- Also, if something was skipped, I think it would be better to show
```
$ helm lint aaa-1.0.0.tgz
==> Skipping aaa-1.0.0.tgz
open aaa-1.0.0.tgz: no such file or directory

0 chart(s) linted, 1 chart(s) skipped, no failures
```
- ... [Middle Discussions Snipped for Brevity] ...
- @hickeyma which approach are we going with? helm2 way?
- Personally I think it would make more sense to return an error and set the exit code if the tarball doesn't exist, as @karuppiah7890 has pointed out it would make it obvious if someone made a typo when running it locally or cause faulty CI pipelines to fail. This would also be consistent with trying to lint a non existing directory.

```
helm3 lint /no/such/chart  aaa-1.0.0.tgz
==> Linting /no/such/chart
Error no chart found for linting (missing Chart.yaml)

==> Linting aaa-1.0.0.tgz

Error: 2 chart(s) linted, 1 chart(s) failed
```
