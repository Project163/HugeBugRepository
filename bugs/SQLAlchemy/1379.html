Title

Importing sqlalchemy superfluously forks off file command

Description
### Describe the bug

With the November SQLalchemy 1.4.44 update simply importing `sqlalchemy` now forks of the `file` utility.
This is new behavior in the 1.4 branch and a **regression** when you are running your Python program under a relatively strict seccomp filter, SELinux policy or similar that doesn't allow vfork/pipe2/wait4 syscalls, because your program isn't expected to use those.

Importing `sqlalchemy` now calls the `file` utility because it calls `platform.architecture()` in order to initialize its `is64bit` field (in `lib/sqlalchemy/util/compat.py`).
However, this call is superfluous because the information the `file` call provides is ignored.

Thus, a better way to initialize that field is to write

```
is64bit = sys.maxsize > 2**32
```

as [Link: recommended] by Python's standard library documentation.

See also:

- [Link: Introducing commit in 1.4 branch]
- [Link: Introducing commit in 2 branch]

### To Reproduce

```python
strace -y -f -o s.log python3 -c 'import sqlalchemy'
grep 'fork\|pipe2\|wait\|exec' s.log
```

When running under a seccomp filter that doesn't allow pipe2/vfork/wait4 you would get a core file for which gdb would print something like:

```
Program terminated with signal SIGSYS, Bad system call.
```

### Versions

- OS: Fedora 35 and 37
- Python: 10 and 11
- SQLAlchemy: 1.4.44 (but also present in version 2 branch)
- Database: all
- DBAPI (eg: psycopg, cx_oracle, mysqlclient): all
