Title

Helm lint throws an error where a warning should be thrown instead

Description
As a result of these 2 PRs:

1. **[URL] - feat: implement deprecation warnings in helm lint**
1. **[URL] - feat: lint the names of templated resources**

now `helm lint` validates  whether resource `metadata.name` complies Kubernetes naming rules and whether the `apiVersion` is up to date. And these are great features, thank you for implementing them! 

However, these rules are having ERROR severity instead of WARNING. These should be warnings because these are NOT errors from the Kubernetes perspective - Kubernetes API still accepts resources with deprecated API versions as well as resources with metadata names that, for example, contain `:` in them. If these are warnings instead of errors, then it will be up to a client to decide whether he wants to fail lint (via using `--strict` flag for `helm lint` command) or not.

Setting the error severity level for these issues also complicates the migration of automated deployments 
 to helm 3.3, especially form Helm 2.x.

_How to fix?_ - I believe [Link: these lines] of code should be rewritten to:

```go
linter.RunLinterRule(support.WarningSev, path, validateMetadataName(&yamlStruct))
linter.RunLinterRule(support.WarningSev, path, validateNoDeprecations(&yamlStruct))
```
Discussion
- As of Kubernetes 1.16, those APIs were deprecated and are no longer accepted even with a `kubectl create`, so it is correct for `helm lint` to report an error in those cases. More recent versions of Kubernetes no longer accepts those resources, and users should be upgrading to a supported API version.

See [URL] for more details.
- @bacongobbler, it is true for **some** APIs (listed in the above release notes) but certainly not for all - here is an example... The helm chart has a `ClusterRole` resource defined using the deprecated API version:

```yaml
apiVersion: rbac.authorization.k8s.io/v1beta1
kind: ClusterRole
metadata:
  name: {{ include "example-chart.fullname" . }}
  labels: {{ include "example-chart.labels" . | nindent 4 }}
rules:
  {{- toYaml .Values.clusterRoleRules | nindent 2 }}
```

If you run an installation/upgrade of this chart, it will succeed and there will be no errors. However, `helm lint` command in Helm 3.3 fails for it with the error:

```
[ERROR] templates/clusterrole.yaml: the kind "rbac.authorization.k8s.io/v1beta1 ClusterRole" is deprecated in favor of "rbac.authorization.k8s.io/v1 ClusterRole"
```

The cluster's Kubernetes version is **1.18.7**

An example of a totally valid chart for which `helm lint` fails is [Link: incubator/haproxy-ingress].

- The idea behind making these lint checks of ERROR severity is as follows:

- Deprecated/Removed APIs: Helm will no longer be able to manage a release if it contains a Kubernetes resource with an API which is no longer supported by the Kubernetes version. This can happen by just upgrading Kubernetes to a certain version with existing releases. See [Link: Deprecated Kubernetes APIs doc] for more details
- Metadata names: Following the `kubectl` naming rules is good practice

My thought on this is that the lint severity should mirror Helm's opinionated view. This view is continually developing from experience and best practices, helping users to avoid potential pitfalls. It then is up to the user to decide whether to heed the errors or not. The severity matches the potential of how bad the outcome can be for the user.

As @mattfarina @bacongobbler have mentioned, I am also a practical person and understand that users will be using Kubernetes in different ways and with different version which won't always align to the Helm opinion. This is why there has been  a lot of issues raised against linting and how people think it should best work. @technosophos has given a lot of feedback on the topic in other issues and also in [URL] and [URL]

I agree then that the severity for both check should be downgraded to warning. I have added a suggestion to provide more information to the user for APIs in [URL]
