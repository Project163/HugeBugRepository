Title

Catch::session()run crashes with argc == 0

Description
Catch 1.5.7, Xcode 8, OS X 10.11.6

We had some code that was stripping the binary name before passing argc/argv on to catch. With 1.5.7 that causes a crash because Catch is blindly dereferencing a vector[0] at line 4519 of the single header:

```
* thread #1: tid =  ,   libc++.1.dylib`std::__1::basic_string , std::__1::allocator  >::basic_string(std::__1::basic_string , std::__1::allocator  > const&) + 4, queue = 'com.apple.main-thread', stop reason = EXC_BAD_ACCESS (code=1, address=0x0)
- frame #0:   libc++.1.dylib`std::__1::basic_string , std::__1::allocator  >::basic_string(std::__1::basic_string , std::__1::allocator  > const&) + 4
  frame #1:   lib_tests`Catch::Clara::CommandLineCatch::ConfigData::parseInto(this= , args=size=0, config= ) const + 124 at catch.hpp:4519
  frame #2:   lib_tests`Catch::Session::applyCommandLine(this= , argc=0, argv= , unusedOptionBehaviour=Fail) + 175 at catch.hpp:6363
  frame #3:   lib_tests`Catch::Session::run(this= , argc=0, argv= ) + 58 at catch.hpp:6389
  frame #4:   lib_tests`(anonymous namespace)::catch_main(argc=0, argv= ) + 59 at main.cpp:59
  frame #5:   lib_tests`main(argc=1, argv= ) + 48 at main.cpp:15
```
I've removed the legacy code that did this, but Catch should not be making this assumption.
Discussion
- My opinion on this is that there should always be at least a binary name in the arguments, but I can see why Clara (the cmd-line parser Catch is using) shouldn't be making that assumption.
