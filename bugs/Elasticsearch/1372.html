Title

Batched mapping updates can overwrite existing mappings

Description
The introduction in #14899 of applying mapping updates in batches brought with it a bug that could cause existing mappings to be lost during an update. In particular, in a scenario in which a batch contained updates for at least two distinct existing types on the same index, the existing mappings for all but the first existing type on the index would be lost. This arises because the workflow for applying mapping updates in batches now looks like:
1. [Link: if] any of the indices in the request batch do not exist on master, [Link: create] them for the purpose of applying the mapping update and [Link: merge] in the existing index mappings from the cluster state
2. [Link: apply] the mapping updates
3. [Link: if] any indices were created, [Link: delete] them from master

The code for step 1. [Link: looks like]:

```
java
for (PutMappingClusterStateUpdateRequest request : tasks) {
  // failures here mean something is broken with our cluster state - fail all tasks by letting exceptions bubble up
  for (String index : request.indices()) {
      if (currentState.metaData().hasIndex(index)) {
... [Log Snipped] ...
  }
}
```

The flaw is that on the second distinct existing type for the same index, [Link: `indicesService.hasIndex(index) == false`] will evaluate to false (because the [Link: index was created] for the first existing type for the index) and the existing mapping will never get merged in. This will then cause the mapping update to overwrite the existing mapping so losing it.
