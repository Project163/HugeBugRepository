XMB and XLIFF(both) output the wrong source file for a message

## Current behavior
 
XMB and XLIFF(both) print the wrong source file for a message, [Link: example in repo tests]:
```html
   "> src/module.ts:2 Welcome 
```
## Expected behavior
 
The generated code should have been:
```html
   "> src/basic.html:2 Welcome 
```

## Minimal reproduction of the problem with instructions
 
bazel test //packages/compiler-cli/test:extract_i18n

## What is the motivation / use case for changing the behavior?
 
Tools that rely on the correctness of these XMB/XLIFF files need to hack their way around this limitation. For example, a tool that analyzes these generated files would need to replace ".ts" for ".html" to read the real file and hope that the names match (which is not always the case).

- I'm sending a PR in a bit, there is just one open question I have:

* Inline templates (e.g. `template: '  ',`) point to the "wrong lines". The message source lines point to the hypothetical HTML file that's inlined in the component TS file. Because the line numbers are wrong, should we completely remove these?

How are they wrong?
```ts
// foo.ts
import {Component} from '...';

@Component({
  template: ' bar '.
})
export class Foo{}
```
**Expected:**  \ foo.ts:**5**\  
**Actual:**  \ foo.ts:**1**\
- @Goodwine Thanks for working on this issue.

AFAIK the problem is on the compiler side - ie the compiler do not report the correct SourceSpan for the message:
- It reports ` .ts` when the template is in a separate file (ie `template.html`),
- It doesn't take into account the offset from the start of the ts file for inline template. The SourceSpan is reported as if the file is composed of the template only starting on line 1 column 1.

Both problems should be fixed and they should be independent of each other. Feel free to work on what is most important for you first.

The team is available to support you should you need. Thanks.
- After looking around, I don't think there's a problem with SourceSpan (I initially thought that too, but was not able to go forward), it seems like the html compiler doesn't read HTML files and instead it reads a string from the template which may or may not exist. Thankfully there is a previous process that normalizes the component metadata like:
- if it has `template` -> set component TS file name as `templateUrl`
- if it has `templateUrl` -> load HTML file and set contents as `template`

Before normalization tho:
```
js
// ==== component with templateUrl ===
{
  "encapsulation": null,
  "template": null,
... [Log Snipped] ...
  "template": "  \n       \n     \n    Welcome \n     "
}
```

A way to deal with this could be storing the "template offset" in the template metadata, it would be 0 for loaded templates. Then consumers can choose to take this offset into account if they want.
