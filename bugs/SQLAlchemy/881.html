Title

don't mutate attributes on get(), have it work for collections as well

Description
**Problem:**
1-to-many (e.g., "videos" below) fields of transient/detached objects automatically load empty lists as values after they've been accessed. As shown in the example below, an unbound user object gets created. The first set of asserts show that none of the fields have values loaded, except for `first_name`. After we access the fields through print statements, the last test fails because `mapper.attrs.videos.loaded_value == []`. I would expect videos' value to remain unloaded after the print statement. 

This could lead to problems… for example, if you access a transient object's 1-to-many field, merge the object (using session.merge(obj)) and commit,  the existing relationship values, if exist, gets replaced with an empty list, thus removes the children.

Discussion
- unfortunately this behavior as a default cannot be changed until SQLAlchemy 2.0 at best for which there is not currently timeline.   we can only pursue options which would allow the behavior to be modified if this is actually getting in your way.

The canonical pattern for ORM objects as has been in tutorials for years is:

```
u1 = User()
u1.addresses.append(u1)
```

this would not be possible if the initializer for collections did not both return an empty collection and also establish it as the state on the attribute.

In theory, had SQLAlchemy had a completely new start, the whole concept of "initializers" might not have happened at all, and we'd simply be getting AttributeErrors for any of these operations across scalars or collections, like a regular Python object where an attribute was not set.   That would be the most correct approach and remains an option for SQLAlchemy 2.0 (adding that to the 2.0 document now).

the behavior of state change upon "get" was refined in [URL] to remove this behavior for all scalar values.   This was an easy change which is why you see the `NO_VALUE` for scalars, however this change could not be made for collections.   It is also less critical for collections because relationally, an empty collection is the same database representation as no collection at all.   

So the merge() case which you bring up is the only use case that continues to not function
