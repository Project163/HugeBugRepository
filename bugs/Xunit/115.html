Discussion
- So, turns out this is a much bigger deal than I expected.

In v2, due to our reflection abstractions, all attributes were found using `CustomAttributeData` and we had custom code to instantiate them.

In v3, we reverted to standard reflection, which caused us to fall back on `GetCustomAttributes` from the runtime.

The problem with this is that if any attribute throws in its constructor, the result is that the call to `GetCustomAttributes` get no attributes. This is combined with the fact that in v3, we're now finding almost all attributes by interface rather than concrete type, which is not something the runtime permits with `GetCustomAttribute`. We are filtering all custom attribute instances based on the sought-after interface, so now when any attribute throws, kaboom.

In general, attributes that throw in their constructors are just plain broken in .NET. You can _mostly_ ignore that if you're searching for specific attribute types, but getting all attributes becomes broken. The only way to make this work is to revert back to our `CustomAttributeData`-based system, where we're instantiating the attributes ourselves. It's unfortunate, because this code is complex and potentially buggy, since we're replicating functionality that's best left to the runtime. On the plus side, we did it throughout the whole lifetime of v2, so I did have code to fall back on that should work. 🤞🏼
