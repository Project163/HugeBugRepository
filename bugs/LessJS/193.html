Title

compile font-family name with unicode is something wrong

Description
I have a css rule like this
```css
textarea {
    font-family: 'helvetica neue','wenquanyi micro hei',\5FAE\8F6F\96C5\9ED1, \5B8B\4F53, sans-serif;
  }
```

if i save it to x.less and use less　to compile the file

less tell me
```
bash
{ [Error: Unrecognised input]
  type: 'Parse',
  filename: 'input',
  index: 67,
... [Log Snipped] ...
  message: 'Unrecognised input',
  stack: undefined }
```

is there i miss something?
Discussion
- It looks like it fails to parse `\`-escaped stuff after a value in quotes, i.e.:
```css
foo: bar,   \5B8B\4F53; // ok
foo: 'bar', \5B8B\4F53; // error
foo: '' \5;             // error
```
A workaround is obviously to put unicode-symbols into quotes too (even if it's not required by the standard in this case), e.g.:
```css
foo: 'bar', '\5B8B\4F53'; // ok
```

- @rjgotten Not in the traditional sense. By saying it's a feature request, I don't mean it's not an obvious thing to include. I just mean that Less appears to have never had support for escaped characters in identifiers. Hence it can't be a bug, because nothing was ever there. It's just a missing feature. (To clarify: if Less HAD support for escaped characters in identifiers, but it was working _incorrectly_, you'd traditionally file that as a bug. Either way, it's important to do.)
- Btw, this parsing no longer occurs as of Less 3.7. Not because escaping is supported, per se, but because of permissive parsing. Meaning: unknown chars get interpreted as a permissive value until closing `;`.
