Title

Panache Paging does not support projections

Description
**Describe the bug**
When using projections or retrieve specific fields from a query using pagination the generated `count` query captures incorrectly the fields / projection. Hence, producing a malformed query that throws a hibernate query.

**Expected behavior**
Either capture correctly the fields / projection or use the `count(*)` for the count query.

**Actual behavior**
`org.jboss.resteasy.spi.UnhandledException: java.lang.IllegalArgumentException: org.hibernate.hql.internal.ast.QuerySyntaxException: expecting CLOSE, found ',' near line 1` exception is throw.


**To Reproduce**
Steps to reproduce the behavior:
1. Create query in the form "select a.id, b.field1 from A a joing B b on a.id = b.id"
2. Configure .page(1,25)
3. Try to do pageCount()

- @FroMage I have no doubts that "people would like to page properly" but I'm skeptical about us being able to automate it, without this becoming a significant project.

FYI in many databases the COUNT(*) query operation is very heavy, and takes approximately the same time as running the matching not-counting query.

The effect is extreme in some cases, to the point that for example in the MassIndexer of Hibernate Search when we had the count() approach in its first version - used to give people an approximate "progress bar" logged - this initial count was taking so long as the rest of indexing so the whole point of the progress bar was silly. Got rid of it, it's now twice as fast (it finishes in the same time it would start giving you a clue before).

Several DBs have low-acid alternatives which leverage statistics and lack of locking to give you a fairly accurate approximation; when I worked on systems needing a page count we'd hand-roll such SQL statements as it was much more effective; most importantly, we could toy with tradeoffs we knew were acceptable in our specific use case.

e.g. MySQL has `SELECT FOUND_ROWS();`, other databases have hints, I honestly don't remember how to do it the right way on each.

I'd say in some far future Hibernate ORM could have ad-hoc "dialect" support to know how to generate such things optimally on many databases, but until we get there I would suggest don't try this and let people write some native SQL.
