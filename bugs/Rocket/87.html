Title

Path traversal issue in FileServer on Windows

Description
**Description**

On Windows, when using `FileServer`, a client can request a file on a different drive entirely to the server and have it return it. This is due to Windows' support for paths like `D:test.txt`, which are relative despite referring to a drive, and as such completely skip `rocket`'s path validation which only checks for `:` directly at the end of segments.

**To Reproduce**

Take any code using `FileServer` like [URL] and give it a path such as `D:test.txt` with the server on windows and a drive at `D:/test.txt` (since this is a relative-to-disk path, make sure that `D:/` is the current path on the `D:` drive). The server will return the contents with no error code.

EDIT: This can actually just be reproduced by using a path like `C:../whatever` - which is effectively equivalent to `..`-ing out of the server running directory (as long as the server is running on `C:`), at least in my testing, so this can be used to escape the intended served folder regardless of other drives being available.

**Expected Behavior**

404 as this would be returning a file outside of the served folder.

**Environment:**

 - OS Distribution and Kernel: Windows 10
 - Rocket Version: 0.5.0-rc.1

**Additional Context**

Rocket needs to validate segments more - a possible but perhaps overbearing fix would be to simply disallow `:` in paths everywhere rather than just at the end.

This "feature" seems to cause a lot more confusion and pain than anything else, especially given that [Link: only cmd.exe actually keeps track of the current directories on previous drives anyway].


This sounds right, at least on Windows. In addition to the drive designation, Windows uses `:` to designate alternate data streams. It seems that Rocket's current segment parsing code also allows a few other characters that are illegal in Windows paths - maybe those should be forbidden as well, although I expect those to all result in errors instead of traversal attacks.
