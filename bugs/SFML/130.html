Title

Image loading race condition when image failed to load

Description
## Subject of the issue
sf::Image::loadFromFile can't be safely used from multiple threads on different image instances (each thread having its own sf::Image) if there was an error loading images (such as file not found).

## Your environment

* Arch Linux
* git master
* GCC 10.2.0

## Expected behavior
It should be thread-safe to use different sf::Image instances in different threads.

## Actual behavior
The program can crash when using sf::Image::loadFromFile from multiple threads on different image instances (each thread having its own sf::Image) if there was an error loading images (such as file not found) because stb which sf::Image uses has a global variable for the failure reason string (see: extlibs/headers/stb_image/stb_image.h:832) and sfml tries to print the global variable in src/SFML/Graphics/ImageLoader.cpp:127. Between the call to stbi_load and stbi_failure_reason another thread could be in the middle of writing to the failure reason global variable that stb uses, causing a crash in the error printing.
A crash from this happens occasionally in my program and since its a thread race condition I cant provide a reliable code example to reproduce the issue, but here is what `valgrind --tool=helgrind` complains about:
```
 542 ==860571== Possible data race during write of size 8 at   by thread #7
 543 ==860571== Locks held: none
 559 ==860571==    at  : stbi__err(char const*) (stb_image.h:841)
 560 ==860571==    by  : stbi_load (stb_image.h:1135)
 561 ==860571==    by  : sf::priv::ImageLoader::loadImageFromFile(std::__cxx11::basic_string , std::allocator  > const&, std::vector  >&, sf::Vector2 &) (ImageLoader     .cpp:104)
 562 ==860571==    by  : sf::Image::loadFromFile(std::__cxx11::basic_string , std::allocator  > const&) (Image.cpp:125)
```
stb_image.h probably needs to be modified to use thread-safe error string to fix this issue
Discussion
- Good catch and thanks for the detailed description!

STB claims that their function [Link: `stbi_failure_reason()` is thread-safe], which I would interpret that also the writing part should be. In the sense that there should be no race condition _on the failure string itself_. Even then, it's still possible that this sequence happens:

1. thread A: `stbi_load()`
1. thread B: `stbi_load()`
1. thread A: `stbi_failure_reason()` -> returns error of image B

So I wonder why it crashes. Maybe we use an older STB version, it's not actually thread-safe, or there's another problem.
- It looks like that code you linked to is thread safe but not the version that sfml uses (see: [URL] I guess sfml just needs to update stb_image.h to fix the crash. From the change log:
