Title

Exo Player 2.3 droppedOutputBufferCount get increased during dash playbck

Description
### Issue description
While playing dash vod/live content using ExoPlayer 2.3, we observd "droppedOutputBufferCount" keeps incrementing (this is seen only for video and not for audio). Because of the incrementing value induces video stuttering.

### Reproduction steps
This is seen always with ExoPlayer 2.3 on all devices [android mobile (all major vendors) and android STB/TV ].

### Version of ExoPlayer being used
Exo Player 2.3

### Device(s) and version(s) of Android being used
This is seen always with ExoPlayer 2.3 on all devices [android mobile (all major vendors) and android STB/TV ].

We have cross verified the exo player code and observed that  droppedOutputBufferCount get incresed by checking bufferPresentationTimeUs and elapsedRealtimeUs difference is 30 ms
So could you kindly advice the below cases narrow down the issue
   1) How the player calculate bufferPresentationTimeUs and elapsedRealtimeUs 
   2) On what basis this 30 ms allocated as buffer time
   3) Is there any dependency in Dash manifest field with respect to this dropped buffer count or related 
       to the way in the raw video get packaged

Discussion
- It looks like the presentation timestamps of the frames in the video file are incorrect. They should be increasingly smoothly by 40000us each frame. The actual values (after decoder re-ordering) are:
```
34364096000
34364136000
34364176000
34364216000
34364256000
... [Log Snipped] ...
34366016000
34366056000
```
Note there are 8 frames (indicated above) where the presentation timestamp appears to jump backward in time by a significant amount. These frames are deemed as being late and so are dropped. The media is bad and should be fixed.

- Oops! Took another look at this and it seems we overflow when parsing sample composition time offsets from the trun, [Link: here], which is why the presentation timestamps end up looking incorrect. Changing `1000` to `1000L` on that line fixes the problem. Using `Util.scaleLargeTimestamp` is possibly better. We'll push a fix on Monday and get it into the 2.5.0 release.

Aside: I'm guessing your choice of timescale is unusually large, given we haven't seen this reported before.
