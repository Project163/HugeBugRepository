- that's the going theory, but also the Query hits the database when you iterate it..   it's designed to look kind of invisible.   Plus, it has a whole host of result-fetching methods all(), one(), first(), etc. stuck on it which look extremely similar to the ones that are on Result but don't behave the same way at all, that's a huge inconsistency.   

Overall, I have for years wanted there to be **one** way to write a query and execute it, and we had a lot of issues the way Query makes "convenient" decisions, like query(A) returns a list of objects, query(A.id, A.name) returns tuples?  lot of bug reports about that kind of thing.

a solution for dynamic that I'd prefer would include:

1. there's a single method that makes it "run the query"

2. im thinking there's a single name or method that also "gives you the query"

3. you can get the Result interface fully, so things like partitions(), first(), one_or_none() etc. all act consistently

4. you get a select() object that can be fully manipulated like any other select(), e.g. i want to put it into a union, etc.

otherwise, if we want this to act like "a collection that dynamically filters" then I'd want it to be some much more restricted inte

2. token that can be applied to select() - I like this one a lot except that it will be confusing if the relationship is not the right loader type, and I wish this could work with *all* the lazy strategies but right now `a1.bs` will do a lazyload by default

stmt = select(a1.bs).where(B.foo == 'bar')

3. special function that is kind of the same as with_parent() but is in terms of the parent directly

4. the above might be more succinct and actually easier to implement as

but there's no filter()/ order_by() etc. with that.    and also it doesnt work with asyncio.   if you're writing out WHERE criteria and all that I think you should have a select() object first.
