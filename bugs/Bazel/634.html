Title

Starlark http_archive cannot be referred by //external:[repo_name] from another external repo

Description
### Description of the problem / feature request:

A external repo pulled in by Starlark http_archive cannot be referred by //external:_[repo_name]_ from another external repo. @_[repo_name]_//:_[repo_name]_ works just fine.

### Bugs: what's the simplest, easiest way to reproduce this bug? Please provide a minimal example if possible.

```
git clone [URL]
cd bazel_http_archive_bug/main
bazel build @greeting//:greeting
```

### What operating system are you running Bazel on?

macOS 10.14

### What's the output of `bazel info release`?

release 0.19.2

### Any other information, logs, or outputs that you want to share?

Discussion
- Accessing things via `//external: ` is not recommended. However you seem to hit some other issues, starting with the processing of your WORKSPACE file. We definitely should not crash.
- The whole `//external` virtual package seems like a hack. A minimal
example for the crash is the following.

```
mkdir local
touch local/BUILD
mkdir main
cd main
echo 'local_repository(name="local", path="../local")' > WORKSPACE
bazel build //external:local
```

The error message is also quite telling: `No such attribute tags
in local_repository rule //external:local`, i.e., even though the
rule in charge for that target is a repository rule, it is treated
like a normal build rule, that should have tags, etc. That most
likely also explains the error message in the other case: if we
execute the implementaiton function of a repsoitory rule (in this
case http_archive) with a rule context instead of a repository_rule
context as an argument, we ask for trouble and expect to see the
error message we've seen.

Interestingly enough, it is not the case that the local repository is
actually mapped at that place; it is just the target for the repository
rule. Asking for something like `bazel build //external/local/...`
or `bazel build //external/local:it` does not even find the BUILD
file of the directory `local`, regardless what the contents of that
file are.

And that is not even talking about the case that you have a directory
called `external` at the top-level of your workspace...
