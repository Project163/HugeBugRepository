Title

heap-buffer-overflow with inline virtual text when a chunk ends at right edge and another chunk follows

Description
### Problem

ASAN reports heap-buffer-overflows with inline virtual text when a chunk ends at right edge and another chunk follows. Happen with both 'wrap' and 'nowrap'.

### Steps to reproduce

1. Run `nvim --clean` in a terminal that is at least 80 characters wide
2. Source the following file:
```vim
let ns = nvim_create_namespace('')
" Happens with both 'wrap' and 'nowrap'
" set nowrap
call nvim_buf_set_extmark(0, ns, 0, 0, {'virt_text': [[repeat('a', &columns)], ['b']], 'virt_text_pos': 'inline'})
```
3.
```
=================================================================
==990602==ERROR: AddressSanitizer: heap-buffer-overflow on address   at pc   bp   sp  
WRITE of size 1 at   thread T0
    #0   in schar_from_ascii **/src/nvim/grid.h:37:8
    #1   in win_line **/src/nvim/drawline.c:2939:9
... [Log Snipped] ...
  Right alloca redzone:    cb
==990602==ABORTING
```

### Expected behavior

No heap-buffer-overflow

### Neovim version (nvim -v)

v0.10.0-dev-420+g7e3ff8afa

### Vim (not Nvim) behaves the same?

No

### Operating system/version

Arch Linux

### Terminal name/version

kitty 0.28.1

### $TERM environment variable

xterm-kitty

### Installation

build from repo
Discussion
- Possibly related: [URL]
- What seems to be happening is that since the virtual text exactly fits the length, when we reach `(wlv.n_extra != 0 && (wlv.c_extra != NUL || *wlv.p_extra != NUL)))` on line 3072, `wlv.n_extra` is at 0, as we have finished drawing the first `a` virtual text. This results in no new row being placed, hence the `b` virtual text is placed on the current line after the buffer resulting in an overflow. Odd that is happens with nowrap though.

The best fix I can come up with is to just have a bool that indicates if there is more virtual text (other than the one which sets n_extra/p_extra) on that column/following, and update the above line accordingly. This bug also works with real text followed by virtual inline (when the real text exactly fits into the grid). This makes this a little bit harder, since I'm not sure if that column has been redrawn yet. I've opened a pr which attempts to fix this. Not sure if this is the best approach though.
