Title

beta 0.8.0b2: creating timeseries with index in year 1400 yields wrong timestamp

Description
There seems to be some kind of wrap-around phenomenon if your index is too far away from now. For example if I create a timeseries with an index in 1400, the timeseries I get back has an index which is some time in 1984:

```
python
In [1]: import datetime, pandas

In [2]: pandas.version.version
Out[2]: '0.8.0b2'
... [Log Snipped] ...
In [4]: ts
Out[4]: 1984-07-22 23:34:33.709551    1
```

It doesn't seem to be a display issue because I can do:

``` python
In [7]: ts.index[0].to_pydatetime()
Warning: discarding nonzero nanoseconds
Out[7]: datetime.datetime(1984, 7, 22, 23, 34, 33, 709551)

```

I tested I could get the same behaviour both using 32-bit and 64-bit python on windows. It seems to work fine for 0.7.3:

```
python
In [1]: import datetime, pandas

In [2]: pandas.version.version
Out[2]: '0.7.3'
... [Log Snipped] ...
In [4]: ts.index[0]
Out[4]: datetime.datetime(1400, 1, 2, 0, 0)
```
Discussion
- Actually it seems to work fine when constructing the index from strings instead of datetimes:

``` python
In [1]: import pandas

In [2]: ts = pandas.TimeSeries(index=['1400-02-01'], data = [1])

In [3]: ts
Out[3]: 1400-02-01    1
```

and the numpy.datetime64 construction from datetime.datetime seems fine as well:

``` python
In [5]: np.datetime64(datetime.datetime(1400,1,2))
Out[5]: 1400-01-02 00:00:00
```

so the blame seems to be on pandas for this one.
- `DatetimeIndex`, which uses a nanosecond unit, doesn't support dates that far back in time. This was a deliberate design tradeoff in work revamping the time series processing infrastructure. You can, however, represent dates that far back using `PeriodIndex`. Could you tell me a bit more about your use case?

- Obviously not? =) There are many more places where overflow checks need to be inserted. 

Why not just replace the minimum Boost timestamp with a crazy, but in range pandas timestamp (like `1700-01-01`)}

Performance in alignment should be roughly equivalent (int64 data under the hood).
- The timestamp replacement from a crazy to another crazy but in range timestamp was something I thought about but we might have some edge use cases, although very few of them I would guess, where you need dates earlier than 1677.

Maybe going with PeriodIndex is the best solution for now.
