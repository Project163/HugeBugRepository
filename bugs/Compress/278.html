Discussion
- The archive most likely is corrupt as InfoZIP's unzip says all of the entries have got CRC mismatches. Of course ZipFile shouldn't hang but rather detect the corruption. Am looking into it.
- git commit 2a2f1dc4 fixes the problem (the loop variable was an int, but the the upper bound was a long so the loop wouldn't terminate if the upper bound was bigger than MAX_INT). 

 Now reading the archive dies with an  ArrayIndexOutOfBoundsException  in  parseFileFormat  as the "ivSize" is too big. I'd prefer to turn this into a more useful exception but the method is public and declares no checked exception, so  ZipException  cannot be used. I'm not sure which RuntimeException would be more appropriate - if any.
- ... [Middle Discussions Snipped for Brevity] ...
- I don't think  IllegalStateException  is really correct here as it's not a matter of state of the stream or the field but rather a function of the input. I think leaving things at  ArrayIndexOutOufBounds  is good for now.
- It was later realized this issue can be used to mount a denial of service attack against services using Commons Compress which then became CVE-2018-1324
