- Again, I don't think listing input types solves the issue.  The problem with doing something like that is that `saturate_cast` is just a composite op that calls other ops, including `tf.maximum` and `tf.cast`.  If we ever modify the valid input types for `tf.maximum` or `tf.cast`, it would implicitly modify the valid input types to `tf.saturate_cast`.  They would all need to be kept synced.

We could add a link to the `tf.cast` documentation for further details.

And perhaps it _should_ work for complex inputs.  Complex to real should do what I described above (although again, would produce a warning just as `tf.cast` does).  Complex to complex should probably saturate-cast the real and imaginary components separately.
