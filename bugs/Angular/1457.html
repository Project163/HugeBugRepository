## Current behavior
This is rather informational in Angular 2+ project.

Due to ReactiveX/rxjs#2675 and the fact that AsyncPipe do not clean the reference to `ChangeDetectorRef` - there can be memory leaks. They might be big, as `ChangeDetectorRef` and its subclasses can contain DOM detached elements of previous view.

The problem on rxjs angular boundary lies in passing the closure to rxjs in `AsyncPipe#subscribe`:

This closure is held internally by rxjs `SafeSubscriber` and never released, so it causes that AsyncPipe object cannot be released with its transitive dependencies (ChangeDetectorRef).

```
this._subscription = this._strategy.createSubscription(obj, function (value) { return _this._updateLatestValue(obj, value); });
```

## Expected behavior
There is no yet permanent fix yet, but to limit the memory leakage, I propose to reset `ChangeDetectorRef` too in `onDestroy` method.

## Minimal reproduction of the problem with instructions
See ReactiveX/rxjs#2675 although it is not Angular code

- Using angular6, I can't reproduce the issue. It seems there is a memory leak in the shareReplay operator of rxjs 6 (and probably former versions), tracked there: [URL] 

This stackblitz may provide some insight: [URL]

* The route A uses the shareReplay operator and subscribes using the aync pipe. Instances of this component are never garbage collected.
* The route B (un)subscribes manually using lifecycle hooks and avoid using the shareReplay operator. Instances are garbage collected.
* The route C does not use any share/shareReplay operator and subscribes using the async pipe. I don't understand the behaviour for this one, but it seems that both subscribers are able to receive the emitted values and that the component is correctly garbage collected.
* The route D uses the share operator and subscribes using the async pipe. Instances are correctly garbage collected.
* The route E uses the publishReplay + refcount operators as an alternative to the shareReplay operator and subscribes using the async pipe. Instances are correctly garbage collected.
- @cghislai - I could not access your Stackblitz. It would be great if you could recreate it as a useful test environment for this issue.

It looks to me like this is really an upstream issue with RxJS usage - i.e. if you use certain kinds of RxJS operators on observables that you pass to `async` pipe you can get memory leaks.

That being said, it also seems that it would be prudent to apply the fix proposed by @czterocyty in [URL] which ensures that that `async` pipe is disconnected from the change detector when it is destroyed.

We could really do with a solid reproduction of the memory leak to allow us to test this.
- @petebacondarwin indeed, it is by using the shareReplay operator that we obtain memory leak.

The issue has been addressed upstream by the addition of a `refCount` paramter flag, see [URL]
Using this parameter, the shareReplay operator will unsubscribe from its upstream observable when there are no longer any downstream subscription, allowing the angular component to be garbage collected.
