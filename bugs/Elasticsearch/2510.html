Title

Rolling Upgrading a Cluster from pre-7.3 to a post-7.3 Version can Break Repository Verification

Description
This issue is the result of [URL] and upgrading from a version that doesn't understand the voting only master role to one that does.

Currently, if we rolling-upgrade a cluster containing a voting only master node, we can get into a situation where if we upgrade the voting-only master first, the other nodes will potentially never pick up the role change unless the voting only master is restarted (since the voting only master will not send the voting_only role to old version masters when joining the cluster).

This doesn't seem to have any side effects so far, other than breaking the fix for repository verification in #61016. The breakage comes because the voting_only master will stop creating repositories locally as is desired, but the actual master node will still continue to send it repository verification requests, leading to errors like:

```
[{\"type\":\"repository_verification_exception\",\"reason\":\"[found-snapshots] [[xxxxx, 'RemoteTransportException[[tiebreaker-0000000002][xxxxx][internal:admin/repository/verify]]; nested: RepositoryMissingException[[found-snapshots] missing];']]\"}],\"type\":\"repository_verification_exception\",\"reason\":\"[found-snapshots] [[xxxxxxx, 'RemoteTransportException[[tiebreaker-0000000002][xxxx:xxxx][internal:admin/repository/verify]]; nested: RepositoryMissingException[[found-snapshots] missing];']]\"},\"status\":500}], headers: [List()], protocol: [HttpProtocol(HTTP/1.1)]"}]
````

when running repository verification requests, even though the repository otherwise is functioning just fine.
