Discussion
- Reverting [URL] on the client fixes the issue. For some reason, setting `RECV_INITIAL_METADATA` changes the error message?
- When deadline exceed, [Link: CallError raised], then [Link: remote_read] aborted without setting `@metadata_received = true`.
With [URL] [Link: receive_and_check_status] finds out  `@metadata_received` is false, so RECV_INITIAL_METADATA is sent again and caused the `grpc_call_start_batch failed with outstanding read or write present (code=8)` error.

The complexity here is that there is not enough information propagated to active_call.rb that whether `RECV_INITIAL_METADATA` was sent or not when there was a CallError.

However send `RECV_STATUS_ON_CLIENT` alone without `RECV_INITIAL_METADATA` (although against grpc protocol) indeed can correctly get the deadline exceed error.

As a result I think reverting [URL] might be a good idea, and it appeared didn't solve the mentioned test failure in the PR, which was also a deadline exceed error I think may actually caused by test running slow.

CC: @apolcyn
- @apolcyn @ctiller This issue actually caused a significant regression in production because we handle `DeadlineExceeded` and other `StandardError` types gracefully, but `GRPC::Core::CallError` does NOT inherit from `StandardError`: [URL]

I believe the revert in [URL] solves this issue, so I would appreciate a quick review. Thanks!
