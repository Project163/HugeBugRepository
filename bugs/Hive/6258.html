Title

Snapshot Isolation does not work for Micromanaged table when a insert transaction is aborted

Description
TestTxnCommands2#writeBetweenWorkerAndCleaner with minor  
changes (changing delete command to insert command) fails on MM table. 

 Specifically the last SELECT commands returns wrong results.  

 But this test works fine with full ACID table.  
====== 
MM table inserts were not making entries into TXN_COMPONENTS, thus the  txnHandler.cleanEmptyAbortedTxns();  logic in  Initiator  can wipe out TXNS entry for an aborted transaction before the relevant files on disk are removed.
Discussion
- The test scenario for this jira is: 
1. Create a MM table 
2. Insert 2 rows into the table. 
3. Create TxnHandler and send a minor compaction request on the table.  
4. Run Compaction Worker to do compaction. 
5. Start an insert transaction and roll back this transaction. 
6. Execute SELECT command and verify the result set (should be 2 rows). 
7. Run Initiator. 
8. Execute SELECT command and verify the result set. 

 The above test case fails at 8 with a result set of 3 rows with the current code set.
- The problem is simple:  
DbTxnManager.acquireLocks(..) does not set a flag "isAcid" for LockComponent object for the  
MM table and thus a row for the MM table is not inserted into TXN_COMPONENTS. 

 So when compaction initiator calls a method to delete empty-component-transactions,  
the aborted transaction, let's say, id 25, at step# 5 is deleted (but this transaction left delta directory). 

 Then SELECT at 8 does not contain 25 as aborted transaction in its ValidTxnList because the metadata in the Metastore for transaction 25 is gone. So the SELECT decides that the delta directory for 25 is valid and returns 
the row.
