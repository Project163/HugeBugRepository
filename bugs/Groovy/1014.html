Title

Some GroovyClassLoader issues around recompile

Description
After staring at GroovyClassLoader for some bit trying to understand whether one should use loadClass vs parseClass, I ran across a couple of situations where I do not believe the right thing happens.  BTW, I do now understand the difference although for my use case, loadClass doesn't fit the bill and it seems GroovyScriptEngine hit the same issues when deal with pure scripts.  Anyhow.... 

 This is looking at Groovy 1.5.6

Discussion
- Ah, I see, if cls was not null before then, if recompile fails, it will not remove the class from the cache. Yeah, that sounds like a bug. 

 As for the second... I would say it is right to remove the entry from the source cache when you create anew not cacheable code source. Now the question is if the code source is really not cacheable.  In general, just coming from any URL I would say it is not cacheable. WE need to get a file object for it to be sure. So what is needed at this place is a check if the URL is actually representing a file on the file system (what about files in jars?), then we could use parseClass(File), which automatically creates a cacheable code source. 

 The conclusion that a parseClass followed by a loadClass of that Class will lead to the class being no longer cacheable works only if a recompilation happens. But once recompilation is done, you are right, it looks like the ability to cache something will be lost.... which sounds like a bug too 

 As for GroovyScriptEngine... actually that tries to solve a problem a bit different. Sure it tries to handle recompilation, but not of a single class. If you for example have class A extends B and B is changed, then you usually want to have a recompiled A as as a recompiled B, because A depends on Band a change there might affect A too. GroovyClassLoader is not suited for that kind of dependency tracking and no thread local loadClass trick will make it really work out. What GroovyScriptEngine needs is a complete rewrite. I needs to hook into the compiler and really track which classes are needed there. A custom phase operation in for example the code generation phase could be used for this.
