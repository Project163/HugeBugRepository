Title

cquery fails on remote jdk repository

Description
Attempting to run cquery on the remote jdk repository (`@remotejdk11_linux`) incorrectly reports that there are no targets.

```
$ bazel query '@remotejdk11_linux//...'
@remotejdk11_linux//:xjc
...
$ bazel cquery '@remotejdk11_linux//...'
WARNING: /home/jcater/.cache/bazel/_bazel_jcater/ /external/remotejdk11_linux/BUILD.bazel:108:10: target '@remotejdk11_linux//:bootclasspath' is deprecated: Don't depend on targets in the JDK workspace; use @bazel_tools//tools/jdk:current_java_runtime instead (see [URL]
... [Log Snipped] ...
WARNING: --keep_going specified, ignoring errors. Results may be inaccurate
INFO: Empty query results
```

The deprecation warnings are very strange here.

An error is probably being swallowed somewhere.
Discussion
- Debugging this is interesting. The failure occurs in [Link: `RecursivePackageProviderBackedTargetPatternResolver.findTargetsBeneathDirectory`].

The first time this is called, the `RecursivePackageProvider` is a [Link: `EnvironmentBackedRecursivePackageProvider`], and this correctly returns the targets.

The second time, however, the `RecursivePackageProvider` is a [Link: `GraphBackedRecursivePackageProvider`], which returns no targets. This appears to be because this implementation is checking the `universeTargetPatterns`, and that is set to `//...`, which does not match `@remotejdk11_linux`, and so all targets are filtered out.

So the question is: why are there multiple instances of `RecursivePackageProviderBackedTargetPatternResolver` in use, why are they different, and is this the correct use of `universeTargetPatterns`?
- It looks like that universe scope is defined from the [Link: `PostAnalysisQueryEnvironment`]. However, the code is clearly wrong: `//...` does not mean "all patterns", it means "all patterns in the main repository". I'm going to investigate if this can be fixed.

Unfortunately, this ignores the `--universe_scope` flag.
