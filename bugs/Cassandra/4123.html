Title

Altering a UDT might break UDA deserialisation

Description
CASSANDRA-10650   switched UDA's  initcond  serialisation in schema to its CQL literal. This means that if any particular field is renamed in the UDT, or of its type gets changes, we will not be able to parse initcond back. 

 We should either: 
1) Forbid renames and type switches in UDTs that are being used in UDAs, or 
2) Make sure we alter the UDAs in schema alongside the new UDT at all times
Discussion
- I think preventing such a change is the better option. Otherwise we'd also have check permissions on the aggregates. Additionally changing nested tuple/collection/type structures might become a nightmare. 

 Will also see whether we need a check for "garbaged" initcond values into LegacySchemaMigrator.
- I'm fine with simply preventing it for 3.0.1/3.1, to fix the bug itself, but I'd prefer that we at least eventually address this properly.
