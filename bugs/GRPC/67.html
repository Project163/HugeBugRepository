Title

Signficant unnecessary but avoidable allocations when TCP trace enabled at ignored log-level

Description
There are multiple code-paths that follow the pattern:

```
if (grpc_tcp_trace.enabled()) {
          size_t i;
          for (i = 0; i  read_slices->count; i++) {
            char* dump = grpc_dump_slice(tcp->read_slices->slices[i],
                                         GPR_DUMP_HEX | GPR_DUMP_ASCII);
... [Log Snipped] ...
          }
        }
```

where `grpc_dump_slice` builds a nul-terminated string of the fragment; this applies to most network read/write; useful for debugging.

However! If the log-level is low (meaning: less logging - for example ERROR only), but the trace is enabled: this performs a **LOT** of unnecessary CPU and memory overhead, including allocating/releasing the memory for the chunks, and performing hex+ascii dumps - only to have it all ignored by the log-level check.

Proposal: add a log-level test earlier, so that expensive work is not performed for no reason; for example:

```
if (grpc_tcp_trace.enabled() && gpr_should_log(GPR_LOG_SEVERITY_INFO)) // whatever the relevant log-level is
```

or, perhaps more cleanly (but with a new overload):

```
if (grpc_tcp_trace.enabled(GPR_LOG_SEVERITY_INFO)) // whatever the relevant log-level is
```

- [URL] (INFO)
- [URL] (INFO)

However, there may be many more
