Title

Allow third party extensions to avoid validating the default JAXB context

Description
### Describe the bug

The change   by @Sgitario has brought hard times to Quarkus CXF and Camel Quarkus. Basically all our CXF related tests fail, because duplicate JAXB classes seem to a normal situation in CXF. 

Here an example of the stack trace see when running [Link: quarkus-cxf-integration-test-client]: 

```
Caused by: java.lang.IllegalStateException: Failed to configure JAXB context
        at io.quarkus.jaxb.deployment.JaxbProcessor.validateContext(JaxbProcessor.java:395)
        at io.quarkus.jaxb.deployment.JaxbProcessor.setupJaxbContextConfig(JaxbProcessor.java:318)
        at java.base/jdk.internal.reflect.DirectMethodHandleAccessor.invoke(DirectMethodHandleAccessor.java:104)
        at java.base/java.lang.reflect.Method.invoke(Method.java:578)
... [Log Snipped] ...
        at io.quarkus.jaxb.deployment.JaxbProcessor.validateContext(JaxbProcessor.java:393)
        ... 10 more
```

In this particular case, both conflicting classes come through transitive dependencies of CXF:

* `jakarta.xml.ws.wsaddressing.W3CEndpointReference` comes via

```
io.quarkiverse.cxf:quarkus-cxf-integration-test-client:2.0.0-SNAPSHOT:jar:
        -> io.quarkiverse.cxf:quarkus-cxf:2.0.0-SNAPSHOT:jar:
        -> org.apache.cxf:cxf-rt-frontend-jaxws:4.0.0:jar:
        -> org.apache.cxf:cxf-rt-bindings-soap:4.0.0:jar:
        -> jakarta.jws:jakarta.jws-api:3.0.0:jar
```

* `org.apache.cxf.ws.addressing.EndpointReferenceType` comes via

```
io.quarkiverse.cxf:quarkus-cxf-integration-test-client:2.0.0-SNAPSHOT:jar:
        -> io.quarkiverse.cxf:quarkus-cxf:2.0.0-SNAPSHOT:jar:
        -> org.apache.cxf:cxf-rt-frontend-jaxws:4.0.0:jar:
        -> org.apache.cxf:cxf-core:4.0.0:jar
```

I doubt we can exclude the artifacts and I doubt we can exclude the classes via `quarkus.jaxb.exclude-classes`.

Advising all users of `camel-quarkus-cxf` and `quarkus-cxf` to always have `quarkus.jaxb.validate-jaxb-context=false` in their `application.properties` do

- To sum up, we're now validating the generated JAXBContext at build time, so users can fix this kind of failure before running the application, but the Quarkus CXF and Camel Quarkus extensions use third-party dependencies that produce an invalid JAXBContext and you can't fix this because you do need these dependencies. 

About the options you suggest:
- A. Validate the JAXB context only if some JAXBContext injection point is available in the user application.

I would not go in this direction because at the moment users want to use the JAXBContext and use one of your extensions, it would fail and users would not directly see how to address it. 

- C. Have some sort of ValidateDefaultJAXBContextBuildItem that would allow third-party...

Again, I would not go in this direction because users would miss this feature if they do want to use the generated JAXBContext. 

Therefore, option B looks good to me. However, I think it would be simpler to create a new build item to exclude the class that causes the conflict. But, on your side, you would need to produce this build time with the mentioned classes.
