Title

Determination of MAX_DIRECT_MEMORY in io.netty.util.internal.PlatformDependent fails on z/OS

Description
### Expected behavior
 MAX_DIRECT_MEMORY, which controls later behaviour of Netty , should be initialized with correct value.

### Actual behavior
On z/OS netty initializes this value with 64M, even the direct accessible memory is actually unbounded.

Reason is the way, how the IBM Java VM administrates direct memory. 
The Windows- or Linux-based VMs report the correct final value asking the corresponding APIs , i.e. sun.misc.VM.maxDirectMemory(().
But the IBM JVM on z/OS returns here just the initial start value for accessible direct memory, 64MB, even this is not the final limit. (see [Link]
The IBM JVM increments this value on demand in 32MB steps.

Netty asks only once in a static initializer for this value and, for z/OS, erroneously assumes, that would be the final value. 
The so unnecessarily bounded value of 64M leads finally to 
 memory (used: 67092277, max: 67108864)
 at io.netty.util.internal.PlatformDependent.incrementMemoryCounter(PlatformDependent.java:615)

Conclusion: on z/OS the used APIs offer not the desired correct value for available direct memory.

Suggested solution:
the heuristic in io.netty.util.internal.PlatformDependent.maxDirectMemory0() has to consider the System.os. In case of z/OS the first try with sun.misc.VM.maxDirectMemory() is to skip. the following search for -XX:MaxDirectMemorySize or Runtime.maxMem() may offer the correct value.

by the way: limit the available direct memory with -XX:MaxDirectMemorySize=512M helps as workarround. Adding this argument at start the IBM VM returns 512M as initial value which is quite the correct final value.

run added code on z/OS
