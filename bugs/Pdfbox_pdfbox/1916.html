Discussion
- Here's what I found out so far... 
 
	 it's a type 0 otf font with CFF 
 

 
	 The first glyph should appear as "T". Its code is 175, its GID (according to both PDFDebugger and DTL OTM light) is 17. 
 

 
	 When PDFBox gets the path (in PDCIDFontType0.java), it uses the CID 175. The GID 175 is the "ü" that appears. So a CID to GID transformation is missing. 
 

 The PDF specification has this 
  There are two cases, depending on the contents of the font program: 
 • The "CFF" font program has a Top DICT that uses CIDFont operators: The CIDs shall be used to determine the GID value for the glyph procedure using the charset table in the CFF program. The GID value shall then be used to look up the glyph procedure using the CharStrings INDEX table. 

   

 NOTE Although in many fonts the CID value and GID value are the same, the CID and GID values can differ. 
 • The "CFF" font program has a Top DICT that does not use CIDFont operators: The CIDs shall be used directly as GID values, and the glyph procedure shall be retrieved using the CharStrings INDEX.  
   

 So I guess we have the first case, but I don't know how to identify whether "Top DICT that uses CIDFont operators".
