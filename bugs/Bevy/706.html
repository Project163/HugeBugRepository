Title

Observers, systems and commands that use closures and panic require explicit return type after Rust 2024 edition

Description
## Bevy version

[Link: v0.16.0-rc.3]

## \[Optional\] Relevant system information

Rust 1.86.0, 2024 edition.

## What you did

```
rust

fn test() {
    let mut app = App::new();
    app.add_observer(|_: Trigger | {
... [Log Snipped] ...
#[derive(Event)]
struct TestEvent;
```

## What went wrong

The code no longer compiles, though it worked in Bevy 0.15.0 (which used the 2021 edition).

It also compiles when I explicitly specify the return type `()`:

```
rust

fn test() {
    let mut app = App::new();
    app.add_observer(|_: Trigger | -> () {
... [Log Snipped] ...
#[derive(Event)]
struct TestEvent;
```
Discussion
- As discussed [Link: on Discord] with @NthTensor, this is due to Rust 2024, and is not our bug. It's arguably not a bug at all!

See [URL] for the context on this change, which recommends the same workaround of explicitly specifying the return type. The same code will compile just fine as functions rather than closures, because the return type of functions is never inferred (even if it's defaulted to ()).
- Actually, reopening this to track the fix in the same issue: we should be able to just implement these traits for functions which return the `!` (never) type.
- ... [Middle Discussions Snipped for Brevity] ...
- [URL] We can't fix it yet on stable 🙃 Definitely a "complain upstream" problem.

Note that this regression is only for closures, so I would consider this a moderate-severity UX problem. I almost never write closures for systems / observers. It's more common for commands though.
- I expect the inline Observer closure use case to go up considerably when next generation Bevy UI takes off. Imo solving this is a "big deal".
