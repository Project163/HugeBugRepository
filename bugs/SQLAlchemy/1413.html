Title

versioned_history example no longer works with sqlalchemy 2.0

Description
### Describe the bug

The `versioned_history` example relies on `sqlalchemy.orm.mapper` which was deprecated in 1.4 and removed in 2.0.

[URL]
[URL]

With sqlalchemy 1.4 I was able to replace `mapper` with `map_imperatively`.
With sqlalchemy 2.0 the same attempted change errors out due to changes in [URL]

### To reproduce

```
python3 -m unittest examples/versioned_history/test_versioning.py
```

### Error

Running the example
```
sqlalchemy.exc.InvalidRequestError: The 'sqlalchemy.orm.mapper()' function is removed as of SQLAlchemy 2.0. 
Use the 'sqlalchemy.orm.registry.map_imperatively()` method of the ``sqlalchemy.orm.registry`` class to perform classical mapping.
``` 

Running the example with attempting to change `mapper` with `map_imperatively`
```
File "sqlalchemy/orm/decl_api.py", line 1357, in _add_manager
    assert manager.registry is None
```

### Versions

- SQLAlchemy: 2.0+

next, the way that `map_imperatively()` works now is not a direct port of `mapper()`, so the particular hook that's being used here, `__mapper_cls__`, which fortunately seems to be undocumented, has to actually return the `Mapper` class, not the `mapper` function's equivalent anymore.

however that fix sucks.   I am not able to get a better fix working right now as the history thing seems to work in an extremely specific way.  so far it's looking like I have to add a new mapper configuration hook, this will require some effort.
- **Mike Bayer** has proposed a fix for this issue in the **main** branch:

**WIP - port history meta to 2.0** [URL]
- the attempts im making to restore this in a better way are suggesting that this might benefit from adding a new mapper event `after_mapper_constructed`, just to get in that spot.  this spot has the following special things:

1. the `polymorphic_on` is actually configured here
2. we can add things to the mapper, or make new mappers, without the need for `configure_mappers()` to be called
3. if we do make new mappers, they *will* get configured on the next configure() call
4. we can iterate through the mapper's properties

there's no other hook right now that has all those things at once.
