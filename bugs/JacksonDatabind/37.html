Title

`@JacksonInject` causes deserialization failure (unresolved forward reference)

Description
Jackson 2.4.4 is able to successfully deserialize forward references, but it fails to do so if the constructor contains a `@JacksonInject` parameter.

- Actually I think this is different, and bit trickier. Problem is that there is an actual cycle from deserializer perspective, since `parent2` may not be constructed before all JSON for it (and its descendants) are consumed; but its child `child2` needs parent reference passed via constructor. So the solution here would be to remove `@JsonCreator` on `child2` with non-creator alternative.

Except that in theory, since `parent2` only needs injectable value, perhaps implementing #1268 would allow this to be handled even without removing of `@JsonCreator`.

``` json

```

and the reason this can not be resolved at this point is only partially due to `@JacksonInject`. The underlying problem is that neither `Parent2` nor `Child2` may be constructed before all data is available, as both have `@JsonCreator` annotated constructor.

### Testing Recommendations

Before implementing a fix:
1. Create additional test cases isolating different scenarios:
   - Injectable + forward ref in constructor param (current failing case)
   - Injectable + forward ref in regular field (works per test #538)
   - No injectable + forward ref in constructor param (need to verify)
2. Test with deeper nesting (3+ levels of circular references)
3. Test with multiple forward references in single constructor

## Conclusion

Issue #639 exposes a fundamental limitation in how Jackson handles the combination of:
- Property-based creators (constructors/factory methods)
- Injectable constructor parameters
- Forward references in those same constructor parameters

The current architecture's timing of ObjectId binding (inside `creator.build()`) conflicts with the timing of `BeanReferring` initialization (after `creator.build()`). The attempted fix reveals that the problem is deeper than just timing - the forward reference registration mechanism doesn't properly distinguish between constructor parameter dependencies and property dependencies.

A proper fix will require careful architectural changes to one of the core deserialization flows, with thorough testing to ensure existing functionality isn't broken.
