Title

Parallelizable attribute not invalidating invalid parallel scope combinations

Description
I was looking through the ParallelizableAttribute.cs, and the changes made with [URL] I noticed that there is the functionality to invalidate tests with invalid parallel combinations in the ApplyToTest() method, but it does not appear to be actually invalidating them. Is this intentional? 

Using 3.7.1, 
I tested and was able to reproduce the hanging found in [URL] by placing [NonParallelizable] on the test fixture, and [Parallelizable(ParallelScope.Self)] on the test method. 

I placed [Parallelizable(ParallelScope.Fixture)] on a test method with no parallelization on the fixture, and the tests ran and passed normally without any parallelization.

Instead of invalidating the setting, it could potentially be useful. What are your thoughts on allowing ParallelScope.Fixtures for methods? It would be useful in the case where you would only like to run one particular test one at a time at the fixture level, but run the rest of the tests in the fixture at ParallelScope.Self. It allows for the specific test in the fixture to be isolated without affecting other fixtures in the way ParallelScope.None does.
Discussion
- Both the issues you refer to are clearly marked as fixed for the 3.8 release, so you won't see any sign of the changes when running 3.7.1. You can, if you like, download later dev versions of the framework from our myget feed.

`ParallelScope.Fixtures` indicates that any fixtures below that point in the tree should be run in parallel. It's not valid on methods because methods don't contain fixtures.

If you want some tests in a fixture to be run in parallel (with one another) those fixtures should be marked as Parallelizable (ParallelScope.Self or omitted). 

In general, you should avoid those settings marked as non-browsable even though some versions of VS show them in error in the Intellisense. Use NonParallelizable rather than ParallelScope.None.
