Title

Thread safety and DefaultCompositeByteBuf / CompositeByteBuf

Description
Hi Guys,

Am having an issue with thread safety and the use of DefaultCompositeByteBuf by multiple threads at once.

Currently our application creates a CompositeByteBuf (of up to 512MB in size when all underlying ByteBuf's are included), and we are passing this single ByteBuf off to a number of threads to have specific read-only actions performed. (There is no modification of the ByteBuf itself, the threads are just reading information from it). These operation include compression of the ByteBuf, hashing it (md5, sha256, etc), and string/keyword/byte[] searches, etc in separate threads.

To allow all threads to operate on the single buffer concurrently and independently, we are using `duplicate()` to create duplicate ByteBuf before passing the ByeBuf off to each thread. (This allows each thread to maintain it's own indexes/marks into the ByteBuf, and in theory should allow independent use of a shared CompositeByteBuf).

eg.

``` java
ByteBuf buf = ...
CompressionThread comp = new CompressionThread(buf.duplicate());
HashThread hash = new HashThread(buf.duplicate());
comp.run();
hash.run(); 
// wait for completion and get results.
```

However during thread execution we are getting `IllegalStateException("should not reach here - concurrent modification?");` exceptions in `findComponent()` and `toComponentIndex()`, despite the ByteBuf being duplicated.

From what we can gather, not all state information is being replicated, just the indexes and marks (which according to the javadoc is all `duplicate()` it does), however for composites, this doesn't allow for multiple threads to access the duplicates while sharing the underlying buffer?

Alternatively, we could use copy(), but this duplicates all information, so we end up 3-4 copies of the original ByteBuf, which for us means instead of having 512MB shared between multiple threads, we end up with 4x 512MB buffers being used!

Thoughts, ideas or workarounds are greatly appreciated.

- Thanks for reporting a bug.  A workaround I can think of is to make a non-composite copy first and then duplicate the copy multiple times assuming this bug affects only `DefaultCompositeByteBuf`.
- Hi, No problem on the bug report. As someone who does other F/OSS stuff on the side, it's the only way to know when something is broken. ;)

We've implemented our own patch for this issue, and it has resolved it for our own use case. (I won't warrant it's fixed it for all use cases).

In `DefaultCompositeByteBuf`, we removed the two variables `lastAccessed` and `lastAccessedId`, and rewrote `findComponent()` and `toComponentIndex()` as follows:

```
java
    @Override
    public int toComponentIndex(int offset) {
        assert !freed;
        checkIndex(offset);
... [Log Snipped] ...
        throw new IllegalStateException("unknown offset?");
    }
```

We also removed references to those variables in `updateComponentOffsets()` and elsewhere as needed.

While I acknowledge the above replacements are not as performant as the originals, they are essentially stateless so should allow multiple threads access to the duplicates without issues. (I've used a for loop in the `findComponent()` method to avoid creating an iterator on `components`.) 

We also considered writing a `duplicate()` method as an alternative, but we got the above working quicker, and requires less deeper knowledge of netty.

PS. You're free to use the above replacements if desired without restriction.
