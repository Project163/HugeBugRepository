Title

'Exception deframing message' when building large outputs remotely

Description
### Description of the problem / feature request / question:

I'm trying to build tensorflow  remotely and getting this exception in the process(full output at end of the issue):
```
WARNING: CppCompile remote work failed (io.grpc.StatusRuntimeException: INTERNAL: Exception deframing message)
io.grpc.StatusRuntimeException: INTERNAL: Exception deframing message
...
Caused by: io.grpc.StatusRuntimeException: INTERNAL: Frame size 167773175 exceeds maximum: 104857600, 
...
```

The problem is that some of the tensorflow outputs are more than 100Mb in size, and they are being sent in a single grpc "message", hitting the grpc's limit for the maximal input message size.

### If possible, provide a minimal example to reproduce the problem:
1. Compile `bazel` and `//src/tools/remote_worker `
2. Run remote_worker
```
./bazel-bin/src/tools/remote_worker/remote_worker --listen_port=8080 --work_path=/tmp/test
```
3. Unpack [Link: huge-link.tar.gz].
4. Run bazel to build it
```
bazel --host_jvm_args=-Dbazel.DigestFunction=SHA1 build --spawn_strategy=remote --remote_worker=localhost:8080 --remote_cache=localhost:8080  --noremote_allow_local_fallback --noremote_accept_cached --verbose_failures //:huge
```

**Expected**: builds suceeds
**Actual**: exception "Frame size 167773175 exceeds maximum: 104857600" is fired.

Discussion
- The proper solution to this problem is to chunk the protobuf message into smaller messages (say 4KiB). We are on a very old version of gRPC and since then gRPCs default max message size has been decreased to a saner 4MiB. 

The main problem with very large message sizes is that the whole message needs to eventually be reconstructed in memory. Lot's of buffering overhead internally in gRPC and also (moving) garbage collectors very much dislike objects/byte[] sized >100MiB.
- We're already chunking protobuf messages, aren't we? Maybe the server-side isn't chunking, because our upload code path is chunking, unless I'm misremembering.
- I think this is a bug in remote_worker, not Bazel as such.
