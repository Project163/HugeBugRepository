### Steps to reproduce

In words:
1) Set the "backup" option on.
2) Open a symlink to a file in a different directory.
3) Write to the file. This creates a file in the backup directory.
4) Write to the file again. This one fails because it cannot overwrite the backup file created in step 3.

I wrote a script to make doing the bisect easier, it might come in handy.

```
#! /bin/bash

# Make a backup dir free of any previous files
mkdir test_backupdir

... [Log Snipped] ...
# Running "ls -lA test_backupdir" shows that the only file is a symlink named
# "link_to_test.txt~" pointing to the path of the test.txt file
```

### Actual behaviour

The second attempt to write to the symlink fails.

In versions with the bug, the backup file is a symlink to the real one. In versions without it, it is a real text file.

### Expected behaviour

You can write to a file (or symlink to that file) as many times as you'd like.
Discussion
- I took a quick look at the commit in question (https://github.com/neovim/neovim/pull/9709/commits/ ) and the libuv docs (http://docs.libuv.org/en/v1.x/fs.html#c.uv_fs_copyfile), and I think the problem is that we're copying the literal file that we're editing, i.e. the symlink, instead of the file that our link is pointing to. Without the flag that the commit added, libuv appears to have been following through the symlink to get to the underlying file, while with the flag it doesn't follow the link.

If that's truly the case, then that seems like an inconsistency on libuv's part and the real change needs to be made upstream there.
