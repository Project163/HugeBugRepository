Title

Built-in multi-character commands with fake motions (`dd`, `<<`, `yy`, ...) are hard to override with custom mappings

Description
### Neovim version (nvim -v)

Latest

### Vim (not Nvim) behaves the same?

Yes

### Operating system/version

macOS 12

### Terminal name/version

N/A

### $TERM environment variable

N/A

### Installation

From source

### How to reproduce the issue

## Scenario 1

- `:map dd  echo "Hello, world" `
- Press `d`.
- Wait more than `timeoutlen`.
- Press `d`.

## Scenario 2

- `:map dd  echo "Hello, world" `
- Press `d`.
- Wait more than `timeoutlen`.
- Press `dd` quickly.

### Expected behavior

## Scenario 1

`Hello, world` is printed.

## Scenario 2

`Hello, world` is printed, then we re-enter Operator-pending mode (because of the third `d`).

### Actual behavior

## Scenario 1

After the second `d` keystroke, Neovim waits another `timeoutlen`, then deletes the line under the cursor.

## Scenario 2

`Hello, world` is printed, nothing is deleted, and we are back in Normal mode. This is because after the second press of `d`, Vim waits to see if the user will complete that `d` to the Operator-pending mode `dd` `:map` created by `:map dd ...`.

## Note

This is particularly annoying when trying to remap ` >` if you use a short `timeoutlen`. I was doing this to customize the behavior of `<<` for some `filetype` and I thought I was going crazy because my custom indent logic was behaving nondeterministically -- because sometimes I was pressing both `<` within `timeoutlen` and sometimes I wasn't, so sometimes I would get a normal one-indent shift and sometimes I would get my custom behavior to fire.
Discussion
- multicursor is related here because it requires adding internal understanding of the "atoms" of normal-mode editing actions. That opens the door for meaningful input handlers (Lua callbacks instead of "mappings").
