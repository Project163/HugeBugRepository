Title

Error NG6002, caused by enableIvy with libraries of a specific naming scheme

Description
# 🐞 bug report

### Affected Package
 
  

The issue is caused by package `@angular/compiler` maybe? ngcc

### Is this a regression?

 

Yes, the previous version in which this bug was not present was: 8.x.x

Introduced by adding `"enableIvy": true` to an application in a monorepo.

### Description

The following error occurs under a very specific setup in an Angular CLI monorepo:

```
error NG6002: Appears in the NgModule.imports of AppModule, but could not be resolved to an NgModule class
```

This is related to several other reported issues, but never under this scenario AFAIK:

* Create a monorepo, where a library name matches a substring of another repo (ie: "**my-lib**" and "**my-lib**-second").
* Build the libraries with `"enableIvy": false` .
* Build the app, referencing both libraries in their **dist** folder.

Discussion
- CLI team: I investigated this reproduction, and it appears that invoking `ngcc` from the command-line correctly compiles `my-lib-second`. I tested both:

```
$ ngcc -s dist -t my-lib-second
```
(direct compilation of `my-lib-second` as a single target)
and
```
$ ngcc -s dist
```
(compilation of all of `dist`)

and both appeared to work correctly.

I think something funny is happening between the CLI and `ngcc` here. Feel free to transfer this back if needed!
- Whoops, spoke too soon. Apparently the CLI passes `pathMappings` in (which is the difference between the CLI invocation and the command-line version), and`ngcc` infers an incorrect package path for `my-lib-second` when `pathMappings` are present.

It looks like `ngcc` is doing a string prefix check here: [URL]

which is clearly going to fail in cases like this.
