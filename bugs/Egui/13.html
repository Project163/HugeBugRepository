Title

Build fails when depending on `winit` with `android-game-activity` feature enabled

Description
**Describe the bug**
[Link: This example] fails to build with latest egui.

**To Reproduce**
Steps to reproduce the behavior:
1. Clone [Link: this repository].
2. Navigate to `agdk-eframe` directory.
3. Follow the instructions in `README.md` to build the example.
4. Build fails with the following error.

```
[2023-02-12T06:45:41Z INFO  cargo_ndk::cli] Using NDK at path: /home/rishabh/Android/Sdk/ndk/25.2.9519653 (ANDROID_NDK_HOME)
[2023-02-12T06:45:41Z INFO  cargo_ndk::cli] NDK API level: 21
[2023-02-12T06:45:41Z INFO  cargo_ndk::cli] Building targets: arm64-v8a
[2023-02-12T06:45:41Z INFO  cargo_ndk::cli] Building arm64-v8a (aarch64-linux-android)
warning: file `/home/rishabh/software/myprogs/rust-android-examples/agdk-eframe/src/lib.rs` found to be present in multiple build targets:

[2023-02-12T06:45:54Z INFO  cargo_ndk::cli]     rustup target install aarch64-linux-android
```

**Expected behavior**
The example should build successfully.

**Desktop (please complete the following information):**
 - OS: Linux
 - Version: master branch

**Additional context**
According to the error log, the build probably fails because two conflicting features `native-activity` and `game-activity` are enabled at the same time. `android-game-activity` feature is enabled for `winit` dependency in the example and `native-activity` is enabled by `egui-winit`. The example builds successfully if [Link: this line] is removed.
Discussion
- I guess we need to make the activity type a feature flag of egui-winit, though I am not a big fan of that abstraction leak
- @emilk please check this PR: [URL]
- Yeah, it's awkward but Cargo doesn't really give us many options in this case.

Cargo doesn't give a way to provide some kind of global feature that would allow an application crate to choose a backend feature for an indirect dependency and so we have to plumb the features for configuring the backend through Winit and any middleware frameworks like egui.

It's relatively likely that Android applications will need to implement a subclass of `Activity` in Java or Kotlin and they will have to choose to subclass `NativeActivity` or `GameActivity`. Since there are significant pros and cons to each one it wouldn't really be appropriate for Egui to force a choice here.

The other fiddly detail we have to consider here is that it's only possible to link a single version of the `android-activity` crate into an application - which isn't the case for most Rust crates.

android-activity provides the `android_main()` entry point for an Android application and effectively provides a minimal runtime for the application. There would be a linker failure if you try to link multiple versions.

_(Prior to android-activity we had the same constraint with ndk-glue except it would only manifest as a failure at runtime)_

With this constraint then we _really_ want to keep the number of crates that have any direct dependency on the `android-activity` crate to a bare minimum, to reduce any chance of a conflict in the future if there will need to be a semver bump for `android-activity`. (If there is a semver bump for `android-activity` then that should ideally only need to be synchronized with Winit and not also with crates like Egui or every single Android application crate.)
