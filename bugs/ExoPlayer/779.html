Title

DownloadRequest.toMediaItem always discards keySetId

Description
### Problem

The method is defined as follows:

[URL]

However, `MediaItem.Builder` constructs the `MediaItem` in the following way:

[URL]

Hence `drmKeySetId` is never applied because `drmUuid` was never set. This makes it confusing in the least. `.toMediaItem` should accept a DRM UUID to prevent this from happening, or `.toMediaItem` should never set `drmKeySetId` since it implies it has any significance.

### Workaround

Not using `.toMediaItem` and setting all values manually, like so:

```
java
new MediaItem.Builder()
           .setMediaId(download.request.id)
           .setUri(download.request.uri)
           .setCustomCacheKey(download.request.customCacheKey)
... [Log Snipped] ...
           .setDrmUuid(C.WIDEVINE_UUID)
           .build();
```
Discussion
- Or should `DownloadRequest` have a `drmUuid` field?
- Adding a `drmUuid` field to `DownloadRequest` (or passing it via `toMediaItem`) is quite a narrow solution to the problem. It's the minimal additional data that we could add so that `MediaItem` builds a usable `DrmConfiguration` internally, but it's not necessarily sufficient. If the use case ever involves potentially having to refresh the DRM keys at playback, then it's also going to be necessary to specify `drmLicenseUri` and potentially `drmLicenseRequestHeaders` as well, for example. `DrmConfiguration` also contains some runtime configuration that an application might need to set to something other than the default values.

I don't think we want to add the whole `DrmConfiguration` into `DownloadRequest` (and we'd have to handle the possibility of it being omitted anyway, for downloads previously written into the download database). We could perhaps pass the whole `DrmConfiguration` into `toMediaItem` and then have `toMediaItem` add the `keySetId` into it. A bit of thought is probably required to come up with something nice.

Note that in the meantime, I think you can easily work around this problem by not using `toMediaItem`, and building the `MediaItem` directly from the `DownloadRequest` fields instead. This is what `PlayerActivity` currently does in the ExoPlayer demo app.

Marking as a triaged bug, since dropping of the `keySetId` is unexpected.
