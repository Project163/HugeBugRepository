### To Reproduce

- Clone repo
- `npm install`
- `npm exec jest`

### Describe the Bug

While investigating [URL] I discovered that `next/jest` generates a jest config that is not JSON-serializable [Link: by attaching the next config to the transformer config].

The Jest docs [Link: clearly state] that the config should always be JSON-serializable, and violating that results in tasks run with [Link: Jest's child process worker] failing with the error message `()=>null could not be cloned.` (basically the serialization to send the job to the child process fails).

The most consistent way I've found to reproduce the issue is to use something based on `create-jest-runner`, such as `jest-runner-eslint`, alongside the next jest runner, but it's most certainly not the only way to get jest to put work on the child process worker (I'm a bit hazy on the details of exactly what causes jest to use the child process worker and what doesn't TBH).

The simplest fix here is to strip non-serializable elements from the next config before passing it to the transformer [Link: here].  In my testing, it seems like `generateBuildId` is the function that causes the problem for my minimal repro case.  However, I'm sure there are other functions that will make their way into the config and cause problems, so it may be more appropriate to create an allowlist of parts of the next config that get passed down to the swc jest transformer rather than trying to delete non-serializable elements out of it.
