- I was able to get the example working and reproduce the problem as described. Here's a trivial reproduction: [URL]

It's actually a fascinating bug, and is a combination of several factors:

At the root of the issue is an assumption Angular makes: if the injector being used to create a component doesn't have a binding for `RendererFactory2`, then a factory that creates `Renderer3` (that is, `document`) is used. Exactly this happens for the dynamically instantiated component in the example. That component then attempts to inject `Renderer2`, which causes the crash.

So why is `RendererFactory2` missing? Firstly, the example app creates an injector via `Injector.create([...])`. This injector doesn't inherit from the app injector, so it doesn't have a binding for `RendererFactory2`. This didn't used to be a problem, however, since `ViewContainerRef.createComponent()` tries to create a chained injector using the given injector and the component's `NgModuleRef`. Even if the given injector was missing `RendererFactory2`, the `NgModuleRef` (usually the app injector or derived from it) would have it!

Where did the `NgModuleRef` come from? It's not common to explicitly pass that argument to `ViewContainerRef.createComponent()`. Previously that API required a `ComponentFactory`, though, which _has_ an internal `NgModuleRef` obtained from its `ComponentFactoryResolver`.

In a recent Angular though, we introduced a factory-less API for `createComponent()`, which made it easy to call the API with no `NgModuleRef`. So the _only_ tokens available for injection when creating this component are those in the user-provided injector, which does not include `RendererFactory2`. Therefore, `Renderer3` gets selected, and the component crashes!
- @tk2rush90 a workaround would be to inject `Injector` inside your modal service, and use that as the base of the `Injector.create` call when you create the injector for whatever modal component is being displayed.
