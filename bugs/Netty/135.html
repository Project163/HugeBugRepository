Title

Review *ToMessageDecoder.decode(...) and *ToMessageEncoder.encode(..) methods

Description
While @trustin and me talked about some issue which is related to folding we agreed that our current way to handle folding is kind of a design-flaw.

We want to remove folding completely if possible to simplify things.

For this we also want to revisit the *ToMessageDecoder.decode(..) and *ToMessageEncoder.encode(..) method. 

At the moment they look like this for example:

``` java
Object decode(ChannelHandlerContext, ByteBuf);
```

This may should more look like:

``` java
void decode(ChannelHandlerContext, ByteBuf, MessageBuf );
```

There are few issues that may make it hard:
1) It is not so easy to extend and "intercept" the decoded message to change it. This is for example done by MarshallingDecoder. We could fix this by using some kind of MessageBuf wrapper that does the convert under the hood. 
2)It is harder to handle the case of handling ByteBufs which may need to get written to a ByteBuf if the next handler in the pipeline is of type Channel*ByteHandler. We could  do this again by some special wrapper which will intercept add / offer and just write it to the next ByteBuf if needed.
Discussion
- @trustin I also start to wonder if it may not give sometimes bad side effects when we "automatically" write ByteBuf messages to the next ByteBuf in the pipeline. I think for encoders (outbound) it may not so much an issue.. But I wonder for inbound as it may "screw up" framing .. WDYT ?
- I think it is fine.  A decoder could provide an overridable factory method like this:

```
protected MessageBuf  newDecoderOutput() {
    return Unpooled.messageBuffer();
}
```

Note that we should not add a decoded message to the next handler's buffer directly because 1) we have to handler `ByteBuf`s, 2) we have to allow a user filtering messages like you mentioned, and 3) the decoder has to determine if the decode() method decoded anything easily.

- @trustin ok I had some more thoughts on this and also did some prototyping. I think we should not allow the user to "intercept" MessageBuf.\* calls. What we should do is to just have an extra decode method in the classes that we think that should be extendable which return one object at one time. So in this case the user could just override this method and use it like before. This would for example be true for FixedLengthFrameDecoder. 

Why I think we should not allow to intercept is for a few reasons:
1) The "conversion" from one type to an other while be in the MessageBuf.add(...) method may want to throw an exception. Which must be wrapped in a RuntimeException then
2) The intercepter may "surpress" a message but the implementation he extend may depend on the fact that it is added.

So I think it is more clear if we just not allow it.
- Re: having a field - I wonder if we can rely on escape analysis. i.e. allocate decoder/encoderOutput for every decode/encode().

Re: Throwing an exception - we could allow `FilteredMessageBuf.filter()` to throw any exception and then use `PlatformDependent.throwException()` internally.

Re: An interceptor that suppresses a message - that's obviously a user fault? Usually, a user just should use `FilteredMessageBuf`, so I don't think this is a problem.

By the way, there's no `ByteToMessageEncoder` in our API.  If you meant `ByteToMessageDecoder`, why should we make it sharable?
