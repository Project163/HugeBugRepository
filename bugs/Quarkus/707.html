Discussion
- Hi, @radcortez, have you tried specifying reflection config for Graal? I had just the same issue and it worked for me. Basically, it takes a .json file which contains metadata on all classes that utilize reflection (and ServletConfigEtc certainly does) in your project. This .json is then fed to the GraalVM so that it could instantiate classes on build-time with reflective access preserved.

It is documented on Quarkus page [Link: here]. To assemble such a file you can use built-in GVM tool called 'native-agent', which is available from your GMV distribution (see [Link: here] and [Link: also here] for more information on how to configure it. The agent will produce this file for you, but it takes some use-case coverage, because GraalVM agent will only pick metadata that were accessed in runtime.

As a result you will get a relatively big .json (~60kbs for my project), which you can definetely sift through, since Graal is oblivious on which classes are already configured for reflection on the Quarkus side. Takes some time to do it though :) Hope it helps.

BTW, @geoand I'm not sure who to address this point to (I just saw you in discussion frequently :) ), but I think it would make sense to add reference to [Link: this] to the Quarkus page too.
- That process should rarely be needed, unless your **application** code does a ton of reflection on its own.
