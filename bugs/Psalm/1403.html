Discussion
- I've been able to isolate the problem:
[URL]
- Another test, which does not output any exception on psalm.dev, but still fails:
[URL]
- I'm not sure what to do here. Those chars are not allowed in a json but we use that for creating a hash. 

Is there a weird string compliant way to flatten an array for hashing? If the method is performant, it could be a plus, we probably create a lot of hashes on a single execution
- In case the scalar value of that `if` statement should be kept, e.g. for static matching particular values, the only way to preserve non-UTF8 literals in a UTF8-scope, is to encode/serialize them again (not to be mixed with `utf8_encode` or similar, which just would guess the actual "charset").

Thus for the scenario in `Clause.php` (I did not check other places, where this is assigned or compared), it might be

```php
$this->hash = md5(serialize($possibility_strings));
```

* `serialize` to keep structural integrity (`array` items here)
* `md5` as hash/signature of the input literals is basically just the only aspect that's interesting
* (we never deserialize, simply because it's not possible - just wanted to mention, that "insecure deserialization" wouldn't be a topic here)
