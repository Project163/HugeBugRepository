Title

Assert.That with a Throws constraint does not provide as much info as Assert.Throws

Description
When using `Assert.Throws` and an unexpected exception is thrown nunit provides information about the unexpected exception. 

```
csharp
[Test]
public void UnexpectedExceptionWithInfo()
{
  Assert.Throws (() =>
... [Log Snipped] ...
  });
}
```

This test expects an `IOException` to be thrown but instead a `FormatException` is thrown. This provides the following output:

```
 Expected:  
  But was:   c. b__0_0() in Program.cs:line 23
   at NUnit.Framework.Assert.Throws(IResolveConstraint expression, TestDelegate code, String message, Object[] args)>

at Testit.Tests.UnexpectedExceptionWithInfo() in Program.cs:line 21
```

It is providing information about the unexpected `FormatException` (message + stack trace). The problem is that in our codebase we are using `Assert.That` with a `Throws.TypeOf<>` constraint like this:

```
[Test]
public void UnexpectedExceptionWithoutInfo()
{
  Assert.That(() =>
  {
    throw new FormatException("This is a format exception.");
  }, Throws.TypeOf ());
}
```

But when this example encounters the unexpected `FormatException` the following is output:

```
  Expected:  
  But was:   

at Testit.Tests.UnexpectedExceptionWithoutInfo() in Program.cs:line 30
```

Note here that the information about the unexpected exception (message + stack trace) is gone. But exactly those two exception details would be relavant for debugging the failed test.

Is this behaiviour intended? And if yes are there easy ways to fix this issue?

My current workaround is to use a `ThrowsConstraint` with an `ExceptionTypeConstraint` as base constraint: 

```
[Test]
public void UnexpectedExceptionFixedInfo()
{
  Assert.That(() =>
  {
    throw new FormatException("This is a format exception.");
  }, new ThrowsConstraint(new ExceptionTypeConstraint(typeof(IOException))));
}
```

- I thought I had a solution to this, but as already mentioned above, the fundamental problem here is that `Throws.TypeOf()` returns `ExactTypeConstraint`, rather than `ExceptionTypeConstraint`.

This is a problem because it forces `ThrowsConstraint.ApplyTo()` to return an instance of `ThrowsConstraintResult`, with the base result set to the caught exceptions type (rather than the actual exception). As mentioned before, this makes sense for a `TypeConstraint`.

I think a potential fix to this issue is to introduce a new `ExceptionConstraintExpression`, who's `TypeOf()` methods return `ExceptionTypeConstraint`, rather than `ExactTypeConstraint`. (This may well be a dumb idea, as it's the first time I've looked at the code, so I don't really understand the architecture / internals.)
