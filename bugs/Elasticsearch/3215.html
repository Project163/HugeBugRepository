Title

DELETE _all fails if an index is deleted during the request

Description
### Elasticsearch Version

9.x, main

### Installed Plugins

_No response_

### Java Version

_bundled_

### OS Version

N/A

### Problem Description

**Current behaviour**

Request `DELETE /_all` might fail if another process deletes one of the resolved indices while it is running.

**Expected behaviour**

Request `DELETE /_all` should be resilient to another process deleting one of the resolved indices considering that the user did not specify which indices to delete.

### Steps to Reproduce

We saw this while debugging #136585 but it doesn't reproduce locally.

We believe a test that forces the following sequence of events should be able to reproduce this:
- Create 2 indices.
- Request for all indices to be deleted, but add a delay after [Link: the index resolution].
- Take advantage of the delay and delete one of the two indices.
- The above will ensure that the delete index cluster update task will actually run on a new cluster state without one of the two indices. 
- Then when the cluster update will try to [Link: resolve the project via the index name] we get an `IndexNotFoundException`.

Discussion
- Pinging @elastic/es-data-management (Team:Data Management)
- It might look like we can fix this by moving the index name resolution step into the cluster state update since this would eliminate the gap in which the race occurs, but note that if security is enabled then we will already have performed index name resolution in `org.elasticsearch.xpack.security.authz.IndicesAndAliasesResolver#resolveIndicesAndAliases` so there'll still be a race.
