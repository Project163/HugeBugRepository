Title

Do not call inbound event methods from the same handler's handler method

Description
The current `AbstractChannel.Unsafe` implementation always invokes `pipeline.fireChannel*()` directly rather than scheduling the event using `eventLoop().execute(Runnable)`.

This can sometimes cause a trouble in the user code because the inbound event being fired can affect the state of the handler or its context while the handler's other methods are running.

For example, let's say there's a `handler.inboundBufferUpdated()` method like the following:

```
void inboundBufferUpdated(ctx) {
    in = ctx.inboundMsgBuf();
    for (;;) {
        MyMsg m = in.poll(); // <--- (A)
        if (m == null) break;
... [Log Snipped] ...
    }
}
```
1. At (B), ctx.close() will invoke `unsafe.close()` directly if no `EventExecutor` was specified with the handler.
2. At `unsafe.close()` the connection will be closed immediately and `channelInactive()` and `channelUnregistered()` events will be triggered in turn _from the same thread immediately_. This means `inboundBufferUpdated()` will invoke `channelInactive()` and `channelUnregistered()` indirectly while it's still in the loop.
3. Once `channelUnregistered()` is invoked, Netty will also call `handler.freeInboundBuffer()` to free the inbound buffer.
4. Now that the control returns to `handler.inboundBufferUpdated()` and the loop continues.
5. At (A), a user sees an `IllegalBufferAccessException`.

So, we have 2 problems.  One is that inbound event methods call each other unintentionally.  The other is that it leads to a bad state.

To fix this issue, AbstractChannel.Unsafe() should not call `channel*()` immediately in this kind of cases.
