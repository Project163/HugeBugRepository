Title

AnyClass.class and AnyClass.getClass() always return java.lang.Class.

Description
The following script demonstrates the problem.  The ".class" syntax and calls to getClass() on any class return the same result: java.lang.Class. 

 Script: 
------- 

 System.out.println java.lang.String.class 
System.out.println java.lang.String.getClass() 
System.out.println java.util.LinkedList.class 
System.out.println java.util.LinkedList.getClass() 
System.out.println java.sql.Timestamp.class 
System.out.println java.sql.Timestamp.getClass() 

 Output: 
------- 

 class java.lang.Class 
class java.lang.Class 
class java.lang.Class 
class java.lang.Class 
class java.lang.Class 
class java.lang.Class 

 This may be related to   GROOVY-440  : 

  [URL]
Discussion
- The current behavior of a class name is to return the class so: 

 AnyClass in groovy == AnyClass.class in Java 

 So you can either close this as it is not a bug, or you can lobby to have it changed to your expected behavior.
- This is a Groovy feature that I wish go away in favor of Java semantics. I know it's the property syntax thing, but one strong argument for the Java way is performance. The Groovy compiler as of now attempts to resolve every single variable as a class name, wasting a lot of CPU cycles.  

 The dilemma is with the .class "property": 

 a.class  

 is interpreted as  

 a.getClass()  

 in Groovy and "a" has to be an object instance. The same syntax in Java means the Class object for class a.  

 BTW, this is also a piece of inconsistancy in Java syntax where .something may not always mean a field access. Another example is the .length in eg.  

 new Object[] 
{"a", "b"}
 .length.  

 I'm wondering if we can build special logic in processing the .class suffix, something like: 

 1. try resolving "a" as a class; on failure, and optionally,  
2. interpret it as a.getClass() 

 I said "optionally", because we can also simply mandate using getClass() on a class instance.
- The current groovy syntax also creates problems as reported in issue 515. Basically, we can't have a static property the same name as a java.lang.Class method, because they conflict: 

 class A { 
  static methods = "blah" 
} 

 println A.methods 

 this will return a MethodClosure for the getMethods() method on A.class. 

 I vote we force the user to use ".class" or getClass() instead of just "A".  

 As a side note, I also don't like getting a MethodClosure (method reference) when referring to a method name.
- fix got in cvs today. Now a fully qualified class name with a .class will be resolved to the class name given before the dot
