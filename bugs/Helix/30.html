Title

Panic on exit when mouse support is disabled

Description
Recently helix has started crashing for me every time I exit;the error message I get is `thread panicked while processing panic. aborting.`.

I was able to trace the issue back to handling mouse support:
Inside the panic hook `execute!(std::io::stdout(), DisableMouseCapture)` ([Link: application.rs:565]) produces another panic if mouse support is disabled, crashing the application. Commenting it out reveals the original stack trace - which conviniently seems to be the same bug:

 
 backtrace 

```
thread 'main' panicked at 'Original console mode not set: TryFromIntError(())', [...]\.cargo\registry\src\github.com- \crossterm-0.21.0\src\event\sys\windows.rs:36:10
stack backtrace:
   0: std::panicking::begin_panic_handler
             at /rustc/ \/library\std\src\panicking.rs:515
   1: core::panicking::panic_fmt
... [Log Snipped] ...
  26: core::ops::function::FnOnce::call_once  enum$ , anyhow::Error>, 1,  , Err>,tuple<>>
             at /rustc/ \library\core\src\ops\function.rs:227
```
 

-> When attempting to disable mouse capture without it being enabled first the `execute()!` call panics.

### Reproduction steps

1. turn off mouse support (`mouse = false` in the `[editor]` section of config.toml)
2. run helix and close it again

### Environment

- Platform: Win10 x64
- Helix version: `v0.4.1-199-g8925fdd`

I thought about making a PR to check `self.config.editor.mouse` before executing the mouse capture commands but I don't think that's a good fix, as it doesn't necessarily reflect the current state (i.e. if the program panics before the mouse was captured or if the config is changed/reloaded at runtime).

It's also surprising that `execute!()` panics internally, even though it returns a result.
Discussion
- I started looking into this, it's an issue because crossterm only calls `init_original_console_mode` if you've previously called `enable_mouse_mode`.

[URL]

Looking at the logic, I think it's okay to only call disable if we previously called enable, since disable will actually revert to what the mode was before we started crossterm (https://github.com/crossterm-rs/crossterm/blob/ /src/event/sys/windows.rs#L49)
