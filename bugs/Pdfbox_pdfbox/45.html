Title

Performance regression in PDFBox 1.2.0

Description
Arjohn Kampman reported a notable performance drop in PDFBox 1.2.0, possibly caused by   PDFBOX-754  .
Discussion
- The performance degradation seems to be related to files that can not be found. For example, with some PDF files, pdfbox tries to load org/apache/pdfbox/resources/afm/MicrosoftSansSerif.afm over and over again. Normally, the result of such load operations are cached in PDTrueTypeFont.afmObjects, but not so when the result is <null>. 

 Here's (one of?) the relevant stack trace(s):

- Arjohn is correct. PDFont.getAFM is the showstopper. If we prevent PDFont from searching for a metric file which isn't there again and again the performance will increase by a factor of 8-10. I'll provide a patch later, if no one else is faster ...
- I fixed this in revision 959587 by reintroducing the fixed list of known font metrics that I removed during   PDFBOX-754  , assuming it would be better to allow also other font metrics to be installed by client applications. We'll probably need to tackle that in some other way now.
- Just verified with the current trunk: performance is on par with 1.1.0 again. Thanks!
