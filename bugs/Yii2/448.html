Title

Response->sendHeaders() patch to allow sending a Location header with a 202 status

Description
The current sendHeaders method in the Response class does not handle a php bug.

The fix is very simple and the explanation is in the comments below:

```
/**
 * Sends the response headers to the client
 */
protected function sendHeaders()
{
... [Log Snipped] ...
    $this->sendCookies();
}
```
Discussion
- Sorry, that was an opinion.  Actually I'm planning on submitting this to the PHP group as a bug.

However, I do believe it's an actual bug.  The PHP documentation mentions the following:

Quote:
(from [URL]

The second special case is the "Location:" header. Not only does it send this header back to the browser, but it also returns a REDIRECT (302) status code to the browser unless the 201 or a 3xx status code has already been set.

Endquote

This works as mentioned.  The bug is that the http status 202 is also used with a Location header, but php will convert the 202 to a 302 unless you force it.  I would consider that a bug, since the auto-conversion for the Location header simply does not work as it should.

The 202 is used for asynchronous RESTful operations:

Quote:
(from: [URL]

Instead of creating the actual resources, create a temporary one. Instead of returning a 201 (Created) HTTP response, you can then issue at 202 (Accepted) response code. This informs the client that the request has been accepted and understood by the server, but the resource is not (yet) created. Send the temporary resource inside the Location header.

Request:
POST /blogs HTTP/1.1
 
    blogdata
 

Response:
HTTP/1.1 202 Accepted
Location: /queue/12345

This location can store information about the status of the actual resource: an ETA on when it will be created, what is currently being done or processed.

Endquote

I hope that helps.
