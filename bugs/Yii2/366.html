Title

Error in Formatter normalizeDateTimeValue

Description
I got the following Error:
[Image: formatter_error]
I found out that `$timestamp` is a DateTime object which causes the error. The source come from `normalizeDateTimeValue`
[Image: formatter_cause]
IfI format the DateTime object to a timestamp with `->format('U')` then it works. See:
[Image: formatter_correction]
I think that Intl's format function expects a number.
Discussion
- we have covered this in our tests so passing a DateTime object should not be a problem in general.

How do you call the formatter and with which value?
Also please give your PHP and ICU version.
- @cebe I get the error with the standard `DetailView` widget generated by gii. see:

```
php
  $model,
                'template' => '  {label}  {value}  ',
        'attributes' => [
... [Log Snipped] ...
        ],
    ]); ?>
```

My index grid worked. In my further research I found out that the attributes `'rcv_valid_from:dateTime'` and `'rcv_valid_until:dateTime'`are not in the grid. Then I excluded attribute by attribute from DetailView. So I found out that `'rcv_valid_until:dateTime'` produces the problem. Without formatting it looks like:
[Image: view]

The datetime in 'rcv_valid_until' is '9999-12-31 23:59:59'. Therefore it's the year 2038 bug (Y2K38). The php DateTime object can handle dates after 2038 but not it's getTimestamp method. That's why the conversion with `->format('U')` works. `->format('U')` produces a long integer (64bit) in 32bit php also. The 'Intl' format call converts a DateTime object to a timestamp with getTimestamp internally. If I added `->format('U')`within normalizeDatetimeValue the 'intl' formatter gets a timestamp as long integer already.

Now it's clear why your tests were successful. You don't use a date >2038. Try to test a date like 01/01/2040.
- Well, we are actually skipping these tests for INTL on 32bit systems: [URL]
We may use PHP as the fallback for date ranges >= 2038 and < 1902
