Title

NPE when accessing RecordHeader.key() concurrently

Description
Summary 

 After upgrading clients to  2.8.0 , reading  ConsumerRecord 's header keys started resulting in occasional  java.lang.NullPointerException  in case of concurrent access from multiple(2) threads. 
   Where 

 NPE happens here  RecordHeader.java:45 : 
  
 
 public   String  key() {
     if  (key ==  null ) {
        key = Utils.utf8(keyBuffer, keyBuffer.remaining());  // NPE here 
         keyBuffer =  null ;
    }
     return  key;
}
 
  
   When/why 

 Cause of issue is introduced by changes of   KAFKA-10438   to avoid unnecessary creation of key's    String    when it might never be used. 
 It is good optimization but this  lazy  initialization of field  RecordHeader.key  creates a problem if being accessed/initialized by 2 threads concurrently since it's now no longer read-only operation and there is race between initializing    key    and nullifying    keyBuffer    
   Simple workaround 

 Upon consuming record(s) and before passing    ConsumerRecord    to multiple processing threads, eagerly initialize all header keys by iterating through headers and invoking    key()    or even    ConsumerRecord.headers().hashCode()    which will initialize all keys (and header values too) 
   Consequences 

 Current implementation renders RecordHeader not thread-safe for read-only access. 
   Reproducibility 

 With enough iterations it's always possible to reproduce (at least on my local)

- Thanks for the ticket. This class was never meant to be thread safe, the value was initialized lazily previously and it just so happened the key was not. Since the consumer is single threaded, this was deemed ok. 

 For now, the easiest path is for you to copy the data you care about to your own thread safe class. We could consider making ConsumerRecord thread safe, but it would require a KIP and it would probably only be done in a feature release.
