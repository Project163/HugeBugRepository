Title

[YSQL] Upgrade did not clean up the old postgres process

Description
This was observed in an internal test system. Upgrade did not clean up the old postgres process .
Discussion
- Some observations:
```
[yugabyte@ip-172-151-25-83 ~]$ ps -ef | grep postgres
yugabyte 11074 31432  0 02:00 ?        00:00:00 [postgres]
yugabyte 11076 10888  0 02:00 pts/0    00:00:00 grep --color=auto postgres
yugabyte 19255 25507 15 Mar27 ?        06:48:51 postgres: postgres postgres  (50384) INSERT
yugabyte 19256 25507 15 Mar27 ?        06:49:36 postgres: postgres postgres  (50386) INSERT
... [Log Snipped] ...
yugabyte 25520 25507  0 Mar27 ?        00:00:00 postgres: checkpointer
yugabyte 25521 25507  0 Mar27 ?        00:00:31 postgres: stats collector
```
When we launch the postgres process from the tserver, we should store its pid somewhere (ideally independently from postgres's own pidfile), and then on tserver restart we need to kill the postgres process if it is still running.
- In the `ps` output above, pid `25507` is the old postgres process that was started by the old tserver.
- ... [Middle Discussions Snipped for Brevity] ...
- What about SIGKILL @robertpang ?

On slack channel, a user mentioned: 

 >
- @ndeodhar: we need to parameterize the `Subprocess` class to be able to customize the signal that the child process would receive on parent process termination, and as @robertpang mentioned, we need to set that signal to `SIGINT` for the PostgreSQL child process.

See this in `subprocess.cc`:
```
    // TODO: prctl(PR_SET_PDEATHSIG) is Linux-specific, look into portable ways
    // to prevent orphans when parent is killed.
    prctl(PR_SET_PDEATHSIG, SIGTERM);
```
