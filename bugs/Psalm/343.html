Title

Issue with templates and intersection types

Description
I've tried to trim down most of the implementation details from the actual scenario here, hence there are a few nonsense looking empty structures.

A bit of motivation for the current setup:
I have a few classes that implement `Foo`, and some that almost implement `Foo` but require some `State` object that will be provided later in order to produce the final `Foo` result—these implement `AlmostFoo` which requires a `makeFoo(State $State): Foo` method.

In some cases I want to place the eventual result of an `AlmostFoo` inside an object that implements `Foo`, to do this in-place I use a `callable(State):Foo` closure to delay evaluating the `Foo` upfront. I wanted to create a templated class `AlmostFooMap` to wrap this closure so that this wrapper could too implement `AlmostFoo` via this callable (i.e. so that when I compose a `Foo` in terms of an `AlmostFoo` I can pass around a summary `AlmostFoo` that can produce a `Foo` given the later `State`).

I wanted to constrain the templated `T` so that the acceptable closures used to construct `AlmostFooMap` are `callable(State):(T&Foo)`, although when trying to implement the `makeFoo(State $State):Foo` Psalm complains that the returned `T` is more general then `Foo` (when in-fact it is both a `T` and a `Foo`).

I wasn't sure if this might be an issue with support for covariance of the declared return type, although when dropping the generic `T` type information from the implemented `makeFoo` in `AlmostFooMap` (i.e. change the return type on line 36 of the example to just `Foo`) I still run into some `MixedTypeCoercion` warnings,

I think that if Psalm knows the concrete type for any intersection expression involving (any number of) templated types then they should all get assigned to that concrete type

e.g. with `T`, `U` templated and `Foo` an already known type: if Psalm needs to check that a specified `someClass` is a `T&U&Foo` when instantiating a templated object, then it must check that `someClass` is a `Foo`, and then it can set `T` is a `someClass` and `U` is a `someClass` (it's possible that `T` and `U` could be allowed to be more general than `someClass`, but they cannot be more specific).
