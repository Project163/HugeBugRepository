Title

cqlsh column header can be incorrect when no rows are returned

Description
Upon migration, we internally create a pair of surrogate clustering/regular columns for compact static tables. These shouldn't be exposed to the user. 

 That is, for the table 
  
 CREATE TABLE bar (k  int , c  int , PRIMARY KEY (k)) WITH COMPACT STORAGE;
 
  

  SELECT * FROM bar  should not be returning this result set: 

  
 cqlsh:test> select * from bar;

 c | column1 | k | value
---+---------+---+-------

(0 rows)
 
  

 Should only contain the defined  c  and  k  columns.
Discussion
- Are we sure this is not a driver/cqlsh issue? I wrote a simple test (attached) that checks the metadata generated for the  SELECT  of your example above, and unless I've done something wrong in the test, only  c  and  k  are included in the response metadata. 

 I know next to nothing of the python driver and cqlsh implementations, but it would be possible that one of those is using the metadata from its reading of the schema rather than the response schema (that the surrogate columns are part of the schema table is a necessity and it's probably the driver that will need fixing on that front, though that probably mostly depend on   CASSANDRA-6717   in practice). Could someone with more knowledge of the python driver/cqlsh confirm is the hypothesis above is plausible?
- Actually, I think this may be a cqlsh problem.  If the result has no rows, cqlsh doesn't know the column names, so it recreates them based on the python driver's view of the table metadata. 

 It turns out that's broken in more ways than just this – if you select functions or use aliases, the column header for empty results will be incorrect.  I think the proper fix is to somehow expose the result set metadata in the driver so that cqlsh can use it instead of relying on table metadata.
