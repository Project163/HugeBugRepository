Title

regexp_match produces unstable cache keys when used with flags parameter

Description
### Describe the bug

When the regexp_match function is used with the flags parameter (e.g. `regexp_flags('*', flags='i')`) then the resulting construct receives a different cache key for SQL compilation caching every time the function is called. The result is that any SQL containing the function pollutes the compilation cache without ever being reused.

_No response_

### Additional context

The interesting part of the output above is the cache key part for the flags parameter of regexp_match:

```
   >, 
  'modifiers', 
  (
    (
      'flags', 
       >, 
    ),
  ),
```

As you can see, it uses the BindParameter object itself instead of its more stable cache key. This results in a different key for every call. I would even argue that a BindParameter object is wrong here, at least for the Postgresql dialect where `flags='i'` results in a different operator being used.
