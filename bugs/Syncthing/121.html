Title

.stignore rules are ignored/buggy for existing/synced files

Description
Hi,

I have 2 nodes:
1. v0.9.8 on linux armv5
2. v0.9.5 on android (syncthing for android 0.4.8)

I synced the camera folder from my android device to the linux box (setting the "master repo" on android). Then I realized, that the two folders `cache` and `thumbnails` had been synced as well and wanted to remove those off the linux box while keeping them on android. So I created a `.stignore` on both nodes (just to be sure) like this:

```
cache
thumbnails
```

However the folders (+contents) where not ignored by syncthing (file count did not decrease on either node). I went on deleting the folders on the Linux box. This resulted in the conflict showing up on the android device: It wants to delete the folders but can't, because it has the master repo. When using "Override Changes", the folders will be resynced (despite the rule in `.stignore`).

The problem seems to be, that `.stignore` rules are ignored, if they where created after the respective files have been created/synced, i.e. when the file already has been scanned.

I reproduced the problem the other way around (linux box has the master repo). In general:
1. Set up a repo synced between node A and B.
2. (optional) Enable the option "Master Repo" on A
3. Create a file on A. e.g. `testfile.txt`. Let it sync to B
4. Create `.stignore` on A containing `testfile.txt`

**Expected**: The file count in syncthing will be reduced (on the local repo with the .stignore file) and deleting the file on one node will have no effect on the other node.
**Actual**: No change in file count and deleting the file on B will delete the file on A (or leave a conflict if A has the master repo). And deleting the file on A will also delete it on B.

Additionally, I tried editing the file `testfile.txt` after the procedure described above.

Discussion
- Right. Prior to v0.9, the effect would have been (given your scenario above) that `testfile.txt` was deleted on B when it was ignored on A (because it "disappeared" from A:s point of view). Currently, `.stignore` only means that we don't see the file locally any more so no more changes will be picked up, but we'll still see changes from other nodes and try to sync to it. This change wasn't intentional. When solving it now we should define (and write tests for) the desired behavior.
