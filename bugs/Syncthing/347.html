Title

Listen address expansion does not respect specified scheme

Description
Thanks to the new feature that displays the discovered addresses in the GUI in syncthing v0.13.8 I found strange addresses in this list for one of my devices.

```
dynamic
relay:// :22067
tcp6:// :22000
tcp6:// :22000
tcp6:// :22000
tcp6:// % :22000
```

Obviously, the IPv4 addresses with the tcp6:// scheme do not make sense. I checked against the STTRACE=discovery output of 0.13.8 and 0.13.7 and it does not look like an display issue.

The device only has a "dual-stack-lite" connection to the internet, so no direct IPv4 connections are possible (only in LAN). Because of this, the listen addresses of the device are configured as follows:

```
         dynamic+[URL]
         tcp6://:22000 
```
Discussion
- What appears to be happening here is the following:
- The listen is done correctly on v6 interfaces only
- A global announcement is made, the announced address is `tcp6://:22000` so the discovery server uses the source address as the device address

That works for the v6 case. But the client is apparently also able to access the v4 only discovery servers, presumably via nat64? Or, if it is DSLite as you're describing they will have v4 connectivity but tunneled and possibly NATed. Anyway, the v4 servers get a v4 announcement and dutifully insert the source address, getting a `tcp6:// `. Maybe they should be smarter...
- Actually, the device is configured for DS-Lite, because it usually has only such a connection, but currently has a complete dual stack connectivity. I don't know if this really makes any difference.

So, we just need a check if the scheme matches the IP address type in the discosrv [Link: here]?
- Probably yes. Only for the unspecified case, as it's fine to announce an actual IPv6 address over v4 and vice versa.
- Just noticed, that this also requires a patch for syncthing, since the local discovery also returns these invalid URIs.
