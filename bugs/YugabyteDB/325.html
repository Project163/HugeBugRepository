Title

[docdb] Iterate over intents after last regular record

Description
EDIT: This issue was previously thought to have been a colocation-only issue.  Now, it seems to be a broader one.  The example in this first post uses a colocated database in YSQL.

After setting up a table as follows,

```sql
CREATE TABLE r (i int, PRIMARY KEY (i ASC));
INSERT INTO r VALUES (1), (11), (111);
```

I get this, as expected

```sql
BEGIN;
INSERT INTO r VALUES (2);
SELECT * FROM r;
ROLLBACK;
```

```
  i
-----
   1
   2
  11
 111
(4 rows)
```

but I get this, which is not expected

```sql
BEGIN;
INSERT INTO r VALUES (222);
SELECT * FROM r;
ROLLBACK;
```

```
  i
-----
   1
  11
 111
(3 rows)
```

and this, which is not expected to succeed

```sql
INSERT INTO r VALUES (333), (333);
SELECT * FROM r;
```

```
  i
-----
   1
  11
 111
 333
(4 rows)
```

All of this seems tied to something wrong with the iterator on intents.  I have observed that the intents iterator (`IntentAwareIterator::intent_iter_`, a `BoundedRocksDbIterator`) does not find any intents past the last regular record.  That is why an intent with key `2` is found but an intent with key `222` is not.  `IntentAwareIterator::SeekForwardToSuitableIntent`, when passed the `intent_key_prefix` with key `111` and suffix `0xFF` does not manage to find key `222` during `ROCKSDB_SEEK(&intent_iter_, intent_key_prefix.AsSlice());`.  Rather, `intent_iter_.Valid()` is false after the seek.  If I instead do `intent_iter_.SeekToLast()`, I get an error.

I have observed the writes to RocksDB (as with the flag `docdb_log_write_batches`), and I found that the intent with key `222` really does get written and not deleted by the time of the `SELECT`.  I have also verified that the `BoundedRocksDbIterator::key_bounds_` for `intent_iter_` has no bounds, so I'm afraid that the issue might go as deep as the internal iterator implementation of RocksDB.

I realized that the `TXN META` and `TXN REV` records sort earlier than the intent key records for colocated tables.  This makes sense because the value type `kPgTableOid` (currently ASCII `z`) is higher than the value type `kTransactionId` (currently ASCII `x`).

While I don't know how that ties to this issue, moving the `kPgTableOid` to a lower value type causes this issue to get resolved.  The implication of this is that other records whose keys start with value types higher than `kTransactionId` may have this issue.  When colocated tables used to use `kTableId` (currently ASCII `y`) before issue #3365 was closed, this was a problem, and that makes sense.  @mbautin pointed out that `kNullHigh` is also susceptible to this, and he helped me come up with a repro which I will provide in a new comment.
- Here is a repro to show that intents whose keys begin with `kNullHigh` may not be visible during a `SELECT`.  This is in YSQL on a non-colocated database.

```sql
CREATE TABLE t (i int, j int, PRIMARY KEY (j DESC));
CREATE INDEX ON t (i ASC);
INSERT INTO t VALUES (1, 2), (3, 4);
BEGIN;
INSERT INTO t VALUES (null, 6);
SELECT i FROM t ORDER BY i NULLS LAST;
```

```
 i
---
 1
 3
(2 rows)
```

```sql
COMMIT;
SELECT i FROM t ORDER BY i NULLS LAST;
```

```
 i
---
 1
 3

(3 rows)
```
