Title

In PostgreSQL, `find_by(' ')` raises an error instead of returning `nil`

Description
Reproduction steps: [URL]

This bug actually is present in 4.1 as well (but it only affected the first `find` test case), and what is shown here is just an example of a bigger issue.

The problem is that on 4.1 we switched to use parameterized queries with the `find` call, and in 4.2 more of those calls followed (I noticed it in `find_by`, but there might be more). However, besides the safety and efficiency factors, there is one semantic difference between the "straight up SQL" and "parameterized" queries.

@matthewd can explain that in more details than I could... and he has some thoughts about a plausible fix, so I'll let him add those details later :smile:
Discussion
- cc @senny @sgrif @tenderlove
- We used to directly insert the value (without quotes, because it's Numeric):

```
SELECT .. WHERE id::integer = 9999999999;
```

When parsed, PostgreSQL would recognise that the right-hand literal is clearly a numeric (because it doesn't fit in anything else), and therefore we're using `numeric = numeric`. So, we'd get a slow upcast + seqscan, but it would work.

---

Now, we use a bind param:

```
SELECT .. WHERE id::integer = $1;
```

When that one is parsed, $1's type must be resolved from "unknown" to a real type. And as it's being compared with an integer, it thus follows that $1 must also be an integer.

Later, we attempt to execute our prepared statement, passing 9999999999. That won't fit in an integer -> error.

---

Incidentally, the same unknown -> integer -> error pattern can be seen if we run the query with a quoted literal:

```
SELECT .. WHERE id::integer = '9999999999';
```

---

There's no way we can avoid the immediate type-resolution of the bind parameter: that's part of what the prepare is all about.

We could force the first interpretation, by explicitly casting one side of the equality to numeric:

```
SELECT .. WHERE id::integer = $1::numeric;
```

... but that would mean a slow indexless plan for all queried values. (Or at least, the need to explicitly create a different, less efficient, index -- which is essentially equivalent.)

Thus, I believe our only option is to pre-emptively refuse to stuff an over-sized value into a bind param.

For the cases we care about, we should always have the column info. So, if we start tracking the width of integer columns (which we currently ignore), then we should have all we need to be able to refuse to DB-cast an out-of-range value.

That still leaves you raising an exception, but a far more manageable one than the inscrutable PGError we see right now.
