- Guys, 

 I have only one comment here, which I already expressed before - I do not like any mention of "endian" inside GridUnsafe. This just appears  fundamentally wrong  for me. 

 Java's  sun.misc.Unsafe  doesn't operate on endians anyhow. It just write bytes to memory. And our initial problem was alignment, not endians. If i am to do that ticket from scratch, I would only add "ALIGNMENT" flag to GridUnsafe. And all endian-related logic would reside in concrete users of GridUnsafe. This would give clear separation of concerns: 
1) GridUnsafe operate on memory taking in count alignment; 
2) Users of GridUnsafe decides how to deal with endians depending on their requirements. 

 With current implementation GridUnsafe looks virtually unusable for me. Should I need to use it, I simply would not understand which method to use in which situation.  

 Nevertheless, I haven't follow this ticket closely and my concern is somewhat a matter of taste. I do not ask anyone to follow it, this is just my thought. 

 The rest looks fine for me.
- There are two use cases: 

 
	 Work with multibyte types in offheap memory: use GridUnsafe methods with out byte order in signature. 
	 Marshalling requires fixed byte order. Use methods that operates with byte order. 
 

 It is simple enough.
