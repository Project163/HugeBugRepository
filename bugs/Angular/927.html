## Current behavior
 
Background of all pages is a light (20%) gray.

These light grays have been used extensively on the web because they soften the harsh black-and-white look. They also reduce contrast, which with some background-text combinations (such as 80% gray text on 20% gray background) makes the doc harder to use for some users. 

Light gray background also means that all graphics need to either be transparent or have borders so the white background of the graphics looks normal. 

## Expected behavior
 
It would be interesting to see if a white background improves readability/look overall, esp with the blue font areas, in tables, and near graphics.

- Ah, it looks like that's been changed in the 2018 update. The pre-I/O version was `#fafafa` for app background with the pure white reserved for "sheets of material" like cards and dialogs.
- I'm not surprised that technically it meets accessibility standards. Every site I've worked on with this gray did, and it didn't stop readers from complaining that text blurs into background a little so they wanted a higher contrast option.

So...if I understand your point @jelbourn, the light gray background makes sense when you have cards and other elements that you want to offset...is that the idea? I can see how it pops nicely there. 

The tricky part of a text-rich site is that we want the main body to as readable as possible. Same reason the cards have white background. 

As @gkalpak pointed out in another thread, with a white background for the whole page, we do lose the ability to offset code regions or images with white card-like boxes. I'm not sure, however, that those elements are so much more important than the main text that they deserve special offset the way navigation cards are offset. But I definitely wouldn't want to offset code or images by giving them a darker background than the main page, because that definitely moves us into readability challenges.
