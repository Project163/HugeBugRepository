Title

Output migration transforms eventEmitter.emit() into invalid output.emit()

Description
### Which @angular/* package(s) are the source of the bug?

core

### Is this a regression?

Yes

### Description

The output migration transforms:

```ts
@Output() eventEmitter = new EventEmitter ();

// later
eventEmitter.emit();
```

into
```ts
eventEmitter = output ();

// later
eventEmitter.emit();
```

But the value is mandatory in the `output.emit` signature, so the application breaks.
The migration could generate `emit(undefined)` in that case, or add a `TODO` or only treat this in with the `--best-effort-mode` option.

To repro, in the following Stackblitz, run:

```
ng g @angular/core:signals --migrations=outputs --path=./ --no-best-effort-mode
```

Discussion
- I agree that we could add a TODO, or skip in "safe mode", but IMO it would also be acceptable to say that we are intentionally breaking here and surfacing a real brittle problem in the user code (caused by the bad typings of `EventEmitter` clearly).

```ts
@Output() eventEmitter = new EventEmitter ();

// later
eventEmitter.emit();
```

can already break in subtle ways at runtime, given `undefined` being used as value, but `eventEmitter.subscribe` only _receiving_ values of type _string_.
- I would also prefer the code to break. IMO, that's clearly a bug that should be fixed.
BTW, another godd thing to do woulmd be to document what happens when emit is called without argument: does the parent component receive an `undefined` (and thus incorrectly typed) event? Is `undefined` somehow filtered out?
- This was my thinking while authoring this migration. I've marked this issue as a "bug" so we can insert a TODO indicating why it is breaking / what a user should do in this case.
