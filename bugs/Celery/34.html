Title

Autodiscovery fails for empty "related_name"

Description
## Checklist

The issue is affecting `v4.2.0` and current `master` branch.

## Steps to reproduce

In previous versions doing something like:

```python
celery.autodiscover_tasks(['my_package.tasks'], related_name='')
```

was fine and loaded all of the tasks in `my_package/tasks.py` ([Link: the `find_related_module` function was returning here]).

The same call with `v4.2.0` returns a `KeyError: my_package.tasks.'` (notice the trailing dot `.` at the end of the package), since it tries to build and import an invalid python package path [Link: here].

I'm not sure if this is/was the intended behaviour, though it kind of makes sense to be able to specify any kind of import path without having to always conform to a specific suffix (i.e. `.tasks`), we have use-cases where packages organize tasks like this:

```
my_package.tasks.models
my_package.tasks.api
my_package.tasks.foobar
```

Maybe the intended behaviour was to also return [Link: at this point].
Discussion
- This seems to boil down to a Python 2.7 vs 3.x issue. 

[Link: ``importlib.import_module()``] throws a ``KeyError`` in Python 2.7 and an ``ImportError`` in Python 3. The Celery function ``find_related_module()`` only catches the ``ImportError`` so probably just need to also catch the ``KeyError`` to be Python 2.7 compatible.
