Title

Excessive HTTP/2 packets with TCP_NODELAY

Description
### Steps to reproduce

    wireshark &
    curl [URL]
    curl --no-tcp-nodelay [URL]

### Expected behavior

HTTP/2 GET is sent together with TLS Finished (optimally) or in one packet thereafter (realistically) in both cases.

### Actual behavior

Unless --no-tcp-nodelay is specified, HTTP/2 GET is sent in four separate TCP packets after TLS Finished: Magic, SETTINGS, WINDOW_UPDATE, HEADERS.

### Additional information

curl 7.74.0 (x86_64-pc-linux-gnu) libcurl/7.74.0 OpenSSL/1.1.1i zlib/1.2.11 brotli/1.0.9 libidn2/2.3.0 nghttp2/1.42.0

Although it doesn't cause additional RTT, three packets is still (40+32+22)*3 = 282 bytes on IPv6, plus PHY overhead. Additionally, the server usually sends four ACKs back when one would suffice, eating up 216 bytes on the way back. That's a decent chunk on slow cellular devices, considering that as far as I know there's no good reason to send those bytes.

Firefox and Chromium send one Magic+SETTINGS+WINDOW_UPDATE packet, then a separate HEADERS packet. This seems reasonable, if suboptimal. Firefox also sends a large number of PRIORITY messages in the first packet, perhaps in an effort to "warm up" multiplexing.
