Title

channelInactive events with no previous channelActive

Description
I believe there may be a race condition in `AbstractChannel` that allows for multiple `channelInactive` events to fire.

While there are checks for `wasActive` before firing `channelInactive` events, the actual firing of `channelInactive` is done asynchronously. So, two back-to-back (or concurrent) calls to close the channel may result in duplicate `channelInactive` events firing.

I can gather more data on the precise call stacks that are triggering this if we need. However, we definitely think we see this in a simple metrics handler that increments a counter on `channelActive` and decrements it on `channelInactive`. It should never be possible for this to result in negative values, but that is what we are observing.

Perhaps the `AbstractChannelHandlerContext` should be responsible for enforcing valid state transitions? This could simplify some of the calling code in `AbstractChannel`, and at the time of actually invoking a state change inside the event loop, the context could record the updated state in order to de-dupe any concurrent attempts at changing state?
