Title

Music interface getPosition() gives seconds or milliseconds based on backend.

Description
The documentation in com.badlogic.gdx.audio.Music for getPosition() reads
 
/*\* Returns the playback position in milliseconds. */
 

The desktop backend call with AL11.AL_SEC_OFFSET natively returns a value in  seconds .
The android and gwt backends return values that are divided by 1000, giving  seconds .
The iOS backend returns a value multiplied by 1000, giving  milliseconds  (I assume).

Perhaps change the documentation and the iOS backend or change the desktop, android, and gwt backends.

(On another note, issue #921 still is around, this issue especially breaks games that need to sync time to the music, like Stepmania. Calls to Music.getPosition() on the desktop backend return values that increase too quickly (maybe this depends on the hardware implementation?). You can test this by playing music and keeping elapsed time in the application's render method with Gdx.graphics.getDeltaTIme(). If you compare the elapsed time to what getPosition() returns you will see that getPosition() increases at a faster rate that the elapsed time. You can modify the MusicTest file in gdx-tests to set this up quickly but note that this does not happen with all songs, here is one that it does happen with (for me at least): [URL]

I have no clue about openal but doing a quick google search many people say that AL11.AL_SEC_OFFSET rounds and that perhaps AL_SAMPLE_OFFSET divided by the sample rate will be a more accurate value? I also notice that the desktop backend keeps track of renderedSeconds which gets added to AL_SEC_OFFSET??)
Discussion
- Since iOS is the outlier here, I think the correct fix is to change the javadoc to indicate seconds and fix iOS to return the same. Are you in agreement @badlogic? Would prefer to address the position "drift" separately.
- Created pull request for the simple fix.

About the "drift" issue, I'm pretty sure it is related to the MP3 decoder / the way the audio is being streamed into the buffers since everything else works fine when using OGG and WAV files. (Disclaimer: I don't know anything about audio or OpenAL)

I set up an experiment using the same song (in mp3 format originally) and converted to wav and ogg using Audacity. Then each frame in MusicTest render() I printed the total amount of buffers processed (because this determines how often the seconds per buffer is added to the total time in lwjgl.audio.OpenALMusic.update()) and also printed what getPosition() returns and what the elapsed time (using Gdx.graphics.deltaTime()) was.

The result was that a memorable part of the song occurs when 50 buffers have been processed (or 11.5 seconds into the song) for both the OGG and WAV files. But for the MP3 file this part of the song occurs after 55 buffers have been processed, and so getPosition() returns (seconds per buffer) \* 55 which is going to be more than the amount of "real" time it takes to get to this part of the song. Just so no one is confused the OGG, WAV, and MP3 all take 11.5 seconds (real time) to get to this part in the song, but the MP3 file takes 5 more "buffers processed" to get there and since the seconds per buffer is always the same no matter the file type, getPosition() will return a value too big. 

So I guess the question is why does the MP3 format take more buffers to get to the same part? Can it be fixed or can the seconds per buffer be adjusted for the MP3 format?
