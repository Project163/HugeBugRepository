Title

Call to flush squashed by reentrancy check

Description
The following can cause the second flush() to fail to be executed, resulting in an unsent message:

``` java
ChannelFuture future = channel.writeAndFlush(message);
future.addListener(new ChannelFutureListener() {
    public void onOperationComplete(ChannelFuture future0) throws Exception {
        future0.channel().write(message2);
        future0.flush();
    }
});
```

If the pipeline is not single threaded, i.e. it's possible to attach the listener before the original future has been set to success or failure, then the onOperationComplete will be called from within flush0 (specifically, at the end of doWrite() for an NioSocketChannel). This results in a reentrant call to flush0, which is ignored due to the inFlush0 check. However, the write loop in doWrite(), called by flush0, has already finished at this point, so message2 is not ever sent.
Discussion
- Can you elaborate on "if the pipeline is not single threaded." All calls to flush() are scheduled to occur on the channel's event loop.
- Sure. Let's say you have two handlers and two EventExecutorGroups, like so:

``` java
pipeline.addLast(groupA, "handlerA", handlerA);
pipeline.addLast(groupB, "handlerB", handlerB);
```

My initial code above resides in handlerB, although 'onOperationComplete' will be called from groupA's threadpool, since it does the final flush, causing the write to complete and the future to be fulfilled. This will result in a reentrant call to flush from within groupA's thread (to simplify debugging, I set groupA and groupB to have a single thread each), after the write loop has finished, but before inFlush0 is set to false.

- Re: threading confusion, I have my ServerBootstrap set up with groups like so:

``` java
serverBootstrap.group(bossGroup, groupA);
```

So, if I'm getting the terminology right, that makes groupA's thread the same as the Channel's thread, correct? Then handlerA above is likely unnecessary to demonstrate the issue.

I will try the suggested fix and see how that goes.
- I think this is a bug in `NioSocketChannel.doWrite()`.  It has to loop until there are no more flushes left (or the socket buffer is full).  It currently just doesn't loop at all.  Other doWrite() implementations are fine because it relies on `ChannelOutboundBuffer.current()` which always makes sure all flushed messages are considered.
