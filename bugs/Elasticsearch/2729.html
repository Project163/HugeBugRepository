Title

[ML] Model snapshot upgrade processes need better cleanup/cancellation functionality

Description
While working on #81519 I noticed a few things about model snapshot upgrades related to cancellation and cleanup:

1. If a model snapshot upgrade persistent task gets cancelled then we don't explicitly kill the associated `autodetect` process.  That process will _probably_ exit pretty soon when its named pipes disconnect from the JVM, but there's no guarantee.  Cancelling the persistent task should explicitly kill the native process.
2. Deleting a job should cancel any model snapshot upgrade tasks for that job before it tries to delete other data.
3. If errors occur in the node operation of a model snapshot upgrade then they shouldn't be logged as errors or generate audit messages if the persistent task has been cancelled.  We've seen with other types of persistent task that these spurious errors can cause noise, confusion and unnecessary support cases, so we should take steps to silence them.
4. I couldn't see how model snapshot upgrade tasks that get set to `failed` ever get removed from cluster state.  Although they'll do nothing, they cause clutter in the cluster state.  This could get bad if some other problem causes a user to repeatedly try upgrading model snapshots and all fail to upgrade for some reason.  For other persistent tasks we have the idiom that force-closing or force-stopping them removes the persistent task from cluster state.  We need _something_ to eventually remove failed model snapshot upgrades from cluster state.
