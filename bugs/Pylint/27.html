Title

consider --init-hooks precedence over --load-plugins on the command line

Description
Originally reported by: **Yann Dirson (BitBucket: [Link: ydirson], GitHub: @ydirson?)**

---

I have written a small pylint plugin, stored in my project as Overlord/pylint.py.
First, I had to blindly try to find out I had to use " load-plugins=Overlord/pylint" and not
"load-plugins=Overlord.pylint", as would be expected from the "as comma separated values of python modules names". That gives a cryptic "ImportError: No module named interfaces".

Then I can't seem to configure pylint to find the module :
- default sys.path includes ".", so "import Overlord.pylint" works from the interpreter
- "PYTHONPATH=$PWD pylint" finds the plugin
- just "pylint" does not find it

It is again not very intuitive to have a behaviour that's not consistent with python. strace reveals that the directory search nearly follows sys.path, but looks in /usr/bin/ first instead of cwd - is that a misinterpretation of '' as sys.path element ?

Then I stumbled on [URL] which looks like it could be used as a workaround, but even appending an absolute hardcoded version of $PWD does not result in anything. Introducing a typo in the init-hook does not even produce an error, in fact : is it even run ?

Discussion
- _Original comment by_ **Yann Dirson (BitBucket: [Link: ydirson], GitHub: @ydirson?)**:

---

Oh I see, I have dealt with the '.' case in my app's launch script and forgot about it, sorry for this.

Having to set PYTHONPATH=$PWD each time pylint is run seems however quite suboptimal. Isn't there a way to add to sys.path from pylintrc ?  What about this init-hook, which the doc touts for this use, but does not provide any example ?
`pylint --init-hook='assert False' --load-plugins=Overlord/pylint` even fails with the ImportError, while `pylint --init-hook='assert False'` triggers the assert, apparently showing the hook is just run too late for this use.

On the module-name issue, I take your statement as a confirmation that I hit a real bug too:
