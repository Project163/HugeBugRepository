Title

SQL server does not report on foreign key constraint that targets a unique, non PK column

Description
**The bug**
Alembic creates redundant migrations with foreign keys drop/create if foreign keys referencing to the field
with unique index with no unique constraint

**Expected behavior**
Warning (Error?) when trying to create a foreign key on a field with unique index with no unique constraint and no migration file generated at all, since there's no changes to the schema

**To Reproduce**
I used the following model:
```
from sqlalchemy import (
    BigInteger,
    Column,
    ForeignKey,
    Unicode,
... [Log Snipped] ...
    mother_id = Column(ForeignKey(BaseTable.id))
    mother_name = Column(ForeignKey(BaseTable.name), nullable=False)
```

- Install alembic 1.7.3
- `alembic revision --autogenerate`
- `alembic upgrade head`
- `alembic revision --autogenerate` -> redundant migration


**Versions**
- OS: Windows 10
- Python: 3.8.10
- Alembic: 1.7.3
- SQLAlchemy: 1.4.25
- Database: Microsoft SQL Server 2019
Discussion
- hi as youll note SQLAlchemy is not able to receive information from SQL Server regarding this foreign key constraint.   Generating your tables as follows using alembic:

```
sql
CREATE TABLE [BaseTable] (
	id BIGINT NOT NULL IDENTITY, 
	name NVARCHAR(50) NOT NULL, 
	PRIMARY KEY (id)
... [Log Snipped] ...
	FOREIGN KEY(mother_name) REFERENCES [BaseTable] (name)
)
```

we see what's special about the second FK is that it targets a column that's not in the primary key of the table, it just has a unique index (which in my experience also constrains it uniquely but perhaps SQL Server has some strange behavior here?) on it.  im not sure that we have a standard test suite that specifically targets that style of FK, but at least in this case it does not seem to work on SQL Server.  The query we issue and the result returned by SQL server can be seen in the session below:

```
py
In [1]: from sqlalchemy import create_engine

In [2]: e = create_engine("mssql+pyodbc://scott:tiger^5HHH@mssql2017:1433/test?driver=ODBC+Driver+13+for+SQL+Server", echo='debug')

... [Log Snipped] ...
  'referred_table': 'BaseTable',
  'referred_columns': ['id']}]
```

above we can see there's only one FK coming back, nothing about the second one.   We'd need to know how to query information schema to get info on that other one.  cc @gordthompson
- why?  is that not valid in SQL Server?  is SQL Server silently ignoring the constraint?   I'm not familiar with this behavior.   a "unique index" in a DB such as Postgresql is suitable as a target for an FK, and if you try to create an invalid FK, you'd get an error.
