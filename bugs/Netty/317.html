Title

thread cache eviction task can erroneously prevent jvm from exiting

Description
- It is scheduled on the global event executor -- a non-daemon thread that will not die until no tasks have been on it for a minute (according to the docs at least; that taskQueue.take() call is vaguely suspicious even if it should never be called in theory).
- The task itself is recurring and will not go away until there is no living thread with a thread local cache.
- If your living thread with a thread local cache is a daemon thread, then you have effectively and quite unexpectedly upgraded that thread to a non-daemon thread.

It is probably not a great idea to circumvent standard thread logic this way, and it is particularly problematic for library code that would prefer not to break the ByteBufAllocator abstraction to figure out whether it needs to be on guard for pooled allocators that can affect its thread life cycle logic.

We can probably also assume that the cache eviction logic does not need to be protected by shutdown logic since it is just freeing memory and it will all be freed anyway when the jvm exits. However, I suppose it wouldn't be terribly surprising if there was some awful reason this wasn't the case so I am open to correction on that. 

Otherwise, two relatively easy/ naive solutions might be:
1. just have a second global event executor instance that runs on a daemon thread. It might be nice to make it public, but it could also just be internal to the pooled allocator.
2. make the existing executor a daemon thread but guard it with a shutdown hook to perform some time limited clean up (similar to guava's exiting executors). This may affect current uses though so a trade off might have to be considered for delayed/ non-delayed tasks and grace period.

- Review complete. I already implemented my own work around, and actually, it _is_ kind of funny...

The daemon thread that was holding a thread local cache and therefore inadvertently preventing shutdown was actually a cache maintenance thread of my own. It tracks buffers used by open files and makes sure idle write streams don't keep huge dangling buffers. Since it sits in a scheduled thread pool executor, I couldn't even manually shut down the thread (to free the thread local cache) without losing the ability to start it back up again or starting it up every time the task runs. So I just absorbed its responsibilities into application threads. Funny how similar it was.
