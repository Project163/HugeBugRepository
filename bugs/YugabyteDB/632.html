### Description

Full details of this issue including links to prior discussions are available for internal users in Zendesk ticket 2908.

- If the amount of data is not very big, you can skip the compaction step.
- Tried the steps below to repro locally, but upgrade consistently goes through without issues.

#### Download yugabyte releases `2.4.4` and `2.8.3`
```
wget [URL]
tar xvfz yugabyte- -b7-darwin-x86_64.tar.gz
wget [URL]
tar xvfz yugabyte- -b19-darwin-x86_64.tar.gz
```

#### Create a 2.4.4 cluster
In the ` ` release folder run:
```
./bin/yb-ctl destroy && ./bin/yb-ctl create --rf 3
./bin/ysqlsh
```

#### Set up database objects
Create user, schemas, databases, tables, indexes, foreign-key constraints, etc.
```
CREATE ROLE test_user WITH LOGIN PASSWORD '1234';
CREATE SCHEMA myschema;

CREATE TABLE myschema.t1(h1 int, r1 text, v1 int unique, v2 text, primary key (h1 HASH, r1 ASC));
CREATE INDEX ON myschema.t1(v2);

#### Simulate the cluster upgrade
```
./bin/yb-ctl stop
```
Go to ` ` release folder
```
./bin/yb-ctl start
./bin/yb-admin --master_addresses  :7100, :7100, :7100 -timeout_ms 600000 upgrade_ysql
```

- This issue happens when upgrading from cluster created prior to YB v2.3.3, and it affects the following indexes:

* `pg_class`
  * `pg_class_relname_nsp_index`
  * `pg_class_tblspc_relfilenode_index`
* `pg_type`
  * `pg_type_typname_nsp_index`
* `pg_attribute`
  * `pg_attribute_relid_attnam_index`
* `pg_depend`
  * `pg_depend_depender_index`
  * `pg_depend_reference_index`

However, tables with a primary key (`pg_class`, `pg_type`, `pg_attribute`) don't seem to suffer from it.
