Title

The browser build fails because of one of the rules

Description
Running the bundle script currently fails because the `no-mixed-requires` rule uses the `repl` module which does not have a browserified equivalent.
Discussion
- I'd like to hear thoughts around the way the `no-mixed-requires` rule could be changed to make it more generic and not tied to Node. Currently it will only run in Node (since the `repl` module doesn't get browserified) and is specific to Node anyway (if it were to run against code designed for use in the browser it could flag `require` calls incorrectly).

My stop-gap solution was to simply exclude the rule from the bundle. As it was decided this was not a good approach the other solution is to change the behaviour of the rule.

A couple of suggestions:
- Remove the parts of the rule that are specific to Node
- Remove all code that can produce the "Do not mix core, module, file and computed requires" message
- Shim the `_builtinLibs` property of the `repl` module when it isn't available (what would it return? An empty array?)
-  Exclude the rule from the bundle 

\cc @pigulla (since you wrote the rule originally)
- I'm not sure what exactly you mean by "more generic". RequireJS, for instance, does not have any built-in modules, as far as I am aware. Statements like 

```
var x = require('foo');
```

are very rarely to be seen in a Browser environment.

If I remember correctly, `no-mixed-requires` is disabled by default, so it shouldn't be too much of a problem anyways - don't enable it if you're in a Browser environment. Maybe we should use a prefix and rename it to `node-no-mixed-requires`?

- Okay, I see your point. I'm not particularly happy with a hard coded list of modules that needs to be maintained when Node.JS provides a way to retrieve exactly that. Plus I don't see who would want to lint Node.JS-code in a browser anyway (but I guess there are circumstances where that makes sense).

I would throw a warning if the `env.node` config option is set but eslint doesn't run under node to inform the user that the rule may potentially report incorrect errors. Seems the cleanest and most easily maintained solution to me.

However, I'd agree that misidentifying a built in module is not the end of the world so I can totally live with your suggestion ;-)
- If we really want to get fancy, we can auto-generate this list as part of
the build process, too. (However, you do end up relying on the person
running the build process to have the latest Node.js version installed
while doing it.)
