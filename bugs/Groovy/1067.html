Title

Use of generics causes "The class p.A refers to the class p.A and uses 1 parameters, but the referred class takes no parameters"

Description
Description   	« Hide 
If I create a class 
p.A<T> 
and a class 
p.B extends p.A<Long> 
I get an error "The class p.A refers to the class p.A and uses 1 parameters, but the referred class takes no parameters", if I instantiate a class p.B 

 The error comes, if I put class A and B in different files. 
If I put them in one file, it works fine 

 see attached test cases in testcase.zip 

 
	 folder ok contains one script show.groovy which works fine 
	 folder notok contains one script which defines class p.A and one script which defines class B and uses it
Discussion
- In the notok case, when p.A and p.B are defined in different script files, the failure is being encountered because groovy compiler is first processing p.B and for p.B when it reaches GenericsVisitor#checkGenericsUsage(ClassNode n, ClassNode cn), its superclass cn (p.A) is not resolved yet and hence does not have its generics information loaded. 

 I am not sure how to delay p.B's generics check so that it lets p.A's compilation happen first when it sees it unresolved yet. 

 The current compiler design does not support such pause and resume later kind of thing, does it?  

 Jochen? 

 Can it pause p.B's compilation at resolve phase (generics check) when it sees p.A unresolved, do p.A first and resume p.B's rest of the compilation? 

 If not, any suggestion on what can be done currently about it?
- Well, sadly we have no continuations. The solution would be to use GenericsVisitor not in the same phase as ResolveVisitor. Since the GenericsVisitor is doing only checks it should be in the same phase as Verifier. With that, the problem solves itselfs
- Fixed as suggested - i.e., by changing the phase in which GenericsVisitor runs. 

 Tried hard to add a test in the codebase for it but couldn't figure out how to do it - as it depended on 2 classes using 
generics in being 2 different files and also their ordering. I took care of that but then all test scripts's SourceUnits 
are loaded by the compiler when groovy compiles test files, which means that their source-level generics info 
is loaded by APP, which was against the scenario needed to reproduce this issue - as this scenario needed  
dependent file's ast as not being loaded yet.
