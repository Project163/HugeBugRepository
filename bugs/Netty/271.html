Title

SslHandler silently errors when write() is called with something other than a ByteBuf

Description
This may not technically be a bug, but it is a change in behavior from the previous version. Now, when SslHandler's write() method is invoked from DefaultChannelHandlerContext#invokeWrite, if the message is not a ByteBuf, an exception will be thrown, caught, and other than failing the promise, discarded. 

Previously (v3.5), such a message would simply be passed on down the pipeline. Depending on how you all feel it should work, it may be ok as is in the new version. Currently I'm working around this by extending SslHandler to pass non-ByteBuf messages down the pipeline, so it's not a blocker.
Discussion

Am 11.09.2013 um 05:31 schrieb Greg Soltis notifications@github.com:
- Sure. In our case, we keep track of total bytes in/out, before the ssl encryption is removed or added. These bytes are then tagged with the account that the request came from. However, it is impossible to know the account before the encryption has been unwrapped and the request parsed. So, we have a stage at the very beginning of the pipeline that just counts bytes as they go by. Then we have a stage later in the pipeline that writes a tag into the channel. This tag is intercepted by the first stage and used to tag the byte counts to an account.

- Can fireUserEvent be made to go in the outbound direction? Or are you suggesting firing user events in the first stage, when the byte counts are updated? I suppose it could also be done with a separate pipeline stage post-tagging that maintains a reference to the byte counter, but I'm less inclined to do that since the byte counting and account identification happen in separate thread pools. The netty pipeline is already set up to handle passing the messages back and forth across threadpools, so I would prefer to use it. My current solution of wrapping the SslHandler class to ignore non-ByteBuf messages is working, so it's not an urgent issue.
