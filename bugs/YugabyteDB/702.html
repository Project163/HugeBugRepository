Title

[DocDB] Post-split compactions can crash tserver

Description
Jira Link: [Link: DB-3333]
### Description

Originally crashes were observed by @qvad during stress test.
I was able to reproduce with on local RF=1 cluster with the following settings and workload:
```
RF=1
MASTER_FLAGS='"enable_automatic_tablet_splitting=true","tablet_split_low_phase_size_threshold_bytes=0","tablet_split_high_phase_size_threshold_bytes=0","tablet_split_low_phase_shard_count_per_node=0","tablet_split_high_phase_shard_count_per_node=0","tablet_force_split_threshold_bytes=100000"'

TSERVER_FLAGS="db_write_buffer_size=100000"

./bin/yb-ctl --rf=$RF create --num_shards_per_tserver=1 --ysql_num_shards_per_tserver=1 --master_flags "$MASTER_FLAGS" --tserver_flags "$TSERVER_FLAGS"
java -jar ~/code/yb-sample-apps/target/yb-sample-apps.jar --workload SqlSecondaryIndex --nodes  :5433 --num_threads_read 2 --num_threads_write 6 --num_unique_keys 1000000000 --nouuid
```
Discussion
- Post-split compaction could be triggered and started before `TabletPeer` is fully initialized, in this case before `TabletPeer::tablet_` is set. But during compaction `Tablet::DeleteMarkerRetentionTime` could be called by compaction context.

In its turn `Tablet::DeleteMarkerRetentionTime` can result to following calls:
```
../../src/yb/tablet/running_transaction.cc:219:                                                         @        yb::tablet::RunningTransaction::SendStatusRequest(long, shared_ptr  const&)
../../src/yb/tablet/running_transaction.cc:132:                                                         @        yb::tablet::RunningTransaction::RequestStatusAt(yb::StatusRequest const&, std::unique_lock *)
../../src/yb/tablet/transaction_participant.cc:792:                                                     @        yb::tablet::TransactionParticipant::Impl::MinRunningHybridTime()
../../src/yb/tablet/transaction_participant.cc:1769:                                                    @        yb::tablet::TransactionParticipant::MinRunningHybridTime() const
../../src/yb/tablet/tablet.cc:3863:                                                                     @        yb::tablet::Tablet::DeleteMarkerRetentionTime(std::vector  > const&)
```

Where `RunningTransaction::context_.participant_context_` is actually a reference to `TabletPeer` (which is not yet fully initialized and `TabletPeer::tablet_` is not set).
So on `RunningTransaction::SendStatusRequest` send
...[Text Truncated]...
                                                                   @        non-virtual thunk to yb::tablet::TabletPeer::SafeTimeForTransactionParticipant()
../../src/yb/tablet/transaction_participant.cc:1166:                                                    @        yb::tablet::TransactionParticipant::Impl::ProcessRemoveQueueUnlocked(yb::tablet::MinRunningNotifier*)
../../src/yb/tablet/transaction_participant.cc:1145:                                                    @        yb::tablet::TransactionParticipant::Impl::EnqueueRemoveUnlocked(yb::StronglyTypedUuid  const&, yb::tablet::RemoveReason, yb::tablet::MinRunningNotifier*)
../../src/yb/tablet/running_transaction.cc:345:                                                         @        yb::tablet::RunningTransaction::DoStatusReceived(yb::Status const&, yb::tserver::GetTransactionStatusResponsePB const&, long, shared_ptr  const&)
../../src/yb/tablet/running_transaction.cc:247:                                                         @        yb::tablet::RunningTransaction::StatusReceived(yb::Status const&, yb::tserver::GetTransactionStatusResponsePB const&, long, shared_ptr  const&)
```

And we then have a crash there, because `tablet_ == nullptr` :
```
HybridTime TabletPeer::SafeTimeForTransactionParticipant() {
  return tablet_->mvcc_manager()->SafeTimeForFollower(
      /* min_allowed= */ HybridTime::kMin, /* deadline= */ CoarseTimePoint::min());
}
```
- Fixed by reverting [URL] which introduced the issue.
