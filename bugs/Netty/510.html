Title

PemReader chokes on headers in private key block generated by old versions of OpenSSL

Description
I have a certificate/key in a .p12 file. I exported the key to a .pem file as follows:

``` sh
openssl pkcs12 -in aps-key.p12 -nocerts -out aps-key.pem
```

…and wound up with a file that looks like this:

```
Bag Attributes
    friendlyName: HTTP/2 test
    localKeyID: F6 24 E2 FE 0A 69 C5 BA D5 FD 0C 57 01 9F 0C 1D FF 8F 4B 62 
Key Attributes:  
-----BEGIN RSA PRIVATE KEY-----
... [Log Snipped] ...
 
-----END RSA PRIVATE KEY-----
```

I'm trying to load the key using `SslContextBuilder#keyManager(File, File, String)`, but `PemReader` is failing to find the key in the file because `KEY_PATTERN` doesn't match. It appears to be stumbling on the headers (`Proc-Type` and `DEK-Info`, which contain unexpected characters) inside the private key block. Those headers are generated by at least OpenSSL 0.9.8zg, but don't seem to be generated by OpenSSL 1.0.2e at the latest. I haven't checked versions in between.

For the sake of completeness, the stack trace looks like:

```
… java.lang.IllegalArgumentException: File does not contain valid private key: /Users/jon/Desktop/aps-key.pem
    at io.netty.handler.ssl.SslContextBuilder.keyManager(SslContextBuilder.java:201)
    at SslHandshakeClient.main(SslHandshakeClient.java:34)
Caused by: java.security.KeyException: found no private key: /Users/jon/Desktop/aps-key.pem
    at io.netty.handler.ssl.PemReader.readPrivateKey(PemReader.java:99)
    at io.netty.handler.ssl.SslContext.toPrivateKey(SslContext.java:923)
    at io.netty.handler.ssl.SslContextBuilder.keyManager(SslContextBuilder.java:199)
    ... 1 more
```

EDIT: This is happening with Netty 4.1 beta 8.

- I just ran through those steps, and just converting to a PKCS#8-formatted key is enough to clear those headers (i.e. it doesn't look like we necessarily need to explicitly call out an algorithm).

That said, I think there may be another (masked?) issue at play here. From the [Link: OpenSSL release notes] (emphasis added):

So that means that the key I originally extracted with OpenSSL 0.9.8zg with:

```
openssl pkcs12 -in key.p12 -nocerts -out key.pem
```

…wasn't PKCS#8-encoded at all. It was in the "traditional format." So I guess this leaves me with two thoughts:
1. If we wind up with bonus headers in the private key block, we're probably not looking at a PKCS#8-formatted key at all, and explicitly converting to PKCS#8 will be enough to set things right both by way of removing the headers and by converting to the correct format (which I think would have surfaced as an issue if the headers weren't present).
2. My "traditional format" key began with `-----BEGIN RSA PRIVATE KEY-----`, while my PKCS#8-formatted key began with `-----BEGIN ENCRYPTED PRIVATE KEY-----`. I haven't found anything in writing that says that PKCS#8-formatted keys will always begin with that string, but if we can build confidence that they do, that might be an easy way to detect this problem going forward.

So, yeah, @normanmaurer, looks good to me ;)
