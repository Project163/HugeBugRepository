Title

alt-svc should fallback if alt-svc doesn't work

Description
### I did this
Using curl with alt-svc support compiled in:
```
$ curl --alt-svc test.txt [URL]
 
  
 301 Moved Permanently 
  
... [Log Snipped] ...
$ curl --alt-svc test.txt [URL]
curl: (7) Failed to connect to 3dbbdetxoyw4nsp6c3cc456oj2aysmzhbfzz6s43ezxzsfxxri3h5xqd.onion port 443: Connection refused
```
[URL] uses an alt-svc header pointing to a tor .onion address. Cloudflare does this too: [URL]

### I expected the following
The second curl invocation should have worked.

According to [URL]

So falling back is okay.

I can see a few of approaches:
* Only add the alt-svc to the cache when curl determines that the service is reachable. This is what Chrome and Firefox do.
* Always add the alt-svc to cache (which is what curl does today), but then fall back to the original origin if the alt-svc isn't reachable. This is like how the IPv6 to IPv4 fallback works.

Discussion
- You're right. The current alt-svc code is just a switch without fall-back logic. Not good enough.


Well, that would basically just force us to have two caches since we still need to store the information about all the *possible* alternatives until they've been verified. I don't think that's good approach. Also, an alternative that works now can suddenly not work the next time, or vice versa.


In my mind this is the most sensible way to go about it. I presume that actually will rather be translated into a *list* of options to try in a given order until one works, as there can be several listed alternatives and the "un-alternative" version would then be the last to try...
