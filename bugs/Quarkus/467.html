Title

CDI lifecycle behavior different when using reactive messaging and @Incoming and @StartupEvent

Description
**Describe the bug**
It appears that although the default lifecycle behavior of JAX-RS resource classes is that of `@Singleton` (as described in the [Link: REST/JSON guide]), when using reactive messaging and `@Incoming`, multiple instances of the resource appear to be created, so that variables initialized in startup events aren't accessible when JAX-RS endpoints are accessed.

**Expected behavior**
Variables initialized in a `@Observes StartupEvent` method are accessible later on when JAX-RS endpoints are accessed.

**Actual behavior**
Instance variables initialized in a `@Observes StartupEvent` method in a JAX-RS resource class are not set to the right values when the JAX-RS endpoints are accessed. Basic debugging shows multiple instances are created, not "respecting" the default behavior from docs.


**To Reproduce**
Steps to reproduce the behavior:
1. Generate new basic JAX-RS project
2. Change `GreetingResource` to this:

```
java
package org.acme.quickstart;

import java.io.IOException;
import java.util.concurrent.CompletionStage;
... [Log Snipped] ...
    }
}
```
2a. Fire up a temporary kafka server on `localhost:9092` using the `docker-compose.yml` from the [Link: kafka guide].
3. Compile and run executable jar
4. Access `localhost:8080`.
5. Observe the value returned is *blank*, rather than the expected value of `bar` as set in the `init()` method. Also observe the identifiers generated in the `init()` method are different than those generated in the `getfoo()` method. I would expect these to be identical if indeed the behavior was that of a singleton.
6. Add `@Singleton` to the resource class, rebuild, re-run, and try curl again
7. Observe expected behavior (the value `bar` is output).
8. You can also comment out the `@Incoming` method which makes it work.
