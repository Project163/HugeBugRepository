Title

Field with const kwarg allows empty value

Description
# Bug

Output of `python -c "import pydantic.utils; print(pydantic.utils.version_info())"`:
```
             pydantic version: 1.6.1
            pydantic compiled: True
                 install path: .../.venv/lib/python3.8/site-packages/pydantic
               python version: 3.8.0 (default, Oct 28 2019, 16:14:01)  [GCC 8.3.0]
                     platform: Linux-5.4.0-42-generic-x86_64-with-glibc2.27
     optional deps. installed: ['typing-extensions']
```
 

 

 

```
py
from pydantic import BaseModel, Field

class SomeModel(BaseModel):
    type: str = Field('set', const=True)
... [Log Snipped] ...
try_parse({'type': 'lol', 'value': 'some value'})
try_parse({'value': 'some value'})
```
The result will be:
```
success
cannot parse
success
```
It looks pretty strange, I expect the last one will be `cannot parse` because field 'type' is **required** and I provide no value. Doc says:
```
:param const: this field is required and *must* take it's default value
```

There is a workaround:
```py
from typing import Literal
from pydantic import BaseModel

class SomeModel(BaseModel):
    type: Literal['set']
    value: str
```
but first example looks like bug.
Discussion
- Hi @perminovs 
You're right it looks like a bug according to the documentation. In the tests we actually have [Link: one] where default value is expected to be used.
Fixing this would be trivial but IMO it's very weird to write `Field('a', ...)` (so writing a default value) but still expect it to be required.
The `Literal` approach seems like the way to go and maybe we should just
- update the documentation for `const=True` and remove the `field is required` mention
- deprecate this option

I would be in favor of second option as I can't see what it brings to the table compared to `Literal`. It has been added for schema generation but it just makes things messy. @samuelcolvin WDYT ?
- Yes, I'll show our use case for clarifying why we want to use Field with both default and const.
We have json messages with the same structure. While processing we want to hold it as different classes instance, which depends on 'type' value. So we have something like that:
```
py
from pydantic import BaseModel, Field

class CreateSomeEntity(BaseModel):
    type: str = Field('create', const=True)
... [Log Snipped] ...
invalid_input = {'id': 1, 'value': 'value'}
model = deserialize(invalid_input)  # does not raise
```

That's why successful parsing of `{'id': 1, 'value': 'value'}` is confusing. May be I should provided this example when I had opened the issue :smile:

- Because we have removed the `const` argument to `Field` in V2, and `Literal` is handled properly, I'm going to consider this issue completed and will close it.

Regarding how to annotate a field as a list of a few allowed literal values — you can actually put multiple items in a literal:

```python
class Model(BaseModel):
    literal_json_list: List[Literal["foo", "bar"]]
```
You won't be able to enforce the order of the items or length of them like this, but it will at least require that it be a list of just those two literal strings.
- To be clear, if you want to enforce the length you can do `Annotated[List[Literal[...]], Field(max_length=10)]`.
If you want to enforce the length _and_ position then you're right, a tuple is your only option, that's just how Python's type system works.
