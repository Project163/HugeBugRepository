Title

d3.behavior.zoom shouldn’t d3_eventCancel touchstart.

Description
I imagine this is related to #1005 / #1175.

I had implemented panning using `d3.behavior.drag`, and switched to using `d3.behavior.zoom` and now all the elements with tap/click events are no longer responding to taps, but are happily responding to clicks.

Here's a minimal example: [URL]

Obviously, to see the tap-eating you need to view it on a touchscreen device...

Does whatever was done in #1175 need tweaking, or is there a deeper issue?
Discussion
- It’s unrelated to the bug you mentioned. The zoom behavior has always called preventDefault and stopPropagation on touchstart events. The drag behavior has a special fix, which should probably be ported to the zoom behavior:

``` js
// Only cancel mousedown; touchstart is needed for draggable links.
if (touchId == null) d3_eventCancel();
```

Actually, I think the solution would be to just remove the d3_eventCancel from touchstart in behavior/zoom.js, since that implementation already has a separate handler for touch events (whereas with drag, they both go through mousedown).

Care to try it and send a pull request?

- There seems to a [Link: bug] in Android 4.1.x relating to touch events, whereby preventDefault seems to be needed on touchstart to prevent native scrolling from eating up the touchmove events.

However, it doesn't seem to affect Android 4.2.x, so I don't think we need to anything here.  Unfortunately, pretty much anyone targeting Android will likely need to include their own touchstart with preventDefault to work around this, at least until enough users move to ≥4.2, so I'm recording this here for their benefit.
