Title

Dependencies: Resolve version when only URL is known

Description
Currently, when is resolving dependencies and a dependency is specified as a URL but it has not been added to Helm via `helm repo add` the dependency is locked to the exact value specified for the requested dependency. If the specified value is a range (e.g., `^1.2.3) the range is the version it is locked to.

The current situation creates a situation where locking isn't really locked to a version.

With more distributed repos that cross link each other this problem has the potential to get worse.

Instead of locking to the range, Helm should work out the version and lock to the version.

I would suggest the steps:

1. If not cached locally via `helm repo add`, create an automated and not-visible to the user cache.
2. Resolve the version from this invisible cache
3. Lock to the version
4. Clean up any invisible caches (periodically?)
Discussion
- If we are talking about the lockfile, then I :100: agree. We should NEVER lock to a range, as that makes reproducible builds sketchy at best.

The issue above was one of the reasons why I argued for a long time that all repositories must have a named local repo cache. I did not like the implementation that was merged using URLs directly with no cache.

So this proposal is much closer to the way Helm was intended to work. I am okay with it, and would be even happier if these caches were not invisible. I don't see a reason to hide sources from users. (Other package managers don't do that, so I don't see why we should.)

The push-back I have heard that "helm shouldn't write cache data to the local filesystem" is a non-starter here. That's based on an exceedingly niche use case (CI in which no writable volumes are attached), and we should not design Helm around those cases to the detriment of the vast majority of our user population.
- I'm marking this as a bug. A lock file should lock to a specific version. If a range is ending up in the lock file it's not actually locked.
