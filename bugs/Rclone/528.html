Title

lsjson --hash on local filesystem is very inefficient

Description
I was attempting to do an lsjson --hash on my local filesystem to produce MD5 hashes so I can compare with a lsjosn dump from Google Drive to see if I have duplicate files in different folders on Google Drive before uploading the files due to poor internet bandwidth.

[URL]

I noticed that it was incredibly slow to produce the hashes on larger files and even when doing lsf --hash MD5 it was still taking lots of time. (30mins vs 2mins with Powershell)

After reviewing the code I found that lsf calls lsjson and lsjson steps through and performs each hash sequentially on the file.

[URL]

Would it be possible to rewrite this in a few ways, 

- One to pass a command line option to perform an array of hashes e.g. something like MD5,SHA256,SHA512 etc (from the list of already supported hashes) defaulting to all if not supplied
- Two to read the file once and perform all requested hashes concurrently to reduce disk access wear and IO bottle necks
- Three to perform the multiple hashes in a way where each one is on it's own thread to make use of multicore CPU's and reduce CPU as a bottle neck

Unfortunatly my Go skills will allow me to build a custom rclone binary that only does an MD5 hash but I don't think I would be able to add the above functionality to a pull request.
