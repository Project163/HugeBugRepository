Title

ngcc: should support `browser` property

Description
Good day!

I'm the author of the [Link: OverlayScrollbars] library and I'm providing a Angular wrapper. This wrapper is written in TypeScript but isn't using ng-packagr for building. Instead I've written my own build script, and I'm compiling it with `ngc` the repo can be found [Link: here]. 
The wrapper isn't very complex and also isn't using any special, exotic or deprecated features of Angular.

Since Angular9 user have reported issues ([Link: here] and [Link: here]) with the wrapper, which are related to ivy. After a bit of experimenting I found out, that you have to run `npx ngcc` to make it function (at least its working in my project).

My question is, how do I prevent this? I know that Angular is running the `ngcc` command if you compile your project with `ng serve` but for some reason this isn't enough for my library. I have to run it manually in order to not getting a error in the browser console.

I checked the `package.json` before and after running `ngcc` manually and the difference is small, but there is a difference in the `__processed_by_ivy_ngcc__` section:
**Before running ngcc manually:**
```json
"__processed_by_ivy_ngcc__": {
  "module": "9.0.6",
  "typings": "9.0.6"
}
```
**After running ngcc manually:**
```json
"__processed_by_ivy_ngcc__": {
  "main": "9.0.6",
  "module": "9.0.6",
  "typings": "9.0.6"
}
```
How can I tell angular to run ngcc also on the main module without executing `ngcc` manually, or how can I solve the whole issue differently?
Discussion
- So when you run `ng serve` I can see that the CLI is asking ngcc to process the `module` entry-point, which is the ESM5 format: 

```
$ ng serve
0% compiling
Compiling @angular/core : es2015 as esm2015
Compiling @angular/common : es2015 as esm2015
Compiling @angular/platform-browser : es2015 as esm2015
... [Log Snipped] ...
** Angular Live Development Server is listening on localhost:4200, open your browser on [URL] **
: Compiled successfully.
```

But then when you look at the bundle that the CLI build (i.e. webpack) is producing, it appears to have used the `main` entry-point instead (which was not processed by ngcc).
