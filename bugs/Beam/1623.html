Title

Flink uber jar job server hangs

Description
This was observed on Kubernetes. I suspect this behavior might also be the reason beam_PostCommit_PortableJar_Flink is timing out.
Discussion
- The Flink uber jar job server has two streams, one for state and one for messages. They share history  [1]  and don't yield a message if it is a duplicate according to that history  [2] . So if the message stream reads the terminal state first, the state history will never yield it, and the job will never register as complete. 

 I avoided this in the Spark implementation by deferring de-duplication to later, so all messages are yielded regardless of whether they are duplicates or not.
