Title

[DocDB] YSQL select max() returns inconsistent result after tablet splitting

Description
Jira Link: [Link: DB-4257]
### Description

Tried multiple times on RF=3 cluster with version `version   build PRE_RELEASE revision   build_type RELEASE`.
```
create table demo2 ( id int generated always as identity, data text, primary key(id asc) );
copy demo2(data) from program 'base64 -w 16384 /dev/urandom | head -c 419430400';
COPY 25599

copy demo2(data) from program 'base64 -w 16384 /dev/urandom | head -c 419430400';
... [Log Snipped] ...
 37735
(1 row)
```

Then restarted ysqlsh and getting:

```
yugabyte=# select max(id) from demo2;
  max
-------
 19302
(1 row)
```
Discussion
- Restarting both `yb-tserver` and `postgres` processes on cluster fixes the issue until the next split.
- Summarizing analysis from the slack thread [URL]
The key facts here are that 
- we have a backward scan
- tablet split has happened

Postgres planner applies min/max optimization when there is suitable (asc or desc) index on the column, so it scans the index in correct direction and picks the first row. 
So executor composes a request to scan the PK backward with 1 row limit. However, executor does know about the split, and thinking there is only one partition, it routes the request to the tablet with empty lower bound (we use lower bound to identify target tablet). In practice, the target tablet has a higher bound, which differ from expected (empty), but nonetheless tserver starts scan and return one row, which is taken by PG as one with the highest key.

When doing forward scan tserver handles mismatched upper bound by injecting paging info into the response when end of the tablet is reached, so scan continues into the next partition. To be consistent, backward scan shouldn't start if target tablet has mismatching upper bound, instead it should return no rows and paging state with redirection to correct tablet.

There is a problem if there was multiple splits. It is easy to identify next partition, its lower bound would be the same as the upper bound of the current partition, however lower bound of the last partition may be not known.
