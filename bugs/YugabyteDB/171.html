Title

RocksDB checkpoint could be incorrect in case it is taken in parallel to compaction finish

Description
The checkpoint is executed with the following order of commands:
1) Disable .SST files deletion
2) Take a list of DB live files (.SST + CURRENT + MANIFEST)
3) Copy/hard link all necessary files.
4) Enable .SST files deletion

When compaction/flush finishes it writes new .SST file and adds it to MANIFEST.
But usually, it is just added to the end of MANIFEST.
And it could happen in parallel to the checkpoint.
So manifest would reference a new file, that was not listed at step (2).
Such a checkpoint is incorrect and could not be opened as RocksDB.

This problem affects remote bootstrap and backups, that use RocksDB checkpoints.
Remote bootstrap could fail to open the bootstrapped tablet, it is not critical, since we could always redo remote bootstrap.
Backup based on such a checkpoint would not be possible to restore.
Discussion
- This regression is recent, happened in D5756
