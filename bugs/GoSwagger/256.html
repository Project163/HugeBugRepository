Discussion
- A few comments on that issue.

1. It is futile to override the Content-Type header this way: it is overridden by the client runtime based on the "consumes" mime types
2. Everything works just fine if the operation declares only one "consumes": "multipart/form-data" (see a working example: [URL]
3. The problem comes from the two "consumes" types specified:
   * problem N°1: the order of the mime types for the client is reversed. So it picks primarily "application/x-www-form-urlencoded", which was not intended
   * problem N°2: although the swagger 2.0 states that files _may_ be transferred over "application/x-www-form-urlencoded" ([Link: reference]), our client runtime (go-openapi/runtime/client) does not support that (because it is not the _preferred_ way) and results in a mismatch: sending a multipart body with Content-Type: "application/x-www-form-urlencoded"

It is possible to work around this problem by forcing the MIME type in the operation by using an option.
Like so:

- There are a few ways we could improve this situation:
* generate a `UseMIME(...)` option with the client, so that the caller may switch easily when several mimes are consumed
* generate the client with mime types in the specified order
* support application/x-www-form-urlencoded for files in runtime (this would be workable only for small files, and we'd lose the ability to stream). This would make the runtime 100% compliant with the spec, but with little practical use (IMHO).
