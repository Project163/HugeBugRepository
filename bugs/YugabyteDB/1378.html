Title

[DocDB] Fix export/import snapshot so it preserves the DocDB next column ID of tables

Description
Jira Link: [Link: DB-16545]
### Description

Currently this code does not save the DocDB next column ID as part of the snapshot so it is forced to estimate what it should be after the restore.  It does this by just taking one beyond the maximum DocDB next column ID in the snapshot schema.

Here is an example:

# What happens to column IDs when we backup and restore a database?

Suppose we backup a database with:
TABLE my_table:
  * column x, PG column ID 1, DocDB column ID 0
  * column y, PG column ID 2, DocDB column ID 1, marked deleted
  * column z, PG column ID 3, DocDB column ID 3
  * column q, PG column ID 4, DocDB column ID 4, marked deleted
  * next DocDB column ID: 5

Note that there is a skip in the DocDB column ID from 1 to 3 due to a failed ADD COLUMN DDL.

After restoring this ends up with:
TABLE my_table:
  * column x, PG column ID 1, DocDB column ID 0
  * column z, PG column ID 2, DocDB column ID 3
  * next DocDB column ID: 4

Notice:
  * Postgres column IDs can differ on the two sides
  * the DocDB column IDs for columns are the same on the two sides
  * the next DocDB column ID can differ between the two sides

(The above is from my understanding of the code rather than an actual test.)

The problem here is that the next DocDB column ID is 4 on the restored database but 5 on the database being backed up.

It may not be obvious, but this can cause major problems.  In particular, this allows reuse of DocDB column IDs with different types.  The following sample test:
