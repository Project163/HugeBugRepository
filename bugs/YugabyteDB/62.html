Title

Several issues with transactions during tserver shutdown

Description
While trying to reproduce ENG-3945 TServer restarts were added to QLTransactionTest.WriteConflicts.
That uncovered several issues:

1. Suppose the following scenario:
Transaction is created and writes 2 intents to tablet TABLET1. last_write_id is set to 2.
TServer restart happens.
Transaction tries to write additional intents to TABLET1 (that could be retry for the same intents).
Since write request contains metadata and transaction participant does not have such running transaction, it creates new running transaction from specified metadata, w/o checking rocksdb, so last_write_id is set to 0.
So newly added intents has write_id starting with 0, instead of 2. 

2. Log is running in appender_pool, but uses allocation_pool. And allocation_pool is being shutted down before appended_pool. There could be case when operation fails because allocation_pool is shutted down. But Log does not allow such failes, so whole tserver would crash. 

3. It is possible that transaction cannot be aborted, because of remote tserver shutdown. So conflict resolver could hang in endless retry loop. 

4. Verify checksum uses max read time to calculate checksum for cluster. That could hang checksum calculation, because it cannot determine state of pending transaction. 

5. Abort transaction did not check that this tserver is tablet leader. Usually it does not have side effect, because it fails to submit appropriate record to RAFT. But there could be case when we do appropriate checks in non leader mode, and concurrently become leader. So submit to RAFT is successful. That could cause abort of committed transaction.
