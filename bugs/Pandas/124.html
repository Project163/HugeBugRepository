Discussion
- Thanks for pointing this out. I was waffling about an API change regarding label-based slicing with integer-indexed Series and I just changed it back. Which also fixes this bug
- Have you decided on what the API will be for indexing using ix when the index uses integers? I wrote a [Link: gist] that produces the same error.  I used ix[0] to try and get first element (there is no 0 in the index).  This is sort of a slippery slope as you can't really infer what the user wants when an integer is used as the index.
- Never mind, I just saw the ticket in the issue list.  I think that whatever you decide, perhaps being explicit, instead of having "smart" code, would perhaps be the best course of action.  For example, ix is only used for index look up and not for look up based on row number -- use a different function for that.  This would, however, require users to fix their existing code if they upgrade to the latest version.  Just a thought though.
- Yeah, using `ix` on an integer index is going to cause KeyError. Before it would "fall back" on location-based indexing which would lead to very subtle bugs. 

I'm going to add some API functions for integer-only based indexing on the columns and the rows so that should help alleviate the ambiguity. Users shouldn't have been using location-based indexing with integer indexes anyway! It's kind of an esoteric use case imho but I'm sure that it does happen in practice...
