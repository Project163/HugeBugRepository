Title

HttpChunk.isLast() semantic change for incomplete requests with Content-Length

Description
I recently upgraded netty from 3.3.1 to 3.5.1 and noticed a semantic change concerning HttpChunk.isLast() method behaviour.

It appears for large http PUT requests, not chunked on protocol layer (not using chunked encoding but standard Content-Length header).

For such requests if client closes connection before sending all request data (sending less than he declared in Content-Length header) last HttpChunk object passed to application request handler returns true on isLast() method call.

In netty 3.3.0 it returned false so i treated isLast()==true as signal that whole request is completed and all request body bytes have been passed to application logic. 

As this change in netty breaks my code i would like to ask if it was made on purpose or by mistake. 

If on purpose how should application validate that all request data has been send. Should application handler store value of Content-Length header and count sum of all bytes in each chunk until it reaches stored value? I can do that but I thing this is not very convenient because it requires application logic to understand the low level details of http connection used for request.

P.S. I was not sure if issue tracker or stackoverflow would be better for this. Sorry if I picked wrong.
