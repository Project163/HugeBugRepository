Title

Local discovery should use ipv6 multicast, not last address of subnet

Description
The Beacon module lists all addresses available on the machine with net.net.InterfaceAddrs() and tries to send a UDP packet to the last address of the subnet of each of these addresses.
While in ipv4 this happens to be the subnet's broadcast address, it is not true for ipv6, which has no notion of broadcast.

Here's what I see when starting syncthing:

```
$ tcpdump -pns0 -ien0 multicast
17:36:00.396746 IP  .21025 >  .21025: UDP, length 76
17:36:00.886795 IP6 2601:9:5920:f31:5620:96ff:fed2:4caa > ff02::1:ffff:ffff: ICMP6, neighbor solicitation, who has 2601:9:5920:f31:ffff:ffff:ffff:ffff, length 32
17:36:01.897840 IP6 2601:9:5920:f31:5620:96ff:fed2:4caa > ff02::1:ffff:ffff: ICMP6, neighbor solicitation, who has 2601:9:5920:f31:ffff:ffff:ffff:ffff, length 32
17:36:01.897840 IP6 2601:9:5920:f31:5620:96ff:fed2:4caa > ff02::1:ffff:ffff: ICMP6, neighbor solicitation, who has 2601:9:5920:f31:ffff:ffff:ffff:ffff, length 32
```

The first packet is an udp/ipv4 announce (works as expected).
The following 3 packets are icmp6 neighbor solicitations due to syncthing trying to send an udp/ipv6 packet to 2601:9:5900:4b6:ffff:ffff:ffff:ffff, which is a regular global unicast address.

Syncthing should instead use an actual multicast address when announcing over ipv6 (it seems like some older code used ff02::2012:1025, which seems OK).

On the ipv4 side of things, no change is required AFAIK.

I noticed this while trying to set up syncthing between a few ipv6-only hosts and my dual-stacked macbook.
I could still use syncthing by configuring addresses manually, but it'd be nice to have automatic discovery for ipv6-only hosts as their addresses usually change over time.
Discussion
- Agreed. The discovery protocol has gone through a couple of iterations (v4 broadcasts, then v6 multicasts, then v4 multicasts and finally back to v4 broadcast (plus this bug)). The reason for the last switch was that not everything supports v6 yet (...) and v4 multicasts are apparently often filtered/dropped. Anyway, v4 broadcasts + v6 multicasts will be the way to go, yes.
