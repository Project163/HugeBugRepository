Title

EdgeHTML: Cannot execute webview.eval immediately after startup (replaces #190)

- I was thinking this may be because webview uses async js execution for edge. See source [Link: here] and docs [Link: here]
- Regardless of whether or not its due to the async execution, this exercise reveals yet another flaw in the edge implementation.  When you run this on MSHTML, the other elements in the list of 1000 appear almost instantly but when you run it with edge, they appear a couple at a time and take at least .5 seconds to render.  

On another note, if it was a result of the async function call, then it wouldn't just drop executions; instead it would execute the code but maybe give it back in a strange order.  My theory is that there is something that is blocking the execution of the code on startup (A large computation or set of computations etc).  Look here:

```
CoWaitForMultipleHandles(COWAIT_DISPATCH_WINDOW_MESSAGES
                    | COWAIT_DISPATCH_CALLS | COWAIT_INPUTAVAILABLE,
                INFINITE, 1, hs, &i);
```

There are a bunch of async operations occurring in the initializer for the webview object. The code awaits for these to return and then calls `IsScriptNotifyAllowed` which enables sending JS into the webview.  I suspect that in other implementations, you can immediately send the JS in and have it run, where as in this one, you have to wait for those other computations to complete before its allowed. 

I dunno much about the windows apis, but if I had to bet on a block that is causing these troubles I would say its somewhere in these lines:
```
auto op = m_process.CreateWebViewControlAsync(
            reinterpret_cast (m_window), Rect());
        if (op.Status() != AsyncStatus::Completed) {
            handle h(CreateEvent(nullptr, false, false, nullptr));
            op.Completed([Link: h = h.get()] { SetEvent(h); });
... [Log Snipped] ...
                INFINITE, 1, hs, &i);
        }
```
In fact, I am pretty confident that this is where the error occurs.  The op gets setup using the async call and then until it comes back with a completion, the code doesn't await on these different handles.  In other words, the code will cycle through this multiple times and everything inside of that if statement will not execute until it comes back with a completed event.  Look at the name of those await handles: dispatch_window_messages, dispatch_calls, etc.  If they aren't open for incoming calls then we would see this kind of dropping behavior.  There needs to be a place where they block the code for this to come back otherwise none of the other async calls can go through.
