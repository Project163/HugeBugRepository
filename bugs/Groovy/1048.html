Title

Strange behavior for properties that differ only in their capitalization

Description
class  Foo {
  def F = 1
  def f = 2
}

def foo =  new  Foo()
foo.F = 5  // output remains the same  if  we change  this  to: foo.f = 5
 
println foo.@f  // 2
 println foo.@F  // 5
 
println foo.f   // 5
 println foo.F   // 5
 
println foo.getProperty( "f" )  // 5
 println foo.getProperty( "F" )  // 5 
 
  

 The funny thing is that if the lower-case property definition comes first... 
  
  class  Foo {
  def f = 2
  def F = 1
}
 
  
 ... then the output is much more sensible (2 5 2 5 2 5).
Discussion
- Here's the elephant in the room question: when could using variables that differ in case only ever be considered good practice?  If any dev tried that on my team I'de either have them change it or change it for them. 

 Perhaps the correct solution here is to register a compiler error when such collisions occur, in the most narrow case when two properties differ only in the capitalization of the first letter.  This is actually a requirement of the JavaBeans naming conventions leaking out into the compiler, (we cannot fully support the listed sample because of the first class javabeans support in Groovy)  and I think it's better to have the compiler refuse than do strange things.
- Obviously it's never a good practice, but it's the compiler's responsibility to reject what it cannot support.

- I think APP and ClassNode are the wrong places for such a check. Currently ClassCompletionVerifier for example checks for duplicated field. I think there checking for this case as well might be a better idea. 

 Also the number of cases can be reduced if it is checked that the property starts with a capitalized letter
