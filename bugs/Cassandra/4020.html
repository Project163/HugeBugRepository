Discussion
- I originally though this might not be related to static columns but it actually is. Basically, queries that include static and have no clustering conditions will trigger this if partition is indexed (and I mean here the sstable "row" index). And that's because in that specific case we actually end up not calling some necessary initialization. 

 Follows a patch to fix this: 
 
  
 
   3.0 patch   
   utests   
   dtests   
 
  
 

 As of this writing, utests are clear but dtests are still running. 

 The main change of this patch is to move the code from  SSTableIterator.ForwardReader.init()  inside  AbstractSSTableIterator.IndexState.updateBlock()  to make sure it's always called when we need it. The rest is mostly clean up as we don't need the  init()  method and its related field anymore. 

 The patch includes a basic unit test to reproduce the issue, but I'll work on  CASSANDRA-10911  to get finer grained coverage of those classes.
- I'll leave the full review to Branimir, but I'll note that this patch does fix the issue for me.
- Patch looks good overall. 

 It is a bit unclear why the reverse iteration if fine, could you extend the test a little to also exercise the reversed iterator? Also, I think  IndexState.updateBlock  needs an  assert !reversed  or at least a comment to state that it is only used when going forwards.
- I've pushed a simple followup that adds assertion and comment for  udpateBlock  and adds the reverse case in the test (but again, indirect testing through CQL is not ideal and  CASSANDRA-10911  will be a better to get decently exhausting testing of this). For the records, the reverse case was not affected because we're unconditionally seeking to the last block which wasn't done as part of the  init  method that was at fault here.
