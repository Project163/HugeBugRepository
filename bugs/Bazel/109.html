Title

Implement SMT detection on OS X

Description
When building large pieces of software using Bazel on a Mac, we sometimes overload the host CPU. OS X doesn't like this much and starts behaving erratically (very slow UI, lost network packets) depending on the machine.

The `src/main/java/com/google/devtools/build/lib/actions/LocalHostCapacity.java` file implements the logic to determine the number of available CPUs and total RAM in the current machine. Hyperthreads, when present, should be weighted as not full CPUs to prevent overloading the host machine.

For Linux, we do the right thing and we give each hyperthread a weight of 0.6. The information on the number of CPUs vs. logical CPUs comes from `/proc/cpuinfo`.

For Mac... well, `/proc/cpuinfo` does not exist, so we just rely on what the JVM thinks are the number of cores — and that is wrong. At least on my MacBook Pro 13", which has 2 physical cores and 4 hyperthreads, `Runtime.getRuntime().availableProcessors()` returns 4. This causes Bazel to think that the machine has in fact 4 full CPUs and is a reason for the overload.

On the Mac, we should read this information from `sysctl` via the `hw.ncpus` and the `hw.physicalcpu` properties, which are 4 and 2 respectively in my case. Whether accessing `sysctl` from Java is easy or not... I don't know.
Discussion
- I guess we just need to add the necessary `sysctl(3)` queries to `src/main/native/unix_jni_darwin.cc`. Shelling out to `sysctl(8)` would be ugly.
- I hacked my local Bazel build to multiply the number of cores by 0.6 on OS X, just like we do for Linux... and this resulted in a slightly better experience. At the very least, building Bazel itself with the hacked version didn't render my WiFi network connection dead. But the network still behaves incredibly slowly when building; maybe we should go lower than 0.6 on OS X.

Some experimentation will be required to find the right scaling factor on OS X as it might not match Linux's due to OS X's own scheduling. Also, we should keep in mind that most OS X machines are used as desktops, not remote servers, so being too aggressive during a build, to the point where we make the machine unusable, may not cause a great impression of Bazel on our users.
