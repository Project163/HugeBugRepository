Title

Access to outer class private field from closure leads to ClassCastException (@CompileStatic)

Description
Given the following code: 
  
 
 package  org.example

 import  groovy.transform.CompileStatic
 import  org.objectweb.asm.ClassReader
 import  org.objectweb.asm.util.TraceClassVisitor

@CompileStatic
 class  OuterClass {
    private  int  counter

    void call() {
        { ->
             def  closureClassName =  new  Throwable().stackTrace[0].className
            counter++

            printClass(closureClassName)
        }.call()
    }

    static void printClass( String  className) {
         new  ClassReader(className).accept( new  TraceClassVisitor( new  PrintWriter( System .err)), ClassReader.EXPAND_FRAMES)
    }

    static void main( String [] args) {
         try  {
             new  OuterClass().call()
        }  catch  (ClassCastException e) {
            printClass(e.stackTrace[0].className)
             throw  e
        }
    }
}

Discussion
- Groovy 3 sees  counter++  as a private field mutation due to changes in  StaticTypeCheckingVisitor#visitPrefixOrPostifExpression .  If  counter++  is changed to  counter += 1  in the sample code, the ClassCastException is thrown at runtime for Groovy 2.5.9 as well. 

 I will try to understand why access and mutation get different behavior as  counter += 1  and  counter++  should both work as expected.
- If you need to continue testing/using Groovy 3, you can rewrite "counter++" as "counter = counter + 1" until this bug is fixed.
- I can see a few possible approaches to fixing this issue.  "counter++" and "counter += 1" are two examples of an expression where there is both read and write on the same target.   StaticTypeCheckingVisitor#checkOrMarkPrivateAccess  chooses either read or write based on the context. 

 
	 We could also add read metadata when a write is detected.  This would cover compound assignment. 
	 We could visit the target expression "counter" as both an access and a mutation.  This is a bit higher level but has the effect of adding both sets of metadata. 
	 We could check for field mutation metadata in makeGetPrivateFieldWithBridgeMethod if no access metadata is found. 
 

 The decomposed expression "counter = counter + 1" has separate visits for read and write, since there are two expressions in the AST. 

 Update: The third approach will not work because the method saved in metadata is for writing, not reading the field.
