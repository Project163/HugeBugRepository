Hmm. tough to know what's happened 😅 

The current `require-atomic-updates` looks aggressive. If one or more closures used a variable, the rule addresses the variable to be a danger. I'm considering how the rule should address closures.
- I'm leaning towards that we should report the `bar.installDate` consistently because the `bar` is a parameter. If we called the function `foo` twice in parallel, it would cause a race condition. It's the case that the `no-atomic-updates` rule should report.
- I'm confused by the report and the fix (PR) and the comments there, and what has actually been fixed/changed. I just upgraded to eslint 6, is the linked PR already in there?

In this issues based on function parameters I found this inconsistency — no matter what one thinks of the validity of the error report itself, it is inconsistent between the examples:

Code:

```
js
'use strict';

import {someSyncFunction, wait} from 'somewhere';

... [Log Snipped] ...
    planObjPointerCopy.endTime = Date.now();
}
```

The third example is no better than the first one, yet there is no error.

Of course, I think there is no reason for there to be an error even in the first function. Even if the `someSyncFunction` were to mutate the object, what of it? The following code is not reading but writing!

I think the rule is too broad. Of course some object might be mutated, but it is simply _impossible_ to know for eslint who might be holding a pointer to some object, unless it is created locally. So mutation cannot be ruled out ever if an object reference is received from somewhere else. The only way to be "safe" would be to completely disallow any mutation of objects for which a function received pointers from somewhere else, is that the (final function never-mutating coding style) goal?
- In any case, the opinions about what the rule is supposed to catch made here are much(!) more than what the documentation says. The example there is simple and straightforward, what @mysticatea says above is much broader.

So I would like to add that the documentation should be updated too.

Furthermore, for _writes_ such as in my example, where the values are never read, the error message 
```
obj.X might be reassigned based on an outdated value of obj.X`
```
is plain confusing.
