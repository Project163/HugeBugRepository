My understanding of the problem is that `dot( lVector, pointHalfVector)` can yield a value that is larger than `1.0` (`1.0 + very small delta` maybe), which makes the base of the power negative. According to [Link: GLSL spec](section 8.2), result of the `pow()` function with a negative base is undefined.

There are two possible reasons why the problem manifests itself only with some drivers:
1. Some drivers may handle `pow()` with negative base, even though it is not required by the standard.
2. Or the result of `dot( lVector, pointHalfVector)` may be always `<= 1.0` with drivers that yield good looking results.

Is this a correct understanding?

If so, maybe a valid fix would be:

```
 "vec3 schlick = specular + vec3( 1.0 - specular ) * pow( max( 1.0 - dot( lVector, pointHalfVector ), 0.0 ), 5.0 );",
```

Such code ensures that a base of the power is not smaller than `0.0`, so always yields a well defined result (unless `0.0` constant can be handled on some hardware as `0.0 - very small delta`, I'm not sure if this can be the case).
- Actually, `dot(  lVector, pointHalfVector )` should never be greater than `1.0`, and in your example, it should be exactly `1.0` across the face of the cube. So what is happening is due to floating-point errors. On your machine the value varies around `1.0 +/- epsilon`.

Your suggested PR is fine, but it needs to be done everywhere. Here are some instances, but there are others in different files.

```
"vec3 schlick =       specular + vec3( 1.0 - specular ) * pow( 1.0 - dot( lVector, pointHalfVector ), 5.0 );",
"vec3 schlick =       specular + vec3( 1.0 - specular ) * pow( 1.0 - dot( lVector, spotHalfVector ), 5.0 );",
"vec3 schlick =       specular + vec3( 1.0 - specular ) * pow( 1.0 - dot( dirVector, dirHalfVector ), 5.0 );",
"vec3 schlickSky =    specular + vec3( 1.0 - specular ) * pow( 1.0 - dot( lVector, hemiHalfVectorSky ), 5.0 );",
"vec3 schlickGround = specular + vec3( 1.0 - specular ) * pow( 1.0 - dot( lVectorGround, hemiHalfVectorGround ), 5.0 );",
```
