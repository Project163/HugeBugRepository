Title

[grpc-c++] pick_first policy can end up in state where it is not watching channel connectivity

Description
[URL] modified the pick_first policy to promote pending subchannel list to the active subchannel list if all subchannels in the pending list were attempted and unavailable. However when doing so selected_ is not cleared and thus points to now deleted memory (it was owned by the previous active subchannel list).

I am sending a PR to address this but am opening this issue to track it and add more details
Discussion
- Leaving the selected_ pointing to now deleted memory is generally not an issue except for one special case where the allocator reuses that for a new allocation of a PickFirstSubchannelData.  Allocators such as tcmalloc have freelists and caches so this is possible.

Then if PickFirst handles a resolution of address where the first address is such reallocated memory, and because selected_ is non-null and the pending list subchannels are all IDLE since they are new, it connects to the first subchannel of the pending list in the background.
Then when  PickFirst notices the state change of the subchannel from IDLE->CONNECTING. However the pointer equality check incorrectly interprets this notification as part of the current subchannel list not the pending list because of pointer equality with selected_. In that case, since it is not in the READY state it changes the pending list to the active list. However as it does so it cancels the connectivity watcher for selected_ (which was actually in the pending list). In this case we end up with selected_ now being valid (in that it points to allocated memory which is part of the active list), however we have lost the connectivity watcher for it.

Thus if the subchannel becomes connected, goes into an error etc it is unnoticed by the pick first policy and the channel remains in a CONNECTING state.  If using a resolver that requires requests to initiate resolution (ie c ares) then a resolution never occurs and the channel can remain in this state.
