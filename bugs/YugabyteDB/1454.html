Title

[YSQL] Ensure aborted ALTER TABLE's are rolled back even if master restarts

Description
Jira Link: [Link: DB-16494]
### Description

I found at least one problem here but there may be more.

In particular, in CatalogManager::AlterTable, I see code to first change the table's DocDB schema on disk:
```
~/code/yugabyte-db/src/yb/master/catalog_manager.cc:7590:
  RETURN_NOT_OK(UpdateSysCatalogWithNewSchema(
      table, ddl_log_entries, new_namespace_id, new_table_name, epoch, resp));
```

Only after that do we attempt to save the rollback information with the previous schema:
```
~/code/yugabyte-db/src/yb/master/catalog_manager.cc:7620:
        LOG_WITH_FUNC(INFO)  id();
        table_pb.mutable_transaction()->CopyFrom(req->transaction());
        auto *ddl_state = table_pb.add_ysql_ddl_txn_verifier_state();
        SchemaToPB(previous_schema, ddl_state->mutable_previous_schema());
... [Log Snipped] ...
  if (schedule_ysql_txn_verifier) {
    RETURN_NOT_OK(ScheduleYsqlTxnVerification(table, txn, epoch));
```

If we crash between those two points then we have lost the rollback information so the schema will not be rolled back properly.

Moreover, I also don't see any persistence of the rollback state to disk so we  also appear to not rollback if the master restarts after AlterTable completes but before the DDL finishes.

(`l.Commit();` does not persist to disc; it only makes in memory changes visible to other threads.)


Looks like a crash could prevent the SendAlterTableRequestInternal from being called.
- I am hitting this issue while testing a race condition between creating a backup and an ALTER TABLE.
Will fix this one before addressing [URL]
- I was writing a basic test where I crashed the master in the middle of DDL. I wanted to check if we roll back the DDL in DocDB. However, the test was passing (which was unexpected from the persistent perspective).
Digging deeper, it turns out we persist `ysql_ddl_txn_verifier_state` in disk by chance as a by-product of calling `CatalogManager::SendAlterTableRequest` :
```
{
      LOG(INFO)  id();
      TRACE("Locking table");
      auto l = table->LockForWrite();
      auto& tablet_data = *l.mutable_data();
... [Log Snipped] ...
      l.Commit();
    }
```
Here we are only saving the transaction info. However, `ysql_ddl_txn_verifier_state` is already committed in-memory, and that's how it gets persisted by chance.
We still have a small window between committing in-memory and before executing `CatalogManager::SendAlterTableRequest` where a DDL will not be rolled back in case of a master crash. I am working on a fix.
