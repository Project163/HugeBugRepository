Title

[DocDB] YCQL: Slow DELETE execution for a deleted row

Description
Jira Link: [Link: DB-4260]
### Description

If we execute YCQL DELETE statement twice - the Index can be unexpectedly updated.
The wrong entry in the Index tablet has NULL PK.
These extra entries get written with the same null values of hash and range keys regardless of the primary key. So, there could be conflicts on these index keys between many otherwise unrelated deletion operations. In that case, we would wait for `SharedLockManager` locks a lot and only one such write would get replicated at a time.
As result the second DELETE operation can be very slow in case of many parallel DELETE operations.

Reproducer:
```
CREATE TABLE users (id text PRIMARY KEY, name text, age int)
       WITH tablets = 1  AND transactions = {'enabled': 'true'};
CREATE INDEX IF NOT EXISTS name_idx ON users(name) WITH tablets=1;

INSERT INTO users(id, name, age) VALUES('id1', 'name1', 25);
DELETE FROM users WHERE id='id1';
DELETE FROM users WHERE id='id1';
```

Log:
```
=== INSERT INTO users(id, name, age) VALUES('id1', 'name1', 25); ===
DoSetPrimitive: doc_path=DocPath(DocKey( , ["id1"], []), [SystemColumnId(0)]), value={ value_pb:   ->  value_type: kNullLow }
DoSetPrimitive: doc_path=DocPath(DocKey( , ["id1"], []), [ColumnId(11)]), value={ value_pb:   -> string_value: "name1" value_type: kInvalid }
DoSetPrimitive: doc_path=DocPath(DocKey( , ["id1"], []), [ColumnId(12)]), value={ value_pb:   -> int32_value: 25 value_type: kInvalid }
Updating indexes
... [Log Snipped] ...
Updating indexes
DoSetPrimitive: doc_path=DocPath(DocKey( , [null], [null]), []), value={ value_pb:   ->  value_type: kTombstone }
```
The `DocKey( , [null], [null])` is the wrong entry.
After fixing we should not touch the Index during the second DELETE processing.
(Actually the table update is also useless, as the row is already deleted.)
