Title

UnsupportedOperationException: not supported for Type 3 fonts

Description
As reported by Manfred P. on the user mailing list: 
  
 Exception in thread  "main"  java.lang.UnsupportedOperationException: not supported  for  Type 3 fonts
        at org.apache.pdfbox.pdmodel.font.PDType3Font.readEncodingFromFont(PDType3Font.java:68)
        at org.apache.pdfbox.pdmodel.font.PDSimpleFont.readEncoding(PDSimpleFont.java:118)
        at org.apache.pdfbox.pdmodel.font.PDType3Font.<init>(PDType3Font.java:56)
        at org.apache.pdfbox.pdmodel.font.PDFontFactory.createFont(PDFontFactory.java:79)
Discussion
- All three type3 fonts have the "symbolic" flag set, which results in readEncodingFromFont() being called. 
  
                  if  (!encodingDict.containsKey(COSName.BASE_ENCODING) && isFlaggedAsSymbolic)
                {
                    builtIn = readEncodingFromFont();
                }
- Looks like this shares some similarity with the Type 3 problem from   PDFBOX-2299  . I see this code in DictionaryEncoding: 

  
  //FIXME, see PDFBOX-2299, happens with Type3 fonts of the isartor test suite
  //  throw   new  IllegalArgumentException( "Built-in Encoding required  for  symbolic font" ); 
 
  

 Both sections of code make the assumption that a Type 3 font should have an underlying encoding, which isn't true - in fact, the Differences array defines the complete encoding.

[  [URL] ] 

   PDFBOX-2794  : Type 3 font Encoding is defined by Differences array
- Ok, I've removed the expectation that builtIn != null for Type 3.
