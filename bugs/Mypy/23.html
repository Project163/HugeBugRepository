Title

Disallow int and float as base classes

Description
It should not be possible to extend int and float. This code is accepted now, but it should be rejected by the type checker:

```
class n(int): pass
```
Discussion
- I do not agree! This is a feature! (see GCC mailing lists - hard typedef)
- Alec: Can you give a pointer to the GCC mailing list discussion?

The rationale is simple, especially for floats (and fixed-width integers types, see [URL] We want to be able to implement types such as float[] as arrays of unboxed values. If we support subclassing of floats, lists of floats could contain subtypes of floats. This would severely affect the optimization potential of numerical code. 

Also ordinary float variables would be affected, especially on a JVM back end: at the least, we would have to represent floats as (float, reference) pairs. The reference item would be used for float subclasses.

Even tricks such as having multiple representations for float lists (boxed & unboxed) don't seem to work with multi-threading. They would also seriously complicate the implementation.

Subclassing ints or floats is not common in Python code, so this won't affect most programs at all.

However, there could be library classes (most likely not in the std lib) such as UserInt and UserFloat (similar to Python UserString) that would give you some of the benefits of subclassing integers and floats. You would need to use explicit conversions to/from int/float objects, however.
- maybe for certain platforms you need to know the exact sizes of values, for example 32 bit vs 64 bit quantity depending on the platform, there should be a typesafe mechanism for generating "incompatible" int types, such as a type for HWND on windows
- I see the need for an incompatible / hard typedef. However, I'm not sure what is the best way to implement it,
and how important the feature is. 

There are several alternative ways to support them:
- Type alias which is incompatible in either direction. In order to also work in dynamically typed code, 
   this requires a different runtime representation for the alias object (e.g. different type object). The latter
   makes it impractical to use an efficient unboxed int/float representation.
- The above could also be 
   supported via "pure implementation inheritance", i.e. subclassing without subtyping, but only 
   for non-primitives, as primitives don't support subclassing. For non-primitives, the UserInt trick is available.
- Type alias which is incompatible in statically typed code, but this distinction is erased at runtime (i.e.
   runtime representations are identical). This would be easy to implement but the distinction would be
   lost in dynamically typed code.
- Subclassing. This way the typedef would be compatible with the original type but not the other way, which 
   does not really address the need.
