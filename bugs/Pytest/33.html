Title

py.test accepts non-ASCII Python files with no encoding declared

Description
Originally reported by: **David D Lowe (BitBucket: [Link: flimm], GitHub: [Link: flimm])**

---

Take this Python file, `example.py`, which I have saved in my text editor in the UTF-8 encoding:

```
#!python

def test_length():
    string = u"I♥U"
    assert len(string) == 3

if __name__ == "__main__":
    test_length()
```

If I run it using Python 2 on the command-line, I will get this error:

```
$ python example.py
  File "example.py", line 2
SyntaxError: Non-ASCII character '\xe2' in file hi.py on line 2, but no encoding declared; see [URL] for details
```

This is expected. When Python 2 encouters a non-ASCII source file with no encoding declared, it assumes it is in ASCII, and will complain if it finds invalid ASCII.

py.test should behave in a similar manner. Instead, it runs the file and interprets it as Latin9 or some byte-per-character encoding:

```
================================================================================ test session starts ================================================================================
platform linux2 -- Python 2.7.3 -- pytest-2.3.4
collected 1 items 

example.py F
... [Log Snipped] ...
example.py:3: AssertionError
============================================================================= 1 failed in 0.02 seconds ==============================================================================
```

Once an encoding is declared using a magic comment, py.test behaves as expected. But it should complain when a non-ASCII file does not have a magic comment to declare its encoding.

Note that this bug only manifests itself when the source file does not begin with a BOM.

Why wouldn't you want a test file to fail because of an undeclared encoding? I'm quite surprised at this. Is it there a rationale behind this, or is it just a knee-jerk reaction against encoding errors? All you have to do is a add a magic comment.

Python 2 fails to load a non-ASCII file with no declared encoding. As far as Python 2 is concerned, it's as bad as a syntax error.

I definitely think Python 2's behaviour is sensible, and py.test should follow it. I wasted my time assuming an encoding issue was related to the database layer, I didn't realise py.test was interpreting my source file as latin9 without having been told to.
