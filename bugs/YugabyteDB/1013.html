Title

[YSQL] Index aggregate pushdown double-counts

Description
Jira Link: [Link: DB-7464]
### Description

Could get wrong results with index only aggregate pushdown on range partitioned index that is split.  If the query asks for values on partition != first, double the requests can be sent.

```sql
create table split (i int, primary key (i asc)) split at values ((2));
insert into split values (1), (2), (3);
explain select count(*) from split where i = 2;
```

```
                                  QUERY PLAN                                  
------------------------------------------------------------------------------
 Finalize Aggregate  (cost=4.12..4.12 rows=1 width=8)
   ->  Index Scan using split_pkey on split  (cost=0.00..4.11 rows=1 width=0)
         Index Cond: (i = 2)
         Partial Aggregate: true
(4 rows)
```

```sql
select count(*) from split where i = 1; -- 1
select count(*) from split where i = 2; -- 2
select count(*) from split where i = 3; -- 2
```

```sql
create index on split (i asc) split at values ((3));
explain /*+IndexOnlyScan(split split_i_idx)*/ select count(*) from split where i = 3;
```

```
                                     QUERY PLAN                                      
-------------------------------------------------------------------------------------
 Finalize Aggregate  (cost=5.15..5.16 rows=1 width=8)
   ->  Index Only Scan using split_i_idx on split  (cost=0.00..5.12 rows=10 width=0)
         Index Cond: (i = 3)
         Partial Aggregate: true
(4 rows)
```

```sql
/*+IndexOnlyScan(split split_i_idx)*/ select count(*) from split where i = 1; -- 1
/*+IndexOnlyScan(split split_i_idx)*/ select count(*) from split where i = 2; -- 1
/*+IndexOnlyScan(split split_i_idx)*/ select count(*) from split where i = 3; -- 2
```

Comparing the docdb requests (`SET yb_debug_log_docdb_requests TO on`), `count(*)` target for `i = 3` indexonlyscan gives

Discussion
- The first pkey case is actually not on master: that was from in-progress IndexScan aggregate pushdown work.  But the second IndexOnlyScan case still holds.  Both are probably from the same bug.

Disabling PopulateParallelSelectOps fixes the issue, but that should be properly fixed.  Either the parallel ops created should be marked inactive if condition isn't satisfied or upperbound shouldn't be altered badly in `InitRangePartitionKey` `SetKey(max_key, request->mutable_upper_bound());`
