Title

HashedWheelTimer appears to be spinning a core on 3.6.4.Final

Description
On 3.6.4.Final HashedWheelTimer now seems to be spinning a core (On Windows 7 64-bit, anyway) after a channel is first used even after channel is in finished with and has been closed. 

It didn't do this in 3.6.3.Final so appears to be some sort of regression. We have no weird setup or configuration - just using a standard NioClientSocketChannelFactory with CachedThreadPools for the two executors.

Debugging the class indicates on 3.6.4.Final sleepTimeMs is always 0 so it seems to just keep spinning around the loop from

```
while (workerState.get() == WORKER_STATE_STARTED) {
```

The source of the error seems to me to be a bad port of code in [URL]

Akka:

```
final long currentTime = System.nanoTime();
long sleepTimeMs = (deadline - currentTime + 999999) / 1000000;
```

Netty 3.6.4.Final

```
final long currentTime = System.currentTimeMillis();
long sleepTimeMs = (deadline - currentTime + 999999) / 1000000;
```

It doesn't appear to make sense to me to add 999999 and divide by 1000000 unless you're dealing with nanos so my guess is this is why the sleepTime is always 0 causing it to spin a core.
