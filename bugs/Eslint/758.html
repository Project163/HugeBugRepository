Title

no-loop-func shouldn't warn when a function is used inside a forEach or such functions

Description
**What version are you using?**
2.0.0-beta.1

**What did you do?**
I tested this code using the no-loop-func rule:

``` javascript
  for (const score in scores) {
    const letters = scores[score];
    letters.split('').forEach(letter => {
      result[letter] = score;
    });
  }
```

Because of the function in forEach, the no-loop-func gives a warning here. Yet this is not an issue because forEach's parameter actually runs right away, it's not an asynchronous callback.

This should be relaxed at least for all Array iteration methods (also for Map and Set, but this is also a `forEach` method; maybe we can accept that all forEach/map/etc methods will behave the same).
And also the Promise constructor.
I'd be happy enough with a rule configuration.
Discussion
- The rule is warning not because of the `forEach`, but because of the outer `for...in` loop. You are creating a new function for each iteration of the outer loop. I think the rule is behaving correctly. It will actually not flag functions inside `forEach`.
- Thank you for this issue.

I know that immediate called functions are no problem even if those exist in a loop. But it's too hard to detect whether it's immediate called or not in static analysis. So I guess `no-loop-func` is warning all functions in a loop.

I often write `// eslint-disable-line no-loop-func`, so I think it's inconvenient, though....

- @michaelficarra :-1: The utility to maintenance cost ratio for your proposal seems low. Not everyone would think to try that style of invoking forEach and it would have to be called out in docs, and it doesn't really gain all that much. On the other hand, the code to do that isn't super trivial either. I don't much like it, sorry.
- Creating exceptions for array methods is far too specific a change for this rule. 

It looks like we already have exceptions for using `let` or `const` loops, so the question is, why is this warning at all right now?
