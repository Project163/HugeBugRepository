Title

SQL: integer parameter validation in string functions

Description
The following query uses `Integer.MAX_VALUE` as parameter input: `SELECT SUBSTRING('a', 2147483647, 1), INSERT('ab', 2147483647, 1, 'x')`, returning the correct result:
```
SUBSTRING('a', 2147483647, 1)|INSERT('ab', 2147483647, 1, 'x')
-----------------------------+--------------------------------
                             |ab                              
```

Going over the Integer limit by 1:
* `SELECT SUBSTRING('a', 2147483648, 1)` returns an expected error: 
  ```
        "type" : "string_index_out_of_bounds_exception",
        "reason" : "begin 2147483647, end -2147483648, length 1"
  ```
* `SELECT INSERT('ab', 2147483648, 1, 'x')` is surprisingly accepted and returns a correct result:
  ```
  INSERT('ab', 2147483648, 1, 'x')
  --------------------------------
  ab                              
  ```
. But going over the limit with more than 1: `SELECT SUBSTRING('a', 2147483649, 1), INSERT('ab', 2147483649, 1, 'x')` behaves as an integer overflow:
```
SUBSTRING('a', 2147483649, 1)|INSERT('ab', 2147483649, 1, 'x')
-----------------------------+--------------------------------
a                            |xb                              
```

The expectation would be either for the functions to accept a long parameter _or_ throw an arithmetic overflow error.
Discussion
- Pinging @elastic/es-ql (:Query Languages/SQL)
- There's one more discrepancy that'd be worth addressing with the string functions: some will only accept an integer parameter (like [Link: `SUBSTRING`]), while others will accept floating points too (like [Link: `INSERT`]).
- @bpintea Yes, the parameter type was different from `insert`, `locate` and `substring`. But in *FunctionProcessor, the integer or rational parameters of these functions are all cast into integer, hence they can treat as integer to check integer overflow.
