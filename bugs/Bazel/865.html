Title

IncompatibleMergeException in branch coverage for C++ headers

Description
_This only occurs when C++ branch coverage is enabled._
_Add `-b` to the gcov command line in collect_cc_coverage.sh and rebuild bazel._

An assumption made in commits 3481d5ec and 51ec2228 is that the number of branches recorded in coverage reports for a given line are constant across the reports to be merged from a single bazel invocation. This is not a valid assumption, at least for header files in C++. Functions defined in header files may be compiled several times in different contexts, resulting in slightly different structures that can fail the naive check made in the coverage merge tool.

Suppose the following function exists in a header file `lib.h`:
```
template  
T foo(T x, T y) {
    T z = y > 0 ? x + y : x - y; // line N
    return z;
}
```
If `foo` is instantiated with `int` or similar, there is a single branch at line N with two paths.
If `foo` is instantiated with a more complicated struct with the required operators, then more branches may be generated by the compiler at the same line.

Since two object files may have instantiated this function differently, it is entirely possible for a coverage run to fail to merge the reports and fail to produce a final coverage.dat file.

A demonstration is provided here:
[URL]

```
cd lcov_issues
bazel coverage --combined_report=lcov --instrumentation_filter="lib" //branch_merge:foo_test //branch_merge:bar_test //branch_merge:baz_test
```

- Honestly, I don't think there is a good solution; inconsistent data cannot be meaningfully merged

Something that might be fixable is the inconsistency in the output when faced with mismatched inputs. We keep the "first" set of branches when there's a mismatch; if the order changes between runs, then we can end up with a different result.
- I agree, inconsistency data cannot be merged.

Having said that, I understand the solution for this is hard, but choosing the first set does not sound like a final solution to me. I'm not exepert in code coverage in C++ to say how this is resolved in other environments, I don't think this is a Bazel problem but a more generic one.
If you grab the example in the ticket and you apply it to a real life scenario, you can imagine that `baz` is the object file that instantiated the header for testing it with all possible instantiations you might have in the project.
In that case, what the user might want is to grab the set of branches from `baz` but taking the first you are just relying on lack.

One way to mitigate the problem is to use some tool like gcovr to exclude branches generated by the compiler.
[URL]
In the end, I would expect that most of the users when they want to test different branches they care mainly about the branches that are visible in the C++ code.

Maybe a flag where you can choose between taking the first set or throw an exception would be the best? Do you see a way how a user could in practice influence how the first set of branches is choosen?
