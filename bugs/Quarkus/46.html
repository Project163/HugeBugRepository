Title

Fix support for maps in Config

Description
As discussed at the standup meeting, let's create an issue to track these problems.

See [URL] for a complete description of the issues and how to reproduce them.
Discussion
- The current #945 PR has a test that shows this issue:
org.jboss.shamrock.extest.ConfiguredBeanTest#validateRuntimeConfigMap
- The problem is related to this block of code in ConfigurationSetup#generateParserBody:

```
java
            // branches for each next-string
            final Iterable  names = keyMap.childNames();
            for (String name : names) {
                if (name.equals(ConfigPatternMap.WILD_CARD)) {
... [Log Snipped] ...
                    // TODO: string switch
                    // if (keyIter.nextSegmentEquals(name)) {
```
  Map types are hitting this skip statement and not having their children parsing generated.

For example, when the map object associated with the ConfiguredBeanTest#validateRuntimeConfigMap hits that skip, this is the parent ConfigPatternMap:

```
keyMap = {ConfigPatternMap@2616} 
 matched = null
 children = {TreeMap@2628}  size = 13
  0 = {TreeMap$Entry@2631} "double-primitive" -> 
  1 = {TreeMap$Entry@2632} "long-list" -> 
... [Log Snipped] ...
  11 = {TreeMap$Entry@2642} "ovo-with-default" -> 
  12 = {TreeMap$Entry@2643} "string-list" ->
```
The generated ConfigHelper.class ends up with an empty parseKey_rt_all_values_nested_config_map parse method for the map.

I tried just adding this little hack to see what would happen:
```
java
            // branches for each next-string
            final Iterable  names = keyMap.childNames();
            for (String name : names) {
                if (name.equals(ConfigPatternMap.WILD_CARD)) {
... [Log Snipped] ...
                }
            }
```

and this does generate parsers for the map children, but the runtime map is still not populated, so something is not matching up in the generated code.
- I have gotten to the point of every other value for a given set of map properties is being set. Hopefully I should be able to get this resolved soon now.
- My current hypothesis is that it's related to the order in which the config values appear in the iteration.  But that's only a circumstantial observation.
