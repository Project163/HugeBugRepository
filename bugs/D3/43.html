Title

Clarify behavior for selection.data in re. to duplicate keys.

Description
In the function d3_selectionPrototype_data, in the bind function

In data with a key argument, exitNodes are added at two stages:

1) culling duplicates
for (i = -1; ++i < n; ) {
          keyValue = key.call(node = group[i], node.**data**, i);
          if (nodeByKeyValue.has(keyValue)) {
            exitNodes[j++] = node;
          } else {
            nodeByKeyValue.set(keyValue, node);
          }
          keyValues.push(keyValue);
        }

2) Cleaning up remaining values in nodeByKeyValue
        for (i = -1; ++i < n; ) {
          if (nodeByKeyValue.has(keyValues[i])) {
            exitNodes[i] = group[i];
          }
        }

Note that exitNodes in the second pass is indexed by i, but in the first pass by j.

J starts at groupData.length, in other words the first pass exits are shuffled into slots after the maximum number of nodes that can validly be in the list.

I starts at zero and extends all the way up to group.length, in other words the number of nodes we started with.

This leave the possibility of a node with an unwanted key being in the range groupData.length to group.length.  In this case a node stored in pass 2 will overwrite a node stored in pass 1 in the exitNodes list, which means the pass 1 node escapes the exit list and is neither removed nor updated - and remains in the DOM.

Fix: in pass 2, use j++ to index the exitNodes array (not tested, i will do that next).

- This problem is entirely specific to duplicate keys which are not well supported. We could probably do a better job of defining the behavior for duplicate keys.

Consider the following example:

``` js
var div = d3.select("body").selectAll("div")
    .data(["aa", "ab", "ac", "ba", "bb", "bc"])
  .enter().append("div")
    .text(function(d) { return d; });

div = div
    .data(["aa", "ab", "ba", "bb"], function(d) { return d.substring(0, 1); });
```

Because the key function only takes the first character, there are duplicates in both the data and the selection. Looking at the second join, here are the elements and their corresponding keys (in parentheses):

```
data      - [ aa (a), ab (a), ba (b), bb (b)]
selection - [ aa (a), ab (a), ac (a), ba (b), bb (b), bc (b)]
```

The current behavior in 3.0.2 is:

```
enter     - [   null, ab (a),   null, bb (b)]
update    - [ aa (a),   null, ba (b),   null]
exit      - [   null,​   null,   null,   null, ab (a), ac (a), bb (b), bc (b)]
```

The intent is that the _enter_ and _update_ selections match the data, while the _exit_ selection matches the original selection. But because of the duplicates, **ab** and **bb** appear in both the enter and exit selection. And likewise, the exit selection doesn’t match the structure of the original selection.

Probably the more correct output is:

```
enter     - [   null,   null,   null,   null]
update    - [ aa (a),   null, ba (b),   null]
exit      - [   null,​ ab (a), ac (a),   null, bb (b), bc (b)]
```

The result of this change will be that when there is a duplicate key in your data, only the first datum is considered and subsequent matching data are ignored.
