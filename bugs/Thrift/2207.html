Title

byte count of FrameBuffer(AbstractNonblockingServer.readBufferBytesAllocated) is not subtracted

Description
AbstractNonblockingServer.readbufferbytesallocated is used to indicate “How many bytes are currently allocated to read buffers.”, however, we find that readbufferbytesallocated does not decrease as expected in rare cases. we added the following logs in FrameBuffer.read: 
  
 
 //  if   this  frame will push us over the memory limit, then  return .
  // with luck, more memory will free up the next time around.
 LOGGER.info( "print readBufferBytesAllocated: {}, {}" ,  readBufferBytesAllocated.get(), frameSize);
 if  (readBufferBytesAllocated.get() + frameSize > MAX_READ_BUFFER_BYTES) {
   return   true ;
}  
  
 and we found:

Discussion
- libthrift allocate buffer(size of frame size + 4) after read frame size and increase value of readBufferBytesAllocated.  it will keep until connection closed or response ready.  

 as you said: What may be the reason why the readbufferbytesallocated  has not decreased?  

 1. it is reading frame data 
2. response not ready
- joecqupt  However, from the perspective of phenomenon, readbufferbytesallocated is always greater than a certain value, such as 141028722, It's like some buffers are not released after allocate. 

 Is it possible that the responseReady() method was not called because the request processing failed?
- This problem should be split to 2 part: 
 
	 The variable(readBufferBytesAllocated) seem not to be correctly computed; 
	 select() will infinite loop when thrift server received a large requeset but frameSize < MAX_READ_BUFFER_BYTES and readBufferBytesAllocated + frameSize > MAX_READ_BUFFER_BYTES; 
 

 Aim at fix second problem, could add new parameter such as MAX_SINGLE_FRAME_BYTES to replace MAX_READ_BUFFER_BYTES in  if(frameSize < MAX_READ_BUFFER_BYTES). 

 This will solve the problem of CPU is full all the time, although readBufferBytesAllocated still possible compute wrong.
