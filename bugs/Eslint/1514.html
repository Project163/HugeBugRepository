Title

Bug: camelcase v8.0.0 regression on properties: "never"

Description
### Environment

Node version: 16.7.0
npm version: 7.20.3
Local ESLint version: 8.8.0
Global ESLint version: none
Operating System: Ubuntu

### What parser are you using?

Default (Espree)

### What did you do?

 
 Configuration 

```
{
    "rules": {
        "camelcase": [
            "error",
            { "properties": "never", "ignoreDestructuring": true }
        ]
    }
}
```
 

```js
var { some_property } = obj;
doSomething({ some_property });
```

### What did you expect to happen?

No lint error as described in the last statement of [URL]

### What actually happened?

Identifier 'some_property' is not in camel case. (line 2)

```js
/*eslint camelcase: ["error", {"properties": "never", ignoreDestructuring: true}]*/

```

- Given that this rule reports all references to non-camelcased variables, this behavior is actually logical.

In `var { some_property } = obj`, shorthand `some_property` is a property name used to read property value (which is always allowed by this rule) and a variable name in destructuring pattern (which is allowed by `"ignoreDestructuring": true`).

In `doSomething({ some_property })`, shorthand `some_property` is a property name used to create property (which is allowed by `"properties": "never"`) and a variable name. It is reported as a variable name (a reference to the variable). because this isn't a destructuring pattern, so `"ignoreDestructuring": true` doesn't apply here.


It seems that ESLint v7.32.0 had a bug - `"properties": "never"` should allow property names, but this option was mistakenly allowing all child nodes of Property nodes:

```
js
// ESLint v7.32.0

/* eslint camelcase: ["error", { ignoreDestructuring: true, properties: "never" }] */

... [Log Snipped] ...
    foo_bar,  // not reported. It's a bug because this is both a reference to variable and a property name.
}
```

This bug has been fixed in ESLint v8:

```
js
// ESLint v8.8.0

/* eslint camelcase: ["error", { ignoreDestructuring: true, properties: "never" }] */

... [Log Snipped] ...
    foo_bar,  // reported as a reference to variable.
}
```

That said, the example from the original post was one of the two primary use cases for `ignoreDestructuring` option, so I agree that we should change the rule to allow this example for backward compatibility, although the current behavior makes more sense.
