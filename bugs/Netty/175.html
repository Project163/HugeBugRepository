Title

Javassist unavailable when Netty is loaded using custom classloader

Description
I'm not really sure if this is an important issue, but I will report it anyway.

I'm writing a program which should perform partial class isolation using classloaders. That is, there is a classloader which loads shared classes, there is another classloader which inherits from the first and loads main program classes, and this main program also creates additional classloaders for plugins which inherit from the first loader. This way plugin classpaths do not intersect with main program classpath except for several classes from shared classpath. Netty is used from the main program and is loaded by the second classloader. All works well, but I noticed the following messages in the logs:

```
16:58:22.782 [main] DEBUG i.n.util.internal.PlatformDependent - Javassist: unavailable
16:58:22.782 [main] INFO  i.n.util.internal.PlatformDependent - You don't have Javassist in your class path or you don't have enough permission to load dynamically generated classes.  Please check the configuration for better performance.
```

However, javassist jar is present in the classpath of the second classloader (together with Netty). A small inspection has shown that this happens because in Netty internals javassist `ClassPool` is created in the following way:

```
    private static final ClassPool classPool = new ClassPool(true);
```

And this means that `classPool` will only use system classpath (something like `new ClassClassPath(java.lang.Object.class)`). It seems that because of this `JavassistTypeParameterMatcherGenerator.generate()` method fails with an exception when trying to load `NoOpTypeParameterMatcher` class (which is loaded by the second classloader), and Netty reports that javassist is not available.

I understand that my case is highly special and that I probably don't need javassist at all and should ignore the message in logs (or add javassist to the root classloader, which I don't want to do), but I thought that it still worth reporting.

This happens on Netty 4.0.0.CR
