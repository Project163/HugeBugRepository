Title

Memory leak

Description
I wanted to isolate this generic problem further before opening this up but I've been at it for about two days now and I just wanted to see if anyone else has seen this or has any ideas. With the latest version of eslint there seems to be a significant memory leak, enough to cause Node to run out of memory:

```
FATAL ERROR: CALL_AND_RETRY_2 Allocation failed - process out of memory
```

This happens when running eslint on Windows on a directory of 4,463 items totaling 118.6mb. The process memory approached 1.5gb shortly before this error. When run on the same directory on OS X the memory also seems to increase but not enough to be fatal.

I'm trying to profile it and narrow down the naughty code, but Node's memory profiling tools seem to be a little lacking. I'm fumbling around with memwatch heap diffs at the moment, but they're not granular enough to do much narrowing down.
Discussion
- When you say "the latest version", are you saying that previous versions didn't have this problem? Or just that you're using the latest version?

I haven't run into this, but then again, I've never run ESLint on that many files. 

For comparison, can you run JSHint on the same set of files and see what happens?
- Sorry, haven't done any more of that narrowing down because any time I put into this issue is still just trying to figure out how to do basic memory profiling. node-inspector is hopeless, it doesn't work with the latest devtools updates so it only allows step-through debugging. node-memwatch works but doesn't have enough information to make any useful conclusions. node-heapdump generates a useful heap dump that can be viewed in devtools but on OS X it refuses to generate more than one dump no matter how or how many times it's called. Which is frustrating because I might be able to find the issue with just two. On Windows I am still trying to get it to even compile. All of these tools are very outdated. I'm still baffled how scant and unmaintained the open-source Node.js profiling tools are.

Will continue to look into this when I get time.

- Okay. So it looks like what was going on is that we were keeping the AST of each file in memory due to attaching a node to each message. We don't really need that node, so it's probably safe to remove it. We'll need to change how eslint-tester works since it relies on the node, but that's okay.
- The `node` is really only used by ESLintTester to verify the correct node was passed into `report()`. However, we really only check the node type, so I can just attach a new `nodeType` property to the result and use that instead.
