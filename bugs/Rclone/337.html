Title

when copying an `Fs` implementation, its `Features()` should not retain the original receiver

Description
This is a spin-off from #2176 because we realized this is an unrelated issue.

For instance, this bug hits when in the `newFs` of Google Drive whenever a path to a file is given. The code realizes this and creates a *new* `Fs` with an adjusted root folder. When doing so, it copies the already filled `Features` from the *original* `Fs`. 

Consider this pseudo code to get an idea of the bug:
```
go
f := &Fs{name:  "old"}
f.features = (&fs.Features{}).Fill(f)

newF := *f
... [Log Snipped] ...

// prints "old new old"
```

There's many options to avoid that:
1. ensure in a test that `&someF == getReceiver(someF.Features().someOptionalFeature)`. It depends on implementation details, though. See e.g. [URL] (license unknown)
2. resolve the methods in `Features()` whenever needed instead of once through `Fill()` (?)
3. attempt to replace the `Features()` approach by making all optional interfaces mandatory and return `errNotImplemented` when a backend doesn't support them

I have not yet looked into the feasibility of either. Maybe there's even a better solution I'm overlooking.

In the short term, I will provide a patch that fixes the specific bug for the Drive backend.
Discussion
- For the record: When I wrote this, I intended it more as an illustration of why this is impossible to do reliably, not to actually use it :) I don't mind if you end up using it, but I would advise against it - even in tests ;)

The main risk here is that future changes (especially around heuristics for inlining and devirtualization) may make this method change behavior based on the context it's called in. This might cause non-deterministic, hard to trace and to debug test failures. Imagine a randomly failing test, where the location from the stacktrace is not related to the actual bug location, which is not reproducible in a debugger (which compiles with different optimizations) and whose root cause you can't write a test for, because *that* test might pass, while the original one still fails (because the optimization decisions are based on context). It may seem unlikely to break this way, but the pain it would cause seems immense to me :)

If it helps, [Link: strings.Builder] uses a trick to detect copies-by-value by comparing a self-pointer; would that be useful to maybe prevent copying of `fs.Features`? Though it seems they get, in general, used as a pointer, so that probably doesn't help…

Personally, I believe I would recommend making the optional features their own interface and then do type-assertions at the use-site. There don't seem to be a significant syntactical difference between

    if ps, ok := f.(PutStreamer); ok {
        ps.PutStream(foobar)
    }
