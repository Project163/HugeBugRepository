Title

Race in Netty's DefaultPromise

Description
As reported on the grpc issue tracker [URL]

There seems to be a race between `DefaultPromise.trySuccess()` and `DefaultPromise.addListener(...)`. It looks like the offending line is [Link: `if (listeners == null)`].

Now, `listeners` is written in a `synchronized` block and read outside of it. Reasoning about about visiblity guarantees and ordering seems complicated. I think it's probably more complex than that comment one line above. We should probably make `listeners` volatile.

cc: @carl-mastrangelo @ejona86 @nmittler @Scottmitch @normanmaurer
Discussion
- I don't think writes of a field from within a synchronized block guarantee ordering and visiblity for reads of the field outside of a synchronized block. My reasoning is that the compiler might place the `listeners` field in a register and thus concurrent updates to `listeners` might not be populated between threads.

Worst case that could happen is Thread 0 executes `DefaultPromise.addListener(...)` and Thread 1 executes `DefaultPromise.trySuccess()`. If `addListener` completes before `trySuccess()`, then `trySuccess` might not have gotten the update of `listeners`, and thus not execute the listener.

I think if that's true, there should probably be a new release of Netty, as this seems really serious.
- @nitsanw would you mind checking as well mister concurrent wizard!
- Here is one explanation of why this is not correct: [URL]
- Using the "write in syncronized block, read outside of it" requires the field to be volatile to be correct at all and even then it's an error prone optimization usually used for simple value fields and not references to potentially complex objects.
I'm not sure the DefaultFutureListeners is thread safe, but if it isn't that would be further trouble.
