Discussion
- This appears to have nothing to do with MV. I am now also seeing in in readrepair_test on trunk 

  [URL]
- I fixed a problem in  LogAwareFileLister.classifyFiles , which would have affected transactions spread across multiple disks. However, this is not what is causing these tests to fail unless we are using multiple disks and I haven't noticed. 

 I've also fixed another problem with the existing logic, in that we should only check that OLD sstable files still exist to determine if there is a race, we don't need to look at NEW sstable files.  Since we cannot tell in advance how many NEW sstables files will be created and when, this might explain the problems we are seeing although I would have expected them on 3.0 as well. 

 Finally, if we fail to classify files due to an inconsistent disk state, I've added a log message showing the list of files detected and the content of the transaction.
