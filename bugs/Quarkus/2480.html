Title

Qute template with null default parameter fails with unclear NPE

Description
### Describe the bug

As a developer, it may seem like a good idea to define a Qute template parameter with an explicit null default. This would ensure that the parameter is always available, even when templates are sometimes rendered without this parameter provided.

Example:

```qute
{@String name=null}

Hello {name} from Qute!
```

### Expected behavior

This should work or should provide a clear error message outlining what template may have an error, ideally including the parameter name that failed.

### Actual behavior

The code fails with a generic stacktrace:

Discussion
- Hm, I'm not so sure that `{@String name=null}` param declaration makes a lot of sense. The primary purpose of parameter declarations is to enable build-time validations. In this particular case, Qute can validate all output expressions like `{name.length}`. The default value is used if a template instance does not receive the data with the given key _or if it's set to `null`_. It's translated to something like: `{#let name?='somedefaultvalue'}` (in this particular case `{#let name?=null}`). So for example, if you say `template.data("val", null).render()` then the default value `null` is used instead... `null` will be replaced with `null` 🤔. And the same applies to type-safe templates.

The only use case where it could "help" is when you don't use type-safe templates AND forget to set the template data with `template.data("val", null)` AND strict rendering is enabled (it is by default). Because in that case, a missing property would result in a `TemplateException` but `null` is handled as a `falsy` value that outputs an empty string.

Of course, a `NullPointerException` thrown from validation is wrong and needs to replaced with an actionable error message. And we should also mention this use case in the docs.
- @mkouba thanks for your detailed response. The scenario that I ran into was indeed a code base without type-safe templates. While refactoring some of the (reused) templates; I added a few parameters and figured I'd specify default values (empty list or null) to allow the application to build again before all usages were updated. Both 'solutions' don't work well and aren't listed in the docs as something that should work.

I agree that from a type checking perspective supporting this doesn't make a lot of sense so catching this with an actionable error sounds reasonable to me.
- It was actually easier to skip the validation, because otherwise it just works 🤷.
