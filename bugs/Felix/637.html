Discussion
- I can't reproduce this on OSX (1.5 or 1.6), but can reliably on Linux (1.6.0_13)
- While there does seem to be a race condition here, there is fallback code that should handle the situation.  In URLHandlers.getFrameworkFromContext(), if it can't determine the framework, it should go through the callstack to find a class loaded by the bundle class loader.  Unfortunately, it matches based on the class name, which it mistakenly thinks should be "org.apache.felix.framework.searchpolicy.ModuleImpl.ModuleClassLoader".  After much debugging, I realized the actual class name that will be returned from the classloader is "org.apache.felix.framework.searchpolicy.ModuleImpl$ModuleClassLoader".  Since changing this string, I haven't seen the error occur again.
