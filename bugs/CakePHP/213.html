Title

Fatal error with Result Set serialization

Description
I'm not sure if this is an issue but it has caused me a bit of a headache. Since the Validation portion of the framework is packaged separately I figured it couldn't hurt to let you guys know about it.

So in my Cake 3 application I have Debug Kit installed. Now that the Validation section is packaged separately I have included it in another project I am working on. In my application I have a model that stores a class name and in the entity I use it like this:

```
php
    class SomeEntity extends Entity {

        protected $_Instance;

... [Log Snipped] ...

    }
```

On that instance class I have several validation recipes. Everything works fine until I add conditional validation. When I add a closure to the `on` key I get the following error: `Serialization of 'Closure' is not allowed`. It is triggered [Link: here] on Debug Kit and ultimately traces back to [Link: Cake\ORM\ResultSet::serialize()]. I understand that I am not using the validation suite in the traditional way which probably makes this issue a grey area as far as what you guys need to support but since it is packaged separately now I figured it was something you guys would like to be aware of.

I'm sure there is an easy solution to this but I couldn't immediately find it. I played around with the idea of using [Link: PHP magic methods] to control the information serialized or maybe just unsetting the instance variable before serialization. I was worried I would mess up some expected data. If this is the solution it might be helpful to have the `__sleep()` and `__wakeup()` methods on the base `Entity` class so they can be overloaded. Kind of an inherited event callback, I guess.

Anyway, just wanted to let you guys know. Thanks for all of your hard work. I really enjoy Cake 3!
Discussion
- Is the issue that resultset has your entity, and your entity has a validator, which has a closure?

Preventing serialization issues is a tough part of debugkit as there aren't many good options to serilaize() and there are landmine objects everywhere in php. Between resources, pdo and closures serialization of arbitrary data is pretty challenging.
- Correct.

I know there isn't going to be a great way to handle this which is why I was hesitant to report it at all. Especially since I was using the validation classes in an unconventional way. Would it be reasonable to incorporate the event system into object serialization? Maybe a `beforeSerialize` and `afterSerialize` event? I imagine this would end up with some kind of `EventSerializeTrait` to make a standard way to do this. Even if the `__sleep()` and `__wakeup()` methods were there for me to overload I would be happy with:

``` php
    public function __sleep () {

        unset($this->_Instance);
        return parent::__sleep();

    }
```

In my specific case I'm not really worried about preserving the instance but I don't really have control to unset it before serialization.
