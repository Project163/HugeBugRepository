Title

Text Detection Fails on Mostly Non-ASCII UTF-8 Files

Description
If a file contains relatively few ASCII characters and more 8 bit UTF-8 characters the TextDetector and TextStatistics classes fail to detect it as text.
Discussion
- Do you have a sample file that shows this problem? And is it more than just a few bytes long? (The detection algorithms need a decent stretch of text to work properly)
- I do have a test file and it's more than a few bytes long. 

 The problem arrises when there's no UTF-8 BOM and the parsers doesn't have access to the file name as a hint. 

 I'm looking into a solution that will call some UTF-8 validation if the TextDetector doesn't see enough ASCII.  It appears the universalchardet library is also looking for a BOM on initial investigation. 

 I'll look into this further.
- ... [Middle Discussions Snipped for Brevity] ...
- I see where you're going, but it's a really tricky path. I tried doing something like that earlier on, but I found no easy way to keep down the number of false positives. 

 The ICU4J classes are written with the assumption that the data you're working on is always text and they just figure out which character encoding is most likely. They fail to take into account the possibility of the document being in some unknown binary format. 

 That's why we currently run the full ICU4J encoding detection (using the  o.a.t.parser.txt.Icu4jEncodingDetector  and  o.a.t.detect.AutoDetectReader  classes, see   TIKA-322   and   TIKA-471  ) only once we already know by other means that we're dealing with textual data.
