Title

Partition#remoteReplicasMap can be empty in certain race conditions

Description
In Partition#updateAssignmentAndIsr, we would previously update the `partition#remoteReplicasMap` by adding the new replicas to the map and then removing the old ones ( [source] ( [URL]

 During a recent refactoring, we changed it to first clear the map and then add all the replicas to it ( [source] ( [URL]

 While this is done in a write lock (`inWriteLock(leaderIsrUpdateLock)`), not all callers that access the map structure use a lock. Some examples: 
 
	 Partition#updateFollowerFetchState 
	 DelayedDeleteRecords#tryComplete 
	 Partition#getReplicaOrException - called in `checkEnoughReplicasReachOffset` without a lock, which itself is called by DelayedProduce. I think this can fail a  `ReplicaManager#appendRecords` call. 
 

 While we want to polish the code to ensure these sort of race conditions become harder (or impossible) to introduce, it sounds safest to revert to the previous behavior given the timelines regarding the 2.6 release. Jira  [URL] tracks further modifications to the code.
