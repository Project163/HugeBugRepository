Title

for big attachment, a temporary file is left on disk and keep opend, if the application just close the DataSource's inputStream and doesn't consume it;

Description
when the client receiving multiple larget attachments from server. here "large" means : attachment size is large enough to be saved as temporary file on disk; 

 for the last attachment, if the user application only close the input stream got from DataSource and doesn't consume the input stream at all, a temporary file will be left on the disk.
Discussion
- this is the test case's pom project.
- This is caused by still can read MimeBodyPartInputStream after closing it, so that after closing the unread stream , it cache to temp file but have no chance to delete temp file even the process exit.

by the way, I suggest you'd better to add the checking code of Delegate input stream's close to avoid recursively close one delegate-input-stream twice;  

 Tne delegate-input-stream will be recursived closed twice; to ensure this, you can tracking it use a java-debugger: the calling stack is : 

 DelegateInputStream.close- >deserailizer.markClosed()  >attachmentDeserailizer.hasNext()  >attachment.cache() ->DelegateInputStream.close()  [here recursive occurs]  

 Anyway, if we don't check it, thinks will also work right.(because delegate-input-stream is only used by the last attachment). but it may cause potential problem in future;
