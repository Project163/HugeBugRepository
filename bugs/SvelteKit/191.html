Title

API endpoint, called from the server, with cache-header cannot be cleared

Description
### Describe the bug

This is similar to, but different than [URL] 

I have an api endpoint that looks like this 

```
js
export async function GET({ url, setHeaders, request }) {
	console.log('ENDPOINT', x++);

	const search = url.searchParams.get('search') || '';
... [Log Snipped] ...
	return json(todos);
}
```

This endpoint is called from a SHARED loader. So the first time I view a page, the fetch is called from SvelteKit's internals, on the server. With the cache-control header, as above, these results are cached for 60 seconds. Even a call to invalidate to the api endpoint url does not clear that cached entry. Even adding a depends call in the shared loader, and called invalidate on that does not clear the cached entry. Even manually passing a different value of the header on each call (to test) does not clear the cached entry.

Is this by design? Note that I'm not talking about browser caching. I can already modify the header I'm Vary'ing on (todos-cache) on the client, and successfully clear the cache, which works.

The only workaround I've found is to just not add the cache-control header at all, depending on whether the loader is running client-side, or server-side (which I can surmise by snooping around the headers).

Again, mainly trying to surmise if this is by design. If it is, by all means close this. If not, I'd be happy to whip up a minimal repro.

Discussion
- Likely a bug where the inlined response is reused, not taking into account the Vary header. To keep the implementation simply I'd say we shouldn't keep responses with a vary header cached. This might result in some false negatives but very few people will actually use that header.
