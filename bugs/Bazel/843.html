Title

Race condition in VanillaJavaBuilder

Description
Under sufficiently high load when using VanillaJavaBuilder, we intermittently see this exception crashing the worker:

---8<---8<--- Start of log, file at …/bazel-workers/worker-1-Javac.log ---8<---8<---
java.nio.file.NoSuchFileException: bazel-out/k8-fastbuild/bin/build-plugin-showcase/testing-build-plugin-generated.srcjar
\tat sun.nio.fs.UnixException.translateToIOException(UnixException.java:86)
\tat sun.nio.fs.UnixException.rethrowAsIOException(UnixException.java:102)
\tat sun.nio.fs.UnixException.rethrowAsIOException(UnixException.java:107)
\tat sun.nio.fs.UnixPath.toRealPath(UnixPath.java:837)
\tat com.sun.nio.zipfs.ZipFileSystemProvider.removeFileSystem(ZipFileSystemProvider.java:322)
\tat com.sun.nio.zipfs.ZipFileSystem.close(ZipFileSystem.java:305)
\tat com.google.devtools.build.buildjar.VanillaJavaBuilder.close(VanillaJavaBuilder.java:348)
\tat com.google.devtools.build.buildjar.VanillaJavaBuilder.runPersistentWorker(VanillaJavaBuilder.java:114)
\tat com.google.devtools.build.buildjar.VanillaJavaBuilder.main(VanillaJavaBuilder.java:89)
---8<---8<--- End of log ---8<---8<---

Some debugging later has tracked this down to a race condition between VanillaJavaBuilder's cleanup functions and bazel's; the semantics are that once a worker has sent back the response to the bazel server, it can't assume any input files still exist, because bazel will start deleting them.
