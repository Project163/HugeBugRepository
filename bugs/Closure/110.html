Title

javascript file order causes namespace creation problem in compiled code

Description
What steps will reproduce the problem? 

1. I have attached a tar.gz file with three javascript files (file1.js, file2.js, and file3.js) and two output files (out123.js and out213.js).

2. I compiled the outputs using the following commands:

java -jar ../compiler.jar --js=file1.js --js=file2.js --js=file3.js --formatting=PRETTY_PRINT --js_output_file=out123.js

java -jar ../compiler.jar --js=file2.js --js=file1.js --js=file3.js --formatting=PRETTY_PRINT --js_output_file=out213.js


 What is the expected output? What do you see instead? 

One output will work when run in a browser (output123.js) and one will not (output213.js).  The problem in output213.js is it cannot declare xFuncs because file1.Obj is not declared yet, error on line 2.

It appears that when file2 is added to the compiled file it realizes that file1.Obj will be declared in the file that goog.provides that namespace, and thus skips that declaration.  Then when file1 is added to the compiled file the declaration occurs.


 What version of the product are you using? On what operating system? 

Just to make sure that it was easy to repeat, I downloaded the most recent version (Version: 20100917 (revision 440)) of the jscompiler from code.google.com/p/closure-compiler/downloads/list.  I am running it on a variant of Ubuntu linux.


 Please provide any additional information below. 

This issue arose in a project I am working on where:
a.  file2 is automatically generated
b.  file3 represents the overarching project that will be compiled into a single javascript file
c.  The order in which the files are given to the compiler is automatically generated by two other programs.
Discussion
- I think we've said in the past we don't plan on fixing this, because the behavior is not well-defined. 

I honestly think it should be a compiler error if one file tried to goog.provide a property on a function that's defined in another file.

what do you think?
- It's also worth pointing out that this is also broken in uncompiled code, but breaks in a much more subtle way. (the property is just overwritten by the 3rd file).
- ... [Middle Discussions Snipped for Brevity] ...
- There are plenty of examples where it's not safe for us to move the function. For example, suppose you have:

goog.provide('Foo.bar');
Foo.bar = true;
alert(Foo);
var Foo = function() {};

Putting the function at the top would cause different behavior.

One of the things I like about Java is that it forces you to be very explicit about where the entry points of your code are, and tries to re-order top-level statements to make sense. But JS does not do this. And as a matter of principle, we try not to "fix" broken uncompiled code. (It's really a PITA when your compiled code works, but when you try to debug the uncompiled code it breaks).
