Title

Arithmetic overflow when calculating sampleDecodingTime resulting in negative value

Description
When using dynamic DASH stream, the decodeTime is a very large value. I have seen e.g.  .

In com.google.android.exoplayer.extractor.mp4.FragmentedMp4Extractor.parseTrun() line 498 that large value is used in this calculation (cumulativeTime is derived from decodeTime):

```
 sampleDecodingTimeTable[i] = (cumulativeTime * 1000) / timescale;
```

This calculation can overflow and result in a negative sampleDecodingTime which prevents the player from starting playback further on.

This can be fixed by rearranging the calculation like this:

```
  sampleDecodingTimeTable[i] = (cumulativeTime / timescale) * 1000L;
```
Discussion
- To clarify, is   the sampleDecodingTimeTable value or the cumulativeTime value? What's the value of timescale in this case?

You can't change the calculation in that way without losing precision in some cases, although we do have a util method that attempts to "do the right thing" [Link: here].
- is the sampleDecodingTimeTable, but it doesn't really matter since cumulativeTime gets a value in the same range. Timescale is 1000000.
- ... [Middle Discussions Snipped for Brevity] ...
- It is my stream (or rather a stream produced by another department in my company). Perhaps it contains odd timestamps. Unfortunately, we cannot easily provide access to it due to DRM and licensing issues.

My initial proposal:

```
sampleDecodingTimeTable[i] = (cumulativeTime / timescale) * 1000L;
```

does not work properly, probably due to losing precision. But then I tried:

```
sampleDecodingTimeTable[i] = Util.scaleLargeTimestamp(cumulativeTime, 1000, timescale);
```

and that solved my issue.
- Ignore my comment above about the values not being sensible. They are. The reason you're hitting this issue where other people aren't is simply because the timescale you're using is so large. You really don't need the level of precision that such a large timescale allows, and I would advise you to follow up with the team generating this content and suggest that they might like to change it. It will likely improve compatibility across different players by avoiding this kind of issue. For reference, YouTube's DASH streams use 90000 for video and the frequency for audio (e.g. 44100).

That said, we will make the change proposed above. Thanks!
