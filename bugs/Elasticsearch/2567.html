Title

Lock contention on EnrichCoordinatorProxyAction$Coordinator

Description
I observed the following stack trace in a 7.8.1 cluster:

```
app//org.elasticsearch.action.support.TransportAction$RequestFilterChain.proceed(TransportAction.java:177)
app//org.elasticsearch.action.support.TransportAction.execute(TransportAction.java:155)
app//org.elasticsearch.action.support.TransportAction.execute(TransportAction.java:83)
app//org.elasticsearch.client.node.NodeClient.executeLocally(NodeClient.java:83)
app//org.elasticsearch.client.node.NodeClient.doExecute(NodeClient.java:72)
... [Log Snipped] ...
java.base@14.0.1/java.util.concurrent.ThreadPoolExecutor$Worker.run(ThreadPoolExecutor.java:630)
java.base@14.0.1/java.lang.Thread.run(Thread.java:832)
```

Note that we are within `EnrichCoordinatorProxyAction$Coordinator.coordinateLookups` (note [1]) which is `synchronized`, and we're executing an `EnrichShardMultiSearchAction` (note [2]). Although this action does fork onto a `search` thread at this point, it looks to be doing a quite substantial amount of work under this mutex, and there are an enormous number of other threads in the hot threads which are blocked waiting to enter this method. Looking over multiple diagnostics bundles, over multiple nodes, yields this:

```
$ for i in $(find . -name 'nodes_hot_threads.txt' | sort); do cat $i | grep -e 'coordinateLookups('; done | sort | uniq -c
6817        org.elasticsearch.xpack.enrich.action.EnrichCoordinatorProxyAction$Coordinator.coordinateLookups(EnrichCoordinatorProxyAction.java:144)
   1        org.elasticsearch.xpack.enrich.action.EnrichCoordinatorProxyAction$Coordinator.coordinateLookups(EnrichCoordinatorProxyAction.java:147)
  25        org.elasticsearch.xpack.enrich.action.EnrichCoordinatorProxyAction$Coordinator.coordinateLookups(EnrichCoordinatorProxyAction.java:153)
```
