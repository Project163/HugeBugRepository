Title

Search - better caching logic for queries on wildcard field

Description
A user reported slow performance with the new wildcard field which, oddly, was thousands of times faster when they ran the same query through a profiler.

The reason for the huge difference was revealed in a stack trace of the unprofiled query:

```
94.2% (4.7s out of 5s) cpu usage by thread 'elasticsearch[instance-0000000032][search][T#13]'
     6/10 snapshots sharing following 51 elements

       app//org.apache.lucene.codecs.lucene80.Lucene80DocValuesProducer$BinaryDecoder.decode(Lucene80DocValuesProducer.java:856)
       app//org.apache.lucene.codecs.lucene80.Lucene80DocValuesProducer$19.binaryValue(Lucene80DocValuesProducer.java:904)

       app//org.apache.lucene.search.Boolean2ScorerSupplier.getInternal(Boolean2ScorerSupplier.java:113)
       app//org.apache.lucene.search.Boolean2ScorerSupplier.get(Boolean2ScorerSupplier.java:90)
```

There is query caching going on which is something that doesn't happen with profiled queries, hence the speed difference.

For some unknown reason the query caching logic in `LRUQueryCache.cacheIntoBitSet`  had singled out the very expensive `AutomatonQueryOnBinaryDv` normally used to verify a (hopefully) small set of docs that match an approximation query for wildcard/regex queries and decided to ask it to iterate across ALL docs in the index. This should not have happened - the LRUQueryCache should have [Link: favoured] caching the BooleanQuery that the wildcard field uses to contain both the approximation query and the expensive AutomatonQueryOnBinaryDv verifying query. I can't explain why this would happen other than a hashing collision or bug somewhere.

Discussion
- Pinging @elastic/es-search (Team:Search)
- This sounds to me like a general problem with queries that operate on doc values, I'm afraid we'll see a similar problem with caching when we implement [URL] and start creating queries on doc values that are not wrapped within an `IndexOrDocValuesQuery`.

There is another level of protection that we have via [Link: `skipCacheFactor`], a parameter that prevents queries from being cached if their cost exceeds the cost of the top-level query times `skipCacheFactor`. The current value of this parameter is 250, maybe means that we allow caching clauses that are up to 250x more costly than the top-level query. Maybe this default is too high?

We'd have at least `SourceConfirmedTextQuery` and this wildcard query that would fall into this category, so it looks worth exploring if there is code that can be reused indeed. We just need to make sure to call `query.createWeight(searcher)` like `IndexOrDocValuesQuery` rather than `searcher.createWeight(query)` so that the wrapped queries are not considered for caching on their own.
