Title

Excessive heap usage of post-snapshot-delete index metadata cleanup

Description
Today `RepositoryData#indexMetaDataToRemoveAfterRemovingSnapshots` constructs a `HashMap >` identifying every index metadata blob to be removed after deleting some collection of snapshots. This data structure can in theory be arbitrarily large, and in practice has been seen to consume many GiBs of heap in a cluster in which snapshotting was disrupted for an extended period of time in a way that prevented snapshots from being deleted and then the disruption was removed.

I believe we don't need to construct this data structure up-front at all, because these days `BlobContainer#deleteBlobsIgnoringIfNotExists` accepts an iterator over blob names from which it constructs the delete-blob requests progressively. It's not essential to deduplicate the blob names since deleting a blob multiple times is acceptable, but it would also seem reasonable to construct each per-index `HashSet ` as needed. Note that this would mean retaining `RepositoryData#indexMetaDataGenerations` for longer, past the end of the snapshot delete, so we should make sure there's enough backpressure to stop a buildup of excessively many of these things.

Alternatively, we could generalize `ShardBlobsToDelete` slightly to keep track of both shard-data and index-metadata blobs to be deleted, enforcing a strict bound on the memory footprint of all this data, and preferring to leak some blobs rather than sending the node OOM.
Discussion
- Pinging @elastic/es-distributed-coordination (Team:Distributed Coordination)
- On reflection I prefer this idea. Today we work out which index metadata blobs to delete based on the difference between the two successive `RepositoryData` instances but if a blob delete fails for some reason then it won't be picked up by a future cleanup. We should instead compare the index metadata in the new `RepositoryData` instance against a listing of the index metadata blobs which really exist in the repository, since that will include any leaked blobs.
