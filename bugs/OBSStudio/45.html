Title

srt & rist auto-reconnect partly broken

Description
### Operating System Info

Windows 10

### Other OS

_No response_

### OBS Studio Version

27.2.4

### OBS Studio Version (Other)

_No response_

### OBS Studio Log URL

[URL]

### OBS Studio Crash Log URL

_No response_

### Expected Behavior

Auto-reconnect should work fine.

### Current Behavior

Auto-reconnect works partially with srt (or rist & hls).
If the network is temporarily down, reconnection eventually works.
But at each reconnection attempt, the reconnect is displayed as successful even if it is not.
Then it's displayed as disconnected and the auto-reconnect sets in.
The problem with that is that at each time, the reconnect counter is reset. So it'll keep trying to reconnect indefinitely. There's no exponential waiting in between reconnects either.
I investigated closely the reason for the bug:
- the current auto-reconnect feature was written for rtmp and assumes two different threads: (1) the connect thread, (2) the send thread. 
- the auto-reconnect sends a successful message when obs_output_begin_data_capture is called. For rtmp, this is done in the connect thread.
- currently, for srt/rist/hls, the obs_output_begin_data_capture is called BEFORE there's been an actual reconnect attempt done in obs-ffmpeg-mux.exe. This is the reason why the auto-reconnect is bugged with ffmpeg-mux.
This is not something which can be fixed imo, apart from modifying in a major way the auto-reconnect feature (which is in libobs, obs-output.c) so that it waits for a signal. The said signal would have to be from ffmpeg-mux to obs.
The only other way to fix this bug is to rewrite the srt/rist output and not use ffmpeg-mux.

### Steps to Reproduce

1. Start a stream to any srt or rist URL w/ auto-reconnect enabled in Settings/Advanced.
2. Unplug the ethernet cord.
3. Auto-reconnect sets in. It displays a succesful reconnect although the cord is still unplugged.
