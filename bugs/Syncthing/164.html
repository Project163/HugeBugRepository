Title

Staggered file versioning - files missing in .stversions

Description
I just noticed that some deleted files never end up in the `.stversions` folder
Settings (both devices): Staggered File Versioning, 30 days

**Scenario 1** - file "today.jpg" (11/20/2014 16:01) 
1. device A: copy file "today.jpg" to synced folder and rescan
2. device B: file is downloaded
3. wait some time
4. device A: rename file to "today2.jpg" and rescan
5. device B: file is renamed and old version moved to `.stversions` with suffix "~20141120-1601"
6. wait some time
7. device A: delete file and do rescan 
8. device B: file is deleted / moved to `.stversions` with suffix "~20141120-1601"

_Result_: 2 files (today.jpg and today2.jpg, both with suffixes) in `.stversions` 

**Scenario 2** - file "old.jpg" (04/04/2014 14:32)
1. device A: copy file "old.jpg" to synced folder and do rescan
2. device B: file is downloaded
3. wait some time
4. device A: rename file to "old2.jpg" and do rescan
5. device B: file is renamed
6. wait some time
7. device A: delete file and do rescan
8. device B: file is deleted

_Result_: no files in `.stversions` 

This seems to be a bug because both scenarios were tested at ~ 8pm today (11/20/2014) and it seems that Syncthing is appending the wrong "timestamp". Instead of date/time when file was renamed/deleted it uses the original creation timestamp "20141120-1601" and "20140416-1432". The problem shows in scenario 2: the timestamp is outside of the 30 days which are set as maximum age and the file is deleted immediately. Expected in both scenarios would be an appended timestamp with date/time of actual file change/rename/deletion, e.g. "20141120-2005" so if you change/delete old.jpg and today.jpg both today, they will be kept in `.stversions` until 12/18/2014
Discussion
- To find files in `.stversions` it's easier to have the modification date as timestamp in my opinion.
But "file is harder to find because of sync time as timestamp" is probably better than "file is gone because it had a old modification time"... 
So it's not really a bug but maybe a bad behavior in some cases.
- it should be:
file changed = modification date as timestamp
file renamed/deleted = actual date as timestamp
- ... [Middle Discussions Snipped for Brevity] ...
- I just looked at the code and i think the behaviour @uok suggested is not that hard to implement. We could add a boolean to the archive function that tells us if it's a delete or not. 
`Archive(filePath string, delete bool)` instead of just `Archive(filePath string)` 
(or we make a separate function that is called on deletes)

If a file with a pretty old modification time gets modified we still instantly delete the version which could also be bad. 

Another Idea which keeps modification time as timestamp in most cases but does not instantly delete stuff would be something like this:

modification time > 0.5_maximumAge => use 0.5_maximumAge to show that it's a really old file but we still keep the file for a while
modification time   use modification time

I don't really know what the best way to solve it will be, I think I like the "0.5*maximumAge" most because it will never instantly delete versions (but it could cause some confusions with the date) and is still easy to implement.

As soon as it's decided what to do I could work on that and make a pull request if you like :)
- To keep it simple: as @calmh suggested, always use the timestamp when the action of versioning (after change/move/delete) happens.
