Title

[YCQL] Race between restoring a snapshot and writing consensus updates during hearbeat processing can fail queries

Description
Jira Link: [Link: DB-3636]
### Description

Scenario is restoring few times in the row and at some point we throw an exception on YCQL query that validates number of restored rows. During validation following exception may occurs.

Discussion
- @qvad , Is this is still a problem for tablet-splitting?
- Tablet splitting is a red herring. The issue is:

1. Tserver sends a heartbeat to master
2. RPC handler for TSHeartbeat begins running and grabs in-memory state for tablets to update.
3. Client sends a RestoreSnapshotSchedule request to master
4. Master updates tablet and table sys catalog entries for the restored DB
5. RPC handler thread writes tablet state to sys catalog, clobbering update in (4)

  fixed this by putting a barrier in based on the number of PITRs performed. RPC handler threads that want to write tables or tablets to the sys catalog must grab the current count of PITRs when they begin, and then pass that count to the sys catalog mutation APIs. If that count doesn't match the current count, the mutation is rejected. The PITR flow updates the count before doing any sys catalog writes.
