Title

Remove mnemonic dependency from sandbox multiplex workers

Description
### Description of the bug:


When Bazel creates an environment for a multiplex worker, it uses the mnemonic to create the name of the environment (e.g. `Mnem-multiplex-worker-workdir`. This creates a race condition if

 - two targets are built in parallel,
 - they have intersecting dependencies, and
 - they use the same mnemonic.

Bazel will try to overwrite the environment of the first target that starts building. The error message will be: `IOException while preparing the execution environment of a worker`

### Which category does this issue belong to?

Core

### What's the simplest, easiest way to reproduce this bug? Please provide a minimal example if possible.


1. Create a multiplex worker rule with sandboxing, say `some_library`. (The worker doesn't have to do anything, but it should sleep long enough so the race happens)
2. Create three files, `a.txt`, `b.txt`, and `c.txt`.
3. Write the following in a BUILD file:

```
filegroup(
  name = "ab",
  data = [":a", ":b"],
)

... [Log Snipped] ...
  ]
)
```
4. Try to build `:ab`

Discussion
- I'm curious what the latest with this issue is. I'm pretty sure we're encountering it and haven't found a good workaround yet, so we'd like to help fix it.

*Background*
We implemented multiplex sandboxing support a few months ago on a Scala rule set for dynamic execution and path mapping benefits. That said, we haven't been able to enable multiplex sandboxing because of flaky build failures. The issues we've encountered include:
* `FileNotFoundException` in JVM workers from the rule set when writing to files in the sandbox
* `IOException while preparing the execution environment of a worker` from Bazel
*  Files 'missing' from the sandbox, presumably because something couldn't write them or something clobbered them.

The issues were inconsistent and hard to reproduce, but common enough to be problematic.

The issues would all go away when we disabled multiplex sandboxing/stopped using dynamic execution for mnemonics that supported multiplex sandboxing.

*Mitigation*
I seem to have mitigated the issue by giving every action its own mnemonic, but that's not a viable solution. I more or less set mnemonic to `mnemonic = " {}".format(_sanitize_label_for_mnemonic(ctx.label))` for all the mnemonics in the rule set that support multiplex sandboxing. This seems to have consistently stopped the aformentioned issues.

Based on the symptoms and the mitigation, I think we're encountering this issue.
