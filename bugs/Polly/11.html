- ## The good part

This happens only if you run the test against non-release code. For release code the strategy works as expected (you will see explanation bellow):

```

var pipeline = new ResiliencePipelineBuilder ()
.AddHedging(new HedgingStrategyOptions ()
{
	ShouldHandle = new PredicateBuilder ().HandleResult("foo"),
```

## The bad part

### The happy path

Let's amend the `OnHedging` delegate to the following:
```cs
_options.OnHedging = _ => default;
```
1. After the `OnHedging` has been successfully executed the `TaskExecution` finishes the [Link: `HandleOnHedgingAsync`] method.  
2. Its caller the [Link: `InitializeAsync`] continues the execution
3. Its caller the `HedgingExecutionContext`'s [Link: `LoadExecutionAsync`] continues the execution
4. And the execution continues its journey inside the `HedgingResilienceStrategy`'s [Link: `ExecuteCoreAsync`]

Finally we reach this code where we mark the `TaskExecution` as **Accepted**.
[URL]

### The unhappy path

Let's run the original `OnHedging` delegate which throws an `InvalidOperationException`

1.  There is no explicit exception handling inside the `TaskExecution`'s `HandleOnHedgingAsync` and `InitializeAsync` methods so, the exception bubbles up to the`HedgingExecutionContext`
2. There is no explicit exception handling inside the `HedgingExecutionContext`'s `LoadExecutionAsync` method so, the exception bubbles up to the `HedgingResilienceStrategy`
3. There is no explicit exception handling inside the `ExecuteCoreAsync` **BUT** there is a `try-finally` block inside the `ExecuteCore` which is its caller

[URL]

 4. Inside the `finally` block we dispose the `HedgingExecutionContext`. Its [Link: `DisposeAsync`] calls the [Link: `UpdateOriginalContext`]
 5. And since we did not have any `AcceptOutcome` calls on this execution path, that's why the test fails with a `Microsoft.VisualStudio.TestPlatform.TestHost.DebugAssertException`.

[URL]

If we comment out the `Debug.Assert` then the test passes as expected.
