Title

Extremly slow http initialization

Description
I am having trouble with the http backend taking excessively long on startup. It takes roughly a full minute to initialize. However, in a broswer the URL loads nearly instantly.

The behavior is the same in Windows (1.43.1) [Link: windows.log] and Linux (1.49.2) [Link: rpi.log]

I have also confirmed the behavior with mount and lsd. In the case of mount I also experienced the issue when there was a change to the page (roughly every 10 minutes). The change triggered a roughly 1 minute pause before it would show me the files again.
Discussion
- If you add -vv -dump bodies to the command you can see what it is doing.

The answer is HEAD requests on all the contents of the directory. This is to discover the date and time of the files.

I think there are a lot of files in that directory hence the delay.

I could put in a --http-no-head flag to stop this. This would mean instant listings but rclone would no longer knows there size of any of the files. That would mean you would have troubles using the files with mount 

I could also parallelize the head requests to speed things up. That might be a better solution.
- Thank you. I'm not sure why -vv refuses to show me the HEAD requests. I tried that and --log-level DEBUG on both of my installs and only saw what is in the attached logs.

A few additional thoughts. Most directory lists I've seen show the file size as well. Could that be used as a temp file size and the HEAD request only verifies as needed with a lazy load? I guess even a size of "unknown" with lazy load to find out should work as well. Assuming that is a possibility in the existing code base.

Perhaps more simply, in my particular case I'm happy to use an include or exclude filter to knock down the file count to a very small number of files. Potentially as low as one. However, the HEAD requests happen before the filters kick in so the delay is the same. Can the HEAD requests occur after the filtering? Hmm, looking closer at the filtering docs I see that size is a possible filter. So maybe not. Can this be done if there is not size filter in use? My case doesn't have one.

Otherwise yes parallelization would definitely help.

Thanks again for this amazing program by the way.
