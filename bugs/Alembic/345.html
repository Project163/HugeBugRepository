Title

Problem in MSSQL altering column when change type and server_default in one statement

Description
**Describe the bug**

Hi
I'm Trying to change type and server default value of a column, but it complains about it have a dependent object with an error, the idea is to have the same `mssql_drop_*` parameters in alter table also

**Expected behavior**
To be able to drop the constraints asociated with the column

**To Reproduce**
```python
    op.alter_column('access', 'created_at',
               existing_type=sa.DATETIME(),
               type_=sqlalchemy_utc.sqltypes.UtcDateTime(timezone=True),
               server_default=sqlalchemy_utc.utcnow(),  # type: ignore
               existing_nullable=False,
               existing_server_default=sa.text('(getutcdate())'))
```

**Error**

```
    cursor.execute(statement, parameters)
sqlalchemy.exc.ProgrammingError: (pyodbc.ProgrammingError) ('42000', "[42000] [Microsoft][ODBC Driver 18 for SQL Server][SQL Server]The object 'DF__access__created___2B0A656D' is dependent on column 'created_at'. (5074) (SQLExecDirectW)")
[SQL: ALTER TABLE access ALTER COLUMN created_at DATETIMEOFFSET NOT NULL]
(Background on this error at: [URL]
```

**Versions.**
 - OS:  Linux KDE Neon / Ubuntu Noble 2024.4 
 - Python: Python 3.12.3 (main, Aug 14 2025, 17:47:21) [GCC 13.3.0] on linux
 - Alembic: alembic 1.17.0
 - SQLAlchemy:  2.0.37
 - Database:  Microsoft SQL Server 2025 preview
 - DBAPI: mssql (UnixODBC)

Discussion
- hi -

the DROP for default constraints is automatic with alter_column() and SQL Server , because you pass in the existing_default so we know there's a default that has to be dropped.  so there's no boolean, it runs that drop default query automatically.

also, the mssql_drop_default is a boolean that runs basically the same query that alter_column() does automatically.    so it's just the one query.

It looks like the issue is if you are changing the type and the default at the same time, the existing defaults need to be dropped before we touch either of those (and in any case there's nothing wrong with dropping the default earlier in the process).

i was able to create a reproducer that can fix this, stay tuned
- **Mike Bayer** has proposed a fix for this issue in the **main** branch:

**run drop default constraint ahead of type** [URL]
