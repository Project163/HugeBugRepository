Title

move handle_error listener from engine to dialect; implement for pre_ping handler

Description
as noted in #5646 there's a [Link: recipe] to augment the is_disconnect() handler.  however we don't consult it in dialect pre-ping.  looks like we can add classlevel "_handle_dbapi_exception_noconnection" pretty easily to at least allow the hook to be consulted.
Discussion
- welp, we don't have even the engine at that stage, so that approach can't be done w/o some rearchitecture which would make this 1.4.

another way might be to keep retrying the reconnect handler three times in any case even if it raises.  but that still means there's be an exception raise in the logs and still nullifies the "i want to augment is_disconnect" recipe.   the main use case here is "how do i add new is_disconnect codes" ?

which....in fact looks a lot like a dialect event rather than handle_error, honestly.  which means, change the docs, change the recipe, etc.
- steps are:

1. add dbapi_connection and dialect to ExceptionContext.   "engine" and "connection" can now be None in some cases
2. move handle_error to be part of DialectEvents.  nothing else needs to change here and existing code that links the event from an Engine will be the same.  Connection will still call upon the handler as always.
3. move the production of the ExceptionContext and actually running the hook from engine/base into defaultdialect
3. in DefaultDialect.do_ping(), catch exceptions and call the same hook we created in step 3, where it will call upon ExceptionContext without an Engine or Connection
4. update docs to indicate Engine / Connection may be None for the do_ping handler, maybe others, look more to dbapi_connection and Dialect for forwards compat.

- this was not implemented for mysql , postgresql and possibly others.  whatever test support is in place is not testing those backends
