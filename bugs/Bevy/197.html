Title

Memory leak when changing font sizes

Description
## Bevy Release v0.8.0

commit 0149c41
Rust Version: cargo 1.62.1 (a748cf5a3 2022-06-08)

## What you did

Just recently completed in a game jam which was my first time using both Bevy and Rust (after which I want to say I really enjoyed both and am looking forward to being a part of the community). That being said please forgive any ignorance in my usage of either. One effect I attempted to implement during the game jam was to have the title text grow and shrink over time. My first approach was to modify the font size over time. 

## What went wrong

Modifying the font size over time performs the behavior I desired just fine, however I noticed if I left my game title screen running for a little(like 5 minutes or so) my computer would start chugging and when looking at resource usage, the game was eating over 30GB of memory. 

I worked around this by modding the scale of the transform on the text entity rather than modifying the text size. Thinking on it this is probably a more "correct" solution to the problem, but seeing my simple game take up 30+ GB of memory just sitting at the title screen of my game was concerning. This also means that dynamically modifying fonts can pose a memory leak issue that might be harder to catch in a more complicated use case. I would expect the font system to cleanup after itself ( or if not better communicate to the user that each change to the font is allocating more memory, since that is not a base expectation)

- Just wanted to update my theory some more after some testing and browsing through code. After some testing I looks like the issue only occurs when you are changing the font size to non-repeating floating point numbers. Exploring around the Bevy code I am seeing that the generated Fonts are stored in a Hashmap indexed by fontsize:

[URL]

Haven't had an opportunity to test and confirm this theory, but looking at the code I am guessing we are continually adding to this hash map since the font sizes are are different calculated floats. This results in this hashmap blowing up as new fonts are generated to match up with the new font sizes.

That being said here are some thoughts on how to handle this. Probably needs some design input since each of these solutions has pluses and minuses. Additionally there may be a solution I am not thinking of. 

## Proposed Solution 1 
Limit the size of the hashmap. 

### Pros:
- simple to implement
- will definitely stop this memory leak
- fail fast, fail early
- provides a way to warn the user that they are doing something potentially dangerous and in an unintended way. 

### Cons:
- what is an appropriate limit? 
- doesn't really address the underlying issue
- Still allows the user to waste a ton of memory caching FontAtlas'es that they wont use very often if at all

The takeaways from that discussion were:

1. Probably need a garbage collector for fonts (e.g. unload after a few frames)
2. For animation use-cases, this isn't solved, because we're still allocating frequently.
3. *An alternative approach might be to provide different APIs for different uses. If you're animating the font size, then choose some type where this is garbage collected, or rendered immediately perhaps and without any caching involved. If you want to keep the font atlas around and re-use it, then choose some type where you would load it with a character set and a font size, then future accesses would pull from that existing atlas - basically as it is now, but more explicit than implicit.*

So that would be my suggestion: a "retained mode" FontAtlas (which is explicit over a font, a size, and perhaps a set of characters) and an "immediate mode" (which caches nothing).
