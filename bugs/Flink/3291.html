Title

Performance regression in TwoInputStreamOperator

Description
[URL] introduced a performance regression visible for example  here  as a drop on August 30th (note that the later performance improvement is caused by serialisation improvement, which is unrelated to the previous slow down).  

 Probable suspect is the following  .isDone()  check executed inside  StreamTwoInputProcessor  once per record: 

  
 
 // to avoid starvation,  if  the input selection is ALL and availableInputsMask is not ALL,
  // always  try  to check and set the availability of another input
  // TODO: because  this  can be a costly operation (checking  volatile  inside CompletableFuture`
  //   this  might be optimized to only check once per processed NetworkBuffer
  if  (inputSelectionHandler.shouldSetAvailableForAnotherInput()) {
	checkAndSetAvailable(1 - readingInputIndex);
}
Discussion
- After the performance improvement of  [URL] which is unrelated to this performance regression, I'm struggling to reproduce this issue. Before rebasing on the master I could reproduce it and I could confirm that fixing the "TODO" mentioned in the description was speeding up the code. However after rebasing on the latest master, I can not reproduce it anymore. I would be afraid that trying to reproduce it, would require substantial effort, that might be even not very visible to the final user. 

 Additionally when serialisation optimisation ( [URL] is accounted for, it looks like even with this performance regression, we have better throughput compared to 1.9. 

 Because of that, I would suggest to close the ticket, unless someone is willing to spend more time investigating it.
