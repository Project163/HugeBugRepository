Possible Collections.sort assertion failure in STCS.filterColdSSTables

 The comparator ant SizeTieredCompactionStrategy line 94 breaks the assertions in the new JDK7 default sort algorithm, because (I think just) the hotness value (based on meter) may be modified concurrently by another thread 

 This bug appears to have been introduced in   CASSANDRA-6109
Discussion
- Note the java option java.util.Arrays.useLegacyMergeSort could be used as a workaround, but it is unclear to me if that would produce desirable results
- The simplest fix is probably just to precompute an IdentityMap to any of the mutable data, and use it from within the comparator (since the comparator happens to be non static) 

 Alternatively use a List of a new wrapper type and sort that instead.

 I answered this on the dev ML, but I'll repeat it here for others who are interested.  The default max_cold_reads_ratio is 0.0, so  filterColdSSTables()  shouldn't filter any SSTables.  When writing this patch, I realized that even with that set to 0.0, SSTables that have no read activity at all would still be filtered out.  However, after this patch, that's no longer true, and a setting of 0.0 will prevent any filtering at all. 

  I’m guessing there is no actual downside (other than ERROR level messages in the logs which cause alerts), since it just fails a subset of compactions?  

 That's correct, this shouldn't cause any other problems, only delay some compactions.
