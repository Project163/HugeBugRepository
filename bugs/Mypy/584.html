Title

(Some) Class variables have `Any` type in methods declared above them

Description
The following test fails, producing no error messages:
```
[case testClassVariableOrdering]
def foo(x: str) -> None: pass

class Something:
    def run(self) -> None:
... [Log Snipped] ...
    IDS = [87]
[builtins fixtures/list.pyi]
```
If `IDS` is declared *above* `run`, the test passes. If `IDS` is made just an `int` instead of an int list and the call is adjusted similarly, the test passes. A `reveal_type(self.IDS)` in `run` reports `Any`.


To make matters worse, this is a mismatch with fine-grained reprocessing of `run`. The following test that fine-grained behavior matches the regular mode also fails:
```
[case testClassVariableOrderingRefresh]
from b import bar

def foo(x: str) -> None: pass

... [Log Snipped] ...
[out]
==
```
In fine-grained mode, type-checking passes in the first iteration, but fails in the second iteration, since the type of `IDS` is now available.
Discussion
- We could probably fix this by deferring `Something.run` since it accesses a variable without an inferred type, instead of inferring `Any` as the type. On the second type checking pass it would have a precise type for the class variable. Hopefully this is easy to fix since a slightly modified example already works correctly:

```
py
[case testInstanceVariableOrdering]
def foo(x: str) -> None: pass

class Something:
... [Log Snipped] ...
        self.IDS = [87]
[builtins fixtures/list.pyi]
```
- This works with the new semantic analyzer. I'll prepare a PR that adds test cases.
