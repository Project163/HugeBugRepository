Title

ysql: fix miscalculation of limit using offset

Description
Jira Link: [Link: DB-1956]
Postgres sends an RPC to a tserver to retrieve rows.  It sets a limit in the PgsqlReadRequestPB to indicate the max number of rows it wants in the response.  The number shouldn't be too low or else there would be overhead from many RPCs; the number shouldn't be too high or else timeouts or memory may become issues.  Therefore, the flag for this limit, `ysql_prefetch_limit`, is, by default, set to a moderate number 1024.

However, if the user specifies LIMIT or OFFSET in the query, there is a further optimization to use that number as the limit if it is smaller.  But the math was not done well because it just adds user-limit and user-offset together.

The questionable part is offset.  It sort of makes sense if both LIMIT and OFFSET are specified because we can then retrieve everything in one RPC call (provided the sum was less than the `ysql_prefetch_limit`); on the other hand, it does not make sense if only OFFSET is specified since limit is unbounded, so it should act more like a full scan.  The worst case is when OFFSET is set to 1 because limit in the PB request is set to 1, meaning one RPC call for each row (minus one because the offset omits the first row).

Here, I show that the timing gets really bad with OFFSET 1:

```
yugabyte=# create table t (i int);
CREATE TABLE
yugabyte=# insert into t values (generate_series(1, 10000));
INSERT 0 10000
yugabyte=# \timing on
... [Log Snipped] ...

Time: 13738.745 ms (00:13.739)
```

Copy-paste version:

```sql
create table t (i int);
insert into t values (generate_series(1, 10000));
\timing on
select from t;
select from t offset 1;
```

You can `set yb_debug_log_docdb_requests = on` to see the read requests in postgres logs.
