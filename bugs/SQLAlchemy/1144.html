Title

consider restoring 1.3's "begin_nested() returns root transaction" for non-future mode

Description
**Describe the bug**


If I use `Connection.begin_nested()` as a contextmanager inside an implicit transaction, I would expect that the outer implicit transaction shoudl be committed after the savepoint is released.

However, the savepoint is released as expected and then the transaction is rolled back.

This is a regression in 1.4.x - my snippet below works fine in 1.3.23.

- I still have to decide if I'm going to change this behavior or not, the bug is that this is a behavioral change that wasnt documented and is not emitting a warning, and additionally that the docs in 1.3 are wrong, the docs in 1.4 are wrong too.  and overall, while I have hundreds of different transactional combinations tested, none of them apparently ever tested this.   so lots of bugs all around but at the core of it, you should be calling connection.begin() before you call begin_nested() since that's what the usage model is based around.

in 1.3, your begin_nested() is not using a savepoint at all, it's just defaulting to doing the same thing as connection.begin(), which is part of 1.3's "automatically guess for everything" behavior, which is fine, but there's no tests otherwise this change wouldn't have passed silently.

1.4 is doing more of the "future" style "commit as you go" thing, which you don't have access towards if you didn't set the "future" flag, so that suggests if future isn't set we should probably have begin_nested() silently decide to return you a non-savepoint transaction but that seems like a big change now that we've released.   but there's no way for you to commit that transaction in 1.4 right now unless you use future mode, so...changing it might be safe.

So steps I see are:

1. for your side, you should use connection.begin() before calling begin_nested().
2. in 1.4, if future mode isn't set I might consider just making this do what 1.3 does but I'm going to have it emit a warning for sure that this pattern is 
3. if future mode is set, this is "commit as you go" and it's fine, you would call conn.commit() to commit the transaction.
