Title

Double checked locking done wrong in several places

Description
There's several places inside pdfbox where double-checked locking is done wrong. Specifically, double checked locking is the pattern of: 
  
 
 private   volatile   boolean  doneInit =  false ;

 if  (!doneInit) {
     synchronized  ( this ) {
         if  (!doneInit) {
            ...  do  init
            doneInit =  true ;
        }
    }
} 
  
 Common issues are - lack of  volatile  or the volatile set not being last. Here are the cases I found so far: 
 
	  [URL] -  volatile  set isn't the last statement in the block. 
	  [URL] -  volatile  set isn't the last statement in the block. 
	  [URL] -  initialized  isn't  volatile  
	  [URL] -  names  isn't  volatile  and the second check is missing (which might be harmless) 
	  [URL] -  fonts  isn't even locked and it's a vanilla hashmap that can be modified by other threads. 
	  [URL] - (tricky to see, but the constructor adds itself to the map) - the map isn't locked before the blind  put , so unclear which invocation "wins" (not sure if this is an issue, logic wise). 
	  [URL] -  fontProvider  isn't volatile, though is used as a double checked lock marker. (Not sure if this an issue, concurrency wise). 
 

 Fixing these one-by-one is possible and what I started doing around  [URL] - but would it make sense to make a class that does this properly? Guava has  Suppliers.memoize  which does the right thing - it's trivial to make an equivalent without the dep in pdfbox as well if necessary.
