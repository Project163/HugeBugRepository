Title

HttpContentDecompressor should change decompressed requests to chunked encoding

Description
In Netty, how do I know if an incoming HTTP request message has a body or not immediately without waiting for subsequent content messages?

If the answer to that is you can't, then there is no bug here, you can close this issue.

If the answer to that is by following the HTTP spec - ie, if the request has a `Content-Length` or `Transfer-Encoding` header, then you know it has a body, otherwise, you know it doesn't have a body - then there is a bug in `HttpContentDecompressor`, since it removes the `Content-Length` header from request, making it impossible to reliably determine whether a message has a body or not by looking at these two headers.

My opinion is that semantically the `HttpContentCompressor` is turning the request into one that uses a transfer encoding to indicate the size of the request message - ie, you now need an empty (last) content message to know the end of the message.  So if it's going to do that, in order to not break downstream handlers, it should add a chunked transfer encoding header - this means downstream handlers that use the content length and or transfer encoding headers according to the spec won't break.  Just removing the content length header violates the HTTP spec, and seeing as Netty generally requires apps to implement and enforce much of the HTTP spec themselves, Netty shouldn't confuse things by breaking it.
