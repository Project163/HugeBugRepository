Title

closing an http/2 stream a second time throws an exception

Description
h/t to @vkostyukov for finding this issue.  I'm just the messenger!

### Expected behavior

Closing an http/2 stream a second time should not have a performance impact

### Actual behavior

We found this stack trace when we ran the java async-profiler.

```
Total: 1087173410 (0.97%)  samples: 1084
  [ 0] java_lang_Throwable::fill_in_stack_trace(Handle, methodHandle, Thread*)
  [ 1] java_lang_Throwable::fill_in_stack_trace(Handle, methodHandle)
  [ 2] JVM_FillInStackTrace
  [ 3] Java_java_lang_Throwable_fillInStackTrace
... [Log Snipped] ...
  [165] com.twitter.finagle.util.BlockingTimeTrackingThreadFactory$$anon$1.run
  [166] java.lang.Thread.run
```

- Netty's internal (server-side) logic closes the stream via [Link: closeForcibly] (note usage of a VoidPromise,
- which triggers pipelie.fireChannelInactive() via [Link: Http2ChannelUnsafe.close]
- which fails the async queue in the channel transport,
- which calls channel.close again,
- which ends up in the same [Link: Http2ChannelUnsafe.close] method,
- which tries to assign a listener to a void promise (and fails)

By making sure that we don't close the stream a second time, we were able to achieve a 20% perf improvement.

### Steps to reproduce

Close an http/2 stream from Http2MultiplexCodec on the server-side after it has already been closed (note, streams are closed after the stream is finished, ie after one request and response).

### Netty version
4.1.16.Final

### JVM version (e.g. `java -version`)
jdk7

### OS version (e.g. `uname -a`)
centos7
