Title

Enum forward compatibility

Description
It seems that enums in the Rust implem are not forward compatible. As Thrift enums are mapped 1:1 to Rust enum, if a newer Thrift definition adds a case to an enum, an error will be returned when parsing the message. 

 Is this intended? Is there a workaround? 

 (We met this problem in the Rust parquet implem:  [URL]
Discussion
- > Is this intended? 

 Thrift APIs are allowing for soft-versioning, so aside from a few constraints basically anything can change in an IDL file. Especially adding more enum values is not really something unusual, so the Rust implementation should be enaboed to handle such a case of it curretly does not work..
- What should the right behavior be? If the receiver gets a new enum value that exists in the sender...what should the receiving code generate?

 After looking at the alternatives: 

 
	 the one I proposed:  [URL]
	 the flatbuffer implementation:  [URL]
 

 I decided that comments from others were correct: the flatbuffer one was cleaner, avoided the use of a magic  __Unknown  and still allowed us to use basic matching. 

 At the core, we now implement enums using the newtype idiom: 

 Old way: 
  
 pub enum Foo {
  VariantOne = 1,
  VariantTwo = 2.
   ...
}
 
  

 New way: 
  
 pub struct Foo(pub i32);
impl Foo {
  pub const VARIANT_ONE: Foo = 1;
  pub const VARIANT_TWO: Foo = 2;
  pub const ENUM_VALUES: &'static [Self] = &[Self::VARIANT_1, Self::VARIANT_2];
  ...
}
 
  

 I've also implemented  std::convert::From  for some types. 

 Please note that to conform to the Rust style guide enum variants are now in uppercase as opposed to camelcase. Whenever possible I prefer to use Rust's default conventions.
