Discussion
- I just tried changing it to:
```
final_task = celery.chain(
        tc.print_task.si(val="Starter task"),
        celery.chord([
            tc.print_task.si(val='group1, task1'),
            tc.print_task.si(val='group1, task2'),
... [Log Snipped] ...
        ], tc.print_task.si(val="FINAL task")),
    )
```
And this gave me a different structure:
```
print_task(val='Starter task')
| %(print_task([
		print_task(val='group1, task1'),
		print_task(val='group1, task2')
	], val='group1, after-task')
... [Log Snipped] ...
		], val='FINAL task')
)
```
And it works ...
So, I guess it's an issue with group tasks and how they are not converted to chords correctly in canvases.
- I've come across this issue as well. With my test case looking like this, where `t` is a dummy task that print its arg.

```
@app.task
def t(arg):
    print(arg)
```

This

```python
(group([t.si('a')]) | t.si('b') | t.si('c') | group([t.si('d')])).delay()
```

Gave output of

```
[2019-08-11 04:30:23,076: WARNING/ForkPoolWorker-4] a
[2019-08-11 04:30:23,097: WARNING/ForkPoolWorker-1] b
[2019-08-11 04:30:23,122: WARNING/ForkPoolWorker-4] c
```

My workaround was to do the chain of the end, then add the first group to the beginning, like this:

```python
(group([t.si('a')]) | (t.si('b') | t.si('c') | group([t.si('d')]))).delay()
```

Which gave the expected result of

```
[2019-08-11 04:30:55,442: WARNING/ForkPoolWorker-1] a
[2019-08-11 04:30:55,449: WARNING/ForkPoolWorker-4] b
[2019-08-11 04:30:55,459: WARNING/ForkPoolWorker-3] c
[2019-08-11 04:30:55,477: WARNING/ForkPoolWorker-1] d
```

I may take a look into this bug more over the coming week, depending on what priorities are at work.
- I've faced similar issues with 4.2 and 4.3

My workaround has been to always use a chord and never use a group.
When using a chord, and I don't want the task at the ending, I use a dummy
empty-task to make it look like a group.
