Title

CryptographyException on Adobe Distiller generated file

Description
Well... this is actually  not  a PDFBox bug, but an Adobe Distiller (7.0.x) one... 

 The following exception is thrown in StandardSecurityHandler.computeEncryptedKey: 

 org.apache.pdfbox.exceptions.CryptographyException: Error: length should be 5 when revision is two actual=16 

 The PDF file is accepted by various readers and contains the following object:

 Referenced by an encrypt tag:

 PDFBox rejects (rightly) such an object with version 1, revision 2 and a length != 5*8 

 That said, we are parsing many of those files to feed a Lucene index. Could the validation be relaxed ?
Discussion
- IMO it is possible to replace the exception with a log entry. Is it possible to provide us with a sample file?
- There seems to be a confusion between the 'version' and 'revison' encryption dictionnary entries. 

 The PDF spec says: 
(7.6.1) For version 1: Encryption of data using the RC4 or AES algorithms" in 7.6.2, "General Encryption Algorithm," with an encryption key length of 40 bits; see below. 
... 
Length integer (Optional; PDF 1.4; only if V is 2 or 3) The length of the encryption key, in bits. The value shall be a multiple of 8, in the range 40 to 128. Default value: 40. 
... 

 Note that length is optional and meaningful only if v > 1. If v is 1, the length is always of 40 bits. 

 A working patch of StandardSecurityHandler.java consists of 
1) replacing in decryptDocument() 
        int dicLength = dictionary.getLength()/8; 
by 
        int dicLength = (dictionary.getVersion() == 1) ? 5 : (dictionary.getLength()/8); 

 2) deleting the two erroneous tests in getUserPassword() and computeEncryptedKey(): 
            if( (encRevision == 2) && (length != 5) ) 
            {
              throw new CryptographyException(
                  "Error: Expected length=5 actual=" + length );
            }
 (the revision was evaluated instead of the version, and the test is now useless)
