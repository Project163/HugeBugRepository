Title

[DocDB] splitting: Improve throttling for large clusters

Description
Jira Link: [Link: DB-648]
### Description

Currently, we throttle tablet splitting using a pretty trivial gflag, counting total number of outstanding splits. This currently defaults to `outstanding_tablet_split_limit=1`, to minimize the resource overhead in the cluster. This might be ok for a minimal cluster deployment, but at scale, we should consider a more refined approach!

In particular, let's consider an example. Each tablet that is splitting will generate 2 children. Each child has to do a full compaction. This will happen on all the peers for that tablet. So for a default RF=3, that's 3 servers, each of which will be doing 2 compactions.
- When we have more than 3 servers, then we could be scheduling splits to happen for tablets on different sets of tablet servers.
- If the servers have high CPU, we might consider doing even more than 1 split, per server.
