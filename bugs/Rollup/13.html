Title

Loophole in import alias protection

Description
Normally an attempt to modify the import alias is protected, e.g. the following doesn't work:

``` js
import * as constants from './constants';
constants.foo = 'bar';
```

But careless use of mutating functions can still mess with the import alias - and even lead to it becoming out-of-sync with the backing variable:

``` js
import * as constants from './constants';
import { λ } from './constants';
Object.assign(constants, { 'λ': 20 }); // mutates `constants`
console.log('λ === λ', constants['λ'] === λ); // false
```

Both snippets are based on the dynamic namespaces example, just replacing the `main.js` code.
Discussion
- I feared this might happen.

This bug is caused by an unsafe optimisation where the `* as constants` namespace import generates

``` js
var constants = { λ: λ };
```

where

``` js
var constants = {};
Object.defineProperties(constants, {
  λ: { value: λ }
});
```

(or sinilar) is required.

We'll look into it.
- We'll need to add `enumerable: true`, [Link: per the spec]. I'm torn – should this be behind a `strict` option or similar? It's certainly a good deal less elegant than the looser version, and would fail in some older browsers. Or are there enough realistic scenarios in which this could cause problems that it ought to be the default? (i.e. maybe we have a `loose` mode instead of a `strict` mode)
- I guess we should do something about that too while we're at it.

What about:

``` js
var constants = Object.freeze({ λ: λ });
```

The object is no longer extensible, while all properties are made constant and non-configurable but enumerable as per the spec. It's arguably prettier and less verbose than using `defineProperties`.
- Ah, of course. I always forget about `Object.freeze`. Would still fail in older browsers, though maybe we should cross that bridge when we come to it
