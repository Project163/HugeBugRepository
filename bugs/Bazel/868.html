Title

Crash for --compilation_mode in transition

Description
### Description of the problem

`//command_line_option:compilation_mode` exposes a Java class when used as input in a transition, not a string. It is possible to set it to a string as output, but not to read the input.

The same problem also applies for `//command_line_option:run_under` and possibly more.

I would prefer a quick fix for `compilation_mode` whereas `run_under` is not such a big problem for me (just annoying).

Discussion
- There is a systematic issue where the transitions API will blindly return the current value of any command_line_arg requested as an input. A lot of them, e.g. compilation_mode, are stored as various Java classes, e.g. an Enum, that do do not have the proper StarlarkAPIs attached.

Raising the issue with the Front End team to see if we can determine a generally applicable solution (versus playing too much whack-a-mole with accessing native options from Starlark).
- FunctionTransitionUtil.buildSettings constructs a Dict whose values are options, which are not legal Starlark values, so it must be changed. (Also, the type of the argument passed to Starlark.call should be Map not Dict, as 'call' does not implicitly convert values as if by Starlark.fromJava. The actual value is in fact a Dict, at least for now, but we should enforce this in the Java types.)

The doc for the transition implementation function says: 

"This function always has two parammeters [sic]: settings and attr. The settings param is a dictionary whose set of keys is defined by the inputs parameter. So, for each build setting --//foo=bar, if inputs contains //foo, settings will have an entry settings['//foo']='bar'."

From this description, I would expect the dict values to be strings of text as they appeared on the command line. Whether or not this was the intent, the documentation should be made more explicit. Similarly, the documentation of the return value should also be clarified with respect to the dict element types, and the meaning of the dict-of-dict case for split transitions.
- @brandjon @juliexxia  this reminds me of older discussions of how much typing should be applied at the point of usage in transitions. Was this documented or recorded anywhere?

There was some real thought in what `settings` and the return values should support. I think we should recall that as a starting point for figuring out how to handle this. I agree that we really need to advance this from a principled root perspective vs. one-off tweaks.
