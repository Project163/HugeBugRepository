Title

Master is not configured as Slave after failure and reboot

Description
I had thought that Sentinel would (after a master crashed), wait for the old master to come back online, when it detects it, it would configure it to be the slave of the newly promoted master.

I see this on the main documentation for Sentinel:
"Moreover, after a failover, the failed over master is virtually added as a slave of the new master, this way it will be reconfigured to replicate with the new master as soon as it will be available again."

We're using version "3.2.0-1.el6.remi".   We carried out this test as a way to smoke test our installation\configuration was correct, but are left a bit puzzled as the slave is promoted to master, but when we restart the redis server on the old master, it never gets its configuration updated (to configure it as a slave).  It seems like Sentinel has stopped monitoring it.

Could I get a comment from the Redis team, is this a bug?

- On top of that note that, actually, it is not possible to reset `pending_commands` in `instanceLinkConnectionError()`, since this gets called only in the context of an error reported by hiredis. If we reset the count there, the hiredis callback, after returning, will process the pending requests that will contain `pending_commands--` in order to report back the count to 0, so we'll get negative pending commands count.

Apparently the best strategy appears to do that on reconnection instead:

```
             redisAeAttach(server.el,link->cc);
```
