Title

ChannelOutboundBuffer can cause data-corruption because of caching ByteBuffers

Description
We cache the ByteBuffers in ChannelOutboundBuffer.nioBuffers() for the Entries in the ChannelOutboundBuffer to reduce some overhead. The problem is this can lead to data-corruption if an incomplete write happens and next time we try to do a non-gathering write.

To fix this we should remove the caching which does not help a lot anyway and just make the code buggy.
Discussion
- Well, the cache won't help if the network is not congested enough.  However, if it's under load and gathering writes are often incomplete, this change will result in unnecessarily repetitive iteration.  Why don't you fix the cache?
- @trustin I thought about this... doing it in remove(...) but was worried that there may be still some chances for a race if the user for example call discardSomeReadBytes() etc.

- Not caching if nioBuffersCount() > 1 is pretty much similar to disabling the cache.  nioBufferCount is always greater than 1 if a user flushes more than one writes.

It sounds to me that the problem is: `nioBuffers()` isn't always invoked by a transport and thus there's no way to update/invalidate the cache easily.  Why don't we just add something that updates the cache on partial write so that NIO/Epoll transport calls it?  We could simply invalidate the cache there, but I think we can do a better job hopefully.
