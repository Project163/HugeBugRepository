Title

Camel bean component invokes cached instance of bean (that impl processor) in Registry

Description
Related SO question:  [URL]

 Every invocation of bean component should query Registry for actual instance. Now it is cached in  BeanProcessor#delegate  variable, even if endpoint parameter  cache=false  specified. 

 This behavior breaks java-ee compliance:  [URL]
  Every invocation of the   Context.get(Contextual, CreationalContext)   operation of the context object for the  @Dependent  scope returns a new instance of the given bean.  
 Marking this as Major, because upgrading of Camel from 2.19.x to 2.2x.x leads to unpredictable results in CDI environment. Since this is tied to CDI environment, this issue is hard to notice even in well junit covered application and can result in major issues in pre-production or production environment. 

 Full reproducible project with unit test and deployable WAR package, which passes with 2.19.x and lower. Fails with 2.20.x and higher  on Github .  

 Attachments are based on version 2.21.1
Discussion
- This issue is caused by the recent change of   CAMEL-11375  , camel always try to get the processor from bean instance and the processor is is cached no matter the "cache" option is set or not. The quick fix could be avoiding using processor usage when the cached option is set.
- Applied patch into master, camel-2.22.x and camel-2.21.x branches.
