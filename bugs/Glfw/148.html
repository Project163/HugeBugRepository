Title

glfwGetKeyName depends on current locale

Description
Steps to reproduce:

- switch the keyboard to some variant of French AZERTY
- run a program that calls `glfwGetKeyName(GLFW_KEY_2, 0)`

This should return "é". On a system with locale fr_FR.UTF-8, this should be "\xC3\xA9" but it returns "\xE9", the same character but in ISO8859-15 encoding (this is a limitation of `XkbTranslateKeySym`).

I would expect `glfwGetKeyName` to return unicode keynames across all platforms, regardless of the user's locale.

This is related to #837.

An easy solution is to use the a public domain keysym dataset compiled by Markus G. Kuhn ([Link: C code]).
Discussion
- I can send a PR if that helps, but there are a few things that need to be discussed:

- Since the function documentation does not specify any encoding, fixing this in GLFW 3.x may be considered a breaking change.
- Is the proposed solution acceptable (the linked code is in the public domain)?
- Agreed. This is a bug. Since your specific locale is UTF-8 you should get UTF-8 key names if you do `setlocale(LC_ALL, "");` at the beginning of your program, but that's a workaround and not a proper solution.


Kuhn's data and code are already available in `src/xkb_unicode.c` and for regular printable keys this approach would work well, but it doesn't handle dead keys without additional work. I will happily merge a solution based on that data if it also handles dead keys.


I consider it a bug that the documentation doesn't mention the encoding of the returned key name. That was simply an oversight on my part. The string should be UTF-8 as are all other public strings in GLFW, and this is what is returned on other platforms.
