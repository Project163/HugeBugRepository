Title

Missing OSGi import-package commons-lang3 version can make commons-text unusable in OSGi

Description
Since commons-text 1.11.0, there's commons-text codes that requires the presence of commons-lang3 3.13.0 or higher. However, in an OSGi environment, this requirement is not enforced due to shortcoming an the commons-text 1.11.0 MANIFEST.MF, which may lead to unpredictable, uncontrollable failure when trying to use commons-text 1.11.0. 

 Some more detail: 

 Since commons-text 1.11.0, the NumericEntityEscaper makes uses of the method  Range.  of  (...)  in commons-lang3 : 

   
  
 
 private  NumericEntityEscaper( final   int  below,  final   int  above,  final   boolean  between) {
     this .range = Range.of(below, above);
     this .between = between;
} 
  
   

 Method Range.of(...) was added in  commons-lang3 3.13.0  : 

   
  
 
 * @since 3.13.0
 */
 public   static  <T  extends  Comparable<?  super  T>> Range<T> of( final  T fromInclusive,  final  T toInclusive) { 
  
   

 Previously, in commons-text 1.10.0 or earlier, NumericEntityEscaper made use of the the commons-lang3 method  Range.  between  (...)   (which is now marked as deprecated since commons-lang3 3.13.0) 

   
  
 
 private  NumericEntityEscaper( final   int  below,  final   int  above,  final   boolean  between) {
     this .range = Range.between(below, above);
     this .between = between;
} 
  
   

 This is all fine in a non-OSGi environment. 

   

 However, to always resolve this correctly in an OSGi environment, some essential information is missing in the commons-text 1.11.0  MANIFEST.MF . 

 The commons-text 1.11.0 declares the following  Import-Package  in its manifest: 

   
  
 Import-Package: javax.script,javax.xml.xpath,org.apache.commons.lang3,or
 g.apache.commons.lang3.time,org.xml.sax
 
  
 Notice how this indeed imports the required package " org.apache.commons.lang3 ", but this import  is not qualified with a version number .

- Well, you mean that we would do the following in the pom? : 
  
 
<commons.lang3.version>3.14.0</commons.lang3.version>  
  
  
 
<commons.osgi. import >
org.apache.commons.lang3;version= "${commons.lang3.version}" ,
org.apache.commons.lang3.time;version= "${commons.lang3.version}" ,
*
</commons.osgi. import >
 
  
   
  
 
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>${commons.lang3.version}</version>
</dependency>  
  
   

   

 i.e. define a property for the commons-lang3 version dependency, 
and then use that property in both the dependency (like other dependencies where the version is defined in a property) and the osgi customization property (commons.osgi.import) that is picked up by the felix maven-bundle-plugin. 

 Then at least the version in OSGi Import-Package manifest header will be consistent with the version of the maven compile-time and runtime dependency. 

 ( Note: I'm  not  using the separate macro definitions which apparently are supported by the maven-bundle-plugin, separate to the maven properties. That would require breaking elsewhere into the maven-bundle-plugin <instructions> in the commons-parent pom.xml. Where we can't just break in easily. Doesn't seem worth the trouble; only complicating things without added value. ) 

 This seems to be the cleanest way to build a commons-text jar that will be guaranteed to resolve correctly at runtime in OSGi, i.e. resolve against a compatible commons-lang3 jar. 

 It's also the easiest to comprehend and maintain, I think.
